Business Value Pillars — 5 ผลลัพธ์ที่ใช้ประเมินความคุ้มค่าของ Claude Solutions: Efficiency, Transformation, Productivity, Cost และ Performance SLAs โดยทุกการตัดสินใจทางสถาปัตยกรรม (Architectural Decision) ต้องระบุได้ว่าขับเคลื่อนเสาหลักใด และใช้ Metric ใดในการพิสูจน์ผลลัพธ์

1. เสาหลัก 5 ด้าน (Five Pillars) โครงร่างหลักของ Business Case

Sponsor จ่ายเงินเพื่อซื้อผลลัพธ์ (Outcomes) ไม่ใช่ Architecture ก่อนที่โซลูชัน Claude จะผ่านการอนุมัติ ต้องระบุให้ชัดเจนว่าโซลูชันนี้จะเปลี่ยนธุรกิจอย่างไร และจะวัดผลการเปลี่ยนแปลงนั้นด้วยอะไร โดย Five Value Pillars จะช่วยวางโครงสร้างให้ Cost จะมองต้นทุนต่อผลลัพธ์ที่เสร็จสมบูรณ์แต่ละชิ้น Efficiency จะดูว่างานแต่ละหน่วยใช้ Resource ไปเท่าใด Performance SLAs กำหนด Latency และ Availability ที่ระบบต้องรักษาไว้ Productivity วัดงานที่เสร็จสมบูรณ์และใช้งานได้จริงต่อ Run หรือต่อ Person-hour และ Transformation บ่งชี้งานใหม่ๆ ที่กระบวนการเดิมไม่สามารถทำได้มาก่อน

เสาหลักแต่ละด้านต้องผูกกับตัวเลขที่ Sponsor ติดตามอยู่แล้ว เกณฑ์ความสำเร็จที่ดีต้องชัดเจน วัดผลได้ ทำได้จริง และตรงประเด็น (Specific, Measurable, Achievable, Relevant) ซึ่งงานจริงส่วนใหญ่จะถูกประเมินจากหลายเกณฑ์พร้อมกัน เช่น ฟีเจอร์ Summarisation อาจกำหนดเกณฑ์เป็น Cost ต่อยอด Summary ที่เสร็จสมบูรณ์, p95 Response Time, จำนวนสรุปประจำสัปดาห์ที่ Analyst รับไปใช้งานโดยไม่ต้อง Rework และประเภท Report ใหม่ที่ไม่เคยทำได้มาก่อน ทั้งหมดนี้คือ 4 เสาหลักพร้อม 4 Metrics ที่ตรวจวัดได้จริงหลัง Launch

Efficiency คือทรัพยากรที่ใช้ต่องานหนึ่งหน่วย วัดจากจำนวน Tokens ที่ต้องจ่ายราคาเต็ม, ส่วนที่ต้องประมวลผลซ้ำ และเวลาที่เสียไปกับการรอ Synchronous call ที่ไม่จำเป็น Efficiency มีความเกี่ยวเนื่องกับ Cost แต่ไม่ใช่สิ่งเดียวกัน ดีไซน์ระบบอาจมี Efficiency สูงแต่ยังคง Cost แพงได้หากงานนั้นต้องใช้ Frontier model และ Efficiency คือปัจจัยสำคัญที่ช่วยลด Cost ลงได้โดยไม่ต้องแลกกับ Quality

Prompt Caching คือกลไกเพิ่ม Efficiency ที่ส่งผลมากที่สุด สำหรับ Agent Loops เพราะในทุก Turn ของงานแบบ Agentic ระบบจะส่ง Context การสนทนาที่ยาวขึ้นเรื่อยๆ กลับไปเสมอ งานขนาด 40 Turns จึงส่ง Turn แรกซ้ำถึง 40 ครั้ง ทำให้ Cost พุ่งสูงขึ้นแบบ Exponential ตามจำนวน Turns บทความ [Prompt caching: stable prefix, automatic caching and breakpoints](lesson:2.5) อธิบายวิธีคิดค่าบริการ Prefix ซ้ำเดิมในอัตรา Cache-read rate ทั้งนี้ Cache-read share ถือเป็น Metric หลักที่วัดผลได้ชัดเจน จากสถิติภายในของ Anthropic บน Claude Platform ตลอด 24 ชม. ค่ามัธยฐานของ Loop อ่านข้อมูลจาก Cache สูงถึง 84% หากต่ำกว่า 80% แปลว่า Cache กำลังหลุดที่จุดใดจุดหนึ่ง และจากการคำนวณ Token counts ในชุด Benchmark หากปิด Caching งาน Long-running (SWE-bench Pro coding tasks และ Bug-triage agent) จะมี Cost พุ่งสูงขึ้น 3.1 ถึง 7.3 เท่า ข้อมูลนี้เป็นผลชี้วัดทิศทางภายใน คุณจึงควรวัดผล Loops ของระบบคุณเองด้วย

Batch Processing เป็นอีกหนึ่งเครื่องมือเพิ่ม Efficiency แต่เหมาะกับงานบางประเภทเท่านั้น Message Batches API มอบส่วนลด 50% จากราคามาตรฐาน โดยงานส่วนใหญ่จะประมวลผลเสร็จภายใน 1 ชั่วโมง (จำกัดเวลาสูงสุด 24 ชั่วโมง) จึงเหมาะกับงาน Nightly evaluations, Bulk content generation และ Back-office analysis แต่ไม่เหมาะอย่างยิ่งกับงานที่ User กำลังรอผลลัพธ์ Batch แลก Latency กับส่วนลดราคา จึงตอบโจทย์ด้าน Efficiency แต่ห้ามนำไปใช้กับงานที่ต้องรักษา Interactive SLA เด็ดขาด

Efficiency is resource consumed per unit of work: how many tokens are paid at full price, how much is recomputed, how much waits on a synchronous call that did not need to. It overlaps with cost but is not the same thing. A design can be efficient and still expensive if the task needs a frontier model, and efficiency is what lets the cost pillar improve without a quality trade-off.

Prompt caching is the largest efficiency lever for agent loops. Every turn of an agentic task resends the whole growing conversation, so a 40-turn task sends its first turn 40 times and cost rises with roughly the square of the turn count. [Prompt caching: stable prefix, automatic caching and breakpoints](lesson:2.5) explains how to bill that repeated prefix at the cache-read rate. As a pillar metric, cache-read share is concrete. In Anthropic's own measurements of agent loops on the Claude Platform, taken over a full day of real traffic, the median loop read 84% of its input from cache, and a loop below about 80% is probably breaking its cache somewhere. Anthropic also priced the token counts recorded from its benchmark runs as if caching had been off (none of those runs actually was). Without caching, the longer-running workloads (SWE-bench Pro coding tasks and a bug-triage agent) would have cost 3.1 to 7.3 times as much. Anthropic describes these results as internal and directional, so measure your own loops.

Batch processing is the second efficiency item, but it only fits some work. The Message Batches API bills all usage at 50% of standard prices, and most batches finish within an hour, with a 24-hour limit. That suits nightly evaluations, bulk content generation and back-office analysis. It does not suit anything a person is waiting on. Batch trades latency for its discount, which is why it belongs in the efficiency column and never in a plan that has to meet an interactive SLA.

The performance pillar is a set of commitments, not an aspiration. [What the service tiers and SLAs actually promise](lesson:6.3) covers what the platform guarantees. The architect's job is to turn the product's promise into targets the design must meet, written in operational terms such as "95% response time < 200ms" and an uptime percentage. Time to first token matters separately when responses stream, because users judge responsiveness by when text starts appearing.

Model class is the most direct latency lever, and it lines up with cost. The Haiku class is built for high-frequency workloads where latency and cost both matter: real-time applications, high-volume processing and cost-sensitive deployments. Within a model, effort is the main control for speed and cost. Effort is a request parameter that trades intelligence for latency and cost inside a single model: it sets how much reasoning the model does before answering, so low effort answers sooner and spends less, at some cost in capability. Fewer input and output tokens make every response faster, and streaming improves perceived responsiveness without changing total generation time.

Three tempting answers to a latency SLA fail one pillar or another. Fast mode on an Opus model raises output speed by up to 2.5x, but at premium pricing, on top of a model that already costs far more per token. It meets the SLA and fails the cost pillar for routine, high-volume questions. Turning thinking off is not a general lever: several current models run adaptive thinking that is always on, and effort is the documented control for speed. Loading a whole knowledge base into a large context window on every request inflates input tokens, which slows each response and raises its cost. For routine questions at high volume under a sub-second target, start with the fastest, lowest-priced class and tune effort.

Productivity counts completed, usable work per agent run or per person-hour. Tokens, calls and turns are inputs. An agent that uses a million tokens and produces one finished, correct pull request is more productive than one that uses a hundred thousand tokens and leaves a half-done draft someone has to rewrite. The unit is the deliverable: a resolved ticket, an accepted summary, analysis carried through to a finished document, spreadsheet or deck.

Measure it the way users experience it. Task completion rate is an implicit user-feedback signal: did the output get used without rework? Per person-hour, the question is how many finished items one analyst signs off when Claude drafts and the analyst reviews, compared with drafting by hand. Model choice affects this directly. More capable models often take fewer turns and less thinking to get a task right, so a stronger model can raise finished work per run even where its token count looks worse.

Productivity also covers the cost of complexity. Agentic systems often trade latency and cost for better task performance, so adding an agent loop is justified only when it raises completed work enough to pay for those extra turns. Where a single well-built call already produces the finished output, a multi-step agent adds spend without adding deliverables.

Transformation is value from new capability, not from doing an existing task cheaper or faster. Use one test to recognise it: would the old process, run with more people or more time, produce this outcome at all? If the same workflow runs faster with the same roles, that is productivity. If fewer hours are billed per item, that is cost. If the case rests on a turnaround commitment, that is a performance SLA. Transformation is when the workflow itself is redesigned, roles move to different work such as exception review and negotiation, or the organisation produces something it never could before, like reviewing every contract instead of a sample.

Model capability is what makes this feasible. Frontier classes are described as especially capable at long-running agent tasks and at problems AI has not reliably handled before. A task that takes a long time, involves many steps or was previously unsolved calls for a more capable model class. Economics can transform as well: agent applications that were once too expensive to run can now operate at scale, which turns a pilot nobody could afford into a standing workflow.

Transformation is the hardest pillar to argue because there is no baseline to beat. Build the evidence anyway. Assemble an evaluation set drawn from production that deliberately includes difficult tasks your current tools fail at, with success criteria the team defines in advance. A pass rate on tasks the old process could not do at all is the transformation metric, and it gives the sponsor a number in place of a vision statement.
