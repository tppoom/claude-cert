A sponsor funds outcomes, not architecture. Before a Claude solution gets approved, someone has to say what it will change for the business and how that change will be measured. The five value pillars give that argument a fixed structure. Cost asks what each finished outcome costs. Efficiency asks how much resource each unit of work uses. Performance SLAs set the latency and availability the system has to hold. Productivity counts finished, usable work per run or per person-hour. Transformation names work that was not feasible before.

Each pillar has to end in a number the sponsor already tracks. The evaluation guidance describes good success criteria as specific, measurable, achievable and relevant, and notes that most real applications are judged on several criteria at once. A summarisation feature might commit to a cost per finished summary, a p95 response time, a weekly count of summaries analysts accept without rework, and a new report type that nobody produced before. Those are four pillars with four metrics, and each one can be checked after launch.

Some things are not outcomes. Context window size, token throughput and rate limits are properties of the platform. They constrain the design but tell the sponsor nothing about value. Prompt templates written and tools integrated are implementation artefacts. Developer satisfaction scores collected after launch measure how the build felt, not what it delivered, and they arrive too late to support a funding decision. A business case built on any of these does not answer the question the sponsor asked.

The cost pillar's headline number is cost per outcome, not price per token. [Cost per solved task (not price per token)](lesson:2.1) divides total spend by the tasks that actually succeeded. In the business case, that means quoting "dollars per resolved ticket" or "dollars per accepted summary", never a rate card. A credible cost plan comes in two steps. [Free wins versus real trade-offs](lesson:4.5) separates levers that cut spend at the same quality (caching, token hygiene, a prompt audit, batch for work that can wait) from levers that buy savings with intelligence: model choice, effort, output caps and session budgets, an elapsed-time clock, and multi-model architectures. Efficiency is resource consumed per unit of work: how many tokens are paid at full price, how much is recomputed, how much waits on a synchronous call that did not need to. It overlaps with cost but is not the same thing. A design can be efficient and still expensive if the task needs a frontier model, and efficiency is what lets the cost pillar improve without a quality trade-off.

Prompt caching is the largest efficiency lever for agent loops. Every turn of an agentic task resends the whole growing conversation, so a 40-turn task sends its first turn 40 times and cost rises with roughly the square of the turn count. [Prompt caching: stable prefix, automatic caching and breakpoints](lesson:2.5) explains how to bill that repeated prefix at the cache-read rate. As a pillar metric, cache-read share is concrete. In Anthropic's own measurements of agent loops on the Claude Platform, taken over a full day of real traffic, the median loop read 84% of its input from cache, and a loop below about 80% is probably breaking its cache somewhere. Anthropic also priced the token counts recorded from its benchmark runs as if caching had been off (none of those runs actually was). Without caching, the longer-running workloads (SWE-bench Pro coding tasks and a bug-triage agent) would have cost 3.1 to 7.3 times as much. Anthropic describes these results as internal and directional, so measure your own loops.

Batch processing is the second efficiency item, but it only fits some work. The Message Batches API bills all usage at 50% of standard prices, and most batches finish within an hour, with a 24-hour limit. That suits nightly evaluations, bulk content generation and back-office analysis. It does not suit anything a person is waiting on. Batch trades latency for its discount, which is why it belongs in the efficiency column and never in a plan that has to meet an interactive SLA.

Within a model, effort is the main control for speed and cost. Effort is a request parameter that trades intelligence for latency and cost inside a single model: it sets how much reasoning the model does before answering, so low effort answers sooner and spends less, at some cost in capability. Loading a whole knowledge base into a large context window on every request inflates input tokens, which slows each response and raises its cost. For routine questions at high volume under a sub-second target, start with the fastest, lowest-priced class and tune effort.

Productivity counts completed, usable work per agent run or per person-hour. Tokens, calls and turns are inputs. An agent that uses a million tokens and produces one finished, correct pull request is more productive than one that uses a hundred thousand tokens and leaves a half-done draft someone has to rewrite. The unit is the deliverable: a resolved ticket, an accepted summary, analysis carried through to a finished document, spreadsheet or deck.

Measure it the way users experience it. Task completion rate is an implicit user-feedback signal: did the output get used without rework? Per person-hour, the question is how many finished items one analyst signs off when Claude drafts and the analyst reviews, compared with drafting by hand. Model choice affects this directly. More capable models often take fewer turns and less thinking to get a task right, so a stronger model can raise finished work per run even where its token count looks worse.

Productivity also covers the cost of complexity. Agentic systems often trade latency and cost for better task performance, so adding an agent loop is justified only when it raises completed work enough to pay for those extra turns. Where a single well-built call already produces the finished output, a multi-step agent adds spend without adding deliverables.

Transformation is value from new capability, not from doing an existing task cheaper or faster. Use one test to recognise it: would the old process, run with more people or more time, produce this outcome at all? If the same workflow runs faster with the same roles, that is productivity. If fewer hours are billed per item, that is cost. If the case rests on a turnaround commitment, that is a performance SLA. Transformation is when the workflow itself is redesigned, roles move to different work such as exception review and negotiation, or the organisation produces something it never could before, like reviewing every contract instead of a sample.

Model capability is what makes this feasible. Frontier classes are described as especially capable at long-running agent tasks and at problems AI has not reliably handled before. A task that takes a long time, involves many steps or was previously unsolved calls for a more capable model class. Economics can transform as well: agent applications that were once too expensive to run can now operate at scale, which turns a pilot nobody could afford into a standing workflow.

Transformation is the hardest pillar to argue because there is no baseline to beat. Build the evidence anyway. Assemble an evaluation set drawn from production that deliberately includes difficult tasks your current tools fail at, with success criteria the team defines in advance. A pass rate on tasks the old process could not do at all is the transformation metric, and it gives the sponsor a number in place of a vision statement.

#2 2. ค่าใช้จ่าย: กำหนดราคาผลลัพธ์ และเก็บออมเงินธนาคารฟรีก่อน

อ่านเนื้อหา ↗
  • ▸
    ตัวเลขสำคัญของเสาหลักต้นทุนคือค่าใช้จ่ายต่อผลลัพธ์ ไม่ใช่ราคาต่อโทเค็น [ค่าใช้จ่ายต่อภารกิจที่สำเร็จ (ไม่ใช่ราคาต่อโทเค็น)](lesson:2.1) คือการหารการใช้จ่ายทั้งหมดด้วยจำนวนภารกิจที่สำเร็จจริง ในกรณีธุรกิจ หมายถึงการอ้างอิง "ดอลลาร์ต่อบัตรที่แก้ไขแล้ว" หรือ "ดอลลาร์ต่อสรุปที่ยอมรับ" ไม่ใช่อัตราค่าบริการ โมเดลที่มีราคาต่อโทเค็นสูงกว่ายังสามารถชนะในการวัดนี้ได้ เพราะโมเดลที่มีความสามารถมากกว่ามักจะใช้รอบการทำงานและเวลาคิดน้อยกว่าในการทำภารกิจให้ถูกต้อง
  • ▸
    แผนการค่าใช้จ่ายที่น่าเชื่อถือประกอบด้วยสองขั้นตอน [ช่องทางที่ได้ประโยชน์ฟรีเทียบกับการแลกเปลี่ยนที่แท้จริง](lesson:4.5) แยกคันโยกที่ลดค่าใช้จ่ายในขณะที่ยังคงคุณภาพเท่าเดิม (เช่น การแคช ทำความสะอาดโทเค็น การตรวจสอบพรอมต์ การจัดกลุ่มงานที่สามารถรอได้) ออกจากคันโยกที่ทำให้เกิดการประหยัดด้วยความฉลาด
  • ▸
    การเลือกโมเดล ความพยายาม ข้อจำกัดของผลลัพธ์ และงบประมาณต่อเซสชัน นาฬิกาติดตามเวลาที่ผ่านไป และสถาปัตยกรรมหลายโมเดล จัดเก็บกลุ่มแรกและรายงาน จากนั้น หากยังมีช่องว่าง ให้เสนอคันโยกกลุ่มที่สองเป็นการแลกเปลี่ยนอย่างชัดเจนโดยระบุค่าใช้จ่ายด้านคุณภาพ แผนที่เริ่มด้วยการลดระดับโมเดลจะทิ้งเงินที่สามารถได้ฟรีไว้บนโต๊ะและขอให้ผู้สนับสนุนยอมรับความเสี่ยงด้านคุณภาพที่พวกเขาไม่จำเป็นต้องรับ

#3 3. ประสิทธิภาพ: การแคชเป็นสิ่งสำคัญหลัก

อ่านเนื้อหา ↗
  • ▸
    สําหรับ Agent Loop ทุกรอบของงาน Agent จะส่งต่อการสนทนาที่เพิ่มขึ้นทั้งหมด
  • ▸
    งาน 40 รอบจะส่งรอบแรก 40 ครั้ง และต้นทุนจะเพิ่มขึ้นโดยประมาณเท่ากับกําลังสองของจํานวนรอบ 📖 การแคชแบบพุช: คํานําหน้าเสถียร การแคชอัตโนมัติ และจุดหยุด (2.5) จะอธิบายวิธีการเรียกเก็บเงินสําหรับคํานําหน้าที่ทําซ้ํานั้นที่อัตราการอ่านแคช ในฐานะตัวชี้วัดหลัก อัตราส่วนการอ่านแคชนั้นเป็นสิ่งที่ชัดเจน ในการวัด Agent Loop ของ Anthropic บนแพลตฟอร์ม Claude โดยดูจากการรับส่งข้อมูลจริงตลอดทั้งวัน ลูปกลางจะอ่าน 84% ของอินพุตจากแคช และลูปที่ต่ํากว่าประมาณ 80% อาจจะทําลายแคชของตัวเองที่ไหนสักแห่ง Anthropic ยังกําหนดราคาสําหรับจํานวนโทเค็นที่บันทึกจากการดําเนินการเปรียบเทียบเกณฑ์มาตรฐาน ราวกับว่าการแคชถูกปิดใช้งาน (การดําเนินการเหล่านั้นไม่ได้ถูกปิดใช้งานจริงๆ) หากไม่มีการแคช ปริมาณงานที่ทํางานนานกว่า (งานเขียนโค้ด SWE-bench Pro และ Agent การคัดกรองข้อบกพร่อง) จะมีค่าใช้จ่าย 3.1 ถึง 7.3 เท่า Anthropic อธิบายผลลัพธ์เหล่านี้ว่าเป็นผลลัพธ์ภายในและเชิงทิศทาง ดังนั้นให้วัดลูปของคุณเอง
  • ▸
    ประสิทธิภาพคือการใช้ทรัพยากรต่อหน่วยงาน: จำนวนโทเค็นที่จ่ายในราคาเต็มจำนวนที่มีการคำนวณใหม่จำนวนการรอสายแบบซิงโครนัสที่ไม่จำเป็นต้องรอมันซ้อนทับกับค่าใช้จ่ายแต่ไม่เหมือนกันการออกแบบอาจมีประสิทธิภาพและยังคงมีราคาแพงหากงานต้องการแบบจำลองพรมแดนและประสิทธิภาพคือสิ่งที่ช่วยให้เสาต้นทุนดีขึ้นโดยไม่ต้องแลกเปลี่ยนคุณภาพ

#4 4. มาตรฐานการดำเนินงาน (SLA): ความหน่วงเวลาและความพร้อมในการใช้งานที่การออกแบบต้องตอบสนอง

อ่านเนื้อหา ↗
  • ▸
    คลาสโมเดลเป็นตัวลดความหน่วงที่ตรงที่สุด และสอดคล้องกับต้นทุน คลาส Haiku ถูกสร้างขึ้นสำหรับงานที่มีความถี่สูงซึ่งความหน่วงและต้นทุนมีความสำคัญทั้งคู่: แอปพลิเคชันแบบเรียลไทม์ การประมวลผลปริมาณมาก และการปรับใช้งานที่ต้องคำนึงถึงต้นทุน ภายในโมเดล ความพยายามเป็นการควบคุมหลักสำหรับความเร็วและต้นทุน ความพยายามเป็นพารามิเตอร์คำร้องที่แลกปัญญากับความหน่วงและต้นทุนภายในโมเดลเดียว: มันตั้งค่าปริมาณการให้เหตุผลของโมเดลก่อนตอบ
  • ▸
    เสาหลักด้านประสิทธิภาพคือชุดของความมุ่งมั่น ไม่ใช่ความปรารถนา [สิ่งที่ระดับการให้บริการและ SLA รับประกันจริง ๆ](lesson:6.3) ครอบคลุมสิ่งที่แพลตฟอร์มรับประกัน งานของสถาปนิกคือการเปลี่ยนคำมั่นสัญญาของผลิตภัณฑ์ให้เป็นเป้าหมายที่การออกแบบต้องบรรลุ ซึ่งเขียนในรูปแบบปฏิบัติ เช่น "เวลาตอบสนอง 95% < 200ms" และเปอร์เซ็นต์การทำงานต่อเนื่อง เวลาในการออกโทเค็นแรกมีความสำคัญแยกต่างหากเมื่อการตอบสนองถูกส่งแบบสตรีม เพราะผู้ใช้จะประเมินความตอบสนองจากเวลาที่ข้อความเริ่มปรากฏ
  • ▸
    คำตอบที่มีความพยายามต่ำจะตอบเร็วขึ้นและใช้ต้นทุนน้อยลง แต่มีค่าความสามารถที่ลดลง การใช้โทเค็นป้อนเข้าและผลลัพธ์ที่น้อยลงทำให้ทุกคำตอบเร็วขึ้น และการสตรีมช่วยเพิ่มความรู้สึกของความตอบสนองโดยไม่เปลี่ยนเวลาการสร้างทั้งหมด

#5 5. ผลผลิต: งานที่เสร็จสิ้นต่อการทำงานหนึ่งครั้ง

อ่านเนื้อหา ↗
  • ▸
    ประสิทธิภาพการทํางานนับเป็นงานที่เสร็จสิ้นและใช้งานได้ต่อการเรียกใช้ Agent หรือต่อชั่วโมงของบุคคล โทเค็น API Call และการหมุนเวียนเป็นอินพุต Agent ที่ใช้โทเค็นหนึ่งล้านรายการและสร้างคําขอ pull ที่เสร็จสมบูรณ์และถูกต้องหนึ่งรายการจะมีประสิทธิภาพการทํางานมากกว่า Agent ที่ใช้โทเค็นหนึ่งแสนรายการและทิ้งฉบับร่างที่ยังไม่เสร็จสมบูรณ์ไว้ให้คนอื่นเขียนใหม่ หน่วยคือสิ่งที่สามารถส่งมอบได้
  • ▸
    วัดจากประสบการณ์ของผู้ใช้ อัตราการเสร็จสิ้นงานเป็นสัญญาณแสดงความคิดเห็นของผู้ใช้โดยนัย: ผลลัพธ์ถูกใช้โดยไม่ต้องทํางานใหม่หรือไม่ คําถามต่อชั่วโมงของบุคคลคือ มีรายการที่เสร็จสิ้นแล้วกี่รายการที่นักวิเคราะห์คนหนึ่งทําเครื่องหมาย
  • ▸
    ในขณะที่การเรียกที่สร้างขึ้นอย่างดีเพียงครั้งเดียวสามารถสร้างเอาต์พุตที่เสร็จสมบูรณ์ได้แล้ว Agent แบบหลายขั้นตอนจะเพิ่มค่าใช้จ่ายโดยไม่ต้องเพิ่มสิ่งที่ส่งมอบได้

#6 6. การเปลี่ยนแปลง: งานที่ก่อนหน้านี้ทำได้ยาก

Batch halves the price but trades latency for that discount. It only fits work where immediate responses are not required, never an interactive SLA.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
ในการทดสอบ เมื่อสถานการณ์สมมติให้เวลาแฝงและต้นทุนต่อตั๋วที่ยั่งยืนรวมกัน คำตอบคือคลาสโมเดลที่เร็วที่สุดและมีราคาต่ำสุด ตัวเลือกที่ซื้อความเร็วด้วยพรีเมียม (Fast Mode) หรือโทเค็นพิเศษ (การโหลดแบบเต็มบริบท) จะให้บริการเสาหลักหนึ่งและทำลายอีกเสาหนึ่ง
On the Exam:: When a scenario names latency and sustainable per-ticket cost together, the answer is the fastest, lowest-priced model class. Options that buy speed with a premium (fast mode) or with extra tokens (full-context loading) serve one pillar and break the other.
✅

❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
กับดักการทดสอบ: Fast Mode ในโมเดลระดับบนสุดเป็นวิธีที่ดีที่สุดเพื่อให้เป็นไปตาม SLA ที่มีความหน่วงที่เข้มงวดสำหรับการรับส่งข้อมูลตามปกติที่มีปริมาณสูง
Fast mode on a top-tier model is the best way to meet a strict latency SLA for high-volume routine traffic.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
Fast Mode จะเพิ่มความเร็วเอาต์พุตในราคาพรีเมียมเท่านั้น ดังนั้นจึงล้มเหลวในเสาหลักของต้นทุน สำหรับงานประจำที่มีปริมาณมากภายใต้เป้าหมายเวลาแฝง คลาสโมเดลที่เร็วและราคาต่ำสุดจะตรงตามทั้งสองเสาหลัก
Fast mode raises output speed only at premium pricing, so it fails the cost pillar. For routine, high-volume work under a latency target, the fastest and lowest-priced model class meets both pillars.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
โปรเจกต์ใดก็ตามที่พนักงานทํางานเดียวกันเสร็จเร็วขึ้นถือว่าเป็นการเปลี่ยนแปลง
Any project where staff finish the same tasks faster counts as transformation.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
เวิร์กโฟลว์เดียวกันที่ผลิตงานที่เสร็จสิ้นมากขึ้นคือประสิทธิภาพการทํางาน การเปลี่ยนแปลงหมายถึงเวิร์กโฟลว์หรืองานที่มีโครงสร้างใหม่ซึ่งก่อนหน้านี้เป็นไปไม่ได้ โดยทั่วไปจะเป็นงานที่ยากหรือยังไม่ได้แก้ไขซึ่งจําเป็นต้องมีโมเดลที่มีความสามารถมากขึ้น
The same workflow producing more finished work is productivity. Transformation means a restructured workflow or work that was not feasible before, typically the hard or previously unsolved tasks that need more capable models.
