💡 แนวคิดหลักสำคัญ (Key Concept)

Business value pillars — The five outcomes a Claude solution is justified against: efficiency, transformation, productivity, cost and performance SLAs. Every architectural decision should name the pillar it moves and the metric that proves it moved.

ID: 56684

A solutions architect is scoping a new Claude-based document summarization feature for an enterprise sponsor. The sponsor asks for a business case that ties the proposed architecture to measurable outcomes before funding is approved. Which set of pillars should the architect use to structure that business case?

A Efficiency, transformation, productivity, cost, and performance SLAs, each mapped to a specific metric the sponsor already tracks
B Model context window size, token throughput, and API rate limits, since these are the only quantifiable technical properties available
C Number of prompt templates created and number of tools integrated, since implementation artifacts are the most concrete deliverables
D Developer satisfaction survey scores collected after the feature ships, since adoption sentiment predicts long-term success
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. Anthropic's guidance frames solution value in terms of the business pillars of efficiency, transformation, productivity, cost, and performance SLAs; mapping each to a metric the sponsor already tracks is what makes a business case measurable and fundable.

ตัวเลือก B: ไม่ถูกต้อง

Context window size, throughput, and rate limits are technical model specifications, not business outcomes, and a funding sponsor needs the case tied to value pillars rather than raw model capability numbers.

ตัวเลือก C: ไม่ถูกต้อง

Counting prompt templates or integrated tools measures implementation activity, not business value delivered, so it does not give the sponsor a basis for approving funding against outcomes.

ตัวเลือก D: ไม่ถูกต้อง

Post-launch developer sentiment is a useful secondary signal but is collected after shipping and does not itself constitute the pre-approval business case the sponsor is requesting.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Five pillars as the skeleton of a business case" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A sponsor funds outcomes, not architecture. Before a Claude solution gets approved, someone has to say what it will change for the business and how that change will be measured. The five value pillars give that argument a fixed structure. Cost asks what each finished outcome costs. Efficiency asks how much resource each unit of work uses. Performance SLAs set the latency and availability the system has to hold. Productivity counts finished, usable work per run or per person-hour. Transformation names work that was not feasible before.

Each pillar has to end in a number the sponsor already tracks. The evaluation guidance describes good success criteria as specific, measurable, achievable and relevant, and notes that most real applications are judged on several criteria at once. A summarisation feature might commit to a cost per finished summary, a p95 response time, a weekly count of summaries analysts accept without rework, and a new report type that nobody produced before. Those are four pillars with four metrics, and each one can be checked after launch.

Some things are not outcomes. Context window size, token throughput and rate limits are properties of the platform. They constrain the design but tell the sponsor nothing about value. Prompt templates written and tools integrated are implementation artefacts. Developer satisfaction scores collected after launch measure how the build felt, not what it delivered, and they arrive too late to support a funding decision. A business case built on any of these does not answer the question the sponsor asked.

2.Cost: price the outcome, and bank free savings first

การแยกงานให้ Subagents ทำจะช่วยยกระดับผลลัพธ์ให้ดีขึ้นใน 3 สถานการณ์หลัก เท่านั้น หากอยู่นอกเหนือจากนี้ การประสานงานมักจะสร้างต้นทุนมากกว่าประโยชน์:

1. ป้องกัน Context Pollution (ผลลัพธ์เครื่องมือมีขนาดใหญ่มาก): เมื่อการทำงานย่อยสร้างโทเค็นที่ไม่เกี่ยวข้องมากกว่า 1,000 โทเค็น (เช่น อ่านเอกสารหนาๆ หรือค้นหาเว็บ) การให้ Subagent ทำจะช่วยกักกันข้อมูลส่วนเกินไม่ให้รบกวนการตัดสินใจของ Orchestrator
2. เมื่องานสามารถทำพร้อมกันได้ (Parallelization): หากงานย่อยหลายชิ้นเป็นอิสระต่อกัน (เช่น ตรวจสอบความปลอดภัย 3 ด้านคนละมุม) การส่งให้ Subagents ทำงานขนานกันจะช่วยลด Latency รวมของระบบได้อย่างมหาศาล
3. เมื่องานต้องการเครื่องมือเฉพาะทางสูง (Tool Specialization): การใส่เครื่องมือให้เอเจนต์ตัวเดียวมากเกินไป (Capability Bloat) จะทำให้ความแม่นยำในการเลือกเครื่องมือลดลง การแยก Subagent ตามหน้าที่ช่วยให้แต่ละตัวมีเครื่องมือเฉพาะทางเพียง 3-5 ชิ้นเท่านั้น
💰 ต้นทุนโทเค็นที่ต้องแลก (Token Cost): สำหรับงานประเภทเดียวกัน ระบบ Multi-Agent มักใช้โทเค็นมากกว่าระบบเอเจนต์เดี่ยวประมาณ 3 ถึง 10 เท่า เนื่องจากต้องส่งคำสั่งระบบซ้ำให้กับ Subagent แต่ละตัว และต้องเสียโทเค็นในรอบการรวบรวมข้อมูล

The cost pillar's headline number is cost per outcome, not price per token. [Cost per solved task (not price per token)](lesson:2.1) divides total spend by the tasks that actually succeeded. In the business case, that means quoting "dollars per resolved ticket" or "dollars per accepted summary", never a rate card. A model with a higher token price can still win on this measure, because more capable models often take fewer turns and less thinking to finish a task correctly.

A credible cost plan comes in two steps. [Free wins versus real trade-offs](lesson:4.5) separates levers that cut spend at the same quality (caching, token hygiene, a prompt audit, batch for work that can wait) from levers that buy savings with intelligence: model choice, effort, output caps and session budgets, an elapsed-time clock, and multi-model architectures. Bank the first group and report it. Then, if a gap remains, propose the second group as an explicit trade-off with its quality cost stated. A plan that opens by downgrading the model leaves free money on the table and asks the sponsor to accept a quality risk they did not need to take.

Efficiency is resource consumed per unit of work: how many tokens are paid at full price, how much is recomputed, how much waits on a synchronous call that did not need to. It overlaps with cost but is not the same thing. A design can be efficient and still expensive if the task needs a frontier model, and efficiency is what lets the cost pillar improve without a quality trade-off.

Prompt caching is the largest efficiency lever for agent loops. Every turn of an agentic task resends the whole growing conversation, so a 40-turn task sends its first turn 40 times and cost rises with roughly the square of the turn count. [Prompt caching: stable prefix, automatic caching and breakpoints](lesson:2.5) explains how to bill that repeated prefix at the cache-read rate. As a pillar metric, cache-read share is concrete. In Anthropic's own measurements of agent loops on the Claude Platform, taken over a full day of real traffic, the median loop read 84% of its input from cache, and a loop below about 80% is probably breaking its cache somewhere. Anthropic also priced the token counts recorded from its benchmark runs as if caching had been off (none of those runs actually was). Without caching, the longer-running workloads (SWE-bench Pro coding tasks and a bug-triage agent) would have cost 3.1 to 7.3 times as much. Anthropic describes these results as internal and directional, so measure your own loops.

Batch processing is the second efficiency item, but it only fits some work. The Message Batches API bills all usage at 50% of standard prices, and most batches finish within an hour, with a 24-hour limit. That suits nightly evaluations, bulk content generation and back-office analysis. It does not suit anything a person is waiting on. Batch trades latency for its discount, which is why it belongs in the efficiency column and never in a plan that has to meet an interactive SLA.

The performance pillar is a set of commitments, not an aspiration. [What the service tiers and SLAs actually promise](lesson:6.3) covers what the platform guarantees. The architect's job is to turn the product's promise into targets the design must meet, written in operational terms such as "95% response time < 200ms" and an uptime percentage. Time to first token matters separately when responses stream, because users judge responsiveness by when text starts appearing.

Model class is the most direct latency lever, and it lines up with cost. The Haiku class is built for high-frequency workloads where latency and cost both matter: real-time applications, high-volume processing and cost-sensitive deployments. Within a model, effort is the main control for speed and cost. Effort is a request parameter that trades intelligence for latency and cost inside a single model: it sets how much reasoning the model does before answering, so low effort answers sooner and spends less, at some cost in capability. Fewer input and output tokens make every response faster, and streaming improves perceived responsiveness without changing total generation time.

Three tempting answers to a latency SLA fail one pillar or another. Fast mode on an Opus model raises output speed by up to 2.5x, but at premium pricing, on top of a model that already costs far more per token. It meets the SLA and fails the cost pillar for routine, high-volume questions. Loading a whole knowledge base into a large context window on every request inflates input tokens, which slows each response and raises its cost. For routine questions at high volume under a sub-second target, start with the fastest, lowest-priced class and tune effort.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Productivity: finished work per run" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Productivity counts completed, usable work per agent run or per person-hour. Tokens, calls and turns are inputs. An agent that uses a million tokens and produces one finished, correct pull request is more productive than one that uses a hundred thousand tokens and leaves a half-done draft someone has to rewrite. The unit is the deliverable: a resolved ticket, an accepted summary, analysis carried through to a finished document, spreadsheet or deck.

Measure it the way users experience it. Task completion rate is an implicit user-feedback signal: did the output get used without rework? Per person-hour, the question is how many finished items one analyst signs off when Claude drafts and the analyst reviews, compared with drafting by hand. Model choice affects this directly. More capable models often take fewer turns and less thinking to get a task right, so a stronger model can raise finished work per run even where its token count looks worse.

Productivity also covers the cost of complexity. Agentic systems often trade latency and cost for better task performance, so adding an agent loop is justified only when it raises completed work enough to pay for those extra turns. Where a single well-built call already produces the finished output, a multi-step agent adds spend without adding deliverables.

6.Transformation: work that was not feasible before

สาระสำคัญและหลักการทำงานของหัวข้อนี้: หัวข้อนี้เจาะลึก Transformation: work that was not feasible before ตามมาตรฐานและพิมพ์เขียวการสอบของ Anthropic โดยมุ่งเน้นการทำความเข้าใจสถาปัตยกรรมเชิงลึก ข้อดีข้อเสียทางเทคนิค และแนวทางการปฏิบัติจริงในโปรดักชัน

Hours per contract is evidence for productivity or cost, turnaround time is an SLA, and a satisfaction survey taken after launch measures how the build felt, not what it delivered.

A legal operations team currently has paralegals manually reading and tagging thousands of contracts per month. Leadership frames the initiative not as automating the existing manual process but as fundamentally redesigning the contract intake workflow so that paralegals shift to reviewing model-flagged exceptions and negotiating terms. Which business value pillar does this framing primarily represent?

A Transformation, because the initiative restructures the underlying workflow and staff roles, not merely speeding up the same process
B Productivity, because the same paralegals complete the same tagging tasks faster within the same unchanged workflow structure
C Cost reduction, because fewer paralegal hours are billed per contract under the newly introduced tagging process
D Performance SLA, because the initiative is measured against a fixed contract turnaround time commitment made to clients
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. Redesigning the intake workflow and shifting staff to exception review and negotiation is a structural change to how work is done, which is the hallmark of the transformation pillar rather than simply accelerating an unchanged process.

ตัวเลือก B: ไม่ถูกต้อง

Productivity gains describe doing the same tasks faster or with less effort within the existing workflow; this scenario explicitly changes the workflow and role structure, which goes beyond a productivity framing.

ตัวเลือก C: ไม่ถูกต้อง

Cost reduction focuses on lowering spend for a given output, but the scenario is framed around role and workflow redesign, not a stated cost target, so cost is not the primary pillar being described.

ตัวเลือก D: ไม่ถูกต้อง

Performance SLA pillars center on measurable service commitments such as latency or turnaround guarantees; the scenario describes a role and workflow change with no SLA metric mentioned.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Transformation is value from new capability, not from doing an existing task cheaper or faster. Use one test to recognise it: would the old process, run with more people or more time, produce this outcome at all? If the same workflow runs faster with the same roles, that is productivity. If fewer hours are billed per item, that is cost. If the case rests on a turnaround commitment, that is a performance SLA. Transformation is when the workflow itself is redesigned, roles move to different work such as exception review and negotiation, or the organisation produces something it never could before, like reviewing every contract instead of a sample.

Model capability is what makes this feasible. Frontier classes are described as especially capable at long-running agent tasks and at problems AI has not reliably handled before. A task that takes a long time, involves many steps or was previously unsolved calls for a more capable model class. Economics can transform as well: agent applications that were once too expensive to run can now operate at scale, which turns a pilot nobody could afford into a standing workflow.

Transformation is the hardest pillar to argue because there is no baseline to beat. Build the evidence anyway. Assemble an evaluation set drawn from production that deliberately includes difficult tasks your current tools fail at, with success criteria the team defines in advance. A pass rate on tasks the old process could not do at all is the transformation metric, and it gives the sponsor a number in place of a vision statement.
