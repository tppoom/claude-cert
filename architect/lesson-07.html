💡 แนวคิดหลักสำคัญ (Key Concept)

Business value pillars — The five outcomes a Claude solution is justified against: efficiency, transformation, productivity, cost and performance SLAs. Every architectural decision should name the pillar it moves and the metric that proves it moved.

1. Five pillars as the skeleton of a business case

💡 แนวคิดหลักของหัวข้อนี้ (Core Concept)

A sponsor funds outcomes, not architecture. Before a Claude solution gets approved, someone has to say what it will change for the business and how that change will be measured. The five value pillars give that argument a fixed structure. Cost asks what each finished outcome costs. Efficiency asks how much resource each unit of work uses. Performance SLAs set the latency and availability the system has to hold. Productivity counts finished, usable work per run or per person-hour. Transformation names work that was not feasible before.

📌
Some things are not outcomes. Context window size, token throughput and rate limits are properties of the platform. They constrain the design but tell the sponsor nothing about value. Prompt templates written and tools integrated are implementation artefacts. Developer satisfaction scores collected after launch measure how the build felt, not what it delivered, and they arrive too late to support a funding decision. A business case built on any of these does not answer the question the sponsor asked.

A sponsor funds outcomes, not architecture. Before a Claude solution gets approved, someone has to say what it will change for the business and how that change will be measured. 💰 ประหยัดต้นทุนโทเค็น โทเค็นที่อ่านจากแคช (Cache Read) จะมีราคาถูกกว่าอินพุตปกติถึง 90% (จ่ายเพียง 10% ของราคาอินพุตปกติ)

💡 แนวคิดหลักของหัวข้อนี้ (Core Concept)

ประสิทธิภาพคือการใช้ทรัพยากรต่อหน่วยงาน: จำนวนโทเค็นที่จ่ายในราคาเต็มจำนวนที่มีการคำนวณใหม่จำนวนการรอสายแบบซิงโครนัสที่ไม่จำเป็นต้องรอมันซ้อนทับกับค่าใช้จ่ายแต่ไม่เหมือนกันการออกแบบอาจมีประสิทธิภาพและยังคงมีราคาแพงหากงานต้องการแบบจำลองพรมแดนและประสิทธิภาพคือสิ่งที่ช่วยให้เสาต้นทุนดีขึ้นโดยไม่ต้องแลกเปลี่ยนคุณภาพ

📌
Prompt caching is the largest efficiency lever for agent loops. Every turn of an agentic task resends the whole growing conversation, so a 40-turn task sends its first turn 40 times and cost rises with roughly the square of the turn count. [Prompt caching: stable prefix, automatic caching and breakpoints](lesson:2.5) explains how to bill that repeated prefix at the cache-read rate. As a pillar metric, cache-read share is concrete. In Anthropic's own measurements of agent loops on the Claude Platform, taken over a full day of real traffic, the median loop read 84% of its input from cache, and a loop below about 80% is probably breaking its cache somewhere. Anthropic also priced the token counts recorded from its benchmark runs as if caching had been off (none of those runs actually was). Without caching, the longer-running workloads (SWE-bench Pro coding tasks and a bug-triage agent) would have cost 3.1 to 7.3 times as much. Anthropic describes these results as internal and directional, so measure your own loops.
📌
Batch processing is the second efficiency item, but it only fits some work. Efficiency is resource consumed per unit of work: how many tokens are paid at full price, how much is recomputed, how much waits on a synchronous call that did not need to. It overlaps with cost but is not the same thing. A design can be efficient and still expensive if the task needs a frontier model, and efficiency is what lets the cost pillar improve without a quality trade-off.

Prompt caching is the largest efficiency lever for agent loops. Every turn of an agentic task resends the whole growing conversation, so a 40-turn task sends its first turn 40 times and cost rises with roughly the square of the turn count. [Prompt caching: stable prefix, automatic caching and breakpoints](lesson:2.5) explains how to bill that repeated prefix at the cache-read rate. As a pillar metric, cache-read share is concrete. In Anthropic's own measurements of agent loops on the Claude Platform, taken over a full day of real traffic, the median loop read 84% of its input from cache, and a loop below about 80% is probably breaking its cache somewhere. Anthropic also priced the token counts recorded from its benchmark runs as if caching had been off (none of those runs actually was). Without caching, the longer-running workloads (SWE-bench Pro coding tasks and a bug-triage agent) would have cost 3.1 to 7.3 times as much. Anthropic describes these results as internal and directional, so measure your own loops.

Productivity counts completed, usable work per agent run or per person-hour. Tokens, calls and turns are inputs. An agent that uses a million tokens and produces one finished, correct pull request is more productive than one that uses a hundred thousand tokens and leaves a half-done draft someone has to rewrite. The unit is the deliverable: a resolved ticket, an accepted summary, analysis carried through to a finished document, spreadsheet or deck.

Measure it the way users experience it. Task completion rate is an implicit user-feedback signal: did the output get used without rework? Per person-hour, the question is how many finished items one analyst signs off when Claude drafts and the analyst reviews, compared with drafting by hand. Model choice affects this directly. More capable models often take fewer turns and less thinking to get a task right, so a stronger model can raise finished work per run even where its token count looks worse.

Productivity also covers the cost of complexity. Agentic systems often trade latency and cost for better task performance, so adding an agent loop is justified only when it raises completed work enough to pay for those extra turns. Where a single well-built call already produces the finished output, a multi-step agent adds spend without adding deliverables.

Transformation is value from new capability, not from doing an existing task cheaper or faster. Use one test to recognise it: would the old process, run with more people or more time, produce this outcome at all? If the same workflow runs faster with the same roles, that is productivity. If fewer hours are billed per item, that is cost. If the case rests on a turnaround commitment, that is a performance SLA. Transformation is when the workflow itself is redesigned, roles move to different work such as exception review and negotiation, or the organisation produces something it never could before, like reviewing every contract instead of a sample.

Model capability is what makes this feasible. Frontier classes are described as especially capable at long-running agent tasks and at problems AI has not reliably handled before. A task that takes a long time, involves many steps or was previously unsolved calls for a more capable model class. Economics can transform as well: agent applications that were once too expensive to run can now operate at scale, which turns a pilot nobody could afford into a standing workflow.

Transformation is the hardest pillar to argue because there is no baseline to beat. Build the evidence anyway. Assemble an evaluation set drawn from production that deliberately includes difficult tasks your current tools fail at, with success criteria the team defines in advance. A pass rate on tasks the old process could not do at all is the transformation metric, and it gives the sponsor a number in place of a vision statement.
