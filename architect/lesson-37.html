1. Three policies and their defaults

ใน Managed Agents นั้น Permission Policy จะเป็นตัวกำหนดว่า Server-executed Tools จะรันโดยอัตโนมัติ, หยุดรอการอนุมัติจากผู้ใช้ (Human Confirmation), หรือให้ Server ประเมินความปลอดภัยทีละ Call โดย Policy จะครอบคลุมเฉพาะ Pre-built Agent Toolset และ MCP Toolsets เท่านั้น ไม่รวม Custom Tools เนื่องจาก Application ของคุณเป็นผู้ execute เอง ดังนั้นหากต้องการระบบ Approval สำหรับ Custom Tools คุณจะต้อง implement เพิ่มเองทั้งหมด

Policy
Behaviour
always_allow
The tool executes automatically with no confirmation
Tool รันโดยอัตโนมัติทันที ไม่ต้องรอการยืนยัน
always_ask
The session pauses and waits for your approval before executing
Session จะ Pause และรอการอนุมัติก่อนที่ Tool จะเริ่มรัน
auto
The server evaluates each call and runs it, denies it, or pauses for your approval
Server จะประเมินทุกๆ Call แบบไดนามิก โดยจะเลือกระหว่าง รันทันที, ปฏิเสธ (Deny), หรือ Pause รอการอนุมัติ

✓ ตอบถูกแล้ว Predict

You connect a new MCP server and add both the agent toolset and the MCP toolset without setting any permission_policy. Which tools run without asking?

คำแปลโจทย์:
คุณเชื่อมต่อเซิร์ฟเวอร์ MCP ใหม่ และเพิ่มทั้งชุดเครื่องมือ Agent และชุดเครื่องมือ MCP โดยไม่ต้องตั้งค่า Permission_policy ใดๆ เครื่องมือใดทำงานโดยไม่ต้องถาม?
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Official Explanation (คำอธิบายเฉลย):

Each toolset kind has its own default. The agent toolset defaults to always_allow and MCP toolsets default to always_ask, so new MCP tools never run unreviewed.

คำแปลไทย:
  • ▸
    แต่ละชุดเครื่องมือมีค่าดีฟอลต์ของตัวเอง ชุดเครื่องมือพร็อกซีเป็นค่าเริ่มต้น always _ allow และชุดเครื่องมือ MCP เป็นค่าเริ่มต้น always _ ask
  • ▸
    ดังนั้นเครื่องมือ MCP ใหม่จะไม่ทํางานโดยไม่มีการตรวจสอบ
““the agent toolset defaults to always_allow, and MCP toolsets default to always_ask.””
คำแปล: “ชุดเครื่องมือ Agent มีค่าเริ่มต้นเป็น Always_allow และชุดเครื่องมือ MCP มีค่าเริ่มต้นเป็น Always_ask”
🔗 Source: https://platform.claude.com/docs/en/managed-agents/permission-policies
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage

ค่า Default ของ MCP ถูกออกแบบมาอย่างตั้งใจ เพราะผู้ดูแล MCP Server สามารถเพิ่ม Tool ใหม่เมื่อไหร่ก็ได้ การตั้งค่า Default เป็น always_ask จึงช่วยป้องกันไม่ให้ Tool ที่เพิ่งเพิ่มมาใหม่รันได้ทันทีโดยไม่ผ่านการอนุมัติ หากต้องการ Trust ทั้ง Server ให้กำหนด default_config.permission_policy ใน mcp_toolset ทั้งนี้ ไม่มี Toolset ใดที่ใช้ Policy auto เป็นค่า Default

หากต้องการจำกัดสิทธิ์เฉพาะ Tool ที่มีความเสี่ยง ให้เปลี่ยน Policy เฉพาะ Tool นั้นโดยไม่ต้องแก้ทั้ง Toolset โดย configs array สามารถใช้ Override ค่า Default ของ Toolset ได้ ตัวอย่างเช่น Agent สามารถรัน Tool อื่นๆ ได้อย่างอิสระ แต่กำหนดให้คำสั่ง Bash ทุกครั้งต้องรอคนอนุมัติก่อน

Allow the agent toolset by default, but require confirmation for bash yaml
อนุญาตชุดเครื่องมือ Agent ตามค่าเริ่มต้น แต่ต้องมีการยืนยัน bash yaml
---
name: Coding Assistant
model: claude-opus-5-5
tools:
  - type: agent_toolset_20260401
    default_config:
      permission_policy:
        type: always_allow
    configs:
      - name: bash
        permission_policy:
          type: always_ask
---

การแก้ Policy จะไม่มีผลย้อนหลังกับ Session ที่กำลังรันอยู่ (Active Sessions) โดยแต่ละ Session จะคง Config ของ Toolset ตามที่ถูกสร้างไว้ตอนแรก ดังนั้นการเพิ่มความเข้มงวดของ Policy จะมีผลเฉพาะกับ Session ที่สร้างขึ้นใหม่หลังจากการอัปเดตเท่านั้น นอกจากนี้ Policy ยังควบคุมเฉพาะจังหวะการรันของ Tool ที่ถูกเปิดใช้งาน (Enabled) เท่านั้น หากต้องการนำ Tool ออกจาก Agent โดยสมบูรณ์ ต้องใช้วิธี Disable Tool

2. The auto policy: server-side judgement per call

Under auto, the server looks at the tool, the call's input and the session's content so far, so two calls to the same tool can get different answers. Each call ends one of three ways. It runs if the server judges it safe. It is denied if the server judges it high-risk: the agent gets an error tool result and the session continues. It pauses for your approval, just as under always_ask, if the server cannot decide.

A high-risk denial is final. Your client cannot override it, so auto lets the server refuse a call before any person gets to approve it. Every agent.tool_use and agent.mcp_tool_use event records the outcome in evaluated_permission. Under auto, the event's evaluation object also records the server's determination and, for ask or deny, a reason_code. Use that code for branching and for audit records, not as a message to show end users.

The server decides partly by judging intent, and it takes intent from only one place. What you post in user.message events counts as your intent and can lead the server to allow a call it would otherwise deny. The server assesses tool results, fetched webpages, MCP responses and messages between threads, but it does not take instructions from them. That makes an injected instruction inside a webpage less dangerous. It also creates a gap: if your application relays an untrusted end user's text in user.message events, the server reads it as your intent. Put always_ask on any tool you would not let that end user run without review.

3. การตอบรับ Confirmation Request

Tool call จะถูกประเมินผลเป็น `ask` ใน 2 กรณี: เมื่อตั้งค่าเป็น `always_ask` หรือเมื่อใช้ `auto` mode แล้ว Server ไม่สามารถตัดสินใจได้เอง ไม่ว่าจะกรณีใด Session จะหยุดชั่วคราวและรอให้ Client ตอบกลับ โดยมี Flow การทำงาน 4 ขั้นตอน:

  1. 1
    Session ส่ง event `agent.tool_use` หรือ `agent.mcp_tool_use` ออกมาพร้อม `evaluated_permission` ที่มีค่าเป็น `ask`
    The session emits an agent.tool_use or agent.mcp_tool_use event with evaluated_permission set to ask.
  2. 2
    Session ส่ง event `session.status_idle` โดยระบุ `stop_reason.type` เป็น `requires_action` และแนบ ID ของ Event ที่ติดบล็อกอยู่ใน `stop_reason.event_ids`
    The session emits session.status_idle with stop_reason.type set to requires_action. The IDs of the blocking events are in stop_reason.event_ids.
  3. 3
    Client ส่ง `user.tool_confirmation` สำหรับแต่ละ Event ที่ติดบล็อก โดยระบุ Event ID ลงใน `tool_use_id` และกำหนด `result` เป็น `allow` หรือ `deny` (หากไม่อนุญาต สามารถใส่ `deny_message` เพื่ออธิบายเหตุผลได้ ทั้งนี้สามารถส่ง Confirmation หลายรายการพร้อมกันในหนึ่ง Request ได้)
    Your client sends one user.tool_confirmation per blocking event, with the event ID in tool_use_id and result set to allow or deny. A deny_message explains the refusal. Several confirmations can go in one events request.
  4. 4
    เมื่อทุก Blocking Event ได้รับการ Resolve ครบถ้วน Session จะกลับมาทำงานต่อ Tool ที่ได้ `allow` จะถูก Execute ส่วน Tool ที่ได้ `deny` จะคืนสถานะ Rejection พร้อม `deny_message` เพื่อให้ Agent รับรู้เหตุผล
    Once every blocking event is resolved, the session runs again. Allowed tools execute. Denied tools return a rejection that includes your deny_message, so the agent knows why it was refused.

คำถามหลอก / สิ่งที่มักเข้าใจผิด? (ทำไมถึงผิด): ไม่จริง: เราสามารถส่ง Confirmation เพื่อ override การตัดสินใจปฏิเสธของ auto policy ได้ — ในความเป็นจริง Confirmation ใช้ได้กับ Call ที่มีสถานะรอ (`ask`) เท่านั้น หากส่ง `user.tool_confirmation` ให้ Event ที่ไม่ได้มี `evaluated_permission` เป็น `ask` (รวมถึง Call ที่ auto policy ตัดสินใจ `deny`) API จะ Reject ด้วย 400 Bad Request ทันที เพื่อป้องกันการ Override การปฏิเสธของระบบ

🔗 เอกสารอ้างอิงทางการจาก Anthropic
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A call evaluates to ask in two cases: under always_ask, or under auto when the server cannot decide. Either way, the session stops and your client has to answer it. The round trip has four steps:

1. The session emits an agent.tool_use or agent.mcp_tool_use event with evaluated_permission set to ask. 2. The session emits session.status_idle with stop_reason.type set to requires_action. The IDs of the blocking events are in stop_reason.event_ids. 3. Your client sends one user.tool_confirmation per blocking event, with the event ID in tool_use_id and result set to allow or deny. A deny_message explains the refusal. Several confirmations can go in one events request. 4. Once every blocking event is resolved, the session runs again. Allowed tools execute. Denied tools return a rejection that includes your deny_message, so the agent knows why it was refused.

A paused session waits indefinitely, so a confirmation nobody answers stalls the work silently. Subscribe to webhooks or watch the event stream so a person learns when a session needs them. For interactive use, ant beta:sessions connect shows the waiting call and sends the confirmation when you allow or deny it.

Confirmations work only on calls that are waiting. Sending user.tool_confirmation for an event whose evaluated_permission is not ask returns a 400 error. That includes calls the auto policy denied, which is how the API enforces that those denials cannot be overridden.
