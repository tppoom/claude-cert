1. Three policies and their defaults

สาระสำคัญและหลักการทำงานของหัวข้อนี้: หัวข้อนี้เจาะลึก Three policies and their defaults ตามมาตรฐานและพิมพ์เขียวการสอบของ Anthropic โดยมุ่งเน้นการทำความเข้าใจสถาปัตยกรรมเชิงลึก ข้อดีข้อเสียทางเทคนิค และแนวทางการปฏิบัติจริงในโปรดักชัน
PolicyBehaviour
always_allowThe tool executes automatically with no confirmation
always_askThe session pauses and waits for your approval before executing
autoThe server evaluates each call and runs it, denies it, or pauses for your approval
⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

คาดการณ์ก่อน คุณเชื่อมต่อเซิร์ฟเวอร์ MCP ใหม่ และเพิ่มทั้งชุดเครื่องมือตัวแทนและชุดเครื่องมือ MCP โดยไม่ต้องตั้งค่า Permission_policy ใดๆ เครื่องมือใดทำงานโดยไม่ต้องถาม ทั้งสองทำงานอย่างอิสระจนกว่าคุณจะเพิ่ม Always_ask ชุดเครื่องมือเอเจนต์ทำงานได้อย่างอิสระ เครื่องมือ MCP รอการอนุมัติ: ค่าเริ่มต้นของเครื่องมือที่เรียกใช้งานเซิร์ฟเวอร์ทุกรายการเป็น Always_ask ชุดเครื่องมือแต่ละประเภทจะมีค่าเริ่มต้นของตัวเอง ชุดเครื่องมือตัวแทนมีค่าเริ่มต้นเป็น Always_allow และชุดเครื่องมือ MCP มีค่าเริ่มต้นเป็น Always_ask ดังนั้นเครื่องมือ MCP ใหม่จะไม่ทำงานโดยไม่ได้รับการตรวจสอบ “ชุดเครื่องมือตัวแทนมีค่าเริ่มต้นเป็น Always_allow และชุดเครื่องมือ MCP มีค่าเริ่มต้นเป็น Always_ask” ที่มา: platform.claude.com

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Exam Trap: Setting always_ask on a toolset also makes your application's custom tools wait for confirmation. (ทำไมถึงผิด): Permission policies govern only server-executed tools. Your application executes custom tools, so it has to add any approval step for them itself.

This agent should let the whole agent toolset run on its own but make every bash command wait for a person to approve it. Which policy completes the bash override?

คำตอบที่ถูกต้อง: ตัวเลือก A
💡 คำอธิบายเฉลยภาษาไทย (Thai Explanation):

รายการในอาร์เรย์การกำหนดค่าจะแทนที่ค่าเริ่มต้นของชุดเครื่องมือสำหรับเครื่องมือเดียว ภายใต้ Always_ask เซสชันจะหยุดชั่วคราวก่อนการโทร bash ทุกครั้งจนกว่าจะมีคนอนุมัติ ภายใต้อัตโนมัติ เซิร์ฟเวอร์สามารถเรียกใช้หรือปฏิเสธการโทรโดยไม่ต้องถามใครเลย และ Always_allow จะทำซ้ำค่าเริ่มต้น

EN: An entry in the configs array overrides the toolset default for one tool. Under always_ask the session pauses before every bash call until someone approves it. Under auto the server could run or deny a call without asking anyone, and always_allow would just repeat the default.

A Managed Agent uses the agent toolset with default_config set to always_ask. It also has a custom refund_payment tool that your application executes. What happens when Claude calls refund_payment?

คำตอบที่ถูกต้อง: ตัวเลือก C
💡 คำอธิบายเฉลยภาษาไทย (Thai Explanation):

นโยบายการอนุญาตครอบคลุมเฉพาะเครื่องมือที่ทำงานบนเซิร์ฟเวอร์ ซึ่งหมายถึงชุดเครื่องมือตัวแทนและชุดเครื่องมือ MCP แอปพลิเคชันของคุณรันเครื่องมือแบบกำหนดเอง ดังนั้นการตั้งค่า Always_ask จึงไม่มีผลกับเครื่องมือเหล่านั้น ต้องมีการสร้างเช็คของมนุษย์สำหรับการคืนเงิน_การชำระเงินไว้ในใบสมัครของคุณ

EN: Permission policies cover only server-executed tools, meaning the agent toolset and MCP toolsets. Your application executes custom tools, so the always_ask setting has no effect on them. Any human check for refund_payment has to be built into your application.
“Custom tools are executed by your application and controlled by you, so they are not governed by permission policies.”

In Managed Agents, a permission policy decides whether a server-executed tool runs on its own, waits for a person or is judged by the server one call at a time. Policies cover the pre-built agent toolset and MCP toolsets. Custom tools are not covered, because your application executes them, so any approval step for a custom tool is yours to build.

The MCP default is deliberate. Whoever runs an MCP server can add tools to it at any time, and the always_ask default means a newly added tool cannot run in your application until someone approves it. To trust a known server, set default_config.permission_policy on its mcp_toolset entry. No toolset uses auto by default.

To protect one dangerous tool, change that tool's policy and leave the rest of the toolset alone. The configs array overrides the toolset default per tool. In this agent the whole toolset runs freely, but every bash command waits for a person:

Policy changes do not reach sessions that are already running. Running sessions keep the toolset configuration they were created with, so tightening a policy protects only sessions created after the update. A policy also controls only when an enabled tool runs. To remove a tool from the agent completely, disable it.

Under auto, the server looks at the tool, the call's input and the session's content so far, so two calls to the same tool can get different answers. Each call ends one of three ways. It runs if the server judges it safe. It is denied if the server judges it high-risk: the agent gets an error tool result and the session continues. It pauses for your approval, just as under always_ask, if the server cannot decide.

A high-risk denial is final. Your client cannot override it, so auto lets the server refuse a call before any person gets to approve it. Every agent.tool_use and agent.mcp_tool_use event records the outcome in evaluated_permission. Under auto, the event's evaluation object also records the server's determination and, for ask or deny, a reason_code. Use that code for branching and for audit records, not as a message to show end users.

The server decides partly by judging intent, and it takes intent from only one place. What you post in user.message events counts as your intent and can lead the server to allow a call it would otherwise deny. The server assesses tool results, fetched webpages, MCP responses and messages between threads, but it does not take instructions from them. That makes an injected instruction inside a webpage less dangerous. It also creates a gap: if your application relays an untrusted end user's text in user.message events, the server reads it as your intent. Put always_ask on any tool you would not let that end user run without review.

💡 คำอธิบายเฉลยภาษาไทย (Thai Explanation):

The session starts running again only after every blocking event has an answer, and a refused call then reaches the agent as a rejection that carries the deny_message.
“The session pauses with a session.status_idle event whose stop_reason.type is requires_action. The blocking event IDs are in the stop_reason.event_ids array.”

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A call evaluates to ask in two cases: under always_ask, or under auto when the server cannot decide. Either way, the session stops and your client has to answer it. The round trip has four steps:

1. The session emits an agent.tool_use or agent.mcp_tool_use event with evaluated_permission set to ask. 2. The session emits session.status_idle with stop_reason.type set to requires_action. The IDs of the blocking events are in stop_reason.event_ids. 3. Your client sends one user.tool_confirmation per blocking event, with the event ID in tool_use_id and result set to allow or deny. A deny_message explains the refusal. Several confirmations can go in one events request. 4. Once every blocking event is resolved, the session runs again. Allowed tools execute. Denied tools return a rejection that includes your deny_message, so the agent knows why it was refused.

A paused session waits indefinitely, so a confirmation nobody answers stalls the work silently. Subscribe to webhooks or watch the event stream so a person learns when a session needs them. For interactive use, ant beta:sessions connect shows the waiting call and sends the confirmation when you allow or deny it.

Confirmations work only on calls that are waiting. Sending user.tool_confirmation for an event whose evaluated_permission is not ask returns a 400 error. That includes calls the auto policy denied, which is how the API enforces that those denials cannot be overridden.
