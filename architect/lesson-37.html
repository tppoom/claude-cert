1. Three policies and their defaults

💡 แนวคิดหลักของหัวข้อนี้ (Core Concept)

ใน เอเจนต์ที่มี การจัดการ นโยบายสิทธิ์อนุญาตจะกําหนดว่าเครื่องมือที่เรียกใช้โดยเซิร์ฟเวอร์จะทํางานด้วยตัวเอง รอคนใช้ หรือถูกตัดสินโดยเซิร์ฟเวอร์ครั้งละหนึ่ง

การเรียกใช้ นโยบายครอบคลุมชุดเครื่องมือ

เอเจนต์ที่สร้างไว้ล่วงหน้าและชุดเครื่องมือ MCP เครื่องมือแบบกําหนดเองไม่ครอบคลุม

เนื่องจากแอปพลิเคชันของคุณเรียกใช้เครื่องมือเหล่านั้น ดังนั้นขั้นตอนการอนุมัติสําหรับเครื่องมือแบบกําหนดเองทั้งหมดเป็นของคุณใน

💡 คำถามท้าทายความคิดก่อนอ่านเนื้อหา (Predict First Challenge)
✓ ตอบถูกแล้ว Predict

You connect a new MCP server and add both the agent toolset and the MCP toolset without setting any permission_policy. Which tools run without asking?

คำแปลโจทย์: คุณเชื่อมต่อเซิร์ฟเวอร์ MCP ใหม่ และเพิ่มทั้งชุดเครื่องมือตัวแทนและชุดเครื่องมือ MCP โดยไม่ต้องตั้งค่า Permission_policy ใดๆ เครื่องมือใดทำงานโดยไม่ต้องถาม?
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Official Explanation (คำอธิบายเฉลย):

Each toolset kind has its own default. The agent toolset defaults to always_allow and MCP toolsets default to always_ask, so new MCP tools never run unreviewed.

คำแปลไทย: แต่ละชุดเครื่องมือมีค่าดีฟอลต์ของตัวเอง ชุดเครื่องมือพร็อกซีเป็นค่าเริ่มต้น always _ allow และชุดเครื่องมือ MCP เป็นค่าเริ่มต้น always _ ask ดังนั้นเครื่องมือ MCP ใหม่จะไม่ทํางานโดยไม่มีการตรวจสอบ
““the agent toolset defaults to always_allow, and MCP toolsets default to always_ask.””
คำแปล: “ชุดเครื่องมือตัวแทนมีค่าเริ่มต้นเป็น Always_allow และชุดเครื่องมือ MCP มีค่าเริ่มต้นเป็น Always_ask”
🔗 Source: https://platform.claude.com/docs/en/managed-agents/permission-policies
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📌
The MCP default is deliberate. Whoever runs an MCP server can add tools to it at any time, and the always_ask default means a newly added tool cannot run in your application until someone approves it. To trust a known server, set default_config.permission_policy on its mcp_toolset entry. No toolset uses auto by default.
📌 หากต้องการปกป้องเครื่องมือที่เป็นอันตรายให้เปลี่ยนนโยบายของเครื่องมือนั้นและปล่อยให้เครื่องมือ
  • ▸
    ส่วนที่เหลืออยู่ตามลำพังอาร์เรย์ การกำหนดค่าจะแทนที่ค่าเริ่มต้นของชุดเครื่องมือต่อเครื่องมือใน
  • ▸
    เอเจนต์: นี้ชุดเครื่องมือทั้งหมดทำงานได้อย่างอิสระแต่คำสั่งทุบตีทุกคำสั่งจะรอบุคคล:
Allow the agent toolset by default, but require confirmation for bash yaml
อนุญาตชุดเครื่องมือตัวแทนตามค่าเริ่มต้น แต่ต้องมีการยืนยัน bash yaml
---
name: Coding Assistant
model: claude-opus-5-5
tools:
  - type: agent_toolset_20260401
    default_config:
      permission_policy:
        type: always_allow
    configs:
      - name: bash
        permission_policy:
          type: always_ask
---
📌
Policy changes do not reach sessions that are already running. Running sessions keep the toolset configuration they were created with, so tightening a policy protects only sessions created after the update. A policy also controls only when an enabled tool runs. To remove a tool from the agent completely, disable it.
⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Exam Trap: Setting always_ask on a toolset also makes your application's custom tools wait for confirmation. (ทำไมถึงผิด): Permission policies govern only server-executed tools. Your application executes custom tools, so it has to add any approval step for them itself.

คำอธิบายเจาะลึก: หลุมพรางการสอบ: การตั้งค่า always_ask บนชุดเครื่องมือยังทําให้เครื่องมือแบบกําหนดเองของแอปพลิเคชันของคุณต้องรอการยืนยัน (ทําไมจึงผิดพลาด): นโยบายสิทธิ์อนุญาตควบคุมเฉพาะเครื่องมือที่ทํางานบนเซิร์ฟเวอร์เท่านั้น แอปพลิเคชันของคุณเรียกใช้เครื่องมือแบบกําหนดเอง ดังนั้นจึงต้องเพิ่มขั้นตอนการอนุมัติสําหรับตัวมันเอง

In Managed Agents, a permission policy decides whether a server-executed tool runs on its own, waits for a person or is judged by the server one call at a time. Policies cover the pre-built agent toolset and MCP toolsets. Custom tools are not covered, because your application executes them, so any approval step for a custom tool is yours to build.

The MCP default is deliberate. Whoever runs an MCP server can add tools to it at any time, and the always_ask default means a newly added tool cannot run in your application until someone approves it. To trust a known server, set default_config.permission_policy on its mcp_toolset entry. No toolset uses auto by default.

To protect one dangerous tool, change that tool's policy and leave the rest of the toolset alone. The configs array overrides the toolset default per tool. In this agent the whole toolset runs freely, but every bash command waits for a person:

Policy changes do not reach sessions that are already running. Running sessions keep the toolset configuration they were created with, so tightening a policy protects only sessions created after the update. A policy also controls only when an enabled tool runs. To remove a tool from the agent completely, disable it.

2. The auto policy: server-side judgement per call

💡 แนวคิดหลักของหัวข้อนี้ (Core Concept)

Under auto, the server looks at the tool, the call's input and the session's content so far, so two calls to the same tool can get different answers. Each call ends one of three ways. It runs if the server judges it safe. It is denied if the server judges it high-risk: the agent gets an error tool result and the session continues. It pauses for your approval, just as under always_ask, if the server cannot decide.

📌
A high-risk denial is final. Your client cannot override it, so auto lets the server refuse a call before any person gets to approve it. Every agent.tool_use and agent.mcp_tool_use event records the outcome in evaluated_permission. Under auto, the event's evaluation object also records the server's determination and, for ask or deny, a reason_code. Use that code for branching and for audit records, not as a message to show end users.

3. Responding to a confirmation request

💡 แนวคิดหลักของหัวข้อนี้ (Core Concept)

การเรียกจะประเมินเพื่อถามในสองกรณี: ภายใต้ always_ask หรือภายใต้ auto เมื่อเซิร์ฟเวอร์ไม่สามารถตัดสินใจได้ ไม่ว่าจะเป็นกรณีใด เซสชันจะหยุดลงและไคลเอนต์ของคุณต้องตอบสนอง การเดินทางไปกลับมีสี่ขั้นตอน:

  1. 1
    เซสชันจะออกเหตุการณ์ agent.tool_use หรือ agent.mcp_tool_use โดยตั้งค่า evaluated_permission ให้ร้องขอ
    The session emits an agent.tool_use or agent.mcp_tool_use event with evaluated_permission set to ask.
  2. 2
    เซสชันจะออกเหตุการณ์ session.status_idle โดยตั้งค่า stop_reason.type เป็น requires_action ID ของเหตุการณ์การบล็อกอยู่ใน stop_reason.event_ids
    The session emits session.status_idle with stop_reason.type set to requires_action. The IDs of the blocking events are in stop_reason.event_ids.
  3. 3
    ไคลเอ็นต์ของคุณส่ง user.tool_confirmation หนึ่งรายการต่อเหตุการณ์การบล็อก โดยตั้งค่า ID ของเหตุการณ์เป็น tool_use_id และผลลัพธ์เป็นอนุญาตหรือปฏิเสธ ข้อความปฏิเสธจะอธิบายการปฏิเสธ สามารถมีการยืนยันหลายครั้งในคําขอเหตุการณ์เดียว
    Your client sends one user.tool_confirmation per blocking event, with the event ID in tool_use_id and result set to allow or deny. A deny_message explains the refusal. Several confirmations can go in one events request.
  4. 4
    เมื่อเหตุการณ์การบล็อกทั้งหมดได้รับการแก้ไข เซสชันจะทํางานอีกครั้ง เครื่องมือที่ได้รับอนุญาตจะดําเนินการ เครื่องมือที่ถูกปฏิเสธจะส่งคืนการปฏิเสธที่มีข้อความปฏิเสธของคุณ ดังนั้นเอเจนต์จะทราบว่าทําไมจึงถูกปฏิเสธ
    Once every blocking event is resolved, the session runs again. Allowed tools execute. Denied tools return a rejection that includes your deny_message, so the agent knows why it was refused.

Your client sends a user.tool_confirmation with that event ID in tool_use_id and result set to allow or deny, plus a deny_message if it refuses ไคลเอนต์ของคุณส่ง user.tool_confirmation พร้อมด้วย ID เหตุการณ์นั้นใน tool_use_id และตั้งค่าผลลัพธ์เป็นอนุญาตหรือปฏิเสธ รวมถึง deny_message หากปฏิเสธ
4
Once every blocking event is resolved, the session runs again: an allowed call executes, and a denied call returns a rejection that includes the deny_message เมื่อทุกเหตุการณ์การบล็อกได้รับการแก้ไข เซสชันจะทำงานอีกครั้ง: การโทรที่ได้รับอนุญาตจะดำเนินการ และการโทรที่ถูกปฏิเสธจะส่งคืนการปฏิเสธซึ่งรวมถึง deny_message
💡 Reasoning (เหตุผลเบื้องหลังลำดับขั้น):

The client can't answer until the session pauses with requires_action and lists the blocking event IDs, because each confirmation has to name one of those IDs. The session starts running again only after every blocking event has an answer, and a refused call then reaches the agent as a rejection that carries the deny_message.

คำแปลไทย: ลูกค้าไม่สามารถตอบได้จนกว่าเซสชันจะหยุดชั่วคราวด้วย need_action และแสดงรายการรหัสเหตุการณ์การบล็อก เนื่องจากการยืนยันแต่ละครั้งจะต้องตั้งชื่อหนึ่งในรหัสเหล่านั้น เซสชันจะเริ่มทำงานอีกครั้งหลังจากทุกเหตุการณ์การบล็อกได้รับคำตอบเท่านั้น และการโทรที่ถูกปฏิเสธจะไปถึงตัวแทนเป็นการปฏิเสธที่มี deny_message
“The session pauses with a session.status_idle event whose stop_reason.type is requires_action. The blocking event IDs are in the stop_reason.event_ids array.”
คำแปล: เซสชันหยุดชั่วคราวพร้อมกับเหตุการณ์ session.status_idle ซึ่ง stop_reason.type ต้องใช้_การกระทำ รหัสเหตุการณ์การบล็อกอยู่ในอาร์เรย์ stop_reason.event_ids

🔗 เอกสารอ้างอิงทางการจาก Anthropic
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A call evaluates to ask in two cases: under always_ask, or under auto when the server cannot decide. Either way, the session stops and your client has to answer it. The round trip has four steps:

1. The session emits an agent.tool_use or agent.mcp_tool_use event with evaluated_permission set to ask. 2. The session emits session.status_idle with stop_reason.type set to requires_action. The IDs of the blocking events are in stop_reason.event_ids. 3. Your client sends one user.tool_confirmation per blocking event, with the event ID in tool_use_id and result set to allow or deny. A deny_message explains the refusal. Several confirmations can go in one events request. 4. Once every blocking event is resolved, the session runs again. Allowed tools execute. Denied tools return a rejection that includes your deny_message, so the agent knows why it was refused.

A paused session waits indefinitely, so a confirmation nobody answers stalls the work silently. Subscribe to webhooks or watch the event stream so a person learns when a session needs them. For interactive use, ant beta:sessions connect shows the waiting call and sends the confirmation when you allow or deny it.

Confirmations work only on calls that are waiting. Sending user.tool_confirmation for an event whose evaluated_permission is not ask returns a 400 error. That includes calls the auto policy denied, which is how the API enforces that those denials cannot be overridden.
