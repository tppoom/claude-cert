ต้นฉบับ: Explore, plan, implement, commit: the Claude Code loop

Anthropic Claude Certified Architect – Professional (CCAR-P) · สรุปและขยายความตามเอกสารทางการ 100%

🎯 สิ่งที่คุณจะสามารถทำได้หลังจบบทเรียนนี้ (What you will be able to do)

  • ✓Run a Claude Code task as four separate phases (explore, plan, implement, commit) and say why research and planning come before any code is written
  • ✓Choose the permission mode that matches how much the task should be allowed to change without your approval
  • ✓Write prompts that point Claude at exact files, sources and symptoms instead of describing them loosely
  • ✓Keep a session clean by interrupting, rewinding, clearing and delegating research to subagents
  • ✓Give Claude a check it can run (a test, a screenshot or a build) so it can verify its own work
💡 แนวคิดหลักสำคัญ (Key Concept)

Explore, plan, implement, commit — A Claude Code workflow that keeps reading and planning apart from editing. Claude first learns the relevant code, then proposes a plan you can review, and only after that writes, tests and commits the change.

📑 หัวข้อในบทเรียนนี้ (In this lesson)
  • ▸1. Explore, plan, implement, commit
  • ▸2. Matching the permission mode to the task
  • ▸3. Pointing Claude at exact context
  • ▸4. Redirecting, clearing and delegating
  • ▸5. Giving Claude a way to check its own work

1. Explore, plan, implement, commit

Claude Code is an agent It reads files, runs shell commands, edits code and uses git in your project, so a vague request such as "add Google OAuth" can turn straight into edits across a codebase it has not read yet

The explore, plan, implement, commit loop prevents that

Each phase is its own prompt, and no code is written until Claude understands the existing code and you have agreed on a plan.

The four phases as separate prompts, using an OAuth feature as the example text

Plan mode makes the first two phases safe

If you start a session with claude --permission-mode plan, Claude can investigate and propose changes but cannot write to your source files

You review the proposal and then leave plan mode to implement it, so nothing reaches disk until you have seen the plan.

Claude Code is an agent. It reads files, runs shell commands, edits code and uses git in your project, so a vague request such as "add Google OAuth" can turn straight into edits across a codebase it has not read yet. The explore, plan, implement, commit loop prevents that. Each phase is its own prompt, and no code is written until Claude understands the existing code and you have agreed on a plan.

Explore asks Claude to read and explain, and nothing else. Plan asks which files will change and how the flow will work, and the answer is something you can review and correct while correcting it costs nothing. Implement refers back to "your plan" and includes its own check: write tests, run the suite, fix the failures. Commit turns the finished work into a commit and a pull request.

Plan mode makes the first two phases safe. If you start a session with claude --permission-mode plan, Claude can investigate and propose changes but cannot write to your source files. You review the proposal and then leave plan mode to implement it, so nothing reaches disk until you have seen the plan.

4. Redirecting, clearing and delegating

Correct a session as soon as it drifts Waiting means more wasted work to undo

Press Esc to stop Claude in the middle of an action: the running tool call is cancelled and the context is kept, so you can redirect it straight away

If Claude is heading the right way and only needs a nudge, type the correction and press Enter without stopping it

The message is queued, and Claude reads it as soon as its current tool calls finish, within the same turn

If the work has already gone wrong, press Esc twice or run /rewind to restore an earlier state of both the conversation and the code.

Leftover context also costs you A long session full of material from an unrelated earlier task can make Claude perform worse

Run /clear between unrelated tasks to start from an empty context

For a quick side question, use /btw: its answer never enters the conversation history

When a session has to keep going, /compact Focus on the API changes summarizes it according to your instructions instead of whatever the automatic summary would choose to keep.

Subagents keep the main context clean in a different way

Correct a session as soon as it drifts. Waiting means more wasted work to undo. Press Esc to stop Claude in the middle of an action: the running tool call is cancelled and the context is kept, so you can redirect it straight away. If Claude is heading the right way and only needs a nudge, type the correction and press Enter without stopping it. The message is queued, and Claude reads it as soon as its current tool calls finish, within the same turn. If the work has already gone wrong, press Esc twice or run /rewind to restore an earlier state of both the conversation and the code.

Leftover context also costs you. A long session full of material from an unrelated earlier task can make Claude perform worse. Run /clear between unrelated tasks to start from an empty context. For a quick side question, use /btw: its answer never enters the conversation history. When a session has to keep going, /compact Focus on the API changes summarizes it according to your instructions instead of whatever the automatic summary would choose to keep.

Subagents keep the main context clean in a different way. A prompt such as "use subagents to investigate how our authentication system handles token refresh" sends the file reading to a separate agent, and only its findings come back to your session. 5. Giving Claude a way to check its own work

[Feedback loops and iterative refinement inside the system](lesson:1.2) mean the system checks its own output and improves on it

In Claude Code, that requires giving Claude something concrete to check against

"Implement a function that validates email addresses" has no finish line

Adding example cases (user@example.com is true, invalid is false, user@.com is false) and the instruction "run the tests after implementing" gives Claude a result it can verify

UI work follows the same pattern: paste a screenshot of the design, ask Claude to screenshot its result, compare the two, and fix the differences

For a failing build, paste the actual error and ask for the root cause to be fixed, not for the error to be suppressed.

There are four ways to attach the check, depending on how long it needs to apply and how firmly it must hold:

- In one prompt: ask Claude to run the check and keep iterating in the same message. - Across a session: set the check as a /goal condition. A separate evaluator re-checks it after every turn, and Claude keeps working until the goal is met. - As a deterministic gate: a Stop hook runs your check as a script and blocks the turn from ending until it passes. - As a second opinion: a verification subagent has a fresh model try to refute the result, so the agent that did the work is not the one grading it.
