📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Claude Code is an agent. It reads files, runs shell commands, edits code and uses git in your project, so a vague request such as "add Google OAuth" can turn straight into edits across a codebase it has not read yet. The explore, plan, implement, commit loop prevents that. Each phase is its own prompt, and no code is written until Claude understands the existing code and you have agreed on a plan.

Explore asks Claude to read and explain, and nothing else. Plan asks which files will change and how the flow will work, and the answer is something you can review and correct while correcting it costs nothing. Implement refers back to "your plan" and includes its own check: write tests, run the suite, fix the failures. Commit turns the finished work into a commit and a pull request.

Plan mode makes the first two phases safe. If you start a session with claude --permission-mode plan, Claude can investigate and propose changes but cannot write to your source files. You review the proposal and then leave plan mode to implement it, so nothing reaches disk until you have seen the plan.

The permission mode sets which actions Claude takes on its own and which ones wait for you. Choosing a mode is a workflow decision. Exploring an unfamiliar repo, reviewing untrusted code and doing a routine refactor each need a different amount of freedom.

Take a security engineer reviewing a pull request from outside the team. Claude should read the files and run analysis, but every edit and every command needs the engineer's approval first. Manual is the only mode in the table that meets this. Accept edits would apply file changes without asking. Auto would let a classifier approve most actions. Plan blocks edits, but it is a mode for proposing changes, not for approving them one at a time. bypassPermissions goes further than any of these and drops the prompts entirely. It is not even in the normal Shift+Tab cycle until you start Claude Code with --allow-dangerously-skip-permissions. In recent versions of Claude Code, Auto is the built-in starting mode for interactive sessions, so you switch to Manual deliberately when you need it.

Between these modes, permission allowlists let you pre-approve individual commands you know are safe, such as npm run lint or git commit. Claude then stops asking about those commands while still asking about everything else. Pre-approving a few specific commands is safer than switching the whole session to a more permissive mode.

The four options differ in how long the check applies and how firmly it holds. A prompt covers one message. /goal lasts the whole session and uses a separate evaluator. A Stop hook is a deterministic script that can block the turn from ending. A verification subagent gets an independent model to challenge the work.

[Feedback loops and iterative refinement inside the system](lesson:1.2) mean the system checks its own output and improves on it. In Claude Code, that requires giving Claude something concrete to check against. "Implement a function that validates email addresses" has no finish line. Adding example cases (user@example.com is true, invalid is false, user@.com is false) and the instruction "run the tests after implementing" gives Claude a result it can verify. UI work follows the same pattern: paste a screenshot of the design, ask Claude to screenshot its result, compare the two, and fix the differences. For a failing build, paste the actual error and ask for the root cause to be fixed, not for the error to be suppressed.

There are four ways to attach the check, depending on how long it needs to apply and how firmly it must hold:

- In one prompt: ask Claude to run the check and keep iterating in the same message. - Across a session: set the check as a /goal condition. A separate evaluator re-checks it after every turn, and Claude keeps working until the goal is met. - As a deterministic gate: a Stop hook runs your check as a script and blocks the turn from ending until it passes. - As a second opinion: a verification subagent has a fresh model try to refute the result, so the agent that did the work is not the one grading it.
