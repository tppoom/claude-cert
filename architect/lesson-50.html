💡 แนวคิดหลักสำคัญ (Key Concept)

Explore, plan, implement, commit — A Claude Code workflow that keeps reading and planning apart from editing. Claude first learns the relevant code, then proposes a plan you can review, and only after that writes, tests and commits the change.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Explore, plan, implement, commit" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Claude Code is an agent. It reads files, runs shell commands, edits code and uses git in your project, so a vague request such as "add Google OAuth" can turn straight into edits across a codebase it has not read yet. The explore, plan, implement, commit loop prevents that. Each phase is its own prompt, and no code is written until Claude understands the existing code and you have agreed on a plan.

Explore asks Claude to read and explain, and nothing else. Plan asks which files will change and how the flow will work, and the answer is something you can review and correct while correcting it costs nothing. Implement refers back to "your plan" and includes its own check: write tests, run the suite, fix the failures. Commit turns the finished work into a commit and a pull request.

Plan mode makes the first two phases safe. If you start a session with claude --permission-mode plan, Claude can investigate and propose changes but cannot write to your source files. You review the proposal and then leave plan mode to implement it, so nothing reaches disk until you have seen the plan.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Matching the permission mode to the task" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

The permission mode sets which actions Claude takes on its own and which ones wait for you. Choosing a mode is a workflow decision. Exploring an unfamiliar repo, reviewing untrusted code and doing a routine refactor each need a different amount of freedom.

Take a security engineer reviewing a pull request from outside the team. Claude should read the files and run analysis, but every edit and every command needs the engineer's approval first. Manual is the only mode in the table that meets this. Accept edits would apply file changes without asking. Auto would let a classifier approve most actions. Plan blocks edits, but it is a mode for proposing changes, not for approving them one at a time. bypassPermissions goes further than any of these and drops the prompts entirely. It is not even in the normal Shift+Tab cycle until you start Claude Code with --allow-dangerously-skip-permissions. In recent versions of Claude Code, Auto is the built-in starting mode for interactive sessions, so you switch to Manual deliberately when you need it.

Between these modes, permission allowlists let you pre-approve individual commands you know are safe, such as npm run lint or git commit. Claude then stops asking about those commands while still asking about everything else. Pre-approving a few specific commands is safer than switching the whole session to a more permissive mode.

Correct a session as soon as it drifts. Waiting means more wasted work to undo. Press Esc to stop Claude in the middle of an action: the running tool call is cancelled and the context is kept, so you can redirect it straight away. If Claude is heading the right way and only needs a nudge, type the correction and press Enter without stopping it. The message is queued, and Claude reads it as soon as its current tool calls finish, within the same turn. If the work has already gone wrong, press Esc twice or run /rewind to restore an earlier state of both the conversation and the code.

Leftover context also costs you. A long session full of material from an unrelated earlier task can make Claude perform worse. Run /clear between unrelated tasks to start from an empty context. For a quick side question, use /btw: its answer never enters the conversation history. When a session has to keep going, /compact Focus on the API changes summarizes it according to your instructions instead of whatever the automatic summary would choose to keep.

Subagents keep the main context clean in a different way. A prompt such as "use subagents to investigate how our authentication system handles token refresh" sends the file reading to a separate agent, and only its findings come back to your session. [Feedback loops and iterative refinement inside the system](lesson:1.2) mean the system checks its own output and improves on it. In Claude Code, that requires giving Claude something concrete to check against. "Implement a function that validates email addresses" has no finish line. Adding example cases (user@example.com is true, invalid is false, user@.com is false) and the instruction "run the tests after implementing" gives Claude a result it can verify. UI work follows the same pattern: paste a screenshot of the design, ask Claude to screenshot its result, compare the two, and fix the differences. For a failing build, paste the actual error and ask for the root cause to be fixed, not for the error to be suppressed.

There are four ways to attach the check, depending on how long it needs to apply and how firmly it must hold:

- In one prompt: ask Claude to run the check and keep iterating in the same message. - Across a session: set the check as a /goal condition. A separate evaluator re-checks it after every turn, and Claude keeps working until the goal is met. - As a deterministic gate: a Stop hook runs your check as a script and blocks the turn from ending until it passes. - As a second opinion: a verification subagent has a fresh model try to refute the result, so the agent that did the work is not the one grading it.
