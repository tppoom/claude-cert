📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Claude Code and the Agent SDK export OpenTelemetry metrics, log events and traces from the process that runs them. That covers one client at a time. Watching a whole organisation takes four further streams, each answering a different question: spans emitted by the Claude API itself, the usage and cost of individual Managed Agents sessions, organisation-wide usage and cost reports, and adoption and audit records. This page covers each in turn. A Managed Agents session is a run of an agent on the Claude Platform, with its own threads, tools and usage totals, which you can inspect in the Claude Console.

Client-side telemetry stops at your process boundary. The Claude API can emit its own spans, one for each model request and each tool use it runs on Messages API requests and Managed Agents sessions, without any code change. You receive them by adding a destination: an OTLP/HTTP endpoint that accepts protobuf over HTTPS on port 443, plus the headers that authenticate to it. Only organisation admins can add or change destinations. A destination covers All workspaces, Selected ones, or All except a list. Its content mode is either Metadata only or Full content. That is the same opt-in idea as in Claude Code, which redacts prompt, response and tool content by default and records it only when you switch it on.

Leave /v1/traces off the endpoint URL, because the API appends it. After saving, run Test from the destination's menu and look for an anthropic.test span. Real spans arrive under service.name = claude-platform. If you run your own Collector, note that its OTLP/HTTP receiver listens on port 4318 by default. Either reconfigure it for HTTPS on 443 or put a reverse proxy in front.

On their own, API spans start their own traces. To nest them under your application's spans, call the SDK from inside one of your own spans. The SDK writes a W3C traceparent header, and your sampler controls its sampled flag. When the flag is off, the API emits no spans for that request. The same propagation continues into MCP servers connected through the MCP connector, which receive a traceparent in params._meta and can attach their own spans.

Delivery is at least once and best effort. Expect duplicate spans and deduplicate on trace ID plus span ID. A lost span is never resent. The Console's Delivery column shows Healthy, Failing, No data or Disabled. The API disables a destination that answers with a 3xx redirect, resolves to a non-public IP, or fails every delivery for 24 hours.

1. ป้องกัน Context Pollution (ผลลัพธ์เครื่องมือมีขนาดใหญ่มาก): เมื่อการทำงานย่อยสร้างโทเค็นที่ไม่เกี่ยวข้องมากกว่า 1,000 โทเค็น (เช่น อ่านเอกสารหนาๆ หรือค้นหาเว็บ) การให้ Subagent ทำจะช่วยกักกันข้อมูลส่วนเกินไม่ให้รบกวนการตัดสินใจของ Orchestrator
2. เมื่องานสามารถทำพร้อมกันได้ (Parallelization): หากงานย่อยหลายชิ้นเป็นอิสระต่อกัน (เช่น ตรวจสอบความปลอดภัย 3 ด้านคนละมุม) การส่งให้ Subagents ทำงานขนานกันจะช่วยลด Latency รวมของระบบได้อย่างมหาศาล
3. เมื่องานต้องการเครื่องมือเฉพาะทางสูง (Tool Specialization): การใส่เครื่องมือให้เอเจนต์ตัวเดียวมากเกินไป (Capability Bloat) จะทำให้ความแม่นยำในการเลือกเครื่องมือลดลง การแยก Subagent ตามหน้าที่ช่วยให้แต่ละตัวมีเครื่องมือเฉพาะทางเพียง 3-5 ชิ้นเท่านั้น
💰 ต้นทุนโทเค็นที่ต้องแลก (Token Cost): สำหรับงานประเภทเดียวกัน ระบบ Multi-Agent มักใช้โทเค็นมากกว่าระบบเอเจนต์เดี่ยวประมาณ 3 ถึง 10 เท่า เนื่องจากต้องส่งคำสั่งระบบซ้ำให้กับ Subagent แต่ละตัว และต้องเสียโทเค็นในรอบการรวบรวมข้อมูล

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Usage and cost of a Managed Agents session" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A single Managed Agents session reports its own consumption. The session object's usage field holds cumulative token counts, cache reads and writes, server tool requests, active_seconds and list_cost. A session can run several threads, for example one per agent in a multiagent session, and the Console's session viewer shows one timeline lane per thread, a transcript, and a Tools tab with failure counts and median duration. active_seconds is the time during which at least one thread was running, with overlapping threads counted once. The session's running-time cost is priced on that duration. Each thread also reports its own list_cost, but per-thread costs are rounded independently and leave out the running-time cost, so the session figure is the authoritative one.

A session.usage event carries the same cumulative snapshot on the session stream, so you don't have to poll. It is emitted on idle transitions rather than on a timer: immediately before the session goes idle, and when a thread pauses at a session budget. During a long run you therefore see no new totals until one of those moments. That is why a spend cap built from watching usage and stopping the session yourself fails, since the stop arrives after the money is spent. A session budget is a dollar cap on list cost. The platform prices consumption continuously and pauses each thread before its next model request once the cap is reached, so enforcement doesn't depend on your code noticing in time.

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 56905

During an active incident, an on-call engineer needs a near real-time view of organization-wide token consumption spikes, checking for anomalies roughly once a minute. Which Usage API configuration fits this monitoring need within the documented granularity limits?

A Request bucket_width=1m, raise the limit above the 60-bucket default up to the 1440-bucket maximum as needed, and poll about once per minute
B Request bucket_width=1d with the default 7-bucket limit, since daily granularity is sufficient to detect minute-level spikes retroactively
C Request bucket_width=1h with the 168-bucket maximum limit, since hourly buckets update automatically every 60 seconds
D Request bucket_width=1m but poll every 5 seconds to catch spikes as soon as they occur, since finer polling improves data freshness
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. Minute-level buckets are intended for real-time monitoring, the limit can be raised well past its default to capture a longer recent window, and roughly once-per-minute polling matches the documented sustained polling guidance.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. Daily buckets aggregate an entire day into one data point, which cannot reveal minute-level spikes during an active incident regardless of how many buckets are requested.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Hourly buckets aggregate a full hour of usage into a single value; they do not refresh at 60-second intervals, and they are too coarse to spot a spike within a given hour.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Polling far more frequently than the recommended once-per-minute cadence does not produce fresher underlying data, since usage figures typically finalize within about five minutes of request completion, and it needlessly increases API load.

The Usage & Cost Admin API answers organisation-wide questions: tokens by model, workspace, API key or service tier over time, and spend by day. You call it with an Admin API key. The response is a series of time buckets, and bucket_width sets their granularity. Each width has its own default and maximum limit, which is the number of buckets returned per request. The cost endpoint offers only daily buckets.

So for incident monitoring, use 1m buckets, raise limit past the default 60 when you need a longer window, and poll about once a minute. Spend data shows what Claude Code costs. Adoption data shows whether people use it. The Claude Code analytics dashboard reports usage metrics: lines of code accepted, suggestion accept rate, and daily active users and sessions. Teams and Enterprise plans add contribution metrics from a GitHub integration, such as merged PRs that contain Claude Code lines, plus a leaderboard and CSV export. On API organisations the dashboard lives in the Claude Console and adds spend tracking and team insights.

Administrative actions are a different stream again. The compliance activities endpoint lets you query actions such as workspaces being created or archived, members being added or removed, RBAC custom roles being created or assigned, spend limits being changed, and the zero data retention override being toggled. It also logs reads: viewing the Claude Code usage report or the messages usage report is itself an activity.

Claude Code's per-user activity reaches a retention store such as a SIEM through the logs exporter. Managed settings are the policy settings an admin deploys and enforces across all Claude Code users, so they are the right place for this configuration. When managed settings set an endpoint or credential, Claude Code removes any per-signal endpoints a developer set, so a developer can't send logs to a different collector. Three switches matter here. CLAUDE_CODE_ENABLE_TELEMETRY=1 turns telemetry collection on, and nothing is exported without it. OTEL_LOGS_EXPORTER=otlp sends log events to an OTLP endpoint, where none would disable them. OTEL_LOG_TOOL_DETAILS=1 is an opt-in that is off by default: it makes tool events carry the Bash commands and MCP server and tool names that ran, where otherwise those arguments are not logged.
