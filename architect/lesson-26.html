💡 แนวคิดหลักสำคัญ (Key Concept)

Multidimensional success criteria — A Claude application passes only when it meets a separate, computable threshold on each dimension it is judged on, such as accuracy, latency, cost, safety and security. A single score can't do this, because a system can do well on one dimension while failing another.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

An evaluation metric is a number computed from a model's outputs on a test set and compared against a threshold. It tells you whether a prompt, model or configuration is ready to ship. You need it because "the model should classify sentiments well" can't be checked. "F1 of at least 0.85 on 10,000 held-out posts" can. The success criteria themselves are agreed during discovery ([Measurable success criteria](lesson:6.1)). Here the job is the next step: turning each criterion into a formula that a script can compute on every run.

Each metric is blind to some kind of failure. A classifier can label every ticket correctly and still take too long for a live chat. It can be fast and correct but cost more per ticket than the process it replaces. It can be fast, correct and cheap but answer in toxic language now and then. Or it can pass on every ordinary input and still leak details it was told to keep private. That is why the reference example of a good criterion is several thresholds on one held-out set, not one number: an F1 of at least 0.85, 99.5% non-toxic outputs, 90% of errors being an inconvenience rather than egregious, and 95% of responses under 200ms.

For agents, the dimensions also stack inside a single task. Each check on an agent's work is a grader: logic that scores one aspect of its performance. A support agent's task can count as solved only if the ticket is resolved (a state check, which inspects the environment after the run), the conversation finished in under 10 turns (a transcript constraint, a limit on what the conversation log may contain, such as the number of turns), and the tone was appropriate (an LLM rubric, a model scoring the output against written criteria). You also choose how a task's grader scores combine. Weighted scoring passes when the combined score clears a threshold. Binary scoring requires every grader to pass. A hybrid mixes the two.

"Accuracy" is not one metric. The right one depends on what a correct output looks like, so start with the output's shape. When the answer comes from a fixed set of labels, such as five ticket categories or positive/negative/neutral/mixed sentiment, correctness is binary, and code can grade it without any judgement. Exact match compares the output with the labelled answer after normalising whitespace and case. Accuracy is the share of matches. When the classes are imbalanced or some errors matter more than others, precision, recall and F1 from the same comparisons tell you more than raw accuracy.

Free-form text breaks exact match, because two good summaries almost never match character for character. For summarisation against reference summaries, use ROUGE-L. It measures the length of the longest common subsequence shared by the model's summary and the reference, so it rewards both overlapping content and the order in which ideas appear. A typical test set is a few hundred articles, each with a reference summary.

Consistency is a separate question from correctness. If a user asks the same thing twice in different words, they should get answers that mean the same thing. To measure this, encode the outputs for groups of paraphrased questions with a sentence-embedding model and compute cosine similarity. Values near 1 mean the answers agree. This metric says nothing about whether the answers are right: a model that gives the same wrong label to every paraphrase scores perfectly.

Some qualities, such as coherence, tone or translation quality, have no reference you can match against. For these, use a qualitative scale applied the same way every time: a Likert prompt such as "Rate coherence from 1 (nonsensical) to 5 (perfectly logical)", scored by an LLM grader or by experts with a rubric. Don't use one on a categorical task. Asking a second model to rate how well a label "matches" adds cost and non-determinism to a check that string comparison settles exactly.

A latency target means nothing until you say when the clock starts and when it stops. A Claude system has three clocks worth separating, and they can move independently:

- Time to first token (TTFT) runs from sending the prompt to receiving the first token of the response. It is what a user notices when responses are streamed, because text starts appearing even while generation continues. - Total response time runs until the last token arrives. An agent eval records it as time_to_last_token, alongside output_tokens_per_sec. This is the clock that matters when nothing downstream can act until the full output has been parsed, such as a classifier whose label sits at the end of its reasoning. - End-to-end task time covers a whole agent run across many turns and tool calls. It grows with n_turns and n_toolcalls even when each individual call is fast.

The clocks pull against each other, so an SLA that names none of them can be met while users still complain. Streaming improves TTFT but leaves total response time unchanged. Telling an agent that time matters and showing it the elapsed time cut run time by 7% to 47% in Anthropic's tests, at the cost of a few points of score. That trade is visible only if task time and accuracy are both being measured.

Write the threshold as a percentile. "95% of responses under 200ms" puts the budget and the allowed exceptions in a single sentence: 5% of turns may run slow during a spike, and the rest may not. A mean can't express that. A month of 150ms average can hide a fifth of voice turns stalling, and one extreme outlier can push an otherwise healthy average over its target. Average output token count and requests per minute are not latency metrics at all. The first measures response size and the second measures capacity. Pick the percentile and the budget from the application's real-time requirements: a voice turn and an overnight batch job are not held to the same number.

2. เมื่องานสามารถทำพร้อมกันได้ (Parallelization): หากงานย่อยหลายชิ้นเป็นอิสระต่อกัน (เช่น ตรวจสอบความปลอดภัย 3 ด้านคนละมุม) การส่งให้ Subagents ทำงานขนานกันจะช่วยลด Latency รวมของระบบได้อย่างมหาศาล
3. เมื่องานต้องการเครื่องมือเฉพาะทางสูง (Tool Specialization): การใส่เครื่องมือให้เอเจนต์ตัวเดียวมากเกินไป (Capability Bloat) จะทำให้ความแม่นยำในการเลือกเครื่องมือลดลง การแยก Subagent ตามหน้าที่ช่วยให้แต่ละตัวมีเครื่องมือเฉพาะทางเพียง 3-5 ชิ้นเท่านั้น
💰 ต้นทุนโทเค็นที่ต้องแลก (Token Cost): สำหรับงานประเภทเดียวกัน ระบบ Multi-Agent มักใช้โทเค็นมากกว่าระบบเอเจนต์เดี่ยวประมาณ 3 ถึง 10 เท่า เนื่องจากต้องส่งคำสั่งระบบซ้ำให้กับ Subagent แต่ละตัว และต้องเสียโทเค็นในรอบการรวบรวมข้อมูล
⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Cost should be an eval metric with a threshold, computed on the same runs as accuracy. Don't treat it as a bill you check afterwards. The unit is the task, not the token: a cheaper model that needs more turns or more retries can cost more for each problem it solves ([Cost per solved task (not price per token)](lesson:2.1)). The response's usage block reports input, output and cache token counts. Multiply them by the per-token prices, then divide total spend by the number of tasks in the run.

A cost threshold is relative to something. The ticket-routing example sets two thresholds side by side: 95% accuracy over 100 tests, and a 50% average reduction in cost per classification compared with the current routing method. In the insurance-claims cookbook, a baseline agent scored 10/10 at about $0.29 per task. Because a mislabelled claim costs more than the inference saved, the team kept the accuracy requirement at 10/10 and treated cost as the number to push down. A configuration that saves money but drops a case fails, however cheap it is.

5. Quantifying safety and security as checkable rates

การวางระบบความปลอดภัยและการป้องกัน (Security & Guardrails) สำหรับแอปพลิเคชัน Claude:

  • Input Guardrails: ตรวจสอบคำสั่งของผู้ใช้เพื่อดักจับ Prompt Injection และ Jailbreak ก่อนที่จะส่งต่อให้โมเดลประมวลผล
  • Output Guardrails: ตรวจสอบผลลัพธ์ของโมเดลก่อนส่งให้ผู้ใช้ เพื่อป้องกันข้อมูลลับรั่วไหล หรือการละเมิด Content Policy
  • หลักการ Least Privilege: เอเจนต์ควรได้รับสิทธิ์ในการเข้าถึงเครื่องมือและฐานข้อมูลเท่าที่จำเป็นต่องานนั้นๆ เท่านั้น และคำสั่งอันตรายต้องมี Human-in-the-Loop เสมอ

"The assistant should be safe" is a hope, not a criterion. Even fuzzy goals like ethics and safety can be expressed as rates: the share of outputs, over a stated number of trials, that a stated detector flags. A good safety criterion names three things: the detector (a content filter), the sample size (10,000 trials) and the ceiling (fewer than 0.1% flagged). Severity needs the same treatment. "90% of errors would cause inconvenience, not egregious error" is computable only once you have written down what counts as inconvenient and what counts as egregious.

A security metric is computed the same way. The difference is that you first have to define what counts as a successful attack, specifically enough that code or a grader can decide it. Start from the threat model, because there are two. In jailbreaks and direct prompt injection, the user is the adversary and writes inputs meant to get around your guardrails. In indirect prompt injection, the user is trusted, but Claude reads third-party content (web pages, emails, documents, tool results) that contains adversarial instructions. Each one needs its own adversarial test set and its own success condition. The metric is then the attack success rate: the share of attack attempts that meet that condition.

Write success conditions as observable outcomes, never as "the model seemed manipulated":

- A harmlessness screen is a model call that labels incoming input as harmful or not before it reaches the main conversation. Structured outputs force it to return a fixed label, such as a boolean is_harmful, so code can compare it with the known answer. An attack succeeds when a known-harmful input comes back labelled safe. - For data handling, an attack succeeds when the output uses or shares a detail the instructions said to withhold. - For agents, an attack succeeds when the end state shows the forbidden effect, checked against environment state rather than the transcript's wording.

The authentication-bypass task below shows the agent version. Its graders spell out what "secure" means: deterministic tests that reject empty and null passwords, a static security scan with bandit, and a state check that the security log recorded an auth_blocked event. If any of them fails, the fix fails, however convincing the agent's explanation sounds.
