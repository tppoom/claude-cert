Audience-bound access token — An MCP access token is issued for one specific MCP server, named by its canonical URI. That server must reject any token issued for another server, and it must never pass a token it received on to a different service.

1.The transport decides how an MCP server authenticates

Model Context Protocol (MCP) คือเกณฑ์วิธีมาตรฐานเปิดที่เชื่อมต่อ Claude เข้ากับแหล่งข้อมูลภายนอกและเครื่องมืออย่างปลอดภัย:

1. Tools (เครื่องมือ) ฟังก์ชันที่โมเดลสามารถสั่งรันได้เพื่อสร้างผลกระทบต่อระบบภายนอก (เช่น รันคำสั่ง SQL หรือยิง API)
2. Resources (ทรัพยากร) ข้อมูลแบบอ่านอย่างเดียว (Read-only data) ที่คล้ายกับไฟล์หรือเนื้อหาเอกสารสำหรับให้อ่านเป็นบริบท
3. Prompts (พร้อมต์) เทมเพลตคำสั่งและกระบวนการทำงานที่เตรียมไว้ให้ผู้ใช้หรือเอเจนต์เรียกใช้งานได้อย่างรวดเร็ว

Reviewing authentication for an MCP integration starts with one question: how does the client reach the server? A server reached over HTTP is a network service. Anyone who can reach its URL can send it requests, so it needs real authorization, and the MCP authorization specification is built on OAuth 2.1. A server launched locally over STDIO is a child process of the client. It has no network listener to protect, and the specification tells it to skip OAuth and retrieve credentials from the environment.

Each transport has its own typical gap. An HTTP server that accepts requests with no token, or with a static key everyone shares, has skipped the OAuth flow the specification expects of it. A STDIO server that tries to run browser-based OAuth is overbuilt. The real risk there is the environment itself: any secret it reads from an environment variable is visible to everything else running in that environment. The remaining sections apply to the HTTP case.

An audit log shows an MCP client receive a 401, follow the resource_metadata URL, and fetch the authorization server's metadata over HTTPS. That metadata has no code_challenge_methods_supported field. The client completes the authorization flow anyway and gets a valid token. What should the audit report?

A No gap. The endpoints used HTTPS and the token the client received is valid.
B A gap. The missing field means the authorization server does not support PKCE, so the client should have refused to proceed.
C A gap. The client should have retried discovery through OpenID Connect Discovery, which always lists PKCE methods.
D A gap. The client should have skipped the Protected Resource Metadata and gone straight to the authorization server's well-known URI.
คลิกดูเฉลยคำตอบพร้อมคำอธิบาย (Click to view answer & explanation) ▼
คำตอบที่ถูกต้อง: ตัวเลือก B

If code_challenge_methods_supported is absent, the authorization server does not support PKCE, and the client must stop. A client that carries on has an authentication gap even if the token it gets is valid. Protected Resource Metadata is the required way to discover the authorization server, so skipping it is not the fix.

“If code_challenge_methods_supported is absent, the authorization server does not support PKCE and MCP clients MUST refuse to proceed.”

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The client does not need to know in advance where to get a token. Discovery begins with an unauthenticated request. The MCP server replies 401 Unauthorized with a WWW-Authenticate header, and that header carries a resource_metadata URL pointing to the server's OAuth 2.0 Protected Resource Metadata document. Every MCP server must publish this document, and clients must use it to find the authorization server. It can be served at a well-known URI, either at the root (/.well-known/oauth-protected-resource) or with the MCP endpoint's path appended.

Next, the client fetches the authorization server's own metadata. The authorization server must offer at least one of OAuth 2.0 Authorization Server Metadata (/.well-known/oauth-authorization-server) or OpenID Connect Discovery (/.well-known/openid-configuration), and the client must support both. If the metadata has no code_challenge_methods_supported field, the client must stop. A missing field means the server does not support PKCE, and the client must not proceed without it.

These are the transport rules to check in an audit. Every authorization server endpoint must be served over HTTPS. Every redirect URI must be either localhost or HTTPS. A client that continues after any of these checks fails has an authentication gap, even if every token it later receives is valid.

Before a client can request tokens, the authorization server has to know who that client is. The specification sets an order of preference:

1. Use pre-registered client information, if the client and server already have a relationship. 2. Use a Client ID Metadata Document, if the authorization server advertises client_id_metadata_document_supported. This is the usual case when the two have no prior relationship. 3. Fall back to Dynamic Client Registration, if the server publishes a registration_endpoint. 4. Otherwise, ask the user to enter client details.

With a Client ID Metadata Document, the client's client_id is itself an HTTPS URL with a path component. The JSON hosted at that URL must include client_id, client_name and redirect_uris, and its client_id must match the document URL exactly. The authorization server fetches the document and must check the redirect URI in each authorization request against the list in the document. Dynamic Client Registration now remains only for backwards compatibility: the specification calls it deprecated and keeps it for authorization servers that do not support metadata documents.

Localhost redirects open the main impersonation path. An attacker can present the legitimate client's metadata URL as their own client_id and bind to a localhost port listed in its redirect URIs. When the user approves, the attacker's listener receives the authorization code. The specification responds on the consent screen. Authorization servers must clearly display the redirect URI hostname, should add warnings for localhost-only redirect URIs, and may require additional attestation. Servers that protect sensitive resources can also restrict which client domains they accept, using trusted-domain allowlists or reputation checks.

Every token request names the server the token is for. The client sends a resource parameter in both the authorization request and the token request. The value must be the MCP server's canonical URI, which identifies the server the client intends to use the token with. That URI includes a scheme and has no fragment. For consistency, the specification prefers the form without a trailing slash.

Tokens must also travel in the right place. The client sends the token in the Authorization: Bearer header and must never put it in the URI query string. Query strings end up in logs and browser history. Refresh tokens must be kept confidential both in transit and in storage. Clients must not assume a refresh token will be issued at all, because the authorization server decides that.

Audience binding fails in two ways. In the first, the server skips audience validation and so accepts tokens issued for other services. An attacker can then reuse a legitimate token against a service it was never meant for. The second, token passthrough, is worse: the server also forwards those unmodified tokens to downstream APIs. That creates a confused deputy. The downstream API may treat the token as if it came from the MCP server, or assume the upstream API already validated it. A safe server validates the audience of every incoming token and calls downstream services with a token issued for that call.

Each of these status codes calls for a different response from the client. A 401 means authorization is required or the token is invalid, so the client has to authenticate. A 403 means the token is valid but its scopes are insufficient. Signing in again with the same scopes will fail again. The client needs a token with more scope.

Step-up authorization lets a client start with a narrow grant and add scope only when an operation needs it. When a 403 challenge arrives, the client re-authorizes with the union of the scopes it already requested and the scopes named in the challenge, so permissions it already has are not lost. It then retries the original request. If the retry fails more than a few times, the client must treat it as a permanent authorization failure and stop looping.

The initial request is where over-broad scopes usually come from. The client uses the scope hint from the first 401, if the server sent one. If there is no hint, it requests every scope listed in scopes_supported. A server that never sends a scope hint therefore gets tokens carrying its full scope set on first contact. In an audit, look for servers whose 401 responses omit scope, and for tokens that already hold write scopes before any write has been attempted.
