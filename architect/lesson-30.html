💡 แนวคิดหลักสำคัญ (Key Concept)

Free wins versus trade-offs — Some cost levers lower spend without changing output quality (caching, token hygiene, batching), while others buy savings with quality (smaller model, lower effort, tight caps). Use up the free levers first, then spend quality only where evals show you can afford it.

1. Two kinds of cost levers

การแยกงานให้ Subagents ทำจะช่วยยกระดับผลลัพธ์ให้ดีขึ้นใน 3 สถานการณ์หลัก เท่านั้น หากอยู่นอกเหนือจากนี้ การประสานงานมักจะสร้างต้นทุนมากกว่าประโยชน์:

1. ป้องกัน Context Pollution (ผลลัพธ์เครื่องมือมีขนาดใหญ่มาก): เมื่อการทำงานย่อยสร้างโทเค็นที่ไม่เกี่ยวข้องมากกว่า 1,000 โทเค็น (เช่น อ่านเอกสารหนาๆ หรือค้นหาเว็บ) การให้ Subagent ทำจะช่วยกักกันข้อมูลส่วนเกินไม่ให้รบกวนการตัดสินใจของ Orchestrator
2. เมื่องานสามารถทำพร้อมกันได้ (Parallelization): หากงานย่อยหลายชิ้นเป็นอิสระต่อกัน (เช่น ตรวจสอบความปลอดภัย 3 ด้านคนละมุม) การส่งให้ Subagents ทำงานขนานกันจะช่วยลด Latency รวมของระบบได้อย่างมหาศาล
3. เมื่องานต้องการเครื่องมือเฉพาะทางสูง (Tool Specialization): การใส่เครื่องมือให้เอเจนต์ตัวเดียวมากเกินไป (Capability Bloat) จะทำให้ความแม่นยำในการเลือกเครื่องมือลดลง การแยก Subagent ตามหน้าที่ช่วยให้แต่ละตัวมีเครื่องมือเฉพาะทางเพียง 3-5 ชิ้นเท่านั้น
💰 ต้นทุนโทเค็นที่ต้องแลก (Token Cost): สำหรับงานประเภทเดียวกัน ระบบ Multi-Agent มักใช้โทเค็นมากกว่าระบบเอเจนต์เดี่ยวประมาณ 3 ถึง 10 เท่า เนื่องจากต้องส่งคำสั่งระบบซ้ำให้กับ Subagent แต่ละตัว และต้องเสียโทเค็นในรอบการรวบรวมข้อมูล

แรงผลักดันต้นทุนแต่ละรายการบนแพลตฟอร์ม Claude จะแบ่งออกเป็นสองกลุ่ม และควรดึงกลุ่มตามลําดับ กลุ่มแรกคือ Free Wins ซึ่งจะย้ายเวิร์กโหลดให้ใกล้กับขอบเขตต้นทุนถึงความชาญฉลาดมากขึ้น: คุณจ่ายน้อยลงสําหรับเอาต์พุตเดียวกัน กลุ่มที่สองจะย้ายเวิร์กโหลดไปตามขอบเขตนั้น ดังนั้นเงินที่ประหยัดได้แต่ละดอลลาร์จะเสียไปกับคุณภาพบางอย่าง Free Wins ประกอบด้วยการแคชแบบทันที การทําความสะอาดโทเค็น การตรวจสอบแบบทันทีเทียบกับโมเดลที่คุณใช้งานจริง การประมวลผลเป็นชุดพร้อมส่วนลด 50% สําหรับงานที่สามารถรอได้ถึง 24 ชั่วโมง และขีดจํากัดค่าใช้จ่ายของพื้นที่ทํางานเป็นขั้นสุดท้าย ข้อแลกเปลี่ยนคือการเลือกโมเดล ความพยายาม ขีดจํากัดเอาต์พุตและงบประมาณเซสชัน นาฬิกาเวลาที่ผ่านไป และสถาปัตยกรรมแบบหลายโมเดล

Every cost lever on the Claude Platform falls into one of two groups, and the groups should be pulled in order. The first group, the free wins, moves a workload closer to the cost-to-intelligence frontier: you pay less for the same output. The second group moves the workload along that frontier, so each dollar saved costs some quality. Free wins include prompt caching, token hygiene, a prompt audit against the model you are actually running, batch processing at 50% off for work that can wait up to 24 hours, and workspace spend limits as a backstop. 2. Why caching dominates agent-loop cost

การแยกงานให้ Subagents ทำจะช่วยยกระดับผลลัพธ์ให้ดีขึ้นใน 3 สถานการณ์หลัก เท่านั้น หากอยู่นอกเหนือจากนี้ การประสานงานมักจะสร้างต้นทุนมากกว่าประโยชน์:

1. ป้องกัน Context Pollution (ผลลัพธ์เครื่องมือมีขนาดใหญ่มาก): เมื่อการทำงานย่อยสร้างโทเค็นที่ไม่เกี่ยวข้องมากกว่า 1,000 โทเค็น (เช่น อ่านเอกสารหนาๆ หรือค้นหาเว็บ) การให้ Subagent ทำจะช่วยกักกันข้อมูลส่วนเกินไม่ให้รบกวนการตัดสินใจของ Orchestrator
2. เมื่องานสามารถทำพร้อมกันได้ (Parallelization): หากงานย่อยหลายชิ้นเป็นอิสระต่อกัน (เช่น ตรวจสอบความปลอดภัย 3 ด้านคนละมุม) การส่งให้ Subagents ทำงานขนานกันจะช่วยลด Latency รวมของระบบได้อย่างมหาศาล
3. เมื่องานต้องการเครื่องมือเฉพาะทางสูง (Tool Specialization): การใส่เครื่องมือให้เอเจนต์ตัวเดียวมากเกินไป (Capability Bloat) จะทำให้ความแม่นยำในการเลือกเครื่องมือลดลง การแยก Subagent ตามหน้าที่ช่วยให้แต่ละตัวมีเครื่องมือเฉพาะทางเพียง 3-5 ชิ้นเท่านั้น
💰 ต้นทุนโทเค็นที่ต้องแลก (Token Cost): สำหรับงานประเภทเดียวกัน ระบบ Multi-Agent มักใช้โทเค็นมากกว่าระบบเอเจนต์เดี่ยวประมาณ 3 ถึง 10 เท่า เนื่องจากต้องส่งคำสั่งระบบซ้ำให้กับ Subagent แต่ละตัว และต้องเสียโทเค็นในรอบการรวบรวมข้อมูล

Agent loops are expensive because every turn resends the entire conversation so far: system prompt, tool definitions and every prior turn. A 40-turn task sends its first turn 40 times, so cost grows with roughly the square of the number of turns. Caching doesn't stop the resending. It makes each resend cheap: the cached prefix is billed at the cache-read rate, and only new content pays the 1.25x write rate. On most models a read costs a tenth of the input price, on Claude Opus 5.5 and Claude Sonnet 5.5 a twentieth, and on Claude Fable 5.1 and Claude Mythos 5.1 a fortieth. Cached prefixes are also processed faster, so the same change cuts latency too. 4. Token hygiene: trimming what each call carries

Token hygiene means cutting tokens the task doesn't need from every call: redundant instructions, verbose tool output, and history that no longer matters. The prompt is the first place to look. Say what you mean concisely and drop unnecessary detail and repetition, but keep in mind that Claude knows nothing about your use case and won't fill gaps you leave in unclear instructions. On output, ask Claude directly to be concise. Fewer tokens processed and generated also means a faster response. A prompt audit against the model you are running belongs here too: instructions written for an older model can carry weight the current one doesn't need.

Input trimming covers bulky inputs such as images and tool definitions. In a measured triage job, resizing images and deferring tool definitions with tool search took 26% off the cost of a 20-issue run and 21% off a longer run, on top of caching. Tool output is usually the largest bulk in a long agent session.

Long agent sessions also need lifecycle levers, because history keeps growing even after its tool results stop being useful. Three work together:

- Context editing clears old tool results once the prompt passes a token threshold, keeping only recent tool uses. In one measured configuration it cleared at least 2,000 tokens once the prompt passed 20,000, keeping the three most recent tool uses. - Compaction acts once input reaches a set size (50,000 input tokens on one measured job). It shrinks earlier history so the session can go on without hitting the context window. - The memory tool writes state that must survive, such as learned patterns or progress, to durable storage, so clearing old context doesn't lose it.

Two levers that sound similar don't address a filling context window. Lowering effort cuts the tokens of each response and makes tool calls fewer and terser. But the session still carries every earlier turn and tool result, so the window keeps filling. Raising effort to max removes the limit on token spending. The Message Batches API runs each request on its own as an asynchronous job, which can't carry a live agent session that needs one turn's result before it can take the next.

7. Bounding spend: max_tokens, budgets and re-running failures
