📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Every cost lever on the Claude Platform falls into one of two groups, and the groups should be pulled in order. The first group, the free wins, moves a workload closer to the cost-to-intelligence frontier: you pay less for the same output. The second group moves the workload along that frontier, so each dollar saved costs some quality. Free wins include prompt caching, token hygiene, a prompt audit against the model you are actually running, batch processing at 50% off for work that can wait up to 24 hours, and workspace spend limits as a backstop. The trade-offs are model choice, effort, output caps and session budgets, an elapsed-time clock, and multi-model architectures.

The order matters because the two groups fail differently. A free win that doesn't pay off leaves quality where it was. A trade-off that goes too far shows up as lower task success, and you only find out through evals. So the default advice for any workload on any model is to turn on caching and trim unneeded tokens first. Only when costs are still too high, with quality fine, do you try lower effort or a smaller model. All of Anthropic's figures here are internal and directional, so check every lever against your own workload.

Agent loops are expensive because every turn resends the entire conversation so far: system prompt, tool definitions and every prior turn. A 40-turn task sends its first turn 40 times, so cost grows with roughly the square of the number of turns. Caching doesn't stop the resending. It makes each resend cheap: the cached prefix is billed at the cache-read rate, and only new content pays the 1.25x write rate. On most models a read costs a tenth of the input price, on Claude Opus 5.5 and Claude Sonnet 5.5 a twentieth, and on Claude Fable 5.1 and Claude Mythos 5.1 a fortieth. Cached prefixes are also processed faster, so the same change cuts latency too. For the mechanics of stable prefixes, automatic caching and breakpoints, see [Prompt caching: stable prefix, automatic caching and breakpoints](lesson:2.5).

The savings depend on turn count, because shorter loops re-read less, which is why the short Haiku sessions save the least. Your benchmark is the cache-read share of input. Over a full day of real traffic, agent loops read a median 84% of their input from the cache, and a well-built loop deep in a task pays full price on under 1% of its input. Below about 80%, something is breaking the cache.

The thing that gets cached is a prefix, and it has to match byte for byte. Take a support bot that sends a 30,000-token product manual in its system prompt ahead of a short, different question on every request, with requests 30 to 90 seconds apart. Putting a cache breakpoint on the manual block means each request reads those 30,000 tokens from cache instead of processing them again. That cuts both cost and latency, and the gaps between requests are well inside the default 5-minute lifetime. Other changes don't help. Moving the manual after the question puts changing content in front of it, so no request shares a prefix. Rotating ten manual fragments splits the traffic across ten prefixes. Lowering max_tokens shortens output but leaves all 30,000 input tokens to be processed on every call.

The cache duration is a pricing choice, and the right answer comes from the gaps between consecutive requests, not from how long a session lasts. The default lifetime is 5 minutes, and it is refreshed at no extra cost whenever the cache is read. The 1-hour duration costs 2x the input price to write instead of 1.25x. A miss on either duration bills the whole prefix at the write price, not the read price. So the 1-hour cache earns its higher write price only when pauses long enough to expire a 5-minute entry come up often enough.

The 1-hour duration is not a free upgrade. With turns seconds apart, the default cost about 19% less than the 1-hour setting on Claude Sonnet 5.5. When gaps over an hour are common, both durations expire, and the 1-hour setting then rewrites the prefix at its higher write price. The 1-in-20 rule leaves a margin over the measured break-even of about 1 turn in 30. At 1 turn in 10, staying on the 5-minute setting cost 54% more.

Keeping the 5-minute cache warm is the alternative to buying the hour. Take the previous request, set max_tokens to 0, drop stream, and change nothing in the prefix. Resend it with the original headers, including any anthropic-beta header. Send it within 4 minutes of the previous request's start and every 4 minutes after that, because the lifetime counts from when a request starts. It returns no output and costs little more than a cache read. A max_tokens: 0 request is rejected when it sets thinking.type: "enabled", structured outputs, a forced tool choice, or the top-level compaction parameter. For those workloads, buy the 1-hour duration instead.

Token hygiene means cutting tokens the task doesn't need from every call: redundant instructions, verbose tool output, and history that no longer matters. The prompt is the first place to look. Say what you mean concisely and drop unnecessary detail and repetition, but keep in mind that Claude knows nothing about your use case and won't fill gaps you leave in unclear instructions. On output, ask Claude directly to be concise. Fewer tokens processed and generated also means a faster response. A prompt audit against the model you are running belongs here too: instructions written for an older model can carry weight the current one doesn't need.

Input trimming covers bulky inputs such as images and tool definitions. In a measured triage job, resizing images and deferring tool definitions with tool search took 26% off the cost of a 20-issue run and 21% off a longer run, on top of caching. Tool output is usually the largest bulk in a long agent session.

Long agent sessions also need lifecycle levers, because history keeps growing even after its tool results stop being useful. Three work together:

- Context editing clears old tool results once the prompt passes a token threshold, keeping only recent tool uses. In one measured configuration it cleared at least 2,000 tokens once the prompt passed 20,000, keeping the three most recent tool uses. - Compaction acts once input reaches a set size (50,000 input tokens on one measured job). It shrinks earlier history so the session can go on without hitting the context window. - The memory tool writes state that must survive, such as learned patterns or progress, to durable storage, so clearing old context doesn't lose it.

Two levers that sound similar don't address a filling context window. Lowering effort cuts the tokens of each response and makes tool calls fewer and terser. But the session still carries every earlier turn and tool result, so the window keeps filling. Raising effort to max removes the limit on token spending. The Message Batches API runs each request on its own as an asynchronous job, which can't carry a live agent session that needs one turn's result before it can take the next.

The Message Batches API halves the price of any workload where nobody is waiting on the answer. You submit many Messages requests together, each with its own custom_id and a standard params object. The system processes them asynchronously, and you poll for results. All usage is charged at 50% of standard prices. Most batches finish within an hour, but results are guaranteed only once every request is done or 24 hours have passed. The discount is paid for in latency.

Consider a nightly job that scores 50,000 archived support tickets against a rubric, takes six hours on synchronous calls, and has no user waiting. Batching is the direct fix: same model, same prompts, half the price. A single batch holds up to 100,000 requests or 256 MB. Raising effort to max or turning on extended thinking would add tokens rather than cut them. Switching to the 1-hour cache only pays when there are pauses between 5 minutes and an hour, and it doesn't cut the price of every request.

Good fits include large-scale evaluations, content moderation, data analysis and bulk content generation. Bad fits are anything interactive. A user-facing chat needs the opposite: streaming, which shows output as it arrives and makes the application feel more responsive, and which a batch can't do.

Once the free wins are used up, lowering effort is the first trade-off to try when costs are too high and quality is fine. Effort sets how many tokens the model spends on its reply, its thinking and its tool calls; the full picture is in [Effort: the accuracy-latency dial within one model](lesson:3.3). As a cost lever it saves a lot and costs real quality. At low, Claude Opus 5.5's typical task took 84% less time than at medium on DRACO, and scored 13.3 points lower. Moving steps to a smaller model is the other trade-off; how to design tiered and multi-model systems is in [Model tiering and multi-model designs](lesson:2.1). As an optimisation, measure it as cost per completed task, not cost per token. A cheaper model that fails more often and needs retries or fixes can cost more per finished task. max_tokens is a hard limit on total output, thinking plus response text, so it bounds the worst case. It doesn't set a target. Setting it too low is the common mistake: attempts end with stop_reason: max_tokens and the work is lost. The fix is to raise it to 64,000. In Anthropic's tests only 2 of about 14,000 turns went past that, and cost per solved task stayed about the same, because a model that doesn't need the room doesn't use it.

Agent loops have a different risk: most runs are cheap, and a few are very expensive. Bound those with a Claude Managed Agents session budget, plus a workspace spend limit as the account-wide backstop. On newer models you can also give the model an explicit budget through task budgets, which are in beta. When the clock matters more than the bill, tell the model that time matters and show it the elapsed time. In Anthropic's tests that cut run time by 7% to 47% for a few points of score.

When you can check an outcome with tests or a verifier, the cheapest point on the effort curve isn't any fixed setting. Run everything cheaply and spend more only on the attempts that failed. On Claude Opus 5.5's SWE-bench Pro runs, 13% of tasks failed at low. Re-running those at high gave a slightly higher pass rate than running everything at high, for a little over half the cost. Adopt the policy for the savings, not the gain in pass rate: re-running the failures of an all-high run scores about the same.

max_tokens เป็นฮาร์ดแคป ไม่ใช่เป้าหมาย เพิ่มต้นทุนเหลือ 64,000 ต่องานที่แก้ไขได้เท่าๆ กัน และหยุดความพยายามไม่ให้ถูกตัดออก
max_tokens is a hard cap, not a target. Raising it to 64,000 left cost per solved task about the same and stopped attempts from being cut off.
