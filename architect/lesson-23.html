Retrieval matched to data shape — No retrieval method is best everywhere. Pick it from what the corpus contains and how users ask: put the corpus in the prompt if it fits, use BM25 for exact identifiers, embeddings for meaning, a weighted blend for mixed traffic, and agent-driven tool search when an index would go stale.

การเรียกดูข้อมูลมีอยู่เพราะบาง corpora มีขนาดใหญ่เกินไปสําหรับ

หน้าต่างบริบท ดังนั้นคําถามการออกแบบแรกคือว่าคุณมีหรือไม่ ฐานความรู้ที่มีโทเค็นน้อยกว่า 200,000 รายการประมาณ 500 หน้า สามารถเข้าไปในทั้งหมดของพร้อมท์ได้ จากนั้นจะไม่มีการแบ่งส่วน ไม่มีดัชนีที่ต้องรักษาให้เป็นปัจจุบัน และไม่มีขั้นตอน

การเรียกดูข้อมูลที่อาจส่งคืนข้อความผิด

Prompt caching is what makes the full-context option cheap. The first request processes the whole prompt and caches the prefix. Later requests that start with the same prefix reuse the cached version, which cuts processing time and cost. Anthropic reports that caching frequently used prompts cuts latency by more than 2x and cost by up to 90%. A handbook that every conversation reads is the ideal case, because the prefix is identical on every request.

Fitting in the window sets an upper limit. It does not mean you should fill the window. As the token count grows, accuracy and recall degrade, so what you put in context matters as much as how much room there is. Once the knowledge base grows past what fits, you need a retrieval method that scales, and the rest of this lesson is about choosing one.

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Exam Trap: Any knowledge base used for grounding needs a RAG pipeline with chunking and a vector index. (ทำไมถึงผิด): A corpus under about 200,000 tokens (about 500 pages) can go into the prompt whole, and prompt caching keeps that fast and cheap. Build retrieval only when the corpus does not fit.

คำแปลโจทย์: ผู้ช่วยภายในมีพื้นฐานอยู่บนคำถามที่พบบ่อยเกี่ยวกับผลิตภัณฑ์ 150 หน้าที่อ่านทุกการสนทนา ปีหน้าทีมงานวางแผนที่จะเพิ่มเอกสารทางวิศวกรรมประมาณ 2,000 หน้า แผนใดเหมาะกับคำแนะนำมากที่สุด?
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Official Explanation (คำอธิบายเฉลย):

The two basic retrievers fail in opposite ways. Embeddings turn text into vectors so that chunks close in meaning to the query rank high, even when they use different words. They are good at semantic relationships, but they can miss an exact match that matters.

BM25 adds a correction for document length and a saturation function on term frequency, so common words cannot dominate the ranking. That makes it strong wherever queries carry unique identifiers or technical terms.

Take the query "Error code TS-999" against a technical support database. An embedding model may return content about error codes in general and miss the one page about TS-999. The reverse also holds: a question phrased in the user's own words, with none of the document's vocabulary, gives BM25 nothing to match, while embeddings find it through meaning.

6. The same logic for tool catalogs and long sessions

Tool definitions are a corpus too, and the first question is the same: do they fit? Tool search marks definitions with defer_loading: true, so they enter context only when Claude finds them by searching. It is a form of [progressive discovery vs monolithic context](lesson:3.8). It comes in two built-in variants, tool_search_tool_regex_20251119 and tool_search_tool_bm25_20251119.

Tool search adds a search step before each tool call. It only pays off when the context saved and the gain in tool-selection accuracy outweigh that extra latency. Typical signals are definitions totalling more than 10K tokens or more than ten tools. Even then, keep your 3–5 most-used tools non-deferred so Claude can call them without searching. Eight small tools that nearly every request uses fall well below that threshold, so load them directly. Deferring them, with regex or BM25 search or behind a deferred

MCP toolset, would add a search before every call Claude was going to make anyway.

Matching on meaning works for tools the same way it works for chunks. Both built-in variants match on words or patterns. When tool descriptions are short and related only through an embedding space, BM25 has too few shared words to match, and broad regex wildcards do not capture meaning either. Instead, build a custom search tool that queries your embeddings index and returns tool_reference blocks in its tool_result. Every tool it references must still be defined in the top-level tools array, normally with defer_loading: true.

Tool definitions are a corpus too, and the first question is the same: do they fit? Tool search marks definitions with defer_loading: true, so they enter context only when Claude finds them by searching. It is a form of [progressive discovery vs monolithic context](lesson:3.8). It comes in two built-in variants, tool_search_tool_regex_20251119 and tool_search_tool_bm25_20251119.

Tool search adds a search step before each tool call. It only pays off when the context saved and the gain in tool-selection accuracy outweigh that extra latency. Typical signals are definitions totalling more than 10K tokens or more than ten tools. Even then, keep your 3–5 most-used tools non-deferred so Claude can call them without searching. Eight small tools that nearly every request uses fall well below that threshold, so load them directly. Deferring them, with regex or BM25 search or behind a deferred MCP toolset, would add a search before every call Claude was going to make anyway.

Matching on meaning works for tools the same way it works for chunks. Both built-in variants match on words or patterns. When tool descriptions are short and related only through an embedding space, BM25 has too few shared words to match, and broad regex wildcards do not capture meaning either. Instead, build a custom search tool that queries your embeddings index and returns tool_reference blocks in its tool_result. Every tool it references must still be defined in the top-level tools array, normally with defer_loading: true.

A long agent session can outgrow the window by itself. A research agent that retrieves and discusses documents for hours builds up a history that, like an oversized corpus, eventually stops fitting. For long-running conversations and agentic workflows, server-side compaction is the main way to manage this. It lets the session continue past the limit without the agent losing its earlier findings. Other fixes make things worse. The context window holds both the history and the new output, so raising max_tokens leaves less room for history. Re-uploading earlier documents on every turn fills the window faster. More on managing the window in [context window management](lesson:2.4).
