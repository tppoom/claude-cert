Retrieval matched to data shape — No retrieval method is best everywhere. Pick it from what the corpus contains and how users ask: put the corpus in the prompt if it fits, use BM25 for exact identifiers, embeddings for meaning, a weighted blend for mixed traffic, and agent-driven tool search when an index would go stale.

คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Retrieval exists because some corpora are too big for the context window. So the first design question is whether yours is. A knowledge base under 200,000 tokens, about 500 pages, can go into the prompt whole. Then there is no chunking, no index to keep fresh, and no retrieval step that can return the wrong passage.

Prompt caching is what makes the full-context option cheap. The first request processes the whole prompt and caches the prefix. Later requests that start with the same prefix reuse the cached version, which cuts processing time and cost. Anthropic reports that caching frequently used prompts cuts latency by more than 2x and cost by up to 90%. A handbook that every conversation reads is the ideal case, because the prefix is identical on every request.

Fitting in the window sets an upper limit. It does not mean you should fill the window. As the token count grows, accuracy and recall degrade, so what you put in context matters as much as how much room there is. Once the knowledge base grows past what fits, you need a retrieval method that scales, and the rest of this lesson is about choosing one.

The two basic retrievers fail in opposite ways. Embeddings turn text into vectors so that chunks close in meaning to the query rank high, even when they use different words. They are good at semantic relationships, but they can miss an exact match that matters.

BM25 is a lexical ranking function: it looks for the exact words or phrases in the query. It builds on TF-IDF, which scores how important a word is to one document within a collection. BM25 adds a correction for document length and a saturation function on term frequency, so common words cannot dominate the ranking. That makes it strong wherever queries carry unique identifiers or technical terms.

Take the query "Error code TS-999" against a technical support database. An embedding model may return content about error codes in general and miss the one page about TS-999. BM25 searches for that exact string and finds it. The reverse also holds: a question phrased in the user's own words, with none of the document's vocabulary, gives BM25 nothing to match, while embeddings find it through meaning.

Embedding retrieval has one setting that is easy to get wrong: input_type. Set it to query for user questions and to document for corpus text. Each value prepends its own instruction before embedding, which gives better vectors for retrieval. Leaving it out or setting it to None throws that gain away.

Hybrid search runs both retrievers and merges what they find. The standard pipeline:

1. Split the corpus into chunks, usually a few hundred tokens or fewer. 2. Build TF-IDF encodings and semantic embeddings for every chunk. 3. Take the top chunks by exact match with BM25. 4. Take the top chunks by semantic similarity with embeddings. 5. Combine and deduplicate the two lists using rank fusion. 6. Add the top-K chunks to the prompt.

The fusion step is where you tune for your data. Anthropic's reference implementation takes the top 150 candidates from each retriever and merges them with weighted Reciprocal Rank Fusion. The default is 80% weight on semantic search and 20% on BM25, and the weights are meant to be tuned. A corpus full of function names, part numbers or error codes calls for more BM25 weight. A corpus where users paraphrase calls for more semantic weight.

Even at 80/20 the lexical side does real work. In a codebase evaluation, BM25 still supplied about 39–45% of the final results after fusion, depending on how many results were kept. Code is full of exact identifiers, and those are the queries embeddings miss.

The embedding side can be matched to the data as well. Domain-specific models exist for code retrieval and agentic coding (voyage-code-4), legal work (voyage-law-2) and finance (voyage-finance-2). Providers that allow continued training on private data can improve results on unusual vocabularies. Before you add a second retriever to cover vocabulary a general model handles badly, check whether a domain model already covers it.

Beyond plain hybrid search there are two more layers you can add, and each one costs something. [Contextual retrieval (contextual embeddings and contextual BM25)](lesson:3.5) uses Claude to prepend a short, chunk-specific context to each chunk before it is indexed. [Reranking and how many chunks to pass](lesson:3.5) re-scores a large candidate set with a specialised model and keeps only the best few.

Contextual retrieval pays off when the data is made of chunks that lose their meaning once cut out of the document. SEC filings are the usual example. A chunk that says "The company's revenue grew by 3% over the previous quarter" names neither the company nor the period, so neither retriever can match it to a question about ACME in Q2 2023. The cost is paid once, at ingestion: about $1.02 per million document tokens with prompt caching, and about $3 for the whole codebase dataset above. Plain hybrid search needs no LLM pass at all, but you have to run and maintain Elasticsearch.

Reranking costs something on every query: roughly 100–200 ms of extra latency and about $0.002 per query in API fees. Within reranking there is a further trade-off. Scoring more candidates improves accuracy, and scoring fewer lowers latency and cost. Rerankers come in tiers too: rerank-3 is the most accurate, and rerank-3-lite is optimised for latency and cost.

The results suggest three typical choices. For high-volume, cost-sensitive traffic, contextual embeddings alone reach about 92% Pass@10 with no per-query cost. For a balanced production system, add hybrid search for about 93% without per-query fees. When maximum accuracy matters and some latency is acceptable, add reranking to reach about 95%. For most production systems the best performance per dollar comes from contextual embeddings.

Everything so far assumes an index built before any query arrives. Just-in-time retrieval drops that assumption. The agent keeps lightweight references such as file paths, stored queries and web links, and uses tools to load data into context only when it needs it. Claude Code works this way on large databases: it writes targeted queries, stores the results, and uses head and tail to inspect large outputs without ever loading the full objects into context.

This approach wins when the data changes faster than an index can be rebuilt. Claude Code's glob and grep read files as they are now, which avoids stale indexes and complex syntax trees in a codebase that is edited all day. The surroundings are also information: a test_utils.py file in a tests folder means something different from one in src/core_logic/. Folder structure, naming conventions and timestamps all help the agent decide what to open next.

The cost is speed and reliability. Exploring at run time is slower than looking up precomputed results. The agent also needs the right tools and guidance, or it will misuse tools, chase dead ends and fill its context with noise. That last risk is serious, because accuracy and recall drop as the token count grows.

Many systems combine the two. Claude Code loads its CLAUDE.md files into context at the start and greps for everything else. A mixed approach suits content that changes less often, such as legal or finance material: load the stable core up front for speed, and let the agent explore the rest when it needs to.

Tool definitions are a corpus too, and the first question is the same: do they fit? Tool search marks definitions with defer_loading: true, so they enter context only when Claude finds them by searching. It is a form of [progressive discovery vs monolithic context](lesson:3.8). It comes in two built-in variants, tool_search_tool_regex_20251119 and tool_search_tool_bm25_20251119.

Tool search adds a search step before each tool call. It only pays off when the context saved and the gain in tool-selection accuracy outweigh that extra latency. Typical signals are definitions totalling more than 10K tokens or more than ten tools. Even then, keep your 3–5 most-used tools non-deferred so Claude can call them without searching. Eight small tools that nearly every request uses fall well below that threshold, so load them directly. Deferring them, with regex or BM25 search or behind a deferred MCP toolset, would add a search before every call Claude was going to make anyway.

Matching on meaning works for tools the same way it works for chunks. Both built-in variants match on words or patterns. When tool descriptions are short and related only through an embedding space, BM25 has too few shared words to match, and broad regex wildcards do not capture meaning either. Instead, build a custom search tool that queries your embeddings index and returns tool_reference blocks in its tool_result. Every tool it references must still be defined in the top-level tools array, normally with defer_loading: true.

A long agent session can outgrow the window by itself. A research agent that retrieves and discusses documents for hours builds up a history that, like an oversized corpus, eventually stops fitting. For long-running conversations and agentic workflows, server-side compaction is the main way to manage this. It lets the session continue past the limit without the agent losing its earlier findings. Other fixes make things worse. The context window holds both the history and the new output, so raising max_tokens leaves less room for history. Re-uploading earlier documents on every turn fills the window faster. More on managing the window in [context window management](lesson:2.4).
