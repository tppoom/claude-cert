1. ทำความเข้าใจและวาง Map ขั้นตอน Business Process ก่อนเลือก Model

โจทย์ทางธุรกิจมักเริ่มจากปัญหาหน้างานจริง ไม่ใช่ Spec ที่ชัดเจน เช่น Ticket ถูกส่งไปผิดทีม, คิว Support ล้นช่วงเปิดตัว Product หรือฝ่ายกฎหมายเสียเวลาหลายชั่วโมงเพื่อสรุปสัญญา การถามว่า "ควรใช้ Model ไหนดี?" ตั้งแต่แรกจึงเป็นการข้ามปัญหาที่แท้จริง: จุดไหนใน Process ปัจจุบันที่เป็นคอขวด? ในคู่มือการทำ Ticket Routing ของ Anthropic จึงเน้นให้เริ่มจากการสำรวจระบบเดิมก่อนเขียน Prompt เสมอ โดยดูว่าทีม Support ปัจจุบันกระจาย Ticket อย่างไร, เกณฑ์กำหนด SLA คืออะไร และการ Route นั้นเป็นการส่งหา Support Tier ทั่วไปหรือ Specialist กันแน่

คำถามสำคัญที่สุดคือ Automation เดิมหลุดตรงไหน? หากมี Rules หรือ Workflows อยู่แล้ว ต้องหาให้เจอว่ามัน Fail ตรงไหน และทีมจัดการ Edge Cases หรือ Ticket ที่กำกวมอย่างไร เพราะจุดที่ระบบเดิมพังมักเป็นจุดที่สร้าง Value ได้สูงสุด เช่น Rule แบบจับ Keyword ส่ง Ticket ทุกใบที่มีคำว่า "payment" ไปแผนก Billing จะใช้ได้ดีจนกว่าลูกค้าจะแจ้งบั๊กบนหน้า Payment Page ซึ่งจริง ๆ แล้วเป็นปัญหา Software ปัญหานี้จึงต้องพึ่งคนมาแก้ Routing ด้วยตัวเองทุกครั้ง งาน Manual ที่ต้องคอยแก้นี้คือต้นทุนแฝง และเป็นจุดที่ Claude ควรเข้ามาทำแทน

เมื่อทำ Map ของ Process เสร็จแล้ว ให้แยก Interaction ออกเป็น Tasks ย่อย ๆ แม้ Customer Support Chatbot จะดูเหมือนเป็น Feature เดียว แต่เบื้องหลังประกอบด้วย Tasks หลายอย่าง ตั้งแต่การตอบคำถาม, การดึงข้อมูล (Information Retrieval) ไปจนถึงการ Execute Actions ตามที่ขอ ตัวอย่างเคสของ Anthropic ใน Chatbot ประกันภัยรถยนต์: ลูกค้าเริ่มแชท, ถามความคุ้มครองของรถ EV, ชวนคุยนอกเรื่อง แล้วขอใบเสนอราคา Tasks ที่ต้องจัดการจึงมีทั้ง การทักทาย (Greeting), การให้ข้อมูล Product, การคุมบทสนทนา (Conversation Management เพื่อให้อยู่ในเรื่องประกัน) และการสร้างใบเสนอราคาผ่าน API โดยแต่ละ Task จะต้องมี Prompt และ Evaluation ของตัวเอง คุณไม่สามารถเทส "Chatbot" แบบภาพรวมก้อนเดียวได้ แต่สามารถเทสเจาะจงได้ว่า ขั้นตอนสร้างใบเสนอราคานั้นถามคำถามคัดกรองคุณสมบัติได้ถูกต้องหรือไม่

Not every step in the map belongs to an LLM. Claude earns a step when the work involves language, judgement or variety that rigid systems handle badly. For ticket classification, Anthropic lists concrete signals that favour Claude over traditional ML:

- Labelled data is scarce: Claude can classify with a few dozen labelled examples, where traditional ML needs massive labelled datasets. - Categories change often: Claude adapts to new or redefined classes without extensive relabelling. - Inputs are unstructured, or classes are defined by conditions rather than by examples. - Decisions must be explainable: Claude can give human-readable reasons for each classification. - Tickets arrive in many languages, and you do not want a separate model for each one.

In support chat, the signals relate to volume and coverage. Claude handles a large number of similar questions efficiently, which frees human agents for complex issues. It also provides round-the-clock coverage and absorbs sudden spikes without new hires. If none of these apply, Claude may not be the right tool for the step. A stable, well-labelled, single-language classification problem that a traditional model already solves is one example.

The model's limits shape the design too. A language model produces text by predicting the next token, so every answer is the most plausible continuation, not a looked-up fact. That works well for summaries and classifications, and it fails in predictable places: a citation that reads correctly but does not exist, a precise figure or name the model never learned, anything that happened after its knowledge cutoff, and details specific to your company that were never in its training data. Where coverage is thin, the model still writes fluent text, so fabrication looks the same as accuracy. A step that needs current or company-specific facts is therefore designed with retrieval, web search or a tool from the start. Any step whose output cannot be checked needs a human or a programmatic gate after it.

ระดับสูงสุดคือ Agents: ระบบที่ LLM กำหนดทิศทางการทำงาน เลือกลำดับขั้นตอน และตัดสินใจเรียกใช้ Tools ด้วยตัวเองเพื่อบรรลุเป้าหมาย Agents จะได้เปรียบเมื่องานนั้นไม่สามารถรู้ขั้นตอนล่วงหน้าได้ และจำเป็นต้องอาศัยการตัดสินใจที่ยืดหยุ่นโดย Model ในสเกลใหญ่ เช่น งานแก้ไข Code ที่ไม่รู้ล่วงหน้าว่าจะกระทบไฟล์ใดบ้าง

The rule for solution shape is to use the simplest one that works, and add complexity only when evidence shows it is needed. Sometimes that means not building an agentic system at all. Agentic systems often trade latency and cost for better task performance, so every step up has to pay for itself. From simplest to most complex, there are three shapes.

The base is the augmented LLM: one call to a model that has retrieval, tools and memory. Retrieval-augmented generation (RAG) is this shape with a retrieval step that adds relevant documents to the prompt. Ticket routing, for example, is a classification task. One well-prompted call that returns its reasoning and an intent label solves it.

Next come workflows, where LLMs and tools are orchestrated through predefined code paths. Your code fixes the sequence, for example classify, then hand off to a specialised prompt. This makes the system predictable and consistent for well-defined tasks.

At the top are agents, where the LLM directs its own process and tool use and decides how to reach the goal. Agents win when the steps cannot be known in advance and flexible, model-driven decisions are needed at scale. A coding change that touches an unknown number of files is the typical case.

The process map tells you which shape you need. If the mapped steps are fixed and the same every time, code can sequence them, so build a workflow. If the number or order of steps depends on the input, the model has to decide, so build an agent. The specific workflow patterns, such as chaining, routing and orchestrator-workers, are compared in [architectural patterns](lesson:1.3).

Each shape points toward a natural build path. A single augmented call or a short workflow fits the Messages API, because many patterns take only a few lines of code there. Starting with the API directly also keeps the prompts and responses visible, so they are easier to debug than behind a framework's abstractions. An agent that needs file, shell and web tools inside your own service fits the Agent SDK. A workload that runs for minutes or hours, needs sandboxed cloud infrastructure, or should not require you to build a loop and sandbox at all fits Managed Agents. Managed Agents can also run sandboxes on your own infrastructure when compliance or data residency requires it.

Some business problems need no build at all. In the Claude apps, artifacts let a non-developer describe a tool in conversation and get a shareable interactive app without writing code. An internal team that needs a flashcard generator or a small form helper can start there. Engineering effort is better spent on the processes that need system integration.

Model choice comes last because it depends on what the mapped steps demand: capability, speed and cost. [Model selection trade-offs](lesson:2.1) covers this in depth. At the solution-design level, match each workload's profile to the tier built for it.

Read the requirements in a scenario as a profile and match it to a tier. Here are three common profiles:

- Haiku: high volume, tight latency, tight cost. Take a chat widget that must answer within a few hundred milliseconds at flash-sale volume, on a strict per-conversation budget. That profile points to Haiku. Haiku is still built for deployments needing strong reasoning, so multi-turn troubleshooting does not by itself push the workload up a tier. Ticket routing is the same profile: Haiku is the fastest and most cost-effective current model and handles high-volume classification well. - Opus: multi-hour autonomous work, correctness over cost. An agent that plans and runs a multi-hour refactor of a large legacy codebase, with few human checkpoints, fits Opus. Opus is built for long-running agentic coding and large-scale refactoring. Running many cheap parallel attempts or adding context does not make up for weaker reasoning on that work. - Sonnet: one default for everyday work. A company-wide default for code generation, data analysis, drafting and agentic tool use fits Sonnet. Sonnet balances speed and capability for everyday workloads without premium pricing on every call.

Effort is a setting, supported by several Claude models, that trades intelligence (how much reasoning the model applies) against latency and cost within a single model. Turning it down makes responses faster and cheaper, and turning it up buys more reasoning on hard problems, so tuning it is often a better lever than switching models.

For a new build, there are two ways to start testing. The cost-first path begins with Haiku, tests the use case thoroughly, and upgrades only to close a specific capability gap. The capability-first path begins with Opus for complex reasoning or high-autonomy agentic work, then lowers effort or moves to a smaller model as the workflow is optimised. The process map often uses both. A cheap tier handles bulk steps such as routing, and a stronger tier handles the few hard ones.

A solution is judged by whether it relieves the pain found in the process map, not by how well the model behaves in isolation. Good criteria are specific, measurable, achievable and relevant, as taught in [measurable success criteria](lesson:6.1). The relevance part matters most here: each criterion has to trace back to a business outcome that someone in the organisation already tracks.

The support guides keep two lists apart. Task criteria cover the model's work, such as intent-comprehension accuracy of 95% or higher, or 100% accuracy on generated quotes. Business-impact criteria cover the outcome the business pays for. For a support chatbot, that means a deflection rate of typically 70–80% of inquiries handled without a human, a CSAT of 4 out of 5 or higher, and a lower average handling time than human agents. For ticket routing, the business measures include a 10–20% improvement in tickets resolved per agent, an escalation rate below 20%, and a 10–15% reduction in cost per ticket.

Each task metric should explain how it moves a business metric. If it cannot, it is a vanity metric. Routing accuracy matters because misrouted tickets get escalated and handled twice. So report routing accuracy next to the escalation rate and cost per ticket it is meant to reduce. Define both lists with the support team that owns the process, not only with the engineers building the solution. That way the targets reflect the real shape of the work, including the edge cases the team already handles by hand.

    Messages API ให้การควบคุมสูงสุดเพราะคุณต้องเขียน Agent Loop และจัดการ Tools กับ Infrastructure เอง, Agent SDK จัดเตรียม Loop และ Tool Execution มาให้สำเร็จรูปแต่รันอยู่บน Process ที่คุณดูแลเอง, และ Managed Agents ยกภาระให้ Anthropic มากที่สุด โดย Anthropic จะเป็นผู้ดูแลทั้ง Loop, Tool Execution และ Runtime ทั้งหมด
  • •
    เมื่อเลือกระดับ Solution ได้แล้ว ขั้นต่อไปคือเลือก Build Path โดยจุดตัดสินใจหลักคือคุณต้องการดูแลและควบคุม Implementation เองมากน้อยแค่ไหน ตัวเลือกทั้ง 3 รูปแบบบน API มี Trade-off ระหว่างระดับการควบคุม (Control) กับภาระงานที่ยกให้ระบบจัดการ (Offload)

#5 5. เลือก Model Tier ให้เหมาะกับ Workload

อ่านเนื้อหา ↗
  • •
    สำหรับ Long-running agentic coding และ Large-scale refactoring การพยายามรัน Model เล็กขนานกันหลายรอบหรือการอัด Context เพิ่มไม่สามารถชดเชย Reasoning ที่ด้อยกว่าในงานประเภทนี้ได้ - Sonnet: ค่า Default มาตรฐานสำหรับงานทั่วไป ตอบโจทย์การเป็นตัวเลือกหลักระดับองค์กร ทั้ง Code generation, Data analysis, การร่างเนื้อหา และ Agentic tool use โดย Sonnet ให้ความสมดุลระหว่าง Speed และ Capability ในงานประจำวันโดยไม่ต้องจ่ายราคา Premium ในทุก API Call
  • •
    - Haiku: High volume, Tight latency, Tight cost เช่น Chat widget ที่ต้องตอบภายในไม่กี่ร้อย Milliseconds ในช่วง Flash sale ภายใต้เงื่อนไขควบคุม Cost ต่อบทสนทนาอย่างเข้มงวด Profile แบบนี้ชี้ตรงไปที่ Haiku
  • •
    Haiku ยังออกแบบมาสำหรับงานที่ต้องการ Strong reasoning ด้วย ดังนั้นเพียงแค่เป็น Multi-turn troubleshooting จึงไม่ได้หมายความว่าต้องขยับ Tier ขึ้นเสมอไป ส่วนงาน Ticket routing ก็อยู่ใน Profile นี้เช่นกัน โดย Haiku เร็วที่สุด คุ้มค่าที่สุด และจัดการ High-volume classification ได้ดีมาก - Opus: Multi-hour autonomous work, Correctness over cost เช่น Agent ที่ Plan และ Run งาน Refactor โค้ด Legacy ขนาดใหญ่ต่อเนื่องหลายชั่วโมงโดยมี Human checkpoint น้อยมาก งานนี้เหมาะกับ Opus ซึ่งออกแบบมา

#6 6. ผูก Success Criteria เข้ากับ Business Outcome

อ่านเนื้อหา ↗
  • •
    % (สัดส่วนเคสที่จบได้โดยไม่ต้องพึ่งคน), CSAT ≥ 4/5 และ Average handling time สั้นกว่ามนุษย์ ส่วนงาน Ticket routing ตัววัดทางธุรกิจคือ Agent แก้ไข Ticket ได้เพิ่มขึ้น 10
  • •
    ควรกำหนด Metric ทั้งสองกลุ่มร่วมกับทีม Support ซึ่งเป็น Process owner ไม่ใช่กำหนดโดยทีม Engineer ฝั่งพัฒนา Solution เพียง Single Agent เพื่อให้ Target สะท้อนภาพการทำงานจริง รวมถึง Edge cases ที่ทีมต้อง Manual เองอยู่ในปัจจุบัน
  • •
    การวัดผล Solution จะดูว่ามันช่วยแก้ Pain point ที่ระบุไว้ใน Process map ได้จริงหรือไม่ ไม่ได้ดูแค่ว่า Model ทำงานโดดๆ ได้ดีแค่ไหน Criteria ที่ดีต้อง Specific, Measurable, Achievable และ Relevant ตามหลัก [measurable success criteria](lesson:6.1) โดยจุดสำคัญที่สุดคือ Relevant นั่นคือ Metric ทุกตัวต้องสามารถ Trace กลับไปเป็น Business outcome ที่องค์กร Track อยู่แล้วได้
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (6 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
สิ่งที่ควรนำไปปรับใช้จริง? (ทำไมถึงสำคัญ): ไม่จริง: การปรับปรุง Process ไม่จำเป็นต้องรื้อทำใหม่ทั้งหมด ให้เลือกกระบวนการที่คุ้นเคย เช่น Invoice Approval, Onboarding หรือ Incident Triage แล้วดูว่าขั้นตอนไหนมีงาน Manual Rework ซ้ำซ้อนมากที่สุด จากนั้นวิเคราะห์ว่าจุดนั้นเป็นเรื่องของการตัดสินใจ (Judgement Call) หรือแค่การค้นหาข้อมูล (Lookup)
Apply it to your own work Pick a process you know well, such as invoice approval, onboarding or incident triage. Which step has the most manual rework today, and would a person describe that rework as a judgement call or a lookup?
✅

❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
ปฏิบัติกับ Customer Support Chatbot เป็น Task เดียว โดยใช้ Prompt เดียว และวัด Quality Score รวมเพียงค่าเดียว?
Treat a customer support chatbot as one task, with one prompt and one overall quality score.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Support Chat ประกอบด้วย Tasks ย่อยหลายส่วน (Greeting, Product Information, Conversation Management, Quote Generation) ต้องแยก Interaction ออกเป็นแต่ละ Tasks เพื่อให้สามารถเขียน Prompt ควบคุมและทำ Evaluation วัดผลแยกตามหน้าที่ได้อย่างแม่นยำ
Support chat is several tasks: greeting, product information, conversation management and quote generation. Break the interaction into tasks so you can prompt and evaluate each one.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
เมื่อเจอปัญหาทางธุรกิจ ควร Rebuild กระบวนการทั้งหมดใหม่ด้วย LLM?
On the Exam:: When a scenario describes the business problem, look for the answer that changes the painful step and leaves the working steps alone. Rebuilding the whole process around an LLM is rarely the intended answer.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: ข้อสอบมักลวงด้วย Solution ที่เปลี่ยนทั้งระบบ ให้มองหาคำตอบที่เลือกแก้เฉพาะขั้นตอนที่เป็น Pain Point และคงขั้นตอนเดิมที่ทำงานได้ดีอยู่แล้วไว้ การรื้อทั้ง Process มาใช้ LLM แทบไม่เคยเป็นคำตอบที่ถูกต้องในการออกแบบระบบจริง
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
A business process that touches several systems needs an autonomous agent.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: งาน Business Process ที่ต้องต่อเชื่อมกับหลายระบบจำเป็นต้องใช้ Autonomous Agent เสมอไป — ควรเริ่มจาก Solution ที่เรียบง่ายที่สุดก่อน หากขั้นตอนการทำงานตายตัวและชัดเจน การใช้ Workflow ที่เขียนด้วย Code จะคาดเดาผลลัพธ์ได้ดีกว่าและประหยัดกว่ามาก หรือบางปัญหาก็จบได้ด้วย Augmented LLM เพียงครั้งเดียว ควรเลือกใช้ Agent เฉพาะเมื่องานมีขั้นตอนที่ไม่แน่นอนและขึ้นอยู่กับ Input เท่านั้น
Start with the simplest solution. When the steps are fixed and known, a workflow in code is more predictable and cheaper, and many problems need only one augmented LLM call. Choose an agent only when the steps depend on the input.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
Managed Agents is just the Agent SDK with a different name, so the choice between them does not matter.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Managed Agents ก็คือ Agent SDK แค่เปลี่ยนชื่อเรียก จึงเลือกใช้อันไหนก็ได้ไม่ต่างกัน — ทั้งสองตัวต่างกันตรง 'ใครเป็นผู้ดูแล Runtime' โดย Agent SDK จะรัน Agent Loop และ Tools บน Process หรือ Server ที่คุณดูแลเอง ส่วน Managed Agents ทาง Anthropic จะเป็น Host ดูแลทั้ง Loop, Tool Execution และ Runtime ให้ทั้งหมด
They differ in who operates the runtime. The Agent SDK runs the agent loop and tools in a process you operate. Managed Agents has Anthropic host the loop, tool execution and runtime.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Workload ใดก็ตามที่มี Multi-turn reasoning จำเป็นต้องใช้ Sonnet หรือ Opus เสมอ แม้จะมีข้อจำกัดเรื่อง Latency และ Cost?
Any workload that involves multi-turn reasoning needs Sonnet or Opus, even under tight latency and cost limits.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Haiku ถูกวาง Position มาสำหรับงาน Real-time, High volume และ Cost-sensitive ที่ยังคงต้องการ Strong reasoning ดังนั้น Support chat แบบ Multi-turn troubleshooting ที่ต้องการความเร็วและคุมงบ จึงควรเริ่มต้นด้วย Haiku ก่อน แล้วค่อย Upgrade ต่อเมื่อพบ Capability gap ที่เจาะจงเท่านั้น
Haiku is positioned for real-time, high-volume, cost-sensitive deployments that still need strong reasoning. A fast, budget-bound support chat with troubleshooting fits Haiku first, with an upgrade only for a specific capability gap.
