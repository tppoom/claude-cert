💡 แนวคิดหลักสำคัญ (Key Concept)

Context window as one shared budget — The context window is a single token budget. The system prompt, tool definitions, the whole message history with its tool results, and the turn's output and thinking all draw on it. Caching changes what those tokens cost you, but they still take up space in the window.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "What fills the context window" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The context window is the model's working memory for a single request. Everything Claude can refer to while it answers sits inside it, and so does the answer it is writing. The request side holds the system prompt, every message in messages (tool results, images and documents included) and your tool definitions. The output Claude generates for the turn counts as well, and that includes its extended thinking. Treat these as one budget: a 30,000-token tool catalogue leaves 30,000 fewer tokens for conversation, whether or not any tool gets called.

Window sizes are large now. Claude Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.1 and several others have a 1M-token window and can produce up to 128k output tokens in one request. Older models, such as the deprecated Claude Sonnet 4.5, have 200k. On 1M-window models the full window is the default and is billed at standard pricing. The exception is Claude Haiku 5.5, where prompts over 100,000 tokens cost more.

A bigger window doesn't mean you should fill it. Accuracy and recall get worse as the token count grows, so a sensible budget stays well under the ceiling. [Context limits and context rot](lesson:5.2) explains that degradation. In this lesson it matters because it is the reason to measure context and trim it long before the hard limit.

The API handles two overflow cases differently.

- Input alone is larger than the window. Every model rejects the request with a 400 invalid_request_error ("prompt is too long"). Generation never begins. - **Input fits, but input plus max_tokens doesn't.** On Claude 4.5 models and newer (Opus 4.8 included), the request is accepted. If generation then reaches the window limit, it stops with stop_reason: "model_context_window_exceeded". Earlier models return a validation error unless you opt in with the model-context-window-exceeded-2025-08-26 beta header.

In neither case does the API rescue the request for you. It doesn't drop old turns and it doesn't enlarge the window for one call. Some chat interfaces such as claude.ai manage the window on a rolling first-in, first-out basis, but a plain API request keeps every previous turn in full. If your code doesn't check stop_reason, it will treat a truncated answer as a finished one.

Thinking draws on two budgets at once. In the turn where it's generated, thinking is part of max_tokens, is billed as output and counts toward rate limits. With adaptive thinking, Claude decides how much to think, so thinking usage changes from request to request. What happens to those blocks on later turns depends on the model.

So on a model that keeps thinking, a block is paid for twice in different ways. It is billed once as output when it's generated, and then billed as input on every later request that carries it. Over a 40-turn session that adds up. Thinking block clearing (taught in the context editing lesson) lets you override the default in either direction.

Tool use adds one hard rule. When you send back a tool result, you must include the thinking block from that assistant turn, complete and unmodified, with its signature. This is the only case where returning thinking is required. The API checks the cryptographic signature and returns an error if the block has been changed. Once the tool cycle ends and a new user turn starts, that block no longer has to stay in context.

Some models also see their own budget. Claude Sonnet 5, Sonnet 4.6, Sonnet 4.5 and Haiku 4.5 have context awareness. The API puts the total window in a tag and sends a remaining-capacity warning after each tool call, so the model can pace a long task. Opus 4.7 and later, Sonnet 5.5, Haiku 5.5 and the Fable and Mythos models don't get these tags. On those models you can set an explicit budget with task budgets, which are in beta.

Pre-counting has a few limits worth knowing.

- It returns invalid_request_error for server tools such as web search and code execution, for the MCP connector, and for image or document blocks given as a url or file source. 5.Cutting what tools cost in context

การแยกงานให้ Subagents ทำจะช่วยยกระดับผลลัพธ์ให้ดีขึ้นใน 3 สถานการณ์หลัก เท่านั้น หากอยู่นอกเหนือจากนี้ การประสานงานมักจะสร้างต้นทุนมากกว่าประโยชน์:

1. ป้องกัน Context Pollution (ผลลัพธ์เครื่องมือมีขนาดใหญ่มาก): เมื่อการทำงานย่อยสร้างโทเค็นที่ไม่เกี่ยวข้องมากกว่า 1,000 โทเค็น (เช่น อ่านเอกสารหนาๆ หรือค้นหาเว็บ) การให้ Subagent ทำจะช่วยกักกันข้อมูลส่วนเกินไม่ให้รบกวนการตัดสินใจของ Orchestrator
2. เมื่องานสามารถทำพร้อมกันได้ (Parallelization): หากงานย่อยหลายชิ้นเป็นอิสระต่อกัน (เช่น ตรวจสอบความปลอดภัย 3 ด้านคนละมุม) การส่งให้ Subagents ทำงานขนานกันจะช่วยลด Latency รวมของระบบได้อย่างมหาศาล
3. เมื่องานต้องการเครื่องมือเฉพาะทางสูง (Tool Specialization): การใส่เครื่องมือให้เอเจนต์ตัวเดียวมากเกินไป (Capability Bloat) จะทำให้ความแม่นยำในการเลือกเครื่องมือลดลง การแยก Subagent ตามหน้าที่ช่วยให้แต่ละตัวมีเครื่องมือเฉพาะทางเพียง 3-5 ชิ้นเท่านั้น

Incorrect. Shortening tool names yields negligible savings and is not a documented strategy for managing tool-related context cost compared to the other approaches.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Cutting what tools cost in context" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

In agents, most of the window goes to tools. Tool definitions are sent on every request, and each call leaves a tool_result in the history. Each of the four techniques below targets a different source of that pressure, so start by finding out where your tokens are going.

Take an agent with 45 tools. Instead of sending every schema upfront, tool search sends a single tool_search tool and Claude finds the others when it needs them. That costs one extra turn of latency and removes most of the baseline definition load. A run of small sequential calls is better handled by programmatic tool calling: Claude writes the chain as one code block that runs in a sandbox, so the intermediate results never come back into the conversation. The definitions you still send can be cached, so repeat requests pay the cache-read rate. Caching only makes the definitions cheaper. They still take up window space.

Some fixes sound good and miss these cost sources. Moving to a 1M-token model, raising max_tokens, or shortening tool names leaves the definition load, the roundtrips and the repeated pricing where they were, and a larger window filled with the same tools still suffers context rot. Another fix is structural: hand verbose exploration to a subagent with its own window, so only its condensed answer reaches the main thread. [Coordinator pattern and isolated subagent context](lesson:1.4) covers how that pattern works.
