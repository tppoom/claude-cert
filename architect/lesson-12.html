1. สิ่งที่เติมเต็ม Context Window

Context Window คือหน่วยความจําที่ทํางานของโมเดลสําหรับคําขอเดียว ทุกสิ่งที่ Claude สามารถอ้างอิงได้ในขณะที่ตอบกลับจะอยู่ในนั้น เช่นเดียวกับคําตอบที่มันกําลังเขียน ด้านคําขอมี Prompt ของระบบ ทุกข้อความในข้อความ (ผลลัพธ์ของเครื่องมือ ภาพและเอกสารรวมอยู่ด้วย) และคําจํากัดความของเครื่องมือของคุณ ผลลัพธ์ที่ Claude สร้างขึ้นสําหรับการหมุนเวียนก็นับด้วย ซึ่งรวมถึง Extended Thinking ถือว่าสิ่งเหล่านี้เป็นงบประมาณเดียว: แค็ตตาล็อกเครื่องมือที่มีโทเค็น 30,000 รายการจะเหลือโทเค็นสําหรับการสนทนาน้อยลง 30,000 รายการ ไม่ว่าจะมีการเรียกใช้เครื่องมือใดๆ หรือไม่ก็ตาม

The context window is the model's working memory for a single request. Everything Claude can refer to while it answers sits inside it, and so does the answer it is writing. The request side holds the system prompt, every message in messages (tool results, images and documents included) and your tool definitions. The output Claude generates for the turn counts as well, and that includes its extended thinking. Treat these as one budget: a 30,000-token tool catalogue leaves 30,000 fewer tokens for conversation, whether or not any tool gets called.

Window sizes are large now. Claude Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.1 and several others have a 1M-token window and can produce up to 128k output tokens in one request. Older models, such as the deprecated Claude Sonnet 4.5, have 200k. On 1M-window models the full window is the default and is billed at standard pricing. The exception is Claude Haiku 5.5, where prompts over 100,000 tokens cost more.

A bigger window doesn't mean you should fill it. Accuracy and recall get worse as the token count grows, so a sensible budget stays well under the ceiling. [Context limits and context rot](lesson:5.2) explains that degradation. In this lesson it matters because it is the reason to measure context and trim it long before the hard limit.

Thinking draws on two budgets at once. In the turn where it's generated, thinking is part of max_tokens, is billed as output and counts toward rate limits. With adaptive thinking, Claude decides how much to think, so thinking usage changes from request to request. What happens to those blocks on later turns depends on the model.

So on a model that keeps thinking, a block is paid for twice in different ways. It is billed once as output when it's generated, and then billed as input on every later request that carries it. Over a 40-turn session that adds up. Thinking block clearing (taught in the context editing lesson) lets you override the default in either direction.

Tool use adds one hard rule. When you send back a tool result, you must include the thinking block from that assistant turn, complete and unmodified, with its signature. This is the only case where returning thinking is required. The API checks the cryptographic signature and returns an error if the block has been changed. Once the tool cycle ends and a new user turn starts, that block no longer has to stay in context.

Some models also see their own budget. Claude Sonnet 5, Sonnet 4.6, Sonnet 4.5 and Haiku 4.5 have context awareness. The API puts the total window in a <budget:token_budget> tag and sends a remaining-capacity warning after each tool call, so the model can pace a long task. Opus 4.7 and later, Sonnet 5.5, Haiku 5.5 and the Fable and Mythos models don't get these tags. On those models you can set an explicit budget with task budgets, which are in beta.

Measure in two places. Before a call, the token counting endpoint takes the same structured input as a message request (system prompt, tools, images, PDFs) and returns the input token count. After a call, the response's usage field reports what the request actually consumed. With prompt caching, the input is split across input_tokens, cache_read_input_tokens and cache_creation_input_tokens, and all three count toward the window. A dashboard that adds up only input_tokens will underreport context use badly once caching is on.

Pre-counting has a few limits worth knowing.

- It returns invalid_request_error for server tools such as web search and code execution, for the MCP connector, and for image or document blocks given as a url or file source. Send images and PDFs as base64 to count them. For server-tool requests, use the usage object on the real response. - It gives an estimate without caching logic. cache_control is accepted but has no effect. - It counts with the tokenizer of the model you pass. The Fable and Mythos models use the tokenizer introduced with Opus 4.7, which counts roughly 30 percent more tokens than models before Opus 4.7. Before a migration, count the same request on both models and compare.

The endpoint is free, but it has its own requests-per-minute limits by usage tier (5,000 at Start).

In agents, most of the window goes to tools. Tool definitions are sent on every request, and each call leaves a tool_result in the history. Each of the four techniques below targets a different source of that pressure, so start by finding out where your tokens are going.

Take an agent with 45 tools. Instead of sending every schema upfront, tool search sends a single tool_search tool and Claude finds the others when it needs them. That costs one extra turn of latency and removes most of the baseline definition load. A run of small sequential calls is better handled by programmatic tool calling: Claude writes the chain as one code block that runs in a sandbox, so the intermediate results never come back into the conversation. The definitions you still send can be cached, so repeat requests pay the cache-read rate. Caching only makes the definitions cheaper. They still take up window space.

Some fixes sound good and miss these cost sources. Moving to a 1M-token model, raising max_tokens, or shortening tool names leaves the definition load, the roundtrips and the repeated pricing where they were, and a larger window filled with the same tools still suffers context rot. Another fix is structural: hand verbose exploration to a subagent with its own window, so only its condensed answer reaches the main thread. [Coordinator pattern and isolated subagent context](lesson:1.4) covers how that pattern works.

    บางรุ่นก็เห็นงบประมาณของตัวเองด้วย Claude Sonnet 5, Sonnet 4.6, Sonnet 4.5 และ Haiku 4.5 มีการรับรู้บริบท API จะใส่หน้าต่างทั้งหมดลงใน<budget:token_budget>แท็กและส่งคำเตือนความจุที่เหลือหลังจากการเรียกใช้เครื่องมือแต่ละครั้งเพื่อให้โมเดลสามารถก้าวไปสู่งานที่ยาวนานได้ Opus 4.7 และใหม่กว่า, Sonnet 5.5, Haiku 5.5 และรุ่น Fable และ Mythos ไม่ได้รับแท็กเหล่านี้ในรุ่นเหล่านั้นคุณสามารถกำหนดงบประมาณที่ชัดเจนด้วยงบประมาณงานซึ่งอยู่ในรุ่นเบต้า
  • •
    การคิดใช้งบประมาณสองรายการพร้อมกัน ในขั้นตอนที่มันถูกสร้างขึ้น การคิดเป็นส่วนหนึ่งของ max_tokens จะถูกเรียกเก็บเงินเป็นเอาต์พุตและนับรวมในขีดจำกัดอัตรา ด้วยการคิดแบบปรับเปลี่ยน Claude ตัดสินใจว่าจะคิดมากเพียงใด
  • •
    การใช้ความคิดจึงเปลี่ยนจากการร้องขอไปสู่การร้องขอ จะเกิดอะไรขึ้นกับบล็อกเหล่านั้นในเทิร์นต่อมาขึ้นอยู่กับรุ่น

#4 4. การวัดโทเค็นก่อนและหลังคําขอ

อ่านเนื้อหา ↗
  • •
    วัดในสองตําแหน่ง ก่อนการเรียกใช้ ตําแหน่งข้อมูลการนับโทเค็นจะรับอินพุตที่มีโครงสร้างเดียวกันกับคําขอข้อความ (System Prompt เครื่องมือ ภาพ PDF) และส่งคืนการนับโทเค็นอินพุต หลังจากการเรียกใช้ ช่องการใช้งานของการตอบสนองจะรายงานว่าคําขอใช้ไปเท่าใดจริง ด้วย Prompt Caching อินพุตจะถูกแบ่งออกเป็น input_tokens, cache_read_input_tokens และ cache_creation_input_tokens และทั้งสามจะนับไปยังหน้าต่าง แดชบอร์ดที่เพิ่มเฉพาะ input_tokens จะรายงานการใช้บริบทที่ไม่ดีต่ําลงเมื่อเปิดใช้งานการแคช
  • •
    - ส่งคืน invalid_request_error สําหรับเครื่องมือเซิร์ฟเวอร์ เช่น การค้นหาเว็บและการดําเนินการโค้ด สําหรับตัวเชื่อมต่อ MCP และสําหรับบล็อกภาพหรือเอกสารที่ให้เป็น URL หรือแหล่งที่มาของไฟล์ ส่งภาพและ PDF เป็น base64 เพื่อนับ สําหรับคําขอเครื่องมือเซิร์ฟเวอร์ ให้ใช้วัตถุการใช้งานในการตอบสนองจริง - ให้การประมาณโดยไม่มีตรรกะการแคช cache_control ได้รับการยอมรับ แต่ไม่มีผล - นับด้วยโทเค็นเซอร์ของโมเดลที่คุณส่งผ่าน โมเดล Fable และ Mythos ใช้โทเค็นเซอร์ที่นํามาใช้กับ Opus 4.7 ซึ่งนับโทเค็นได้มากกว่าประมาณ 30 เปอร์เซ็นต์เมื่อเทียบกับโมเดลก่อน Opus 4.7 ก่อนการโยกย้าย ให้นับคําขอเดียวกันในทั้งสองโมเดลและเปรียบเทียบ
  • •
    การนับล่วงหน้ามีข้อจำกัดบางประการที่ควรทราบ

#5 5. การลดค่าใช้จ่ายของเครื่องมือในบริบท

อ่านเนื้อหา ↗
  • •
    ใน Agent หน้าต่างส่วนใหญ่จะไปที่เครื่องมือ คำจำกัดความของเครื่องมือจะถูกส่งไปในทุกคำขอ และการเรียกแต่ละครั้งจะทิ้ง tool_result ไว้ในประวัติ เทคนิคทั้งสี่ด้านล่างนี้กำหนดเป้าหมายไปที่แหล่งที่มาของความกดดันที่แตกต่างกัน
  • •
    การแก้ไขบางประการฟังดูดีและพลาดต้นทุนเหล่านี้ การเปลี่ยนไปใช้โมเดลที่มีโทเค็น 1M การเพิ่ม max_tokens หรือการย่อชื่อเครื่องมือทิ้งภาระการกําหนด การเดินทางไปกลับ และการกําหนดราคาซ้ําไว้ที่เดิม และหน้าต่างที่ใหญ่ขึ้นที่เต็มไปด้วยเครื่องมือเดียวกันยังคงประสบปัญหาการเน่าเฟะของบริบท การแก้ไขอีกประการหนึ่งคือโครงสร้าง: ส่งการสํารวจอย่างละเอียดให้กับ Subagent ที่มีหน้าต่างของตัวเอง
  • •
    เฉพาะคําตอบแบบย่อเท่านั้นที่จะไปถึงเธรดหลัก 📖 รูปแบบผู้ประสานงานและบริบท Subagent แบบแยก (1.4) ครอบคลุมถึงวิธีการทํางานของรูปแบบนั้น
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (2 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Prompt Prefix ้อมท์ที่แคชไว้จะไม่ถูกนับไปยัง Context Window เนื่องจากถูกอ่านจากแคช (ทําไมจึงผิดพลาด): การแคชจะเปลี่ยนราคาของโทเค็นที่แคชไว้ ไม่ว่าโทเค็นเหล่านั้นจะถูกนับหรือไม่ cache_read_input_tokens และ cache_creation_input_tokens ทั้งสองจะใช้พื้นที่ของหน้าต่าง
Cached prompt prefixes don't count toward the context window, because they're read from cache.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
Caching changes the price of cached tokens, not whether they count. cache_read_input_tokens and cache_creation_input_tokens both take up the window.

❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
หากอินพุตบวก max_tokens ใหญ่กว่าหน้าต่าง API จะปฏิเสธคําขอด้วย 400 เช่นเดียวกับที่เกิดขึ้นเมื่ออินพุตยาวเกินไป
If input plus max_tokens is larger than the window, the API rejects the request with a 400, just as it does when the input is too long.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
400 เกิดขึ้นเฉพาะเมื่ออินพุตเพียงอย่างเดียวใหญ่กว่าหน้าต่าง บนรุ่น Claude 4.5 และรุ่นใหม่กว่า การโอเวอร์โฟลว์อินพุตบวก max_tokens จะได้รับการยอมรับและหยุดด้วย model_context_window_exceeded หากการสร้างถึงขีดจํากัด
A 400 happens only when the input alone is larger than the window. On Claude 4.5 models and newer, an input-plus-max_tokens overflow is accepted and stops with model_context_window_exceeded if generation reaches the limit.
