💡 แนวคิดหลักสำคัญ (Key Concept)

Baseline comparison — A change only counts as an improvement if it beats the current production version on the same measurement. Without that measurement, a prompt edit is a guess. The baseline is the version you would keep if the change failed, and the target is how far the change has to beat it.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Baselines and targets come before the change" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Iterative improvement is a loop: change one thing, measure it against what you already have, then keep the change or drop it. The "what you already have" is the baseline, which is usually the prompt, model or configuration serving production today. A candidate counts as better only when it beats that baseline on the criterion you set in advance. Feeling better to the person who wrote it doesn't count. Anthropic's guidance lists A/B testing among the quantitative methods for exactly this: comparing performance against a baseline model or an earlier version.

A target turns the comparison into a decision. The sentiment-classification example in Anthropic's success-criteria guidance does not stop at "F1 of at least 0.85". It also says that this figure is a 5% improvement over the current baseline. Each target is anchored to something real: industry benchmarks, prior experiments, AI research or expert knowledge. A prior experiment is itself a baseline. Setting the bar before you run the comparison stops you from moving it once the numbers come in. Choosing which metrics to track is its own skill, covered under [defining evaluation metrics](lesson:4.1). Here the point is that every metric you iterate on needs both a starting value and a finish line.

Baselines get cheaper once you have them. An eval suite run against the production version records latency, token usage, cost per task and error rates on a fixed bank of tasks. Every later candidate is scored against that record. Teams without one end up in a reactive loop: they wait for complaints, fix one failure, and cannot tell a real regression from noise.

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

Exam trapsA prompt version whose outputs Claude rates with higher average confidence is the more accurate version.Why is that wrong?Confidence is never checked against the answers. For a categorical task, both versions should be scored on the same labelled set by exact match against the ground-truth labels.A small, carefully hand-labelled eval set gives a more trustworthy prompt comparison than a larger automatically graded one.Why is that wrong?Anthropic's guidance prefers volume. A larger set with automated grading supports repeated comparisons, while hand grading has to be paid for again on every re-run.

✓ แบบฝึกหัดตรวจสอบความเข้าใจ (Checkpoint Practice)
Check

Two versions of a support-ticket prompt each label every ticket urgent, normal or low. You have 400 tickets that humans have already labelled. Which offline score gives a fair comparison of the two versions?

A Run both versions on the same 400 tickets and score each by exact match against the human labels
B Ask Claude to rate its confidence in each label it gives, and keep the version with the higher average confidence
C Have two colleagues read a sample of outputs from each version and vote on which one feels more accurate
D Score each version's labels against the human labels with ROUGE-L F1, so near-misses still earn partial credit
คลิกดูเฉลยคำตอบพร้อมคำอธิบาย (Click to view answer & explanation) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A

Ticket priority is a clear-cut categorical answer. Exact match against the labelled ground truth checks correctness directly and costs nothing extra to re-run. Confidence ratings are never checked against the labels, colleague votes are slow and subjective, and ROUGE-L is meant for free-text output like summaries, not single labels.

“It's a simple, unambiguous metric that's perfect for tasks with clear-cut, categorical answers like sentiment analysis (positive, negative, neutral).”

A support-ticket triage team maintains a categorical labeling eval (urgent/normal/low, with human-labeled ground truth) used to compare successive versions of their Claude-based classification prompt. Before promoting a revised prompt candidate, they want the fastest, most objective way to confirm it outperforms the current production prompt on this task. Which approach should they use?

A Run both prompt versions against the same held-out labeled set and compare exact-match accuracy against the ground-truth category labels
B Have two support agents independently read a sample of outputs from each version and vote on which one feels more accurate
C Ask Claude to rate its own confidence in each classification on a 1-5 scale and treat higher average confidence as the better version
D Deploy the revised prompt to all traffic immediately and monitor ticket resolution time as a proxy for classification quality
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. Since ground-truth labels already exist for this categorical task, exact-match accuracy on a held-out set gives an objective, scalable, and directly comparable score between prompt versions before rollout.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. Manual agent voting is slow, inconsistent across raters, and does not scale the way automated grading against existing ground truth does.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Self-reported confidence is not a validated accuracy measure and can be miscalibrated, so it does not substitute for grading against known correct labels.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Shipping to all traffic without a controlled held-out comparison risks degrading production quality and conflates classification accuracy with an indirect proxy metric.

Which evaluation method best fits this need?

A Score each candidate summary against its reference using ROUGE-L and track the F1 score across prompt variants
B Compute exact string match between the candidate summary and the reference summary for each article
C Ask a separate Claude call to output a single yes/no verdict on whether the summary mentions any protected health information
D Measure the wall-clock latency of each prompt variant and prefer whichever version returns a response fastest
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼

ตัวเลือก A: ถูกต้อง

Correct. ROUGE-L measures the longest common subsequence between candidate and reference text, capturing whether key information appears in a similar order, and it is well suited to scoring summarization quality across many articles automatically.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Offline comparisons on a held-out eval set" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The fastest fair comparison is offline. Run the baseline and the candidate over the same held-out, labelled set and score both with the same grader. Real users are never exposed to the candidate, the run can be repeated, and it finishes in minutes. Building that set belongs to [evaluation dataset design](lesson:4.2). For the comparison, two things matter: which grader you use and how many cases you have.

Pick the most objective grader the task allows. A ticket classifier that outputs urgent, normal or low has a clear-cut categorical answer, so exact match against human-labelled ground truth is the right score. It checks whether the output equals the predefined correct label, usually after normalising whitespace and case. Asking Claude to rate its own confidence in each label does not do this, because confidence is not correctness and nothing is checked against the labels. Having two colleagues read samples and vote on which version "feels" more accurate is slower and less objective than a score both versions earn on the same answers.

Open-ended output needs a different score. When a summarisation prompt is compared against human-written reference summaries, exact string match fails almost every case, because two good summaries rarely share wording. ROUGE-L scores a candidate by the longest common subsequence it shares with the reference. A summary that keeps the reference's key information in a similar order scores high, and the F1 can be tracked across prompt variants at scale. Latency is a separate, operational criterion: a faster variant has not shown that its summaries are better.

Volume beats hand-polished quality. Anthropic's rule is that more questions with slightly lower-signal automated grading are better than fewer high-quality, hand-graded ones. The reason is economic. Writing questions is mostly a one-time cost, but grading is paid every time the eval is re-run, and iteration means re-running it constantly. Eighty carefully hand-labelled cases that someone must re-grade by hand after every prompt edit will slow you down. An automatically graded set of several hundred cases gives the same comparison every time you run it, at no extra effort.

A Pass the agent ID with an explicit version in each session, so every run uses the exact prompt it is meant to measure

A comparison is fair when the variable you changed is the only one that differs. Anthropic's support-desk prompt audit shows the discipline. Six system prompts were each built by adding a single pattern, such as "verify twice" or "be maximally thorough", to the same clean prompt. All six ran on the same 44 tickets with deterministic grading. Because each prompt differed from the clean one by one pattern, each result could be attributed. Removing "verify twice" cut cost per ticket by a third. Removing contradictory rules and a hand-rolled scratchpad each restored 7 to 11 points of accuracy. If all six edits had shipped together, only their sum would be visible.

Repeated runs are part of being fair, because the same configuration does not give the same score every time. In a data-file benchmark, three identical Claude Sonnet 5 runs answered 6, 7 and 7 of 25 questions correctly. A one-question difference between two variants in a single run is inside that spread. The prompt audit reports its results with this in mind: the Opus 5 accuracy gain carried a 95% confidence interval of 3 to 8 points, while the Sonnet accuracy differences were described as within noise. Before you call a candidate better, check that its margin is bigger than the baseline's own variation.

Pin everything except the variable under test. That means the same eval set, the same grader, the same model and effort setting, and an explicit version of each prompt. In Managed Agents, passing a bare agent ID gets whatever version is latest. Passing an object with a version pins the session to an exact version, which the prompt-versioning cookbook calls what you want for a controlled comparison. When the variable is the model itself, run your actual prompts and data through each candidate model rather than relying on general benchmarks.

4.When to run a live A/B test

สาระสำคัญและหลักการทำงานของหัวข้อนี้: หัวข้อนี้เจาะลึก When to run a live A/B test ตามมาตรฐานและพิมพ์เขียวการสอบของ Anthropic โดยมุ่งเน้นการทำความเข้าใจสถาปัตยกรรมเชิงลึก ข้อดีข้อเสียทางเทคนิค และแนวทางการปฏิบัติจริงในโปรดักชัน
MethodStrengthLimitation
Automated offline evalFast, fully reproducible, no user impact, can run on every commitCan create false confidence if it doesn't match real usage patterns
Live A/B testMeasures actual user outcomes and controls for confoundsSlow to reach significance, needs traffic, only tests changes you deploy
Production monitoringCatches issues synthetic evals missReactive: problems reach users before you know about them
⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

Exam trapA live A/B test is the quickest way to find out whether a prompt revision is better.Why is that wrong?Live A/B tests take days or weeks to reach significance and need enough traffic. An offline eval on a held-out set is the fast first check, and A/B testing then validates significant changes.

Run the offline eval first on every change. Use a live A/B test to confirm significant changes, because its random split controls for confounds, but it needs traffic and time. Monitoring is reactive. A full rollout with no control group can't separate the prompt's effect from anything else that changed.

A live A/B test splits real traffic between the baseline and the candidate and measures what users actually do. It can measure things an offline set cannot, such as retention and task completion, and the random split controls for confounds. Task completion rate is one of the implicit user-feedback measures in Anthropic's success-criteria guidance. The cost is time and exposure: reaching significance takes days or weeks, it needs enough traffic, and the candidate is already in front of users.

The order follows from that table. Automated evals are the first line of defence on every change and model upgrade. A/B testing is for validating significant changes once you have the traffic to support it. Neither is a reason to skip the other. Pushing a revised prompt to all traffic and watching a proxy such as ticket resolution time is not an A/B test either: with no control group, a change in the proxy cannot be attributed to the prompt. A/B results also carry less signal on *why* a metric moved, so pair them with transcript review when a variant wins or loses unexpectedly. Ongoing production monitoring is a separate discipline, covered in [monitoring with logging and observability](lesson:4.6).

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

An aggregate score is an average, and averages hide where the losses landed. A candidate can gain on the segment it was written for and lose on a neighbouring one, and the overall number may still go up. Real task distributions are mixed, and most use cases are judged on several criteria at once. Score every comparison per category, per input type or per team, as well as overall.

The change targeted API tickets, and the team that paid for it was billing. On this 20-ticket set the regression also shows in the total, which falls from 19 to 17. Now picture the same rule on a set where many API tickets had been misrouted before. The rule would fix those, the total would rise, and billing's drop would vanish into the improvement. The per-team view finds the problem either way. The support-desk audit used the same approach along a different axis: the averaged result said accuracy went up, and only the per-pattern breakdown showed which edits caused it.

When callers are pinned, creating a version changes nothing in production. Only changing the pinned number does that, so the pin change is the release and the step that goes through review. Comparing a candidate with the baseline is only safe when both can be referred to by version. Otherwise the baseline is overwritten the moment you ship the change. Managed Agents makes the prompt a server-side resource. Every agents.update creates a new immutable version, and each session chooses which version to run by number. Version 1 still exists after version 2 is created, so the earlier version can always be compared against and returned to, and client.beta.agents.versions.list(AGENT_ID) lists every version.

Three moves, all done by changing which version is referenced:

- Canary: route a fraction of traffic to the new version and compare before promoting fully, so the version works like a feature flag. - Promote: update the config that tells production callers which version to pass. That config change is what goes through review. - Roll back: callers go back to passing the old version number. No deploy is needed, and the regressed version stays on the server for further iteration.

The safety of all three depends on production callers pinning to an explicit version. agents.update has no built-in approval workflow, and any key in the workspace can call it. A caller passing the bare agent ID picks up the new prompt on its next session, so an unreviewed v2 is live straight away. With explicit pins, anyone can create v2, v3 or v10 as experiments that get no traffic. The pinned number becomes the change-control gate. In the routing example, the billing regression was fixed by re-pinning to version 1, which brought billing back to 4/5, while v2 stayed available to keep working on before a v3 goes through the same comparison.
