💡 แนวคิดหลักสำคัญ (Key Concept)

Baseline comparison — A change only counts as an improvement if it beats the current production version on the same measurement. Without that measurement, a prompt edit is a guess. The baseline is the version you would keep if the change failed, and the target is how far the change has to beat it.

1. Baselines and targets come before the change

Iterative improvement is a loop: change one thing, measure it against what you already have, then keep the change or drop it

The "what you already have" is the baseline, which is usually the prompt, model or configuration serving production today

A candidate counts as better only when it beats that baseline on the criterion you set in advance

Feeling better to the person who wrote it doesn't count

Anthropic's guidance lists A/B testing among the quantitative methods for exactly this: comparing performance against a baseline model or an earlier version.

A target turns the comparison into a decision

The sentiment-classification example in Anthropic's success-criteria guidance does not stop at "F1 of at least 0.85"

It also says that this figure is a 5% improvement over the current baseline

Each target is anchored to something real: industry benchmarks, prior experiments, AI research or expert knowledge

A prior experiment is itself a baseline Setting the bar before you run the comparison stops you from moving it once the numbers come in

Choosing which metrics to track is its own skill, covered under [defining evaluation metrics](lesson:4.1)

Here the point is that every metric you iterate on needs both a starting value and a finish line.

Baselines get cheaper once you have them

An eval suite run against the production version records latency, token usage, cost per task and error rates on a fixed bank of tasks

Every later candidate is scored against that record

Teams without one end up in a reactive loop: they wait for complaints, fix one failure, and cannot tell a real regression from noise.

2. Offline comparisons on a held-out eval set

การเปรียบเทียบที่ยุติธรรมที่เร็วที่สุดคือออฟไลน์ ดำเนินการเส้นฐานและผู้เข้าแข่งขันในเซตที่จัดขึ้น มีป้ายกำกับเดียวกัน และให้คะแนนทั้งคู่ด้วยเครื่องให้คะแนนเดียวกัน ผู้ใช้จริงจะไม่เปิดเผยต่อผู้สมัคร สามารถทำซ้ำได้และเสร็จสิ้นภายในไม่กี่นาที สิ่งปลูกสร้างที่เป็นของ 📖 การออกแบบชุดข้อมูลการประเมิน (4.2) สำหรับการเปรียบเทียบ มีสองสิ่งที่สำคัญ: คุณใช้เครื่องให้คะแนนใด และคุณมีกี่กรณี

Pick the most objective grader the task allows

A ticket classifier that outputs urgent, normal or low has a clear-cut categorical answer, so exact match against human-labelled ground truth is the right score

It checks whether the output equals the predefined correct label, usually after normalising whitespace and case

Asking Claude to rate its own confidence in each label does not do this, because confidence is not correctness and nothing is checked against the labels

Having two colleagues read samples and vote on which version "feels" more accurate is slower and less objective than a score both versions earn on the same answers.

Open-ended output needs a different score

When a summarisation prompt is compared against human-written reference summaries, exact string match fails almost every case, because two good summaries rarely share wording

ROUGE-L scores a candidate by the longest common subsequence it shares with the reference

A summary that keeps the reference's key information in a similar order scores high, and the F1 can be tracked across prompt variants at scale

Latency is a separate, operational criterion: a faster variant has not shown that its summaries are better.

Real users are never exposed to the candidate, the run can be repeated, and it finishes in minutes. Building that set belongs to [evaluation dataset design](lesson:4.2). For the comparison, two things matter: which grader you use and how many cases you have.

Pick the most objective grader the task allows. A ticket classifier that outputs urgent, normal or low has a clear-cut categorical answer, so exact match against human-labelled ground truth is the right score. It checks whether the output equals the predefined correct label, usually after normalising whitespace and case. Asking Claude to rate its own confidence in each label does not do this, because confidence is not correctness and nothing is checked against the labels. Having two colleagues read samples and vote on which version "feels" more accurate is slower and less objective than a score both versions earn on the same answers.

Open-ended output needs a different score. When a summarisation prompt is compared against human-written reference summaries, exact string match fails almost every case, because two good summaries rarely share wording. ROUGE-L scores a candidate by the longest common subsequence it shares with the reference. A summary that keeps the reference's key information in a similar order scores high, and the F1 can be tracked across prompt variants at scale. Latency is a separate, operational criterion: a faster variant has not shown that its summaries are better.

Volume beats hand-polished quality. Anthropic's rule is that more questions with slightly lower-signal automated grading are better than fewer high-quality, hand-graded ones. The reason is economic. Writing questions is mostly a one-time cost, but grading is paid every time the eval is re-run, and iteration means re-running it constantly. Eighty carefully hand-labelled cases that someone must re-grade by hand after every prompt edit will slow you down. An automatically graded set of several hundred cases gives the same comparison every time you run it, at no extra effort.

6. Promote, canary and roll back by version

Comparing a candidate with the baseline is only safe when both can be referred to by version

Otherwise the baseline is overwritten the moment you ship the change

Managed Agents makes the prompt a server-side resource

Every agents.update creates a new immutable version, and each session chooses which version to run by number

Version 1 still exists after version 2 is created, so the earlier version can always be compared against and returned to, and client.beta.agents.versions.list(AGENT_ID) lists every version.

Three moves, all done by changing which version is referenced:

  • ▸
    Canary: route a fraction of traffic to the new version and compare before promoting fully, so the version works like a feature flag.
  • ▸
    Promote: update the config that tells production callers which version to pass. That config change is what goes through review.
  • ▸
    Roll back: callers go back to passing the old version number. No deploy is needed, and the regressed version stays on the server for further iteration.

The safety of all three depends on production callers pinning to an explicit version

agents.update has no built-in approval workflow, and any key in the workspace can call it

A caller passing the bare agent ID picks up the new prompt on its next session, so an unreviewed v2 is live straight away

With explicit pins, anyone can create v2, v3 or v10 as experiments that get no traffic

The pinned number becomes the change-control gate

In the routing example, the billing regression was fixed by re-pinning to version 1, which brought billing back to 4/5, while v2 stayed available to keep working on before a v3 goes through the same comparison.
