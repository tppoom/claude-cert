Every architecture in this lesson, from a two-step pipeline to an autonomous coding agent, is made from one unit: the augmented LLM. This is a model call extended with retrieval, tools and memory. Claude does not just receive these capabilities passively. It writes its own search queries, chooses which tool to call, and decides what information to keep. A pattern describes how several of these units are wired together. It never replaces the unit.

In practice a single call carries more than the user's text. Claude receives the prompt along with the system prompt, the tool definitions and the conversation history, and it may answer in text, request tool calls, or do both. So even before you choose a pattern, one call can search, look things up and act.

Two parts of the implementation matter most. First, the capabilities should fit your use case: a support assistant needs order lookup, not a general web crawler. Second, each capability needs a clear, well-documented interface the model can understand. The Model Context Protocol is one way to connect third-party tools through a simple client; choosing among integration mechanisms is covered in [connection protocols](lesson:3.7). Once each call has the right augmentations, the architectural question becomes how those calls are arranged.

Workflows and agents are both agentic systems, and they differ in one thing: who controls the sequence. In a workflow, your code decides the order of calls: classify, then draft, then translate. In an agent, the model directs its own process and tool use. Using tools, or making many calls, does not by itself make something an agent.

The agent's mechanics are simple. It is a model using tools in a loop and acting on what comes back. The Claude Agent SDK runs this cycle: Claude evaluates the current state and requests tool calls, the SDK runs them, and each set of results goes back to Claude for its next decision. The loop stops when Claude gives a response with no tool calls. In a bug-fix run, Claude might run the tests, read the failing files, edit one, and run the tests again before it reports that all three pass. Because the model judges its progress from these real results, agents usually also get stopping conditions, such as a maximum number of iterations, so they stay under control.

Agents fit open-ended problems where you cannot predict how many steps are needed or hardcode a path, such as resolving a SWE-bench task that touches many files. That autonomy has a price: higher cost and the risk of compounding errors, where one bad decision feeds the next. Agents call for extensive testing in sandboxed environments, guardrails, and enough trust in the model's decision-making to let it run for many turns.

Picking a workflow comes down to a few questions about the task. Are the steps fixed? Do inputs fall into distinct categories? Can the work run in parallel? Can you predict the subtasks before seeing the input? Is there a clear test for quality? Each answer points to a different pattern, and the wrong options in a design review usually answer a question the scenario never asked.

Prompt chaining splits a task into a fixed sequence, and each call processes the output of the one before it. It fits when the task decomposes cleanly into known subtasks. It deliberately trades latency for accuracy, because each call has an easier job. Between steps you can add gates, which are programmatic checks that confirm the process is still on track. A gate is ordinary code: a length limit, a schema check, a required field. Writing marketing copy and then translating it is the standard example. A content team that translates copy into three languages and must keep each string within a UI character limit has a fixed sequence plus a deterministic check, so it is a chain with a gate. It does not need another LLM to judge length, and it does not need an orchestrator to decide which languages to produce, because the languages are already known.

Chaining also helps you run the system. Explicit chains are still worth using when you need to inspect intermediate outputs or enforce a specific pipeline structure, because each step is a separate API call you can log, evaluate or branch on. Smaller, consistent subtasks also reduce inconsistency at scale, since each one gets Claude's full attention.

Routing classifies an input first and then sends it to a specialized follow-up: a different prompt, tool set or process. The reason is separation of concerns. Without routing, tuning one prompt for one kind of input can hurt performance on the others. Routing fits when the categories are distinct and classification is accurate, whether an LLM or a traditional classifier does it. A support queue with billing questions, technical bugs and cancellations, each needing its own tuned prompt, is a routing problem. Running every ticket through all three prompts in a chain wastes calls on the two that don't apply. Running them in parallel and keeping whichever finishes first throws away the reason for having specialists. Routing can also send easy questions to a smaller, cheaper model and hard ones to a more capable model; choosing those models is covered in [model selection](lesson:2.1).

Parallelization runs several LLM calls at the same time and combines their outputs in code. It has two forms. Learn to tell them apart by asking whether the calls do different work or the same work. Sectioning splits a task into independent subtasks that run in parallel: one call checks generated code for vulnerabilities while another checks the same code for licensing problems, and code merges both into one report. Voting runs the same task several times to get different outputs, for example several prompts reviewing code for vulnerabilities, with the code flagged if any of them finds a problem.

Sectioning often helps quality as well as speed. When a task involves several considerations, LLMs usually do better if each one gets its own call with focused attention. Guardrails are the standard case: one instance answers the user while another screens the query for inappropriate content, which works better than one call doing both. Chaining these checks would be wrong, because neither depends on the other's output. An evaluator-optimizer setup would be wrong too, because neither check is critiquing the other.

Orchestrator-workers looks like parallelization: a central LLM breaks the work down, hands pieces to worker LLMs, and combines their results. The difference is that the subtasks are not fixed in advance. The orchestrator decides them at run time from the specific input. In a coding change, the number of files to edit and what changes in each depend on the request, so nobody can write the fan-out beforehand. A fixed set of five prompts is therefore sectioning. Orchestrator-workers is the wrong choice for simple single-output tasks, when latency is critical, or when the subtasks are predictable enough to define ahead of time. In that last case, use the simpler parallel workflow.

In this code the list of facets comes from decompose_query, so it differs for each query. That one line is what makes it orchestrator-workers and not sectioning. When workers become full agents with their own context windows, you are designing a multi-agent system, and its token cost and context isolation are covered in [multi-agent orchestration](lesson:1.4).

In an evaluator-optimizer loop, one call produces a response, a second call critiques it against criteria, and the loop repeats until the response passes. It is the same draft, review and revise cycle a human writer goes through. With Claude it is the most common chaining pattern: generate a draft, review it against criteria, then refine based on the review.

The pattern needs two conditions: clear evaluation criteria, and refinement that measurably improves the result. There are two signs it fits. First, the responses clearly get better when a human states their feedback. Second, an LLM can give that feedback itself. Literary translation passes both tests, because an evaluator can spot nuances the first translation missed. Complex search also fits: the evaluator decides whether another round of searching is needed.

That contrast is the key decision. Use an LLM evaluator when quality is a judgment, such as tone, nuance or completeness, that a model can put into words and the generator can act on. Use a programmatic gate when the test is a rule code can check. Every loop adds at least one more call per round, so stop it with a pass condition rather than letting it run open-ended. Defining the metrics an evaluator scores against is covered in [evaluation metrics](lesson:4.1).
