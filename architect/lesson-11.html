💡 แนวคิดหลักสำคัญ (Key Concept)

Showing versus telling — Instructions tell Claude what you want. Examples show the output pattern, and chain-of-thought shows the reasoning path. You add each one only when telling alone has stopped producing consistent, correct results.

1.Zero-shot, one-shot and few-shot prompting

สาระสำคัญและหลักการทำงานของหัวข้อนี้: หัวข้อนี้เจาะลึก Zero-shot, one-shot and few-shot prompting ตามมาตรฐานและพิมพ์เขียวการสอบของ Anthropic โดยมุ่งเน้นการทำความเข้าใจสถาปัตยกรรมเชิงลึก ข้อดีข้อเสียทางเทคนิค และแนวทางการปฏิบัติจริงในโปรดักชัน
ApproachWhat the prompt containsUse it when
Zero-shotExplicit instructions, format, constraints and the reasons for themThe output can be fully described in words
One-shotInstructions plus one example of the desired outputThe format, tone or style is easier to show than describe

A zero-shot triage prompt gives the correct priority, but the label varies between tickets: "High" on one and "high priority" on the next. What is the most effective fix?

A Have Claude explain in prose why it chose the priority before it gives the label
B Add one example ticket and its output right after the instructions, without tags
C Add several varied ticket-and-output pairs, each wrapped in example tags
D Repeat the rule "always use consistent labels" in capital letters in the zero-shot prompt
คลิกดูเฉลยคำตอบพร้อมคำอธิบาย (Click to view answer & explanation) ▼
คำตอบที่ถูกต้อง: ตัวเลือก C

The priority is right, so the problem is the shape of the output, not the reasoning. Examples are the fix for that. Several varied examples show the exact labels and layout, and tags let Claude tell the demonstrations apart from the instructions. Explaining in prose doesn't change the output's shape, and a single untagged example is the weakest version of the fix.

A team's support-ticket triage prompt asks Claude to output a category label and priority score, but real outputs vary in formatting and label spelling across similar tickets. The team has not yet included any example outputs in the prompt. Which change is most likely to make outputs consistent?

A Raise the temperature parameter so Claude explores a wider range of phrasing options before settling on the final label
B Wrap three to five diverse ticket-and-output pairs in <example> tags so Claude can pattern-match on the intended format and labels
C Add a single example ticket at the very end of the prompt, after the classification instructions, to anchor the closing tokens
D Ask Claude to first summarize the ticket in prose, then separately explain why it did not select the other categories
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก B
ตัวเลือก A: ไม่ถูกต้อง

Incorrect. Raising temperature increases output variability rather than reducing it, and does nothing to establish a consistent output format or label vocabulary.

ตัวเลือก B: ถูกต้อง

Correct. Multishot (few-shot) prompting with several diverse, clearly demarcated examples is the documented technique for steering output format, tone, and structure toward consistency.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. A single example provides too little pattern diversity to reliably anchor formatting across varied ticket types, and best-practice guidance recommends three to five examples.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Adding an unrelated summarization and self-explanation step does not address the underlying lack of demonstrated output format and may introduce further inconsistency.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Zero-shot, one-shot and few-shot prompting" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A zero-shot prompt is made of instructions alone, and for many tasks that is all you need. Claude follows clear, explicit direction well. A zero-shot prompt succeeds when it states the output format and constraints, and when it explains the reason behind each rule. A rule like "never use ellipses" works better with its reason attached: the text will be read aloud by a text-to-speech engine that cannot pronounce them. Given the reason, Claude can also handle cases the rule never mentioned, because it is able to generalise from the explanation.

Some requirements are easier to show than to describe, and that is when examples start to pay off. Typical cases are a summary style, a tone of voice, or a labelling convention with fine distinctions. Another is a set of instructions that keeps producing outputs that differ slightly from run to run. Putting example inputs with their outputs in the prompt is called one-shot prompting when there is one example and few-shot (or multishot) prompting when there are several. A few well-crafted examples improve both accuracy and consistency.

Escalate one step at a time. Start with one example, and add more only if the output still doesn't match. Each example adds length, and as the next section explains, every detail in an example becomes something Claude may copy. Examples also extend beyond text. In one vision walkthrough, Claude misread a speedometer in km/h until example images were added to the prompt. Few-shot prompting with images doesn't always work, though, so test it on your own case.

Few-shot examples are the standard fix when outputs drift in format or label spelling across similar inputs, such as a triage prompt that returns "High" on one ticket and "high priority" on the next. Asking Claude to explain its reasoning in prose does not fix this, because the problem is the output's shape, not its reasoning. Adding one untagged example after the instructions is the weakest version of the fix. A single example shows no variety, and without tags Claude cannot reliably tell the demonstration apart from the instructions. Several varied ticket-and-output pairs, each wrapped in example tags, teach the exact labels and layout you expect.

Claude learns everything an example shows, including what you did not mean to teach. Modern Claude models pay very close attention to details in examples. A shared length, sentence structure or sentiment across your examples will be read as part of the pattern. Example sets should meet three requirements:

- Relevant: they mirror your real use case closely, with the same kind of input and the same output shape. - Diverse: they cover edge cases and vary enough that Claude does not pick up unintended patterns. - Structured: each one is wrapped in example tags, and the set in examples tags, so Claude can tell demonstrations apart from instructions.

A homogeneous example set fails in a specific way. It works on inputs that look like the examples and breaks on everything else. Adding more examples of the same kind makes the unwanted pattern stronger, so the count is not the fix. The fix is coverage: include each label, the hard boundary cases, and varied lengths and phrasings. Varied examples are most useful for nuanced or ambiguous cases, where the line between categories is hard to state in a written description alone.

Tags matter as much as content. If an example sits loose among the instructions, Claude may treat its specific values as requirements, or treat an instruction as sample data. Wrapping each example in its own tag removes that ambiguity. Using the same tag names in every prompt keeps the structure predictable. Examples are also the easiest place to tune behaviour: changing the examples in a moderation prompt changes what it allows and blocks, with no other edits.

Chain-of-thought (CoT) prompting asks Claude to reason step by step before giving its answer. It helps because a model answering in a single pass has no room for scratch work, checking or changing course. When Claude reasons first, it restates the problem, tries approaches and checks intermediate results. This matters most for tasks whose answer depends on intermediate work that would otherwise be squeezed into the response or skipped: multi-step analysis, maths, and decisions that weigh several factors.

Each form gives you more control than the one before. The basic form lets Claude decide what is worth thinking about. The guided form names the stages, for example the donor's giving history first, then the parts of the programme that fit them, then the email. Use it when the reasoning has to cover specific ground. The structured form adds output tags, which production pipelines usually need. A moderation filter can ask for its reasoning in thinking tags and its verdict in output tags, then parse only the verdict. In a vision example, the same thinking-then-answer layout fixed a dog count Claude had first got wrong.

Extended thinking is built-in chain-of-thought. When it is active, Claude reasons in thinking content blocks that arrive before its text response. On models that support it, extended thinking is generally preferable to writing CoT instructions by hand. How you turn it on depends on the model. On Claude Opus 4.6 to 4.8 and Claude Sonnet 4.6, thinking stays off until you set adaptive thinking, which lets Claude decide when and how deeply to think. Claude Sonnet 5 has it on by default.

Manual CoT is still the right choice in two cases. The first is when extended thinking isn't available, such as on the free Claude.ai plan. The second is when you need reasoning you can review. A thinking block never contains the raw chain of thought. With display set to summarized it holds a summary of Claude's reasoning. With omitted, the default on many models, its thinking field comes back empty. Reasoning written in thinking tags as part of the response is exactly what Claude wrote, so an auditor can read it in full. The two approaches can also be combined: even with extended thinking on, explicit CoT instructions can still help on complex tasks.

Thinking has costs, so it should not be on for every request. Thinking tokens are billed as output tokens even when the text is not returned, and they count toward max_tokens. They also add latency. You can steer thinking turn by turn. Adding "Please think hard before responding." to a user message encourages it, and "Answer directly without deliberating." discourages it. An agent harness can add the first phrase on planning steps and the second on routine confirmations. Steering phrases change model behaviour, so measure how often thinking triggers, token use, latency and answer quality before you ship them.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Placing long documents, examples and the query" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Prompts that combine large documents with instructions and examples need a deliberate layout. Inputs of 20k+ tokens are where layout matters most; managing the limits themselves is covered under [context window budgeting](lesson:2.4). Three practices apply:

- Put the long documents near the top, above the query, instructions and examples. This improves performance on all models, so moving the question to the very top is the wrong direction. - Wrap each document in document tags with source and document_content subtags, and nest them all inside a documents tag. Keep this structure rather than pasting raw text, because the tags let Claude tell the documents apart. - Ask Claude to quote the relevant passages, in their own tag, before it does the task. This keeps it focused on the content that matters and ignoring the rest.

Quoting first is the long-document version of chain-of-thought: the extracted quotes become the intermediate work the answer builds on. If answers keep missing details buried mid-document, quote grounding plus a documents-first layout is the fix. Cutting the input down to a single document is not, because the multi-document tag structure exists precisely so Claude can work across several sources in one prompt.
