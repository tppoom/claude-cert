1.Hooks: actions that run every time

คลิกดูเฉลยคำตอบพร้อมคำอธิบาย (Click to view answer & explanation) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A

PostToolUse fires after a tool call succeeds, so the file Claude just edited is on disk and ready to format. PreToolUse fires before the edit happens, so there would be nothing new to format. Stop fires once at the end of the turn, not after each edit. SessionStart fires only when a session begins or resumes.

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 57053

A platform team wants Claude Code to automatically block any Bash tool call that includes rm -rf targeting a path outside the working directory, without relying on the model choosing to avoid it on its own. Which mechanism should they configure?

A Configure a PreToolUse hook that inspects the Bash tool input and returns a deny decision before the command runs
B Set the default permission mode to plan mode so Claude proposes changes without executing any commands
C Add a CLAUDE.md instruction telling Claude never to run destructive delete commands outside the project directory
D Create a subagent with restricted tool access and instruct the main agent to delegate all Bash calls to it
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. A PreToolUse hook is a deterministic shell command that runs before the matching tool executes and can return a blocking decision, so it enforces the rule regardless of what the model decides, which is exactly the guarantee hooks are designed to provide over relying on the model's judgment.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. Plan mode blocks all execution, not just the specific dangerous pattern, so it would stop every Bash command including safe ones, and it is not a targeted, permanent enforcement mechanism for this one rule.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. A CLAUDE.md instruction is guidance the model may follow, but it is not deterministic enforcement; the model could still misjudge or ignore the instruction under certain phrasing of a task.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Delegating to a restricted subagent limits which tools that subagent can call, but it does not deterministically inspect and block a specific dangerous command pattern the way a PreToolUse hook does, and the main agent could still issue the command directly.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Hooks: actions that run every time" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Anything you write in a prompt or in CLAUDE.md is guidance. The model reads it and usually follows it, but it decides each time. A hook is not up to the model. It is a shell command that Claude Code runs whenever a particular event fires, whatever the model has decided. Use a hook when a rule must hold every single time: formatting after every edit, a lint before a turn can end, or a destructive command that must never run.

A hook has three parts. The event says when it fires. The matcher narrows it to particular tools, for example Bash or Edit|Write. The handler is the command that runs. The event matters most, because it decides what the hook is able to do:

To stop a command before it runs, use PreToolUse with matcher Bash. The hook receives the call as JSON, for example { "tool_name": "Bash", "tool_input": { "command": "rm -rf /tmp/build" } }. Your script inspects the command and, if it is not allowed, returns a deny decision:

Compare the alternatives for a rule like "never rm -rf outside the working directory". A CLAUDE.md instruction still depends on the model choosing to obey it. Plan mode blocks edits to every source file, which shuts down normal work instead of targeting the one dangerous command. Sending Bash calls to a restricted subagent still leaves a model in charge of the decision. Only the PreToolUse hook enforces the rule the same way every time.

Hooks become team-wide when they live in .claude/settings.json. That file applies to a single project and can be committed to the repo, so every developer who clones it gets the same hooks. 📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 57056

A team wants Claude Code to query their internal PostgreSQL database directly during a session, without the team writing custom tool-execution code themselves. Which approach fits the Model Context Protocol integration model?

A Configure an MCP server for the database and let Claude discover its tools through the protocol
B Write a PreToolUse hook that executes SQL queries whenever Claude requests database access
C Grant the Bash tool unrestricted access so Claude can invoke the database's command-line client directly
D Create a subagent whose system prompt contains the database schema and query examples
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. MCP servers expose external systems like databases as a set of discoverable tools that Claude can call directly, which is the documented mechanism for connecting Claude to systems such as a PostgreSQL database without hand-writing tool execution code.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. Hooks run deterministic shell commands at lifecycle events for validation or logging; they are not designed to serve as the mechanism through which Claude discovers and calls a database's query capabilities.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Granting unrestricted Bash access lets Claude shell out to a CLI client, but this bypasses the structured, discoverable tool interface MCP provides and removes the scoped, auditable tool boundary the team wants.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Putting schema details in a subagent's system prompt gives Claude static knowledge about the database, not a way to actually execute queries against it; it still lacks the live tool connection MCP provides.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Skills and MCP servers as shared team tooling" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Every developer's session starts from the same checked-in files. [CLAUDE.md as implementation guidance](lesson:6.4) holds the project's conventions. Next to it, hooks enforce rules and Skills package repeatable procedures. Together these three put the whole team on the same workflow without anyone having to configure it locally.

[Agent Skills (SKILL.md)](lesson:2.5) are reusable prompt packages. Checked into the repo, they become a team prompt library. A developer runs a procedure like the one below as /fix-issue 1234, and every teammate's run follows the same eight steps: read the issue, fix it, test, lint, commit and open a PR.

MCP servers are how Claude reaches external systems. When a team wants Claude to query its PostgreSQL database during a session, the fitting approach is to configure an MCP server for that database. The server exposes tools, Claude discovers them through the protocol, and the team writes no tool-execution code of its own. The other options each fail in a specific way. A PreToolUse hook reacts to tool calls that are already happening but gives Claude no new tool. Unrestricted Bash access goes against the practice of permitting only specific tools you know are safe. A subagent whose prompt contains the schema knows about the database but has no way to query it.

Two settings in that example limit what Claude can do. allowedTools lists the one tool the run may call, mcp__postgres__execute_sql. The server's own config sets readonly = true, so a write is rejected even if Claude produces one. Here access control sits in the integration, not in the prompt.

Claude Code does not need someone at the keyboard. With claude -p you pass a prompt, get the result on standard output, and can pipe data in, as in git log --oneline -20 | claude -p "summarize these recent commits". Any shell script, cron job or CI step can use it this way. The Setup hook event covers one-time preparation for these runs: it fires on --init or --maintenance in -p mode.

In GitHub, the Claude Code GitHub Action runs Claude in your CI pipeline. Running /install-github-app from Claude Code installs the GitHub App, adds the authentication secret and opens a pull request with the workflow file. A workflow can run in one of two modes. With no prompt input, it waits for an @claude mention in an issue or PR and posts its progress as a comment. With a prompt input, Claude runs on the trigger alone, and its results go to the workflow run log unless the prompt tells it to post them.

The team's skill library carries over to CI. Put actions/checkout before the Claude step so the files in .claude/skills/ exist on the runner, then pass /skill-name as the prompt. Locally and in CI, the same skill runs the same procedure. To restrict tools in CI, pass flags through claude_args, for example --allowedTools naming the only tool the job may call.

Unattended runs have guardrails of their own. On issue and pull request events, the user who triggers a run must have write access to the repository. Bot actors are rejected unless they are listed in allowed_bots, which stops bots from triggering Claude in a loop. For automation outside GitHub Actions, the Claude Agent SDK is the building block; the GitHub Action itself is built on it. If you only want reviews, Code Review gives every PR an automatic review without you writing a workflow.
