💡 แนวคิดหลักของหัวข้อนี้ (Core Concept)

การค้นพบอย่างมีโครงสร้างคือการทำงานที่คุณทำก่อนการออกแบบใด ๆ คุณจะรวบรวมชุดข้อเท็จจริงที่แน่นอนเกี่ยวกับผู้ที่ระบบให้บริการและข้อจำกัดของระบบ เพื่อให้การตัดสินใจทุกครั้งในภายหลังสามารถตรวจสอบได้ตามข้อเท็จจริงเหล่านี้ คำขอเช่น "ผู้ป่วยต้องการตรวจสอบเวลารอคิวก่อนเข้ามา" เป็นจุดเริ่มต้นของการสนทนา ไม่ใช่ข้อกำหนด ในการเปลี่ยนให้เป็นเอกสารสรุป ให้ตอบคำถามสี่ข้อในภาษาง่าย ๆ:

  • ▸
    ผู้ใช้ ระบุให้ชัดเจน ผู้ป่วยกลุ่มใด? แล้ว Agent ล่ะ? ใครอีกบ้างที่เข้าถึงระบบ
  • ▸
    ความต้องการ พวกเขาหวังผลลัพธ์อะไร นี่ไม่ใช่สิ่งเดียวกับคุณสมบัติที่พวกเขาขอ
  • ▸
    ประสบการณ์ การใช้งานโซลูชันที่ดีเป็นอย่างไร อธิบายประสบการณ์ ไม่ใช่คุณสมบัติ
  • ▸
    ข้อจำกัด งบประมาณ ความเชี่ยวชาญทางเทคนิคของผู้ที่จะใช้งาน การเข้าถึงอุปกรณ์ของผู้ใช้ และข้อกำหนดด้านความเป็นส่วนตัว
  • ▸

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Structured discovery is the work you do before designing anything. You collect a fixed set of facts about who the system serves and what limits it, so every later decision can be checked against them. A request such as "patients need to check wait times before coming in" is where the conversation starts, not a requirement. To turn it into a brief, answer four questions in plain language:

- Users. Be specific. Which patients? What about the staff? Who else touches the system? - Needs. What outcome are they hoping for? This is not the same as the feature they asked for. - Experience. What does a great solution feel like to use? Describe the experience, not the features. - Constraints. Budget, the technical skill of the people who will run it, users' access to devices, and privacy requirements.

A process map is the discovery technique that keeps the brief honest. The idea that [you start from the business process, not the model](lesson:1.1) becomes a concrete step in discovery. Break the user's need into steps, name the stakeholder at each step, and only then decide what role AI plays in each one. There are three roles to choose from: Automation (AI does it and you check), Augmentation (you and AI work on it together) and Agency (AI acts with latitude inside boundaries you set). This produces a small table, one row per step, and the AI decision is made separately for each row. Asking "should we use AI here?" about the whole system skips that step-by-step choice.

Three more questions belong in every first session, because no model can be recommended without the answers:

- Capabilities. What specific features or capabilities must the model have to meet the customer's needs? - Speed. How quickly does the model need to respond inside the customer's application? - Cost. What is the budget, for development and for production usage?

Each answer comes from the customer's own workload. Facts such as how many people work in IT, which social platforms marketing uses, or the version number of an internal ticketing tool change none of the three. They tell you nothing about what the model must do, how fast it must answer, or what it may cost.

Discovery findings point to one of two starting paths. Model trade-offs in general are covered in [selecting Claude models on trade-offs](lesson:2.1). The skill here is reading the brief and seeing which path it already implies.

Both paths also use a second dial, effort. Effort is a per-request setting that controls how much reasoning the model does before it answers. A higher level buys more intelligence and costs latency and tokens; a lower level answers faster and cheaper but thinks less. That is why "the deepest reasoning setting" suits a hard problem and wastes money on simple triage.

Claude Haiku 4.5 suits the first path because it was built for interactive applications and high-volume processing. A support desk triaging 50,000 short tickets a day under a sub-second target is that workload. Starting there and testing on real ticket samples answers every finding at once. Starting with maximum reasoning on every request, or picking a model because of its context window, answers questions the customer never raised. Context window size is not one of the three criteria, and short triage prompts do not need a larger one.

The second path fits the opposite brief. Take a research team that needs multi-step literature synthesis, says accuracy outweighs cost, and wants a long-running agent that plans its own steps. Here, any proposal whose main purpose is lowering cost misses the stated priority. That includes a cheaper model, lower effort, or a batch pipeline. Tuning effort is a real lever, but it comes later: you adjust it on a model you have already chosen, after evals show where you stand. Whichever path you take, the decision is confirmed the same way, by testing with the customer's actual prompts and data.

Good success criteria are specific, measurable, achievable and relevant. Specific means naming the target: "accurate sentiment classification" instead of "good performance". Measurable means a quantitative metric, or a well-defined qualitative scale that is applied consistently. Achievable means the target comes from industry benchmarks, prior experiments, AI research or expert knowledge, and does not demand more than current frontier models can deliver. Relevant means the criterion matches the application's purpose. Strong citation accuracy might be critical for a medical app and matter much less for a casual chatbot.

The techniques in this section are run with Claude, acting as a coding agent that helps build the solution, before it writes any code. Prototypes and mocks are spikes in practice. Each is a small throwaway build that answers one question, such as whether this layout works, without committing to a backend route or new state. Acceptance tests written before implementation give you, the customer and Claude one shared definition of done. Five to seven statements are usually enough. Each one must be concrete enough that a stranger could judge pass or fail. "The system is easy to use" fails that check. "A patient with a basic smartphone can find the current wait time in under 30 seconds without creating an account" passes it. The second version contains a user, a device, a time limit and a constraint, each of which came out of the discovery brief.

First drafts are usually written for humans to judge. Rewrite them so each one is something code could pass or fail, and add edge cases. For the clinic, those include the clinic being closed, having no data, and a wait time of zero.

For agent-built systems, the same discipline scales up to a feature list. A long-running harness is a multi-agent build in which one agent writes the feature list and later agents implement it. An initializer agent starts first and expands the user's initial prompt into a comprehensive file of feature requirements. In the harness's claude.ai clone example that meant over 200 features, each marked failing at the start. Coding agents then work through the list one feature at a time, and may only flip the passes field. Strongly worded instructions forbade removing or editing tests, which would hide missing or buggy functionality.

The Description Chain traces every requirement through four links: the user's own words, a product requirement, a technical spec, and finally the instruction Claude receives. Prompt engineering is only the last link. The builder translates at every step, and each step involves judgement calls the previous one did not make. The chain also has a hard limit: Claude cannot hear what the user did not say.

The chain is a diagnostic tool as well as a writing order. If the code works but the product does not, that is a description failure, and the fix belongs at the link that broke, not in the prompt. Tests are the most precise form of description, which makes them a useful signal. A passing test with an unhappy user means the test described the wrong intent. The break is upstream, between the user's words and the requirement.
