1. The discovery brief: users, needs, experience, constraints

Structured Discovery คือขั้นตอนที่ต้องทำก่อนเริ่มออกแบบระบบ เพื่อรวบรวมข้อเท็จจริงสำคัญเกี่ยวกับกลุ่มผู้ใช้และข้อจำกัดต่างๆ สำหรับใช้ตรวจสอบทุกการตัดสินใจในภายหลัง คำขอประเภท "คนไข้ต้องการเช็กเวลารอก่อนเดินทางมา" เป็นเพียงจุดเริ่มต้นของการพูดคุย ไม่ใช่ Requirement ที่แท้จริง หากต้องการเปลี่ยนให้เป็น Brief ต้องตอบคำถาม 4 ข้อนี้ให้ชัดเจน:

  • •
    Users: ระบุให้เจาะจงว่าเป็นคนไข้กลุ่มไหน Agent แผนกใด และมีใครเกี่ยวข้องกับระบบอีกบ้าง
  • •
    Needs: ผลลัพธ์ (Outcome) ที่ต้องการจริงๆ คืออะไร ซึ่งมักไม่ใช่ฟีเจอร์ที่ขอมาในตอนแรก
  • •
    Experience: ประสบการณ์ใช้งานที่ดีควรเป็นอย่างไร ให้เน้นอธิบาย Flow การใช้งานมากกว่าตัวฟีเจอร์
  • •
    Constraints: ข้อจำกัดด้านงบประมาณ, ทักษะทางเทคนิคของทีม Maintainer, อุปกรณ์ที่ผู้ใช้เข้าถึงได้ และข้อกำหนดด้าน Privacy

Process Map คือเทคนิค Discovery ที่ช่วยให้ Brief สะท้อนความเป็นจริง แนวคิดเรื่อง [เริ่มจาก Business Process ไม่ใช่เลือก Model ก่อน](lesson:1.1) จะถูกนำมาใช้จริงที่นี่ โดยแตก Need ของผู้ใช้ออกเป็นขั้นตอน ระบุ Stakeholder ในแต่ละจุด แล้วจึงพิจารณาว่า AI ควรเข้ามามีบทบาทในระดับใด ซึ่งแบ่งได้เป็น 3 บทบาท: Automation (AI ทำงาน แล้วมนุษย์ตรวจ), Augmentation (มนุษย์และ AI ร่วมกันทำ) และ Agency (AI ดำเนินการเองอย่างอิสระภายในขอบเขตที่กำหนด) กระบวนการนี้จะได้ตารางที่ตัดสินใจเรื่อง AI แยกเป็นรายแถว การตั้งคำถามเหมารวมทั้งระบบว่า "เราควรใช้ AI ไหม?" จะทำให้ข้ามการตัดสินใจทีละขั้นตอนที่จำเป็นไป

นอกจากนี้ มีอีก 3 คำถามสำคัญที่ต้องตอบใน Session แรกเสมอ เพราะไม่สามารถแนะนำ Model ได้เลยหากขาดคำตอบเหล่านี้:

  • •
    Capabilities: Model ต้องมีฟีเจอร์หรือความสามารถเฉพาะด้านใดบ้างเพื่อตอบโจทย์ลูกค้า
  • •
    Speed: Application ของลูกค้าต้องการ Latency หรือความเร็วในการตอบสนองระดับใด
  • •
    Cost: งบประมาณสำหรับการ Development และ Production Usage อยู่ที่เท่าไร

Structured discovery is the work you do before designing anything. You collect a fixed set of facts about who the system serves and what limits it, so every later decision can be checked against them. A request such as "patients need to check wait times before coming in" is where the conversation starts, not a requirement. To turn it into a brief, answer four questions in plain language:

- Users. Be specific. Which patients? What about the staff? Who else touches the system? - Needs. What outcome are they hoping for? This is not the same as the feature they asked for. - Experience. What does a great solution feel like to use? Describe the experience, not the features. - Constraints. Budget, the technical skill of the people who will run it, users' access to devices, and privacy requirements.

A process map is the discovery technique that keeps the brief honest. The idea that [you start from the business process, not the model](lesson:1.1) becomes a concrete step in discovery. Break the user's need into steps, name the stakeholder at each step, and only then decide what role AI plays in each one. There are three roles to choose from: Automation (AI does it and you check), Augmentation (you and AI work on it together) and Agency (AI acts with latitude inside boundaries you set). This produces a small table, one row per step, and the AI decision is made separately for each row. Asking "should we use AI here?" about the whole system skips that step-by-step choice.

Three more questions belong in every first session, because no model can be recommended without the answers:

- Capabilities. What specific features or capabilities must the model have to meet the customer's needs? - Speed. How quickly does the model need to respond inside the customer's application? - Cost. What is the budget, for development and for production usage?

Each answer comes from the customer's own workload. Facts such as how many people work in IT, which social platforms marketing uses, or the version number of an internal ticketing tool change none of the three. They tell you nothing about what the model must do, how fast it must answer, or what it may cost.

Both paths also use a second dial, effort. Effort is a per-request setting that controls how much reasoning the model does before it answers. Claude Haiku 4.5 suits the first path because it was built for interactive applications and high-volume processing. Good success criteria are specific, measurable, achievable and relevant. Specific means naming the target: "accurate sentiment classification" instead of "good performance". Measurable means a quantitative metric, or a well-defined qualitative scale that is applied consistently. Achievable means the target comes from industry benchmarks, prior experiments, AI research or expert knowledge, and does not demand more than current frontier models can deliver. Relevant means the criterion matches the application's purpose. Strong citation accuracy might be critical for a medical app and matter much less for a casual chatbot.

Safety is not exempt from measurement. "Safe outputs" cannot fail. "Less than 0.1% of outputs out of 10,000 trials flagged for toxicity by the content filter" can. The same applies to quality: "classify sentiments well" becomes an F1 score of at least 0.85 on a held-out set of 10,000 diverse Twitter posts, a 5% improvement over the current baseline.

The techniques in this section are run with Claude, acting as a coding agent that helps build the solution, before it writes any code. Claude can search a codebase and the internet quickly, so it finds your unknowns faster than you can alone. Some requirements cannot be collected by asking, because nobody knows to state them. Unknown unknowns are the questions you do not know to ask. In unfamiliar territory you may not know what good looks like, what has been tried before, or what potholes to avoid. Unknown knowns are criteria people only recognise when they see them, such as a layout or a visual style. Both are cheapest to find before implementation. Small changes in a feature or spec can produce drastically different code, and the coding agent finds earlier changes harder to revert.

Prototypes and mocks are spikes in practice. Each is a small throwaway build that answers one question, such as whether this layout works, without committing to a backend route or new state. Reviewing sample data exposes what interviews miss. Real inputs come in shapes nobody mentions in a meeting: irrelevant or nonexistent data, overly long input, poor or harmful user input, and ambiguous cases where even humans would struggle to agree. Asking the customer for a sample of production inputs early lets those cases shape the requirements, instead of appearing first in production.

Acceptance tests written before implementation give you, the customer and Claude one shared definition of done. Five to seven statements are usually enough. Each one must be concrete enough that a stranger could judge pass or fail. "The system is easy to use" fails that check. "A patient with a basic smartphone can find the current wait time in under 30 seconds without creating an account" passes it. The second version contains a user, a device, a time limit and a constraint, each of which came out of the discovery brief.

First drafts are usually written for humans to judge. Rewrite them so each one is something code could pass or fail, and add edge cases. For the clinic, those include the clinic being closed, having no data, and a wait time of zero.

For agent-built systems, the same discipline scales up to a feature list. A long-running harness is a multi-agent build in which one agent writes the feature list and later agents implement it. An initializer agent starts first and expands the user's initial prompt into a comprehensive file of feature requirements. In the harness's claude.ai clone example that meant over 200 features, each marked failing at the start. Coding agents then work through the list one feature at a time, and may only flip the passes field. Strongly worded instructions forbade removing or editing tests, which would hide missing or buggy functionality.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The Description Chain traces every requirement through four links: the user's own words, a product requirement, a technical spec, and finally the instruction Claude receives. Prompt engineering is only the last link. The builder translates at every step, and each step involves judgement calls the previous one did not make. The chain also has a hard limit: Claude cannot hear what the user did not say.

The chain is a diagnostic tool as well as a writing order. If the code works but the product does not, that is a description failure, and the fix belongs at the link that broke, not in the prompt. Tests are the most precise form of description, which makes them a useful signal. A passing test with an unhappy user means the test described the wrong intent. The break is upstream, between the user's words and the requirement.

    การเขียน Acceptance tests ก่อนลงมือ Implement ช่วยสร้าง Definition of Done ร่วมกันระหว่างคุณ, ลูกค้า และ Claude โดยทั่วไป 5-7 ข้อก็เพียงพอแล้ว แต่ละข้อต้องชัดเจนและจับต้องได้จนคนนอกสามารถตัดสินได้ทันทีว่า Pass หรือ Fail เช่น ข้อความอย่าง "ระบบต้องใช้งานง่าย" ถือว่าไม่ผ่านเกณฑ์ แต่ถ้าเป็น "ผู้ป่วยที่ใช้สมาร์ตโฟนทั่วไปสามารถดูเวลารอรับบริการปัจจุบันได้ภายใน 30 วินาทีโดยไม่ต้องสร้างบัญชี" แบบนี้ถือว่าผ่าน เพราะระบุทั้งกลุ่ม User, อุปกรณ์, กำหนดเวลา และข้อจำกัดที่ได้มาจากขั้นตอน Discovery brief ไว้อย่างครบถ้วน
  • •
    ร่างแรกมักเขียนขึ้นเพื่อให้มนุษย์เป็นคนประเมิน ให้ Rewrite ใหม่เพื่อให้กลายเป็นสิ่งที่ Code สามารถตรวจ Pass หรือ Fail ได้จริง พร้อมระบุ Edge cases เพิ่มเข้าไปด้วย สำหรับตัวอย่างคลินิก Edge cases จะครอบคลุมถึงกรณีที่คลินิกปิดทำการ, ระบบไม่มีข้อมูล หรือเวลารอรับบริการเป็น 0

#6 6. The Description Chain: จากคำพูดของ User สู่ Instruction ของ Claude

อ่านเนื้อหา ↗
  • •
    The Description Chain คือการแกะรอยทุก Requirement ผ่าน 4 ข้อต่อ: คำพูดของ User เอง, Product requirement, Technical spec และสุดท้ายคือ Instruction ที่ส่งให้ Claude การทำ Prompt engineering เป็นเพียงข้อต่อสุดท้ายเท่านั้น Developer จะต้องทำหน้าที่แปลความในทุกๆ ขั้นตอน และแต่ละขั้นตอนต้องอาศัยการตัดสินใจเชิงเทคนิคที่ขั้นตอนก่อนหน้าไม่ได้ระบุไว้
  • •
    Chain ยังมีข้อจำกัดที่ตายตัวคือ Claude ไม่สามารถรับรู้สิ่งที่ User ไม่ได้พูดออกมาได้
  • •
    Description chain ไม่ได้เป็นแค่ลำดับขั้นตอนการเขียนเท่านั้น แต่ยังเป็นเครื่องมือ Diagnostic อีกด้วย หาก Code รันผ่านแต่ Product ไม่ตอบโจทย์ นั่นแปลว่าเกิดความผิดพลาดในกระบวนการ Description และจุดที่ต้องเข้าไปแก้คือข้อต่อที่พัง ไม่ใช่การไปแก้ Prompt การเขียน Test ถือเป็นรูปแบบการ Describe ที่แม่นยำที่สุด จึงเป็นสัญญาณตรวจจับที่ดี
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (7 ข้อควรระวัง)
