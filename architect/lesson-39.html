1. GDPR มาจาก DPA ในสัญญาของคุณ

💡 แนวคิดหลักของหัวข้อนี้ (Core Concept)
  • ▸
    กฎระเบียบต่างๆ เข้าถึงคล็อดผ่านกลไกที่แตกต่างกัน และ GDPR เป็นสัญญา บทเสริมการประมวลผลข้อมูล (DPA) ของ Anthropic ซึ่งรวมถึงเงื่อนไขสัญญามาตรฐาน (SCCs) นั้นรวมอยู่ในเงื่อนไขการบริการเชิงพาณิชย์ องค์กรที่ยอมรับเงื่อนไขเหล่านั้นก็ยอมรับ DPA ด้วยเช่นกัน คุณไม่ต้องลงนามในสิ่งอื่นหรือเปิดใช้งานฟีเจอร์ใด ๆ HIPAA ทํางานแตกต่างกัน
  • ▸
    : ที่นั่น ผู้ดูแลระบบต้องยอมรับ BAA บนการ์ดในคอนโซล นโยบายความเป็นส่วนตัวของ Anthropic DPA และบทความช่วยเหลือของบริษัทอธิบายว่า Anthropic จัดการข้อมูลส่วนบุคคลอย่างไรเมื่อทําหน้าที่เป็นผู้ประมวลผลสําหรับลูกค้า
📌
สัญญาเป็นไปตามเส้นทางการเข้าถึง DPA ที่อธิบายไว้ที่นี่ครอบคลุมถึงผลิตภัณฑ์เชิงพาณิชย์ เช่น Claude API และ Claude for Work และแผนสำหรับผู้บริโภคก็มีข้อกำหนดของตนเอง หากคุณติดต่อ Claude ผ่านแพลตฟอร์มหรือผู้ให้บริการบุคคลที่สาม ข้อกำหนดในการให้บริการของแพลตฟอร์มนั้นจะควบคุมการใช้งานของคุณ การตรวจสอบ GDPR ของการปรับใช้ Bedrock จึงเริ่มต้นด้วยข้อตกลง AWS ไม่ใช่กับ DPA ของ Anthropic

DPA จะกำหนดความสัมพันธ์ของตัวประมวลผล ตำแหน่งที่การอนุมานทำงานและตำแหน่งที่จัดเก็บข้อมูลเป็นคำถามแยกต่างหากที่คุณตอบด้วยการกำหนดค่า

An EU company calls Claude through Amazon Bedrock and processes customers' personal data. Their compliance team starts a GDPR review of this deployment. Which agreement should the review start from?

คำแปลโจทย์:
บริษัทในสหภาพยุโรปโทรหา Claude ผ่าน Amazon Bedrock และประมวลผลข้อมูลส่วนบุคคลของลูกค้า ทีมงานด้านการปฏิบัติตามข้อกําหนดของพวกเขาเริ่มการตรวจสอบ GDPR สําหรับการปรับใช้นี้ การตรวจสอบควรเริ่มต้นจากข้อตกลงใด
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Official Explanation (คำอธิบายเฉลย):

The contract follows the access path. On Bedrock, AWS is the data processor and its terms govern the use, so the review starts with the AWS agreement, not Anthropic's DPA. GDPR also needs no Console setting or separate signature: the DPA comes with the Commercial Terms.

คำแปลไทย:
  • ▸
    สัญญาเป็นไปตามเส้นทางการเข้าถึง บน Bedrock นั้น AWS เป็นผู้ประมวลผลข้อมูลและมีข้อกำหนดควบคุมการใช้งาน
  • ▸
    ดังนั้นการตรวจสอบจึงเริ่มต้นด้วยข้อตกลง AWS ไม่ใช่ DPA ของ Anthropic GDPR ไม่จำเป็นต้องตั้งค่าคอนโซลหรือลายเซ็นแยกต่าง
  • ▸

Two independent settings decide where Claude handles your data. Inference geo decides where model inference runs, and you set it per request or as a workspace default. Workspace geo decides where data is stored at rest and where endpoint processing, such as image transcoding and code execution, takes place. Only "us" and "global" exist as inference geos, and "us" is the only workspace geo available.

The default is "global", which lets inference run in any available geography. Each response's usage.inference_geo field records where inference actually ran, so you can log it as evidence. The parameter works on Claude 4.6 and later models. Sending it to Claude Opus 4.5, Sonnet 4.5, Haiku 4.5 or anything older returns a 400 error. In the Batch API, each request can set its own value.

Workspace settings are how you turn a residency rule into something enforced. allowed_inference_geos rejects any geo not on the list. default_inference_geo fills in when a request leaves the parameter out. You set both through the Console or under the Admin API's data_residency field, and they apply to every key in the workspace, so one developer's missing parameter cannot send traffic outside the allowed geos. Organizations that had opted out of global routing under the old setting were migrated automatically to ["us"] for both settings.

Workspace geo is permanent. You choose it when you create the workspace, in the Workspace geo field on the Create workspace page, and you cannot change it afterwards. If the storage location is wrong, the fix is a new workspace. US-only inference costs 1.1x the standard rate on Claude 4.6 and later models. Rate limits are shared across all geos, so pinning to "us" does not give you extra capacity.

FedRAMP and DoD Impact Levels certify cloud services, not models. A Claude model is a software component that runs inside an authorized environment, and the customer's compliance posture comes from that hosting platform. "Is Claude FedRAMP High?" is therefore the wrong question. The right one is which environment you run Claude in and what that environment is authorized for.

Three FedRAMP High paths exist. Claude for Government is Anthropic's own FedRAMP High authorized application, with Anthropic as the contracting and billing party. Claude through Amazon Bedrock in AWS GovCloud (US) is approved for FedRAMP High and DoD IL4/5 workloads. Claude through Google Vertex with Assured Workloads is also FedRAMP High. Bedrock goes further: Claude is available in the AWS Secret region (IL6), and ITAR data can only be processed in Claude through Bedrock.

For an agency already inside a GovCloud authorization boundary, Bedrock in GovCloud is the direct fit. It runs on AWS-controlled infrastructure the agency already has, and AWS is the data processor. The Claude Platform on AWS documentation itself sends FedRAMP High and IL4/IL5 workloads to Bedrock. The standard Claude API is not on the list of FedRAMP-authorized paths. Neither is Claude Enterprise bought through AWS Marketplace, which is not FedRAMP authorized. Consumer plans are not a government path at all.

    3. ส่งคำขอเดียวกันพร้อมกับ inference_geo="global" ทำไม: สิ่งนี้ตรวจสอบว่า allowlist บล็อกการจราจรที่นักพัฒนาพยายามส่งไปที่อื่น คุณควรเห็นว่า: API ส่งกลับข้อผิดพลาดแทนที่จะรันคำขอ
  4. 4
    4. ส่งคำขอโดยไม่มีพารามิเตอร์ inference_geo ทำไม: สิ่งนี้ตรวจสอบว่า workspace default จะเติมค่าให้เมื่อคำขอไม่ส่งพารามิเตอร์ คุณควรเห็นว่า: response.usage.inference_geo อ่านค่า "us"
