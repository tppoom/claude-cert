1. GDPR comes from the DPA in your contract

กฎระเบียบต่างๆ เข้าถึงคล็อดผ่านกลไกที่แตกต่างกัน และ GDPR เป็นสัญญา บทเสริมการประมวลผลข้อมูล (DPA) ของ Anthropic ซึ่งรวมถึงเงื่อนไขสัญญามาตรฐาน (SCCs) นั้นรวมอยู่ในเงื่อนไขการบริการเชิงพาณิชย์ องค์กรที่ยอมรับเงื่อนไขเหล่านั้นก็ยอมรับ DPA ด้วยเช่นกัน คุณไม่ต้องลงนามในสิ่งอื่นหรือเปิดใช้งานฟีเจอร์ใด ๆ HIPAA ทํางานแตกต่างกัน: ที่นั่น ผู้ดูแลระบบต้องยอมรับ BAA บนการ์ดในคอนโซล นโยบายความเป็นส่วนตัวของ Anthropic DPA และบทความช่วยเหลือของบริษัทอธิบายว่า Anthropic จัดการข้อมูลส่วนบุคคลอย่างไรเมื่อทําหน้าที่เป็นผู้ประมวลผลสําหรับลูกค้า

สัญญาเป็นไปตามเส้นทางการเข้าถึง DPA ที่อธิบายไว้ที่นี่ครอบคลุมถึงผลิตภัณฑ์เชิงพาณิชย์ เช่น Claude API และ Claude for Work และแผนสำหรับผู้บริโภคก็มีข้อกำหนดของตนเอง หากคุณติดต่อ Claude ผ่านแพลตฟอร์มหรือผู้ให้บริการบุคคลที่สาม ข้อกำหนดในการให้บริการของแพลตฟอร์มนั้นจะควบคุมการใช้งานของคุณ การตรวจสอบ GDPR ของการปรับใช้ Bedrock จึงเริ่มต้นด้วยข้อตกลง AWS ไม่ใช่กับ DPA ของ Anthropic

DPA จะกำหนดความสัมพันธ์ของตัวประมวลผล ตำแหน่งที่การอนุมานทำงานและตำแหน่งที่จัดเก็บข้อมูลเป็นคำถามแยกต่างหากที่คุณตอบด้วยการกำหนดค่า

The contract follows the access path. On Bedrock, AWS is the data processor and its terms govern the use, so the review starts with the AWS agreement, not Anthropic's DPA. GDPR also needs no Console setting or separate signature: the DPA comes with the Commercial Terms.

คำแปลไทย: สัญญาเป็นไปตามเส้นทางการเข้าถึง บน Bedrock นั้น AWS เป็นผู้ประมวลผลข้อมูลและมีข้อกำหนดควบคุมการใช้งาน ดังนั้นการตรวจสอบจึงเริ่มต้นด้วยข้อตกลง AWS ไม่ใช่ DPA ของ Anthropic GDPR ไม่จำเป็นต้องตั้งค่าคอนโซลหรือลายเซ็นแยกต่างหาก เนื่องจาก DPA มาพร้อมกับข้อกำหนดเชิงพาณิชย์

คำแปล: บน Amazon Bedrock และ Agent Platform ของ Google Cloud ผู้ให้บริการคลาวด์คือผู้ประมวลผลข้อมูล โปรดดูเอกสารการเก็บรักษาข้อมูลและการปฏิบัติตามข้อกำหนดของแพลตฟอร์มเหล่านั้น

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Regulations reach Claude through different mechanisms, and GDPR's is a contract. Anthropic's Data Processing Addendum (DPA), which includes Standard Contractual Clauses (SCCs), is built into the Commercial Terms of Service. An organization that accepts those terms has also accepted the DPA. You do not sign anything else or enable a feature. HIPAA works differently: there, an admin has to accept a BAA on a card in the Console. Anthropic's privacy policy, the DPA and its help articles describe how Anthropic handles personal data when it acts as a processor for its customers.

The contract follows the access path. The DPA described here covers commercial products such as the Claude API and Claude for Work, and consumer plans have their own terms. If you reach Claude through a third-party platform or service provider, that platform's terms of service govern your use. A GDPR review of a Bedrock deployment therefore starts with the AWS agreement, not with Anthropic's DPA.

The DPA sets up the processor relationship. Where inference runs and where data is stored are separate questions that you answer with configuration.

2. Data residency: inference geo and workspace geo

The parameter works on Claude 4.6 and later models. Sending it to Claude Opus 4.5, Sonnet 4.5, Haiku 4.5 or anything older returns a 400 error. In the Batch API, each request can set its own value.

Workspace settings are how you turn a residency rule into something enforced. allowed_inference_geos rejects any geo not on the list. default_inference_geo fills in when a request leaves the parameter out. You set both through the Console or under the Admin API's data_residency field, and they apply to every key in the workspace, so one developer's missing parameter cannot send traffic outside the allowed geos. Organizations that had opted out of global routing under the old setting were migrated automatically to ["us"] for both settings.

Workspace geo is permanent. You choose it when you create the workspace, in the Workspace geo field on the Create workspace page, and you cannot change it afterwards. If the storage location is wrong, the fix is a new workspace. US-only inference costs 1.1x the standard rate on Claude 4.6 and later models. "Is Claude FedRAMP High?" is therefore the wrong question

FedRAMP and DoD Impact Levels certify cloud services, not models. A Claude model is a software component that runs inside an authorized environment, and the customer's compliance posture comes from that hosting platform. "Is Claude FedRAMP High?" is therefore the wrong question. The right one is which environment you run Claude in and what that environment is authorized for.

Three FedRAMP High paths exist. Claude for Government is Anthropic's own FedRAMP High authorized application, with Anthropic as the contracting and billing party. Claude through Amazon Bedrock in AWS GovCloud (US) is approved for FedRAMP High and DoD IL4/5 workloads. Claude through Google Vertex with Assured Workloads is also FedRAMP High. Bedrock goes further: Claude is available in the AWS Secret region (IL6), and ITAR data can only be processed in Claude through Bedrock.

For an agency already inside a GovCloud authorization boundary, Bedrock in GovCloud is the direct fit. It runs on AWS-controlled infrastructure the agency already has, and AWS is the data processor. The Claude Platform on AWS documentation itself sends FedRAMP High and IL4/IL5 workloads to Bedrock. The standard Claude API is not on the list of FedRAMP-authorized paths. Neither is Claude Enterprise bought through AWS Marketplace, which is not FedRAMP authorized. Consumer plans are not a government path at all.

    4. Send a request with no inference_geo parameter. Why: This checks that the workspace default fills in when a request leaves the parameter out. You should see: response.usage.inference_geo reads "us".
