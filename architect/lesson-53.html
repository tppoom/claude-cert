1. แยกประเภท Error ก่อนลงมือแก้

ข้อความ Error ของ Claude Code มักระบุชัดเจนว่าเป็น Error ประเภทไหน ซึ่งประเภทของ Error จะเป็นตัวกำหนด Action ถัดไปของคุณ หมวดหมู่หลักๆ ได้แก่ Server errors, Usage limits, Authentication, Network, Request errors, Command-line errors, Plugin errors และ Tool errors การจำแนกประเภทก่อนจะช่วยป้องกันความผิดพลาดที่เปลืองเวลาที่สุด เช่น การพยายาม Retry สิ่งที่ไม่มีวันสำเร็จ หรือการนั่งแก้ Prompt ทั้งที่จริงๆ ปัญหาเกิดจากระบบล่ม (Outage)

Claude Code retries failures that are transient and that happen before any useful output exists. Compaction summarizes earlier conversation history to free room in the context window; the mechanics are in [Compaction (server-side and client-side SDK)](lesson:2.4). Compaction can fail in a loop. If the context fills back to the limit straight after compacting, three times in a row, Claude Code stops with an "Autocompact is thrashing" error instead of burning more API calls. That error tells you something specific: whatever keeps refilling the window is still in the conversation, so compacting or retrying again won't help.

The fix is to stop the refill at its source. A typical case is reading a 40,000-line log in one go. Work through these steps in order:

1. Ask Claude to read the oversized file in smaller chunks, such as a specific line range or function. 2. Run /compact with a focus that drops the large output, for example /compact keep only the plan and the diff. 3. Move the large-file work to a subagent, so it runs in a separate context window. 4. Run /clear, but only if the earlier conversation is no longer needed.

Each step costs something different, so check what you are giving up. A focused /compact keeps only what you name, and anything else, like earlier hypotheses, survives only as summary. /clear drops the whole conversation, which is a poor trade in the middle of an investigation where the reasoning so far still matters. After recovering, check /context. If Messages is the largest row, some output is refilling the window again. If the other rows together are larger, what loads at startup leaves too little room, so trim it. /compact can also return Not enough messages to compact. even when the context is full, if a single large paste filled it.

    Compaction คือการสรุป History ช่วงก่อนหน้าเพื่อคืนพื้นที่ว่างใน Context Window (ศึกษากลไกเชิงลึกได้ที่ [Compaction (server-side and client-side SDK)](lesson:2.4)) แต่ Compaction อาจติด Loop ล้มเหลวได้ หากทำแล้ว Context ยังเต็มขีดจำกัดทันทีต่อเนื่องกัน 3 ครั้ง Claude Code จะหยุดทำงานพร้อมแจ้งเตือน "Autocompact is thrashing"
  • •
    ย้ายงานประมวลผลไฟล์ใหญ่ไปให้ Subagent จัดการ เพื่อแยกไปรันในอีก Context Window หนึ่ง 4
  • •
    แทนที่จะยิง API calls ทิ้งอย่างไร้ประโยชน์ Error นี้ส่งสัญญาณชัดเจนว่า ต้นเหตุที่ทำให้ Context ล้นยังคงค้างอยู่ใน Conversation การฝืนกด Compacting ซ้ำหรือ Retry ย่อมไม่ช่วยอะไร

#4 4. การกู้คืน Session ที่ติดปัญหา Refusal

อ่านเนื้อหา ↗
  • •
    ตัว Prompting Refusal อาจซ่อนอยู่ใน Customization ไม่ใช่ที่ Prompt ของคุณ หากข้อความระบุ Details: [reasoning_extraction] ให้ตรวจสอบว่ามี Instruction ที่สั่งให้ Claude แสดงกระบวนการ Reasoning ออกมาตรงๆ หรือไม่ ซึ่งอาจฝังอยู่ใน CLAUDE.md, Skills หรือ MCP Tool Descriptions หากต้องการยืนยัน ให้ลองยิง Prompt เดิมใน Session ผ่าน claude --safe-mode และหลังจากแก้ Customization เรียบร้อยแล้ว ให้เริ่ม Session ใหม่อีกครั้ง
  • •
    สำหรับการรันแบบ Headless จะต้องใช้วิธีอื่น เนื่องจากคำสั่ง rewind ไม่สามารถใช้งานได้ภายใต้แฟล็ก -p ให้แก้ไขโดย Retry ด้วย Rephrased Prompt ใน Session ใหม่โดยไม่ต้องใส่ --continue
  • •
    เมื่อเกิด Refusal ตัว Conversation จะถูกบล็อกตั้งแต่ Turn ที่ทริกเกอร์เป็นต้นไป (ศึกษาสาเหตุที่โมเดลปฏิเสธได้ที่ [built-in safety classifiers and refusal fallback](lesson:5.1)) การกู้คืนทำได้โดยย้อนกลับไปยังจุดก่อนหน้า Turn นั้น ด้วยการกด Esc 2 ครั้ง หรือรัน /rewind เพื่อกลับไปยัง Checkpoint ก่อนหน้า แล้วทำการ Rephrase ข้อความหรือเปลี่ยนแนวทางการ Prompt ใหม่ แต่หากระบุไม่ได้ว่า Turn ไหนเป็นสาเหตุ ให้ใช้ /clear เพื่อเริ่ม Conversation ใหม่ใน Project เดิม โดย History เดิมจะยังคงบันทึกอยู่บน Disk และเรียกใช้งานต่อได้ผ่าน /resume

#5 5. การระบุ Agent ที่ติดขัด (Stuck) หรือติด Loop ใน Multi-Agent Session

อ่านเนื้อหา ↗
  • •
    เมื่อ Multi-Agent Session หยุดนิ่งหรือไม่คืบหน้า สิ่งแรกที่ต้องทำคือตรวจสอบว่า Agent ตัวไหนค้างอยู่ก่อนที่จะตัดสินใจดำเนินการใดๆ Claude Code จะแท็กแต่ละ OTEL span ของ `claude_code.tool` ด้วย `agent_id` และ `parent_agent_id` โดย Spans ของ Background Subagents จะซ้อนอยู่ใต้ Agent tool span ที่เป็นตัวเรียกใช้งาน ให้ไล่ตาม ID เหล่านี้ลงไปตามโครงสร้าง Tree
  • •
    Agent ตัวที่ Span ยังคงเปิดค้างอยู่ (stays open) หรือเรียก Tool ซ้ำๆ เดิมไม่รู้จบ คือตัวที่กำลัง Stuck หรือติด Loop
  • •
    แม้ไม่มี Tracing Backend ก็ตรวจสอบโครงสร้าง Tree ได้ด้วยคำสั่ง `/agents` ซึ่งจะแสดง Nested Subagent Tree ขณะกระจายงาน พร้อมจำนวน Descendant ในแต่ละแถวและ Path ย้อนกลับไปยัง Main Agent
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (3 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
Claude Code retries every 429, so a 429 always clears if you wait.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Claude Code ไม่ได้ Retry ทุกกรณีของ 429 ระบบจะ Retry เฉพาะ Throttles ชั่วคราวเท่านั้น หากเป็น 429 จาก Spend cap เต็ม จะยังคง Fail ต่อไปจนกว่าจะมีการปลดล็อกสิทธิ์ใช้งาน การรอเฉยๆ จะไม่ช่วยอะไร
Only temporary throttles are retried. A spend-cap 429 keeps failing until access resumes.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
Autocompact thrashing means compaction needs more attempts, so keep retrying until the large file fits.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Autocompact thrashing แปลว่าระบบแค่ต้องการรอบ Compaction เพิ่ม ให้กด Retry ไปเรื่อยๆ จนกว่าไฟล์ใหญ่จะใส่พอ เพราะ Claude Code ตั้งใจหยุดทำงานเมื่อพบว่า Context กลับมาเต็มทันทีหลัง Compaction ติดกัน 3 ครั้ง ทางแก้คือต้องจัดการที่ Input ซึ่งทำให้เกิดปัญหา เช่น อ่านไฟล์เป็น Chunks, ใช้ /compact แบบระบุ Focus หรือส่งงานต่อให้ Subagent แทน
Claude Code stops on purpose after the context refills straight after compacting three times in a row. The input that keeps refilling it has to change: read in chunks, use a focused /compact, or hand the work to a subagent.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
Apply it to your own work The /agents tree shows one subagent whose descendant count keeps growing while the others have finished. What would you check in its spans before cancelling it?
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
เมื่อ `/agents` tree แสดงว่ามี Subagent ตัวหนึ่งที่จำนวน descendant เพิ่มขึ้นเรื่อยๆ ขณะที่ตัวอื่นทำงานเสร็จหมดแล้ว ควรรีบกดยกเลิกทันที? ไม่จริง: ก่อนกดยกเลิก ให้ตรวจสอบ spans ของ Subagent ตัวนั้นก่อน โดยดูว่า Spans ค้างเปิดอยู่ (`claude_code.tool` span stays open) หรือกำลังเรียก Tool เดิมวนซ้ำๆ เพื่อยืนยันว่าติด Infinite Loop/Stuck จริง หรือเป็นเพียง Task ขนาดใหญ่ที่ต้องแตก Subagents ทำงานคู่ขนานกันตามปกติ
