💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A Claude Code error message usually tells you which category it belongs to, and the category decides your next move. The error reference groups messages into server errors, usage limits, authentication, network, request errors, command-line errors, plugin errors and tool errors. Deciding the category first keeps you from the most expensive mistake: retrying something that will never succeed, or rewriting a prompt to fix what was really an outage.

The HTTP status codes underneath follow the same split. A 529 overloaded_error means the API is temporarily overloaded. A 429 rate_limit_error can mean a rate limit or a reached spend cap. A 400 invalid_request_error means the request's format or content is wrong. If a failure persists and you need support, include the request ID from the error: every API response carries one.

คลิกดูเฉลยคำตอบพร้อมคำอธิบาย (Click to view answer & explanation) ▼
คำตอบที่ถูกต้อง: ตัวเลือก B

A connection broken by sleep counts as a dropped connection, which is transient, so Claude Code retries it with backoff. The content-filter re-send happens only once, so a second block is final. Context-limit and login errors name a fix that you have to apply, and waiting won't clear them.

“Claude Code detects was broken by your computer going to sleep partway through a request. Claude Code counts it as a dropped connection”

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Claude Code retries failures that are transient and that happen before any useful output exists. Server errors, overloaded responses and request timeouts that arrive before any of Claude's response has streamed are retried with backoff. So are dropped connections, including one broken because your computer went to sleep. Temporary 429 throttles are retried too. A message like Waiting for API response · will retry in means this is already happening, and you should wait instead of intervening.

Some retries are deliberately capped:

- Stalled stream: a response stream that stalls before any response arrives is aborted and streamed again at most once. - Error after thinking: a server error that arrives after Claude finishes thinking but before any text or tool call is retried up to two times. - Content filter: a response stopped by the output content filter is re-sent once. A second block shows Output blocked by content filtering policy.

Everything that needs a change from you stays failed. A spend-cap 429 has no retry-after header and keeps failing until access resumes. Authentication and request errors name their own fix, such as /login or /compact or /clear. Waiting longer won't clear either kind.

3.Recovering from context pressure and autocompact thrashing

สาระสำคัญและหลักการทำงานของหัวข้อนี้: หัวข้อนี้เจาะลึก Recovering from context pressure and autocompact thrashing ตามมาตรฐานและพิมพ์เขียวการสอบของ Anthropic โดยมุ่งเน้นการทำความเข้าใจสถาปัตยกรรมเชิงลึก ข้อดีข้อเสียทางเทคนิค และแนวทางการปฏิบัติจริงในโปรดักชัน

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 57065

During a long debugging session, Claude Code raises "Autocompact is thrashing: the context refilled to the limit..." immediately after automatic compaction completes, and it stops retrying. The team was asking Claude to read an entire 40,000-line production log file to find the root cause of an outage. What is the most effective way to recover and continue the investigation?

A Raise CLAUDE_CODE_MAX_RETRIES so Claude Code keeps retrying compaction until the log file finishes loading successfully.
B Ask Claude to read the log file in smaller chunks, such as a specific line range, or delegate the analysis to a subagent instead.
C Set DISABLE_AUTO_COMPACT so Claude Code stops summarizing history and keeps the entire log output available for reference.
D Run /clear to discard the conversation, then paste only the final error line from the log file into a fresh session.
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก B
ตัวเลือก A: ไม่ถูกต้อง

Incorrect. CLAUDE_CODE_MAX_RETRIES governs retries of failed API requests, not the compaction-thrashing loop. Thrashing happens because the file itself refills the context after each compaction, so retrying compaction more times does not solve the underlying problem.

ตัวเลือก B: ถูกต้อง

Correct. Auto-compaction succeeded but the oversized file output immediately refilled the context window several times in a row, so Claude Code stopped retrying to avoid wasted API calls. Reading the file in smaller chunks or moving the work to a subagent's separate context window is the documented recovery path.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Disabling auto-compaction removes the safeguard that prevents the context window from overflowing, so it would make the thrashing problem worse, not better, since the full log would still need to fit in context.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. This is more drastic than necessary and discards useful investigation context. The documented recovery steps are to chunk the file, use a targeted /compact, or delegate to a subagent, not to abandon the conversation entirely.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Compaction summarizes earlier conversation history to free room in the context window; the mechanics are in [Compaction (server-side and client-side SDK)](lesson:2.4). Compaction can fail in a loop. If the context fills back to the limit straight after compacting, three times in a row, Claude Code stops with an "Autocompact is thrashing" error instead of burning more API calls. That error tells you something specific: whatever keeps refilling the window is still in the conversation, so compacting or retrying again won't help.

The fix is to stop the refill at its source. A typical case is reading a 40,000-line log in one go. Work through these steps in order:

1. Ask Claude to read the oversized file in smaller chunks, such as a specific line range or function. 2. Run /compact with a focus that drops the large output, for example /compact keep only the plan and the diff. 3. Move the large-file work to a subagent, so it runs in a separate context window. 4. Run /clear, but only if the earlier conversation is no longer needed.

Each step costs something different, so check what you are giving up. A focused /compact keeps only what you name, and anything else, like earlier hypotheses, survives only as summary. /clear drops the whole conversation, which is a poor trade in the middle of an investigation where the reasoning so far still matters. After recovering, check /context. If Messages is the largest row, some output is refilling the window again. If the other rows together are larger, what loads at startup leaves too little room, so trim it. /compact can also return Not enough messages to compact. even when the context is full, if a single large paste filled it.

5.Finding the stuck or looping agent in a multi-agent session

ใน Claude Agent SDK การทำงานหลักถูกขับเคลื่อนด้วยฟังก์ชัน query() ซึ่งทำหน้าที่จัดการวงรอบเอเจนต์ (Agentic Loop) ให้อัตโนมัติ:

วงรอบการทำงานของ query() Loop:
  1. ส่งพร้อมต์และประวัติการสนทนาไปยัง Claude API
  2. รับผลลัพธ์จากโมเดล หากโมเดลส่ง stop_reason: "tool_use" ระบบจะรันเครื่องมือที่ระบุ
  3. นำผลลัพธ์ของเครื่องมือส่งกลับไปให้ Claude ประเมินซ้ำ
  4. ลูปนี้จะหมุนต่อเนื่องไปเรื่อยๆ จนกระทั่งโมเดลส่ง stop_reason: "end_turn" โดยไม่มีการเรียกเครื่องมือเพิ่ม

When a multi-agent session stops making progress, first find which agent is stuck before deciding what to do. How spans and traces work is covered under [reading a trace: spans across a run and its subagents](lesson:4.6). Claude Code tags each claude_code.tool OTEL span with agent_id and parent_agent_id, and background subagent spans nest under the Agent tool span that dispatched them. Follow those IDs down the tree. The agent whose span stays open, or that keeps producing the same tool calls, is the one stuck or looping.

You can see the same tree without a tracing backend. /agents shows the nested subagent tree as work fans out, with a descendant count on each row and a path back to main. Runaway nesting has a ceiling: subagent chains are capped at five levels deep. Once you've found the stuck agent, press Ctrl+C to try to cancel the current operation. If the session doesn't respond, close the terminal and restart.
