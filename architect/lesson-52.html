💡 แนวคิดหลักสำคัญ (Key Concept)

Diagnose from what loaded, not from what you wrote — A file on disk only tells you what someone meant to configure. Before you edit anything, ask the running session what it actually loaded and which source won. Then narrow down the cause by turning customizations off.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Most Claude Code complaints like "it ignores my settings" come down to one of three things: the configuration was never read, it was read and then overridden, or it was read and matched nothing. Re-reading your own JSON can't tell these apart, because the file looks correct in all three cases. The session can tell them apart, since each kind of customization has a slash command that reports what is in effect right now.

Pick the command that matches the symptom. If a hook never fires, open /hooks. If a deny rule doesn't block, open /permissions. If you can't tell which layer is responsible, /status lists every settings source, including managed settings that no user file can override. A blank or unexpected result is your first real clue: you now know whether the problem is about loading, precedence or matching.

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

Predict firstAn admin sets a key in the project's .claude/settings.json. One engineer's sessions keep behaving as if a different value were set, and /status shows the project settings are being read. Where is the most likely cause?The same key is set in the engineer's .claude/settings.local.jsonThe project settings only apply to directories created after the key was addedThe engineer's shell doesn't export a matching environment variable, so the project file is never consultedThe project file is being read, so this is a precedence problem, not a loading problem. A local settings file overrides the shared project file.“settings.local.json overrides settings.json, and both override ~/.claude/settings.json.”Source: code.claude.com

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

Exam trapIf /status shows the project settings.json is being read, every value in it must be in effect.Why is that wrong?Being read is not the same as winning. The same key in settings.local.json overrides the project file, which in turn overrides the user file.

คลิกดูเฉลยคำตอบพร้อมคำอธิบาย (Click to view answer & explanation) ▼
คำตอบที่ถูกต้อง: ตัวเลือก C

The rule loaded correctly. It just matches the literal command string, so a different command that deletes files gets past it without any error. A hard guarantee needs a PreToolUse hook or the sandbox. ~/.claude.json holds app state, not permissions.

Precedence explains most "ignored" settings values. The order is settings.local.json, then the project settings.json, then the user ~/.claude/settings.json. A value one engineer keeps in their local file wins over what the team committed, and /status will still list the project file as active. A second common mistake is putting configuration in the wrong file. ~/.claude.json holds app state and UI toggles, while permissions, hooks and env belong in ~/.claude/settings.json. A rule added to the first file is never applied.

Writing that guidance well is covered under [CLAUDE.md as implementation guidance](lesson:6.4). Two loading rules catch people out. A subdirectory's CLAUDE.md loads on demand, not at session start, so it only appears once Claude reads a file in that subdirectory. Subagents are the other case: the built-in Explore and Plan agents skip CLAUDE.md at startup, so restate a critical instruction in the delegating prompt. These causes come up again and again:

- Standalone file: the hook sits in its own file. Project and user hooks go under the "hooks" key in settings.json; only plugins load a separate hooks/hooks.json. - Array matcher: the matcher is a JSON array instead of one string. Authentication, model selection, built-in tools and permissions keep working. If the problem goes away, one of the disabled customizations is responsible. The same test works for runaway CPU or memory: if usage drops in safe mode, start looking at plugins, MCP servers and hooks.

A clean configuration directory goes further and tells you which layer is at fault. Create an empty directory, then start Claude Code there with its config pointed at a fresh location and only user settings sources enabled:

Then reproduce the problem. If it's gone, the cause is in your user or project configuration. Copy ~/.claude.json and the files in ~/.claude into the clean directory one at a time until the problem comes back. If none of them brings it back, move to the project directory and launch without --setting-sources user. If the problem persists even in the clean setup, the cause is outside user and project configuration. Run /status to check for managed settings, then look at your shell's environment variables.
