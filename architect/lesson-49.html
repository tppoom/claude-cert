An organization sets its Claude Code policy only in the claude.ai admin console, as server-managed settings. One team runs Claude Code through another provider, with ANTHROPIC_BASE_URL pointed away from Anthropic's API. What happens to that team's policy?

คำตอบที่ถูกต้อง: ตัวเลือก A
💡 คำอธิบายเฉลยภาษาไทย (Thai Explanation):

Claude Code จะดึงการตั้งค่าระยะไกลเฉพาะเมื่อเซสชันตรวจสอบสิทธิ์โดยตรงกับ API ของ Anthropic หรือลงชื่อเข้าใช้ผ่านเกตเวย์ สำหรับผู้ให้บริการรายอื่น จะข้ามแหล่งที่มานั้นและเริ่มที่แหล่งถัดไป ดังนั้นเครื่องเหล่านั้นจึงจำเป็นต้องมี MDM หรือไฟล์

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Managed settings are the top settings scope. Nothing a developer writes in their own files can override them, which makes them the only place to enforce organization policy. The policy is a JSON document with the same keys as any settings file. The hard part is getting it onto every machine and keeping it current.

Choose by what you already run. Server-managed settings give a claude.ai organization one place to change policy without touching any device. MDM fits fleets you already manage with Jamf or Intune. The file is for Linux hosts, machines without MDM, and images you build yourself. On the developer's machine, the terminal, the IDE extensions and Agent SDK sessions all read these sources. The SDK reads them even when settingSources excludes the user, project and local files.

Two gaps catch teams out. First, a cloud session in an Anthropic-hosted environment cannot see a device's MDM profile or file, so its policy has to come from server-managed settings. Second, server-managed settings are fetched only when the session authenticates directly to Anthropic's API, or through a gateway login. A developer on another provider, or with ANTHROPIC_BASE_URL pointed elsewhere, never receives them. Those machines need MDM or the file.

By default, managed sources do not combine. Under first-wins, Claude Code walks down the ranking (remote, then MDM, then files, then HKCU) and uses the first source that carries a policy key. It ignores every source below that one, with no warning. A source that sets only the two control keys, wslInheritsWindowsSettings and managedSourcesBehavior, does not count as delivering policy, so Claude Code moves on to the next source.

/status is how you find a skipped source. It names the source Claude Code used and the ones it skipped. When a deny rule you shipped by MDM seems to have vanished, /status usually shows that a server-managed policy took priority over it.

Setting managedSourcesBehavior to merge (Claude Code v2.1.242 or later) applies every admin source that delivers a policy key. On most keys, the higher-ranked value wins. Lists union, and locks take the strictest value. Some keys are read from every admin source even under first-wins. For example, an entry in deniedMcpServers from any admin source applies. Within the file-based source, managed-settings.d/*.json and managed-settings.json always merge: a later file replaces single values, lists combine with duplicates removed, and nested blocks such as env merge key by key.

Timing matters during a rollout. Most changes reach running sessions on the schedule in the delivery table. A server-managed change to a setting that needs approval, such as a hook or an env variable, waits until the developer accepts a dialog. A few keys, including requiredMinimumVersion, take effect only at the next session start.

3. Locking permissions, MCP servers, plugins and hooks

A managed deny rule cannot be overridden, but by default developers can still add their own allow rules for anything the policy does not deny. Locks close that gap. Each lock tells Claude Code to ignore a whole category of configuration from user and project sources. The most important one for permissions is allowManagedPermissionRulesOnly, which makes managed settings the only source of permission rules. With it set, nothing a developer writes in their own files can loosen the policy.

These keys sound alike but do not substitute for each other. disableBypassPermissionsMode removes only the bypass mode. It leaves user allow rules untouched. allowManagedMcpServersOnly locks the MCP allowlist, not tool permissions. strictKnownMarketplaces limits where plugins come from. Pick the key that matches the risk you are closing. The same managed policy can also set which permission mode sessions start in through permissions.defaultMode, and can remove auto mode with permissions.disableAutoMode. For what each mode means for human review, see [Permission modes: how much the human reviews](lesson:5.3).

The MCP lock behaves differently under first-wins. A true for allowManagedMcpServersOnly in any admin source turns the lock on. The allowlist then comes from the highest-ranked admin source that sets one. If no admin source sets a list, every server that passes the denylist loads. Locking without shipping a list is therefore weaker than it looks.

Provider comes first, because it decides how developers authenticate and how usage is billed. Claude for Teams or Enterprise is the default recommendation. Console suits API-first, pay-as-you-go teams. Bedrock, Google Cloud's Agent Platform and Foundry let a team inherit existing cloud compliance controls and billing. Once you have chosen, allowedProviders (v2.1.285 or later) refuses any session on a provider that is not on the list, checking at startup, at login and on the next API call.

Setting model in managed settings only chooses where sessions start. A managed model is a starting default, not a lock. To restrict models, use availableModels, which filters the picker. Add enforceAvailableModels to make the auto-selected default obey the list as well. Across managed sources, availableModels never merges, so the list from the source that applies is the whole list. maxEffortLevel caps effort, and the lowest cap across admin sources wins.

Version pins come in two strengths. minimumVersion stops auto-update from installing anything below an org-wide floor, so it only blocks downgrades. requiredMinimumVersion and requiredMaximumVersion refuse to start Claude Code outside an approved range. Even these do not end a session that is already running, so a terminal left open for weeks can lag behind a rollout.

Spend sits alongside these pins. The general mechanics are in [Rate limits and spend caps](lesson:6.3). For a Claude Code team, spend and rate limits are set in organization settings on Teams or Enterprise, as workspace limits on Console, or through cloud budget controls or a gateway with per-user limits on third-party clouds. To see usage, use OpenTelemetry export, which works on every provider, or the analytics dashboard.
