1. Why decomposition improves results (ทำไมการแยกส่วนงานจึงให้ผลลัพธ์ที่ดีกว่า)

การใช้ model call เดียวทำงานทุกอย่างทำให้โมเดลโฟกัสแต่ละส่วนได้ไม่เต็มที่ เช่น หาก Prompt เดียวต้องทั้งคัดกรองเนื้อหาที่ไม่ปลอดภัยและตอบคำถามไปพร้อมกัน คุณภาพของทั้งสองงานจะแย่ลง การแยกงาน (Decomposition) เพื่อให้แต่ละ call รับผิดชอบเพียงเรื่องเดียวจึงเป็นหัวใจพื้นฐานของทุก Pattern ในบทนี้ วิธีนี้เหมาะที่สุดเมื่อมีงานย่อยที่ขอบเขตชัดเจนหลายงานประกอบกันเพื่อเป้าหมายรวม

ความแตกต่างของแต่ละ Pattern อยู่ที่ว่า "ใครเป็นผู้กำหนด subtasks" สำหรับ Prompt Chaining, Routing และ Parallelization นักพัฒนาจะกำหนด subtasks ตายตัวไว้ตั้งแต่ตอนเขียนโค้ด แต่ใน Orchestrator-Workers โมเดลจะเป็นผู้วางแผน subtasks เองแบบ dynamic ตาม input แต่ละรอบ ณ Run time ซึ่งเป็นหลักการเดียวกับ [Workflows versus agents](lesson:1.3) นั่นคือ หากสามารถระบุ subtasks ล่วงหน้าได้ทั้งหมด ให้เขียนเป็น Code แต่ถ้าขึ้นอยู่กับ Input ที่เข้ามา ให้ส่งต่อให้ Model เป็นผู้วางแผน

การแยกส่วนงานไม่ได้ฟรี ทุก call ที่เพิ่มขึ้นมาแลกมาด้วย Latency และ Token Cost เสมอ อีกทั้งทุกรอยต่อของการส่งต่องาน (handoff) อาจทำให้ Context หล่นหายได้ แต่ละ Pattern ถัดไปจะระบุต้นทุนและเกณฑ์ความคุ้มค่าในการเลือกใช้

A support assistant uses one prompt to screen each request for unsafe content and also answer it. Both the screening and the answers are mediocre. The team moves screening into its own call, separate from the call that answers. Why should this improve results?

คำแปลโจทย์:
ผู้ช่วยฝ่ายสนับสนุนใช้พรอมต์เดียวเพื่อคัดกรองคำขอแต่ละรายการสำหรับเนื้อหาที่ไม่ปลอดภัยและตอบด้วย ทั้งการคัดกรองและคำตอบนั้นปานกลาง ทีมงานจะย้ายการคัดกรองไปเป็น API Call ของตนเอง โดยแยกจาก API Call ที่รับสาย เหตุใดจึงควรปรับปรุงผลลัพธ์นี้
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Official Explanation (คำอธิบายเฉลย):

Decomposition helps because a call that does one job can give that job its full attention. It does not save time or tokens, because every extra call adds both. Here the designer fixed the subtasks while building the system. Run-time planning applies only to orchestrator-workers.

คำแปลไทย:
  • ▸
    Task Decomposition (การแตกงานย่อย) ช่วยได้เนื่องจากการเรียกที่ทำหน้าที่หนึ่งสามารถให้ความสนใจกับงานนั้นได้อย่างเต็มที่ มันไม่ได้ประหยัดเวลาหรือโทเค็น
  • ▸

One model call that has to do everything gives each part of the job less attention. If a single prompt has to screen a request for unsafe content and also answer it, both jobs get worse. Splitting the work so that each call handles one consideration is the basic move behind every pattern on this page. Decomposition fits best where several well-scoped tasks feed one overall goal.

The patterns differ in who decides the subtasks. In prompt chaining, routing and parallelization, the designer fixes the subtasks when the system is built. In orchestrator-workers, a model works them out at run time for each input. This is the same line drawn in [Workflows versus agents](lesson:1.3), seen here as a decomposition choice: if you can list the subtasks today, write them into code. If they depend on the input, let a model plan them.

Decomposition is not free. Every extra call adds latency and tokens, and every handoff is a place where context can get lost. Each pattern below says what it costs and when that cost is worth paying.

Prompt chaining splits a task into a fixed sequence of steps. Each model call takes the previous call's output as its input. Between steps you can add programmatic checks, called gates, that confirm the process is still on track before the next call runs. Two standard examples: writing marketing copy and then translating it, or writing an outline, checking it against criteria, and only then writing the document.

Chaining fits when a task splits cleanly into fixed subtasks. A worked case: turning a quarterly performance summary into a table takes four calls. The first extracts each metric with its value. The second converts the values to one format. The third sorts them in descending order. The fourth renders a markdown table. Each step is trivial for the model, and a code check between steps (for example, "did step 1 return every metric?") catches a failure before it spreads to the later steps.

The same shape appears in Claude Code dynamic workflows. The first agent call returns a list of files in a declared schema, and that list drives the next step, which audits each file.

Routing คือการทำ Classification ให้กับ Input ก่อน แล้วจึงส่งต่อไปยังขั้นตอนถัดไปที่ออกแบบมาเฉพาะสำหรับหมวดหมู่นั้นๆ ซึ่งแต่ละขั้นตอนสามารถใช้ Prompt, Tools หรือ Model ของตัวเองได้ เหตุผลหลักที่ต้องใช้ Routing คือเพื่อแก้ปัญหา Interference เพราะหากใช้ Prompt เดียวรองรับ Input ทุกประเภท การปรับแต่ง Prompt ให้ดีกับเคสหนึ่งมักส่งผลให้ประสิทธิภาพกับเคสอื่นแย่ลง ตัวอย่างเช่น ระบบ Customer Service อาจ Route คำถามทั่วไป, คำขอคืนเงิน และ Technical Support แยกออกเป็น 3 Process อิสระ โดยแต่ละ Process มี Prompt และ Tools เป็นของตัวเอง

Routing จะได้ผลดีเมื่อแต่ละหมวดหมู่มีความแตกต่างกันชัดเจน และระบบสามารถจำแนกประเภทได้อย่างแม่นยำ ไม่ว่าจะใช้ LLM หรือ Traditional Classifier เพราะหากเกิด Misclassification งานจะถูกส่งต่อไปยัง Specialist ที่ไม่ได้ถูกออกแบบมาเพื่อรองรับงานนั้น

Routing classifies an input first, then sends it to a follow-up step built for that category. That step can use its own prompt, its own tools or its own model. The reason to route is interference. If one prompt has to serve every kind of input, tuning it for one kind tends to make it worse for the others. A customer-service system might route general questions, refund requests and technical support into three separate processes, each with its own prompt and tools.

Routing works when the categories really are distinct and classification can be done accurately, whether by an LLM or by a traditional classifier. If inputs are often misclassified, every downstream specialist receives work it was not built for.

Routing is also the place to choose a model for each subtask. Model classes differ mainly in how hard a problem they can reliably handle and what that capability costs in price and speed. Easy, common requests go to a small, cheap model. Hard or unusual ones go to a more capable model. Take a support pipeline with two subtasks: classifying a large stream of tickets, and drafting detailed remediation plans for the few that need engineering. Classification goes to Haiku. Remediation, which is multi-step and often new, goes to a more capable class such as Opus. Running everything on the largest model pays its price for every routine classification. Running everything on Haiku asks it to carry work beyond what it reliably handles. Assigning models at random is not routing, because nothing about the input decides where it goes. The broader trade-offs are covered in [model selection trade-offs](lesson:2.1).

With agents, routing means sending work to a specialist agent rather than a specialist prompt. In the Agent SDK, each subagent definition has an optional model field, so a cheap classifier and an expensive drafter can live in the same system.

Parallelization runs several model calls at the same time and combines their outputs in code. It comes in two forms that solve different problems.

- Sectioning splits a task into independent subtasks that run side by side. For example, one instance answers the user while another screens the request for inappropriate content. This tends to beat one call doing both. Automated evals can also be sectioned, with each call grading a different aspect of the output. - Voting runs the same task several times and combines the answers to get more confidence. For example, several prompts review the same code for vulnerabilities and flag it if any of them find a problem. Content moderation can also use different vote thresholds to balance false positives against false negatives.

Speed and cost need to be kept apart. Independent subtasks that run concurrently finish in the time of the slowest one, not the sum of all of them, so a single sectioned step takes less wall-clock time. Across a whole multi-agent system the picture is different. Such systems typically use 3 to 10 times more tokens than one agent, and they often take longer overall because there is so much more computation. Choose parallelization for coverage or confidence, and expect a larger bill.

In orchestrator-workers, a central model reads the task, decides which subtasks it needs, hands each one to a worker model, and combines the results. It can look like sectioning, but the subtasks are not pre-defined. The orchestrator chooses them for each input. A coding change is the standard case: you cannot know in advance how many files need editing or what each edit is.

That flexibility has costs. Each run makes N+1 calls: one to the orchestrator and one per worker. The decomposition is only as good as the orchestrator's plan, so the orchestrator prompt is where most of the engineering effort goes. Cost can be managed by splitting models, with a capable model such as Opus planning and Haiku workers executing. Do not use the pattern for simple single-output tasks, for latency-critical paths, or when the subtasks are always the same. In that last case, pre-defined parallelization does the job with less machinery.

Claude Managed Agents provides this as dynamic workflows. The agent writes a program that runs many agents in phases and combines their results, and the server runs it in the background. Audits, migrations, deep research and cross-checking are the typical uses. Every agent in a run uses tokens, so set a session budget.

In the Claude Agent SDK, decomposition takes the form of subagents. You define them with the agents option in code, or as markdown files in.claude/agents/. The main agent invokes them through the Agent tool. Each subagent runs in its own conversation, and its intermediate tool calls stay inside that conversation; only its final message returns to the parent. That isolation is the reason [Coordinator pattern and isolated subagent context](lesson:1.4) applies even when nothing runs in parallel. The main reason to split may be to keep pages of tool output out of the main agent's context.

Three fields carry the decomposition. description is a natural-language statement of when to use the agent, and the orchestrator reads it to decide where each piece of work goes. tools is the allowed list; if you leave it out, the subagent inherits every tool available to subagents, so leaving it blank removes the scoping. prompt is the specialist's system prompt.

Take a codebase audit with three dimensions (security vulnerabilities, code quality and test coverage), each needing different tools and a different focus. The decomposition is an orchestrator plus three subagents, each with a description and a tool set matched to its dimension. A security scanner, a style checker and a coverage checker can then run at the same time instead of one after another. Compare the alternatives:

- One prompt asking the main agent to do all three in sequence. Every dimension's tool output builds up in a single context, and quality drops as the context grows. - One MCP server exposing all the checks as tools for the main agent. This adds tools without separating anything. An agent loaded with tools across unrelated domains confuses which domain applies, and with roughly 20 or more tools it struggles to pick the right one. - A larger context window plus extended thinking. More room does not solve the problem. Response quality can degrade as context grows, so more space for clutter makes the clutter worse.

7. การย้าย Tight Tool Loop ไปประมวลผลในโค้ด (Moving a tight tool loop into code)

บางครั้ง Overhead หรือต้นทุนที่สูงไม่ได้เกิดจาก Subtasks แต่เกิดจากการเรียก Tool ซ้ำๆ หากสเต็ปใดต้องยิง Tool ย่อยๆ หลายสิบครั้งใน Loop การใช้ Tool Use แบบมาตรฐานจะต้องทำ Round Trip ผ่าน Model ทุกครั้ง และผลลัพธ์แต่ละครั้งจะสะสมใน Context การใช้ Programmatic Tool Calling จะเข้ามาตัด Overhead ตรงนี้ โดย Claude จะเขียนโค้ดเพื่อเรียกใช้ Tools เหล่านั้นภายใน Code Execution Container ทำให้ Loop ทำงานจบใน Container ทันที แทนที่จะต้องวิ่งกลับมาผ่าน Model ทุกรอบ

ข้อดีหลักมาจาก Data Filtering ข้อมูลจะถูกประมวลผลและกรองก่อนส่งเข้า Context Window ของ Model ส่งผลให้ Latency ลดลงและประหยัด Token อย่างเห็นได้ชัด ฟีเจอร์นี้ต้องใช้ Code Execution Tool เวอร์ชัน `code_execution_20260120` ขึ้นไป

อีก 2 ทางเลือกที่ดูคล้ายกันแต่แก้ปัญหาไม่ตรงจุด ได้แก่: Message Batches API ซึ่งประมวลผลแบบ Asynchronous และแยกอิสระจากกัน (ส่วนใหญ่เสร็จภายใน 1 ชั่วโมง) เหมาะกับงาน Bulk ที่ไม่ต้องรอผลทันที แต่ไม่สามารถส่งผลลัพธ์ของ Tool หนึ่งไปยังอีก Tool หนึ่งใน Live Loop ได้ ส่วนการ Wrap แต่ละ Tool Call เป็น Subagent แม้จะช่วยให้ Context ของ Orchestrator คลีน แต่การเพิ่ม Agent เข้ามาต่อหนึ่ง Call ในระบบ Multi-agent มักใช้ Token เปลืองกว่าเดิม 3 ถึง 10 เท่า ยิ่งทำให้ปัญหา Overhead แย่ลงไปอีก

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Sometimes the cost is in the tool calls, not in the subtasks. If a step needs dozens of small tool calls in a loop, each standard tool-use turn is a round trip through the model, and each result adds to the context. Programmatic tool calling removes that overhead. Claude writes code that calls your tools inside a code execution container, so the loop runs in the container instead of passing through the model on every call.

The savings come from filtering. Data is processed before it reaches the model's context window, so latency and token use both fall. The feature needs the code execution tool at version code_execution_20260120 or later.

Two other options look similar but do not help. The Message Batches API processes requests asynchronously and independently, and most batches finish within an hour. That suits bulk work that does not need an immediate response, but it cannot feed one tool's result into the next step of a live loop. Wrapping each tool call in its own subagent keeps the orchestrator's context clean, but it adds a whole agent for each call, and multi-agent setups typically use 3 to 10 times more tokens. That makes the overhead problem worse.

อ่านเนื้อหา ↗
  • •

  • •
    Routing คือการทำ Classification ให้กับ Input ก่อน แล้วจึงส่งต่อไปยังขั้นตอนถัดไปที่ออกแบบมาเฉพาะสำหรับหมวดหมู่นั้นๆ ซึ่งแต่ละขั้นตอนสามารถใช้ Prompt, Tools หรือ Model ของตัวเองได้ เหตุผลหลักที่ต้องใช้ Routing คือเพื่อแก้ปัญหา Interference เพราะหากใช้ Prompt เดียวรองรับ Input ทุกประเภท การปรับแต่ง Prompt ให้ดีกับเคสหนึ่งมักส่งผลให้ประสิทธิภาพกับเคสอื่นแย่ลง
  • •
    Routing ยังเป็นจุดสำคัญในการเลือก Model ให้เหมาะกับแต่ละ Subtask เนื่องจาก Model แต่ละระดับมีความสามารถในการจัดการโจทย์ยาก ความเร็ว และค่าใช้จ่ายต่างกัน คำของ่ายๆ ที่พบบ่อยควรส่งให้ Model ขนาดเล็กที่ราคาประหยัด ส่วนงานยากหรือซับซ้อนควรส่งให้ Model ที่มีความสามารถสูงกว่า ตัวอย่างเช่น Support Pipeline ที่มี 2 Subtask: การจำแนกประเภท Ticket จำนวนมากส่งให้ Haiku ทำงาน ส่วนการร่างแผนแก้ไขปัญหาโดยละเอียดซึ่งต้องใช้หลายขั้นตอนและเป็นเคสใหม่ ให้ส่งต่อไปยัง Model ระดับสูงอย่าง Opus การรันทุกอย่างด้วย Model ตัวใหญ่สุดจะทำให้เสียค่าใช้จ่ายสูงเกินจำเป็นกับงาน Routine ทั่วไป

    `description` คือคำอธิบายรูปแบบภาษาธรรมชาติว่าควรเรียกใช้ Agent นี้เมื่อใด (Orchestrator จะอ่านค่านี้เพื่อเลือกว่าจะกระจายงานไปที่ไหน), `tools` คือ Whitelist ของ Tools ที่อนุญาตให้ใช้ (หากเว้นว่างไว้ Subagent จะ Inherit Tools ทุกตัวที่มี ทำให้สูญเสีย Scoping ไป), และ `prompt` ซึ่งเป็น System Prompt ของ Specialist แต่ละตัว
  • •
    ใน Claude Agent SDK การแตกงานจะใช้รูปแบบ Subagents โดยนิยามผ่านออปชัน `agents` ในโค้ด หรือสร้างเป็น Markdown Files ไว้ใน `.claude/agents/` ซึ่ง Main Agent จะเรียกใช้ผ่าน `Agent` Tool แต่ละ Subagent จะรันใน Conversation Context ของตัวเอง ทำให้ Tool Calls ระหว่างทางไม่ปนเปื้อนออกมา มีเพียง Final Message เท่านั้นที่ส่งกลับไปยัง Parent Agent Isolation นี้เป็นเหตุผลที่ [Coordinator pattern and isolated subagent context](lesson:1.4) ถูกนำมาใช้ แม้ว่าจะไม่มีงานที่รันคู่ขนานกันเลยก็ตาม เพราะเป้าหมายหลักมักเป็นการป้องกันไม่ให้ Output ยาวเหยียดของ Tools หลุดเข้าไปรก Context ของ Main Agent
  • •
    ลองนึกภาพ Codebase Audit ที่มี 3 มิติ (Security Vulnerabilities, Code Quality และ Test Coverage) ซึ่งแต่ละด้านต้องใช้ Tools และโฟกัสคนละแบบ Architecture ที่เหมาะสมคือ Orchestrator 1 ตัวพร้อม Subagents 3 ตัว ที่กำหนด `description` และ `tools` ตรงตามขอบเขตงาน จากนั้น Security Scanner, Style Checker และ Coverage Checker จะสามารถรันพร้อมกันได้ทันที

#7 7. การย้าย Tight Tool Loop ไปประมวลผลในโค้ด (Moving a tight tool loop into code)

อ่านเนื้อหา ↗
  • •
    Message Batches API ซึ่งประมวลผลแบบ Asynchronous และแยกอิสระจากกัน (ส่วนใหญ่เสร็จภายใน 1 ชั่วโมง) เหมาะกับงาน Bulk ที่ไม่ต้องรอผลทันที แต่ไม่สามารถส่งผลลัพธ์ของ Tool หนึ่งไปยังอีก Tool หนึ่งใน Live Loop ได้ ส่วนการ Wrap แต่ละ Tool Call เป็น Subagent แม้จะช่วยให้ Context ของ Orchestrator คลีน แต่การเพิ่ม Agent เข้ามาต่อหนึ่ง Call ในระบบ Multi-agent มักใช้ Token เปลืองกว่าเดิม 3 ถึง 10 เท่า ยิ่งทำให้ปัญหา Overhead แย่ลงไปอีก
  • •
    ข้อดีหลักมาจาก Data Filtering ข้อมูลจะถูกประมวลผลและกรองก่อนส่งเข้า Context Window ของ Model ส่งผลให้ Latency ลดลงและประหยัด Token อย่างเห็นได้ชัด ฟีเจอร์นี้ต้องใช้ Code Execution Tool เวอร์ชัน `code_execution_20260120` ขึ้นไป
  • •
    บางครั้ง Overhead หรือต้นทุนที่สูงไม่ได้เกิดจาก Subtasks แต่เกิดจากการเรียก Tool ซ้ำๆ หากสเต็ปใดต้องยิง Tool ย่อยๆ หลายสิบครั้งใน Loop การใช้ Tool Use แบบมาตรฐานจะต้องทำ Round Trip ผ่าน Model ทุกครั้ง และผลลัพธ์แต่ละครั้งจะสะสมใน Context การใช้ Programmatic Tool Calling จะเข้ามาตัด Overhead ตรงนี้ โดย Claude จะเขียนโค้ดเพื่อเรียกใช้ Tools เหล่านั้นภายใน Code Execution Container ทำให้ Loop ทำงานจบใน Container ทันที
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (5 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
การแบ่ง Prompt ออกเป็น Chain ทำให้ระบบทำงานเร็วขึ้นเพราะแต่ละ Call มีขนาดเล็กลง?
Splitting a prompt into a chain makes the system faster because each call is smaller.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Chain ทำงานแบบเรียงลำดับ (Sequential) จึงส่งผลให้ระบบทำงานช้าลง (Latency สูงขึ้น) โดยแลกกับความแม่นยำ (Accuracy) ที่เพิ่มขึ้นเนื่องจากโมเดลโฟกัสกับงานที่ง่ายลงในแต่ละ Call
A chain runs its calls in sequence, so it is slower. It accepts that latency in exchange for accuracy, because each call has an easier job.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
The main reason to run agents in parallel is to finish sooner and spend less.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: เหตุผลหลักในการรัน Agents แบบขนานกัน (Parallel) คือเพื่อให้งานเสร็จไวขึ้นและประหยัดค่าใช้จ่าย แต่ในความเป็นจริง Parallel Agents ทำเพื่อเพิ่ม Coverage และ Confidence โดยการใช้งาน Token รวมจะพุ่งสูงขึ้นอย่างมาก และระบบ Multi-agent โดยรวมมักใช้เวลาประมวลผลนานกว่า Single Agent
Parallel agents buy coverage. Total token use rises sharply, and multi-agent systems often take longer overall than a single agent.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Orchestrator-workers เป็น Default ที่ดีกว่าสำหรับทุก Task ที่มีหลาย Subtasks?
Orchestrator-workers is the better default for any task with several subtasks.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: จุดเด่นของมันคือการตัดสินใจเลือก Subtasks ที่ Run Time หาก Subtasks คาดเดาได้ล่วงหน้าอยู่แล้ว การใช้ Pre-defined Parallelization จะเรียบง่ายกว่าและไม่เปลือง Extra Call ของ Orchestrator
Its value is choosing the subtasks at run time. When the subtasks are predictable, pre-defined parallelization is simpler and avoids the extra orchestrator call.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
จุดเน้นข้อสอบ: เลือกวิธีแก้ปัญหาให้ตรงจุด — หาก Overhead เกิดจากการเรียก Tool ย่อยๆ จำนวนมากในสเต็ปเดียว ให้ใช้ Programmatic Tool Calling, หากเกิดจาก Context บวมเพราะมีงานหลายส่วนปนกัน ให้ใช้ Subagents, หากเป็นงานประมวลผลแบบ Bulk ที่ไม่ต้องรอผลลัพธ์ทันที ให้ใช้ Message Batches
On the Exam:: Match the remedy to the problem. If the overhead comes from many small tool calls inside one step, use programmatic tool calling. If it comes from unrelated work piling up in one context, use subagents. If the work is bulk and nothing waits on the answer, use batches.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
Putting a tight loop of small tool calls into a Message Batches request removes the per-call overhead.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: การยัด Tight Loop ของ Tool Calls ย่อยๆ เข้า Message Batches API จะช่วยลด Overhead ต่อรอบได้ — เพราะ Batch Requests ทำงานแบบ Asynchronous และเป็นอิสระต่อกัน จึงไม่สามารถนำผลลัพธ์ของ Call หนึ่งไปป้อนต่อให้อีก Call หนึ่งได้ หากต้องการรัน Loop ต่อเนื่องโดยไม่เกิด Model Round Trip ทุกรอบ ต้องใช้ Programmatic Tool Calling ที่รัน Loop ในระดับโค้ด
Batch requests are processed asynchronously and independently, so one result cannot drive the next call. Programmatic tool calling runs the loop in code and avoids a model round trip for each call.

  • ✓เลือก Model ให้เหมาะกับแต่ละ Subtask ตามระดับความซับซ้อนและความถี่ในการเรียกใช้
  • ✓ย่อยงานหลายมิติออกเป็น Subagents บน Agent SDK พร้อมกำหนด Tools และ Descriptions ที่เจาะจง
