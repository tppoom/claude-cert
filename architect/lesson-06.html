1. เหตุใดการย่อยสลายจึงช่วยปรับปรุงผลลัพธ์

การเรียกใช้แบบจําลองเดียวที่ต้องทําทุกอย่างจะให้ความสนใจกับแต่ละส่วนของงานน้อยลง หากมีพร้อมท์เดียวที่ต้องคัดกรองคําขอสําหรับเนื้อหาที่ไม่ปลอดภัยและตอบสนองต่อคําขอนั้น งานทั้งสองจะแย่ลง การแบ่งงานเพื่อให้การเรียกใช้แต่ละครั้งจัดการกับข้อพิจารณาหนึ่งข้อเป็นขั้นตอนพื้นฐานที่อยู่เบื้องหลังรูปแบบทั้งหมดในหน้านี้ การแยกส่วนเหมาะสมที่สุดเมื่อหลายงานที่มีขอบเขตที่ชัดเจนตอบสนองเป้าหมายโดยรวมเดียว

รูปแบบจะแตกต่างกันขึ้นอยู่กับว่าใครเป็นผู้ตัดสินใจเกี่ยวกับงานย่อย ในระบบการเชื่อมโยงแบบพุช การกําหนดเส้นทาง และการขนาน นักออกแบบจะแก้ไขงานย่อยเมื่อระบบถูกสร้างขึ้น ในระบบ Orchestrator-Worker โมเดลจะประมวลผลงานย่อยในระหว่างรันไทม์สําหรับแต่ละอินพุต นี่คือแนวทางเดียวกันกับที่วาดไว้ใน 📖 Workflows เทียบกับเอเจนต์ (1.3) ซึ่งที่นี่ถือเป็นตัวเลือกการแยกส่วน: หาก

คุณสามารถแสดงรายการงานย่อยได้ในวันนี้ ให้เขียนเป็นโค้ด หากงานย่อยขึ้นอยู่กับอินพุต ให้โมเดลวางแผนงานย่อย

การแยกส่วนไม่ฟรี การเรียกเพิ่มเติมแต่ละครั้งจะเพิ่มเวลาแฝงและโทเค็น และการส่งต่อแต่ละครั้งเป็นสถานที่ที่บริบทอาจสูญหาย รูปแบบแต่ละรูปแบบด้านล่างบอกว่าราคาเท่าไหร่และเมื่อใดที่คุ้มค่าที่จะจ่าย

✓ ตอบถูกแล้ว Check

A support assistant uses one prompt to screen each request for unsafe content and also answer it. Both the screening and the answers are mediocre. The team moves screening into its own call, separate from the call that answers. Why should this improve results?

คำแปลโจทย์: ผู้ช่วยฝ่ายสนับสนุนใช้พรอมต์เดียวเพื่อคัดกรองคำขอแต่ละรายการสำหรับเนื้อหาที่ไม่ปลอดภัยและตอบด้วย ทั้งการคัดกรองและคำตอบนั้นปานกลาง ทีมงานจะย้ายการคัดกรองไปเป็นการโทรของตนเอง โดยแยกจากการโทรที่รับสาย เหตุใดจึงควรปรับปรุงผลลัพธ์นี้
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Official Explanation (คำอธิบายเฉลย):

Decomposition helps because a call that does one job can give that job its full attention. It does not save time or tokens, because every extra call adds both. Here the designer fixed the subtasks while building the system. Run-time planning applies only to orchestrator-workers.

คำแปลไทย: การสลายตัวช่วยได้เนื่องจากการเรียกที่ทำหน้าที่หนึ่งสามารถให้ความสนใจกับงานนั้นได้อย่างเต็มที่ มันไม่ได้ประหยัดเวลาหรือโทเค็น เนื่องจากการโทรพิเศษทุกครั้งจะเพิ่มทั้งสองอย่าง ที่นี่ผู้ออกแบบได้แก้ไขงานย่อยในขณะที่สร้างระบบ การวางแผนรันไทม์ใช้กับผู้ปฏิบัติงานออร์เคสตราเท่านั้น
“LLMs generally perform better when each consideration is handled by a separate LLM call, allowing focused attention on each specific aspect.”

One model call that has to do everything gives each part of the job less attention. If a single prompt has to screen a request for unsafe content and also answer it, both jobs get worse. Splitting the work so that each call handles one consideration is the basic move behind every pattern on this page. Decomposition fits best where several well-scoped tasks feed one overall goal.

The patterns differ in who decides the subtasks. In prompt chaining, routing and parallelization, the designer fixes the subtasks when the system is built. In orchestrator-workers, a model works them out at run time for each input. This is the same line drawn in [Workflows versus agents](lesson:1.3), seen here as a decomposition choice: if you can list the subtasks today, write them into code. If they depend on the input, let a model plan them.

Decomposition is not free. Every extra call adds latency and tokens, and every handoff is a place where context can get lost. Each pattern below says what it costs and when that cost is worth paying.

Prompt chaining splits a task into a fixed sequence of steps. Each model call takes the previous call's output as its input. Between steps you can add programmatic checks, called gates, that confirm the process is still on track before the next call runs. Two standard examples: writing marketing copy and then translating it, or writing an outline, checking it against criteria, and only then writing the document.

Chaining fits when a task splits cleanly into fixed subtasks. A worked case: turning a quarterly performance summary into a table takes four calls. The first extracts each metric with its value. The second converts the values to one format. The third sorts them in descending order. The fourth renders a markdown table. Each step is trivial for the model, and a code check between steps (for example, "did step 1 return every metric?") catches a failure before it spreads to the later steps.

The same shape appears in Claude Code dynamic workflows. The first agent call returns a list of files in a declared schema, and that list drives the next step, which audits each file.

Routing classifies an input first, then sends it to a follow-up step built for that category. That step can use its own prompt, its own tools or its own model. The reason to route is interference. If one prompt has to serve every kind of input, tuning it for one kind tends to make it worse for the others. A customer-service system might route general questions, refund requests and technical support into three separate processes, each with its own prompt and tools.

Routing works when the categories really are distinct and classification can be done accurately, whether by an LLM or by a traditional classifier. If inputs are often misclassified, every downstream specialist receives work it was not built for.

Routing is also the place to choose a model for each subtask. Model classes differ mainly in how hard a problem they can reliably handle and what that capability costs in price and speed. Easy, common requests go to a small, cheap model. Hard or unusual ones go to a more capable model. Take a support pipeline with two subtasks: classifying a large stream of tickets, and drafting detailed remediation plans for the few that need engineering. Classification goes to Haiku. Remediation, which is multi-step and often new, goes to a more capable class such as Opus. Running everything on the largest model pays its price for every routine classification. Running everything on Haiku asks it to carry work beyond what it reliably handles. Assigning models at random is not routing, because nothing about the input decides where it goes. The broader trade-offs are covered in [model selection trade-offs](lesson:2.1).

With agents, routing means sending work to a specialist agent rather than a specialist prompt. In the Agent SDK, each subagent definition has an optional model field, so a cheap classifier and an expensive drafter can live in the same system.

Parallelization runs several model calls at the same time and combines their outputs in code. It comes in two forms that solve different problems.

- Sectioning splits a task into independent subtasks that run side by side. For example, one instance answers the user while another screens the request for inappropriate content. This tends to beat one call doing both. Automated evals can also be sectioned, with each call grading a different aspect of the output. - Voting runs the same task several times and combines the answers to get more confidence. For example, several prompts review the same code for vulnerabilities and flag it if any of them find a problem. Content moderation can also use different vote thresholds to balance false positives against false negatives.

Speed and cost need to be kept apart. Independent subtasks that run concurrently finish in the time of the slowest one, not the sum of all of them, so a single sectioned step takes less wall-clock time. Across a whole multi-agent system the picture is different. Such systems typically use 3 to 10 times more tokens than one agent, and they often take longer overall because there is so much more computation. Choose parallelization for coverage or confidence, and expect a larger bill.

👑 1. Orchestrator (ตัวประสานงานกลาง) ทำหน้าที่วิเคราะห์โจทย์ วางแผนกลยุทธ์ แตกงานย่อย (Subtasks) และรวบรวมสังเคราะห์ข้อค้นพบขั้นสุดท้าย
🛠️ 2. Subagents (เอเจนต์ย่อยเฉพาะทาง) รับงานย่อยเฉพาะเรื่องไปดำเนินการในห้องบริบทแยกส่วน (Isolated Context) และส่งกลับเฉพาะข้อสรุปที่จำเป็น
โครงสร้างและข้อเท็จจริงสำคัญ: สิ่งที่ส่งกลับขึ้นมาตามลำดับชั้นคือ "ผลลัพธ์ข้อสรุป" ไม่ใช่ประวัติการสนทนาหรือการเรียกเครื่องมือทั้งหมด เอเจนต์ย่อยจะกักกันผลลัพธ์ของเครื่องมือ (เช่น การอ่านไฟล์ยาวๆ หรือผลการค้นหาเว็บขนาดใหญ่) ไว้ในเซสชันของตนเอง ทำให้ Context Window ของ Orchestrator สะอาดและไม่เกิดปัญหา Context Pollution

ในระบบ Orchestrator-worker โมเดลส่วนกลางจะอ่านงาน ตัดสินใจว่าต้องการงานย่อยใด ส่งแต่ละงานไปยังโมเดล worker และรวมผลลัพธ์เข้าด้วยกัน อาจดูเหมือนการแบ่งส่วน แต่งานย่อยไม่ได้กําหนดไว้ล่วงหน้า Orchestrator เลือกงานย่อยสําหรับแต่ละอินพุต การเปลี่ยนแปลงการเข้ารหัสเป็นกรณีมาตรฐาน: คุณไม่สามารถรู้ล่วงหน้าได้ว่ามีไฟล์กี่ไฟล์ที่ต้องแก้ไขหรือแต่ละการแก้ไขคืออะไร

In orchestrator-workers, a central model reads the task, decides which subtasks it needs, hands each one to a worker model, and combines the results. It can look like sectioning, but the subtasks are not pre-defined. The orchestrator chooses them for each input. A coding change is the standard case: you cannot know in advance how many files need editing or what each edit is.

That flexibility has costs. Each run makes N+1 calls: one to the orchestrator and one per worker. The decomposition is only as good as the orchestrator's plan, so the orchestrator prompt is where most of the engineering effort goes. Cost can be managed by splitting models, with a capable model such as Opus planning and Haiku workers executing. Do not use the pattern for simple single-output tasks, for latency-critical paths, or when the subtasks are always the same. In that last case, pre-defined parallelization does the job with less machinery.

Claude Managed Agents provides this as dynamic workflows. The agent writes a program that runs many agents in phases and combines their results, and the server runs it in the background. Audits, migrations, deep research and cross-checking are the typical uses. Every agent in a run uses tokens, so set a session budget.

In the Claude Agent SDK, decomposition takes the form of subagents. You define them with the agents option in code, or as markdown files in.claude/agents/. The main agent invokes them through the Agent tool. Each subagent runs in its own conversation, and its intermediate tool calls stay inside that conversation; only its final message returns to the parent. That isolation is the reason [Coordinator pattern and isolated subagent context](lesson:1.4) applies even when nothing runs in parallel. The main reason to split may be to keep pages of tool output out of the main agent's context.

Three fields carry the decomposition. description is a natural-language statement of when to use the agent, and the orchestrator reads it to decide where each piece of work goes. tools is the allowed list; if you leave it out, the subagent inherits every tool available to subagents, so leaving it blank removes the scoping. prompt is the specialist's system prompt.

Take a codebase audit with three dimensions (security vulnerabilities, code quality and test coverage), each needing different tools and a different focus. The decomposition is an orchestrator plus three subagents, each with a description and a tool set matched to its dimension. A security scanner, a style checker and a coverage checker can then run at the same time instead of one after another. Compare the alternatives:

- One prompt asking the main agent to do all three in sequence. Every dimension's tool output builds up in a single context, and quality drops as the context grows. - One MCP server exposing all the checks as tools for the main agent. This adds tools without separating anything. An agent loaded with tools across unrelated domains confuses which domain applies, and with roughly 20 or more tools it struggles to pick the right one. - A larger context window plus extended thinking. More room does not solve the problem. Response quality can degrade as context grows, so more space for clutter makes the clutter worse.
