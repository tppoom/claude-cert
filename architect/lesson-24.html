1. สามวิธีในการเชื่อมต่อ Claude เข้ากับระบบภายนอก (Three ways to connect Claude to a system)

เมื่อใดก็ตามที่ Claude ต้องเชื่อมต่อกับระบบภายนอก เช่น Database, Issue Tracker หรือ Build Server ทาง Architect สามารถเลือกใช้ได้ 3 รูปแบบ: Direct Tool ที่ Application นิยามและรันขึ้นมาเอง, MCP Server หรือเชื่อมต่อไปยัง Agent ตัวอื่นที่ดูแลระบบนั้นโดยตรง ทั้งสามวิธีสามารถบรรลุเป้าหมายเดียวกันได้ แต่ต่างกันตรงที่ว่าใครเป็นผู้ดูแล Integration, สามารถนำไปใช้ซ้ำในหลาย Clients ได้หรือไม่ และระบบปลายทางต้องใช้ Judgement หรือการตัดสินใจมากน้อยเพียงใด

Direct Tool Use เป็นเส้นทางที่สั้นและตรงที่สุด โดย Application ของคุณจะนิยาม Tool ด้วย `input_schema`, Claude จะส่ง `tool_use` block กลับมา จากนั้น Code ฝั่งคุณจะรัน Operation นั้นแล้วส่ง `tool_result` กลับไป (สำหรับรายละเอียดว่าโค้ดส่วนนี้รันที่ไหน สามารถดูต่อได้ที่ [Who executes tools: client tools versus server tools](lesson:1.2)) ตัวเลือกนี้ตอบโจทย์ที่สุด เมื่อ Application หนึ่งตัวเป็นเจ้าของระบบนั้นเพียงผู้เดียว และคุณเป็นผู้ควบคุม Schema ทั้งหมด ซึ่ง CLI ก็จัดอยู่ในรูปแบบนี้เช่นกัน เช่น Anthropic มี Bash Tool Schema ให้ แต่ Application ของคุณยังคงเป็นตัวรันแต่ละคำสั่งเอง ข้อเสียคือ Integration นี้จะฝังแน่นอยู่ภายใน Application เท่านั้น Client อื่น (เช่น Session ของ Claude Code บนเครื่อง Developer) จะไม่สามารถนำไปใช้ซ้ำได้

MCP Server ย้ายส่วน Integration ออกมาจาก Application แล้วหุ้มไว้ด้วย Protocol มาตรฐาน ทำให้ Server ตัวเดียวสามารถให้บริการกับ MCP Client ใดๆ ก็ได้ และ Client หนึ่งตัวก็สามารถเชื่อมต่อหลายๆ Server ร่วมกันได้ MCP Server แต่ละตัวจะมองเห็นเฉพาะข้อมูลที่จำเป็นต่อการทำงานเท่านั้น เพราะ Full Conversation จะยังคงอยู่กับฝั่ง Host วิธีนี้เหมาะอย่างยิ่งเมื่อคุณต้องการให้หลายๆ Interface เข้าถึงความสามารถเดียวกันได้ หรือเมื่อ Vendor ของระบบนั้นมี MCP Server สำเร็จรูปมาให้ใช้งานโดยไม่ต้องสร้างเองตั้งแต่ต้น

Agent-to-agent Hand-off เป็นตัวเลือกที่ถูกต้องเมื่อระบบปลายทางต้องใช้การคิดและตัดสินใจ (Judgement) ของตัวเอง ไม่ใช่แค่การเรียก Function Call ธรรมดา เช่น การทำ Security Review, การเขียน Test หรือการใช้ Specialist เฉพาะทางที่มี System Prompt และ Toolset เป็นของตัวเอง ฝั่ง Lead Agent จะทำการ Delegate งานออกไปแล้วรอรับสรุปผลจาก Specialist แทนที่จะต้องคุม Control Flow ทุกขั้นตอนด้วยตัวเอง (สามารถศึกษาความแตกต่างระหว่าง Subagents, Agent Teams และ Workflows เพิ่มเติมได้ที่ [Subagents vs agent teams vs workflows across Managed Agents, Agent SDK and Claude Code](lesson:1.4))

🔗 เอกสารอ้างอิงทางการจาก Anthropic
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Each time Claude needs to reach an outside system, such as a database, an issue tracker or a build server, the architect picks one of three mechanisms: a tool your application defines and runs, an MCP server, or another agent that owns that system. All three can get the job done. They differ in who maintains the integration, how many clients can reuse it, and how much judgement sits on the other side.

Direct tool use is the shortest path. Your application defines a tool with an input_schema, Claude returns a tool_use block, your code runs the operation and returns a tool_result. Where that code runs is covered in [Who executes tools: client tools versus server tools](lesson:1.2). As an integration choice, it wins when one application owns one system and you control the schema. A CLI belongs here too: Anthropic publishes a bash tool schema, but your application still runs each command. The cost is that this integration lives inside your application. A second client, say a developer's Claude Code session, cannot reuse it.

An MCP server moves the integration out of your application and puts it behind a protocol. One server can then serve any MCP client, and one client can combine several servers. Each server sees only what it needs, because the full conversation stays with the host. MCP wins when the same capability has to be reachable from more than one surface, or when the vendor of the system already ships an MCP server you can attach rather than build.

Agent-to-agent hand-off is the right choice when the system needs its own judgement, not just a function call: a security review, a test-writing pass, a domain specialist with its own system prompt and toolset. The calling agent delegates the task and reads back what the specialist reports, instead of driving each step itself. How subagents, agent teams and workflows differ is taught in [Subagents vs agent teams vs workflows across Managed Agents, Agent SDK and Claude Code](lesson:1.4).

In Managed Agents the specialist is either a predefined agent listed in the multiagent block of the lead's definition, or an inline agent that the lead defines when it delegates. Each subagent works in its own session thread, so its working context stays out of the lead's. Delegation is one level deep: a specialist cannot hand work on to further agents. Pick this over a tool or an MCP server when the system must reason about the task, and expect the lead to receive a report rather than a raw result.

Server และ Client มีการทำ Capability Negotiation ก่อนเสมอ ฝั่ง Server ต้องประกาศว่ารองรับ Tools ก่อน Client จึงจะสามารถสั่งรัน Tools ได้ และฝั่ง Client ก็ต้องประกาศรองรับ Sampling Support ก่อน Server จึงจะร้องขอการ Sampling ได้ กลไกนี้ช่วยให้ทั้งสองฝั่งสามารถเพิ่มฟีเจอร์ใหม่ๆ ตามรอบการพัฒนาของตนเองได้อย่างอิสระ นอกจากนี้ Protocol ยังรองรับการสื่อสารแบบสองทิศทาง (Bidirectional): ใน Claude Code ตัว MCP Server สามารถทำหน้าที่เป็น Channel คอย Push ข้อความจาก Telegram, Discord หรือ Webhook Events เข้ามาใน Session ได้โดยตรง แตกต่างจาก Direct Tool ที่ Claude ทำได้เพียงแค่รอให้สั่งเรียกใช้งานก่อนจึงจะตอบกลับ

MCP ทำงานบน 2 Transports หลัก ซึ่งเป็นตัวกำหนดว่า Client ประเภทใดบ้างที่จะสามารถเชื่อมต่อเข้ามาได้ แบบแรกคือ `stdio` โดย Client จะ Spawn ตัว Server เป็น Subprocess และรับส่งข้อความ JSON-RPC แบบ Newline-delimited ผ่าน `stdin` และ `stdout` ตัว Server สามารถพ่น Log ออกทาง `stderr` ได้ แต่ห้ามเขียนอะไรลง `stdout` เด็ดขาดนอกจากข้อความ MCP ที่ถูกต้องตามรูปแบบ `stdio` จึงเป็น Transport หลัก สำหรับ Local Server ที่รันบน Laptop ของ Developer แบบที่สองคือ Streamable HTTP ซึ่งตัว Server จะเป็น Remote Endpoint ฝั่ง Client จะส่ง JSON-RPC ผ่าน HTTP POST ไปยัง Endpoint นั้น แล้ว Server จะตอบกลับเป็น JSON Object ก้อนเดียวหรือเป็น SSE (Server-Sent Events) Stream นอกจากนี้ Client ยังสามารถเปิด GET Stream ค้างไว้เพื่อให้ Server สามารถส่ง Event หรือ Message แจ้งเตือนกลับมาได้ทันทีโดยไม่ต้องรอให้ Request ถามก่อน

Remote Server ต้องแบกรับภาระงานด้านความปลอดภัยที่ Subprocess แบบ Local ไม่จำเป็นต้องมี โดยจะต้อง Validate `Origin` Header ในทุกๆ Connection เพื่อป้องกันการโจมตีแบบ DNS Rebinding หากรันแบบ Local ควร Bind เข้ากับ `127.0.0.1` แทนที่จะเป็น `0.0.0.0` พร้อมทั้งตรวจสอบ Authentication ในทุก Connection เสมอ ดังนั้น การแปลง Local `stdio` Server ไปเป็น Production HTTP Service จึงเป็นงานด้าน Infrastructure และ Deployment เต็มรูปแบบ ไม่ใช่แค่การเปลี่ยน Config Toggle เพียงอย่างเดียว

MCP standardises three kinds of things a server can expose, and each one is controlled by a different party. That split matters when you compare MCP with a plain tool definition, because a tool definition only covers the first row of the table below. Resources and prompts give a client context and templates that it, or the user, chooses to bring in.

Servers and clients also negotiate capabilities. A server has to declare tool support before tools can be invoked, and a client has to declare sampling support before a server can request it. This lets each side add features at its own pace. The protocol can also run in the other direction: in Claude Code, an MCP server can act as a channel that pushes Telegram messages, Discord chats or webhook events into a session. A tool that Claude calls directly can only answer when Claude asks.

Two transports carry the protocol, and the choice between them decides which clients can reach a server. With stdio, the client launches the server as a subprocess and exchanges newline-delimited JSON-RPC messages over stdin and stdout. The server may log to stderr but must write nothing to stdout except valid MCP messages. Stdio is the transport behind the server that runs on a developer's laptop. With Streamable HTTP, the server is a remote endpoint. The client POSTs each JSON-RPC message to that endpoint, and the server answers with either one JSON object or an SSE stream. The client may also open a GET stream so the server can send messages without being asked.

A remote server takes on duties a subprocess never has. It must validate the Origin header on every incoming connection to block DNS rebinding. When it runs locally it should bind to 127.0.0.1 rather than 0.0.0.0, and it should authenticate every connection. Turning a stdio server into a production HTTP service is therefore deployment work, not a configuration toggle.

Where you attach an MCP server depends on which surface runs the agent, so pick the surface first. The four options differ in who writes the agent loop and whether a person is watching while it runs.

The Client SDK and the Agent SDK sound alike, but they split the work differently. With the Client SDK your code checks stop_reason, runs each tool_use block and sends the results back, which is exactly the code a pipeline team wants to avoid writing. The Agent SDK already contains that loop, along with Read, Edit and Bash tools and a permission system that decides which tools run automatically and which need approval. For CI, the headless form claude -p "Find and fix the bug in auth.py" --allowedTools "Read,Edit,Bash" pre-approves the tools, so nobody has to answer prompts.

Interactive approval is the deciding case for the CLI. An engineer debugging a failing build, who wants to see every file Claude opens and approve each risky command, needs the terminal session, with no integration code. An SDK script on a schedule has nobody watching. Managed Agents runs the session in a sandbox. The Messages API connector has no terminal at all.

In the Agent SDK, MCP servers go in the mcpServers option of query(). Tools from a server get names of the form mcp__<server>__<tool>, which is what allowedTools matches against.

The MCP connector lets a Messages API request use a remote MCP server directly, without a separate MCP client. Anthropic's side makes the connection. That is also why its limits are strict. The server must be publicly reachable over HTTP, using Streamable HTTP or SSE, and its url must start with https://. The API has no process to launch a stdio server from, so the laptop server above has to be deployed before production can use it. Only tool calls are supported, so the server's resources and prompts are not available through this path.

A request names the server and enables its tools in two separate places. The mcp_servers array holds connection details: type (currently only "url"), url, name and an optional OAuth authorization_token. The tools array holds an mcp_toolset that refers to that server by name. Each server name must be referenced by exactly one toolset. The toolset is also where you enable every tool, allowlist some or denylist others. One request can attach several servers. The connector sits behind a beta flag.

Rewriting the server's functions as client tools also connects the system, but it changes who does the work. Your backend would run every call and return each tool_result itself, so the query logic moves into the application and stops being a server other clients can share. Use the connector when the server can be exposed remotely and you want the API to handle the MCP round trip. Use client tools when the system must stay private to your backend.

6. When the system is better reached as another agent

บางระบบเหมาะกับการดีไซน์เป็น Agent แยกตัว มากกว่าการผูกเป็น Tool ตัว Tool หรือ MCP server ให้ผลลัพธ์ทีละ function โดยที่ agent ผู้เรียกยังต้องแบกรับ reasoning ทั้งหมด ในขณะที่การสร้าง predefined agent จะมาพร้อม model, system prompt, tools, MCP servers และ skills ของตัวเอง การส่งต่องาน (hand-off) ให้ subagent จึงเป็นการมอบหมายทั้งการตัดสินใจ (judgement) พร้อมกับชุด integrations ที่จำเป็นสำหรับการทำงานนั้นไปพร้อมกัน

ตัวอย่างเช่น: Lead agent ต้องการทำ code review และ test writing หากผูก review tools และ test runner ทั้งหมดไว้ที่ lead agent จะทำให้ context บวมและ prompt instruction ไม่โฟกัส การ route งานไปยัง reviewer agent และ test-writer agent ซึ่งมี focused prompt และ tools ของตัวเอง จะช่วยแยกขอบเขตความรับผิดชอบ (separation of concerns) ให้ชัดเจน หลักการนี้ใช้กับ MCP server เช่นกัน: หากระบบใดจำเป็นเฉพาะ สำหรับ specialist ให้ attach ไปที่ specialist agent นั้นโดยตรง ไม่ใช่ที่ orchestrator/lead agent

  1. 1
    Agents ภายใน Managed Agents session จะแชร์ sandbox, filesystem และ vault credentials ร่วมกัน ดังนั้นการ hand-off งานจึงไม่ได้ isolate permission แต่เป็นการ isolate context เนื่องจาก agent แต่ละตัวจะรันใน session thread และ history ของตัวเอง
  2. 2
    Thread ของ subagent จะ persist อยู่ ทำให้ lead agent สามารถส่ง follow-up เพื่อทำงานต่อเนื่องกับ specialist ที่ยังจำ context ก่อนหน้าได้ ควรเลือกใช้ Agent แทน MCP server เมื่อการสื่อสารกับระบบนั้นต้องมี multi-turn interaction ไม่ใช่แค่การ request แล้วรอผลลัพธ์แบบเที่ยวเดียวจบ

Some systems need a whole agent rather than a tool. A tool or an MCP server gives Claude one function at a time, and the calling agent still does all the reasoning. A predefined agent brings its own model, system prompt, tools, MCP servers and skills. Handing work to it means handing over the judgement, together with the integrations that judgement needs.

Here is a concrete case. A lead agent needs code review and test writing. Attaching every review tool and test runner to the lead fills its context and blurs its instructions. Routing the work to a reviewer agent and a test-writer agent, each with a focused prompt and its own tools, keeps each concern self-contained. The same reasoning applies when the system is an MCP server that only a specialist needs: attach it to the specialist agent, not to the agent that coordinates the work.

Two properties of this option affect its design. Agents in a Managed Agents session share the same sandbox, filesystem and vault credentials, so a hand-off does not isolate permissions. It isolates context, because each agent runs in its own session thread with its own history. A subagent's thread also persists, so the lead can send follow-ups to a specialist that keeps its earlier work. Choose an agent over an MCP server when the conversation with the system may take several turns, not one request and one result.

    ในขณะที่การสร้าง predefined agent จะมาพร้อม model, system prompt, tools, MCP servers และ skills ของตัวเอง การส่งต่องาน (hand-off) ให้ subagent จึงเป็นการมอบหมายทั้งการตัดสินใจ (judgement) พร้อมกับชุด integrations ที่จำเป็นสำหรับการทำงานนั้นไปพร้อมกัน
  • •
    ตัวอย่างเช่น: Lead agent ต้องการทำ code review และ test writing หากผูก review tools และ test runner ทั้งหมดไว้ที่ lead agent จะทำให้ context บวมและ prompt instruction ไม่โฟกัส การ route งานไปยัง reviewer agent และ test-writer agent ซึ่งมี focused prompt และ tools ของตัวเอง จะช่วยแยกขอบเขตความรับผิดชอบ (separation of concerns) ให้ชัดเจน หลักการนี้ใช้กับ MCP server เช่นกัน: หากระบบใดจำเป็นเฉพาะ
  • •
    การ hand-off งานจึงไม่ได้ isolate permission แต่เป็นการ isolate context เนื่องจาก agent แต่ละตัวจะรันใน session thread และ history ของตัวเอง 2) Thread ของ subagent จะ persist อยู่ ทำให้ lead agent สามารถส่ง follow-up เพื่อทำงานต่อเนื่องกับ specialist ที่ยังจำ context ก่อนหน้าได้ ควรเลือกใช้ Agent แทน MCP server เมื่อการสื่อสารกับระบบนั้นต้องมี multi-turn interaction ไม่ใช่แค่การ request แล้วรอผลลัพธ์แบบเที่ยวเดียวจบ

#7 ลงมือปฏิบัติจริง

อ่านเนื้อหา ↗
  • •
    เชื่อมต่อ Remote MCP Server เข้ากับ Claude Code และตรวจสอบสถานะการทำงาน
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (5 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
Agent-to-agent delegation can chain: a subagent can hand its work on to further agents, so deep hierarchies are the normal design.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Agent-to-agent Delegation ไม่สามารถ Chain ต่อกันเป็นลำดับชั้นลึกๆ ได้ เนื่องจากการ Delegate ของ Subagents รองรับเพียงระดับเดียว (One level deep) Specialist จึงส่งต่องานให้ Agent อื่นต่อไม่ได้ สถาปัตยกรรมที่ถูกต้องและรองรับคือรูปแบบ Wide Fan-out ที่กระจายงานออกจาก Lead Agent ตัวเดียวเท่านั้น
Delegation through subagents is one level deep, so a specialist cannot delegate onward. Wide fan-out from one lead is the supported shape.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
การใส่แค่ url ในบล็อก mcpServers ก็เพียงพอแล้วที่จะทำให้ Claude Code มองว่า Server นั้นเป็น Remote Server?
An mcpServers entry with just a url is enough for Claude Code to treat the server as remote.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Claude Code จะมอง Entry ที่ไม่ระบุ type เป็น stdio เสมอ ดังนั้นหากเป็น Remote URL จำเป็นต้องระบุ type เป็น http, sse หรือ ws กำกับไว้ด้วย
Claude Code treats an entry with no type as stdio, so a url entry also needs type http, sse or ws.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Client SDK มี Agent Loop เตรียมไว้ให้แล้ว ทำให้ Pipeline ที่สร้างขึ้นไม่ต้องเขียนโค้ดจัดการ Tool เอง?
The Client SDK provides the agent loop, so a pipeline built on it needs no tool-handling code.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Client SDK บังคับให้คุณต้องเขียน Tool Loop จัดการเองทั้งหมด (หรือใช้ Beta Tool Runner) แต่ Agent SDK ต่างหากที่เป็น Library ที่เตรียมทั้ง Agent Loop และ Built-in Tools มาให้พร้อมใช้ทันที
With the Client SDK you write the tool loop yourself or use its beta tool runner. The Agent SDK is the library that already contains the loop and the built-in tools.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Messages API MCP connector สามารถรัน local stdio server ได้หากระบุ command หรือ path ของ process?
The Messages API MCP connector can use a local stdio server if you give it the command or process path to launch.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Connector รองรับเฉพาะ server แบบ public ที่เชื่อมต่อผ่าน HTTP (Streamable HTTP หรือ SSE) ด้วย https:// URL เท่านั้น หากเป็น stdio server ต้องนำไป deploy เป็น remote server ก่อน | การเชื่อมต่อ server ผ่าน MCP connector จะเปิดให้ Claude เข้าถึงทั้ง tools, resources และ prompts ของ server ได้ทั้งหมด? (ทำไมถึงผิด): ไม่จริง: Connector รองรับเฉพาะส่วน tool calls ตาม MCP specification เท่านั้น หากต้องการใช้งาน resources และ prompts จำเป็นต้องใช้ full MCP client อย่าง Claude Code
The connector only connects to servers publicly exposed over HTTP (Streamable HTTP or SSE) at an https:// URL. A stdio server must first be deployed as a remote server. Attaching a server through the MCP connector exposes its tools, resources and prompts to Claude. (ทำไมถึงผิด): The connector supports only the tool-call part of the MCP specification. Resources and prompts need a full MCP client such as Claude Code.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
นำไปปรับใช้กับการทำงานจริง: ลองเลือกระบบที่ทีมของคุณเชื่อมต่อกับ Claude อยู่ในปัจจุบัน ระบบนั้นถูกเรียกจาก application เดียว, ถูกแชร์ข้ามหลาย client, หรือต้องใช้ reasoning ในการตัดสินใจของตัวเอง? เงื่อนไขเหล่านี้ชี้ไปที่แนวทางสถาปัตยกรรมใดใน 3 รูปแบบ (Client Tools, MCP Connector, หรือ Subagent)?
Apply it to your own work Pick one system your team connects to Claude today. Is it called from one application only, from several clients, or does it need its own reasoning? Which of the three mechanisms does that point to?
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
🎯 ทักษะที่ข้อสอบประเมินในบทนี้ (Exam Competency Checklist) 5 วัตถุประสงค์
  • ✓เลือกใช้งานระหว่าง Direct Tool/CLI call, MCP Server และ Hand-off ไปยัง Agent อื่น เพื่อเชื่อมต่อกับระบบปลายทางที่กำหนด
  • ✓อธิบายมาตรฐานของ MCP รวมถึง 3 Primitives หลัก และ Transport แบบ stdio กับ Streamable HTTP
  • ✓เชื่อมต่อ MCP Server เข้ากับ Claude Code, Agent SDK และ Messages API MCP Connector พร้อมเข้าใจข้อจำกัดของแต่ละรูปแบบ
  • ✓เลือก Claude Surface (Claude Code CLI, Agent SDK, Client SDK, Managed Agents) ที่ตอบโจทย์แต่ละ Workflow
  • ✓ระบุ Use Case ที่เหมาะกับ Agent-to-Agent Delegation มากกว่าการใช้ Tool หรือ MCP Server พร้อมเข้าใจข้อมูล Input และ Output ของ Delegated Agent
