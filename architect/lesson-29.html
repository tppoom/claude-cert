💡 แนวคิดหลักสำคัญ (Key Concept)

Symptom-to-layer diagnosis — A bad output is a symptom. Before you pick a fix, work out which layer produced it: grounding, the prompt, the tool definitions or the model's capability. A fix aimed at the wrong layer leaves the real cause in place.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Four layers a failure can come from" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Once a Claude-based system is live, failures reach you as symptoms: a figure nobody can find in the source, JSON whose keys keep changing, a tool called when another was meant, replies that are slow and expensive. The same symptom can come from different layers, and each layer has its own fix. Diagnosis means naming the layer before you change anything.

There are four layers to check:

- Grounding: the model states things its inputs do not support. - Prompt: the model did what the instructions said, and the instructions were not what you meant. - Tools: descriptions or schemas leave the model guessing about which tool to call or how to call it. - Model: the model is the wrong size for the work. Either it is too weak for the task, or it costs more than the task needs.

A troubleshooting table is the most useful shape for this kind of diagnosis: an observed symptom, its likely cause, then the fix. Anthropic's tool-use troubleshooting guide is organised exactly that way, and the sections below apply the same shape to every layer. The discipline matters most when the fix that comes to mind first belongs to the wrong layer. Adding citations will not make a slow, over-sized model faster. Renaming a tool will not resolve two descriptions that overlap.

2.Confirming a suspected hallucination

สาระสำคัญและหลักการทำงานของหัวข้อนี้: หัวข้อนี้เจาะลึก Confirming a suspected hallucination ตามมาตรฐานและพิมพ์เขียวการสอบของ Anthropic โดยมุ่งเน้นการทำความเข้าใจสถาปัตยกรรมเชิงลึก ข้อดีข้อเสียทางเทคนิค และแนวทางการปฏิบัติจริงในโปรดักชัน
⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

On the examWhen an answer contains a specific fact that is absent from its source documents, the fix is to quote first and allow uncertainty. Instructions that send the model to its general knowledge, or that demand a concrete answer every time, are causes of hallucination, not cures.

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

Exam trapWhen a RAG assistant invents a figure, let it supplement gaps in the documents with its general knowledge.Why is that wrong?Drawing on general knowledge is how ungrounded figures get in. The fix is to restrict Claude to the provided documents, require quotes first, and allow it to say it does not know.

Check

You've confirmed a hallucination and diagnosed why it happened. Match each diagnosed cause to the fix that targets it.

คลิกดูเฉลยคำตอบพร้อมคำอธิบาย (Click to view answer & explanation) ▼
คำตอบที่ถูกต้อง: ตัวเลือก N/A

Each cause has its own fix. Quoting first and restricting Claude to the documents ties claims to the text. Permission to admit uncertainty removes the pressure to fill gaps. A cite-or-retract pass removes claims with no support. Sending the model to its general knowledge would make each of these worse.

“Minimize hallucinations in Claude's outputs by allowing uncertainty, grounding responses in direct quotes, and verifying claims with citations.”

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A hallucination is output that is factually wrong or inconsistent with the context the model was given. It is dangerous because it rarely looks wrong. Claude can display quotes that may look authoritative or sound convincing, but are not grounded in fact. Fluency tells you nothing, so a suspicion has to be confirmed with a check that does not depend on how the answer reads.

Three checks confirm a hallucination in a running system.

1. Check claims against the sources. Ask Claude to extract word-for-word quotes from the documents before it does its task. A claim with no quote behind it is suspect. 2. Check consistency across samples. Run the same prompt several times and compare the outputs. Facts that change from run to run were probably generated, not retrieved. 3. Verify citations. After Claude generates a response, have it find a supporting quote for each claim, and retract any claim it cannot support. A press-release prompt can tell it to delete unsupported claims and mark each gap with empty [] brackets, so a reviewer can see exactly where the gaps were.

When one answer looks wrong and you want to know why, turn on thinking with display: "summarized" and read the summarized reasoning. It can show the faulty assumption the answer was built on.

Once a hallucination is confirmed, ask why the model produced it. The diagnosed cause decides the fix, and [output guardrails against hallucination](lesson:5.1) has the full set of controls. Three causes are common:

- Missing grounding. The answer is not tied to the text. Require quotes first and base the analysis only on those quotes, and tell Claude to use only the provided documents, not its general knowledge. - A forced answer. The prompt leaves no room for "I don't know", so the model fills the gap. Explicitly give Claude permission to admit uncertainty. - Unsupported claims mixed with supported ones. Add a cite-or-retract pass after drafting.

Take a policy assistant that confidently quotes a vacation-accrual rate that appears nowhere in the uploaded PDFs. The cause is missing grounding plus a forced answer. Telling it to fill gaps from general HR knowledge, or to always give a number, makes the failure worse. Repeating the whole document in every reply adds tokens without tying any claim to a quote.

A prompt failure is easy to recognise: the output follows the instructions, and the result is still unwanted. Nothing was made up and no tool misfired. The model filled a gap the prompt left open, or followed an instruction more literally than its author intended. Treat Claude like a brilliant new employee who lacks context on your norms. A useful test is to show the prompt to a colleague with minimal context on the task and ask them to follow it. If they would get it wrong, so will Claude.

Structure that drifts while the input stays stable is a sign of an underspecified prompt. A hallucination changes facts, not key names. A rate limit causes failed requests, not differently shaped JSON. The fix is to anchor the format: list the exact fields and nesting, and include a sample response. A few well-crafted examples improve accuracy and consistency. Wrapping them in tags keeps them separate from the instructions.

The other common prompt cause is an instruction given without its reason, which the model then applies too widely. "NEVER use ellipses" is followed everywhere. "Your response will be read aloud by a text-to-speech engine, so never use ellipses" tells Claude what the rule protects, and it can generalise from that. When you trace a literal-but-wrong behaviour back to its source, look for the bare instruction that caused it. Then apply [specific instructions that give the reason](lesson:2.2) to that line.

A support-desk prompt audited by Anthropic shows how these failures look in practice:

- Contradictions. Line 15 said to confirm before every refund, and line 17 said to process every eligible refund immediately. Another line asked for a complete recap with a three-sentence maximum. - Literal over-application. "Investigate fully even when the ticket looks simple" forced four tool calls on a simple package-status ticket. - Cost from stale instructions. "Verify twice" raised the cost per ticket.

The two kinds of stale text cost different things. Instructions the new model follows too literally cost money. Contradictory or outdated text costs accuracy. Removing the contradictory rules restored accuracy.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Model mismatch: when the model is the wrong size for the work" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A model mismatch is a failure that rewording the prompt or the tools cannot fix, because the cause is the model's capability compared with the task. It runs in two directions, and they look nothing alike.

An over-provisioned model gets the answers right but is slow and expensive for the work. Think of a high-volume chat widget answering short, templated questions about order status and store hours on a frontier model. Nothing is being made up, and short questions do not overflow a context window. The task simply does not need that much model. For high-volume, straightforward tasks and tight latency budgets, the recommended starting point is the fastest, cheapest tier: Claude Haiku 5.5 suits high-volume and latency-sensitive work with checkable outputs. Make the answer longer or the prompt more detailed and you add cost without fixing the mismatch.

An under-provisioned model misses the quality bar even though the prompt is clear and the tools are well defined. Before you switch tiers, check effort. Several models trade intelligence for latency and cost within a single model, and tuning effort is often a better lever than switching models. If quality is not good enough and you lowered effort earlier, restore it. Otherwise, try the next tier up at its default effort. From cheapest to most capable, the current tiers are Claude Haiku 5.5, Claude Sonnet 5.5, Claude Opus 5.5 and Claude Fable 5.1.

The table shows why models should be compared on cost per completed task, not cost per token. On that benchmark subset, Fable 5.1 matched Opus 5.5 within run-to-run noise at about five times the cost per solved task. A suspected mismatch is still a hypothesis until you test it. Build benchmark tests on your own prompts and data, then compare the candidate models on accuracy, response quality and edge-case handling. Run the comparison as a head-to-head eval against your current baseline before switching, using [baselines, offline comparisons and live A/B tests](lesson:4.3).

A mismatch can also come from a model change rather than a capability gap. Prompts written for an older model can fail on a newer one. In the audit above, a budget_tokens setting returned a 400 error on Opus 5, and stale instructions raised costs after the migration. When failures begin right after a model switch, audit the prompts and request code against the new model before you conclude that the model is too weak.
