1.Guardrails when the user is the adversary

การวางระบบความปลอดภัยและการป้องกัน (Security & Guardrails) สำหรับแอปพลิเคชัน Claude:

  • Input Guardrails: ตรวจสอบคำสั่งของผู้ใช้เพื่อดักจับ Prompt Injection และ Jailbreak ก่อนที่จะส่งต่อให้โมเดลประมวลผล
  • Output Guardrails: ตรวจสอบผลลัพธ์ของโมเดลก่อนส่งให้ผู้ใช้ เพื่อป้องกันข้อมูลลับรั่วไหล หรือการละเมิด Content Policy
  • หลักการ Least Privilege: เอเจนต์ควรได้รับสิทธิ์ในการเข้าถึงเครื่องมือและฐานข้อมูลเท่าที่จำเป็นต่องานนั้นๆ เท่านั้น และคำสั่งอันตรายต้องมี Human-in-the-Loop เสมอ

📝 ข้อสอบจำลองทางการ (Official Exam Question)

A team is designing guardrails for a public-facing chatbot that anticipates jailbreak attempts crafted by adversarial users trying to bypass content guidelines. They want a scalable, low-latency way to catch obviously harmful requests before they reach the main conversation. Which architecture pattern is most consistent with Anthropic's recommended approach?

A Use a lightweight model like Claude Haiku 4.5 with a structured output schema to pre-screen user input for harmful intent before it reaches the main conversation
B Route every user message through the largest available model twice, first as a screen and then as the actual response, to maximize screening accuracy regardless of latency cost
C Rely exclusively on the main conversation's system prompt directives, since a strong role and refusal instructions alone are documented as sufficient without any separate screening step
D Disable the chatbot's ability to refuse requests and instead filter all output on the client side after the full response has already been generated and displayed
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. Anthropic recommends harmlessness screens using a lightweight model with structured outputs to classify harmful intent before input reaches the main conversation, which is efficient and scalable.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. Doubling up the largest, most expensive model for both screening and response is not the documented pattern and unnecessarily increases latency and cost versus a lightweight screening model.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. While system prompt directives strengthen guardrails, the documented approach explicitly layers additional strategies like screening and input validation rather than relying on the system prompt alone.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Filtering only after the full response has already been generated and displayed to the user defeats the purpose of a guardrail meant to prevent harmful output from reaching the user.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Guardrails when the user is the adversary" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A guardrail is any measure that keeps Claude within the behaviour you intend, even when something in its input tries to push it out. Anthropic separates the attacks into two threat models, and the right defence depends on which one you face. In the first, jailbreaks and direct prompt injection, the user of your application is the adversary and writes inputs designed to get around your rules. In the second, indirect prompt injection, the user is trusted, but Claude reads third-party content such as web pages, emails, documents or tool results, and that content contains adversarial instructions.

Against a hostile user, the defences are layered. A harmlessness screen runs a lightweight model such as Claude Haiku 4.5 on user input before it reaches the main conversation. It uses structured outputs (an output_config JSON schema with a single boolean such as is_harmful) so your code can branch on a value it can parse. Input validation filters out known injection patterns. An LLM given known jailbreak phrasing as examples can act as a general-purpose screen. In the system prompt itself, state the ethical and legal boundaries and tell Claude how to refuse. The docs' enterprise example lists values in a block and then gives the exact sentence to use when a request conflicts with them. Finally, look at behaviour over time: consider throttling or banning users who keep trying to get around your guardrails.

2.Guardrails for untrusted content Claude reads

การวางระบบความปลอดภัยและการป้องกัน (Security & Guardrails) สำหรับแอปพลิเคชัน Claude:

  • Input Guardrails: ตรวจสอบคำสั่งของผู้ใช้เพื่อดักจับ Prompt Injection และ Jailbreak ก่อนที่จะส่งต่อให้โมเดลประมวลผล

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Guardrails for untrusted content Claude reads" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

With indirect injection, the guardrail is mostly about structure: make it easy for Claude to tell your instructions apart from content it is only reading. Put third-party content only in tool_result blocks, because Claude is trained to be skeptical of instructions that appear there. Say what the content is and where it came from, for example "the body of an inbound email from an unknown sender", either in the tool description or in the result itself. Then state the policy in the system prompt, as in the snippet below.

Three more structural rules follow. First, JSON-encode untrusted strings rather than pasting them into free text. JSON escaping gives clear boundaries, so an attacker can't close a quote or tag and slip into the instruction context. Second, keep your own instructions out of tool results. Claude treats that content as untrusted, so your instructions there may be ignored or flagged as an injection. Send them in a user turn after the tool_result block, or, on supported models, in a mid-conversation system message. Third, apply least privilege so a successful injection does little harm: don't give Claude secrets it doesn't need, run tools in sandboxes, and scope permissions narrowly. You can also screen tool output with the same Haiku classifier pattern you use for user input, asking whether instructions are present rather than whether they would succeed. Before deploying, red-team the agent with documents and emails that contain deliberate injection attempts.

Not every guardrail is about attackers. Some keep Claude's claims tied to evidence. The simplest one is permission to be uncertain. Tell Claude explicitly that it may say it doesn't know, and give it the exact words to use when the material falls short. The docs' M&A-advisor prompt says to reply "I don't have enough information to confidently assess this" in that case, and the guidance says this alone can drastically reduce false information. For long documents (over 20k tokens), have Claude extract word-for-word quotes first and base its analysis only on those quotes.

Several other checks build on this. Verification with citations has Claude find a supporting quote for each claim after drafting, and retract any claim it can't support. Restricting outside knowledge tells Claude to use only the provided documents and not its general knowledge. Chain-of-thought verification asks for step-by-step reasoning so that faulty logic shows up. Best-of-N runs the same prompt several times and treats disagreement between the outputs as a warning sign. Iterative refinement feeds an output back in and asks Claude to verify it.

4.Guardrails against prompt leaks, and their cost

การแยกงานให้ Subagents ทำจะช่วยยกระดับผลลัพธ์ให้ดีขึ้นใน 3 สถานการณ์หลัก เท่านั้น หากอยู่นอกเหนือจากนี้ การประสานงานมักจะสร้างต้นทุนมากกว่าประโยชน์:

1. ป้องกัน Context Pollution (ผลลัพธ์เครื่องมือมีขนาดใหญ่มาก): เมื่อการทำงานย่อยสร้างโทเค็นที่ไม่เกี่ยวข้องมากกว่า 1,000 โทเค็น (เช่น อ่านเอกสารหนาๆ หรือค้นหาเว็บ) การให้ Subagent ทำจะช่วยกักกันข้อมูลส่วนเกินไม่ให้รบกวนการตัดสินใจของ Orchestrator
2. เมื่องานสามารถทำพร้อมกันได้ (Parallelization): หากงานย่อยหลายชิ้นเป็นอิสระต่อกัน (เช่น ตรวจสอบความปลอดภัย 3 ด้านคนละมุม) การส่งให้ Subagents ทำงานขนานกันจะช่วยลด Latency รวมของระบบได้อย่างมหาศาล
3. เมื่องานต้องการเครื่องมือเฉพาะทางสูง (Tool Specialization): การใส่เครื่องมือให้เอเจนต์ตัวเดียวมากเกินไป (Capability Bloat) จะทำให้ความแม่นยำในการเลือกเครื่องมือลดลง การแยก Subagent ตามหน้าที่ช่วยให้แต่ละตัวมีเครื่องมือเฉพาะทางเพียง 3-5 ชิ้นเท่านั้น
💰 ต้นทุนโทเค็นที่ต้องแลก (Token Cost): สำหรับงานประเภทเดียวกัน ระบบ Multi-Agent มักใช้โทเค็นมากกว่าระบบเอเจนต์เดี่ยวประมาณ 3 ถึง 10 เท่า เนื่องจากต้องส่งคำสั่งระบบซ้ำให้กับ Subagent แต่ละตัว และต้องเสียโทเค็นในรอบการรวบรวมข้อมูล

A prompt leak exposes information you meant to keep hidden in the prompt. The docs say plainly that no method is foolproof, and they warn that leak-proofing has a cost. Use leak-resistant techniques only when absolutely necessary, because the added complexity can lower performance on the rest of the task. If you do use them, test thoroughly to confirm output quality hasn't dropped.

When protection is justified, the documented options are: keep key context in the system prompt, separate from user queries, and repeat the critical instruction in the User turn. The AnalyticsBot example does this. Its system prompt is still mostly a role prompt, it contains a proprietary formula with an instruction never to mention it, and it gives a fixed deflection if the user asks about its instructions. Outside the prompt, post-process Claude's output with regular expressions or keyword filters to catch leaks. Leave out proprietary details Claude doesn't need, since extra content distracts it from the no-leak instruction. Audit prompts and outputs regularly.
