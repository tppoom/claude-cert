กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "What CLAUDE.md should contain" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

CLAUDE.md is the implementation guidance Claude Code reads for itself. It is a plain markdown file that Claude reads automatically at the start of every session in that directory. You never attach it or mention it in a prompt. Think of it as the briefing you would give a capable new teammate on their first morning: how the team works, what to avoid, and where the important pieces live.

The test for every line is whether Claude could work it out from the code alone. Bash commands it can't guess, style rules that differ from the defaults, and architectural decisions specific to the project all earn a place. File-by-file descriptions and standard conventions do not. Instructions should also be concrete enough to check. "Use 2-space indentation" can be followed, and "Format code properly" cannot.

Two more items are easy to get wrong. Hard constraints, such as never writing to the production database from tests, belong in the file. Aspirational rules the team does not actually follow do not, because Claude will follow them even though the team doesn't.

Put each instruction at the narrowest scope that still reaches everyone who needs it. Organization-wide policy goes in the managed file and team conventions go in the committed project file. Personal habits that apply to every project go in the user file, and personal details for one project go in CLAUDE.local.md.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Choosing the scope for each instruction" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

CLAUDE.md files exist at several scopes, and Claude merges them from broad to specific. Put each instruction at the narrowest scope that still reaches everyone who needs it. Team conventions go in the project file, committed to source control. Personal habits go in the user file, and sandbox URLs go in CLAUDE.local.md.

Timing matters as much as location. Files at and above the working directory load when the session starts. A subdirectory's CLAUDE.md loads only later, when Claude reads files in that subdirectory. In a monorepo, that makes the root file the place for rules that apply everywhere, such as commit conventions, and each package's own file the place for its stack.

Conventions for one area can live in two places. A per-directory CLAUDE.md sits next to the code, so its owners maintain it and it is versioned with that code. A path-scoped rule lives in .claude/rules/ at the root, with a paths: glob, and loads only when Claude works with a matching file. It is the better choice when you want every convention in one place, or when one rule covers many scattered paths. To keep another team's files out of a session, use claudeMdExcludes.

A CLAUDE.md can also import other files. Writing @ followed by a path, as in - git workflow @docs/git-instructions.md, makes Claude load that file at launch along with the main one. Imports are a way to split a long file into pieces, which raises the question of whether the pieces cost less.

A stale CLAUDE.md does more harm than having none, because Claude follows it with confidence. Running /init gives you a first draft: Claude explores the codebase and writes up build commands, test commands, a structure overview and the conventions it detects. Someone still has to review that draft, delete anything inaccurate and commit it. Keep the file under about 200 lines. Longer files use more context and Claude follows them less reliably.

Several triggers should prompt an edit:

- Claude gets the same thing wrong twice, which means a rule is missing, so add one line. - Conventions change, for example a new framework, test runner or set of lint rules. - A major model release lands, because rules that worked around an older model's limitation may now be overhead. - A quarterly skim turns up stale lines, which should be deleted.

Contradictions are the quiet failure. When two instructions conflict, Claude may pick either one, so periodically review the root file, nested CLAUDE.md files and .claude/rules/ together. Treat CLAUDE.md edits like any other documentation change and review them in pull requests, so conventions keep up with the code. A Stop hook receives the session transcript path when Claude finishes responding, so a script can propose updates while the gap is still fresh.

An edit made mid-session does not take effect straight away. Claude doesn't re-read the file from disk each turn, so a change is picked up only after /compact, after opening the file through /memory, or in the next session.
