💡 แนวคิดหลักสำคัญ (Key Concept)

Lifecycle ownership — An AI solution moves through discovery, design, handoff, monitoring, iteration and retirement, and each phase passes the next a concrete artifact. The architect owns the outcome across all of them: from whether the solution should exist, through how it behaves after launch, to the decision to retire it.

1.Six phases, each handing an artifact forward

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Six phases, each handing an artifact forward" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

An AI solution is never finished when its code runs. It goes through six phases, discovery, design, handoff, monitoring, iteration and retirement, and the useful way to think about each one is what it passes on. If a phase cannot name what it hands to the next, the next phase has to guess, and those guesses come back later as rework.

The phases form a loop rather than a line. Iteration sends you back through design and handoff for each new version. Monitoring keeps running for as long as the solution is live. Retirement can be triggered from outside the loop too, when the model your solution depends on reaches its retirement date. Shipping also brings its own vocabulary of migrations, versioning, rate limits and feature flags, and nobody raises those for you. Each one belongs to a specific phase, so plan for it there.

Discovery decides what success means before anyone writes a prompt. The questions about users, needs, experience and constraints are covered in [The discovery brief: users, needs, experience, constraints](lesson:6.1). At handoff, the artifact engineering depends on most is the set of tests that define done. Writing them is covered in [Acceptance tests defined before code](lesson:6.1). What matters at handoff is that each test is concrete enough for a stranger to judge pass or fail. "A patient with a basic smartphone can find the current wait time in under 30 seconds without creating an account" can be handed over. "The system is easy to use" cannot.

The tests keep working after launch. Each later change gets checked against them, so they are what lets a team keep changing a live system with confidence. A design handed over without them leaves engineering to define done for itself, and each engineer's definition will differ.

Handoff is also the last point before real users depend on the system, which makes it the place for a short readiness gate:

- Understanding: can the team explain what the code does, not just what it should do? - Testing: do the acceptance tests still pass, including edge cases such as missing data or a zero value? - Access: who does this build not serve well? - Responsibility: could the output be misread or misused, and is the AI's role disclosed? - Feedback loop: how will anyone know it is working after it ships?

The last question connects handoff to monitoring. If nobody can answer it, monitoring has nothing to measure.

Monitoring exists to give iteration evidence. That means measuring the success criteria from discovery against real use, along with cost and failures that a test set cannot predict. Instrumentation and dashboards at scale are the subject of [monitoring with logging and observability tools](lesson:4.6). In the lifecycle, the question is which signals feed the ship, fix or stop decision.

On Managed Agents, cost and effort per session show up as a cumulative usage object on the session. Read it once the session goes idle: by then the totals are final, and list_cost puts consumption at public list rates in cents.

Watching a number and cutting the session off yourself is the wrong way to enforce a limit. A session budget is a hard cap: the platform pauses each thread before its next model request once list cost reaches it. Every budget hit is still worth recording, because a solution that keeps hitting its cap is sending a signal that iteration has to deal with.

Webhook deliveries can be missed, so list sessions on a schedule as well and don't rely on push alone. A transcript review also has a limit to plan around: it finds problems only after the calls have run. Monitoring tells you what already happened. Preventing harm is the job of the limits set at design time.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Iteration: ship it, fix it, or stop it" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Every pass through iteration ends in one of three calls. Ship it means the version meets its criteria and holds them in production, so it continues. Fix it means a specific, measured gap exists and a reworked version can close it. Stop it means the solution is not delivering value that justifies keeping it, so it goes to retirement. The rule underneath all three is to prototype freely and ship selectively: cheap code creates value only when paired with honest evaluation.

Two kinds of evals make the call evidence-based. Capability evals start with a low pass rate and give a team something to climb toward. Regression evals should pass nearly 100% of the time, and any drop means something broke. A version that improves on capability evals but slips on regression evals is a fix it, however good the demo looks. A version that holds regression and moves capability toward the discovery criteria is a ship it.

Iteration repeats for as long as the solution is live, and each round should carry less risk than the last. Pinning sessions to an explicit version and moving traffic gradually is covered in [Promote, canary and roll back by version](lesson:4.3). In lifecycle terms, a rollback is a fast fix it: the previous version comes back while the new one is reworked.

Without evals, iteration turns reactive. The team waits for complaints, reproduces the problem by hand, fixes it and hopes nothing else regressed. It cannot tell a real regression from noise, so every decision to ship, fix or stop is a guess. A useful exercise before each release: deploy, share the change with a few real users, make one iteration based on what they report, and add tests that verify the change.

Retirement comes in two forms. Retiring your own work is a stop it decision coming out of iteration, and the willingness to deprecate your own work is an undervalued skill. The other form is set by the model calendar. Each Claude model has a lifecycle state, and once a model is retired, every request to it returns an error, whether or not your solution is ready.

A deprecation notice forces an iteration cycle with a deadline. Developers using Sonnet 4.5 were notified on September 30, 2026 that it retires on November 30, 2026. A team on claude-sonnet-4-5-20250929 has to move to claude-sonnet-5-5 inside that window: run the migration through the regression suite, adjust prompts, then ship. How fast that goes depends mostly on evals. Teams without them face weeks of testing when a new model arrives, while teams with them can find the model's strengths, tune prompts and upgrade in days.

Retiring a Managed Agents solution means deciding what to keep before deleting anything. Session history stays until the session is deleted, and files a session produced are deleted along with it. Copy events to your own logs with the events API before deleting the session. Download any output files you need first. Delete uploaded files, memory stores and vaults separately, because removing a session does not remove them.
