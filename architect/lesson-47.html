  • ✓Name the phases an AI solution passes through and the artifact each phase hands to the next

  • ✓Choose between the Client SDK, the Agent SDK and Managed Agents at design time based on who operates the agent loop and its infrastructure

  • ✓Plan for retirement of your own solution and of the model it runs on
💡 แนวคิดหลักสำคัญ (Key Concept)

Lifecycle ownership — An AI solution moves through discovery, design, handoff, monitoring, iteration and retirement, and each phase passes the next a concrete artifact. The architect owns the outcome across all of them: from whether the solution should exist, through how it behaves after launch, to the decision to retire it.

📑 หัวข้อในบทเรียนนี้ (In this lesson)
  • ▸1. Six phases, each handing an artifact forward
  • ▸2. Discovery hands design a definition of success
  • ▸3. Design picks the build surface the constraints allow
  • ▸4. Handoff gives engineering the tests, not just the design
  • ▸5. Monitoring turns live behaviour into decision inputs
  • ▸6. Iteration: ship it, fix it, or stop it
  • ▸7. Retirement: your work, and the model beneath it

An AI solution is never finished when its code runs. It goes through six phases, discovery, design, handoff, monitoring, iteration and retirement, and the useful way to think about each one is what it passes on. If a phase cannot name what it hands to the next, the next phase has to guess, and those guesses come back later as rework.

The phases form a loop rather than a line. Iteration sends you back through design and handoff for each new version. Monitoring keeps running for as long as the solution is live. Retirement can be triggered from outside the loop too, when the model your solution depends on reaches its retirement date. Shipping also brings its own vocabulary of migrations, versioning, rate limits and feature flags, and nobody raises those for you. Each one belongs to a specific phase, so plan for it there.

2. Discovery hands design a definition of success

Discovery decides what success means before anyone writes a prompt

The questions about users, needs, experience and constraints are covered in [The discovery brief: users, needs, experience, constraints](lesson:6.1)

In the lifecycle, the point is what discovery produces: a use case, success criteria that are specific and measurable, and an evaluation set that design and every later phase will be checked against.

The criteria have to be stated as numbers

"The model should classify sentiments well" gives design nothing to aim at

"F1 of at least 0.85 on a held-out set of 10,000 posts, 95% of responses under 200ms" gives it a target and a test

The evaluation set should mirror the real-world task distribution, including edge cases such as empty input or very long input

Otherwise the numbers measured during design say nothing about production.

Monitoring exists to give iteration evidence. That means measuring the success criteria from discovery against real use, along with cost and failures that a test set cannot predict. Every pass through iteration ends in one of three calls. Ship it means the version meets its criteria and holds them in production, so it continues. Fix it means a specific, measured gap exists and a reworked version can close it. Stop it means the solution is not delivering value that justifies keeping it, so it goes to retirement. The rule underneath all three is to prototype freely and ship selectively: cheap code creates value only when paired with honest evaluation.

Two kinds of evals make the call evidence-based. Capability evals start with a low pass rate and give a team something to climb toward. Regression evals should pass nearly 100% of the time, and any drop means something broke. A version that improves on capability evals but slips on regression evals is a fix it, however good the demo looks. A version that holds regression and moves capability toward the discovery criteria is a ship it.

Iteration repeats for as long as the solution is live, and each round should carry less risk than the last. Pinning sessions to an explicit version and moving traffic gradually is covered in [Promote, canary and roll back by version](lesson:4.3). In lifecycle terms, a rollback is a fast fix it: the previous version comes back while the new one is reworked.

Without evals, iteration turns reactive. The team waits for complaints, reproduces the problem by hand, fixes it and hopes nothing else regressed. It cannot tell a real regression from noise, so every decision to ship, fix or stop is a guess. A useful exercise before each release: deploy, share the change with a few real users, make one iteration based on what they report, and add tests that verify the change.

Retirement comes in two forms. Retiring your own work is a stop it decision coming out of iteration, and the willingness to deprecate your own work is an undervalued skill. The other form is set by the model calendar. Each Claude model has a lifecycle state, and once a model is retired, every request to it returns an error, whether or not your solution is ready.

A deprecation notice forces an iteration cycle with a deadline. Developers using Sonnet 4.5 were notified on September 30, 2026 that it retires on November 30, 2026. A team on claude-sonnet-4-5-20250929 has to move to claude-sonnet-5-5 inside that window: run the migration through the regression suite, adjust prompts, then ship. How fast that goes depends mostly on evals. Teams without them face weeks of testing when a new model arrives, while teams with them can find the model's strengths, tune prompts and upgrade in days.

Retiring a Managed Agents solution means deciding what to keep before deleting anything. Session history stays until the session is deleted, and files a session produced are deleted along with it. Copy events to your own logs with the events API before deleting the session. Download any output files you need first. Delete uploaded files, memory stores and vaults separately, because removing a session does not remove them.
