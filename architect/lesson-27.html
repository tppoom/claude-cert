💡 แนวคิดหลักสำคัญ (Key Concept)

Eval test case — The unit every evaluation is built from. It holds an input fed to the model, the model's output, a golden answer to compare against, and a score from a grader. You design the dataset by choosing the inputs and golden answers, and you design the framework by choosing how each output is scored.

1. Success criteria come before test cases

ชุดข้อมูลการประเมินจะมีประโยชน์ก็ต่อเมื่อมีการวัดสิ่งที่แน่นอนก่อนที่ทุกคนจะเขียนเคสทดสอบทีมต้องการเกณฑ์ความสำเร็จที่บอกว่าผลผลิตที่ดีเป็นอย่างไรเพราะทุกเคสและเกรดเดอร์ทุกคนมีอยู่เพื่อตรวจสอบหนึ่งในนั้นการเลือกมิติข้อมูลที่สำคัญเช่นความถูกต้องเวลาแฝงค่าใช้จ่ายหรือความปลอดภัยเป็นของ 📖 การกำหนดตัวชี้วัดการประเมินผล (4.1) บทเรียนนี้จะเริ่มต้นในอีกหนึ่งขั้นตอนต่อมา: รูปร่างที่เกณฑ์ต้องการก่อนที่ชุดข้อมูลจะสามารถทดสอบได้

A criterion is testable when it has four properties:

  • ▸
    Specific: it names the behaviour. "Accurate sentiment classification" is specific; "good performance" is not.
  • ▸
    Measurable: it uses a number, or a qualitative scale applied consistently alongside numbers. Even safety can be counted, for example fewer than 0.1% of outputs out of 10,000 trials flagged for toxicity.
  • ▸
    Achievable: the target comes from industry benchmarks, prior experiments or expert knowledge, and stays within what current frontier models can do.
  • ▸
    Relevant: it fits the application's purpose. Citation accuracy can be critical for a medical app and matter much less for a casual chatbot.

การเขียนใหม่แสดงให้เห็นถึงความแตกต่าง “โมเดลควรจําแนกความรู้สึกได้ดี” ล้มเหลวทั้งสี่แบบ เวอร์ชันที่ดีต้องการคะแนน F1 อย่างน้อย 0.85 ในชุดทดสอบที่ยืดหยุ่นของโพสต์ Twitter ที่หลากหลาย 10,000 รายการ การปรับปรุง 5% เมื่อเทียบกับเกณฑ์พื้นฐานปัจจุบัน เกณฑ์นั้นอธิบายชุดข้อมูลแล้ว: มันมีขนาดใหญ่แค่ไหน มันมาจากไหน และมันถูกยืดหยุ่น เกณฑ์ที่เขียนในลักษณะนี้บอกคุณว่าจะสร้างอะไรต่อไป

Run the same check on a draft like "summaries should be concise and helpful." Rewritten as "average at least 4 out of 5 on a completeness rubric across a 500-claim sample," it becomes a number you can check on every run, and it holds up: a rubric scale is a legitimate qualitative measure, and an average leaves room for imperfect individual outputs

Three other rewrites look like progress but still fail

"Sound less robotic" is a preference with no measurement attached

"A perfect 5 from every reviewer" is measurable but not achievable, because it demands flawless agreement that no baseline supports

"Every summary signed off by a senior reviewer" is a review process, not a criterion, and it puts a human into the grading of every run.

💡 Official Explanation (คำอธิบายเฉลย):

Only the rubric average is specific, measurable, achievable and relevant: a well-defined qualitative scale averaged over a fixed held-out set, which allows for imperfect individual replies. 📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

An evaluation dataset is only useful if it measures something definite. Before anyone writes a test case, the team needs success criteria that say what good output looks like, because every case and every grader exists to check one of them. Choosing which dimensions matter, such as accuracy, latency, cost or safety, belongs to [defining evaluation metrics](lesson:4.1). This lesson starts one step later: the shape a criterion needs before a dataset can test it.

A criterion is testable when it has four properties:

- Specific: it names the behaviour. "Accurate sentiment classification" is specific; "good performance" is not. - Measurable: it uses a number, or a qualitative scale applied consistently alongside numbers. Even safety can be counted, for example fewer than 0.1% of outputs out of 10,000 trials flagged for toxicity. - Achievable: the target comes from industry benchmarks, prior experiments or expert knowledge, and stays within what current frontier models can do. - Relevant: it fits the application's purpose. Citation accuracy can be critical for a medical app and matter much less for a casual chatbot.

A rewrite shows the difference. "The model should classify sentiments well" fails all four. The good version asks for an F1 score of at least 0.85 on a held-out test set of 10,000 diverse Twitter posts, a 5% improvement over the current baseline. That criterion already describes a dataset: how big it is, where it comes from, and that it is held out. A criterion written this way tells you what to build next.

Run the same check on a draft like "summaries should be concise and helpful." Rewritten as "average at least 4 out of 5 on a completeness rubric across a 500-claim sample," it becomes a number you can check on every run, and it holds up: a rubric scale is a legitimate qualitative measure, and an average leaves room for imperfect individual outputs. Three other rewrites look like progress but still fail. "Sound less robotic" is a preference with no measurement attached. "A perfect 5 from every reviewer" is measurable but not achievable, because it demands flawless agreement that no baseline supports. "Every summary signed off by a senior reviewer" is a review process, not a criterion, and it puts a human into the grading of every run.

Your criteria tell you what to test, and production tells you what mix of inputs to test it on. A dataset of only easy, well-formed inputs will score well and predict little. Automated evals can create false confidence when they don't match real usage patterns. So the first job is to reproduce the inputs the system actually receives: the same document types, lengths, phrasing and noise, in roughly the same proportions.

Next, add edge cases on purpose. They are rare in any sample, and failures tend to hide there. The standard categories are:

- irrelevant or nonexistent input data - overly long input data or user input - poor, harmful or irrelevant user input, in chat use cases - ambiguous cases where even humans would find it hard to agree on an assessment

Each task has its own edge cases. A summarization set adds multitopic articles and misleading headlines. An FAQ consistency set adds typos, long rambling questions and irrelevant personal details. A medical-privacy set adds health information that is explicit, hypothetical ("if my friend Alice, born on…") and implicit ("the same medication as his father"). Every case also needs a golden answer. That is either a mandatory exact match, or an example of a perfect answer that gives the grader something to compare against.

Take a clause-extraction feature tested only on clean, standard commercial leases. Adding more clean leases gives more statistical confidence about a category that was never the risk. Translating the set into other languages measures a capability that production may not use. Having experts re-label the existing leases improves label quality but adds no coverage. What improves prediction is adding the malformed, scanned and non-standard contracts that production actually sees, stratified so that each type sits alongside the standard leases.

After launch, real failures are the best source of new cases. Every bug that becomes a test case guards against that bug coming back, so the dataset tracks production more closely over time.

LLM graders take two common forms A Likert scale grader asks a model to rate an output from 1 to 5 against a target, such as how empathetic a customer-service reply is

It suits nuanced qualities like empathy, professionalism or patience that traditional metrics struggle to measure

A binary grader asks a yes/no question, such as "does this response contain personal health information?"

In both forms the grader prompt should demand a constrained output ("Output only the number", "Output only 'yes' or 'no'") so the verdict can be parsed in code

Use the cheapest grader that can reliably judge the criterion. Code-based grading is the best method whenever the eval can be designed to allow it, because it is fast and highly reliable. Model-based grading covers what code cannot judge. Human grading can judge almost anything, but it is slow and expensive, so avoid designing evals that depend on it where you can.

Code graders come in more than one form, and each answers a different question. Exact match checks whether the output equals the correct answer after whitespace and case are normalized, which suits categorical labels. Cosine similarity between sentence embeddings checks whether paraphrased versions of a question get semantically similar answers, so it measures consistency, not correctness. ROUGE-L measures the longest common subsequence between a generated summary and a reference summary.

LLM graders take two common forms. A Likert scale grader asks a model to rate an output from 1 to 5 against a target, such as how empathetic a customer-service reply is. It suits nuanced qualities like empathy, professionalism or patience that traditional metrics struggle to measure. A binary grader asks a yes/no question, such as "does this response contain personal health information?". It can catch implicit or subtle cases that rule-based checks miss. In both forms the grader prompt should demand a constrained output ("Output only the number", "Output only 'yes' or 'no'") so the verdict can be parsed in code. It is generally best practice to grade with a different model from the one that produced the output.
