💡 แนวคิดหลักสำคัญ (Key Concept)

Evidence-backed, bounded recommendation — A trade-off is communicated well when it comes with one recommended option, the price it pays in cost, speed, quality or risk, evidence from your own evaluation on your own workload, and limits on what can go wrong. Vendor figures tell you what to test, but they are not your evidence.

1. Turning model trade-offs into a plain recommendation

💡 แนวคิดหลักของหัวข้อนี้ (Core Concept)

การตัดสินใจทางสถาปัตยกรรม ทุกครั้งในโซลูชันของ Claude จะต้องแลกบางสิ่งที่ขัดแย้งกัน:

ความสามารถ ความเร็ว ต้นทุน และความเสี่ยง ผู้ที่อนุมัติ

งบประมาณไม่จำเป็นต้องมีพื้นที่ การแลกเปลี่ยนทั้งหมด พวกเขาต้องการคำแนะนำ ค่าใช้จ่าย และเงื่อนไขที่จะเปลี่ยนแปลง วิศวกรต้องการการตัดสินใจแบบเดียวกันโดยอธิบายผ่าน

กลไกของมัน การสื่อสารถึงข้อดีข้อเสียหมายถึงการพูดทั้งสองเวอร์ชันอย่างถูกต้อง และตัวเลือกรุ่นมักจะเป็นสิ่งแรกที่เกิดขึ้น

📌
Each Claude model balances capabilities, speed and cost differently, as covered in [Claude model lineup and its intelligence/speed/cost trade-offs](lesson:2.1). For an executive audience, turn those three axes into one sentence that has a reason and an exit condition. For example: "We start the ticket-triage step on Claude Haiku 5.5 because it is high-volume, straightforward work where latency and price matter most. We move up a tier only if our tests show a specific capability gap." That sentence follows the cost-first path: begin with Haiku 5.5, test thoroughly, and upgrade only where a gap appears. The capability-first path suits complex reasoning or high-autonomy agentic work. It reads differently: start on Claude Opus 5.5 because accuracy outweighs cost here, then lower effort or downgrade once the workflow is tuned.
📌
Present effort as the first dial, before any model switch. Several Claude models expose an effort parameter that trades intelligence for latency and cost within the same model. When a stakeholder says the system costs too much, the honest first answer is "we lower effort and re-measure", not "we move to a cheaper model". Speed can also be bought outright. Fast mode on Opus 5.5, Opus 5 and Opus 4.8 delivers up to 2.5x higher output speed at premium pricing. Put it to stakeholders as a direct exchange of money for response time.

Every architectural decision in a Claude solution trades a few things against each other: capability, speed, cost and risk. The person who approves the budget does not need the whole trade-off space. They need one recommendation, what it costs, and the condition that would change it. Engineers need the same decision explained through its mechanism. Communicating a trade-off means saying both versions accurately, and the model choice is usually the first place this comes up.

Public benchmarks fail in a specific way at the top of the range. The reverse case is just as persuasive: if the smaller model clears the bar, its price and speed win. The same logic decides when to go up a tier. If your evals show Opus struggling on some tasks, Fable is the next step, and the evidence for that step is your eval, not a benchmark table. Your evals also help with diagnosis. A team that starts on a small model can find it harder to tell model failures from setup failures. A head-to-head eval run on the same harness separates the two, so a poor result is not blamed on the wrong thing.

The technical audience needs the same decision explained through mechanism, and here precision is the trade-off. If you misdescribe a feature in a design walkthrough, the team builds the wrong thing. Three choices come up often in long-running agent work, and in each one the wrong explanation sounds plausible.

Compaction and context editing both keep a long session inside the context window, but they work differently and in different places. Compaction runs on the server. When the conversation approaches the context window limit, it automatically summarises the whole conversation, so the session continues without client-side bookkeeping. Context editing is configured from the client and clears specific content, such as old tool results. Neither one requires the Batch API, and neither one is tied to a particular model tier. For a multi-hour coding agent, describe compaction as "keeps the active context small automatically" and context editing as "drops stale tool output we choose to drop". Pair either one with a memory tool when facts must survive summarisation.

Which thinking modes are available depends on the model generation, so the explanation has to name models. Extended thinking is the older manual mode, set with a token budget. Claude 4.7 and later models reject it with a 400 error. On those models, Claude Opus 4.8 included, adaptive thinking is the only mode, and the model decides when and how much to think. On Claude 4.5 and earlier models that support thinking, Claude Haiku 4.5 included, extended thinking is the only mode, and adaptive thinking is not available. A team building on both models needs two code paths. A team planning to send extended-thinking requests to Opus 4.8 should budget for that change now, not find it at the first failed request.

Choosing between Claude Managed Agents and the Claude Agent SDK is a decision about who runs the infrastructure, not about capability. Both work with the same concepts: agents, tools and sessions. The SDK runs in a process you operate, with custom tools defined in your code. Managed Agents is a pre-built agent harness running on Anthropic's infrastructure, aimed at long-running tasks and asynchronous work. Sessions run in an Anthropic-managed cloud sandbox, or in a self-hosted one if you configure that, and the agent definition is stored and versioned on the server. When the requirement is a continuously running agent with no sandbox or session infrastructure for your team to operate, the honest justification is that Anthropic runs the sandbox and session state. It is not that the SDK lacks features.
