1. ค่าใช้จ่ายของ Agent จากเครื่องมือมากเกินไป

คําจํากัดความของเครื่องมือแต่ละรายการที่คุณแนบมาจะได้รับการชําระเงินในบริบทก่อนที่ Agent จะอ่านคําขอของผู้ใช้ Claude จะเห็นชื่อ คําอธิบาย และรูปแบบการป้อนข้อมูลของเครื่องมือแต่ละรายการทุกครั้ง เครื่องมือ 50 รายการสามารถใช้โทเค็นได้ 10-20,000 รายการ การตั้งค่าหลายเซิร์ฟเวอร์ทั่วไปที่เชื่อมต่อ GitHub, Slack, Sentry, Grafana และ Splunk สามารถใช้โทเค็นได้ประมาณ 55,000 รายการบนคําจํากัดความก่อนที่ Claude จะทํางานใดๆ โทเค็นเหล่านั้นจะออกมาจากหน้าต่างเดียวกันกับที่งานต้องการสําหรับไฟล์ ผลลัพธ์ของเครื่องมือ และการให้เหตุผล

ค่าใช้จ่ายเกินกว่าพื้นที่ บริบททํางานเหมือนงบประมาณความสนใจ และโทเค็นที่เพิ่มเข้ามาแต่ละรายการจะลดลง เมื่อจํานวนโทเค็นเพิ่มขึ้น โมเดลจะจําและวิเคราะห์สิ่งที่อยู่ในหน้าต่างได้แย่ลง แค็ตตาล็อกเครื่องมือที่ Agent ส่วนใหญ่ไม่สนใจยังคงให้ความสนใจกับทุกคําขอ ใน Agent ที่ทํางานเป็นเวลานาน คําจํากัดความเหล่านั้นจะแข่งขันกับกองบล็อก tool_result ที่เพิ่มขึ้น และ Agent อาจหมดบริบทก่อนที่จะทํางานเสร็จสิ้น

Every tool definition you attach is paid for in context before the agent reads the user's request. Claude sees each tool's name, description and input schema on every turn. Fifty tools can use 10–20K tokens. A typical multi-server setup that connects GitHub, Slack, Sentry, Grafana and Splunk can use about 55k tokens on definitions before Claude has done any work. Those tokens come out of the same window the task needs for files, tool results and reasoning.

The cost goes beyond space. Context behaves like an attention budget, and every added token draws it down. As the token count rises, the model gets worse at recalling and reasoning over what's in the window. A tool catalogue the agent mostly ignores still takes attention on every request. In a long-running agent, those definitions compete with the growing pile of tool_result blocks, and the agent can run out of context before it finishes the task.

The third cost is wrong choices. Claude picks the right tool less reliably once more than roughly 30–50 tools are loaded at the same time. Overlap makes this worse at any size: if two tools both look like they could answer a request, Claude can pick the wrong one, call the right one with the wrong parameters, or spend turns on a roundabout strategy. A wrong tool call costs a round trip, adds a misleading result to the history, and sometimes performs an action nobody wanted. That last case is why bloat matters for safety as well as cost.

A bloat review reads the configuration against the agent's real workflow and asks one question of every entry: what would break if this were gone? Four kinds of finding come up again and again.

- Overlapping tools. Two or more tools do much the same job, such as list_users and search_users, or separate get-by-id and list endpoints that are always called together. - Unused tools. Definitions the agent never calls in its actual tasks. These are often whole MCP servers connected "just in case". - Vague descriptions. A tool whose purpose Claude can't tell apart from a neighbour's, or whose parameters it keeps getting wrong. - Over-connected MCP servers. Servers picked up from project files, user settings, plugins or organisation connectors that this agent never meant to use.

Transcripts and metrics are better evidence than reading the config. Record the total number of tool calls, token consumption and tool errors per task, and read the raw tool calls rather than only the agent's own account of what it did. The patterns that show up point to specific fixes. A run of tool errors for invalid parameters usually means a description needs to be clearer or needs examples. Tools that are always called in the same order are candidates for merging. Tools that never appear in any transcript are candidates for removal.

Over-connection needs its own check, because MCP servers can come from several places at once. In the Agent SDK, strict_mcp_config set to true uses only the servers passed in mcp_servers, and ignores project.mcp.json, user settings, plugin-provided servers and claude.ai connectors. Consolidation fixes overlap by building tools around tasks rather than endpoints. A common mistake is to write tools that simply wrap existing software functions or API endpoints one-to-one. The agent then has to chain them, reading every intermediate result into its context. A single tool can do several discrete operations or API calls internally and return only what the task needs.

Consolidating pays off twice. There are fewer definitions in context, which keeps the agent further below the 30–50-tool range where selection starts to degrade. And work that used to be the agent's reasoning moves into the tool, so the agent has fewer chances to make a mistake. Give each surviving tool one clear purpose that differs from its neighbours. Tool boundaries should split work the way a person with the same resources would split it.

Namespacing deals with the tools that rightly remain. When an agent can reach many servers, put related tools under shared prefixes: by service (asana_search, jira_search) and, within a service, by resource (asana_projects_search, asana_users_search). Claude can then tell two search tools apart before it reads either description. Some MCP clients add prefixes by default. Whether the prefix goes at the start or the end of the name has had measurable effects on tool-use evaluations, and the effect differs between models. Choose the scheme by running your own evaluation, not by habit.

Scoping gives each agent or subagent only the tools its role needs. In the Agent SDK this is the subagent's tools field, set in its own AgentDefinition. A subagent doesn't automatically get a narrower set than its parent: if you leave tools out, it inherits every tool available to subagents. A code reviewer launched by a lead agent that has Write, Edit and Bash therefore gets all three unless its own definition lists something narrower. Notes in CLAUDE.md and the parent's permission mode don't change the reviewer's tool set.

Removal works at server level too. disallowedTools takes MCP patterns: mcp__server or mcp__server__* removes every tool from that server, and mcp__* removes every MCP tool from any server. A pattern like mcp__legacy__* strips a legacy server out of one agent while other agents keep it. mcpServers on an agent definition names the only servers that agent gets. Unused servers that no agent needs should be disconnected altogether.

Approving a tool and scoping a tool are separate controls. allowedTools approves tools in advance so they run without a prompt, but it doesn't stop Claude from calling other tools. The permission mode decides what happens to those other calls. In default, any call that needs approval and matches no allow rule goes to your canUseTool callback, which is no use in a CI job with nobody to answer. In dontAsk, any call that would have prompted is denied, and canUseTool is never called. An allowlist combined with dontAsk is the closed configuration a headless agent needs: listed tools run and everything else is refused.

The other modes go the opposite way. bypassPermissions lets tools run without prompts, apart from the few actions no mode auto-approves. Combined with a denylist such as Edit, Write and Bash, it fails open: any tool you forgot to list runs freely. acceptEdits approves file edits and filesystem operations automatically, which is exactly what a read-only agent must not do. allowedTools: ["*"] approves everything in advance. During a bloat review, each of these widens the surface rather than shrinking it.

Skills count toward the surface as well. A skill is a reusable set of instructions kept in a SKILL.md file inside a skills/<name>/ folder. The file opens with frontmatter, a short block of name: and description: lines between --- markers, followed by the instructions themselves. At session start Claude loads only a short listing of each skill's description; the full text loads when the skill is invoked, either by Claude when the description fits the request or by a person typing /name. Every skill therefore adds an entry to that listing. The description and the optional when_to_use field (trigger phrases or example requests) are cut off together at 1,536 characters to limit context use. If a skill has side effects and a person should decide when it runs, set disable-model-invocation: true in its frontmatter. Each bloat remedy acts on a different source of pressure, so the diagnosis decides which one to use. Merging, namespacing and scoping change the set of tools an agent has. The context remedies leave the set alone and change where the tokens go. Choose by where your tokens, or your wrong tool calls, are actually coming from.

Programmatic tool calling replaces a chain of tool calls with one script. Instead of five round trips of tool_use and tool_result, Claude writes a single block of code that calls all five functions, and Anthropic's code execution sandbox runs it. Only the script's final output returns to the conversation; the intermediate results never enter the history. It fits repetitive chains of small calls that could run as a single batch, and it does nothing for an oversized toolset.

Tool search fixes having too many definitions in context, not having tools that overlap. [Tool search (defer_loading, tool_reference, ENABLE_TOOL_SEARCH)](lesson:3.8) holds back deferred definitions until Claude searches for them. It costs a little latency, one extra turn to look a tool up, and saves a lot of baseline context. It's the right choice when the catalogue is genuinely large and each request needs only a few tools. It does nothing about two tools with blurred boundaries. When a search turns up both of them, Claude faces the same confusing choice as before, so overlap is still fixed by merging and namespacing.

Prompt caching is the other remedy that's easy to misapply. It doesn't reduce the number of tokens in context. It reduces what you pay for them on later requests, so a large fixed toolset gets cheaper but takes up just as much of the window and the attention budget. Use it when the problem is cost. When the problem is selection accuracy or running out of context, merge, scope or defer instead.

The remedies combine without conflict. A sensible order for a high-volume agent is to cache tool definitions from day one, add tool search once the toolset passes roughly 20 tools or baseline context use becomes noticeable, and add context editing when conversations get long enough that early results no longer matter. Merging and scoping come before all of these. A tool you removed costs nothing to defer, cache or trim.

  • ✓รวมเครื่องมือที่ซ้ำซ้อนเป็นเครื่องมือระดับสูงกว่าและตั้งชื่อพื้นที่ของเครื่องมือที่เหลือโดยบริการและทรัพยากร
  • ✓จำกัด Agent และ Subagents แต่ละตัวให้ใช้เครื่องมือที่บทบาทของมันต้องการโดยใช้ tools, disallowedTools, mcpServers และโหมดการอนุญาต
  • ✓เลือกจากการรวมศูนย์, การกำหนดขอบเขต, การค้นหาเครื่องมือ, การแคชพรอมต์ และการแก้ไขบริบท ขึ้นอยู่กับว่าความกดดันของบริบทมาจากที่ใด
