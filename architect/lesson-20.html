📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Choose a monitoring tool by starting from the question you need answered. An OpenTelemetry pipeline means running a collector and a backend and making content decisions. It is worth that cost when you need per-user token counts, costs and tool activity, or traces of individual runs. Many questions need far less. Spend per workspace, how many developers used Claude Code this week, or what one agent session cost can each be answered with no collector at all.

The lightweight options are already built in. The Agent SDK message stream reports token and cost data your application can read directly. A Managed Agents session carries a usage object with its token counts, active seconds and list cost. A session.usage event delivers the same snapshot on the stream, so you don't need to poll. For an organization, the Usage & Cost API returns usage and cost by workspace, model and API key. For Claude Code on a Team or Enterprise plan, the analytics dashboard covers adoption.

2. Attributing spend with the Usage & Cost API

การแยกงานให้ Subagents ทำจะช่วยยกระดับผลลัพธ์ให้ดีขึ้นใน 3 สถานการณ์หลัก เท่านั้น หากอยู่นอกเหนือจากนี้ การประสานงานมักจะสร้างต้นทุนมากกว่าประโยชน์:

1. ป้องกัน Context Pollution (ผลลัพธ์เครื่องมือมีขนาดใหญ่มาก): เมื่อการทำงานย่อยสร้างโทเค็นที่ไม่เกี่ยวข้องมากกว่า 1,000 โทเค็น (เช่น อ่านเอกสารหนาๆ หรือค้นหาเว็บ) การให้ Subagent ทำจะช่วยกักกันข้อมูลส่วนเกินไม่ให้รบกวนการตัดสินใจของ Orchestrator
2. เมื่องานสามารถทำพร้อมกันได้ (Parallelization): หากงานย่อยหลายชิ้นเป็นอิสระต่อกัน (เช่น ตรวจสอบความปลอดภัย 3 ด้านคนละมุม) การส่งให้ Subagents ทำงานขนานกันจะช่วยลด Latency รวมของระบบได้อย่างมหาศาล
3. เมื่องานต้องการเครื่องมือเฉพาะทางสูง (Tool Specialization): การใส่เครื่องมือให้เอเจนต์ตัวเดียวมากเกินไป (Capability Bloat) จะทำให้ความแม่นยำในการเลือกเครื่องมือลดลง การแยก Subagent ตามหน้าที่ช่วยให้แต่ละตัวมีเครื่องมือเฉพาะทางเพียง 3-5 ชิ้นเท่านั้น

The Usage & Cost API answers organization-level questions with an Admin API key and no infrastructure. It has two endpoints. usage_report/messages returns token counts in 1-minute, 1-hour or 1-day buckets. cost_report returns costs in USD and supports daily buckets only. To build workspace chargebacks, group costs by workspace_id and description. Usage attributed to the Default Workspace appears with a null workspace_id.

The API's limits show when it is the wrong tool. Data usually appears within about five minutes of a request, and the API supports polling once per minute over sustained use. That suits dashboards and budget alerts, but not debugging live. It also has no concept of an individual user. The Console's usage and cost pages cannot break spend down by user, and issuing one API key per developer to fake it runs into performance limits. For per-user Claude Code costs, use the Claude Code Analytics API instead.

Rate limits are set at the organization level, so a Claude Code rollout needs one total allocation, not a set of individual ones. To size it, multiply the headcount by the per-user tokens-per-minute (TPM) and requests-per-minute (RPM) figures for your team-size tier. The per-user figure falls steeply as the team grows, so a figure taken from a small pilot overstates what a large organization needs per developer.

Here is a worked case. A 15-developer pilot sits in the 5–20 tier at 100k–150k TPM per user. Scaling to 300 developers with that figure gives 30M–45M TPM. The 100–500 row is the correct one for 300 developers: 15k–20k TPM and 0.37–0.47 RPM per user, or roughly 4.5M–6M TPM and 111–141 RPM in total. Once usage comes from Console accounts, Claude Code gets its own workspace with its own usage and rate limits, separate from your other workloads. Workspace limits can be set lower than the organization's limits, but not higher.
