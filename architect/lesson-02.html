1. The agent loop from input to output

ทุก Architecture ที่ใช้ Claude ไม่ว่าจะเป็นแค่การเรียก Tool ครั้งเดียว ไปจนถึง Coding Agent ที่ทำงานต่อเนื่องหลายชั่วโมง ต่างรันอยู่บน Cycle เดียวกัน การทำความเข้าใจ Cycle นี้ให้ชัดเจนคือก้าวแรกที่จะกำหนด Design ส่วนที่เหลือทั้งหมด: แหล่งที่มาของ Input, สิ่งที่ถูกประมวลผลระหว่าง Run, สิ่งที่นับว่าเป็น Output และจุดที่รับ Feedback วนกลับเข้ามา

Input ไม่ได้มีแค่ข้อความของผู้ใช้เท่านั้น ทุกครั้งที่เรียก Claude ตัวโมเดลจะมองเห็นทั้ง Prompt, System Prompt, Tool Definitions และ Conversation History ทั้งหมด ดังนั้นการตัดสินใจระดับ Design ในแต่ละ Turn จึงรวมถึง: การเลือก Tool ที่จะเปิดให้ใช้, คำสั่งที่ส่งให้โมเดล และขนาดของ History ที่ต้องส่งไป สำหรับ Agent SDK จะเริ่มต้น Run ด้วย SystemMessage ที่มี subtype เป็น init ซึ่งใช้เก็บ Session Metadata

การประมวลผลจะเกิดขึ้นเป็น Turn โดย Claude จะประเมิน State ปัจจุบันแล้วตอบกลับมาเป็น Text, Tool Calls (หนึ่งคำสั่งขึ้นไป) หรือทั้งคู่ จากนั้นฝั่ง Application จะรัน Tool แล้วส่งผลลัพธ์กลับไปให้ Claude ตัดสินใจในสเต็ปถัดไป วงรอบ evaluate-then-execute ครบหนึ่งครั้งนี้นับเป็น 1 Turn และ Agent อาจต้องใช้เวลาหลาย Turns กว่าจะทำงานเสร็จสิ้น

Output จะเกิดขึ้นเมื่อ Claude ตอบกลับมาโดยไม่มี Tool Calls ใดๆ ใน Agent SDK ข้อความสุดท้ายนี้จะส่งมาเป็น AssistantMessage ตามด้วย ResultMessage ที่เก็บ Final Text, Token Usage, Cost และ Session ID ทั้งนี้จำเป็นต้องตรวจสอบ subtype ของ ResultMessage ด้วยเสมอ เพราะการ Run อาจจบลงเพราะติด Limit ไม่ใช่เพราะงานสำเร็จ

ตัวอย่าง Case จริง: งานแก้ Auth Test ที่พัง ใน Turn 1 Claude สั่งรัน npm test ผ่าน Bash แล้วได้ผลลัพธ์ Failed 3 จุด ใน Turn 2 โมเดลอ่าน auth.ts และ auth.test.ts ใน Turn 3 ทำการ Edit ไฟล์ auth.ts และสั่งรัน Test ซ้ำจนผ่านหมดทั้ง 3 จุด ใน Turn สุดท้ายไม่มีการเรียก Tool Call แต่ส่งเพียงข้อความ "Fixed the auth bug, all three tests pass now." ลำดับขั้นตอนเหล่านี้ไม่ได้ถูก Hardcode ไว้ล่วงหน้า แต่ Claude เลือกแต่ละ Action ตามผลลัพธ์ที่ได้รับจากสเต็ปก่อนหน้า

หากใช้ raw Messages API คุณต้อง Implement ลูปนี้เองด้วย while loop ที่เช็ก stop_reason: ถ้าเหตุผลคือ tool_use ให้รัน Tool ที่ขอมา เพิ่ม tool_result blocks เข้าไปใน Conversation แล้วส่งกลับไปใหม่ หากเป็น stop_reason อื่น ลูปจะสิ้นสุดลง และ Application จะต้องจัดการตามแต่ละเคส

Every Claude-based architecture, from a single tool call to a multi-hour coding agent, runs the same cycle. Draw that cycle first and the rest of the design hangs off it: where the input comes from, what runs during processing, what counts as output, and where feedback comes back in.

Input is more than the user's message. Each time Claude is called it sees the prompt, the system prompt, the tool definitions and the conversation history so far. So the design decisions that shape every turn sit here: which tools to expose, what instructions to give, how much history to carry. The Agent SDK marks the start of a run with a SystemMessage of subtype init, which carries the session metadata.

Processing happens in turns. Claude looks at the current state and replies with text, one or more tool calls, or both. The tools run, and each set of results goes back to Claude for its next decision. One full pass of evaluate-then-execute is a turn, and an agent may take many turns before it finishes.

Output comes when Claude gives a response that contains no tool calls. In the Agent SDK that final text arrives as an AssistantMessage, followed by a ResultMessage that holds the final text, token usage, cost and session ID. Check the ResultMessage subtype as well, because a run can end by hitting a limit rather than by succeeding.

A worked case shows the shape. The task is to fix a failing auth test. In turn 1 Claude runs npm test through Bash and gets back three failures. In turn 2 it reads auth.ts and auth.test.ts. In turn 3 it edits auth.ts and runs the tests again, and all three pass. The final turn has no tool call, only the text "Fixed the auth bug, all three tests pass now." Nobody coded those steps in advance. Claude chose each one based on the result of the step before.

With the raw Messages API you write this loop yourself. It is a while loop keyed on stop_reason: if the reason is tool_use, run the requested tools, add the tool_result blocks to the conversation and send it again. Any other stop reason ends the loop, and your application has to handle each one.

You also have to decide who hosts the loop. The Messages API is best for custom agent loops where you want fine-grained control. Claude Managed Agents gives you a ready-made harness: you don't build your own loop, tool execution or runtime, and it suits long-running, asynchronous work.

Claude never runs a tool itself. It emits a structured request, something outside the model carries it out, and the result goes back into the conversation. The main design question for any tool is therefore where its code runs, because that decides what your application is responsible for.

Tools fall into three groups. User-defined client tools carry most tool-use traffic. You write the schema, run the code and return the result. Claude sees the schema and the result but never your implementation. Anthropic-schema client tools (memory, bash, text_editor, computer, browser) run the same way, in your code. The difference is that Claude was trained on these exact signatures, so it calls them more reliably and recovers from errors better than it would with a custom tool that does the same job. Server tools (web_search, web_fetch, code_execution, tool_search) run on Anthropic's infrastructure. You enable them in the request and never build a tool_result for them.

Client tools put a round trip in every call. The model can't run your code, so it asks, you execute, you report back, and it carries on. Server tools turn that around. A single request can set off several searches or code runs inside Anthropic's own loop, and the response arrives with the server_tool_use blocks already done. Your application usually just reads the answer.

That server-side loop has two exits to design for. It has an iteration cap, and hitting the cap returns pause_turn instead of end_turn. The work isn't finished, so send the conversation again with the paused response and the model picks up where it stopped. Second, if Claude calls a server tool and a client tool in the same group of parallel calls, the response comes back as tool_use with a server_tool_use block that has no result yet. The API runs it only after you return the client tool results.

  • •

Every tool adds a round trip, so include one only when it does something text alone can't. Tool use fits four situations:

- Actions with side effects, such as sending an email or updating a record. The model can describe them, but only a tool can do them. - Fresh or external data, such as current prices or the contents of your database. - Output that must have a fixed structure, where a schema enforces the fields. - Calls into existing systems, such as internal APIs, databases and filesystems.

A design smell gives it away. If you find yourself writing a regex to pull a decision out of model output, that decision should have been a tool call. The reverse case matters as much. Summarization, translation and general-knowledge Q&A need no tool. And when the response is trivial, a tool's latency can cost more than the work itself.

Integrations with several systems raise another question: does each one need its own hand-written execution code? An agent that reads a wiki, queries a ticket database and posts to chat could each be a user-defined client tool, with your loop checking stop_reason and calling a handler for each. That is three integrations to build and maintain. Connecting MCP servers instead exposes each system through one standardized protocol. Claude still decides when to call each tool. Managed Agents, for example, declares MCP servers on the agent and supplies credentials when each session is created. Choosing between MCP and other integration mechanisms is covered under [connection protocols](lesson:3.7).

Two shortcuts fail for different reasons. Pasting the wiki, database and chat contents into the system prompt gives Claude a stale copy and no way to act. It can't post a reply or see a ticket that changed a minute ago. A precomputed decision tree that runs fixed API calls without the model removes the very thing the agent loop adds: the model choosing the next step from the last result.

The model that does the processing sets most of the system's cost and latency, and choosing it is an architecture decision. The default is to start small and earn the upgrade. Start with a fast, low-cost Haiku model, test it on real inputs, and move up to a more capable model only where the tests show a capability gap. Take a ticket-triage pipeline with a strict cost ceiling per ticket. Sending every ticket through the largest model at maximum effort pays for capability most tickets never use. Agentic systems often trade latency and cost for better task performance, and that trade has to be justified rather than assumed. Picking a model at random for each ticket averages the cost, but quality becomes unpredictable and the design has no idea which tickets needed more. Replacing Claude with a separately trained classifier throws away the reasoning about edge cases the task needs. 5. Feedback loops สำหรับแก้ไขการทำงานระหว่าง Run

ระบบจะสามารถแก้ไขข้อผิดพลาดระหว่าง Run ได้ ก็ต่อเมื่อมี Feedback จาก Environment ส่งกลับเข้ามาใน Loop ซึ่งมีจุดออกแบบ Feedback ทั้งหมด 3 ระดับ โดยแต่ละระดับจะมีโครงสร้างที่รัดกุมขึ้นเรื่อยๆ

Tool results คือช่องทาง Feedback ขั้นพื้นฐาน เช่นในเคส auth-bug ผลลัพธ์จากการรัน `npm test` ครั้งแรกทำให้ Claude รู้ว่าต้องไปอ่านไฟล์ไหน และการรันครั้งที่สองช่วยยืนยันการแก้บั๊ก ดังนั้นควรออกแบบ Tools ให้ส่ง Checkable facts ที่ตรวจสอบได้เสมอ เช่น Test results, Validator errors หรือ Schema failures เพื่อให้ Claude นำไปประมวลผลต่อใน Turn ถัดไป เพราะ Tool ที่ตอบกลับแค่คำว่า "done" จะไม่ให้ข้อมูลที่เป็นประโยชน์ต่อการแก้ไขงานเลย

Hooks เปลี่ยน Feedback ให้กลายเป็น Code ที่รันแน่นอนในทุก Turn ไม่ว่า Model จะตัดสินใจอย่างไร โดย Agent SDK อนุญาตให้ Hooks เข้าไป Intercept, ดัดแปลง หรือบล็อก Tool call ก่อนทำงาน (`PreToolUse`) รวมถึงยิง Callback หลัง Tool ทำงานเสร็จ (`PostToolUse`) แต่ละ `HookMatcher` จะจับคู่ Matcher pattern เช่น `Write|Edit` เข้ากับลิสต์ของ Callbacks ตัวอย่างเช่น หากต้องการบันทึก Audit log ทุกครั้งที่ Agent แก้ไขไฟล์ ให้ลงทะเบียน `PostToolUse` Hook คู่กับ `Edit|Write` แล้วใช้ Callback ทำการ Append log การสั่งใน System Prompt ว่า "อย่าลืมบันทึกการแก้ไขนะ" ต้องพึ่งพาการปฏิบัติตามของ Model ทุกรอบใน Long-running session ส่วนการเขียนสคริปต์ภายนอกมา Polling filesystem ก็ทำได้แค่เดาว่าเกิดอะไรขึ้น และการให้ User กดยืนยันทุกครั้งก็เป็นเพียง Human approval gate ไม่ใช่ Audit log

A system corrects itself during a run only if feedback from its environment comes back into the loop. There are three places to design that feedback in, each more structured than the last.

Tool results are the basic feedback channel. In the auth-bug run, the first npm test result is what sent Claude to read the files, and the second run confirmed the fix. Design tools that report checkable facts, such as test results, validator errors or schema failures, and Claude can react to them on its next turn. A tool that only says "done" gives it nothing to correct against.

Hooks turn feedback into code that runs every time, whatever the model decides. The Agent SDK lets hooks intercept, modify or block a tool call before it runs (PreToolUse), and fire after a tool has run (PostToolUse). Each HookMatcher pairs a matcher pattern such as Write|Edit with a list of callbacks. To write an audit entry every time the agent changes a file, register a PostToolUse hook matched to Edit|Write whose callback appends the entry. Putting "remember to log your edits" in the system prompt depends on the model complying on every turn of a multi-hour run. Polling the filesystem from outside only guesses at what changed. Asking the user to confirm each edit is a human approval gate, not an audit log.

Graded outcomes close the loop on the whole deliverable, not on individual tool calls. In Claude Managed Agents you define an outcome: a description of done plus a rubric. The harness then sets up a grader that checks the artifact against the rubric in a separate context window, so the agent's own implementation choices don't sway it. The grader's explanation of which criteria passed or failed goes back to the agent for its next iteration. This is the [evaluator-optimizer pattern](lesson:1.3) built into the harness.

A grader is only as good as its rubric. It scores each criterion on its own, so "The data looks good" produces noisy verdicts while "The CSV contains a price column with numeric values" produces a clear one. The iteration cap is the loop's stop condition. Without it, a rubric the agent can never satisfy would keep the agent revising indefinitely.
