💡 แนวคิดหลักสำคัญ (Key Concept)

Run-level telemetry — Telemetry that records an agent turn as a tree: one parent span for the turn, with child spans for each model request, tool call and subagent. You can then see how a run unfolded and where it went wrong, which a flat list of API calls cannot show.

คำตอบที่ถูกต้อง: ตัวเลือก A

Each tool span has two separate children: claude_code.tool.blocked_on_user for the permission wait and claude_code.tool.execution for the run itself. That split lets you see that a slow tool call was waiting for a human, not running slowly. A flat log of API calls cannot show this.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Why agent runs resist ordinary debugging" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A request log answers the wrong question for an agent. One prompt to an agent can turn into a dozen model requests, several tool calls, a wait for a human to approve a permission, and a subagent that makes its own requests. Each step depends on what the model chose in the step before, so running the same prompt twice can follow a different path. A log with one row per API call shows that request 7 returned max_tokens. It cannot show which turn request 7 belonged to, which agent sent it, or that the tool call before it waited four minutes for approval.

Tracing puts those relationships back. Each turn becomes a claude_code.interaction span. Model calls and tool calls nest under it, and a tool span has separate children for the permission wait and for the execution itself. When the Agent tool starts a subagent, the subagent's own request and tool spans nest under the tool call that started it.

Attributes on the claude_code.llm_request span tell you where in a multi-agent run a request came from. agent_id identifies the subagent or teammate that sent the request, and parent_agent_id identifies the agent that spawned that one. query_source_safe gives a bounded name for the subsystem that sent it, such as repl_main_thread or agent.builtin.general-purpose. The same span also records attempt (how many attempts the request took), stop_reason, and, when the request failed, an error_class such as api_timeout or server_overload. Together these separate a run that ran out of output tokens from one that kept retrying an overloaded endpoint.

Claude Managed Agents gives you a similar view with no code. The session viewer in the Claude Console has a timeline with one lane per thread. Its Tools tab lists each configured tool with call counts, failures and median duration, so a tool that fails on every third call stands out. If you also want the API's own spans in your backend, add an OpenTelemetry destination in the Console. To nest those spans under your application's spans, call the SDK from inside one of your spans: the API reads the W3C traceparent header. Two delivery rules affect your queries. Delivery is at least once, so remove duplicates using the trace ID and span ID. Delivery is also best effort, so a lost span is never sent again.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Claude Code exports three signals, metrics, log events and traces, and each answers a different question (see [Metrics, log events and traces: three signals, three questions](lesson:4.6)). The problem at scale is getting hundreds of machines to send all three to the same collector in the same way. If developers set the variables in their own shell profiles, one typo or one forgotten export creates a silent gap. Instead, put the configuration in the env block of the administrator-managed settings.json, so it reaches every machine without any setup by each developer.

Managed transport settings take priority over the matching developer settings. Setting OTEL_EXPORTER_OTLP_ENDPOINT removes every per-signal endpoint a developer has set, so nobody can send one signal to a different collector. Setting OTEL_EXPORTER_OTLP_PROTOCOL does the same for protocols. Credentials go further. When managed settings supply OTEL_EXPORTER_OTLP_HEADERS or a client key or certificate, Claude Code also removes every endpoint a developer has set. Otherwise your token could be sent to a collector you did not choose.

Exporter selectors are the gap. OTEL_METRICS_EXPORTER, OTEL_LOGS_EXPORTER and OTEL_TRACES_EXPORTER follow normal per-key precedence, so any you leave out of managed settings can be changed on each machine. A selector set to console is the clearest case of telemetry that never arrives. The output appears in that developer's terminal and nowhere else, so the observability team gets no central view. Export intervals belong in managed settings too. Shorten them while debugging, then reset them for production, where the metric default is 60 seconds.

Agent SDK deployments have a matching rule. The recommended approach for production is to set the variables in the process environment: the shell, container or orchestrator. Every query() call then picks them up with no code change.

Fleet telemetry is useful only if you can split it into groups. A cost spike across 400 developers means little until you know which team, which service or which customer caused it. Two standard variables add that context to every signal: OTEL_SERVICE_NAME names the agent, and OTEL_RESOURCE_ATTRIBUTES carries comma-separated key=value pairs such as service.version=1.4.0,deployment.environment=production. The keys are your own choice, so a platform team can add whatever its finance reports group by, such as department or cost center.

In a multi-tenant service, the tags change with each request. The Agent SDK accepts the variables through per-call options, so you can tag each run with the user and tenant who triggered it. Values come from the request, so URL-encode them. In TypeScript, options.env replaces the inherited environment rather than merging with it. Spread process.env into it first, or the agent loses PATH and its API key.

The exporter configuration comment in the example below stands for the variables that turn telemetry on and say where it goes: CLAUDE_CODE_ENABLE_TELEMETRY, one exporter selector per signal (OTEL_METRICS_EXPORTER, OTEL_LOGS_EXPORTER, and for traces OTEL_TRACES_EXPORTER plus CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1), and the transport settings OTEL_EXPORTER_OTLP_PROTOCOL, OTEL_EXPORTER_OTLP_ENDPOINT and OTEL_EXPORTER_OTLP_HEADERS. In Python, the per-call env is merged on top of the inherited environment, so these can also come from the process environment and the per-call dict then needs only the tags.

Claude Code adds your resource attributes to every metric datapoint by default, which is what makes splitting metrics by team possible. It also adds identity attributes you may not need. session.id and the account attributes are on by default, so a fleet sending them gets new attribute values on its metrics with every session and every developer. If your dashboards only ever group by team, turn off the flags they don't use. That keeps the number of distinct time series, and the backend storage bill, from growing with headcount.

API-side spans are separated by workspace instead. A Console destination covers All workspaces, Selected workspaces, or All except the ones you list. The API sends each span to every enabled destination that covers the workspace where the request ran. With separate production and staging workspaces, a destination set to Selected can send only production traffic to the expensive backend.

Content is redacted by default, and each gate you open exposes more of every session on every machine (see [Telemetry content gates (redacted by default)](lesson:4.6)). The decision at scale is about exposure, not capability. One developer turning on prompt logging affects one person's sessions. The same gate in managed settings sends every engineer's prompts to a shared backend that many people can query.

Some data reaches your backend even with every gate closed. Under OAuth, user.email is a telemetry attribute. It goes only to your collector, never to Anthropic, but your backend now stores it, so filter it there if your policy requires. The widest gate, OTEL_LOG_RAW_API_BODIES, emits full request and response bodies, including the entire conversation history. Turning it on counts as consenting to everything the prompt, tool-detail and tool-content gates would reveal. It is rarely the right choice for a whole fleet.

A narrower choice usually meets the real need. A security team auditing which commands ran needs OTEL_LOG_TOOL_DETAILS, sent as log events to a SIEM, not prompt text. Even that exposes a lot: fields such as full_command are emitted untruncated, and commands can contain secrets.

Gates that interact are easy to get wrong. When OTEL_LOG_ASSISTANT_RESPONSES is unset, it takes the value of OTEL_LOG_USER_PROMPTS, so opening prompts also opens responses unless you set the response gate to 0. If you collect prompts and strip them later in the collector, delete both attributes that carry the text, prompt and prompt_text. A rule that names only one leaves the prompt in storage.
