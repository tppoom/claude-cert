📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A long agent session keeps growing until it either runs out of room or degrades well before that, as accuracy falls with length ([Context limits and context rot](lesson:5.2)). Compaction deals with both. It replaces the older turns with a summary Claude writes, so the task can keep going in a small active context. For conversations that regularly approach the limit, server-side compaction is the main strategy. It is in beta for Claude 4.6 and later models and Claude Mythos Preview.

Use on-demand compaction wherever it's available. It is the only server option where kept turns keep their thinking on models that preserve thinking. With threshold compaction, any turns you re-insert on Fable 5.1, Opus 5.5, Sonnet 5.5 or Haiku 5.5 must have their thinking removed. Either way, compaction is an extra sampling step, and it counts toward rate limits and billing.

Client-side SDK compaction is the alternative. Server-side compaction is generally preferred over it. It runs in the TypeScript and Ruby SDKs through tool_runner with a compaction_control setting. After each response the SDK adds input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens. Once that total passes context_token_threshold (100,000 by default), it injects a summary request and replaces the entire history with the summary. In the documented example, that takes the history from about 100k tokens to roughly 2–3k. A lower threshold means more frequent compactions and a smaller context. You can also set a cheaper model for writing summaries, or your own summary_prompt, as long as it wraps the summary in

tags.

That sum can go wrong with server-side tools. After a web search, cache_read_input_tokens can include reads from several internal calls the tool made. A real context of 63,000 tokens then shows up as 334,400, and compaction fires far too early. Check the true length with the token counting endpoint, or avoid SDK compaction in workflows that use server tools heavily. Compaction suits long multi-file tasks and research runs with measurable progress and artifacts saved outside the conversation. It's a poor fit when the task needs precise recall of early details or exact state across many variables.

2.Context editing: clearing tool results and thinking by rule

Extended Thinking คือโหมดที่อนุญาตให้ Claude คิดไตร่ตรองขั้นตอนและกลยุทธ์ก่อนที่จะเริ่มเขียนคำตอบจริง:

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Context editing works by removal, not summarization. You set rules, and once a threshold is crossed the API clears specific content before the prompt reaches Claude. There are two server-side strategies. You can configure each one on its own or combine them.

Tool result clearing (clear_tool_uses_20250919) is meant for agents that make heavy use of tools. A file Claude read twenty turns ago has usually done its job already. When the trigger fires, the API clears the oldest tool results first, in chronological order, and puts placeholder text in each one's place. Set clear_tool_inputs to true to also clear the tool call parameters.

Thinking block clearing (clear_thinking_20251015) controls thinking from earlier assistant turns through keep. Use {type: "thinking_turns", value: N} to keep the last N turns, or "all" to keep everything. If you don't set it, the default follows the model: Opus 4.5+, Sonnet 4.6+, Haiku 5.5+ and the Fable and Mythos models keep all turns, while older Opus, Sonnet and Haiku models keep only the last turn.

Your stored history stays complete. On Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5, server-side context management never invalidates thinking blocks. Editing earlier turns yourself on the client can invalidate the thinking in every later assistant turn. Clearing also works with the memory tool: when context nears the clearing threshold, Claude gets an automatic warning and can write what matters to memory files before the results disappear. To see the effect before turning a rule on, pass the same context_management to the token counting endpoint. It returns the count after clearing next to the original.

3.Context management versus the prompt cache

สาระสำคัญและหลักการทำงานของหัวข้อนี้: หัวข้อนี้เจาะลึก Context management versus the prompt cache ตามมาตรฐานและพิมพ์เขียวการสอบของ Anthropic โดยมุ่งเน้นการทำความเข้าใจสถาปัตยกรรมเชิงลึก ข้อดีข้อเสียทางเทคนิค และแนวทางการปฏิบัติจริงในโปรดักชัน
ActionCache effectHow to tune it
Tool result clearingInvalidates cached prefixes when content is cleared; cache write on each clearSet clear_at_least so every invalidation removes enough tokens to justify it
Thinking block clearingKept blocks preserve the cache; clearing invalidates it at the clearing pointSet keep: "all" to favour cache hits, a small thinking_turns value to favour window space
CompactionThe summary is new content that must be written to the cachePut a cache_control breakpoint at the end of the system prompt so it stays cached separately

Exam trapClearing thinking blocks is free context: it saves tokens with no other cost.Why is that wrong?Clearing thinking invalidates the prompt cache at the clearing point. Keeping the blocks preserves cache hits, so keep is a choice between cache performance and window space.

📝 ข้อสอบจำลองทางการ (Official Exam Question)

A team is building a customer support agent that sends a 6,000-token static system prompt containing product policies and tone guidelines, followed by a short per-request user message that always differs. Both latency and cost matter, and the team wants to maximize the prompt cache hit rate across thousands of daily requests. Where should they place the cache_control breakpoint?

A On the final block of the static system prompt, so the stable policy and tone text is cached and reused across every request
B On the user message block, so each incoming request establishes a brand-new cache entry that later turns can build upon
C On the tools array only, leaving the system prompt uncached because tool schemas change more often than policy text
D On every content block in the request, including the user message, so the entire prompt becomes eligible for caching
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. Cache breakpoints should mark the last block of content that stays identical across requests. Placing the breakpoint at the end of the static system prompt caches that stable prefix and lets it be reused on every request regardless of the changing user message.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. Placing the breakpoint on content that changes every request means the cached prefix hash never matches a prior write, so no cache hit occurs and the write cost is paid repeatedly.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Skipping the system prompt leaves the largest, most stable portion of the request uncached, forfeiting most of the available savings even if the tools array is cached.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Adding a breakpoint on the changing user message does not create a cache hit for that block and only adds unnecessary cache-write overhead without improving the hit rate.

Prompt caching reuses an identical prompt prefix ([Prompt caching](lesson:2.5)). Compaction and context editing both change the prompt partway through, and cache hits stop at the first change. Each clearing or compaction saves context and costs you a cache write. That trade only pays off when the edit is big enough to justify it.

Compaction shows why breakpoint placement matters. Without a breakpoint of its own, the system prompt is invalidated along with everything else when compaction rewrites the conversation, and has to be re-cached alongside the summary. With a cache_control breakpoint on the last block of the system prompt, the system prompt is still read from cache after compaction, and only the summary is written as a new entry.

The same rule applies to any request with a large fixed preamble. Put static content first (tool definitions, system instructions, examples) and mark the end of it with cache_control. Take a support agent with a 6,000-token policy prompt and a user message that changes every time. The breakpoint goes on the final block of the policy text. A breakpoint on the user message would create a new cache entry that no later request matches. Putting one on every block doesn't help either, because the changing part can never be a shared prefix.
