Every compliance question about Claude starts with the same fact: who processes the data in this deployment. On the Claude API (api.anthropic.com), Claude Platform on AWS and Claude in Microsoft Foundry, Anthropic processes prompts and outputs. That means Anthropic's two data handling arrangements, zero data retention (ZDR) and HIPAA readiness, are the controls you request and configure. On Amazon Bedrock and Google Cloud's Agent Platform, the cloud provider is the processor, and the equivalent controls are in that provider's own retention and compliance documentation.

Claude Platform on AWS is the surface people most often get wrong. It is billed through AWS Marketplace and opened from the AWS Console, but Anthropic operates it and it follows the same data retention policy as the first-party API. On Bedrock, AWS runs inference. If you put a deployment in the wrong column, you will read the wrong vendor's compliance terms for it.

Some commitments apply even without either arrangement. Retained data is never used for model training without your express permission. Conversation content is not retained by default. The exception is Covered Models, which require 30-day retention. Where a feature has to store something, its own page gives the retention period.

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

คาดการณ์ก่อนองค์กรภายใต้ ZDR ส่งคำขอ /v1/messages ที่ใช้การเรียกใช้โค้ด ซึ่งเป็นคุณลักษณะที่ทำเครื่องหมายว่า "ไม่" สำหรับ ZDR API ทำอะไร? ปฏิเสธด้วยข้อผิดพลาด 400 เนื่องจากคุณสมบัติไม่มีสิทธิ์ยอมรับ แต่จะตัดเครื่องมือการเรียกใช้โค้ดก่อนที่จะรันคำขอ ยอมรับ และข้อมูลการเรียกใช้โค้ดอยู่ภายใต้นโยบายการเก็บรักษาของฟีเจอร์นั้น ZDR จะไม่กรองคำขอ การใช้คุณสมบัติที่ทำเครื่องหมายว่า "ไม่" หมายความว่าคุณก้าวออกจาก ZDR สำหรับข้อมูลนั้น และการเก็บรักษาที่บันทึกไว้ของคุณสมบัติจะมีผล “ภายใต้ ZDR นั้น API จะไม่ปิดกั้นคุณสมบัติเหล่านี้ การใช้อย่างใดอย่างหนึ่งเป็นทางเลือกในการก้าวออกนอกการจัดเตรียม ZDR ของคุณสำหรับข้อมูลเฉพาะนั้น” ที่มา: platform.claude.com

Using a feature marked "No" means you step outside ZDR for that data, and the feature's documented retention applies. “ Under ZDR, the API does not block these features; using one is a choice to step outside your ZDR arrangement for that specific data ” Source: platform.claude.com
⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Exam Trap: Under ZDR, the API rejects requests that use non-eligible features, just as it does under HIPAA readiness. (ทำไมถึงผิด): Only HIPAA readiness rejects them. Under ZDR the request goes through, and that data falls under the feature's own retention policy.

HIPAA readiness is the arrangement for organizations that handle protected health information (PHI). It needs a signed Business Associate Agreement (BAA) and a HIPAA-enabled organization. The controls apply as soon as you accept, and the setting is permanent: an administrator cannot turn it off. Organizations that need a negotiated BAA go through the sales team instead.

Once HIPAA readiness is on, the API enforces the feature list. A request from a HIPAA-enabled organization that includes a non-eligible feature gets a 400 error naming that feature. You remove the feature and send the request again. The error text says "without Zero Data Retention", but that is only the API's wording. Turning on ZDR does not fix the error. One exception: client-side tools whose eligibility entry says they are not blocked are accepted, but they are still outside HIPAA readiness.

PHI is protected only in certain places. Message content, attached images and PDFs, and file names or metadata tied to messages are all protected. Workspace names, user details, billing data and support tickets are not expected to contain PHI. JSON schemas are the trap. With structured outputs or strict: true tools, the API compiles each schema into a grammar and caches it separately, without PHI protection. Keep patient details out of property names, enum values, const values and pattern regexes.
