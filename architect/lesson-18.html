💡 แนวคิดหลักสำคัญ (Key Concept)

Effort as the accuracy-latency dial — Effort sets how many output tokens one model spends on a request: its thinking, its tool calls and its text. Raising it buys accuracy with time and money, lowering it does the reverse, and none of it requires changing the model.

A latency complaint only gets fixed when you know which clock it is about. Latency is the time the model takes to process a prompt and generate its output, and it depends on the size of the model, how complex the prompt is, and the infrastructure behind it. Users feel two things: the wait before anything appears, which is time to first token (TTFT), and the wait until the answer is finished. An agent run has a third clock, the elapsed time across all of its turns. [Latency metrics: which clock you measure](lesson:4.1) defines these clocks. What matters here is that every lever moves only some of them.

The levers fall into the same two groups described in [Free wins versus real trade-offs](lesson:4.5). Streaming and trimming unneeded tokens make things faster without lowering quality. A smaller model, lower effort and tighter caps are real trade-offs, because they make things faster by doing less reasoning. Fast mode is a third kind. Accuracy stays the same and you pay more for the speed. If a proposal promises lower latency at the same price and the same accuracy, check which group its lever is actually in.

For a workload limited by latency, choosing the model is the most direct lever. Anthropic's model guide gives two starting strategies. The cost-first one begins with the fastest, cheapest tier, Claude Haiku, tests the use case thoroughly, and upgrades only where there is a specific capability gap. That path is recommended for applications with tight latency requirements, cost-sensitive deployments and high-volume, straightforward tasks. The capability-first path begins with Claude Opus and works down. It fits complex reasoning and work where accuracy matters more than cost.

Consider a support chat that has to reply within a second or two, classifies huge numbers of simple intents and has a tight budget. Every one of those constraints points to the Haiku tier. Intent classification does not need frontier reasoning, so the larger models would add latency and cost without a gain in accuracy that anyone would notice. The same tier is the guide's suggestion for real-time applications and sub-agent tasks. Effort applies to every output token, not only to thinking. It sets the size of the response, the tool calls and their arguments, and the thinking when thinking is active. So it works whether or not thinking is on, and lower effort also means fewer, shorter tool calls. That matters for agents. In an agent, much of the elapsed time goes on tool round trips, so lowering effort shortens the run as well as each reply. You set effort with output_config.effort, not inside the thinking object.

For a swarm of parallel subagents doing simple lookups, low is the setting designed for the job. Each call finishes sooner and costs less, and a lookup has little to gain from more depth. The higher settings each fail for their own reason. max makes no promise of a better lookup. Effort is soft guidance, not a guarantee: at every level Claude still decides per request whether to think, and on most workloads max adds a lot of cost for relatively small quality gains. xhigh is meant for long agentic tasks with large token budgets, the opposite of a quick lookup. And leaving the default high does nothing for a goal of minimising latency.

Three details catch out people who configure effort. First, effort does not set how long the visible answer is. On Claude Opus 5, lowering effort does not reliably shorten the reply, so if you want shorter answers, ask for them in the prompt. Second, the resolved effort value is rendered into the prompt. Changing the top-level effort between requests therefore invalidates cache breakpoints, and the cache misses add latency back. Keep one level for each conversation, and use per-message effort (beta) where it is supported, because it keeps the cache. Third, if a lower setting gives shallow reasoning on a hard problem, the fix the documentation gives is to raise effort, not to prompt around the low setting.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Streaming improves perceived latency, not real latency. The response is sent while it is still being generated, so users read text as it arrives and your application can update the UI or work in parallel. Total generation time does not change. That makes streaming the right answer to "it feels frozen" and the wrong answer to "the batch job takes too long".

Fast mode is for when generating the output is the bottleneck. It runs the same model weights at up to 2.5x higher output tokens per second, with no change to intelligence or capabilities. It costs a multiplier on standard rates. Fast mode is supported on Claude Opus 5.5, Claude Opus 5 and Claude Opus 4.8. You opt in with speed="fast" and a beta header. The gain is most visible with streaming. It helps long generations such as a large refactor and does little for a short answer that sits waiting for its first token.

Hard problems that need thinking have another lever: the thinking display field. With display: "omitted" the thinking still runs in full, but the thinking blocks come back with an empty thinking field. The signature field keeps the encrypted full thinking so a multi-turn conversation can continue. Its main benefit is a faster time to the first text token when streaming, because the server does not stream the reasoning text. Picture a valuation tool that solves multi-step problems with extended thinking, where users find the wait unacceptable. Omitting the display shortens the visible wait and keeps every bit of the reasoning. Turning thinking off, or capping budget_tokens at a small fixed number for every request, would make the answers fast by making them worse on exactly the problems that need the reasoning. A larger budget does not lower latency at all.

“Run an effort sweep on your own evals rather than carrying settings over from an earlier model”

คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A configuration choice is defensible when it comes from your own eval run across effort levels and models. Settings carried over from an earlier model or picked by feel are not. Levels are recalibrated between model generations, so the guidance is to run a fresh effort sweep instead of reusing old settings. Compare the results on cost per completed task, not per token. A cheap configuration that fails half the time is not cheap.

Re-running failures belongs in the sweep as a configuration of its own. When outputs can be checked, by tests or a verifier, you can run everything at low effort and re-run only the failures at high. In Anthropic's tests that cost about 40% less than running everything at high, at the same pass rate. It also helps latency: most tasks finish on the quick path, and only the hard ones pay for depth. These figures are internal and directional, so measure on your own workload.

Agent runs need a bound on their elapsed time as well as on each turn. Output caps and session budgets, covered in [max_tokens, task budgets and re-running failures](lesson:4.5), put a hard ceiling on how long a run can go. Telling the model that time matters and showing it the elapsed time cut run time by 7% to 47% in Anthropic's tests, for a few points of score. Multi-model setups add latency that has to go into the same comparison: an advisor adds about one or two extra frontier-model calls per task, each on the critical path. Inside a RAG pipeline, how many chunks you retrieve and whether you rerank them is the same trade between accuracy and time, explained in [Reranking and how many chunks to pass](lesson:3.5). Those settings belong in the sweep too.
