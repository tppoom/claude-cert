คำตอบที่ถูกต้อง: ตัวเลือก A

Use subagents when the agent needs listed specialists with their own system prompts and tools, or needs to follow up with them. A subagent's thread persists, so follow-ups work. A dynamic workflow's threads can't receive follow-ups. An advisor is a model that the primary thread consults while it does the work itself, so it doesn't delegate to listed agents.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Managed Agents: the multiagent block" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A coordinator works the same way on every platform. It delegates to subagents, and each subagent runs in an isolated context and returns only a condensed result (see the companion page on designing multi-agent systems). What changes from platform to platform is where you declare the coordinator, its specialists and the alternatives to subagents. In Claude Managed Agents, you declare them in the multiagent block of the agent definition. With type multiagent_20261001, subagents and dynamic workflows are both on by default, and you can also give the session an advisor.

The table below talks about threads, so one definition first. Each agent in a session runs in its own session thread: a context-isolated event stream with its own conversation history. The agent that the session runs reports in the primary thread, the session-level event stream, and every delegated agent gets an additional thread spawned at runtime. Whether a thread can be messaged again after its agent reports is what separates subagents from workflow runs.

You decide which of these the agent may use, and the agent decides when to use them. Steer that decision in the system prompt, for example by telling the agent when to start a workflow run. The coordinator below is a lead that lists two specialists by ID. Its system prompt is a short routing brief: send review work to the reviewer and test writing to the test writer. The reviewer and test writer are separate agents running claude-haiku-5-5, each with its own one-line system prompt.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Predefined and inline agents, and the limits on them" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Each subagent is either predefined or inline. A predefined agent is one you have already created and listed. It runs with its own model, system prompt, tools, MCP servers and skills. An inline agent isn't saved anywhere. The coordinator, or a workflow, defines it at the moment it hands out the work, and it uses the coordinator's model, tools, MCP servers and skills. Inline agents are on by default, so unless you turn them off, the coordinator can create helpers you never reviewed.

Inline agents have no definition of their own, so you can't use one to narrow their access. They take on the MCP servers and tools of the agent the session runs. To give a specialist tools the coordinator doesn't have, make it a predefined agent. In the GitHub example, only a predefined researcher declares the GitHub MCP server, so the coordinator never has access to it. To allow only the agents you list, set inline_agents to {"type": "disabled"} under subagents and under workflows. Each setting with inline agents off needs at least one agent in its list, or the request fails with a 400 error.

The two predefined_agents lists are separate. Listing an agent under subagents does not make it available to workflows, and the reverse is also true. Four rules apply to both lists:

- Pinning: when you create or update the coordinator, each referenced agent is pinned to its version at that moment. Later edits to that agent don't reach the coordinator until you update the coordinator's list. - One level: listing an agent that has its own multiagent block fails with a 400 validation error. - Up to 20 agents per list: the coordinator can still run several copies of each one, within the session's thread limit. - Same inference geography: every listed agent must pin the same inference_geo as the coordinator, or none of them may pin one.

Claude Code offers several ways to run work in parallel. Three of them are coordination patterns, and each one fits a different kind of work.

The main difference is how the workers communicate. Subagents talk only to the session that started them, and each returns a single summary, so they suit isolated side tasks such as investigating one bug across dozens of files. Teammates in an agent team are peer sessions. They share a task list and message one another, which helps when pieces of a project depend on each other's progress. That shared state also brings back the coordination cost that subagents avoid. A dynamic workflow takes coordination out of the conversation entirely: a script runs the subagents and checks their results against each other, for jobs too big to manage one turn at a time. Agent teams are a Claude Code feature. They are experimental and must be turned on before use.
