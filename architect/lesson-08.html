Each Claude model makes a different trade between intelligence, speed and cost. Every model can do the same kinds of work, so you are not picking a specialist. You are deciding how hard a problem the model has to handle reliably, and how much you will pay in money and latency for that. All current models accept text and images, return text, and support vision, multilingual work and tool use. The real differences are in latency, price and how hard a problem each one can carry.

Context window size does not decide the choice. All four models have a 1M-token window and a 128K output limit. Long prompts change the price, though. Haiku 5.5 bills $0.10 per input MTok for prompts up to 100,000 tokens, and $0.50 input and $2.50 output per MTok above that. A Haiku workload that stuffs whole documents into every request therefore costs five times as much per token as one that keeps prompts short. Fable 5.1 and Opus 5.5 also leave you less control than the smaller models: their adaptive thinking is always on, so you control how much they reason through effort, not by switching thinking off.

Speed is not only a matter of picking a smaller model. Claude Opus 5.5, Opus 5 and Opus 4.8 support fast mode, which is a research preview. It gives up to 2.5x higher output tokens per second at premium pricing: $8 input and $40 output per MTok on Opus 5.5. Fast mode runs the same model with the same weights, so its quality doesn't change. The gain is in output speed, not time to first token, so it is most noticeable when you stream.

A system that chooses a model at runtime should read model limits from the Models API rather than from a hardcoded table. For every available model, the response includes max_input_tokens, max_tokens and a capabilities object. The capabilities object reports, for example, whether the model accepts thinking: {type: "disabled"} and whether it accepts the web search and code execution server tools. A line field names the model family, such as opus. Read that field instead of parsing it out of the model ID.

You can start testing from either end of the lineup. Which end depends on how hard the task is and how much cost matters. If you have no strong reason either way, the default is Claude Opus 5.5. Use Claude Fable 5.1 for demanding reasoning and long-horizon agentic work, or when Opus 5.5 still falls short in your evals at higher effort.

Small first, then step up. Build with a faster, cheaper model such as Claude Haiku 5.5. Test your use case thoroughly and check whether performance meets your requirements. Upgrade only where you find a specific capability gap. You can iterate quickly and development costs less, and for many common applications the small model turns out to be good enough. This path fits:

- Initial prototyping and development - Applications with tight latency requirements - Cost-sensitive implementations - High-volume, straightforward tasks

Starting small does not mean the small model matches the large one on every task. It is a bet that your task may not need the extra capability, and your tests settle that bet. Nothing about the order is enforced either: every model is available from the first request.

Capability first, then step down. Build with Claude Opus 5.5, optimize your prompts for it, and evaluate the results. Then make it more efficient over time by lowering effort or moving to a smaller model. If Opus 5.5 still falls short at xhigh or max effort on demanding reasoning or long-horizon agentic work, move up to Fable 5.1. This path fits complex reasoning, scientific and mathematical work, tasks that need nuanced understanding, applications where accuracy matters more than cost, and advanced coding and high-autonomy agentic work. Starting high has another benefit: if a small model fails, it can be hard to tell whether the model or your setup caused the failure.

Before you switch models in either direction, adjust effort on the model you already use. [Effort: the accuracy-latency dial within one model](lesson:3.3) trades intelligence for latency and cost without changing models. If costs are too high and quality is fine, lower effort on the current model first. If quality is too low, first restore any effort you lowered. Only then try the next tier up at its default effort. Default effort differs by model, so carry no settings over. Opus 5.5 defaults to medium, while Opus 5 defaulted to high, so a request that omits effort runs one level lower than it did before.

Whichever path you take, the deciding evidence comes from the same test. Build an evaluation set specific to your use case with your real prompts and data. Run every candidate through it and compare accuracy, response quality and handling of edge cases. The method for that comparison is in [Baselines, offline comparisons and live A/B tests](lesson:4.3). Public benchmarks help less at the top of the lineup, because Opus and Fable solve nearly all of their questions.

3. การเปรียบเทียบโมเดลตามต้นทุนต่องานที่ได้รับการแก้ไข

การแยกงานให้ Subagents ทำจะช่วยยกระดับผลลัพธ์ให้ดีขึ้นใน 3 สถานการณ์หลัก เท่านั้น หากอยู่นอกเหนือจากนี้ การประสานงานมักจะสร้างต้นทุนมากกว่าประโยชน์:

1. ป้องกัน Context Pollution (ผลลัพธ์เครื่องมือมีขนาดใหญ่มาก): เมื่อการทำงานย่อยสร้างโทเค็นที่ไม่เกี่ยวข้องมากกว่า 1,000 โทเค็น (เช่น อ่านเอกสารหนาๆ หรือค้นหาเว็บ) การให้ Subagent ทำจะช่วยกักกันข้อมูลส่วนเกินไม่ให้รบกวนการตัดสินใจของ Orchestrator
2. เมื่องานสามารถทำพร้อมกันได้ (Parallelization): หากงานย่อยหลายชิ้นเป็นอิสระต่อกัน (เช่น ตรวจสอบความปลอดภัย 3 ด้านคนละมุม) การส่งให้ Subagents ทำงานขนานกันจะช่วยลด Latency รวมของระบบได้อย่างมหาศาล
3. เมื่องานต้องการเครื่องมือเฉพาะทางสูง (Tool Specialization): การใส่เครื่องมือให้เอเจนต์ตัวเดียวมากเกินไป (Capability Bloat) จะทำให้ความแม่นยำในการเลือกเครื่องมือลดลง การแยก Subagent ตามหน้าที่ช่วยให้แต่ละตัวมีเครื่องมือเฉพาะทางเพียง 3-5 ชิ้นเท่านั้น

In one 20-problem run, two problems accounted for 43% of it.

Some savings involve no intelligence trade-off at all, and these come before any model decision. The Message Batches API processes large volumes of requests asynchronously at a 50% discount. In exchange, you give up latency: most batches finish within an hour, but you should plan for up to 24 hours. Every active model supports batching, so the discount does not depend on tier. Prompt caching is the other free lever. In Anthropic's runs it was usually the largest single saving. For an overnight job that classifies millions of records with no user waiting, use batch at a model your evals show is good enough. Don't use synchronous calls at max effort, and don't turn off caching to save on storage.

4. โมเดลการจัดระดับภายในระบบเดียว

การใช้แบบจำลองเดียวสำหรับทุกคำขอหมายถึงการจ่ายราคาที่เหนือระดับสำหรับงานง่าย ๆ หรือการได้โมเดลขนาดเล็กที่มีคุณภาพจากการทำงานหนัก การออกแบบหลายรุ่นหลีกเลี่ยงทั้งสองอย่างโดยการส่งแบบจำลองราคาแพงเฉพาะการตัดสินใจที่จำเป็นเท่านั้น โทเค็นส่วนใหญ่จะถูกเรียกเก็บเงินในอัตราที่ต่ำกว่า และความสามารถระดับแนวหน้าจะไปถึงกรณียากที่รุ่นที่ราคาถูกกว่าล้มเหลว

มีรูปแบบทั่วไปสองแบบ และเหมาะกับปัญหาที่แตกต่างกัน:

  • ▸
    ตัวดําเนินการพร้อมที่ปรึกษา โมเดลต้นทุนต่ําจะทํางานและปรึกษาโมเดลแนวหน้าเพื่อตรวจสอบแผนหรือตรวจสอบเอาต์พุต สิ่งนี้มีประโยชน์เมื่อโมเดลราคาถูกหยุดชะงักเมื่อต้องตัดสินใจอย่างยากลําบากเท่านั้น ที่ปรึกษาจะช่วยเฉพาะเมื่อมีการปรึกษา ดังนั้นก่อนอื่นให้ราคาโมเดลราคาถูกที่ต้องใช้ความพยายามน้อยด้วยตัวมันเองและวัดความถี่ที่มันปรึกษา ในหนึ่งการวัด ซอนเน็ต 5 ที่มีที่ปรึกษา Fable 5 อยู่ในระดับ 10% ของคะแนน SWE-bench Pro ของ Fable 5 ที่ 63% ของราคาการเรียกใช้ Fable 5 ด้วยตัวมันเอง ตัวเลือกที่ปรึกษาถูกจํากัด: เครื่องมือที่ปรึกษาปฏิเสธโมเดลบางตัวเป็นที่ปรึกษา รวมถึง Claude Haiku 5.5
  • ▸
    ผู้ประสานงานพร้อมผู้ปฏิบัติงาน โมเดลที่มีความสามารถวางแผนงานและมอบส่วนสําคัญให้กับผู้ปฏิบัติงานที่มีต้นทุนต่ํา สิ่งนี้เหมาะกับงานที่ใหญ่เกินไปสําหรับหน้าต่างบริบทเดียว ความสมดุลระหว่างความเร็วและต้นทุนของ Sonnet ทําให้มันเป็นงานทั่วไป และ Haiku มุ่งเน้นไปที่งานย่อย

รูปแบบที่สามคือ 📖 การกําหนดเส้นทาง (1.5) ตัวจําแนกจะจัดเรียงคําขอที่เข้ามาก่อนที่งานจะเริ่ม ส่งคําขอที่ง่ายไปยังโมเดลขนาดเล็ก และส่งคําขอที่ยากไปยังโมเดลขนาดใหญ่ การกําหนดเส้นทางเป็นรูปแบบต้นทุนเฉพาะเมื่อตัวจําแนกเชื่อถือได้เท่านั้น คําขอที่ยากที่ส่งไปยังโมเดลขนาดเล็กจะกลายเป็นงานที่ล้มเหลว และดังที่แสดงในส่วนก่อนหน้า งานที่ล้มเหลวจะเป็นตัวขับเคลื่อนค่าใช้จ่าย เช่นเดียวกับตัวเลือกโมเดลทั้งหมด การออกแบบแบบแบ่งระดับพิสูจน์คุณค่าผ่านต้นทุนต่องานที่แก้ได้บนชุดการประเมินของคุณเอง โทเค็นขอบเขตที่น้อยลงเพียงอย่างเดียวไม่ได้แสดงให้เห็นว่ามีราคาถูกกว่า

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Using one model for every request means paying frontier prices on easy work or getting small-model quality on hard work. Multi-model designs avoid both by sending the expensive model only the decisions that need it. Most tokens are then billed at the lower rate, and frontier capability goes to the hard cases where cheaper models fail.

There are two common patterns, and they suit different problems:

- Executor with an advisor. A lower-cost model does the work and consults a frontier model to check its plan or review its output. This helps when the cheaper model stalls only on hard decisions. The advisor only helps when it is consulted, so first price the cheaper model at low effort on its own and measure how often it consults. In one measurement, Sonnet 5 with a Fable 5 advisor came within 10% of Fable 5's SWE-bench Pro score at 63% of the price of running Fable 5 alone. Advisor choice is restricted: the advisor tool rejects some models as advisors, including Claude Haiku 5.5. - Orchestrator with workers. A capable model plans the work and hands the bulk of it to lower-cost workers. This fits work that is too large for one context window. Sonnet's balance of speed and cost makes it a common worker, and Haiku is aimed at sub-agent tasks.

A third pattern is [Routing](lesson:1.5). A classifier sorts incoming requests before any work starts, sends easy ones to a small model and hard ones to a large one. Routing is a cost pattern only if the classifier is reliable. A hard request sent to a small model becomes a failed task, and as the previous section showed, failed tasks drive the bill. Like every model choice, a tiered design proves its value through cost per solved task on your own eval set. Fewer frontier tokens alone do not show that it is cheaper.
