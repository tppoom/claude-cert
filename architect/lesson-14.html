💡 แนวคิดหลักสำคัญ (Key Concept)

Reusable stable prefix — Reuse works when the start of a request is byte-for-byte the same as an earlier one. Caching stores that prefix so later requests skip reprocessing it. Modular layout keeps the prefix identical by putting changing content last, and Skills keep reusable instructions out of the prefix until a task needs them.

1. คําสั่งการแคชที่ใช้ซ้ําและค่าใช้จ่าย

การแยกงานให้ Subagents ทำจะช่วยยกระดับผลลัพธ์ให้ดีขึ้นใน 3 สถานการณ์หลัก เท่านั้น หากอยู่นอกเหนือจากนี้ การประสานงานมักจะสร้างต้นทุนมากกว่าประโยชน์:

1. ป้องกัน Context Pollution (ผลลัพธ์เครื่องมือมีขนาดใหญ่มาก): เมื่อการทำงานย่อยสร้างโทเค็นที่ไม่เกี่ยวข้องมากกว่า 1,000 โทเค็น (เช่น อ่านเอกสารหนาๆ หรือค้นหาเว็บ) การให้ Subagent ทำจะช่วยกักกันข้อมูลส่วนเกินไม่ให้รบกวนการตัดสินใจของ Orchestrator
2. เมื่องานสามารถทำพร้อมกันได้ (Parallelization): หากงานย่อยหลายชิ้นเป็นอิสระต่อกัน (เช่น ตรวจสอบความปลอดภัย 3 ด้านคนละมุม) การส่งให้ Subagents ทำงานขนานกันจะช่วยลด Latency รวมของระบบได้อย่างมหาศาล
3. เมื่องานต้องการเครื่องมือเฉพาะทางสูง (Tool Specialization): การใส่เครื่องมือให้เอเจนต์ตัวเดียวมากเกินไป (Capability Bloat) จะทำให้ความแม่นยำในการเลือกเครื่องมือลดลง การแยก Subagent ตามหน้าที่ช่วยให้แต่ละตัวมีเครื่องมือเฉพาะทางเพียง 3-5 ชิ้นเท่านั้น
💰 ต้นทุนโทเค็นที่ต้องแลก (Token Cost): สำหรับงานประเภทเดียวกัน ระบบ Multi-Agent มักใช้โทเค็นมากกว่าระบบเอเจนต์เดี่ยวประมาณ 3 ถึง 10 เท่า เนื่องจากต้องส่งคำสั่งระบบซ้ำให้กับ Subagent แต่ละตัว และต้องเสียโทเค็นในรอบการรวบรวมข้อมูล

Many production prompts open with the same few thousand tokens every time: tool definitions, a long system prompt, a block of examples, a reference document. Prompt caching lets later requests skip reprocessing that shared opening. When a request arrives with caching enabled, the system checks whether the prompt prefix up to a cache breakpoint is already cached from a recent query. On a hit it uses the cached version, which cuts processing time and cost. On a miss it processes the full prompt and caches the prefix once the response begins. The workloads that gain most are prompts with many examples, large background context, repetitive tasks with consistent instructions, and long multi-turn conversations.

รายการแคชมีอายุการใช้งาน 5 นาทีตามค่าเริ่มต้น และทุกครั้งที่มีการใช้งานจะรีเฟรชโดยไม่มีค่าใช้จ่ายเพิ่มเติม TTL 1 ชั่วโมงมีให้บริการในราคา 2 เท่าของราคาอินพุตพื้นฐาน อายุการใช้งานนับจากจุดเริ่มต้นของคําขอที่เขียนหรืออ่านรายการ ไม่ใช่นับจากจุดสิ้นสุดของการตอบสนอง ดังนั้นเวลาการสร้างจะใช้ระยะเวลาสูงสุด: หากการตอบสนองใช้เวลา 4 นาทีในการสตรีม การติดตามที่ใช้อีกครั้งกับคํานําหน้าเดียวกันจะต้องเริ่มภายใน 1 นาทีหลังจากการตอบสนองเสร็จสิ้น ด้วย TTL 5 นาที ลูปเอเจนต์ที่ช้าหรือผู้ใช้ที่หยุดชั่วคราวจะพบว่าแคชหายไป

Caching changes the price of input tokens. Writing to the cache costs more than plain input, and reading from it costs a small fraction of plain input. Cache hits are 0.05x the base input price on Claude Opus 5.5 and Claude Sonnet 5.5, 0.025x on Claude Fable 5.1 and Claude Mythos 5.1, and 0.1x on every other model. Breakpoints themselves cost nothing. You pay only for cache writes, cache reads and uncached input, so adding breakpoints does not raise the bill.

On a hit it uses the cached version, which cuts processing time and cost. On a miss it processes the full prompt and caches the prefix once the response begins. The workloads that gain most are prompts with many examples, large background context, repetitive tasks with consistent instructions, and long multi-turn conversations.

A breakpoint marks the end of the prefix to look up, and most requests carry only one. When the exact prefix at the breakpoint has no entry, the system walks backward block by block. It looks for the longest prefix that an earlier request already wrote to the cache. That walk has a fixed reach of 20 positions.

Here is how that plays out over three turns. Turn 1 has 10 blocks with the breakpoint on block 10, and an entry is written there. Turn 2 has 15 blocks. Block 15 has no entry, so the walk goes back to block 10 and hits. Blocks 11–15 are processed fresh and a new entry is written at 15. Turn 3 jumps to 35 blocks, perhaps after a burst of tool calls. The walk from block 35 stops at block 16 and misses the block-15 entry by one position. Nothing has expired and nothing has been deleted. The entry is still there, but no lookup reaches it.

The fix is a second, explicit breakpoint further back, at or near the last place a write happened. Each breakpoint starts its own 20-position lookback, so a breakpoint at block 15 finds the turn-2 entry. Agent loops that add many blocks per turn, such as tool calls and tool results, are where automatic caching alone runs into this window. Watch the cache-read counts as conversations get longer.

4. Modular prompt layout: stable modules first, variables last

Caching only rewards content that stays identical from one request to the next, so the order of a prompt decides how much of it can be cached. Build the prompt from modules ranked by how rarely they change. Tool definitions come first, then system instructions, then reference context and examples, then the conversation. Per-request values go at the very end. The same rule applies to [reusable prompt templates with variables](lesson:2.2): put the fixed template text ahead of every slot, so filling a variable only changes the tail.

5. Agent Skills: packaging repeated instructions as SKILL.md

Caching makes a repeated prefix cheaper. Agent Skills tackle a different kind of repetition: the same procedure pasted into prompt after prompt. A Skill is a directory holding instructions, metadata and optional resources such as scripts and templates. Claude uses it automatically when a request is relevant to it. A prompt holds conversation-level instructions for a single task. A Skill is created once and loads on demand in every conversation where it applies. Anthropic provides pre-built Skills for PowerPoint, Excel, Word and PDF, and custom Skills package an organisation's own procedures.

Every Skill needs a SKILL.md file that starts with YAML frontmatter containing two required fields. The rules are strict, and a violation gets the Skill rejected:

- name: at most 64 characters; only lowercase letters, numbers and hyphens; no XML tags; must not contain the reserved words "anthropic" or "claude". - description: non-empty; at most 1024 characters; no XML tags. - No other field is required. There is no version suffix and no minimum description length.

The description is how Claude decides to trigger the Skill. Claude matches each request against it, sometimes choosing among 100 or more available Skills. A good description therefore states what the Skill does and when to use it, including the words users actually type. "Helps with documents" names no task and no trigger, so it rarely matches. For names, a consistent gerund form such as processing-pdfs or analyzing-spreadsheets makes a library easier to scan. Avoid vague names such as helper or utils.

Caching makes a repeated prefix cheaper. Agent Skills tackle a different kind of repetition: the same procedure pasted into prompt after prompt. A Skill is a directory holding instructions, metadata and optional resources such as scripts and templates. Claude uses it automatically when a request is relevant to it. A prompt holds conversation-level instructions for a single task. A Skill is created once and loads on demand in every conversation where it applies. Anthropic provides pre-built Skills for PowerPoint, Excel, Word and PDF, and custom Skills package an organisation's own procedures.

Every Skill needs a SKILL.md file that starts with YAML frontmatter containing two required fields. The rules are strict, and a violation gets the Skill rejected:

- name: at most 64 characters; only lowercase letters, numbers and hyphens; no XML tags; must not contain the reserved words "anthropic" or "claude". - description: non-empty; at most 1024 characters; no XML tags. - No other field is required. There is no version suffix and no minimum description length.

The description is how Claude decides to trigger the Skill. Claude matches each request against it, sometimes choosing among 100 or more available Skills. A good description therefore states what the Skill does and when to use it, including the words users actually type. "Helps with documents" names no task and no trigger, so it rarely matches. These levels shape how a Skill should grow. Treat SKILL.md as a table of contents, and keep its body under 500 lines. As it nears that size, move detail into separate files that SKILL.md links to, such as FORMS.md, REFERENCE.md or examples.md. For Skills that span several domains, split the reference material by domain, for example reference/finance.md and reference/sales.md. A sales question then loads only the sales schema. Keep every reference one level deep from SKILL.md. When files point to further files, Claude may preview them with partial reads such as head -100 and miss information. Give any reference file over 100 lines a table of contents at the top, so a partial read still shows everything it contains.
