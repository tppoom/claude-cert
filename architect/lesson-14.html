Many production prompts open with the same few thousand tokens every time: tool definitions, a long system prompt, a block of examples, a reference document. Prompt caching lets later requests skip reprocessing that shared opening. When a request arrives with caching enabled, the system checks whether the prompt prefix up to a cache breakpoint is already cached from a recent query. On a hit it uses the cached version, which cuts processing time and cost. On a miss it processes the full prompt and caches the prefix once the response begins. The workloads that gain most are prompts with many examples, large background context, repetitive tasks with consistent instructions, and long multi-turn conversations.

A cache entry lives for 5 minutes by default, and every use refreshes it at no extra cost. A 1-hour TTL is available at 2x the base input price. The lifetime counts from the start of the request that writes or reads the entry, not from the end of its response. Generation time therefore uses up the window: if a response takes 4 minutes to stream, a follow-up that reuses the same prefix has to start within about 1 minute of that response finishing. With a 5-minute TTL, a slow agent loop or a user who pauses for a while finds the cache gone.

Caching changes the price of input tokens. Writing to the cache costs more than plain input, and reading from it costs a small fraction of plain input. Cache hits are 0.05x the base input price on Claude Opus 5.5 and Claude Sonnet 5.5, 0.025x on Claude Fable 5.1 and Claude Mythos 5.1, and 0.1x on every other model. Breakpoints themselves cost nothing. You pay only for cache writes, cache reads and uncached input, so adding breakpoints does not raise the bill.

Here is the arithmetic for a 20,000-token system prompt on Sonnet 5.5. Sent uncached, it costs $0.04 per request. The first cached request writes it for $0.05, and each hit after that costs $0.002. The write premium pays for itself on the first reuse. Short prompts are a different story. Below a model's minimum cacheable length, a prefix is not cached even if it carries cache_control. That minimum is 512 tokens on Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1, and as high as 4,096 tokens on some older models such as Haiku 4.5.

Caching can be turned on in two ways. Automatic caching uses a single cache_control field at the top level of the request. The system places the breakpoint on the last cacheable block and moves it forward as the conversation grows, so you never edit markers by hand. On each turn, everything up to the previous request's end is read from cache, and only the new assistant reply and user message are written. Explicit breakpoints put cache_control on individual content blocks. That gives fine-grained control, for example caching sections that change at different rates.

The two methods combine. A request can have at most four breakpoints, and the automatic one takes one of those slots. If four explicit block-level breakpoints are already present, the request fails with a 400 error because no slot is left for automatic caching. It also returns 400 if the last block already carries an explicit marker with a different TTL. If that marker has the same TTL, automatic caching does nothing extra. A common combination puts an explicit breakpoint on the system prompt and lets automatic caching follow the conversation.

Automatic caching runs on the same infrastructure as explicit breakpoints, so the same pricing, minimum token thresholds, ordering requirements and 20-block lookback window apply. For a 1-hour TTL, write { "type": "ephemeral", "ttl": "1h" } in the same field. Prompt caching, both automatic and explicit, is supported on all active Claude models.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A breakpoint marks the end of the prefix to look up, and most requests carry only one. When the exact prefix at the breakpoint has no entry, the system walks backward block by block. It looks for the longest prefix that an earlier request already wrote to the cache. That walk has a fixed reach of 20 positions.

Here is how that plays out over three turns. Turn 1 has 10 blocks with the breakpoint on block 10, and an entry is written there. Turn 2 has 15 blocks. Block 15 has no entry, so the walk goes back to block 10 and hits. Blocks 11–15 are processed fresh and a new entry is written at 15. Turn 3 jumps to 35 blocks, perhaps after a burst of tool calls. The walk from block 35 stops at block 16 and misses the block-15 entry by one position. Nothing has expired and nothing has been deleted. The entry is still there, but no lookup reaches it.

The fix is a second, explicit breakpoint further back, at or near the last place a write happened. Each breakpoint starts its own 20-position lookback, so a breakpoint at block 15 finds the turn-2 entry. Agent loops that add many blocks per turn, such as tool calls and tool results, are where automatic caching alone runs into this window. Watch the cache-read counts as conversations get longer.

Caching only rewards content that stays identical from one request to the next, so the order of a prompt decides how much of it can be cached. Build the prompt from modules ranked by how rarely they change. Tool definitions come first, then system instructions, then reference context and examples, then the conversation. Per-request values go at the very end. The same rule applies to [reusable prompt templates with variables](lesson:2.2): put the fixed template text ahead of every slot, so filling a variable only changes the tail.

The API builds cache prefixes in a fixed hierarchy: tools → system → messages. A change at one level invalidates that level and everything after it, never what comes before. That is why order matters. An edited tool definition throws away the whole cache, while a change that only touches the messages level keeps tools and system cached.

Forcing a particular tool with tool_choice is a request setting, but it still takes part in the hierarchy. It invalidates only the messages cache. Tools and the system prompt are still read from cache, and only the messages are reprocessed. Dynamic tool discovery fits this layout too. Some tool definitions can be marked as deferred: they are held back from the request, and so stay out of the system-prompt prefix, until the model runs a tool search and finds one it needs. The definition is then appended to the conversation history, after the cached prefix, so the prefix is left alone and the cache keeps hitting.

The most common layout mistake is a variable sitting at the breakpoint. Picture blocks 1–5 holding a large static system context, and block 6 holding a timestamp plus the user message, with cache_control on block 6. The timestamp changes on every request, so the prefix hash at block 6 changes too. The lookback then walks through blocks 5 to 1 and finds nothing, because no entry was ever written there. The lookback only finds entries that earlier requests wrote. It does not cache stable content that sits behind a breakpoint. Put the breakpoint on block 5, the end of the static modules, and move the timestamp after it.

Caching makes a repeated prefix cheaper. Agent Skills tackle a different kind of repetition: the same procedure pasted into prompt after prompt. A Skill is a directory holding instructions, metadata and optional resources such as scripts and templates. Claude uses it automatically when a request is relevant to it. When Claude runs validate_form.py, the code never enters context, only its output, such as "Validation passed". These levels shape how a Skill should grow. Treat SKILL.md as a table of contents, and keep its body under 500 lines. As it nears that size, move detail into separate files that SKILL.md links to, such as FORMS.md, REFERENCE.md or examples.md. For Skills that span several domains, split the reference material by domain, for example reference/finance.md and reference/sales.md. A sales question then loads only the sales schema. Keep every reference one level deep from SKILL.md. When files point to further files, Claude may preview them with partial reads such as head -100 and miss information. Give any reference file over 100 lines a table of contents at the top, so a partial read still shows everything it contains.

#1 1. คําสั่งการแคชที่ใช้ซ้ําและค่าใช้จ่าย

อ่านเนื้อหา ↗
  • ▸
    นี่คือการคำนวณทางคณิตศาสตร์สำหรับระบบพรอมต์ขนาด 20,000 โทเค็นบน Sonnet 5.5 หากส่งโดยไม่เก็บแคช จะเสียค่าใช้จ่าย $0.04 ต่อคำขอ คำขอแรกที่เก็บแคชจะถูกบันทึกในราคา $0.05 และแต่ละครั้งหลังจากนั้นจะเสียค่าใช้จ่าย $0.002 ค่าพรีเมี่ยมสำหรับการเขียนจะคุ้มค่าในการใช้งานครั้งแรก สำหรับพรอมต์สั้น ๆ เป็นเรื่องที่ต่างออกไป ต่ำกว่าความยาวขั้นต่ำที่โมเดลสามารถเก็บแคชได้ คำขึ้นต้นจะไม่ถูกเก็บแคชแม้ว่าจะมี cache_control ความยาวขั้นต่ำนี้คือ 512 โทเค็นบน Opus 5.5, Sonnet 5.5, Haiku 5.5 และ Fable 5.1 และสูงถึง 4,096 โทเค็นในบางโมเดลเก่า เช่น Haiku 4.5
  • ▸
    เวลาการสร้างจะใช้ระยะเวลาสูงสุด: หากการตอบสนองใช้เวลา 4 นาทีในการสตรีม การติดตามที่ใช้อีกครั้งกับคํานําหน้าเดียวกันจะต้องเริ่มภายใน 1 นาทีหลังจากการตอบสนองเสร็จสิ้น ด้วย TTL 5 นาที Agent Loop ที่ช้าหรือผู้ใช้ที่หยุดชั่วคราวจะพบว่าแคชหายไป
  • ▸
    การเก็บแคชเปลี่ยนราคาของโทเค็นขาเข้า การเขียนไปยังแคชมีค่าใช้จ่ายมากกว่าขาเข้าธรรมดา และการอ่านจากแคชมีค่าใช้จ่ายเพียงส่วนน้อยของขาเข้าธรรมดา การเข้าถึงแคชมีค่าใช้จ่าย 0.05 เท่าของราคาขาเข้าพื้นฐานใน Claude Opus 5.5 และ Claude Sonnet 5.5, 0.025 เท่าใน Claude Fable 5.1 และ Claude Mythos 5.1 และ 0.1 เท่าในรุ่นอื่น ๆ ทุกแบบ จุดเบรกเองไม่มีค่าใช้จ่าย คุณจ่ายเฉพาะการเขียนแคช การอ่านแคช และขาเข้าที่ไม่ได้แคช

#2 2. การเก็บแคชอัตโนมัติและจุดหยุดของ cache_control แบบชัดเจน

อ่านเนื้อหา ↗
  • ▸
    การเก็บแคชสามารถเปิดใช้งานได้สองวิธี การเก็บแคชอัตโนมัติใช้ฟิลด์ cache_control เดียวที่ระดับบนสุดของคำขอ ระบบจะวางจุดหยุดบนบล็อกที่สามารถแคชได้ล่าสุดและเลื่อนมันไปข้างหน้าตามการเติบโตของการสนทนา
  • ▸
    คุณไม่ต้องแก้ไขตัวทำเครื่องหมายด้วยตนเอง ในแต่ละรอบ ทุกอย่างจนถึงตอนสิ้นสุดของคำขอที่ผ่านมา จะถูกอ่านจากแคช และมีเพียงคำตอบผู้ช่วยใหม่และข้อความของผู้ใช้เท่านั้นที่ถูกเขียน จุดหยุดที่กำหนดเองจะใส่ cache_control บนบล็อกเนื้อหาแต่ละบล็อก ซึ่งช่วยให้ควบคุมได้ละเอียดมากขึ้น เช่น การเก็บแคชส่วนที่เปลี่ยนแปลงในอัตราที่แตกต่างกัน
  • ▸
    สําหรับ TTL 1 ชั่วโมง ให้เขียน { “type”: “ephemeral”, “ttl”: “1h” } ในช่องเดียวกัน การแคชแบบพุชทั้งแบบอัตโนมัติและแบบชัดเจนได้รับการรองรับในโมเดล Claude ที่ใช้งานอยู่ทั้งหมด

  • ▸

#4 4. เค้าโครงพรอมต์แบบโมดูลาร์: โมดูลที่มั่นคงก่อน ตัวแปรหลัง

  • ▸

  • ▸
    ข้อผิดพลาดในการจัดวางที่พบได้บ่อยที่สุดคือการที่ตัวแปรอยู่ตรงจุดแบ่งภาพ
