💡 แนวคิดหลักสำคัญ (Key Concept)

Reusable stable prefix — Reuse works when the start of a request is byte-for-byte the same as an earlier one. Caching stores that prefix so later requests skip reprocessing it. Modular layout keeps the prefix identical by putting changing content last, and Skills keep reusable instructions out of the prefix until a task needs them.

1. What prompt caching reuses and what it costs

การแยกงานให้ Subagents ทำจะช่วยยกระดับผลลัพธ์ให้ดีขึ้นใน 3 สถานการณ์หลัก เท่านั้น หากอยู่นอกเหนือจากนี้ การประสานงานมักจะสร้างต้นทุนมากกว่าประโยชน์:

1. ป้องกัน Context Pollution (ผลลัพธ์เครื่องมือมีขนาดใหญ่มาก): เมื่อการทำงานย่อยสร้างโทเค็นที่ไม่เกี่ยวข้องมากกว่า 1,000 โทเค็น (เช่น อ่านเอกสารหนาๆ หรือค้นหาเว็บ) การให้ Subagent ทำจะช่วยกักกันข้อมูลส่วนเกินไม่ให้รบกวนการตัดสินใจของ Orchestrator
2. เมื่องานสามารถทำพร้อมกันได้ (Parallelization): หากงานย่อยหลายชิ้นเป็นอิสระต่อกัน (เช่น ตรวจสอบความปลอดภัย 3 ด้านคนละมุม) การส่งให้ Subagents ทำงานขนานกันจะช่วยลด Latency รวมของระบบได้อย่างมหาศาล
3. เมื่องานต้องการเครื่องมือเฉพาะทางสูง (Tool Specialization): การใส่เครื่องมือให้เอเจนต์ตัวเดียวมากเกินไป (Capability Bloat) จะทำให้ความแม่นยำในการเลือกเครื่องมือลดลง การแยก Subagent ตามหน้าที่ช่วยให้แต่ละตัวมีเครื่องมือเฉพาะทางเพียง 3-5 ชิ้นเท่านั้น

✓ ตอบถูกแล้ว Check

An agent sends a request that reads a cached system prompt with the default 5-minute TTL. Claude takes 3 minutes to stream the response. The agent wants its next request to reuse the same cached prefix. What happens?

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Many production prompts open with the same few thousand tokens every time: tool definitions, a long system prompt, a block of examples, a reference document. Prompt caching lets later requests skip reprocessing that shared opening. When a request arrives with caching enabled, the system checks whether the prompt prefix up to a cache breakpoint is already cached from a recent query. On a hit it uses the cached version, which cuts processing time and cost. On a miss it processes the full prompt and caches the prefix once the response begins. The workloads that gain most are prompts with many examples, large background context, repetitive tasks with consistent instructions, and long multi-turn conversations.

A cache entry lives for 5 minutes by default, and every use refreshes it at no extra cost. A 1-hour TTL is available at 2x the base input price. The lifetime counts from the start of the request that writes or reads the entry, not from the end of its response. Generation time therefore uses up the window: if a response takes 4 minutes to stream, a follow-up that reuses the same prefix has to start within about 1 minute of that response finishing. With a 5-minute TTL, a slow agent loop or a user who pauses for a while finds the cache gone.

Caching changes the price of input tokens. Writing to the cache costs more than plain input, and reading from it costs a small fraction of plain input. Cache hits are 0.05x the base input price on Claude Opus 5.5 and Claude Sonnet 5.5, 0.025x on Claude Fable 5.1 and Claude Mythos 5.1, and 0.1x on every other model. Breakpoints themselves cost nothing. You pay only for cache writes, cache reads and uncached input, so adding breakpoints does not raise the bill.

Here is the arithmetic for a 20,000-token system prompt on Sonnet 5.5. Sent uncached, it costs $0.04 per request. The first cached request writes it for $0.05, and each hit after that costs $0.002. The write premium pays for itself on the first reuse. Short prompts are a different story. Below a model's minimum cacheable length, a prefix is not cached even if it carries cache_control. That minimum is 512 tokens on Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1, and as high as 4,096 tokens on some older models such as Haiku 4.5.

Caching can be turned on in two ways. Automatic caching uses a single cache_control field at the top level of the request. The system places the breakpoint on the last cacheable block and moves it forward as the conversation grows, so you never edit markers by hand. On each turn, everything up to the previous request's end is read from cache, and only the new assistant reply and user message are written. The two methods combine. A request can have at most four breakpoints, and the automatic one takes one of those slots. A common combination puts an explicit breakpoint on the system prompt and lets automatic caching follow the conversation.

Automatic caching runs on the same infrastructure as explicit breakpoints, so the same pricing, minimum token thresholds, ordering requirements and 20-block lookback window apply. A breakpoint marks the end of the prefix to look up, and most requests carry only one. When the exact prefix at the breakpoint has no entry, the system walks backward block by block. It looks for the longest prefix that an earlier request already wrote to the cache. That walk has a fixed reach of 20 positions.

Here is how that plays out over three turns. Turn 1 has 10 blocks with the breakpoint on block 10, and an entry is written there. Turn 2 has 15 blocks. Block 15 has no entry, so the walk goes back to block 10 and hits. Blocks 11–15 are processed fresh and a new entry is written at 15. Turn 3 jumps to 35 blocks, perhaps after a burst of tool calls. The walk from block 35 stops at block 16 and misses the block-15 entry by one position. Nothing has expired and nothing has been deleted. The entry is still there, but no lookup reaches it.

The fix is a second, explicit breakpoint further back, at or near the last place a write happened. Each breakpoint starts its own 20-position lookback, so a breakpoint at block 15 finds the turn-2 entry. Agent loops that add many blocks per turn, such as tool calls and tool results, are where automatic caching alone runs into this window. Watch the cache-read counts as conversations get longer.

Caching only rewards content that stays identical from one request to the next, so the order of a prompt decides how much of it can be cached. Build the prompt from modules ranked by how rarely they change. Tool definitions come first, then system instructions, then reference context and examples, then the conversation. Per-request values go at the very end. The same rule applies to [reusable prompt templates with variables](lesson:2.2): put the fixed template text ahead of every slot, so filling a variable only changes the tail.

The API builds cache prefixes in a fixed hierarchy: tools → system → messages. A change at one level invalidates that level and everything after it, never what comes before. That is why order matters. An edited tool definition throws away the whole cache, while a change that only touches the messages level keeps tools and system cached.

Forcing a particular tool with tool_choice is a request setting, but it still takes part in the hierarchy. It invalidates only the messages cache. Tools and the system prompt are still read from cache, and only the messages are reprocessed. Dynamic tool discovery fits this layout too. Some tool definitions can be marked as deferred: they are held back from the request, and so stay out of the system-prompt prefix, until the model runs a tool search and finds one it needs. The definition is then appended to the conversation history, after the cached prefix, so the prefix is left alone and the cache keeps hitting.

The most common layout mistake is a variable sitting at the breakpoint. Picture blocks 1–5 holding a large static system context, and block 6 holding a timestamp plus the user message, with cache_control on block 6. The timestamp changes on every request, so the prefix hash at block 6 changes too. The lookback then walks through blocks 5 to 1 and finds nothing, because no entry was ever written there. The lookback only finds entries that earlier requests wrote. It does not cache stable content that sits behind a breakpoint. Put the breakpoint on block 5, the end of the static modules, and move the timestamp after it.

Caching makes a repeated prefix cheaper. Agent Skills tackle a different kind of repetition: the same procedure pasted into prompt after prompt. A Skill is a directory holding instructions, metadata and optional resources such as scripts and templates. Claude uses it automatically when a request is relevant to it. A prompt holds conversation-level instructions for a single task. A Skill is created once and loads on demand in every conversation where it applies. Anthropic provides pre-built Skills for PowerPoint, Excel, Word and PDF, and custom Skills package an organisation's own procedures.

Every Skill needs a SKILL.md file that starts with YAML frontmatter containing two required fields. The rules are strict, and a violation gets the Skill rejected:

- name: at most 64 characters; only lowercase letters, numbers and hyphens; no XML tags; must not contain the reserved words "anthropic" or "claude". - description: non-empty; at most 1024 characters; no XML tags. - No other field is required. There is no version suffix and no minimum description length.

The description is how Claude decides to trigger the Skill. Claude matches each request against it, sometimes choosing among 100 or more available Skills. A good description therefore states what the Skill does and when to use it, including the words users actually type. "Helps with documents" names no task and no trigger, so it rarely matches. For names, a consistent gerund form such as processing-pdfs or analyzing-spreadsheets makes a library easier to scan. Avoid vague names such as helper or utils.

Who can use a custom Skill depends on where it lives:

Skills give Claude both instructions and code, and a malicious Skill can direct tool calls or code execution that do not match its stated purpose. Install Skills only from trusted sources, and audit every bundled file before you share one.

Put in order what happens when a user with the custom pdf-processing Skill installed asks Claude to "extract the text from this PDF and summarize it".

คำตอบที่ถูกต้อง: ตัวเลือก A
💡 คำอธิบายเฉลยภาษาไทย (Thai Explanation):

คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Skills avoid filling the context window because they load in stages instead of all at once. Claude works in a virtual machine with filesystem access. Each Skill sits on disk as a directory, and Claude reads a file only when it needs it.

Take a request to "extract the text from this PDF and summarize it". At startup the system prompt holds only the pdf-processing name and description. The request matches, so Claude runs cat pdf-processing/SKILL.md and the body enters context. Form filling is not needed, so FORMS.md is never read and costs nothing. Scripts go further still. When Claude runs validate_form.py, the code never enters context, only its output, such as "Validation passed". Running a script is therefore cheaper than generating equivalent code on the fly, and more consistent too.

These levels shape how a Skill should grow. Treat SKILL.md as a table of contents, and keep its body under 500 lines. As it nears that size, move detail into separate files that SKILL.md links to, such as FORMS.md, REFERENCE.md or examples.md. For Skills that span several domains, split the reference material by domain, for example reference/finance.md and reference/sales.md. A sales question then loads only the sales schema. Keep every reference one level deep from SKILL.md. When files point to further files, Claude may preview them with partial reads such as head -100 and miss information. Give any reference file over 100 lines a table of contents at the top, so a partial read still shows everything it contains.
