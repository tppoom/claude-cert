💡 แนวคิดหลักสำคัญ (Key Concept)

Contextual retrieval — Before indexing, Claude writes a short context for each chunk that places it within its source document. That context is prepended to the chunk before it is embedded and before it is added to the BM25 index, so both indexes can find chunks that make no sense on their own.

Your RAG pipeline indexes an HR policy library. One chunk reads: 'Employees in this region receive 25 days of paid leave per year.' The region is only named in the document's title. The query 'How many vacation days do employees in the Netherlands get?' does not return this chunk. What is the cause, and what fixes it?

A The chunk has lost the document around it, so nothing in it says which region it covers. Put that context back by writing chunk-specific context into each chunk before indexing, or by using a contextualized chunk embedding model such as voyage-context-4.
B The chunks are too large. Re-split the corpus into smaller chunks with a basic character splitter so each vector focuses on a single fact.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Retrieval-augmented generation (RAG) finds relevant passages in a knowledge base and adds them to the prompt. The first design question is whether you need it at all. A knowledge base under about 200,000 tokens, roughly 500 pages, can go into the prompt whole, and prompt caching keeps repeated requests fast and cheap. RAG is worth its extra moving parts once the corpus no longer fits in the context window.

Most of a RAG pipeline's work happens at ingestion. The corpus is split into chunks, usually no more than a few hundred tokens each. An embedding model turns each chunk into a vector, and a vector database stores those vectors so they can be searched by semantic similarity. At query time, the closest chunks are added to the prompt sent to Claude.

Chunk size, chunk boundary and chunk overlap are three settings you tune, and each one can change retrieval performance. Splitting on headings keeps each subsection's content together. A basic character splitter cuts wherever the character count runs out, whatever the text says at that point. Overlap belongs in the same list. Removing it to speed up indexing changes retrieval, so measure the effect like any other retrieval change.

Every chunk size has the same cost: once split off, a chunk loses the document around it. Take a set of SEC filings and the chunk 'The company's revenue grew by 3% over the previous quarter.' It answers a question about ACME Corp's revenue growth in Q2 2023, but it names neither the company nor the quarter. A query about ACME in Q2 2023 has little in that chunk to match. Even if the chunk is retrieved, Claude can't tell which company it describes.

There are two ways to put that context back. One is to write it into each chunk before indexing; this is contextual retrieval, covered below. The other is a contextualized chunk embedding model such as voyage-context-4. It produces chunk-level vectors that carry the whole document's context without you adding metadata by hand. You call it with contextualized_embed() instead of embed().

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Anthropic doesn't make an embedding model, so this step uses a third-party provider. Claude's documentation uses Voyage AI as its example and still advises comparing several vendors. Three factors separate providers. The first is how large and how domain-relevant the model's training data is. The second is inference performance, meaning lookup speed and end-to-end latency, which matters most in large production deployments. The third is customization: whether you can keep training the model on private data so it handles an unusual vocabulary.

Context length matters more once you add context to chunks. Some embedding models have a fixed input token limit. If contextualized chunks retrieve worse than plain ones, the added text may be pushing them past that limit so they get truncated. The fix is a model with a larger context window. voyage-law-2, for example, accepts half the input of the general-purpose models.

Embed documents and queries differently. Set input_type="document" when you embed chunks and input_type="query" when you embed the user's question. Don't omit the parameter or set it to None. Voyage prepends a different instruction to each kind of input: 'Represent the document for retrieval: ' for chunks and 'Represent the query for retrieving supporting documents: ' for questions. This gives better vectors for retrieval, which in turn improves retrieval quality.

Voyage vectors are normalized to length 1. That makes cosine similarity equal to dot product, and dot product is quicker to compute. Euclidean distance gives the same ranking too, so the similarity metric you choose won't change which chunks come back.

Two output settings make the index smaller without making retrieval more accurate. output_dtype quantizes each vector. With int8 or uint8, storage, memory and cost drop by 4x; with binary or ubinary, they drop by 32x. The default, float, keeps the highest precision and retrieval accuracy. output_dimension (for example 256 instead of the default 1024) returns shorter Matryoshka vectors, and vectors you've already stored can be cut down to their leading dimensions and normalized again. Use these settings when index size or cost is the problem. They won't help when relevant chunks are going missing.

Contextual retrieval writes the missing document context back into each chunk before indexing. For each chunk, Claude receives the whole document and the chunk and returns a short context, usually 50 to 100 tokens, that places the chunk within the document. That context is prepended to the chunk. The ACME chunk becomes 'This chunk is from an SEC filing on ACME corp's performance in Q2 2023; the previous quarter's revenue was $314 million.' followed by the original sentence.

The same contextualized chunk goes into both indexes. Pipelines keep a lexical index next to the vector index because embeddings can miss exact strings, such as error code TS-999, that BM25 matches ([Semantic embeddings vs BM25, and hybrid search](lesson:3.6)). Prepend the generated context before embedding the chunk; this is contextual embeddings. Prepend the same text before tokenizing the chunk for the BM25 index; this is contextual BM25. The original chunk text is still there, so BM25 still matches product codes and error strings exactly. It now also matches the company names, periods and file names that appeared only elsewhere in the document.

Each index improves measurably. Across codebases, fiction, ArXiv papers and science papers, contextual embeddings alone cut the top-20 retrieval failure rate by 35%, from 5.7% to 3.7%. Adding contextual BM25 raised the cut to 49%, bringing the failure rate to 2.9%. Contextualizing helped with every embedding model tested, and Gemini and Voyage embeddings gained the most.

The context has to be about the specific chunk. Attaching a generic document summary to every chunk gave very limited gains, and summary-based indexing performed poorly. The generic prompt above works well. A prompt tailored to your domain can work better, for example one that includes a glossary of terms defined only in other documents.

Prompt caching keeps the cost down. Each chunk's request repeats the whole document, so put the document first and mark the end of it with cache_control. The first chunk writes the document to the cache, and the following chunks read it at a 90% discount. The cache lasts five minutes, so process each document's chunks one after another instead of mixing chunks from different documents. With 800-token chunks, 8k-token documents and 100 tokens of context per chunk, generating the context costs $1.02 per million document tokens. That cost is paid once, at ingestion, not on every query. On a 737-chunk codebase dataset, caching cut input cost from about $9.20 to about $2.85.
