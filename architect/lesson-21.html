Retrieval-augmented generation (RAG) ทำหน้าที่ค้นหาข้อความที่เกี่ยวข้องใน Knowledge Base แล้วนำไปใส่ใน Prompt คำถามแรกในการออกแบบคือ คุณจำเป็นต้องใช้ RAG จริงหรือไม่? หาก Knowledge Base มีขนาดไม่เกินประมาณ 200,000 Tokens (ราว 500 หน้า) คุณสามารถยัดข้อมูลทั้งหมดลงใน Prompt ได้เลยโดยตรง และการใช้ Prompt Caching จะช่วยให้คำขอที่ซ้ำๆ ทำงานได้เร็วและประหยัดค่าใช้จ่ายอย่างมาก คุณควรเริ่มนำ RAG ที่มีระบบซับซ้อนเข้ามาใช้ก็ต่อเมื่อ Corpus มีขนาดใหญ่เกินกว่าจะใส่ลงใน Context Window ได้หมดเท่านั้น

ขั้นตอนส่วนใหญ่ของ RAG Pipeline จะเกิดขึ้นตอน Ingestion โดย Corpus จะถูกตัดแบ่งเป็น Chunks ย่อยๆ ซึ่งมักจะมีขนาดไม่เกิน 2-3 ร้อย Tokens ต่อ Chunk จากนั้น Embedding Model จะแปลงแต่ละ Chunk ให้เป็น Vector เพื่อจัดเก็บลงใน Vector Database สำหรับใช้ค้นหาด้วย Semantic Similarity เมื่อมี Query เข้ามา ระบบจะดึง Chunks ที่ใกล้เคียงที่สุดไปใส่ไว้ใน Prompt แล้วส่งต่อให้ Claude

Chunk Size, Chunk Boundary และ Chunk Overlap คือ 3 การตั้งค่าที่คุณต้องจูน และแต่ละตัวส่งผลกระทบโดยตรงต่อ Retrieval Performance เช่น การตัดแบ่งตาม Heading ช่วยให้เนื้อหาในแต่ละหัวข้อย่อยอยู่รวมกัน ในขณะที่ Character Splitter พื้นฐานจะตัดข้อความตามจำนวนตัวอักษรทันทีโดยไม่สนใจโครงสร้างเนื้อหา ส่วน Overlap ก็สำคัญไม่แพ้กัน การตัด Overlap ออกเพื่อเร่งความเร็วในการ Indexing จะเปลี่ยนผลลัพธ์ของ Retrieval เสมอ จึงต้องวัดผลทุกครั้งเหมือนกับการปรับจูน Retrieval อื่นๆ

Retrieval-augmented generation (RAG) finds relevant passages in a knowledge base and adds them to the prompt. The first design question is whether you need it at all. A knowledge base under about 200,000 tokens, roughly 500 pages, can go into the prompt whole, and prompt caching keeps repeated requests fast and cheap. RAG is worth its extra moving parts once the corpus no longer fits in the context window.

Most of a RAG pipeline's work happens at ingestion. The corpus is split into chunks, usually no more than a few hundred tokens each. An embedding model turns each chunk into a vector, and a vector database stores those vectors so they can be searched by semantic similarity. At query time, the closest chunks are added to the prompt sent to Claude.

Chunk size, chunk boundary and chunk overlap are three settings you tune, and each one can change retrieval performance. Splitting on headings keeps each subsection's content together. A basic character splitter cuts wherever the character count runs out, whatever the text says at that point. Overlap belongs in the same list. Removing it to speed up indexing changes retrieval, so measure the effect like any other retrieval change.

Every chunk size has the same cost: once split off, a chunk loses the document around it. Take a set of SEC filings and the chunk 'The company's revenue grew by 3% over the previous quarter.' It answers a question about ACME Corp's revenue growth in Q2 2023, but it names neither the company nor the quarter. A query about ACME in Q2 2023 has little in that chunk to match. Even if the chunk is retrieved, Claude can't tell which company it describes.

There are two ways to put that context back. One is to write it into each chunk before indexing; this is contextual retrieval, covered below. The other is a contextualized chunk embedding model such as voyage-context-4. It produces chunk-level vectors that carry the whole document's context without you adding metadata by hand. You call it with contextualized_embed() instead of embed().

Anthropic doesn't make an embedding model, so this step uses a third-party provider. Claude's documentation uses Voyage AI as its example and still advises comparing several vendors. Three factors separate providers. The first is how large and how domain-relevant the model's training data is. The second is inference performance, meaning lookup speed and end-to-end latency, which matters most in large production deployments. The third is customization: whether you can keep training the model on private data so it handles an unusual vocabulary.

Context length matters more once you add context to chunks. Some embedding models have a fixed input token limit. If contextualized chunks retrieve worse than plain ones, the added text may be pushing them past that limit so they get truncated. The fix is a model with a larger context window. voyage-law-2, for example, accepts half the input of the general-purpose models.

Embed documents and queries differently. Set input_type="document" when you embed chunks and input_type="query" when you embed the user's question. Don't omit the parameter or set it to None. Voyage prepends a different instruction to each kind of input: 'Represent the document for retrieval: ' for chunks and 'Represent the query for retrieving supporting documents: ' for questions. This gives better vectors for retrieval, which in turn improves retrieval quality.

Voyage vectors are normalized to length 1. That makes cosine similarity equal to dot product, and dot product is quicker to compute. Euclidean distance gives the same ranking too, so the similarity metric you choose won't change which chunks come back.

Two output settings make the index smaller without making retrieval more accurate. output_dtype quantizes each vector. With int8 or uint8, storage, memory and cost drop by 4x; with binary or ubinary, they drop by 32x. The default, float, keeps the highest precision and retrieval accuracy. output_dimension (for example 256 instead of the default 1024) returns shorter Matryoshka vectors, and vectors you've already stored can be cut down to their leading dimensions and normalized again. Use these settings when index size or cost is the problem. They won't help when relevant chunks are going missing.

Prepend the generated context before embedding the chunk; this is contextual embeddings. Prepend the same text before tokenizing the chunk for the BM25 index; this is contextual BM25. The original chunk text is still there, so BM25 still matches product codes and error strings exactly. It now also matches the company names, periods and file names that appeared only elsewhere in the document.

Each index improves measurably. Across codebases, fiction, ArXiv papers and science papers, contextual embeddings alone cut the top-20 retrieval failure rate by 35%, from 5.7% to 3.7%. Adding contextual BM25 raised the cut to 49%, bringing the failure rate to 2.9%. Contextualizing helped with every embedding model tested, and Gemini and Voyage embeddings gained the most.

The context has to be about the specific chunk. Attaching a generic document summary to every chunk gave very limited gains, and summary-based indexing performed poorly. The generic prompt above works well. A prompt tailored to your domain can work better, for example one that includes a glossary of terms defined only in other documents.

Prompt caching keeps the cost down. Each chunk's request repeats the whole document, so put the document first and mark the end of it with cache_control. The first chunk writes the document to the cache, and the following chunks read it at a 90% discount. The cache lasts five minutes, so process each document's chunks one after another instead of mixing chunks from different documents. With 800-token chunks, 8k-token documents and 100 tokens of context per chunk, generating the context costs $1.02 per million document tokens. That cost is paid once, at ingestion, not on every query. On a 737-chunk codebase dataset, caching cut input cost from about $9.20 to about $2.85.

  • •
    Retrieval-augmented generation (RAG) ทำหน้าที่ค้นหาข้อความที่เกี่ยวข้องใน Knowledge Base แล้วนำไปใส่ใน Prompt คำถามแรกในการออกแบบคือ คุณจำเป็นต้องใช้ RAG จริงหรือไม่?
  • •
    ขั้นตอนส่วนใหญ่ของ RAG Pipeline จะเกิดขึ้นตอน Ingestion โดย Corpus จะถูกตัดแบ่งเป็น Chunks ย่อยๆ ซึ่งมักจะมีขนาดไม่เกิน 2-3 ร้อย Tokens ต่อ Chunk จากนั้น Embedding Model จะแปลงแต่ละ Chunk ให้เป็น Vector เพื่อจัดเก็บลงใน Vector Database สำหรับใช้ค้นหาด้วย Semantic Similarity เมื่อมี Query เข้ามา ระบบจะดึง Chunks ที่ใกล้เคียงที่สุดไปใส่ไว้ใน Prompt แล้วส่งต่อให้ Claude
  • •
    การดึง Context เหล่านั้นกลับมามี 2 วิธี วิธีแรกคือเขียน Context เพิ่มเข้าไปในแต่ละ Chunk ก่อนทำ Indexing ซึ่งเป็นแนวทางของ Contextual Retrieval (จะกล่าวถึงด้านล่าง) อีกวิธีหนึ่งคือใช้ Contextualized Chunk Embedding Model เช่น voyage-context-4 ที่สามารถสร้าง Vector ในระดับ Chunk โดยฝัง Context ของทั้งเอกสารเข้ามาด้วยในตัว

  • •

#3 3. Contextual embeddings และ contextual BM25

อ่านเนื้อหา ↗
  • •
    ผลลัพธ์ของแต่ละ Index ดีขึ้นอย่างชัดเจน จากการทดสอบกับ Codebase, นิยาย, เอกสาร ArXiv และงานวิจัยวิทยาศาสตร์ การใช้ Contextual Embeddings เพียงอย่างเดียวช่วยลด Retrieval Failure Rate (Top-20) ลงถึง 35% (จาก 5.7% เหลือ 3.7%) และเมื่อผสานเข้ากับ Contextual BM25 จะลดลงถึง 49% (เหลือ Failure Rate เพียง 2.9%) โดยเทคนิคนี้ช่วยเพิ่มประสิทธิภาพให้กับ Embedding Model ทุกตัวที่ทดสอบ โดยเฉพาะ Gemini และ Voyage Embeddings ที่เห็นผลชัดเจนที่สุด
  • •
    Contextual Retrieval จะเขียนบริบทของเอกสารที่ขาดหายไปกลับเข้าไปในแต่ละ Chunk ก่อนทำ Indexing โดย Claude จะรับทั้งเอกสารและ Chunk นั้นๆ แล้วสร้าง Context สั้นๆ (ปกติราว 50-100 Tokens) เพื่อระบุตำแหน่งและความหมายของ Chunk ในภาพรวมของเอกสาร จากนั้นนำ Context นี้ไปใส่ไว้ข้างหน้า (Prepend) Chunk เช่น Chunk ของ ACME จะกลายเป็น 'Chunk นี้มาจากรายงานไฟลิ่งของ SEC เกี่ยวกับผลการดำเนินงานของ ACME Corp ใน Q2 2023 โดยมีรายได้ไตรมาสก่อนหน้าอยู่ที่ 314 ล้านดอลลาร์' แล้วตามด้วยประโยคเดิมของ Chunk
  • •
    Chunk ที่เพิ่ม Context แล้วนี้จะถูกส่งไปยังทั้งสอง Index เพราะ Pipeline มักเก็บ Lexical Index ควบคู่กับ Vector Index เพื่อป้องกันไม่ให้ Embeddings พลาด Exact Strings สำคัญ (เช่น รหัส Error 'TS-999' ที่ BM25 จับคู่ได้แม่นยำ) การนำ Context ที่สร้างขึ้นไปใส่ข้างหน้าก่อนทำ Embedding เรียกว่า Contextual Embeddings และการนำข้อความเดียวกันไปใส่ข้างหน้าก่อนทำ Tokenize

Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
You can leave input_type out and embed queries and chunks the same way, because the model handles both.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: ที่คิดว่าสามารถละเว้น input_type หรือทำ Embed ข้อมูล Queries และ Chunks ด้วยวิธีเดียวกันได้เพราะโมเดลรองรับทั้งคู่ แต่ในความเป็นจริง สำหรับงาน Retrieval ต้องระบุ Chunks เป็น document และระบุคำถามเป็น query เสมอ เพราะ Voyage จะเติม Instruction นำหน้าที่แตกต่างกันเพื่อให้ได้ Vector ที่มีประสิทธิภาพสูงสุดสำหรับการค้นหา การละเว้นพารามิเตอร์นี้หรือตั้งเป็น None จะทำให้สูญเสียประสิทธิภาพดังกล่าวไป
For retrieval, label chunks as document and questions as query. Voyage prepends a different instruction to each, which produces better vectors for retrieval. Leaving the parameter out or setting it to None loses that benefit.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
ใส่ Context ที่สร้างขึ้นเฉพาะกับ Embeddings แล้วคง Raw Chunk Text ไว้ใน BM25 เพื่อให้ Match ข้อมูลตรงๆ ได้แม่นยำ?
Add the generated context only to the embeddings and keep the BM25 index on raw chunk text so it still matches exactly.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: ต้อง Prepend บริบทเดียวกันทั้งก่อนทำ Embedding และก่อนทำ BM25 Indexing เพราะข้อความดั้งเดิมยังคงอยู่ใน Chunk ทำให้ Exact Matching ยังทำงานได้ปกติ แถม BM25 ยังสามารถค้นหาคำที่ปรากฏอยู่ส่วนอื่นของเอกสารเจอด้วย | นำ Document Summary เดียวกันไปแปะในทุก Chunk จะได้ผลลัพธ์เทียบเท่ากับ Contextual Retrieval? (ทำไมถึงผิด): ไม่จริง: ประสิทธิภาพที่เพิ่มขึ้นมาจากการเขียน Context ที่เฉพาะเจาะจงสำหรับแต่ละ Chunk จากการทดสอบพบว่าการใช้ Generic Document Summary แปะให้ทุก Chunk ให้ผลลัพธ์ดีขึ้นน้อยมาก
Prepend the same context before both the embedding step and the BM25 indexing step. The original text stays in the chunk, so exact matching still works, and the BM25 index can now match terms that appeared only elsewhere in the document. Attaching the same document summary to every chunk gives the same improvement as contextual retrieval. (ทำไมถึงผิด): The gains come from context written for each specific chunk. Generic document summaries attached to chunks were tested and gave very limited gains.
