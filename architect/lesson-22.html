1. Retrieve broadly, fuse, rerank and pass the top-k

ในเวลาที่สืบค้น ไปป์ไลน์จะเปลี่ยนคำถามของผู้ใช้ให้เป็นรายการสั้นๆ ที่เรียงลำดับอย่างดี การนำเข้าได้สร้างดัชนี BM25 และดัชนีเวกเตอร์ไว้แล้วบนส่วนที่แต่ละส่วนมีบริบทที่สร้างขึ้นสั้นๆ สำหรับสาเหตุที่จำเป็นต้องมีดัชนีทั้งสอง โปรดดู 📖 การฝังความหมายเทียบกับ BM25 และการค้นหาแบบไฮบริด (3.6) แต่ละดัชนีจะส่งกลับอันดับของตัวเอง BM25 จัดอันดับชิ้นส่วนตามการจับคู่คำที่ตรงทั้งหมด และดัชนีเวกเตอร์จัดอันดับตามความคล้ายคลึงทางความหมายกับคำถาม ซึ่งฝังอยู่กับ input_type="query" จากนั้น Rank Fusion จะรวมทั้งสองรายการเข้าด้วยกันและลบรายการที่ซ้ำกันออก โดยเหลือเพียงชุดเดียว

ดึงข้อมูลในวงกว้างแล้วจัดอันดับใหม่ให้แคบลง ในฐานความรู้ขนาดใหญ่ การดึงข้อมูลครั้งแรกสามารถส่งคืนความเกี่ยวข้องแบบผสมหลายร้อยชิ้น โมเดลการจัดอันดับใหม่จะใช้การสืบค้นและรายชื่อผู้สมัคร ให้คะแนนแต่ละส่วนตามความเกี่ยวข้อง และ

คุณจะเก็บเฉพาะ k อันดับแรกเท่านั้น การทดสอบของ Anthropic ได้ส่งผู้สมัคร 150 คนและคงไว้ 20 คน โดยใช้ Cohere reranker Voyage เสนอ rerank-3 เพื่อความแม่นยำสูงสุด และ rerank-3-lite เมื่อเวลาแฝงและต้นทุนมีความสำคัญมากกว่า ทั้งสองเรียกด้วย rerank()

Choosing k trades recall against distraction

More chunks make it more likely the answer is in the prompt, and more text also gives the model more to be distracted by

Twenty beat five and ten in Anthropic's tests, but that doesn't make 20 a constant

Measure it with Pass@k: for each test query, check whether its known relevant chunk appears in the first k results

On one codebase dataset, plain embeddings scored 81% at Pass@5 and 90% at Pass@20.

At query time, the pipeline turns a user's question into a short, well-ordered list of chunks. Ingestion has already built a BM25 index and a vector index over chunks that each carry a short generated context; for why both indexes are needed, see [Semantic embeddings vs BM25, and hybrid search](lesson:3.6). Each index returns its own ranking. BM25 ranks chunks by exact term matches, and the vector index ranks them by semantic similarity to the question, which is embedded with input_type="query". Rank fusion then merges the two lists and removes duplicates, leaving one set of candidates.

Retrieve broadly, then rerank narrowly. In a large knowledge base, the first retrieval can return hundreds of chunks of mixed relevance. A reranking model takes the query and the candidate list, scores each chunk for relevance, and you keep only the top-k. Anthropic's tests sent 150 candidates in and kept 20, using the Cohere reranker. Voyage offers rerank-3 for the highest accuracy and rerank-3-lite when latency and cost matter more, both called with rerank().

Reranking has a cost of its own. Claude gets fewer chunks, so generation is cheaper and faster, but the reranker adds a step to every request. It scores chunks in parallel, yet scoring more candidates still adds latency and cost. Choose the number of candidates against your latency budget: more candidates give better results, fewer give lower latency and cost.

Choosing k trades recall against distraction. More chunks make it more likely the answer is in the prompt, and more text also gives the model more to be distracted by. Twenty beat five and ten in Anthropic's tests, but that doesn't make 20 a constant. Measure it with Pass@k: for each test query, check whether its known relevant chunk appears in the first k results. On one codebase dataset, plain embeddings scored 81% at Pass@5 and 90% at Pass@20.

3. Caching retrieved context that repeats across queries

Prompt Caching คือกลไกสำคัญในการลดต้นทุนและความหน่วงสำหรับระบบที่ใช้พร้อมต์ยาวหรือมีคำสั่งพื้นฐานซ้ำๆ:

💰 ประหยัดต้นทุนโทเค็น โทเค็นที่อ่านจากแคช (Cache Read) จะมีราคาถูกกว่าอินพุตปกติถึง 90% (จ่ายเพียง 10% ของราคาอินพุตปกติ)
⚡ ลดความหน่วง (Latency) เวลาตอบสนองลดลงสูงสุดถึง 85% สำหรับคำขอที่แคชโดน (Cache Hit)

Some pipelines send the same retrieved content on every request

A support bot, for example, might add the same product documentation to the system prompt and then append each user's question

Prompt caching ([Prompt reuse and caching](lesson:2.5)) lets that repeated prefix be read from the cache instead of processed again, but only if the request is ordered and marked correctly.

Put the static content first and mark where it ends

Cache prefixes are built in a fixed order: tools, then system, then messages

The documentation therefore comes before the question, and the cache_control breakpoint goes on the last block of the documentation

The question that follows changes every time and stays outside the cached prefix

A breakpoint on the question would cache a prefix that no other request shares

A breakpoint on the first sentence of the system prompt would leave the documentation uncached.

Requests don't need an identical final message to benefit

A single breakpoint at the end of the static content is enough, because the system finds the longest prefix that an earlier request already wrote to the cache

search_result blocks also accept cache_control, so results passed in the messages can carry the breakpoint themselves.

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Exam Trap: Caching can't help when every user asks a different question, because the final message is never the same. (ทำไมถึงผิด): A breakpoint at the end of the static content caches everything before the question. The system matches the longest prefix already in the cache, so the varying question after it doesn't stop cache reads.

🇹🇭 คำอธิบายเจาะลึก: Exam Trap: การแคชไม่สามารถช่วยได้เมื่อผู้ใช้แต่ละคนถามคําถามที่แตกต่างกัน เนื่องจากข้อความสุดท้ายจะไม่เหมือนกันเลย (ทําไมถึงผิดพลาด): จุดหยุดพักที่จุดสิ้นสุดของเนื้อหาแบบคงที่จะแคชทุกอย่างที่อยู่ก่อนคําถาม ระบบจะจับคู่กับคํานําหน้าที่ยาวที่สุดที่อยู่ในแคชแล้ว ดังนั้นคําถามที่แตกต่างกันหลังจากนั้นจะไม่หยุดการอ่านแคช

A support bot sends the same five search_result blocks of product documentation in the user message on every request, followed by a text block with that user's question. The team wants those repeated blocks read from the cache. Where should the cache_control breakpoint go?

🇹🇭 คำแปลโจทย์: บอทสนับสนุนจะส่งเอกสารประกอบผลิตภัณฑ์ search_result จำนวนห้าบล็อกเดียวกันในข้อความผู้ใช้ในทุกคำขอ ตามด้วยบล็อกข้อความที่มีคำถามของผู้ใช้นั้น ทีมงานต้องการให้บล็อกที่ซ้ำกันเหล่านั้นอ่านจากแคช เบรกพอยต์ cache_control ควรอยู่ที่ไหน
คำตอบที่ถูกต้อง: ตัวเลือก A
💡 Official Explanation (คำอธิบายเฉลย):

Put the breakpoint at the end of the static content, here the last search_result block, which accepts cache_control. The system matches the longest prefix already in the cache, so the question that changes on every request doesn't stop cache reads. A breakpoint on the question caches a prefix no other request shares. A breakpoint on the first sentence of the system prompt leaves the documentation uncached.

🇹🇭 คำแปลไทย: วางเบรกพอยต์ที่ส่วนท้ายของเนื้อหาคงที่ ที่นี่คือบล็อก search_result สุดท้าย ซึ่งยอมรับ cache_control ระบบจะจับคู่คำนำหน้าที่ยาวที่สุดในแคช ดังนั้นคำถามที่เปลี่ยนแปลงในทุกคำขอจะไม่หยุดการอ่านแคช เบรกพอยต์ของคำถามแคชคำนำหน้าโดยไม่มีการแชร์คำขออื่น เบรกพอยต์ในประโยคแรกของพรอมต์ระบบจะทำให้เอกสารไม่แคช

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Some pipelines send the same retrieved content on every request. A support bot, for example, might add the same product documentation to the system prompt and then append each user's question. Prompt caching ([Prompt reuse and caching](lesson:2.5)) lets that repeated prefix be read from the cache instead of processed again, but only if the request is ordered and marked correctly.

Put the static content first and mark where it ends. Cache prefixes are built in a fixed order: tools, then system, then messages. The documentation therefore comes before the question, and the cache_control breakpoint goes on the last block of the documentation. The question that follows changes every time and stays outside the cached prefix. A breakpoint on the question would cache a prefix that no other request shares. A breakpoint on the first sentence of the system prompt would leave the documentation uncached.

Requests don't need an identical final message to benefit. A single breakpoint at the end of the static content is enough, because the system finds the longest prefix that an earlier request already wrote to the cache. search_result blocks also accept cache_control, so results passed in the messages can carry the breakpoint themselves.
