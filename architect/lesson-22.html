A platform team is redesigning their RAG pipeline after an audit found a high rate of retrieval failures, where relevant chunks exist in the knowledge base but are not returned for matching queries. They can implement several changes before the next release. Which of the following changes are documented to measurably reduce retrieval failure rates? (Select all that apply.)

คำตอบที่ถูกต้อง: ตัวเลือก A, B, C
💡 คำอธิบายเฉลยภาษาไทยรายตัวเลือก (Option Analysis):
ตัวเลือก A: ✓ คำตอบที่ถูกต้อง

ถูกต้อง. การฝังตามบริบทซึ่งเพิ่มบริบทอธิบายก่อนการเข้ารหัส ได้รับการบันทึกไว้เพื่อลดความล้มเหลวในการเรียกข้อมูลด้วยตนเอง

EN: Correct. Contextual embeddings, which prepend explanatory context before encoding, are documented to reduce retrieval failures on their own.
ตัวเลือก B: ✓ คำตอบที่ถูกต้อง

ถูกต้อง. การรวมการฝังตามบริบทเข้ากับการจัดทำดัชนีคำศัพท์ตามบริบทของ BM25 ช่วยลดความล้มเหลวในการดึงข้อมูลนอกเหนือจากการฝังเพียงอย่างเดียว

EN: Correct. Combining contextual embeddings with contextual BM25 lexical indexing further reduces retrieval failures beyond embeddings alone.
ตัวเลือก C: ✓ คำตอบที่ถูกต้อง

Correct. Adding a reranking stage on top of contextual embeddings and BM25 produces the largest documented reduction in retrieval failures of the three combined techniques.

EN: Correct. Adding a reranking stage on top of contextual embeddings and BM25 produces the largest documented reduction in retrieval failures of the three combined techniques.
ตัวเลือก D: ตัวเลือกที่ไม่ถูกต้อง

At query time, the pipeline turns a user's question into a short, well-ordered list of chunks. Ingestion has already built a BM25 index and a vector index over chunks that each carry a short generated context; for why both indexes are needed, see [Semantic embeddings vs BM25, and hybrid search](lesson:3.6). Each index returns its own ranking. BM25 ranks chunks by exact term matches, and the vector index ranks them by semantic similarity to the question, which is embedded with input_type="query". Rank fusion then merges the two lists and removes duplicates, leaving one set of candidates.

Retrieve broadly, then rerank narrowly. In a large knowledge base, the first retrieval can return hundreds of chunks of mixed relevance. A reranking model takes the query and the candidate list, scores each chunk for relevance, and you keep only the top-k. Anthropic's tests sent 150 candidates in and kept 20, using the Cohere reranker. Voyage offers rerank-3 for the highest accuracy and rerank-3-lite when latency and cost matter more, both called with rerank().

Reranking has a cost of its own. Claude gets fewer chunks, so generation is cheaper and faster, but the reranker adds a step to every request. It scores chunks in parallel, yet scoring more candidates still adds latency and cost. Choose the number of candidates against your latency budget: more candidates give better results, fewer give lower latency and cost.

Choosing k trades recall against distraction. More chunks make it more likely the answer is in the prompt, and more text also gives the model more to be distracted by. Twenty beat five and ten in Anthropic's tests, but that doesn't make 20 a constant. Measure it with Pass@k: for each test query, check whether its known relevant chunk appears in the first k results. On one codebase dataset, plain embeddings scored 81% at Pass@5 and 90% at Pass@20.

Chunks pasted into the prompt as plain text lose the link to where they came from. Search result content blocks keep that link. Each retrieved chunk goes in as a search_result block with a source and a title. With citations enabled, Claude attributes its answer to those sources the same way it cites web search results. No special prompting is needed: the citations appear on the text blocks that draw on your content.

source accepts any stable string, such as a URL or an internal identifier like kb://article-1234, so point it at the chunk's document in your store. content is an array of text blocks only; images and other media aren't supported. Citations are off by default, so set citations.enabled to true. Every search result in a request must use the same citations setting.

There are two ways to deliver search results. In the first, a custom retrieval tool such as search_knowledge_base returns search_result blocks inside its tool_result. If retrieval must run on every request, force the call with tool_choice. In the second, you fetch the chunks yourself and put the search results directly in the user message. All active models support search results with citations except Claude Haiku 3.

You also choose what text goes into each block. Responses may improve when Claude gets the contextualized chunk with the generated context clearly separated from the original chunk text. Run evals before settling on a format.

Some pipelines send the same retrieved content on every request. A support bot, for example, might add the same product documentation to the system prompt and then append each user's question. Prompt caching ([Prompt reuse and caching](lesson:2.5)) lets that repeated prefix be read from the cache instead of processed again, but only if the request is ordered and marked correctly.

Put the static content first and mark where it ends. Cache prefixes are built in a fixed order: tools, then system, then messages. The documentation therefore comes before the question, and the cache_control breakpoint goes on the last block of the documentation. The question that follows changes every time and stays outside the cached prefix. A breakpoint on the question would cache a prefix that no other request shares. A breakpoint on the first sentence of the system prompt would leave the documentation uncached.

Requests don't need an identical final message to benefit. A single breakpoint at the end of the static content is enough, because the system finds the longest prefix that an earlier request already wrote to the cache. search_result blocks also accept cache_control, so results passed in the messages can carry the breakpoint themselves.
