A platform team is redesigning their RAG pipeline after an audit found a high rate of retrieval failures, where relevant chunks exist in the knowledge base but are not returned for matching queries. They can implement several changes before the next release. Which of the following changes are documented to measurably reduce retrieval failure rates? (Select all that apply.)

A Prepend chunk-specific contextual summaries to chunks before generating their embeddings.
B Index the same contextualized chunk text lexically with BM25 alongside the embeddings.
C Add a reranking stage that rescores initial retrieval candidates before generation.
D Increase the generative model's sampling temperature during the final answer step.
E Store all embeddings using binary quantization to reduce vector index size.
5 Disable overlap between adjacent chunks to speed up index building.
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A, B, C
ตัวเลือก A: ถูกต้อง

Correct. Contextual embeddings, which prepend explanatory context before encoding, are documented to reduce retrieval failures on their own.

ตัวเลือก B: ถูกต้อง

Correct. Combining contextual embeddings with contextual BM25 lexical indexing further reduces retrieval failures beyond embeddings alone.

ตัวเลือก C: ถูกต้อง

Correct. Adding a reranking stage on top of contextual embeddings and BM25 produces the largest documented reduction in retrieval failures of the three combined techniques.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Sampling temperature affects the wording and variability of the generated answer text; it has no effect on which chunks are retrieved or how retrieval failures occur.

ตัวเลือก E: ไม่ถูกต้อง

Incorrect. Binary quantization is a storage and cost optimization that reduces embedding precision; it is not a documented technique for reducing retrieval failure rates and can trade off retrieval accuracy for space.

ตัวเลือก F: ไม่ถูกต้อง

Incorrect. Disabling overlap speeds up index building but removes a safeguard against split-boundary content, which tends to increase rather than decrease retrieval failures.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Retrieve broadly, fuse, rerank and pass the top-k" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

At query time, the pipeline turns a user's question into a short, well-ordered list of chunks. Ingestion has already built a BM25 index and a vector index over chunks that each carry a short generated context; for why both indexes are needed, see [Semantic embeddings vs BM25, and hybrid search](lesson:3.6). Each index returns its own ranking. BM25 ranks chunks by exact term matches, and the vector index ranks them by semantic similarity to the question, which is embedded with input_type="query". Rank fusion then merges the two lists and removes duplicates, leaving one set of candidates.

Retrieve broadly, then rerank narrowly. In a large knowledge base, the first retrieval can return hundreds of chunks of mixed relevance. A reranking model takes the query and the candidate list, scores each chunk for relevance, and you keep only the top-k. Anthropic's tests sent 150 candidates in and kept 20, using the Cohere reranker. Voyage offers rerank-3 for the highest accuracy and rerank-3-lite when latency and cost matter more, both called with rerank().

Reranking has a cost of its own. Claude gets fewer chunks, so generation is cheaper and faster, but the reranker adds a step to every request. It scores chunks in parallel, yet scoring more candidates still adds latency and cost. Choose the number of candidates against your latency budget: more candidates give better results, fewer give lower latency and cost.

Choosing k trades recall against distraction. More chunks make it more likely the answer is in the prompt, and more text also gives the model more to be distracted by. Twenty beat five and ten in Anthropic's tests, but that doesn't make 20 a constant. Measure it with Pass@k: for each test query, check whether its known relevant chunk appears in the first k results. On one codebase dataset, plain embeddings scored 81% at Pass@5 and 90% at Pass@20.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Passing chunks to Claude as citable search results" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Chunks pasted into the prompt as plain text lose the link to where they came from. Search result content blocks keep that link. Each retrieved chunk goes in as a search_result block with a source and a title. With citations enabled, Claude attributes its answer to those sources the same way it cites web search results. No special prompting is needed: the citations appear on the text blocks that draw on your content.

source accepts any stable string, such as a URL or an internal identifier like kb://article-1234, so point it at the chunk's document in your store. content is an array of text blocks only; images and other media aren't supported. Citations are off by default, so set citations.enabled to true. Every search result in a request must use the same citations setting.

There are two ways to deliver search results. In the first, a custom retrieval tool such as search_knowledge_base returns search_result blocks inside its tool_result. If retrieval must run on every request, force the call with tool_choice. In the second, you fetch the chunks yourself and put the search results directly in the user message. All active models support search results with citations except Claude Haiku 3.

You also choose what text goes into each block. Responses may improve when Claude gets the contextualized chunk with the generated context clearly separated from the original chunk text. Run evals before settling on a format.

3.Caching retrieved context that repeats across queries

Prompt Caching คือกลไกสำคัญในการลดต้นทุนและความหน่วงสำหรับระบบที่ใช้พร้อมต์ยาวหรือมีคำสั่งพื้นฐานซ้ำๆ:

💰 ประหยัดต้นทุนโทเค็น โทเค็นที่อ่านจากแคช (Cache Read) จะมีราคาถูกกว่าอินพุตปกติถึง 90% (จ่ายเพียง 10% ของราคาอินพุตปกติ)
⚡ ลดความหน่วง (Latency) เวลาตอบสนองลดลงสูงสุดถึง 85% สำหรับคำขอที่แคชโดน (Cache Hit)
⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

Exam trapCaching can't help when every user asks a different question, because the final message is never the same.Why is that wrong?A breakpoint at the end of the static content caches everything before the question. The system matches the longest prefix already in the cache, so the varying question after it doesn't stop cache reads.

Check

A support bot sends the same five search_result blocks of product documentation in the user message on every request, followed by a text block with that user's question. The team wants those repeated blocks read from the cache. Where should the cache_control breakpoint go?

A On the last search_result block, so the prefix ends with the static documentation and the question follows it
B On the question's text block, because the breakpoint has to be on the final block of the request

คลิกดูเฉลยคำตอบพร้อมคำอธิบาย (Click to view answer & explanation) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A

Put the breakpoint at the end of the static content, here the last search_result block, which accepts cache_control. The system matches the longest prefix already in the cache, so the question that changes on every request doesn't stop cache reads. A breakpoint on the question caches a prefix no other request shares. A breakpoint on the first sentence of the system prompt leaves the documentation uncached.

“cache_control | object | Cache control settings (for example, {"type": "ephemeral"})”

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 56794

A support-bot pipeline retrieves the same set of product documentation chunks for every user session and appends them to the system prompt, followed by whatever question the current user asks. The team wants to use prompt caching to cut latency and cost across the many queries that reuse this documentation. Where should they place the cache breakpoint?

A On the last content block of the retrieved documentation, immediately before the user's question is added to the request.
B On the user's question itself, since that is the part of the request being sent most frequently.
C On the very first sentence of the system prompt only, leaving the retrieved documentation uncached.
D Nowhere, since caching only benefits requests that share an identical final message, and the questions here vary.
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. The cache breakpoint should sit on the last block that stays identical across requests. In this pipeline, that is the end of the retrieved documentation, right before the variable user question, so every query benefits from a cache hit on the stable content.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. The user's question changes on every request, so placing the breakpoint there means the cached prefix never matches between requests and no cache hits occur.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Caching only the first sentence of the system prompt leaves the much larger, genuinely stable retrieved documentation uncached, missing almost all of the available savings.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Caching does not require the entire request to be identical; only the cached prefix (here, the retrieved documentation) needs to match, so this pipeline is a strong caching candidate.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Caching retrieved context that repeats across queries" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Some pipelines send the same retrieved content on every request. A support bot, for example, might add the same product documentation to the system prompt and then append each user's question. Prompt caching ([Prompt reuse and caching](lesson:2.5)) lets that repeated prefix be read from the cache instead of processed again, but only if the request is ordered and marked correctly.

Put the static content first and mark where it ends. Cache prefixes are built in a fixed order: tools, then system, then messages. The documentation therefore comes before the question, and the cache_control breakpoint goes on the last block of the documentation. The question that follows changes every time and stays outside the cached prefix. A breakpoint on the question would cache a prefix that no other request shares. A breakpoint on the first sentence of the system prompt would leave the documentation uncached.

Requests don't need an identical final message to benefit. A single breakpoint at the end of the static content is enough, because the system finds the longest prefix that an earlier request already wrote to the cache. search_result blocks also accept cache_control, so results passed in the messages can carry the breakpoint themselves.
