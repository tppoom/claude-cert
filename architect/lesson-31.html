💡 แนวคิดหลักสำคัญ (Key Concept)

Three opt-in OpenTelemetry signals — Claude Code and the Agent SDK emit three separate signals: metrics (counters), log events (one structured record per thing that happened) and traces (timed spans). Each signal has its own exporter variable, and a signal with no exporter never leaves the process, whatever else you turn on.

A full-featured observability platform can hold all three

It earns its place when you need to correlate them, for example to jump from a cost spike in a metric to the events and spans behind it.

Exporting takes several switches, and each one is a place for a CI rollout to go silently wrong

CLAUDE_CODE_ENABLE_TELEMETRY=1 turns collection on, but it does not choose an exporter

The metrics and logs exporters are optional, and with neither set, nothing reaches the collector

If you pick otlp, you also need a protocol, because Claude Code has no default OTLP protocol

You need an endpoint too OTEL_EXPORTER_OTLP_HEADERS carries whatever credential your collector expects

It is not an Anthropic key CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1 matters only for traces, because metrics and log events do not need it

The console exporter is a debugging aid, not a prerequisite.

The Agent SDK reads the same variables In production, set them in the process environment: every query() call picks them up with no code change

Pass them per call through ClaudeAgentOptions.env only when different agents in one process need different telemetry

That option behaves differently in the two SDKs

In Python, env is merged on top of the inherited environment

In TypeScript, it replaces the inherited environment, so spread process.env into it or you lose PATH and your API key

The default metrics interval is 60 seconds and the default logs interval is 5 seconds

Shorten both while debugging, and reset them for production.

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Exam Trap: Setting CLAUDE_CODE_ENABLE_TELEMETRY=1 is enough for Claude Code to start sending data to the team's collector. (ทำไมถึงผิด): That variable only enables collection. Monitoring an agent in production comes down to three questions. How much are we using, and what does it cost? What exactly happened on this request? Where did this run spend its time? Claude Code and the Agent SDK answer each one with a different OpenTelemetry signal, and each signal has its own exporter. Metrics are counters for tokens, cost, sessions, lines of code and tool decisions, so they suit totals and rates. Log events are structured records for each prompt, API request, API error and tool result, so they answer "what happened". Traces are spans for each interaction, model request, tool call and hook, so they show where the time went.

A full-featured observability platform can hold all three. It earns its place when you need to correlate them, for example to jump from a cost spike in a metric to the events and spans behind it.

Exporting takes several switches, and each one is a place for a CI rollout to go silently wrong. CLAUDE_CODE_ENABLE_TELEMETRY=1 turns collection on, but it does not choose an exporter. The metrics and logs exporters are optional, and with neither set, nothing reaches the collector. If you pick otlp, you also need a protocol, because Claude Code has no default OTLP protocol. You need an endpoint too. OTEL_EXPORTER_OTLP_HEADERS carries whatever credential your collector expects. It is not an Anthropic key. CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1 matters only for traces, because metrics and log events do not need it. The console exporter is a debugging aid, not a prerequisite.

The Agent SDK reads the same variables. In production, set them in the process environment: every query() call picks them up with no code change. Pass them per call through ClaudeAgentOptions.env only when different agents in one process need different telemetry. That option behaves differently in the two SDKs. In Python, env is merged on top of the inherited environment. In TypeScript, it replaces the inherited environment, so spread process.env into it or you lose PATH and your API key. The default metrics interval is 60 seconds and the default logs interval is 5 seconds. Shorten both while debugging, and reset them for production.

2. Controlling what metrics carry

Metric cost in most backends depends on cardinality: every distinct combination of attribute values is its own time series

Short-lived CLI sessions make this worse, because session.id is on metric datapoints by default

A thousand CI jobs therefore produce a thousand separate series for the same counter

The fix is to remove the attribute, not to change how often you flush

Setting OTEL_METRICS_INCLUDE_SESSION_ID=false removes session.id (and ccr.session.id on cloud sessions) and leaves every other datapoint attribute alone, so the remaining breakdowns still work

A longer OTEL_METRIC_EXPORT_INTERVAL only sends the same series less often.

By default, telemetry records the shape of the work and not its content. Prompts are reduced to their length, and the interaction span's user_prompt attribute reads . Assistant responses are reduced to their length too. Tool arguments, tool output and raw file contents are left out. Each kind of content has its own gate, and the gates send data only to the endpoint you configure, never to Anthropic. That still means a collector you run will be holding source code and secrets once a gate is open. One field is present without any gate: under OAuth, user.email appears in telemetry attributes, so filter it in your backend if that matters to you.

Two details catch out redaction rules. First, masking prompt text in a collector has to cover both prompt and prompt_text. Second, under detailed beta tracing the llm_request span carries model output in response.model_output, and that attribute follows OTEL_LOG_USER_PROMPTS, not the responses gate. Raw API bodies are the widest gate: turning them on counts as consent to everything the prompt, tool-detail and tool-content gates would reveal. Inline content is truncated at CLAUDE_CODE_OTEL_CONTENT_MAX_LENGTH, which defaults to 61440 UTF-16 code units (60 KB) so values fit backends that cap attributes at 64 KB.
