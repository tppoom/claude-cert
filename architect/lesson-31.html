💡 แนวคิดหลักสำคัญ (Key Concept)

Three opt-in OpenTelemetry signals — Claude Code and the Agent SDK emit three separate signals: metrics (counters), log events (one structured record per thing that happened) and traces (timed spans). Each signal has its own exporter variable, and a signal with no exporter never leaves the process, whatever else you turn on.

Metrics are counters, so they suit totals and rates such as tokens and cost. Log events are one structured record per prompt, API request, API error or tool result, so they answer what happened. Traces are timed spans per interaction, model request, tool call and hook, so they show where time went.

คลิกดูเฉลยคำตอบพร้อมคำอธิบาย (Click to view answer & explanation) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A

Each signal needs its own exporter, and CLAUDE_CODE_ENABLE_TELEMETRY only turns collection on. OTEL_LOGS_EXPORTER is the exporter for log events. The enhanced-telemetry beta flag and OTEL_TRACES_EXPORTER apply only to traces. OTEL_LOG_USER_PROMPTS controls whether prompt text is included and does not pick an exporter.

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 56897

A platform engineer sets CLAUDE_CODE_ENABLE_TELEMETRY=1 on every CI runner but the team's OTLP collector never receives any spans, metrics, or logs from Claude Code jobs. No other telemetry variables were configured. What is the most likely cause of the missing data?

A The collector rejects every signal until CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1 is also set, regardless of which exporters are chosen
B Telemetry is enabled but no exporter was selected, so OTEL_METRICS_EXPORTER and OTEL_LOGS_EXPORTER default to producing no export at all
C The CLI only emits telemetry once the console exporter has been configured first as a required local fallback
D The organization's Admin API key must be exported through OTEL_EXPORTER_OTLP_HEADERS before the CLI will emit any signal
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก B
ตัวเลือก A: ไม่ถูกต้อง

Incorrect. The enhanced telemetry beta flag is only required to unlock distributed tracing spans; metrics and log events do not depend on it, and it has no bearing on whether an exporter is configured.

ตัวเลือก B: ถูกต้อง

Correct. Enabling telemetry alone does not choose a destination. Each signal has its own exporter switch (OTEL_METRICS_EXPORTER, OTEL_LOGS_EXPORTER, OTEL_TRACES_EXPORTER), and leaving them unset means nothing is exported even though telemetry generation is on.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. The console exporter is one optional choice among several (otlp, prometheus, console, none); it is not a prerequisite the CLI requires before other exporters will function.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. OTEL_EXPORTER_OTLP_HEADERS carries authentication for the collector endpoint, not an Anthropic Admin API key, and its absence would cause auth failures at the collector, not a total absence of any emitted telemetry.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Metrics, log events and traces answer different questions" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

Monitoring an agent in production comes down to three questions. How much are we using, and what does it cost? What exactly happened on this request? Where did this run spend its time? Claude Code and the Agent SDK answer each one with a different OpenTelemetry signal, and each signal has its own exporter. Metrics are counters for tokens, cost, sessions, lines of code and tool decisions, so they suit totals and rates. Log events are structured records for each prompt, API request, API error and tool result, so they answer "what happened". Traces are spans for each interaction, model request, tool call and hook, so they show where the time went.

A full-featured observability platform can hold all three. It earns its place when you need to correlate them, for example to jump from a cost spike in a metric to the events and spans behind it.

Exporting takes several switches, and each one is a place for a CI rollout to go silently wrong. CLAUDE_CODE_ENABLE_TELEMETRY=1 turns collection on, but it does not choose an exporter. The metrics and logs exporters are optional, and with neither set, nothing reaches the collector. If you pick otlp, you also need a protocol, because Claude Code has no default OTLP protocol. You need an endpoint too. OTEL_EXPORTER_OTLP_HEADERS carries whatever credential your collector expects. It is not an Anthropic key. CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1 matters only for traces, because metrics and log events do not need it. The console exporter is a debugging aid, not a prerequisite.

The Agent SDK reads the same variables. In production, set them in the process environment: every query() call picks them up with no code change. Pass them per call through ClaudeAgentOptions.env only when different agents in one process need different telemetry. That option behaves differently in the two SDKs. In Python, env is merged on top of the inherited environment. In TypeScript, it replaces the inherited environment, so spread process.env into it or you lose PATH and your API key. The default metrics interval is 60 seconds and the default logs interval is 5 seconds. Shorten both while debugging, and reset them for production.

Metric cost in most backends depends on cardinality: every distinct combination of attribute values is its own time series. Short-lived CLI sessions make this worse, because session.id is on metric datapoints by default. A thousand CI jobs therefore produce a thousand separate series for the same counter. The fix is to remove the attribute, not to change how often you flush. Setting OTEL_METRICS_INCLUDE_SESSION_ID=false removes session.id (and ccr.session.id on cloud sessions) and leaves every other datapoint attribute alone, so the remaining breakdowns still work. A longer OTEL_METRIC_EXPORT_INTERVAL only sends the same series less often.

Attribution works in the other direction. In an Agent SDK service, OTEL_SERVICE_NAME (for example support-triage-agent) and OTEL_RESOURCE_ATTRIBUTES such as deployment.environment=production, enduser.id or tenant.id let you split usage per deployment or per customer. Every resource attribute is still a dimension, though, so a per-user ID carries the same cardinality cost as a session ID. Metrics export with delta temporality by default. Set OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=cumulative if your backend expects cumulative.

A trace turns one turn of the agent loop into a tree. The root is claude_code.interaction, which runs from the prompt arriving to the response. Under it, each call to the Claude API is a claude_code.llm_request span, and each tool invocation is a claude_code.tool span. A tool span has two children: claude_code.tool.blocked_on_user for the permission wait and claude_code.tool.execution for the work itself. That split is the first thing to check when a turn feels slow. A long wait span means a person was approving a prompt, not that the tool was slow. A subagent is a separate agent that the main session spawns, with its own model requests and tool calls, and the Agent tool is the tool call that starts one. The subagent's own llm_request and tool spans nest under that Agent tool's span.

To find the expensive part of a multi-agent run, group llm_request spans by agent_id and sum their token attributes. Add cache_read_tokens to input_tokens when you want the full input size, because input_tokens leaves cache reads out. A high attempt count next to a long duration_ms points to retries rather than a slow model. stop_reason = max_tokens means the output was cut off. Hook spans (claude_code.hook) wrap each hook execution and appear only under detailed beta tracing (ENABLE_BETA_TRACING_DETAILED=1 plus BETA_TRACING_ENDPOINT). That mode also changes where telemetry goes: Claude Code exports logs and traces to BETA_TRACING_ENDPOINT instead of through the logs and traces exporters, so they can stop arriving at the collector you configured.

By default, telemetry records the shape of the work and not its content. Prompts are reduced to their length, and the interaction span's user_prompt attribute reads . Assistant responses are reduced to their length too. Tool arguments, tool output and raw file contents are left out. Each kind of content has its own gate, and the gates send data only to the endpoint you configure, never to Anthropic. That still means a collector you run will be holding source code and secrets once a gate is open. One field is present without any gate: under OAuth, user.email appears in telemetry attributes, so filter it in your backend if that matters to you.

Two details catch out redaction rules. First, masking prompt text in a collector has to cover both prompt and prompt_text. Second, under detailed beta tracing the llm_request span carries model output in response.model_output, and that attribute follows OTEL_LOG_USER_PROMPTS, not the responses gate. Raw API bodies are the widest gate: turning them on counts as consent to everything the prompt, tool-detail and tool-content gates would reveal. Inline content is truncated at CLAUDE_CODE_OTEL_CONTENT_MAX_LENGTH, which defaults to 61440 UTF-16 code units (60 KB) so values fit backends that cap attributes at 64 KB.
