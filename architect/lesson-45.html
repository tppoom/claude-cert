💡 แนวคิดหลักสำคัญ (Key Concept)

Architecture description — The document that tells engineers what the major pieces of a Claude solution are, how they communicate, which model and tools each piece uses, and where the boundaries sit. It also records why each piece exists, so engineers can build and run the system without reverse-engineering a prototype.

1. What an architecture description must pin down

คําอธิบายสถาปัตยกรรมมีอยู่เพื่อตอบคําถามที่วิศวกรมีก่อนที่จะเขียนโค้ดใด ๆ คอมโพเนนต์ใดที่มีอยู่ คําขอเดินทางระหว่างพวกเขาอย่างไร โมเดลใดที่จัดการการเรียกใช้แต่ละครั้ง เครื่องมือใดที่โมเดลนั้นสามารถใช้ได้ ขอบเขตระหว่างสิ่งที่ทํางานในกระบวนการของคุณและสิ่งที่ทํางานที่อื่นอยู่ที่ไหน ไดอะแกรมที่แสดงกล่อง แต่ไม่รวมโมเดลต่อการเรียกใช้ หรือรายการเครื่องมือต่อคอมโพเนนต์ ส่งวิศวกรกลับไปยังต้นแบบเพื่อแก้ไขด้วยตนเอง

Implementation guidance also has to say how each external system reaches the agent. In Claude Code the usual answer is an MCP server, and the guidance should give the exact command that registers it. MCP servers are what let Claude Code act on issue trackers, monitoring tools and databases. The broader question of which integration mechanism to pick is covered in [connection protocols](lesson:3.7). This page is about writing the chosen one down so engineers can reproduce it.

Write down the transport, because it decides who runs the server. A hosted server is a URL, added with --transport http. A local server is a program the agent launches on its own machine. It needs no transport flag, because local servers use stdio by default. Re-implementing its API calls as custom tools inside the agent just throws that connector away.

Also state the scope you chose. local keeps the server to one person on one project, user gives it to one person across all projects, and project writes it to.mcp.json in the repository root so everyone who clones the repo gets the same server. Guidance meant for a whole team usually needs the project scope.

A prototype shows that the idea works. A service is something other engineers can deploy, configure and keep running. The support-agent example starts life as Python functions in Streamlit, and a real-time chatbot needs an API service instead. The guidance has to cover three changes: how the code is served, how it is configured, and how it handles failure.

For serving, wrap the core function in an HTTP service such as Flask or FastAPI. Stream responses with Server-Sent Events, cache responses to avoid unnecessary API calls, and keep conversation context when a user leaves and comes back. For configuration, list every setup step a fresh checkout needs. An instruction like copying.env.example to.env, without which tests and the dev server fail, is exactly what a new engineer can't guess. Network routing is configuration too. HTTPS_PROXY sends traffic through a corporate proxy, and the ANTHROPIC_BASE_URL family points at an LLM gateway for central usage tracking, rate limits or budgets.

Error handling is where prototypes cut the most corners. Every response from the Messages API reports why generation stopped in its stop_reason field, and a tool loop reads it: end_turn means the model finished normally. refusal is a different value, and a service must branch on it rather than assume every response is usable. It must also tell configuration errors apart from passing failures. On Claude Haiku 4.5, setting both temperature and top_p returns a 400 error, and retrying that request will never fix it. Deployment guidance closes with the rule to test in a development environment before production.
