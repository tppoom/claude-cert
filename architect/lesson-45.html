1. สิ่งที่คำอธิบายสถาปัตยกรรมต้องกำหนดให้ชัดเจน

คําอธิบายสถาปัตยกรรมมีอยู่เพื่อตอบคําถามที่วิศวกรมีก่อนที่จะเขียนโค้ดใด ๆ คอมโพเนนต์ใดที่มีอยู่ คําขอเดินทางระหว่างพวกเขาอย่างไร โมเดลใดที่จัดการการเรียกใช้แต่ละครั้ง เครื่องมือใดที่โมเดลนั้นสามารถใช้ได้ ขอบเขตระหว่างสิ่งที่ทํางานในกระบวนการของคุณและสิ่งที่ทํางานที่อื่นอยู่ที่ไหน ไดอะแกรมที่แสดงกล่อง แต่ไม่รวมโมเดลต่อการเรียกใช้ หรือรายการเครื่องมือต่อคอมโพเนนต์ ส่งวิศวกรกลับไปยังต้นแบบเพื่อแก้ไขด้วยตนเอง

Agent ฝ่ายสนับสนุนลูกค้าแสดงให้เห็นว่าเหตุใดสิ่งเหล่านี้จึงต้องมีรายการของตัวเอง เมื่อบอทเติบโตขึ้น การออกแบบหนึ่งจะส่งทุกคำถามไปยังตัวแยกประเภท Intent ก่อน ตัวแยกประเภทจะกำหนดเส้นทางการสืบค้นไปยังการสนทนาพิเศษ และแต่ละการสนทนาจะมีเครื่องมือและ Prompt ของระบบของตัวเอง ประโยคหนึ่งประกอบด้วยองค์ประกอบ (ตัวแยกประเภท) กระแสข้อมูล (แบบสอบถามไปยังตัวแยกประเภทในการสนทนา) การเรียกแบบจำลองต่อขั้นตอน และชุดเครื่องมือต่อการสนทนา วิศวกรต้องการให้ทุกคนจดบันทึกไว้

The document has to name one, because the choice decides who holds the filesystem, who executes the tools, and what the service exchanges over the network.

Take a platform team that needs an agent to run entirely on its own servers, work on git checkouts there, and call in-process functions as tools. That team should embed the Agent SDK as a library in its service. Managed Agents fails the first requirement, because Anthropic hosts the sandbox: custom tools become agent.custom_tool_use events that the client answers. A hand-written tool loop on top of the Messages API would work, but it rebuilds dispatch the SDK already does.

Write down the transport, because it decides who runs the server. A hosted server is a URL, added with --transport http. A local server is a program the agent launches on its own machine. Guidance meant for a whole team usually needs the project scope.

A prototype shows that the idea works. A service is something other engineers can deploy, configure and keep running. The support-agent example starts life as Python functions in Streamlit, and a real-time chatbot needs an API service instead. The guidance has to cover three changes: how the code is served, how it is configured, and how it handles failure.

For serving, wrap the core function in an HTTP service such as Flask or FastAPI. Stream responses with Server-Sent Events, cache responses to avoid unnecessary API calls, and keep conversation context when a user leaves and comes back. For configuration, list every setup step a fresh checkout needs. An instruction like copying.env.example to.env, without which tests and the dev server fail, is exactly what a new engineer can't guess. Network routing is configuration too. HTTPS_PROXY sends traffic through a corporate proxy, and the ANTHROPIC_BASE_URL family points at an LLM gateway for central usage tracking, rate limits or budgets.

Error handling is where prototypes cut the most corners. Every response from the Messages API reports why generation stopped in its stop_reason field, and a tool loop reads it: end_turn means the model finished normally. refusal is a different value, and a service must branch on it rather than assume every response is usable. It must also tell configuration errors apart from passing failures. On Claude Haiku 4.5, setting both temperature and top_p returns a 400 error, and retrying that request will never fix it. Deployment guidance closes with the rule to test in a development environment before production.

    สำหรับ Agent ขอบเขตที่สำคัญที่สุดคือกระบวนการที่ลูปของ Agent ทำงานอยู่ Claude Agent SDK และ Managed Agents ใช้แนวคิดเดียวกัน (Agent เครื่องมือ การทำงานตามช่วงเวลา) แต่ทำงานในสถานที่ต่างกัน SDK ทำงานในกระบวนการที่คุณควบคุม Managed Agents ทำงานบนโครงสร้างพื้นฐานของ Anthropic เอกสารต้องระบุอย่างใดอย่างหนึ่ง เพราะการเลือกนั้นจะตัดสินว่าใครถือระบบไฟล์ ใครเป็นผู้รันเครื่องมือ และบริการแลกเปลี่ยนข้อมูลผ่านเครือข่ายอย่างไร
  • •
    ลองคิดถึงทีมแพลตฟอร์มที่ต้องการ Agent ที่จะทำงานได้ด้วยตัวเองบนเซิร์ฟเวอร์ของตน ทำงานบน git checkouts ที่นั่น และเรียกใช้ฟังก์ชันในกระบวนการเป็นเครื่องมือ ทีมนี้ควรฝัง Agent SDK เป็นไลบรารีในบริการของตน ฟังก์ชันที่ตกแต่งด้วย @tool จะถูก SDK จัดการโดยอัตโนมัติ และเครื่องมือในตัวทำงานบนระบบไฟล์ท้องถิ่น

#3 3. การบันทึกวิธีการเชื่อมต่อเครื่องมือ

อ่านเนื้อหา ↗
  • •
    ตัวเชื่อมต่อ Confluence หรือ Jira แบบโอเพนซอร์สที่มีอยู่แล้วซึ่ง Agent ควรเริ่มเอง จะถูกบันทึกเป็นเซิร์ฟเวอร์ MCP แบบ stdio การนำการเรียก API ของมันมาทำใหม่เป็นเครื่องมือแบบกำหนดเองภายใน Agent ก็เท่ากับทิ้งตัวเชื่อมต่อนั้นไป
  • •
    แนวทางการนําไปใช้ยังต้องบอกวิธีการที่ระบบภายนอกแต่ละระบบเข้าถึง Agent ใน Claude Code คําตอบปกติคือเซิร์ฟเวอร์ MCP และแนวทางควรให้คําสั่งที่แน่นอนที่ลงทะเบียนมัน เซิร์ฟเวอร์ MCP เป็นสิ่งที่ทําให้ Claude Code สามารถดําเนินการกับตัวติดตามปัญหา เครื่องมือตรวจสอบ และฐานข้อมูล คําถามที่กว้างขึ้นว่าควรเลือกกลไกการผสานรวมใดจะครอบคลุมใน [connection protocols] (บทเรียน
  • •
    ระบุขอบเขตที่คุณเลือกด้วย local จะเก็บเซิร์ฟเวอร์ไว้สำหรับคนคนเดียวในโปรเจกต์หนึ่ง ส่วน user จะให้กับคนคนเดียวในทุกโปรเจกต์ และ project จะเขียนลงในไฟล์.mcp.json ที่รูทของ repository

#4 4. การบันทึกการเลือกโมเดล

อ่านเนื้อหา ↗
  • •
    การเรียกใช้โมเดลแต่ละครั้งในสถาปัตยกรรมควรระบุชื่อโมเดลของตนและเหตุผลที่เลือก เพราะเหตุผลนี้คือสิ่งที่จะช่วยให้ใครบางคนตรวจสอบได้ว่าการเลือกนั้นยังเหมาะสมอยู่หรือไม่ [ข้อแลกเปลี่ยนของโมเดล](lesson:2.1) สอนวิธีตัดสินใจเลือก โมเดลเอกสารนี้บันทึกผลลัพธ์ เลือกตัวอย่างเช่น ตัวจำแนกตั๋วปริมาณสูงที่มีข้อจำกัดด้านเวลาแฝงและงบประมาณค่าใช้จ่ายที่ยังต้องการเหตุผลจริง คำแนะนำคือ Claude Haiku 4.5 ซึ่ง Anthropic เปิดตัวให้เหมาะสมกับงานเรียลไทม์ ปริมาณสูง และมีความไวต่อค่าใช้จ่ายที่ต้องการเหตุผลเข้มแข็ง Haiku เป็นประเภทโมเดลที่มีต้นทุนต่ำที่สุดและเร็วที่สุด ส่วน Opus เป็นประเภทสำหรับงานองค์กรที่ต้องใช้เหตุผลหนัก ซึ่งมากกว่าความจำเป็นสำหรับการจำแนกตั๋วแต่ละใบ

#5 5. การบันทึกเหตุผลที่แต่ละชั้นมีอยู่

อ่านเนื้อหา ↗
  • •
    การออกแบบ Agent สนับสนุนแสดงให้เห็นว่าการเริ่มต้นที่ดีเป็นอย่างไร ก่อนที่จะเพิ่มชั้น คำสั่งแนะนำคือให้ใช้ประโยชน์จากพรอมต์ให้มากที่สุดก่อน จากนั้นค่อยลองเครื่องมือหรือโซ่พรอมต์เพิ่มเติม และจากนั้นค่อยเพิ่มตัวจัดประเภท ตัวจัดประเภทจะมีประโยชน์เมื่อบอทสามารถจัดการงานที่หลากหลายมาก มันจะมีค่าใช้จ่ายการเรียกใช้ Claude เพิ่มซึ่งอาจทำให้เกิดความหน่วง ข้อเท็จจริงแต่ละข้อเหล่านั้นควรถูกบันทึก
  • •
    ทุกชั้นควรถูกบันทึกลงในเอกสารพร้อมเหตุผลและตัวเลือกที่ถูกกว่าที่ได้ลองใช้ก่อน หากไม่มีบันทึกนั้น ทีมต่อไปจะเห็นเพียงตัวจำแนกเจตนา ห่วงโซ่คำสั่ง และชุดเครื่องมือ แต่ไม่สามารถบอกได้ว่าส่วนใดมีความสำคัญ พวกเขาอาจลบตัวจำแนกออกเพราะเห็นว่าเป็นการเรียกที่เสียเปล่าและทำให้การกำหนดเส้นทางสำหรับงานที่หลากหลายเสีย หรือพวกเขาอาจเพิ่มตัวกำหนดเส้นทางตัวที่สองเพราะไม่เคยรู้ว่าตัวแรกมีอยู่

#6 6. จากต้นแบบสู่บริการที่สามารถใช้งานได้

อ่านเนื้อหา ↗
  • •
    แทนที่จะสมมติว่าทุกการตอบสนองใช้งานได้ มันยังต้องแยกความผิดพลาดของการกำหนดค่าจากความล้มเหลวในการส่งได้ ใน Claude Haiku 4.5 การตั้งค่า temperature และ top_p ทั้งคู่จะส่งผลให้เกิดข้อผิดพลาด 400 และการลองส่งคำขอนั้นซ้ำจะไม่เคยแก้ไขได้ คำแนะนำสำหรับการติดตั้งปิดท้ายด้วยกฎให้ทดสอบในสภาพแวดล้อมการพัฒนาก่อนใช้งานจริง
  • •
    ต้นแบบแสดงให้เห็นว่าแนวคิดนี้ใช้ได้ผล บริการคือสิ่งที่วิศวกรคนอื่นๆ สามารถปรับใช้ กำหนดค่า และทำงานต่อไปได้ ตัวอย่าง Agent ฝ่ายสนับสนุนเริ่มต้นชีวิตเมื่อฟังก์ชัน Python ใน Streamlit และแชทบอทแบบเรียลไทม์ต้องการบริการ API แทน คำแนะนำต้องครอบคลุมการเปลี่ยนแปลงสามประการ
  • •
    วิธีการให้บริการโค้ด วิธีการกำหนดค่า และวิธีจัดการกับความล้มเหลว
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (3 ข้อควรระวัง)

กับดักการทดสอบ: Agent ที่ได้รับการจัดการจะนับว่ารัน Agent บนโครงสร้างพื้นฐานของคุณเอง เนื่องจากบริการของคุณเป็นตัวขับเคลื่อน
Managed Agents counts as running the agent on your own infrastructure, because your service drives it.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
Managed Agents รัน Agent และแซนด์บ็อกซ์ในโครงสร้างพื้นฐานของ Anthropic มีเพียง Agent SDK เท่านั้นที่รันลูปและเครื่องมือภายในกระบวนการที่คุณดำเนินการ
Managed Agents runs the agent and its sandbox in Anthropic's infrastructure. Only the Agent SDK runs the loop and tools inside a process you operate.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
ในการสอบ: การยกระดับความพยายามไม่ใช่วิธีประหยัดเงินหรือเวลา ความพยายามแลกการตอบสนองอย่างถี่ถ้วนเทียบกับประสิทธิภาพ ดังนั้นการตั้งค่าที่สูงกว่าจะซื้อความถี่ถ้วน เมื่อคำแนะนำมีจุดมุ่งหมายเพื่อลดเวลาแฝงและต้นทุน ให้เลือกคลาสโมเดลที่เล็กกว่า อย่าเพิ่มความพยายาม
On the Exam:: Raising the effort level is not a way to save money or time. Effort trades response thoroughness against efficiency, so a higher setting buys thoroughness. When a recommendation is meant to cut latency and cost, pick a smaller model class. Don't turn effort up.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
การเพิ่มระดับความพยายามเป็นวิธีมาตรฐานในการลดเวลาแฝงและต้นทุนสำหรับงานที่มีปริมาณมาก
Turning up the effort level is the standard way to cut latency and cost for high-volume work.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ความพยายามแลกกับความทั่วถึงกับประสิทธิภาพ ดังนั้นความพยายามที่มากขึ้นหมายถึงความรอบคอบที่มากขึ้น สำหรับต้นทุนและเวลาในการตอบสนอง แนะนำคลาสที่เล็กกว่า เช่น Haiku
Effort trades thoroughness against efficiency, so more effort means more thoroughness. For cost and latency, recommend a smaller class such as Haiku.
