💡 แนวคิดหลักสำคัญ (Key Concept)

Architecture description — The document that tells engineers what the major pieces of a Claude solution are, how they communicate, which model and tools each piece uses, and where the boundaries sit. It also records why each piece exists, so engineers can build and run the system without reverse-engineering a prototype.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "What an architecture description must pin down" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

An architecture description exists to answer the questions an engineer has before writing any code. Which components are there? How does a request travel between them? Which model handles each call? Which tools can that model use? Where are the boundaries between what runs in your process and what runs somewhere else? A diagram that shows boxes but leaves out the model per call, or the tool list per component, sends engineers back to the prototype to work it out for themselves.

A customer support agent shows why each of these needs its own entry. As the bot grows, one design sends every query to an intent classifier first. The classifier routes the query to a specialised conversation, and each conversation has its own tools and system prompt. That one sentence holds a component (the classifier), a data flow (query to classifier to conversation), a model call per step, and a tool set per conversation. An engineer needs every one of them written down.

2.Where the agent loop runs

ใน Claude Agent SDK การทำงานหลักถูกขับเคลื่อนด้วยฟังก์ชัน query() ซึ่งทำหน้าที่จัดการวงรอบเอเจนต์ (Agentic Loop) ให้อัตโนมัติ:

วงรอบการทำงานของ query() Loop:
  1. ส่งพร้อมต์และประวัติการสนทนาไปยัง Claude API
  2. รับผลลัพธ์จากโมเดล หากโมเดลส่ง stop_reason: "tool_use" ระบบจะรันเครื่องมือที่ระบุ
  3. นำผลลัพธ์ของเครื่องมือส่งกลับไปให้ Claude ประเมินซ้ำ
  4. ลูปนี้จะหมุนต่อเนื่องไปเรื่อยๆ จนกระทั่งโมเดลส่ง stop_reason: "end_turn" โดยไม่มีการเรียกเครื่องมือเพิ่ม

For an agent, the most important boundary is the process the agent loop runs in. The Claude Agent SDK and Managed Agents use the same concepts (agents, tools, sessions) but run them in different places. The SDK runs in a process you operate. Managed Agents runs in Anthropic's infrastructure. The document has to name one, because the choice decides who holds the filesystem, who executes the tools, and what the service exchanges over the network.

Take a platform team that needs an agent to run entirely on its own servers, work on git checkouts there, and call in-process functions as tools. That team should embed the Agent SDK as a library in its service. Functions decorated with @tool are dispatched by the SDK automatically, and built-in tools act on the local filesystem, so nothing about the team's requirements leaves its process. Managed Agents fails the first requirement, because Anthropic hosts the sandbox: custom tools become agent.custom_tool_use events that the client answers. A hand-written tool loop on top of the Messages API would work, but it rebuilds dispatch the SDK already does.

คลิกดูเฉลยคำตอบพร้อมคำอธิบาย (Click to view answer & explanation) ▼
คำตอบที่ถูกต้อง: ตัวเลือก B

Central usage tracking, rate limits and budgets are what an LLM gateway provides, and the ANTHROPIC_BASE_URL family of variables points traffic at it. A corporate proxy routes traffic for security monitoring and network policy, not budgets. Caching and effort settings change individual calls but give no central tracking or limits.

“Use this if you need centralized usage tracking across teams, custom rate limiting or budgets, or centralized authentication management.”

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "From prototype to deployable service" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A prototype shows that the idea works. A service is something other engineers can deploy, configure and keep running. The support-agent example starts life as Python functions in Streamlit, and a real-time chatbot needs an API service instead. The guidance has to cover three changes: how the code is served, how it is configured, and how it handles failure.

For serving, wrap the core function in an HTTP service such as Flask or FastAPI. Stream responses with Server-Sent Events, cache responses to avoid unnecessary API calls, and keep conversation context when a user leaves and comes back. For configuration, list every setup step a fresh checkout needs. An instruction like copying .env.example to .env, without which tests and the dev server fail, is exactly what a new engineer can't guess. Network routing is configuration too. HTTPS_PROXY sends traffic through a corporate proxy, and the ANTHROPIC_BASE_URL family points at an LLM gateway for central usage tracking, rate limits or budgets.

Error handling is where prototypes cut the most corners. Every response from the Messages API reports why generation stopped in its stop_reason field, and a tool loop reads it: end_turn means the model finished normally. refusal is a different value, and a service must branch on it rather than assume every response is usable. It must also tell configuration errors apart from passing failures. On Claude Haiku 4.5, setting both temperature and top_p returns a 400 error, and retrying that request will never fix it. Deployment guidance closes with the rule to test in a development environment before production.
