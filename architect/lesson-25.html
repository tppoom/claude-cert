ต้นฉบับ: Progressive discovery vs. monolithic context: tool search and when to use it

Anthropic Claude Certified Architect – Professional (CCAR-P) · สรุปและขยายความตามเอกสารทางการ 100%

🎯 สิ่งที่คุณจะสามารถทำได้หลังจบบทเรียนนี้ (What you will be able to do)

  • ✓Quantify the per-request cost of loading every tool definition up front, and name the tool count where selection accuracy starts to slip
  • ✓Configure tool search with defer_loading and explain how tool_reference blocks bring deferred tools into context
  • ✓Set ENABLE_TOOL_SEARCH in the Agent SDK and predict when each value loads tools up front
  • ✓Choose between a fixed tool set, tool search, Skills and a hybrid for a given agent, weighing search round-trips against context saved
💡 แนวคิดหลักสำคัญ (Key Concept)

Progressive discovery — Only lightweight entry points stay in context, such as a search tool or a Skill's name and description. Full definitions and instructions load when a request needs them. A monolithic strategy does the opposite: it loads everything on every request, whether or not that request uses it.

1. What a monolithic tool set costs before any work starts

การแยกงานให้ Subagents ทำจะช่วยยกระดับผลลัพธ์ให้ดีขึ้นใน 3 สถานการณ์หลัก เท่านั้น หากอยู่นอกเหนือจากนี้ การประสานงานมักจะสร้างต้นทุนมากกว่าประโยชน์:

1. ป้องกัน Context Pollution (ผลลัพธ์เครื่องมือมีขนาดใหญ่มาก): เมื่อการทำงานย่อยสร้างโทเค็นที่ไม่เกี่ยวข้องมากกว่า 1,000 โทเค็น (เช่น อ่านเอกสารหนาๆ หรือค้นหาเว็บ) การให้ Subagent ทำจะช่วยกักกันข้อมูลส่วนเกินไม่ให้รบกวนการตัดสินใจของ Orchestrator
2. เมื่องานสามารถทำพร้อมกันได้ (Parallelization): หากงานย่อยหลายชิ้นเป็นอิสระต่อกัน (เช่น ตรวจสอบความปลอดภัย 3 ด้านคนละมุม) การส่งให้ Subagents ทำงานขนานกันจะช่วยลด Latency รวมของระบบได้อย่างมหาศาล
3. เมื่องานต้องการเครื่องมือเฉพาะทางสูง (Tool Specialization): การใส่เครื่องมือให้เอเจนต์ตัวเดียวมากเกินไป (Capability Bloat) จะทำให้ความแม่นยำในการเลือกเครื่องมือลดลง การแยก Subagent ตามหน้าที่ช่วยให้แต่ละตัวมีเครื่องมือเฉพาะทางเพียง 3-5 ชิ้นเท่านั้น
💰 ต้นทุนโทเค็นที่ต้องแลก (Token Cost): สำหรับงานประเภทเดียวกัน ระบบ Multi-Agent มักใช้โทเค็นมากกว่าระบบเอเจนต์เดี่ยวประมาณ 3 ถึง 10 เท่า เนื่องจากต้องส่งคำสั่งระบบซ้ำให้กับ Subagent แต่ละตัว และต้องเสียโทเค็นในรอบการรวบรวมข้อมูล
⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

ในการสอบ จำนวนที่ต้องจดจำสำหรับความแม่นยำในการเลือกเครื่องมือคือโหลดเครื่องมือ 30–50 รายการในครั้งเดียว จำนวนเครื่องมือหลักเดียวอยู่ต่ำกว่านั้นมาก เครื่องมือหลายร้อยชิ้นยังห่างไกลจากมันมาก

EN: On the Exam: The number to remember for tool-selection accuracy is 30–50 tools loaded at once. Single-digit tool counts are well below it. Hundreds of tools are far past it.

A monolithic context strategy puts every tool definition into the context window on every request. That is the baseline that progressive discovery is measured against. Tool definitions count toward the context window just as messages do. The full cost of carrying too many tools is covered in [Capability bloat: what too many tools cost](lesson:3.1). The angle here is how large that fixed cost gets. A typical multiserver setup that connects GitHub, Slack, Sentry, Grafana and Splunk can use about 55k tokens on definitions before Claude does anything useful. The Agent SDK documentation gives a smaller rule of thumb: 50 tools can take 10–20K tokens.

Tokens are only half of the cost. Claude's ability to pick the right tool degrades once more than 30–50 tools are available at the same time. An agent that worked well with two MCP servers can start choosing the wrong tool after a third or fourth server is connected, even though no single tool changed. Context rot adds to this. As the token count grows, accuracy and recall both decline, so a large block of mostly unused definitions also makes everything else in the window harder to use.

A larger context window does not fix either problem. More room lets the 55k tokens fit, but it does not restore selection accuracy, and context rot gets worse as the window fills. What matters is how much is in context, not how much space is left over.

Tool search is the API's progressive-discovery mechanism for tools. It replaces the monolithic catalogue with a search step. Tool search typically cuts the definition footprint by over 85 percent, loading only the 3–5 tools a given request needs. Because Claude chooses from a short, relevant list, selection accuracy stays high even when the catalogue holds thousands of tools.

Tool search comes in two variants. With the regex variant (tool_search_tool_regex_20251119), Claude writes regex patterns. With the BM25 variant (tool_search_tool_bm25_20251119), Claude writes natural-language queries. Both search tool names, descriptions, argument names and argument descriptions, so well-written descriptions are what make a tool findable. To enable tool search, add one of the variants to the tools list and mark the tools that should stay out of context with defer_loading: true.

defer_loading decides what goes into Claude's context window, not what goes into the request. At the start, Claude's context holds only the search tool and any tools that are not deferred. When Claude needs something else, it calls the search tool. The search runs on Anthropic's servers and returns the matching tools as tool_reference blocks, five by default. Claude can set a limit between 1 and 10,000. The API then expands each reference into the full tool definition before Claude sees it. You never do the expansion yourself.

The conversation loop has a few rules that are easy to break:

- Send the assistant content back unchanged, including the server_tool_use and tool_search_tool_result blocks. - Never return a tool_result for the srvtoolu_... ID. The API rejects the request. - Execute the discovered tool's ordinary tool_use and return its tool_result as normal. - Expect an empty tool_references array, not an error, when a search matches nothing.

Discovered tools stay available after they are found. The API expands tool_reference blocks throughout the conversation history, so Claude can call a tool again in later turns without searching for it again. Deferred tools are also left out of the system-prompt prefix, and their references are added inline. The prefix therefore does not change and prompt caching keeps working. At least one tool, normally the search tool itself, must stay non-deferred. Never set defer_loading: true on the search tool.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The rule of thumb is to load a small, frequently used tool set up front and to use progressive discovery for large or rarely used catalogues. The cost of tool search is latency: Claude needs one extra turn to look up a tool before calling it. In return, baseline context usage drops sharply. That trade pays off for toolsets of about 20 or more tools where most aren't needed on every turn. It does not pay off when every tool is used constantly.

Take an internal agent with seven tools, about 1,200 tokens of definitions, and nearly every tool used on every request. Deferring those tools would add a search before calls Claude was always going to make, to save tokens that barely register. Keep them all loaded. The guidance to keep the 3–5 most-used tools non-deferred points the same way: whenever a tool is likely to be needed, it belongs in context.

The 55k-token multiserver agent is the opposite case. Tool search is the fix there, because it is the only option that removes definitions from context. Prompt caching makes repeated definitions cheaper, but every token still sits in context and the agent still chooses among dozens of tools. Rewriting every description by hand shrinks the definitions somewhat, but it leaves the tool count as it was and makes search worse, because names and descriptions are exactly what the search matches against. The approaches can be combined: tool search keeps the set lean, and caching lowers the cost of what stays loaded.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Tool search is not the only way to load context on demand. Agent Skills do the same thing for instructions and reference material. Skills load in three levels, described in [Progressive disclosure in Skills (three loading levels)](lesson:2.5): metadata at startup, then the SKILL.md body when the Skill triggers, then bundled files when they are read. What matters for this choice is the always-on cost. Each Skill keeps about 100 tokens of name and description in the system prompt, so many Skills can be installed without paying for content nobody is using.

Tool search and Skills solve different problems. Tool search defers tool schemas, and the API finds and expands them through tool_reference blocks. Skills defer know-how: workflows, schemas and scripts. Claude reads them from a filesystem with bash, and only a script's output enters context, never its code. A large catalogue of actions points to tool search. A large body of procedures and reference documents points to Skills. Skills need the code execution environment to work. Tool search needs a model that supports it, and Claude Opus 4.1 and earlier do not.

A hybrid often works best. Claude Code puts CLAUDE.md files into context up front and uses glob and grep to pull in other files only when they are needed. On-demand exploration has a cost of its own: it is slower than reading data that was retrieved in advance, and an agent with poor guidance can waste context on dead ends. So load what nearly every request needs, and defer the rest.
