1. คำมั่นสัญญาที่แท้จริงของ Standard และ Priority Tier

Stakeholders มักไม่ถามเรื่อง Service Tiers โดยตรง แต่มักถามว่า "ระบบจะล่มไหม?" ซึ่งคำตอบที่แท้จริงขึ้นอยู่กับว่า Traffic วิ่งอยู่บน Tier ไหน Anthropic แบ่ง Tier ออกเป็น 3 ระดับ ได้แก่ Standard ซึ่งเป็นค่า Default สำหรับทุก API Request, Priority Tier ที่ต้องมีการทำ Capacity Commitment ล่วงหน้า และ Batch สำหรับงาน Asynchronous ที่รอได้ การสัญญาเรื่อง Availability โดยไม่ได้จ่ายเงินซื้อ Capacity คือข้อผิดพลาดที่พบบ่อยที่สุดในการตกลง SLA

Standard ให้บริการแบบ Best-effort เท่านั้น Request จะถูกจัด Priority ปะปนกับผู้ใช้อื่นทั้งหมด ดังนั้นช่วง Peak อาจเกิด Error "server overloaded" ได้ และไม่มีตัวเลข Uptime อ้างอิง ขณะที่ Priority Tier จะจัดคิว Request ให้อยู่หน้า Traffic อื่น ช่วยลด Overload Errors แม้ในช่วง Peak โดยตั้งเป้าหมาย (Targets) Uptime ไว้ที่ 99.5% จุดสำคัญมี 2 ประการคือ คำว่า "Targets" ไม่ใช่ "Guarantees" (การันตี) และเป้าหมายนี้ครอบคลุมเฉพาะ Capacity ที่ Commit ไว้เท่านั้น Request ส่วนเกินจะถูกตัดกลับไปเป็น Standard Tier อัตโนมัติ

Two organisation-level limits set how much a deployment can do: rate limits cap requests and tokens per period, and spend limits cap monthly cost. Both come from your usage tier. Organisations are placed on a tier automatically from their usage history and move up over time, and new organisations may start in a lower Evaluation tier. These limits are enforced across the whole organisation. You can set lower limits of your own on individual workspaces, which is how one team's pilot is kept from using up another team's headroom.

Rate limits on the Messages API are measured per model class as requests per minute (RPM), input tokens per minute (ITPM) and output tokens per minute (OTPM). They are enforced over shorter windows than their names suggest. A 60 RPM limit can behave like one request per second, so a burst can fail even when the minute's total is under the limit. Caching is the lever to explain to stakeholders: for most models only uncached input tokens count toward ITPM, so a high cache hit rate raises effective throughput without a tier change. A higher limit can be requested in the Console once you are using at least 50% of your current limits.

Hitting the spend cap does not slow usage down. It stops it. When the organisation reaches its tier's cap, API usage pauses until 00:00 UTC on the first day of the next month. Signed criteria need to be reopened after launch, because the model underneath them changes. Prompts and guardrails tuned for one model can hold back a more capable one, so teams retest tasks as models change and improve. An eval suite keeps that renegotiation honest. Early on it makes the team define what success means, and later it holds the system to a consistent quality bar. A request to relax latency in exchange for a stronger model, or to accept a new model after a retirement, is then decided against numbers rather than impressions.

Every customer's incident runbook should name one public source for Anthropic-side incidents: status.claude.com. It gives real-time updates on the scope, impact and resolution progress of confirmed incidents. Account and billing questions go through a separate channel, Support, which you reach from the message icon in the Help Center or from "Get help" in the Claude Console. Keep the two apart in the handbook. One reports what is happening to everyone. The other handles your organisation's own case.

Some signals look like outages but are not. Capacity constraints, where demand is high but the system is working normally, do not appear on the status page, because they are normal load management. A 429 means your organisation hit a limit; it is not evidence of an incident. Internal dashboards, rate-limit charts and model system cards all have their uses, but none of them is where Anthropic announces incidents.

Model retirement is the other planned event that changes a committed timeline. Anthropic notifies affected customers by email and in the documentation, giving at least 60 days' notice before a publicly released model is retired. Deprecated models still work but have a replacement and a retirement date. Retired models fail every request. You can find which keys still call a deprecated model by exporting the Console Usage page as a CSV broken down by API key and model.

Which platform the traffic runs on decides which retirement date applies. Anthropic's published dates cover the Claude API, Claude Platform on AWS and Microsoft Foundry. Amazon Bedrock and Google Cloud run their own lifecycle, so the same model can be retired on the Claude API and still be available on a partner platform. Direct API traffic has to move to a supported model before Anthropic's date. Traffic on a partner platform follows that platform's timeline. Existing traffic gets no exemption, and retirement blocks API requests, not only the Console. How to run the migration itself is covered in [Lifecycle phases and model migration](lesson:6.5).

4 Weekly summary of decisions taken from feedback (สรุปการตัดสินใจประจำสัปดาห์ที่อิงจาก Feedback)
➔ Shows the cohort that their input has consequences and decides the wider rollout, so the loop is not just a suggestion box แสดงกลุ่มประชากรตามรุ่นว่าข้อมูลที่ได้รับนั้นมีผลกระทบและตัดสินใจเปิดตัวในวงกว้าง ดังนั้นการวนซ้ำจึงไม่ได้เป็นเพียงกล่องข้อเสนอแนะ
💡 Key Takeaway (หลักการสำคัญ):

Each stage does a different job. The channel and its owner handle collection, the weekly prompt keeps input coming, analytics give a signal nobody has to type, and reporting back proves that feedback changes decisions. If any stage is missing, feedback turns into scattered complaints with no context.

Decide how feedback will be collected and used before the pilot starts. Feedback gathered as an afterthought arrives as scattered complaints with no context. The pilot invitation is the first part of the loop. Tell the cohort they were chosen because they will use it on real problems and tell you the truth about it. Then give them a specific request: use it on at least one real task, and post what worked, what was annoying and what surprised them. Close by telling them what their input is for, so they know it has consequences.

Collection needs one place and one owner. A single channel gives questions one place to land. Name an owner to watch it for the first 48 hours, because unanswered launch-day questions kill momentum. Answer in public so each answer benefits everyone watching. A weekly prompt keeps feedback coming without a meeting: each Friday, ask what the tool helped with this week, and accept screenshots or a couple of sentences.

Triage and reporting back keep the loop from becoming a suggestion box. Sort each item before acting on it. Is it a capability gap, a limit or quota problem, a prompt or configuration fix, or a quality complaint that needs checking against evals? Then report the outcome back to the people who raised it. Usage data adds a signal nobody has to type. Analytics show adoption trends and dips in usage that may indicate friction, which tells you where to ask questions. One Anthropic team kept the human side manageable with a weekly "lessons & missteps" report and by batching questions so a reviewer could answer them in one pass. Reviewer attention runs out, so the loop should use it carefully.

6. Separating real degradation from normal variation

"สัปดาห์นี้รู้สึกว่าแย่ลง" เป็นคำร้องเรียนที่ทุก Pilot ต้องเจอ และการรีบตอบสนองก่อนตรวจสอบข้อเท็จจริงคือสิ่งที่ทำให้ทีมเสียเวลาเปล่าเป็นสัปดาห์ หากไม่มี Evals การ Debugging จะกลายเป็นแบบ Reactive คือต้องรอให้มีคนบ่น แล้วนำมา Reproduce แบบ Manual ตามแก้ทีละจุด และหวังว่าจะไม่มีอะไรพังเพิ่ม ปัญหาที่แท้จริงคือทีมที่ไม่มี Evals จะไม่สามารถแยกความแตกต่างระหว่าง Regression ที่เกิดขึ้นจริงกับ Noise ได้ เพราะธรรมชาติของโมเดลย่อมให้คำตอบที่แตกต่างกันได้สำหรับ Input ที่คล้ายกัน การเจอ Output แย่ๆ เพียงไม่กี่ครั้งจึงไม่ใช่หลักฐานว่าระบบมีอะไรเปลี่ยนแปลง

ตรวจสอบหาสาเหตุตามลำดับขั้นตอนที่กำหนดไว้ โดยเริ่มจากวิธีที่ต้นทุนต่ำที่สุด (Cheapest first):

  1. 1
    Confirmed incident: มีรายงานปัญหาบน status.claude.com หรือไม่? หากมี สาเหตุเกิดจากภายนอกระบบของคุณ และหน้า Status page จะบอกทั้งขอบเขตและความคืบหน้า
    Confirmed incident: is there an active entry on status.claude.com? If so, the cause is outside your system and the status page tells you scope and progress.
  2. 2
    Capacity or limits: Error ที่พบเป็น Overload response หรือ 429s หรือไม่? ข้อจำกัดด้าน Capacity ไม่ใช่ระบบล่ม (Outages) และ Error เกี่ยวกับ Limit ก็ไม่ใช่ปัญหาด้าน Quality
    Capacity or limits: are errors overload responses or 429s? Capacity constraints are not outages, and limit errors appear in the table above. Neither is a quality problem.
  3. 3
    Measured regression: คะแนนจาก Eval suite ที่รันบน Build ปัจจุบันต่ำกว่า Baseline หรือไม่? ผลลัพธ์นี้เท่านั้นที่รองรับการ Rollback หรือแก้ Prompt ได้อย่างสมเหตุสมผล
    Measured regression: does the eval suite, run on the current build, score below its baseline? Only this result justifies a rollback or a prompt change.
  4. 4
    Normal variation: หากไม่ตรงกับข้อใดข้างต้น ให้นำตัวอย่างที่รายงานเข้ามาใส่เพิ่มใน Eval set แล้วแจ้ง Stakeholder ตามตัวเลขที่วัดผลได้จริง
    Normal variation: if none of the above applies, add the reported examples to the eval set and tell the stakeholder what you measured.

กำหนดความคาดหวังเรื่อง Variation ไว้ใน Criteria ที่ลงนามตกลงกันตั้งแต่ก่อนจะมีคนร้องเรียน Consistency ถือเป็น Criteria ตัวหนึ่ง: Response ต้องมีความใกล้เคียงกันแค่ไหน สำหรับ Input ที่คล้ายกัน และจำเป็นแค่ไหนที่คำถามเดิมที่ถามซ้ำ 2 ครั้งจะต้องได้คำตอบที่ความหมายเชิง Semantics เหมือนกัน Stakeholder ที่เซ็นรับรองแล้วว่า "คำตอบอาจใช้ถ้อยคำต่างกันได้แต่สาระสำคัญต้องเหมือนเดิม" จะมีเกณฑ์มาตรฐานไว้เทียบเมื่อมีข้อร้องเรียน หากไม่มีมาตรฐานนี้ คำตอบที่ไม่คาดคิดทุกครั้งจะถูกมองว่าเป็น Regression เสมอ

"It feels worse this week" is the complaint every pilot gets eventually, and responding before checking is how teams lose a week. Without evals, debugging is reactive. You wait for complaints, reproduce them by hand, fix something, and hope nothing else regressed. The underlying problem is that a team without evals can't distinguish real regressions from noise. A model gives different answers to similar inputs, so a few bad outputs are not evidence that anything changed.

Check causes in a fixed order, cheapest first:

1. Confirmed incident: is there an active entry on status.claude.com? If so, the cause is outside your system and the status page tells you scope and progress. 2. Measured regression: does the eval suite, run on the current build, score below its baseline? Only this result justifies a rollback or a prompt change. 4. Normal variation: if none of the above applies, add the reported examples to the eval set and tell the stakeholder what you measured.

Set the expectation for variation in the signed criteria, before anyone complains. Consistency is a criterion of its own: how similar responses need to be for similar inputs, and how much it matters that the same question asked twice gets a semantically similar answer. A stakeholder who signed "answers may vary in wording but not in substance" has a standard to judge a complaint against. Without one, every unexpected answer looks like a regression.

    SLA จะมีประสิทธิภาพได้ก็ต่อเมื่อมีเกณฑ์วัดผลที่ชัดเจนรองรับ ควรกำหนดเกณฑ์ให้สามารถวัดค่าได้จริงตามหลัก [Measurable success criteria](lesson:6.1) แล้วให้ Stakeholders ทำการ Sign-off เป้าหมายของ Sign-off Session คือการเปลี่ยน Requirement ลอยๆ เช่น "ต้องเร็วและถูก" ให้กลายเป็นตัวเลือกเชิงเทคนิคและธุรกิจที่ Stakeholders ร่วมรับผิดชอบ การเลือกโมเดล Claude ต้องบาลานซ์ 3 ปัจจัยหลัก ซึ่งทั้งหมดนี้ต้องอาศัยการตัดสินใจจากฝั่ง Business ไม่ใช่หน้าที่ของ Engineering Single Agent

#4 4. วิธีติดตาม System Outages และ Model Retirements

อ่านเนื้อหา ↗
  • •
    Model Retirement เป็นอีกหนึ่ง Scheduled Event ที่กระทบต่อ Timeline การพัฒนา Anthropic จะแจ้งเตือนลูกค้าที่ได้รับผลกระทบทาง Email และ Documentation ล่วงหน้าอย่างน้อย 60 วันก่อนโมเดล Public จะ Retire โดยโมเดลสถานะ Deprecated จะยังใช้งานได้ตามปกติแต่มีโมเดลทดแทนและมีกำหนดวัน Retirement ที่ชัดเจน ส่วนโมเดลที่ขึ้นสถานะ Retired แล้วจะ Reject ทุก Request ทันที คุณสามารถตรวจสอบว่า API Keys ไหนยังเรียกใช้โมเดล Deprecated ได้โดย Export ข้อมูลจากหน้า Console Usage เป็น CSV แยกตาม API Key และ Model
  • •
    โมเดลเดียวกันอาจ Retire บน Claude API ไปแล้วแต่ยังใช้งานได้บน Partner Platforms หากเป็น Direct API Traffic คุณต้อง Migrate ไปยังโมเดลที่ Support ก่อนถึงกำหนดของ Anthropic แต่หากอยู่บน Partner Platform ให้ยึดตาม Timeline ของ Platform นั้น Traffic เดิมจะไม่ได้รับการยกเว้น และเมื่อถึงวัน Retire ระบบจะบล็อก API Requests ทั้งหมด ไม่ใช่แค่ใน Console อ่านขั้นตอนการ Migrate ได้ใน [Lifecycle phases and model migration](lesson:6.5)
  • •
    บางสัญญาณอาจดูเหมือนระบบล่มแต่ความจริงไม่ใช่ เช่น Capacity Constraints ที่เกิดจาก Demand สูงแต่ระบบยังทำงานปกติ จะไม่แสดงบน Status Page เพราะถือเป็น Normal Load Management ทั่วไป การเจอ HTTP 429 หมายถึงองค์กรคุณใช้เกิน Rate Limit ไม่ใช่หลักฐานว่าระบบล่ม แม้ Internal Dashboards, Rate-limit Charts และ Model System Cards จะมีประโยชน์ แต่ไม่ใช่ช่องทางประกาศ Incident ของ Anthropic

#5 5. Building the feedback loop into the pilot

อ่านเนื้อหา ↗
  • •
    การตั้ง Weekly prompt ช่วยกระตุ้น Feedback ได้อย่างต่อเนื่องโดยไม่ต้องนัดประชุม เช่น ทุกวันศุกร์ให้ถามว่าสัปดาห์นี้ Tool ช่วยอะไรได้บ้าง และเปิดรับทั้ง Screenshot หรือข้อความสั้นๆ เพียงไม่กี่ประโยค
  • •
    กำหนดวิธีรวบรวมและนำ Feedback ไปใช้ตั้งแต่ก่อนเริ่ม Pilot เพราะ Feedback ที่เก็บทีหลังโดยไม่วางแผนมักกลายเป็นแค่คำบ่นสะเปะสะปะที่ขาด Context การส่ง Pilot invitation คือจุดเริ่มต้นของ Loop นี้ ควรบอกกลุ่มผู้ใช้งานว่าพวกเขาได้รับเลือกเพื่อให้ทดลองใช้กับงานจริงและต้องการความคิดเห็นตามตรง จากนั้นตั้งโจทย์ให้ชัดเจน
  • •
    การทำ Triage และรายงานผลกลับช่วยป้องกันไม่ให้ Loop กลายเป็นเพียงกล่องรับข้อเสนอแนะที่ถูกมองข้าม แยกแยะแต่ละรายการก่อนลงมือทำ: เป็นช่องว่างด้าน Capability, ปัญหา Limit หรือ Quota, ข้อผิดพลาดที่ต้องแก้ที่ Prompt หรือ Configuration, หรือเป็นเรื่อง Quality ที่ต้องนำไปเทียบกับ Evals จากนั้นแจ้งผลลัพธ์กลับไปยังผู้ที่แจ้งปัญหาเสมอ

⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (6 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
สิ่งที่มักเข้าใจผิดเกี่ยวกับ Availability Promise?
On the Exam:: An availability promise has three parts: which tier, which model version, and how much capacity. A 99.5% figure quoted without all three overstates what Priority Tier gives you.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: การอ้างอิงตัวเลข 99.5% เพียงอย่างเดียวโดยไม่ระบุรายละเอียดให้ครบถ้วนถือเป็นการเคลมเกินจริง เพราะการตกลง Availability ที่ถูกต้องตามข้อสอบต้องระบุให้ครบทั้ง 3 องค์ประกอบเสมอ ได้แก่ Service Tier ไหน, Model Version ใด และขนาด Capacity เท่าใด
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Priority Tier การันตี Uptime 99.5% สำหรับทุก Traffic ของลูกค้าบนทุกโมเดล?
Priority Tier guarantees 99.5% uptime for all of a customer's traffic, on any model.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Priority Tier เพียงแค่ตั้งเป้าหมาย (Targets) Uptime 99.5% เฉพาะ Capacity ที่ Commit ไว้บน Model Version ที่ระบุเท่านั้น โดย Traffic ส่วนเกินจะ Fallback กลับเป็น Standard ทันที อีกทั้งโมเดลปัจจุบันหลายตัวยังไม่รองรับ Priority Tier
Priority Tier targets 99.5% uptime only for committed capacity on a specific model version. Traffic above the commitment falls back to standard, and several current models do not support Priority Tier at all.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Rate Limit คือ Reserved Capacity จึงสามารถการันตี Throughput ตาม Limit ให้ Stakeholders ได้?
A rate limit is reserved capacity, so throughput up to the limit can be promised to stakeholders.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Rate Limits และ Spend Caps คือเพดานสูงสุด (Ceilings) ไม่ใช่การรับประกัน Capacity ขั้นต่ำ และ Short Bursts สามารถทริกเกอร์ Error ได้แม้ปริมาณรวมใน 1 นาทีจะไม่เกิน Limit
Rate limits and spend caps are maximums, not guaranteed minimums, and short bursts can trigger errors even under the per-minute figure. Every 429 clears itself if the client keeps retrying. (ทำไมถึงผิด): The tier spend-cap 429 has no retry-after header, and retries fail until 00:00 UTC on the first of the next month unless the organisation moves up a tier.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
Apply it to your own work Think of a stakeholder wish you have heard recently, such as "it should feel instant". Which of capabilities, speed or cost does it really belong to, and what number would they need to sign?
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: ความต้องการของ Stakeholder เช่น "อยากให้ระบบรู้สึกตอบสนองทันที" เป็น Requirement ที่พร้อมนำไป Implement ทันที ความจริงคือต้องแปลงคำว่า "รู้สึกเร็ว" ให้อยู่ในกลุ่ม Speed แล้วกำหนดเป็นตัวเลข Response Time / Latency ที่แน่นอน (เช่น p95 < 800ms) เพื่อให้ Stakeholder ทำการ Sign-off เป็นเกณฑ์ที่วัดผลได้จริง
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
An Anthropic retirement date applies on every hosting platform, including Amazon Bedrock and Google Cloud.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: กำหนดการ Retirement ของ Anthropic จะมีผลบังคับใช้พร้อมกันทุกโฮสติ้งแพลตฟอร์ม รวมถึง Amazon Bedrock และ Google Cloud ความจริงคือ กำหนดการของ Anthropic ครอบคลุมเฉพาะ Claude API, Claude Platform บน AWS และ Microsoft Foundry เท่านั้น ส่วน Partner Platforms (Bedrock / Google Cloud) จะเป็นผู้กำหนด Lifecycle และตารางเวลา Retirement ของตนเองแยกต่างหาก
Anthropic's retirement dates cover the Claude API, Claude Platform on AWS and Microsoft Foundry. Partner-operated platforms set their own retirement schedules.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
A capacity-constraint message means Anthropic is having an outage, and it will be on the status page.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: ข้อความเตือนเรื่อง Capacity constraint ไม่ได้แปลว่า Anthropic มีระบบล่ม (Outage) และจะไม่ปรากฏบน Status page เพราะ Capacity constraint เป็นเพียงการจัดการโหลดตามปกติ (Load management) เท่านั้น ส่วน Status page จะแสดงเฉพาะเหตุการณ์ที่มีการยืนยันแล้วว่าเป็น Incidents
Capacity constraints are normal load management and are not posted on the status page. Only confirmed incidents are.

  • ✓อธิบายกลไกของ Rate Limits และ Spend Caps ระดับองค์กรในการควบคุม Throughput และค่าใช้จ่าย พร้อมระบุ Error ที่เกี่ยวข้องได้ถูกต้อง

  • ✓สร้าง Pilot Feedback Loop เพื่อรวบรวม, จัดลำดับความสำคัญ (Triage) และรายงานผลตั้งแต่วันแรก
  • ✓แยกแยะปัญหา Quality Drop ที่เกิดขึ้นจริงออกจาก Normal Variation ก่อนตอบสนองต่อข้อร้องเรียน
