💡 แนวคิดหลักสำคัญ (Key Concept)

Settings scope — Each Claude Code settings file has a scope, and the scope decides who the file reaches and how much weight its values carry. Managed settings come from the organization and sit above every file a developer controls. Below them are the shared project file that the team commits, the local file that stays with one developer, and the user file that applies across one developer's projects.

A platform team wants every engineer's Claude Code session to inherit a shared set of Bash allow rules and MCP server configuration that the team maintains and reviews through normal code review, while still letting each engineer add personal overrides that never leave their own machine. Where should the team place the shared rules, and where should individual overrides go?

A Commit the shared rules to .claude/settings.json in the project, and let engineers add personal overrides in .claude/settings.local.json
B Commit the shared rules to ~/.claude/settings.json on a reference machine, and let engineers add personal overrides in .claude/settings.json
C Deploy the shared rules through managed-settings.json at the OS policy path, and let engineers add overrides in .claude/settings.json
D Commit the shared rules to .mcp.json only, and let engineers add their own personal overrides into ~/.claude.json
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. Project settings at .claude/settings.json are git-committed and shared with the team, going through code review, while .claude/settings.local.json is gitignored and machine-specific, exactly matching the two requirements.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. User settings at ~/.claude/settings.json apply only to the individual who owns that home directory and are never shared through version control, so they cannot serve as the team's reviewed, shared configuration.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Managed settings are for organization-wide policy that cannot be overridden and are deployed via IT/MDM tooling, not through the team's normal project code review workflow described in the scenario.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. .mcp.json only covers MCP server definitions, not Bash permission rules, and ~/.claude.json is a per-user file that does not track with individual projects the way settings.local.json does.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

When a team uses Claude Code, the first choice for any setting is which file it goes in. The same permission rule does different things depending on where you put it. Committed to the repository, it reaches every teammate. In your home directory, it stays on your laptop. Deployed by IT, nobody below can override it. Claude Code reads four scopes, and each one answers the question "who gets this?" differently.

For a platform team, the shared project file is the one that matters. .claude/settings.json lives in the repository, so changes to it go through ordinary code review and land in every clone on the next pull. Until you commit it, though, it is just a file on your disk and nobody else has it. A rule you write in ~/.claude/settings.json never leaves your machine, even if that machine is the team's reference box. Managed settings are the wrong tool for team conventions the other way round: the organization deploys them, so developers do not create or edit them, and they skip the repository's review process altogether.

The local file is where personal overrides belong. When Claude Code first writes .claude/settings.local.json in a git repository, it adds the file to your global git excludes so it stays out of your commits. If you create the file by hand, add it to .gitignore yourself. Claude Code also writes to this file for you: choosing "Yes, and don't ask again" on a Bash prompt saves an allow rule here. Because the file belongs to you and not to the repository, its allow rules apply without the workspace trust step that the committed file needs, as long as the file stays untracked.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Which value wins when scopes disagree" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

For a single-value key such as model, the higher scope wins outright. From highest to lowest, the order is: managed settings, then JSON passed with --settings for one session, then project local, then shared project, then user. The --settings flag sits above your user, project and local files but below managed settings. It can set anything your user file can set, but never a managed key.

Arrays work differently, and permission rules are arrays. Across the non-managed scopes, Claude Code merges the arrays instead of letting the higher file replace the lower one. Suppose the project file denies a command and your local file allows something. The local file does not replace the project's deny list. Both rules end up in the effective set. A few keys are exceptions. fallbackModel is an ordered chain, so Claude Code takes the whole value from the highest file that defines it. When managed settings define availableModels, Claude Code applies that list as-is and ignores entries you add lower down.

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 57042

A security lead configures a project-level deny rule Bash(aws *) to block all AWS CLI usage from Claude Code. A developer later adds an allow rule Bash(aws s3 ls) to their local settings so they can list bucket contents. When the developer runs aws s3 ls in a session, what happens?

A The command is blocked, because deny rules are evaluated before allow rules and a broad deny cannot carry allowlist exceptions from a narrower allow rule
B The command runs without a prompt, because the more specific allow rule Bash(aws s3 ls) takes precedence over the broader deny pattern Bash(aws *)
C The command triggers a one-time confirmation prompt, because Claude Code merges conflicting rules of equal specificity into an ask decision
D The command runs without a prompt, because local settings always override project settings regardless of whether the rule is allow or deny
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. Rules are evaluated in the fixed order deny, then ask, then allow, and rule specificity does not change that order, so a broad deny rule like Bash(aws *) blocks every matching call even when a narrower allow rule also matches.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. Specificity does not override the deny-first evaluation order; a narrower allow rule matching the same call as a broader deny rule still loses to the deny rule.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. There is no rule-merging step that converts a deny/allow conflict into an ask prompt; the deny rule wins outright and the command is blocked with no prompt.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Local settings can add stricter or looser rules within their own scope, but they do not grant an exception to a deny rule defined at a different scope, since deny rules from any scope are evaluated before allow rules.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A permission rule names a tool and, optionally, a specifier in parentheses. Bash on its own matches every Bash command. Bash(npm run build) matches only that exact command. Read(./.env) matches reading .env in the current directory, and WebFetch(domain:example.com) matches fetches to that domain. Some tools also accept a parameter match such as Agent(model:opus). Each rule names one parameter, so gating on two parameters takes two rules. Rules go into permissions.allow, permissions.ask or permissions.deny in whichever scope should own them.

The three rule types do three different jobs. An allow rule lets a tool run without asking for approval. An ask rule prompts for confirmation every time. A deny rule stops the tool from being used at all. An allow rule does not grant access past a deny; it only removes the prompt. Because rules from every scope merge into one set, a project-level Bash(aws *) deny and a local Bash(aws s3 ls) allow both apply to aws s3 ls, and the call is blocked. A more specific allow does not carve an exception out of a broad deny, and a local file does not cancel a project's deny.

Path rules hide an asymmetry that catches teams writing secret-file protections. As an allow rule, Edit(src/**) matches only src/ under the current directory. As a deny or ask rule, the same pattern matches a src directory at any depth. So Read(secrets/**) in a deny list also covers nested copies such as vendor/pkg/secrets/. To allow a directory name at any depth, write Edit(**/src/**).

A project CLAUDE.md (or .claude/CLAUDE.md) reaches team members through source control. ~/.claude/CLAUDE.md holds personal preferences for all projects.
