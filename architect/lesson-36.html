💡 แนวคิดหลักสำคัญ (Key Concept)

Human approval checkpoint — A point in the permission pipeline where a tool call stops until a person approves it, changes it or refuses it. The checkpoint only exists if no earlier step has already approved or denied the call.

📑 หัวข้อในบทเรียนนี้ (In this lesson)

  • ▸2. Permission modes: how much the human reviews

  • ▸4. canUseTool: routing tool calls to a person

1. Why an agent needs human approval checkpoints

An agent that can run shell commands, edit files or call external services will sometimes do something its user never meant. Anthropic's incident log lists real cases: deleting remote git branches after misreading an instruction, uploading an engineer's GitHub auth token to a compute cluster, and attempting migrations against a production database. None of these came from hostile intent. In each case the model was overeager and takes initiative beyond what the user would approve.

Human-in-the-loop validation means putting a person between the agent and those actions. The design problem is placing the person well. If every action asks for approval, people stop reading the prompts: Claude Code users approve 93% of permission prompts. If nothing asks, nobody catches the deleted branch. A good design sends routine reads and edits through without a prompt and saves the person's attention for actions that are irreversible, touch shared infrastructure or send data outside the organisation.

Claude offers three surfaces for this. Claude Code uses permission modes. The Agent SDK uses a canUseTool callback that your application answers. Managed Agents use permission policies that pause a session until your client confirms. All three answer the same question: which calls run on their own and which ones wait for a person?

2. Permission modes: how much the human reviews

A permission mode sets the baseline for how much a person reviews. In Claude Code you switch modes with Shift+Tab in the CLI, and in the SDK you set permissionMode. Going from default to bypassPermissions, each mode takes more decisions away from the person.

A permission mode sets the baseline for how much a person reviews. In Claude Code you switch modes with Shift+Tab in the CLI, and in the SDK you set permissionMode. Going from default to bypassPermissions, each mode takes more decisions away from the person.

Two modes give different kinds of human-in-the-loop control, and they are easy to confuse. plan lets Claude investigate freely but keeps your source files untouched until a person signs off. Claude Code blocks edits until you approve a plan. dontAsk is for runs with no person present. It turns every would-be prompt into a denial, so a CI job never sits waiting on a question nobody will answer. Calls approved by allowedTools or allow rules still run. In the SDK, canUseTool is never called in this mode. A headless run with --dangerously-skip-permissions behaves the same way: the few calls that would still prompt are denied instead.

In auto mode a model-based classifier takes the human approver's place. Before shell commands and network requests run, it checks that they match what the user asked for. Approval fatigue is the reason it exists. It does not remove the person entirely.

Some actions reach a person in every mode, including auto and bypassPermissions, which skips permission prompts except for the actions no mode auto-approves. These are:

- tools matched by an explicit ask rule - connector tools your organisation set to ask, in sessions where that setting reaches Claude Code - tools that need user interaction: the built-in AskUserQuestion tool and MCP tools marked requiresUserInteraction - rm and rmdir removals targeting a critical path - the cross-session messaging safeguards

That last point is why a hook is the strongest checkpoint for a high-impact tool. Hooks run custom code on every matching call (see [Hooks: actions that always run](lesson:7.2)). 📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

In the Agent SDK, every tool call passes through a fixed sequence of steps. The first step that reaches a decision settles the call, and later steps never see it. The person, through canUseTool, is the last step. So whether a human ever sees a call depends on what every step before it did.

The order explains which configurations keep a person in the loop:

- Plan mode keeps a reviewer on every write. The mode step comes before allow rules, so in plan mode no write can be auto-approved. A lead who wants to see each diff before it lands can let Claude investigate with read-only tools while every proposed edit goes to the callback. acceptEdits does the opposite: edits land first and get reviewed afterwards. - A bare allow entry silences the callback. An allowedTools entry such as "Read" approves the whole tool before the callback is consulted. If you allow a tool and expect canUseTool to intercept it, the callback will never run for that tool. - A deny rule cannot be reversed from the callback. Deny rules are step two. A call they block never reaches step six, so canUseTool cannot lift the block for a single call. - bypassPermissions only approves what reaches step four. It approves everything that arrives at the mode step, so a hook or ask rule that already decided the call is not affected.

That last point is why a hook is the strongest checkpoint for a high-impact tool. Hooks run custom code on every matching call (see [Hooks: actions that always run](lesson:7.2)). A PreToolUse hook scoped to a wire-transfer tool decides at step one, before any rule or mode. It adds a second approval layer on top of the permission settings. If someone later switches the session to bypassPermissions, the hook's demand for human approval still holds, because the bypass step comes after it.

4. canUseTool: routing tool calls to a person

canUseTool is how an Agent SDK application asks a person. The SDK calls it in two situations. The first is when Claude wants a tool that no permission rule or mode has auto-approved. The second is when Claude calls AskUserQuestion to ask a clarifying question. The callback receives the tool name, the tool's input and a context object. You show those to a person, wait for their decision and return it. For Bash, the input carries command, description and timeout. For Write, it carries file_path and content. Those are the details a reviewer needs to see.

A minimal Python callback: ask the user, then return allow or deny
EN: A minimal Python callback: ask the user, then return allow or deny
async def can_use_tool(tool_name, input_data, context):
    print(f"Claude wants to use {tool_name}")
    approved = await ask_user("Allow this action?")

    if approved:
        return PermissionResultAllow(updated_input=input_data)
    return PermissionResultDeny(message="User declined")

The callback returns one of two results, and each one sends something back to Claude. An allow result carries the input the tool will run with. That can be Claude's original input or a version the person edited. A deny result carries a message. The tool does not run, and Claude reads the message and continues.

Those two shapes support six reviewer actions:

1. Approve: let the tool run as Claude requested. 2. Approve with changes: edit the input before execution, for example to sanitise a path or add a constraint. 3. Approve and remember: send back a rule from the context's suggestions so matching calls skip the prompt next time. 4. Reject: block the tool and tell Claude why. 5. Suggest an alternative: block the call but point Claude towards what the user wants instead. 6. Redirect entirely: use streaming input to send Claude a completely new instruction.

Two wiring details catch people out. If you pass a tools array, include AskUserQuestion in it, or Claude's clarifying questions never reach the callback. In Python, the documented example also registers a dummy PreToolUse hook that returns {"continue_": True}, because that workaround keeps the stream open for can_use_tool. In TypeScript, the context argument also carries an AbortSignal, which lets you cancel a prompt nobody is answering.
