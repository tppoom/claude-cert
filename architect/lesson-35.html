Hallucination is a model producing text that is factually wrong or that contradicts the context it was given, often with full confidence. It comes from the way generation works. A generative model writes its answer one token at a time, choosing what tends to follow what. Nothing in that process checks whether a sentence is true. It only checks whether the sentence fits the pattern. The same mechanism produces fluent summaries and fabricated details, so better fluency does not mean fewer fabrications.

Risk rises with precision. Summarising, reformatting and explaining common ideas sit in the capability zone because the model has seen those patterns many times. Novel or sparse territory is riskier, and so is any task that needs the model to tell what is true from what merely sounds true. A deadline, a statistic or a quotation is easy to write in a plausible shape and hard to get exactly right. Claude can produce quotes that look authoritative and are not grounded in fact. The tone of an answer is no guide either: a confident answer about an obscure topic is not more reliable than a hedged one.

Sampling adds non-determinism. Run the same request for specific facts in two fresh conversations and some details will differ, because each answer is sampled. That variation can also be used to detect hallucination. Best-of-N verification runs the same prompt several times and compares the outputs, and claims that change between runs are the ones to doubt.

Mitigations work on the prompt and on what the answer is grounded in. Making the answer shorter or more assertive does not reduce fabrication. Here is what does:

- Give Claude explicit permission to say it lacks the information, so a gap does not get filled with something plausible. - For long documents (over about 20k tokens), have Claude extract word-for-word quotes first and base its analysis only on those quotes. - Make claims auditable: Claude cites a supporting quote for each claim and removes any claim it cannot support. - Restrict Claude to the documents provided rather than its general knowledge. Telling it to prefer its own memory over the source document invites exactly the invented details you are trying to remove.

Everything a model knows comes from its training data and stops at a knowledge cutoff. Without tools it cannot see anything published after that date and cannot browse in real time. So the useful question is not whether the model knows something but how well that topic was represented in its training data.

Coverage is uneven. Topics that appeared often, consistently and recently (before the cutoff) are in the capability zone. Rare, niche, local, contested and post-cutoff topics are at the edge. A regional regulation revised last year, jargon specific to one industry, or a recent leadership change all sit at the edge, and the model may present an outdated answer as current without mentioning the cutoff.

Web search, retrieval (RAG and MCP connectors) and tool use are the architectural fixes. They give the model information it was never trained on. Retrieval does not remove the need to check, though. An answer drawn from search results is only as good as the sources it used, and the original pages may contain context that the model's synthesis left out.

The context window is the model's working memory. It holds everything the model can refer to for one request: the system prompt, every message including tool results and documents, the tool definitions, and the output being generated, extended thinking included. Anything outside the window does not exist for the model. It also does not learn from your corrections between sessions. A fresh conversation starts from nothing.

There are two failure modes. Context rot is gradual: as more tokens fill the window, accuracy and recall slip. An instruction buried in the middle of a long document is the classic thing to go missing, while the same instruction placed at the top is followed. A bigger window gives you space, not attention, so choosing what goes into context matters as much as how much fits.

The second is the cliff. Once the window is full, behaviour does not degrade gradually: material gets truncated, sometimes without a warning. Chat interfaces may drop the oldest turns on a first-in, first-out basis, so an early constraint in a long conversation can silently vanish. Compaction, memory features, projects, larger windows and multi-agent workflows all push the cliff further out. None of them removes it.

Models tend to agree with the person they are talking to. Give one a question built on a false premise and it may work within that premise instead of challenging it. Ask it to judge your own diagnosis and it may accept your framing too readily. This sycophancy is hard to notice because the agreement feels like confirmation.

Instructions steer a model only partly, and their hold weakens over long conversations. In long-conversation drift, steerability and working memory interact: early instructions lose influence as the context grows, and output wanders from what was asked. Most real failures involve two properties like this at once, and naming both points to the fix.

Misplaced trust is the risk on the user's side. Fluent, agreeable, confident output invites more reliance than it has earned. Claude should never be the single source of truth for high-stakes advice, and users of a search-backed answer should open the cited sources rather than trust the synthesis alone. Design workflows so someone actually checks the output where a wrong answer is costly.

Jailbreaks and prompt injection both try to make Claude ignore its guidelines or your instructions. They differ in where the adversary sits. In a jailbreak or direct prompt injection, the user of your application is the attacker, crafting inputs to bypass your guardrails. In indirect prompt injection, the user is trusted, but Claude reads third-party content on their behalf (a web page, an inbound email, OCR text, a tool result) and that content carries adversarial instructions. Pick the threat model first, because the mitigations do not carry over from one to the other.

When the user is the adversary, the defences sit around the conversation:

- Harmlessness screens: a lightweight model such as Claude Haiku 5.5 classifies user input before it reaches the main conversation, with structured output limiting the answer to a simple verdict. Haiku's own safety classifiers may decline the screening request, so a response with a refusal stop reason should be treated as a harmful verdict. - Input validation: filter for known injection patterns, for example with an LLM screen shown known jailbreak phrasing as examples. - Prompt engineering: a system prompt that states ethical and legal boundaries and tells Claude exactly how to refuse. - Repeat offenders: tell a user who keeps triggering the same refusal that they are breaking usage policy, then throttle or ban them.

Several plausible-sounding moves fail here. Wrapping user messages in tool results borrows a defence from the other threat model. That technique marks third-party content as untrusted, but the jailbreaker is the user, and their messages are the conversation itself. Disabling refusals removes the behaviour the screen relies on. Giving the chatbot broader tools so it can investigate requests raises the damage a successful attack can do, which is the opposite of [least privilege for agents](lesson:5.1).

Prompt-level defences reduce attacks. They do not eliminate them. Claude resists these attacks on its own, and screens, hardened prompts and untrusted-content policies make that resistance stronger. Still, each of those defences is a probability, not a guarantee, and anyone who can put text into an email or a web page your agent reads gets unlimited attempts.

Red-teaming is attacking your own system before someone else does, under both threat models. Plant instructions in a test email, a web page and an uploaded image's OCR text, and see whether the agent acts on them. Write jailbreak attempts against the chatbot and see which ones get past the screen. Each attempt that gets through is a concrete attack case. Those cases become the test set that your [safety and security metrics](lesson:4.1) count, so the success rate is measured, not guessed, and can be re-measured after every prompt or model change.

Designing for breach means asking what an injected instruction could actually do once it gets through. An agent that can only read and summarise leaks nothing when it is fooled. An agent with a send-email tool and access to credentials can exfiltrate them. Permissions decide how much damage a successful injection can do, so the agent should get only the tools and scopes its task needs.

    ในการฉีดทางอ้อม Trust Boundary จะอยู่ระหว่างคำสั่งของคุณ (Prompt ของระบบและคำขอของผู้ใช้) และทุกสิ่งที่ Claude อ่านขณะทำงาน ผู้โจมตีที่ควบคุมอีเมลขาเข้าหรือหน้าเว็บที่ดึงข้อมูลมาหนึ่งหน้าสามารถฝังคำแนะนำที่พยายามเปลี่ยนเส้นทาง Claude ได้ นั่นอาจหมายถึงข้อมูลรั่วไหล การเปิดเผยข้อความแจ้งของระบบ หรือ Tool Call เพื่อส่งข้อมูลไปยังที่ที่ผู้ใช้ไม่เคยร้องขอ ข้อมูลรั่วไหลผ่าน Agent มักจะเกิดขึ้นในลักษณะนี้
  • ▸
    ใส่เนื้อหาของบุคคลที่สามในบล็อก tool_result เท่านั้น อย่าใส่ใน System Prompt หรือในข้อความธรรมดาของผู้ใช้ Claude ได้รับการฝึกอบรมให้ปฏิบัติต่อคําแนะนําภายในผลลัพธ์ของเครื่องมือด้วยความสงสัย การย้ายเนื้อหาอีเมลไปยัง System Prompt จะทําในทางตรงกันข้าม และให้อํานาจเดียวกับคําแนะนําของคุณเองแก่ข้อความของผู้โจมตี 2. ระบุว่าเนื้อหาคืออะไรและมาจากไหน
  • ▸
    ตัวอย่างเช่น “เนื้อหาของอีเมลขาเข้าจากผู้ส่งที่ไม่รู้จัก” ในคําอธิบายของเครื่องมือหรือโครงสร้างของผลลัพธ์ 3. ระบุนโยบายใน System Prompt: เครื่องมือ เอกสาร และเนื้อหาการค้นหาเป็นข้อมูลที่ไม่น่าเชื่อถือ และต้องไม่แทนที่ System Prompt หรือคําขอของผู้ใช้

#7 7. สมมติว่าการโจมตีบางอย่างสำเร็จ: การทดสอบแบบ red-teaming และการออกแบบเพื่อต้านการละเมิด

อ่านเนื้อหา ↗
  • ▸
    การทำ Red-teaming คือการโจมตีระบบของตัวเองก่อนที่คนอื่นจะทำ ภายใต้ทั้งสองรูปแบบของภัยคุกคาม ใส่คำสั่งในอีเมลทดสอบ หน้าเว็บ และข้อความ OCR ของภาพที่อัปโหลด แล้วดูว่า Agent ตอบสนองต่อคำสั่งเหล่านั้นหรือไม่ เขียนความพยายามใน Jailbreak สำหรับแชตบ็อตและดูว่าอันไหนผ่านการกรองได้ แต่ละครั้งที่ผ่านคือกรณีการโจมตีที่เป็นรูปธรรม กรณีเหล่านั้นจะกลายเป็นชุดทดสอบที่ [ตัวชี้วัดความปลอดภัยและความมั่นคงของคุณ](lesson:4.1) นับ
  • ▸
    มาตรการป้องกันแต่ละข้อเป็นเพียงความน่าจะเป็น ไม่ใช่การรับประกัน และใครก็ตามที่สามารถใส่ข้อความลงในอีเมลหรือหน้าเว็บที่ Agent ของคุณอ่านจะมีโอกาสลองไม่จำกัด
  • ▸
    การออกแบบเพื่อฝ่าฝืนหมายถึงการถามว่าคำสั่งแบบแทรกจะทำอะไรได้บ้างเมื่อผ่านพ้นไปแล้ว Agent ที่สามารถอ่านและสรุปได้อย่างเดียวจะไม่รั่วไหลเมื่อถูกหลอก Agent ที่มีเครื่องมือส่งอีเมลและการเข้าถึงข้อมูลรับรองสามารถกรองข้อมูลเหล่านั้นได้ สิทธิ์เป็นตัวกำหนดว่าการฉีดสำเร็จจะสร้างความเสียหายได้มากเพียงใด
