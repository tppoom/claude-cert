กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Shared service identity versus acting on behalf of each user" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Every tool call an agent makes runs under some identity. Often that identity is a single service credential that all users share. Two gaps follow from that choice. Each user gets whatever that credential can reach, not what they personally are allowed to reach. And downstream audit logs show one service account, so nobody can tell which end user caused an action. The safer design is for the agent to act as each user, holding a token issued to that user.

Claude Managed Agents builds this model into vaults. A vault is the collection of credentials for one end user. You register it once and pass its ID when you create a session, so the agent definition stays shared while the credentials change per session. MCP credentials (mcp_oauth, static_bearer) are keyed by mcp_server_url and injected automatically when the agent connects to that server. For mcp_oauth, Anthropic refreshes the access token on your behalf if you supply a refresh block. Credential values are write-only and never returned by the API. In Claude Code, managed MCP configuration supports the same pattern: OAuth or per-user headers let each user authenticate as themselves.

Three runtime rules decide whose identity a call actually uses, and each one can open a gap if you overlook it:

- If no credential matches the server URL, the connection is attempted unauthenticated. It fails only if the server requires authentication, so a server that allows anonymous access will quietly serve anonymous data. - If several vaults hold a matching credential, the first vault with a match wins. Passing a shared vault ahead of a user's vault makes every call run as the shared identity. - In multiagent sessions, vault credentials apply to every thread. Every subagent whose definition declares that server acts as the same user.

2.Keeping credentials outside the agent's boundary

สาระสำคัญและหลักการทำงานของหัวข้อนี้: หัวข้อนี้เจาะลึก Keeping credentials outside the agent's boundary ตามมาตรฐานและพิมพ์เขียวการสอบของ Anthropic โดยมุ่งเน้นการทำความเข้าใจสถาปัตยกรรมเชิงลึก ข้อดีข้อเสียทางเทคนิค และแนวทางการปฏิบัติจริงในโปรดักชัน
⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

On the examFor exfiltration questions, choose controls that hold regardless of what the model decides: no direct network interface, credentials injected outside the boundary, and a TLS-terminating proxy that can inspect traffic. Broad IAM on the agent, proxy environment variables on their own, and trusting the model's judgment all fail once the model is persuaded.

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

Exam trapSetting HTTP_PROXY and HTTPS_PROXY is enough to force all agent traffic through a credential-injecting proxy.Why is that wrong?Some tools ignore the proxy variables, and a proxy that does not terminate TLS cannot see inside requests to inject into them. Remove the agent's network interface and terminate TLS at the proxy.

คำตอบที่ถูกต้อง: ตัวเลือก B

Placeholder substitution only applies to outbound requests. A token that comes back from an exchange lands in the sandbox as a real value, where a prompt-injected instruction could send it out. Doing the exchange yourself and storing the token in the vault keeps it outside the agent's boundary.

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 56771

A security architect is designing an Agent SDK deployment that will process untrusted third-party documents and must prevent credential exfiltration even if a prompt injection convinces the agent to try to send data to an attacker-controlled endpoint. Which combination of controls together address this threat, given that TLS-encrypted traffic through a plain forward proxy cannot be inspected or have credentials injected into it? (Select 3)

A Run the agent in a container with --network none and route all outbound calls through a Unix socket to a proxy on the host, so the agent has no direct network interface at all
B Keep credentials outside the agent's security boundary entirely, injecting them at a proxy so the agent only ever sends requests without the underlying secret
C Deploy a TLS-terminating proxy with its CA certificate trusted in the agent's environment so encrypted HTTPS traffic can be inspected and have credentials injected before re-encryption
D Set HTTP_PROXY and HTTPS_PROXY environment variables alone, since every tool the agent might invoke respects these variables and a standard forward proxy can inject credentials into an encrypted tunnel
E Grant the agent process broad IAM permissions directly so it can reach any downstream service on its own, without depending on any proxy being available or reachable
5 Rely on the model's built-in judgment to avoid contacting suspicious domains instead of enforcing any network-level boundary that would hold regardless of the model's own decisions
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A, B, C
ตัวเลือก A: ถูกต้อง

Correct. Removing the network namespace and forcing all traffic through a Unix socket to a host-side proxy means the agent has no path to reach arbitrary destinations directly, which is the architecture recommended for defense against prompt-injection-driven exfiltration.

ตัวเลือก B: ถูกต้อง

Correct. The proxy pattern keeps the actual credential outside the agent's trust boundary; the agent can make calls but never sees the secret, so even a fully compromised agent process can't leak the credential itself.

ตัวเลือก C: ถูกต้อง

Correct. A plain forward proxy only sees an opaque CONNECT tunnel for HTTPS and cannot modify or inspect its contents; injecting credentials into arbitrary HTTPS services requires terminating TLS at the proxy and having the agent trust its certificate.

ตัวเลือก D: ไม่ถูกต้อง

Not every tool respects HTTP_PROXY/HTTPS_PROXY, and even when they do, a standard forward proxy cannot see or modify HTTPS contents without terminating TLS, so it cannot inject credentials into an encrypted tunnel on its own.

ตัวเลือก E: ไม่ถูกต้อง

Granting broad IAM permissions directly to the agent process is the opposite of least privilege and increases the blast radius of a prompt injection rather than mitigating it.

ตัวเลือก F: ไม่ถูกต้อง

Relying on model judgment alone is not a security boundary; defense in depth requires network-level enforcement that holds even when the model's decision-making is manipulated.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Keeping credentials outside the agent's boundary" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

An agent that reads untrusted content can be prompt-injected. If it holds a secret, an injected instruction can try to send that secret somewhere. The robust fix is to make sure the agent never has the secret. Vault environment-variable credentials work this way. The sandbox holds only an opaque placeholder, which is swapped for the real value at egress, so the agent never sees the secret value. Setting injection_location to header-only narrows this further. Request bodies are often built from content the agent is working with, so the body is the larger exposure surface.

Substitution only applies to requests going out. If a client uses the stored secret to fetch a session token, for example through an OAuth client-credentials grant, the returned token arrives in the sandbox unredacted. For exchange-based flows, perform the exchange yourself and store the resulting token in the vault.

Self-hosted Agent SDK deployments get the same property from a proxy outside the agent's container. Run the container with --network none, which removes every network interface, and mount a Unix socket connected to a proxy on the host. The proxy injects credentials, enforces an endpoint allowlist and logs every request. The agent sees only the tool interface. A prompt-injected request to an attacker's domain then has no network path except through a proxy that refuses it.

Two details decide whether the proxy actually works. First, injecting a credential into HTTPS traffic means the proxy has to read the request, so it must terminate TLS, for example with mitmproxy. The proxy's CA certificate then goes into the agent's trust store. A plain forward proxy only relays the encrypted tunnel and can neither inspect nor inject. Second, setting HTTP_PROXY/HTTPS_PROXY on its own is not a boundary, because not every tool reads those variables: plain ssh and most database drivers ignore them. Removing the network interface enforces the boundary whatever the tool does. Give the agent's service account minimal IAM permissions, not broad ones, and route sensitive access through the proxy where possible.

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 56768

While auditing an Agent SDK integration, you find allowed_tools=["Read", "Glob", "Grep", "Bash"] combined with permission_mode="bypassPermissions", and a canUseTool callback that logs every request and denies anything touching a credentials directory. The developer believed this callback was their safety net. What should the audit conclude?

A The callback is shadowed: calls approved earlier in the order, including everything bypassPermissions approves, never reach canUseTool; a PreToolUse hook is needed if every call must be checked
B The callback is functioning as intended, because bypassPermissions only affects tools not already listed in allowed_tools, and Bash was never explicitly allowed so it still reaches the callback
C The callback is functioning as intended, because canUseTool is always invoked first in the order, before permission mode or allow rules are ever considered
D The callback is shadowed only for MCP tools with the requiresUserInteraction metadata flag, while ordinary built-in tools like Bash still reach the callback as expected
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. The SDK evaluates hooks, then deny rules, then ask rules, then permission mode, then allow rules, and only then calls canUseTool. With bypassPermissions set, the mode step approves every call that reaches it, so Bash and everything else never falls through to the callback. A logic check that must run on every call belongs in a PreToolUse hook instead, since hooks run first and a hook deny applies even in bypassPermissions mode.

ตัวเลือก B: ไม่ถูกต้อง

bypassPermissions is not scoped only to unlisted tools; it approves every call that reaches the permission-mode step, listed or not, so Bash calls are approved before the callback is ever consulted.

ตัวเลือก C: ไม่ถูกต้อง

This reverses the evaluation order. Hooks, deny rules, ask rules, and permission mode are all checked before allow rules and canUseTool, so canUseTool is one of the last steps, not the first.

ตัวเลือก D: ไม่ถูกต้อง

The requiresUserInteraction exception applies to AskUserQuestion and specially annotated MCP tools, but it does not change the outcome for the ordinary built-in tools in this scenario, which are fully shadowed by bypassPermissions regardless of that flag.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Which permission layer actually decides a tool call" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Credentials control what the agent can reach. The Agent SDK's permission flow controls which calls it actually makes. The flow is a fixed sequence, and the first step that resolves a call ends the evaluation. A security control placed late in the sequence only sees calls that no earlier step settled.

The sequence explains a common audit finding. A team sets permission_mode="bypassPermissions" and adds a canUseTool callback that logs requests and denies anything touching a credentials directory. The callback almost never runs. It is invoked only when the flow falls through to a prompt, and calls auto-approved by allowedTools, allow rules or the permission mode never reach it. The deny logic is skipped, and the audit log is missing most of the calls. A control that must see every call belongs in a hook, because hooks run first and their decisions hold in every mode.

Under bypassPermissions, the steps that run before the mode check still apply. Deny rules, explicit ask rules and hooks all still work: a hook's deny is enforced, and an ask rule still sends the call to canUseTool. disallowed_tools still has teeth too. A bare name such as "Bash" removes the tool from the request entirely, so Claude cannot even attempt it, and a scoped rule such as "Bash(rm *)" denies matching calls in every mode. allowed_tools, on the other hand, gives no protection here: it lists tools to auto-approve and does not restrict Claude to only these tools. Nor is plan mode a variant of bypass. In plan mode, file-edit and shell-write calls go to canUseTool regardless of allow rules.

Tool reach is an authorization question too. An agent that can load any MCP server can call tools no one has reviewed, so the gap is closed by deciding which servers and tools exist at all, through [controlling MCP servers, plugins and hooks through policy](lesson:7.1). At the SDK and settings level, one deny rule removes every MCP tool, across all servers, until specific ones are approved.
