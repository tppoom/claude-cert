1. Shared service identity versus acting on behalf of each user

Every tool call an agent makes runs under some identity

Often that identity is a single service credential that all users share

Two gaps follow from that choice Each user gets whatever that credential can reach, not what they personally are allowed to reach

And downstream audit logs show one service account, so nobody can tell which end user caused an action

The safer design is for the agent to act as each user, holding a token issued to that user.

Claude Managed Agents สร้างโมเดลนี้ให้เป็นห้องนิรภัย ห้องนิรภัยคือการรวบรวมข้อมูลประจำตัวสำหรับผู้ใช้ปลายทางรายเดียว คุณลงทะเบียนเพียงครั้งเดียวและส่ง ID ของมัน

Attaching one end user's vault to a session
EN: Attaching one end user's vault to a session
session = client.beta.sessions.create(
    agent=agent.id,
    environment_id=environment.id,
    vault_ids=[vault.id],
    title="Alice's Slack digest",
)

กฎรันไทม์สามกฎจะตัดสินว่าการโทรใช้ข้อมูลประจำตัวของใคร และแต่ละกฎสามารถเปิดช่องว่างได้หากคุณมองข้าม:

  • ▸
    If no credential matches the server URL, the connection is attempted unauthenticated. It fails only if the server requires authentication, so a server that allows anonymous access will quietly serve anonymous data.
  • ▸
    If several vaults hold a matching credential, the first vault with a match wins. Passing a shared vault ahead of a user's vault makes every call run as the shared identity.
  • ▸
    In multiagent sessions, vault credentials apply to every thread. Every subagent whose definition declares that server acts as the same user.

A session is created with vault_ids=[team_shared_vault.id, alice_vault.id]. Both vaults hold an mcp_oauth credential for https://mcp.slack.com/mcp. Whose identity do the agent's Slack MCP calls use?

🇹🇭 คำแปลโจทย์: เซสชันถูกสร้างขึ้นด้วย vault_ids=[team_shared_vault.id, alice_vault.id] ห้องนิรภัยทั้งสองมีข้อมูลรับรอง mcp_oauth สำหรับ https://mcp.slack.com/mcp การเรียก Slack MCP ของตัวแทนใช้ข้อมูลระบุตัวตนของใคร

Every tool call an agent makes runs under some identity. Often that identity is a single service credential that all users share. Two gaps follow from that choice. Each user gets whatever that credential can reach, not what they personally are allowed to reach. And downstream audit logs show one service account, so nobody can tell which end user caused an action. The safer design is for the agent to act as each user, holding a token issued to that user.

Claude Managed Agents builds this model into vaults. A vault is the collection of credentials for one end user. You register it once and pass its ID when you create a session, so the agent definition stays shared while the credentials change per session. MCP credentials (mcp_oauth, static_bearer) are keyed by mcp_server_url and injected automatically when the agent connects to that server. For mcp_oauth, Anthropic refreshes the access token on your behalf if you supply a refresh block. Credential values are write-only and never returned by the API. In Claude Code, managed MCP configuration supports the same pattern: OAuth or per-user headers let each user authenticate as themselves.

Three runtime rules decide whose identity a call actually uses, and each one can open a gap if you overlook it:

- If no credential matches the server URL, the connection is attempted unauthenticated. It fails only if the server requires authentication, so a server that allows anonymous access will quietly serve anonymous data. - If several vaults hold a matching credential, the first vault with a match wins. Passing a shared vault ahead of a user's vault makes every call run as the shared identity. - In multiagent sessions, vault credentials apply to every thread. Every subagent whose definition declares that server acts as the same user.

Credentials control what the agent can reach. The Agent SDK's permission flow controls which calls it actually makes. The flow is a fixed sequence, and the first step that resolves a call ends the evaluation. A security control placed late in the sequence only sees calls that no earlier step settled.

The sequence explains a common audit finding. A team sets permission_mode="bypassPermissions" and adds a canUseTool callback that logs requests and denies anything touching a credentials directory. The callback almost never runs. It is invoked only when the flow falls through to a prompt, and calls auto-approved by allowedTools, allow rules or the permission mode never reach it. The deny logic is skipped, and the audit log is missing most of the calls. A control that must see every call belongs in a hook, because hooks run first and their decisions hold in every mode.

Under bypassPermissions, the steps that run before the mode check still apply. Deny rules, explicit ask rules and hooks all still work: a hook's deny is enforced, and an ask rule still sends the call to canUseTool. disallowed_tools still has teeth too. A bare name such as "Bash" removes the tool from the request entirely, so Claude cannot even attempt it, and a scoped rule such as "Bash(rm *)" denies matching calls in every mode. allowed_tools, on the other hand, gives no protection here: it lists tools to auto-approve and does not restrict Claude to only these tools. Nor is plan mode a variant of bypass. In plan mode, file-edit and shell-write calls go to canUseTool regardless of allow rules.

Tool reach is an authorization question too. An agent that can load any MCP server can call tools no one has reviewed, so the gap is closed by deciding which servers and tools exist at all, through [controlling MCP servers, plugins and hooks through policy](lesson:7.1). At the SDK and settings level, one deny rule removes every MCP tool, across all servers, until specific ones are approved.
