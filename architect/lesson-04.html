💡 แนวคิดหลักสำคัญ (Key Concept)

Isolated subagent context — Subagent ทำงานใน Conversation ของตัวเอง การอ่านข้อมูลและการเรียก Tool ทั้งหมดจะจำกัดอยู่แค่ในนั้น โดย Coordinator จะได้รับเฉพาะ Final message กลับมา การแยก Context นี้คือเหตุผลหลักในการกระจายงานข้าม Agent และเป็นสาเหตุที่ Subagent ต้องได้ Brief ที่ครบถ้วน เพราะมันไม่สามารถเข้าถึงสิ่งที่ Coordinator รู้ได้เลย

📑 หัวข้อในบทเรียนนี้ (In this lesson)
  • ▸1. เริ่มต้นด้วย Agent เดียวเสมอ และแยก Agent เมื่อมีเหตุผลที่ชัดเจนเท่านั้น
  • ▸2. Coordinator Pattern และ Context ที่แยกขาดของ Subagent
  • ▸3. การทำ Fan-out ให้ Subagents ที่เป็นอิสระต่อกันทำงานแบบ Parallel
  • ▸4. การ Brief งานให้ Subagent ที่ไม่เห็น Context เดิม

1. เริ่มต้นด้วย Agent เดียวเสมอ และแยก Agent เมื่อมีเหตุผลที่ชัดเจนเท่านั้น

ระบบ Multi-agent คือการรัน Claude หลาย Instance พร้อมกัน โดยแต่ละตัวมี Conversation Context ของตัวเอง และทำงานร่วมกันเพื่อจบงานชิ้นเดียว คำถามสำคัญเชิง Design ไม่ใช่ "สร้างอย่างไร" แต่เป็น "ควรสร้างหรือไม่" จากสถิติของ Anthropic พบว่าหลายทีมนำ Multi-agent ไปใช้ในโจทย์ที่ Single Agent ทำงานได้มีประสิทธิภาพมากกว่า บางทีมเสียเวลาทำ Architecture ซับซ้อนหลายเดือน ทั้งที่ปรับ Prompt ของ Agent เดียวให้ดีขึ้นก็ได้ผลลัพธ์เท่ากัน

การแยก Agent มีต้นทุนเสมอ Agent เพิ่มขึ้นหนึ่งตัว หมายถึงจุดล้มเหลว (Point of Failure) เพิ่มขึ้นหนึ่งจุด, ต้องดูแล Prompt เพิ่มขึ้น และเป็นอีกหนึ่งจุดที่อาจเกิดพฤติกรรมคาดไม่ถึง ในการทดสอบของ Anthropic พบว่า Multi-agent ใช้ Token เปลืองกว่า Single Agent ในโจทย์เดียวกันถึง 3–10 เท่า โดย Token ส่วนเกินเกิดจาก 3 ส่วน: Context ที่ซ้ำซ้อนระหว่าง Agent, ข้อความที่ใช้คุย Coordinate ระหว่างกัน และข้อความสรุป (Summary) ที่ต้องสร้างทุกครั้งที่ส่งต่องาน (Handoff) สำหรับ Claude Managed Agents แพลตฟอร์มการจัดการ Multi-agent Orchestration ภายใน Session เดียว ก็สะท้อนหลักการนี้ในเชิง Configuration กล่าวคือ Agent สามารถสร้าง Dynamic Workflow ซึ่งรันหลาย Agent เบื้องหลังแล้วรวมผลลัพธ์ ทุก Agent ที่รันจะผลาญ Token ดังนั้นระบบจึงบังคับให้ตั้ง Session Budget เพื่อจำกัด Cost รวมสูงสุดของทั้ง Session และ Workflow นั้น

A research task that took one agent 10 minutes is split across five parallel subagents. What usually happens?

คำแปลโจทย์:
งานวิจัยที่ใช้เวลาหนึ่ง Subagents 10 นาทีจะถูกแบ่งออกเป็น Subagents คู่ขนาน 5 คน โดยปกติจะเกิดอะไรขึ้น?
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Official Explanation (คำอธิบายเฉลย):

Parallel agents buy thoroughness. Each one needs its own context, and they have to coordinate, so total computation rises and wall-clock time often rises with it.

คำแปลไทย:
  • ▸
    Agent คู่ขนานซื้อความทั่วถึง แต่ละคนต้องการบริบทของตัวเอง และต้องประสานงาน
  • ▸
    ดังนั้นการคำนวณทั้งหมดจึงเพิ่มขึ้นและเวลานาฬิกาแขวนมักจะเพิ่มขึ้นตามไปด้วย
““The primary benefit of parallelization is thoroughness, not speed.””
คำแปล: “ประโยชน์หลักของการทำให้เป็นคู่ขนานคือความทั่วถึง ไม่ใช่ความเร็ว”

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
On the Exam:: When an answer proposes separate planner, implementer, tester and reviewer agents for one feature, it is splitting by role, which is usually the wrong choice. The agent that builds a feature should also write its tests, because it already has the context. Split only where context can be truly isolated.

ข้อสอบเสนอให้แยก Agent ตาม Role สำหรับ Feature เดียว (Planner, Implementer, Tester, Reviewer)? (ทำไมถึงผิด): ไม่จริง: การแบ่งตาม Role คือการออกแบบที่ผิด เพราะสูญเสีย Context ในทุกจุด Handoff Agent ที่สร้าง Feature นั้นควรเป็นตัวที่เขียน Tests เองด้วยเนื่องจากถือ Context ไว้อยู่แล้ว ให้แยก Agent เฉพาะเมื่อ Context ตัดขาดกันได้อย่างแท้จริงเท่านั้น

หน้าที่ของ Coordinator ในการแตกงานออกเป็นส่วนย่อยแบบ Runtime คือรูปแบบ [Orchestrator-workers (dynamic decomposition)](lesson:1.5) และในระบบ Multi-agent ตัว Orchestrator ก็จะกลายเป็น Coordinator Agent ที่แจกจ่ายงานแต่ละชิ้นไปยัง Subagent จริงๆ ที่มี Context Window แยกต่างหากเป็นของตัวเอง

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
Splitting a task across parallel agents makes it finish faster and cost less. (ทำไมถึงผิด): Multi-agent systems typically use 3-10x more tokens than one agent, and they often take longer overall because there is far more total computation. What they buy is thoroughness. The cleanest design gives each type of work its own agent: planner, implementer, tester and reviewer. (ทำไมถึงผิด): Splitting by role loses context at every handoff. Divide work by context boundaries instead, so the agent that writes a feature also writes its tests.

การแยก Task ให้หลาย Agent รันคู่ขนานกัน ทำให้งานเสร็จเร็วขึ้นและประหยัด Cost กว่า? (ทำไมถึงผิด): ไม่จริง: Multi-agent ใช้ Token เปลืองกว่า Agent เดี่ยว 3–10 เท่า และมักใช้เวลาโดยรวมนานกว่าเพราะมีการคำนวณมหาศาล สิ่งที่ได้กลับมาคือความละเอียดถี่ถ้วน (Thoroughness) ไม่ใช่ความเร็วหรือการประหยัด Cost | การออกแบบที่สะอาดที่สุดคือการแยก Agent ตามประเภทของงาน: Planner, Implementer, Tester, Reviewer? (ทำไมถึงผิด): ไม่จริง: การแยกตาม Role ทำให้ Context สูญหายทุกครั้งที่ Handoff ควรแบ่งงานตาม Context Boundaries เพื่อให้ Agent ตัวที่เขียน Feature เป็นตัวเขียน Tests ไปด้วยในตัว

A multi-agent system runs several Claude instances, each with its own conversation context, and coordinates them to finish one piece of work. The design question is not how to build one. It is whether you should. Anthropic sees teams use multi-agent systems in situations where a single agent would do better. Some spend months on elaborate architectures, only to find that better prompting of one agent got the same results.

Splitting has a price. Each extra agent is another place to fail, another prompt to maintain and another source of unexpected behaviour. In Anthropic's testing, multi-agent implementations typically used 3-10x more tokens than a single agent on the same task. The extra tokens come from three places: context duplicated across agents, coordination messages between agents, and summaries written for each handoff. Claude Managed Agents, a platform whose multiagent orchestration lets one agent coordinate others within a single session, makes the same point in configuration terms. There, an agent can write a dynamic workflow: a program that runs many agents in the background and combines their results. Every agent in such a run consumes tokens, so you set a session budget, a cap on the session's total spend that includes its workflow runs.

Three situations reliably pay back that cost. Outside them, coordination usually costs more than it saves. The Managed Agents documentation describes the same territory: work spread across many surfaces, or several well-scoped tasks that feed one goal.

Once you decide to split, draw the boundaries around context, not around the type of work. Splitting by role creates a "telephone game": a planner hands to an implementer, who hands to a tester, who hands to a reviewer, and every handoff loses detail. The tester doesn't know why the code was written the way it was. In one experiment with role-specialised agents, the agents spent more tokens coordinating than doing the work. Good boundaries include independent research paths (Asia versus Europe market trends), components with a clean API contract, and black-box verification that only runs tests. Bad boundaries include sequential phases of the same feature, tightly coupled components, and work that depends on shared state.

The coordinator's job of breaking work into pieces at runtime is the [Orchestrator-workers (dynamic decomposition)](lesson:1.5) pattern. In a multi-agent system, that orchestrator becomes a coordinator agent that hands each piece to a real subagent with its own context window.

2. Coordinator Pattern และ Context ที่แยกขาดของ Subagent

ใน Coordinator Pattern ตัว Lead Agent จะวางแผนงาน ส่งต่องานย่อยให้ Subagents แล้วรวมผลลัพธ์เข้าด้วยกัน หัวใจสำคัญที่ทำให้รูปแบบนี้มีประโยชน์คือ ความเป็นอิสระ (Isolation) ของ Context โดย Subagent แต่ละตัวจะเริ่มบทสนทนาใหม่เสมอ Tool Calls และผลลัพธ์ระหว่างทางจะอยู่ภายใน Subagent เท่านั้น จะมีเพียง Final Message สรุปสุดท้ายเท่านั้นที่ส่งกลับไปยัง Parent Agent เช่น Research Subagent สามารถอ่านเอกสารหลายสิบไฟล์ได้โดยที่เนื้อหาเหล่านั้นไม่เข้าไปรกใน Main Conversation เลย Parent Agent จะได้รับเพียง Summary สั้นๆ ไม่ใช่เนื้อหาทุกไฟล์ที่ Subagent อ่าน

ระบบ Support Agent สะท้อนความสำคัญเรื่องนี้ได้ชัดเจน หากทุกครั้งที่มีการค้นหาคำสั่งซื้อ ประวัติ Order History ขนาดยาวหลายพัน Tokens จะถูกเทลง Context ทำให้ความสามารถในการ Reasoning ปัญหาทางเทคนิคของลูกค้าร่วงลงทันที แต่ถ้าแยกการค้นหานี้ให้เป็น Subagent ตัว Main Agent จะได้รับผลลัพธ์สรุปเพียง 50–100 Tokens (เช่น สถานะและวันที่) ทำให้ Context หลักยังคงสะอาดและโฟกัสตรงจุด Isolation จะมีประสิทธิภาพสูงสุด เมื่อ Subtask มีข้อมูลส่วนเกินเยอะที่งานหลักไม่ได้ใช้ และมีเกณฑ์ที่ชัดเจนว่าต้องการสกัดข้อมูลอะไรกลับมา

Isolation เกิดขึ้นกับ Conversation เท่านั้น ไม่ได้จำกัดกับ Environment ใน Managed Agents ทุก Agent ใน Session จะแชร์ Sandbox, Filesystem และ Vault Credentials ร่วมกัน โดยแต่ละตัวจะรันอยู่บน Session Thread ของตัวเอง ซึ่งเป็น Event Stream ที่เก็บ Conversation History แยกกัน Subagent Thread ใน Managed Agents จะยังคงอยู่ Coordinator จึงสามารถส่งคำถาม Follow-up ซ้ำได้โดยที่ Subagent ยังจำประวัติการคุยในรอบก่อนหน้าได้

Subagent คือ Tool ที่เหมาะสม สำหรับ Side Task ที่ต้องการแยก Working Material ไม่ให้เข้าไปปนใน Main Conversation ส่วน Agent Team (Teammate) คืออีกรูปแบบหนึ่ง: เป็นการรันหลาย Session คู่ขนานที่แชร์ Task List และคุยแลกเปลี่ยน Message กัน เหมาะกับการซิงค์งานระหว่าง Worker หลายตัว ไม่ใช่การซ่อนข้อมูล Investigation ของงานเดี่ยว และ Scripted Workflow จะเหมาะกับสเกลงานที่ใหญ่เกินกว่าจะคุมด้วย Subagent ไม่กี่ตัว ทั้งนี้ ไม่มีรูปแบบใดที่เป็นกลไกการมาตามตัด Transcript ย้อนหลัง เพราะพฤติกรรมการส่งกลับเฉพาะ Summary เป็นคุณสมบัติเฉพาะตัวของ Subagent เองตั้งแต่แรก

In the coordinator pattern, one lead agent plans the work, sends each piece to a subagent, and puts the results together. What makes this useful is isolation. Each subagent starts with a fresh conversation, its intermediate tool calls and results stay inside it, and only its final message goes back to the parent. A research subagent can read dozens of files without any of that content building up in the main conversation. The parent receives a short summary, not every file the subagent read.

A support agent shows why this matters. If every order lookup puts thousands of tokens of order history into context, the agent reasons worse about the customer's technical problem. Move the lookup into its own agent, and the main agent gets back 50-100 tokens of order status and date while its context stays focused. Isolation works best when the subtask produces a lot of material that the main task mostly doesn't need, and when there are clear criteria for what to extract.

Isolation applies to the conversation, not to the environment. In Managed Agents, all agents in a session share the same sandbox, filesystem and vault credentials. Each one runs in its own session thread, an event stream with its own conversation history. A Managed Agents subagent's thread also stays available, so the coordinator can send it follow-up questions and the subagent remembers its earlier turns.

A subagent is the right tool for one side task whose working material you want kept out of the main conversation. An agent-team teammate is a different arrangement: it is one of several coordinated sessions that share a task list and send each other messages, so it suits keeping many workers in sync, not hiding one investigation. A scripted workflow suits a job too large for a handful of subagents. None of these is a mechanism for trimming the transcript after the fact. The summary-only return is a property of the subagent itself.

  • •

  • •

  • •
    Tools: กำหนด Scope ของ Tools ขั้นต่ำที่จำเป็นในระดับ Definition ของ Subagent
  • •
    Boundaries: ขอบเขตและข้อห้ามว่าสิ่งใดห้ามแตะต้อง และเงื่อนไขที่ต้องหยุดทำงาน

Specialised Subagent จะเก่งได้เท่ากับ Instructions ที่มันได้รับ แนวทาง Prompt Engineering สำหรับ Single Agent จึงต้องนำมาใช้กับ System Prompt ของ Subagent ทุกตัวเช่นกัน รวมถึงต้องเขียน Description ใน Definition อย่างประณีต เพราะ Coordinator จะอ่าน Description นี้เพื่อตัดสินใจเลือกเรียก Subagent หากเขียนไม่ชัดเจนจนแยกความต่างของ Subagents สองตัวไม่ออก Task จะถูกส่งไปผิดตัวทันที (Misrouted)

การกำหนด Tools Scope คือหัวใจสำคัญของ Brief ในระบบ Multi-agent Design คุณควรเซ็ตรายการ Tools ลงใน Definition ของ Specialist แต่ละตัวโดยตรง เช่น Doc-reviewer ที่มีหน้าที่แค่วิเคราะห์ Documentation แต่ต้องไม่แก้ไขไฟล์ ควรได้รับสิทธิ์เฉพาะ Read และ Grep เท่านั้น โดยตัด Edit, Write หรือ Bash ออก วิธีนี้จะป้องกัน Accidental Modification ได้อย่างเด็ดขาดในระดับ System Permission การละเว้นไม่ระบุ Tools ไม่ใช่ Safe Default เพราะหากไม่กำหนด Subagent จะ Inherit สิทธิ์ Tools ทุกตัวที่มีอยู่ในระบบมาทันที

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
Leaving the tools field off a subagent definition keeps it limited and safe. (ทำไมถึงผิด): Omitting tools gives the subagent every tool available to subagents. To keep a reviewer read-only, list only Read and Grep.

(ทำไมถึงผิด): ไม่จริง: การละเว้นฟิลด์ tools จะทำให้ Subagent ได้รับ Tools ทุกตัวที่มีในระบบมาใช้งานโดยปริยาย (Inherit All Tools) หากต้องการให้เป็น Read-only ต้องระบุเฉพาะ Tools ที่จำเป็นอย่างชัดเจน เช่น Read และ Grep

คำแปลโจทย์:
ในช่วงกลางของเซสชัน ผู้ประสานงานจะมอบหมายคําสั่งสั้นๆ ว่า “ตรวจสอบเอกสารที่เราได้พูดคุยและทําเครื่องหมายว่าล้าสมัยแล้ว” คําจํากัดความของผู้ตรวจสอบเอกสารมีคําอธิบายและ Prompt แต่ไม่มีช่องเครื่องมือ การประเมินใดที่ถูกต้อง
คำตอบที่ถูกต้อง: ตัวเลือก C
💡 Official Explanation (คำอธิบายเฉลย):

A subagent knows only its own system prompt, project-level context and the task message, so the brief has to name the docs and the output it wants. Omitting tools isn't a safe default: the subagent inherits every tool available to subagents. Listing only Read and Grep makes changes impossible, while a prompt instruction only discourages them.

Isolation cuts both ways. A subagent doesn't see the coordinator's turns: not the user's request, the files already read, or decisions already made. It knows only its own system prompt, project-level context such as CLAUDE.md, and the task message it is given. If the coordinator writes "now check the other module", the subagent has no idea which module, what to look for, or what form the answer should take. Every brief has to stand on its own.

A self-contained brief has four parts:

- Objective: the specific question or task, stated with any facts from the coordinator's context that the subagent needs. - Output format: exactly what to return. Isolation works best when the subtask has clear criteria for what to extract, because the subagent's final message is all the coordinator will see. - Tools: the minimum set the job needs, set on the subagent's definition. - Boundaries: what the subagent must not touch and when it should stop.

A specialised subagent is only as good as its instructions. The prompt-engineering practices that improve a single agent apply to every subagent's system prompt. Write the definition's description with the same care. The coordinator reads it to decide when to call that subagent, and if it can't tell two subagents apart, requests get misrouted.

Scoping tools is part of the brief, and how you restrict tools in general is covered in [Scoping tools per agent and matching the remedy to the pressure](lesson:3.1). In a multi-agent design, set the tools list on each specialist's definition. A doc-reviewer that should analyse documentation but never change it gets Read and Grep and nothing else, with no Edit, Write or Bash. That makes accidental modification impossible rather than merely discouraged. Leaving tools out is not a cautious default. If you omit it, the subagent inherits every tool available to subagents.
