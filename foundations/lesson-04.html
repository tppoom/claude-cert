💡 แนวคิดหลักสำคัญ (Key Concept)

1. รูปแบบ Workflow ทั้ง 5 แบบ และจังหวะที่ควรเปลี่ยนไปใช้ Agent

เริ่มจากดีไซน์ที่เรียบง่ายที่สุดก่อนเสมอ และเพิ่ม Structure เข้ามาก็ต่อเมื่อผลลัพธ์ที่วัดผลได้คุ้มค่ากับการลงทุนเท่านั้น ระบบที่เป็น Agentic มักจะต้องแลก Latency และ Cost ที่สูงขึ้นเพื่อให้ได้ประสิทธิภาพงานที่ดีกว่า สำหรับหลายๆ Use case การยิง LLM แค่ครั้งเดียว (Single Call) พร้อม Retrieval และตัวอย่าง (Few-shot) ที่ดีก็เพียงพอแล้ว แต่ถ้าเอาไม่อยู่ เรามี Workflow มาตรฐานอยู่ 5 รูปแบบ ซึ่งแต่ละแบบ Code ของคุณจะเป็นตัวกำหนด Flow ที่แน่นอน และให้ Model จัดการประมวลผลงานในแต่ละ Step

Prompt chaining
A fixed sequence of calls. Each call works on the previous output, and code checks can gate between steps
ยิง Call ตามลำดับแบบตายตัว แต่ละ Call รับ Output จากขั้นตอนก่อนหน้า โดยใช้ Logic ใน Code คอยตรวจสอบระหว่างทางได้
The task splits cleanly into known steps, such as drafting copy and then translating it
งานสามารถแบ่งเป็นลำดับขั้นตอนที่ชัดเจนได้ เช่น ร่างข้อความเสร็จแล้วจึงนำไปแปลภาษา
Routing
A classifier call sends each input to a specialised prompt or model
ใช้ Call หนึ่งเป็น Classifier เพื่อคัดแยกและส่ง Input ไปยัง Prompt หรือ Model ที่เฉพาะทาง
Inputs fall into distinct categories that are better handled separately, such as easy questions sent to a smaller model
Input แบ่งเป็นหมวดหมู่ชัดเจนและจัดการแยกกันได้ดีกว่า เช่น ส่งคำถามง่ายๆ ไปให้ Model ตัวเล็กจัดการ
Parallelization
Sectioning (independent subtasks run at once) or voting (the same task run several times)
แบ่งเป็น Sectioning (รัน Subtasks ที่ไม่ขึ้นต่อกันพร้อมกัน) หรือ Voting (รัน Task เดิมซ้ำกันหลายครั้ง)
Subtasks are independent and speed matters, or you need several attempts for higher confidence
Subtasks แยกอิสระจากกันและเน้น Speed หรือต้องการรันหลายรอบเพื่อเพิ่ม Confidence ของผลลัพธ์
Orchestrator-workers
A central LLM breaks the task down at runtime, hands parts to workers, and combines their results
มี LLM ตัวกลางคอยแตก Task ย่อยที่ Runtime แล้วส่งให้ Worker ทำงาน ก่อนจะนำผลลัพธ์มารวมกัน
You can't predict the subtasks in advance, such as code changes across an unknown number of files
ไม่สามารถคาดเดา Subtasks ล่วงหน้าได้ เช่น การแก้ Code ที่ไม่รู้จำนวนไฟล์ที่แน่นอน
Evaluator-optimizer
One call generates, another evaluates and gives feedback, and the loop repeats
Call แรกทำหน้าที่ Generate ส่วนอีก Call ทำหน้าที่ Evaluate พร้อมให้ Feedback แล้ววน Loop ปรับปรุง
There are clear evaluation criteria and refining the output measurably improves it
มีเกณฑ์การประเมิน (Evaluation Criteria) ที่ชัดเจน และการ Refine ผลลัพธ์ช่วยเพิ่มคุณภาพงานได้อย่างวัดผลได้
Autonomous agent
The model chooses its own tool calls in a loop, guided by feedback from its environment
Model เลือกใช้ Tool ได้เองใน Loop โดยมี Feedback จากสภาพแวดล้อม (Environment) คอยชี้นำ
The number of steps is open-ended and each step can be checked against reality, such as by re-running tests
จำนวน Step ไม่ตายตัว (Open-ended) และแต่ละ Step สามารถตรวจวัดผลกับความเป็นจริงได้ เช่น การรัน Test ซ้ำเพื่อเช็กผล

ทั้ง Parallelization และ Orchestrator-workers ต่างก็แบ่งงานเหมือนกัน จึงเป็นคู่ที่คนสอบสับสนบ่อยที่สุด: ใน Sectioning ตัว Subtasks จะถูก Fix ไว้ใน Code ตั้งแต่ก่อนรัน แต่ใน Orchestrator-workers ตัว Model จะเป็นผู้กำหนด Subtasks เองที่ Runtime ส่วน Voting จะต่างออกไป คือการรัน Task เดิมซ้ำหลายครั้ง เช่น ใช้หลาย Prompt ตรวจสอบช่องโหว่ของ Code ชุดเดียวกันแล้วนำ Verdict มารวมกัน นอกจากนี้ การรันแบบขนานยังช่วยลด Wall-clock Time ลง เพราะ Subagents ที่รันพร้อมกันจะเสร็จเมื่อตัวที่ช้าที่สุดเสร็จ ไม่ใช่ผลรวมเวลาของทุกตัวบวกกัน

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
A complex multi-step task always calls for an autonomous agent. (ทำไมถึงผิด): Start simple and add complexity only when it is needed. A fixed workflow, or even a single call, often wins on cost and predictability. Agents fit when the steps can't be predicted.

งานที่ซับซ้อนและมีหลายขั้นตอน จำเป็นต้องใช้ Autonomous Agent เสมอไปหรือไม่? (ทำไมถึงผิด): ไม่จริง: ควรเริ่มจากระบบที่เรียบง่ายที่สุดก่อน และเพิ่มความซับซ้อนเมื่อจำเป็นเท่านั้น Fixed Workflow หรือแม้แต่ Single LLM Call มักจะชนะเรื่อง Cost และความสามารถในการคาดเดา (Predictability) Agent จะเหมาะสมก็ต่อเมื่อไม่สามารถคาดเดาจำนวนและลำดับขั้นตอนล่วงหน้าได้เท่านั้น

คำแปลไทย:
งานเดียวกันจะดำเนินการหลาย ๆ ครั้งในแบบคู่ขนานและเอาต์พุตจะถูกรวมเข้าด้วยกัน ซึ่งเป็นรูปแบบการลงคะแนนของ Parallelization (การประมวลผลคู่ขนาน) ไม่มี Orchestrator ตัดสินใจงานย่อยขณะรันไทม์

Start with the simplest design and add structure only when a measured gain pays for it. Agentic systems usually trade latency and cost for better task performance. For many applications, a single well-prompted LLM call with retrieval and a few examples is enough. When it isn't, there are five standard workflow shapes. In each one your code fixes the path, and the model does the work at each step.

Parallelization and orchestrator-workers both split work, and they are the pair candidates confuse most often. In sectioning, the subtasks are fixed in code before the run starts. In orchestrator-workers, the model decides the subtasks at runtime. Voting is a different case: it runs the same task several times, such as several prompts each reviewing code for vulnerabilities, and combines the verdicts. Running the parts at the same time also cuts wall-clock time, because concurrent subagents finish when the slowest one finishes, not after the sum of all of them.

Every agent runs the same cycle: Claude asks for a tool, the tool runs, and the result goes back to Claude. That cycle is covered in [the tool-use (agentic) loop](lesson:8.1). The design choice is who drives it. The answer decides what your code is responsible for and how much of the cycle you can see.

Whoever drives the loop decides what to do next by reading the stop_reason on each API response, which reports why Claude stopped generating. "tool_use" means Claude wants a client tool run, and "end_turn" means it produced a final answer; "max_tokens", "stop_sequence", and "refusal" are other stops your code has to handle. "pause_turn" belongs to server tools: their internal loop has an iteration limit, and when it is reached before the work is done the response comes back paused. Re-sending the conversation, including the paused response, lets Claude continue where it left off.

With the Agent SDK, the loop runs inside the library. Claude responds, the SDK runs each requested tool, the results go back to Claude, and the cycle repeats until a response contains no tool calls. Then the SDK yields a ResultMessage with the final text, token usage, cost, and session ID. Your code watches the message stream instead of building requests.

Agent frameworks such as the Claude Agent SDK, Strands Agents SDK by AWS, LangGraph, and PydanticAI take over the low-level wiring: calling the model, defining and parsing tools, and chaining calls together. Taking over that wiring is also what hides things from you. When an agent misbehaves, the cause is usually in a prompt or tool result that the framework assembled and you never saw. That makes calling the API directly the better choice in two cases: when a pattern needs only a few lines of code, and when you must inspect exactly what Claude received. If you do adopt a framework, read the code it runs underneath, and don't add steps just because the framework makes them easy to add.

The context window holds everything Claude sees in a request: the system prompt, every message, every tool result, and the tool definitions. Filling it has a cost. As token count grows, accuracy and recall degrade, which is known as context rot. In an agent loop, tool results are what fill the window fastest. Twenty file reads to find one function leave twenty files in the history for every later turn.

Subagents solve this by isolation. Each subagent runs in its own conversation, and its intermediate tool calls stay inside it. Only its final message returns to the parent. A research subagent can read dozens of files while the main conversation receives a short summary. Subagents bring three other benefits. Several can run at once, which is parallelization. Each can carry a specialised system prompt. And each can be limited to specific tools. In the Agent SDK you define them in the agents option of query(), or as markdown files in.claude/agents/. Claude can also call a built-in general-purpose subagent through the Agent tool.

Isolation is not the only tool. When a single conversation has to keep going past its limit, compaction replaces the older turns with a summary that Claude writes on the server. The broader discipline of what to keep in context belongs to [context engineering](lesson:6.1).

Pulling the agentId out of an Agent tool result so the subagent can be resumed later
def extract_agent_id(block: ToolResultBlock) -> str | None:
    """Extract agentId from an Agent tool result's text content."""
    parts = block.content if isinstance(block.content, list) else [{"text": block.content}]
    for part in parts:
        if match := re.search(r"agentId:\s*([\w-]+)", part.get("text") or ""):
            return match.group(1)
    return None

The context window is working memory, and it ends with the session. Resuming carries one transcript forward. Compaction keeps one conversation inside the window's limit. Neither one lets an agent start a new task next week already knowing what it learned this week. For that, knowledge has to leave the context window and go into storage.

The memory tool provides that storage as files. Claude can create, read, update, and delete files in a memory directory, under /memories, and those files persist between sessions. When the tool is enabled, Claude checks the directory before it starts a task. As it works, it writes down what it learns. This is just-in-time retrieval: the agent loads a memory file only when the current task needs it, instead of putting everything it has ever learned into context at the start. A research agent running across dozens of sessions keeps a small active context and still builds up a knowledge base.

The memory tool runs client-side. Claude only requests file operations. Your application performs them against storage you control and returns each result in a tool_result block, so you decide where the data lives and who can read it. Because Anthropic publishes the tool's schema, Claude has been trained on it and calls it more reliably than a homemade equivalent.
