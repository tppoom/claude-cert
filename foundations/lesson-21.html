1. การคิดแบบขยายและคิดแบบปรับตัว

Extended Thinking คือโหมดที่อนุญาตให้ Claude คิดไตร่ตรองขั้นตอนและกลยุทธ์ก่อนที่จะเริ่มเขียนคำตอบจริง:

  • โมเดลจะสร้างกระบวนการคิดอยู่ในแท็ก <thinking> ซึ่งมองเห็นได้ผ่าน API แต่ไม่ควรนำไปแสดงตรงให้ผู้ใช้ทั่วไป
  • ต้องกำหนดพารามิเตอร์ budget_tokens (ขั้นต่ำ 1,024 โทเค็น) และค่า max_tokens ต้องมากกว่า budget เสมอ
  • โทเค็นในการคิดจะคิดราคาในอัตราเดียวกับ Output Tokens ปกติ

โมเดลที่ให้คําตอบในครั้งเดียวต้องทําให้ทุกอย่างถูกต้องในครั้งแรกโดยไม่มีการขัดเกลา การคิดจะยกขีดจํากัดนั้นขึ้น เมื่อมีการคิดแบบแอ็คทีฟ คล็อดจะทํางานผ่านปัญหาด้วยคําศัพท์ของตัวเองก่อนที่จะตอบ: มันจะถามคําถามใหม่ ทดลองแนวทาง ตรวจสอบผลลัพธ์ขั้นกลาง และทิ้งเส้นทางที่ล้มเหลว การคิดนี้เกิดขึ้นในบล็อกเนื้อหาของการคิดก่อนข้อความ นั่นคือเหตุผลที่การคิดช่วยในการคํานวณ การเขียนโค้ด การวิเคราะห์ และงานเชิงปฏิบัติการที่ยาวนาน ข้อความที่คุณเห็นในบล็อกการคิดเป็นบทสรุปของการคิด ไม่ใช่ห่วงโซ่ความคิดดิบ

มีสองวิธีในการกำหนดค่า การคิดแบบขยายเป็นรูปแบบที่เก่ากว่าและกำหนดเอง: คุณส่งประเภท: "เปิดใช้งาน" พร้อมงบประมาณคงที่_โทเค็น เลิกใช้งานแล้วใน Opus 4.6 และ Sonnet 4.6 และใน Claude 4.7 และรุ่นที่ใหม่กว่า Budget_tokens ส่งคืนข้อผิดพลาด 400 การคิดแบบปรับเปลี่ยนได้ (ประเภท: "adaptive") ช่วยให้ Claude ตัดสินใจว่าควรคิดเมื่อใดและมากน้อยเพียงใด โดยขึ้นอยู่กับการตั้งค่าความพยายามและความซับซ้อนของแบบสอบถาม คำถามง่ายๆ จะได้รับคำตอบโดยตรง ในรุ่น Claude Opus 5.5, Fable 5.1 และ Fable และ Mythos 5 การคิดแบบปรับตัวจะเปิดอยู่เสมอและไม่สามารถปิดการใช้งานได้

การคิดไม่มีวันเป็นอิสระ โทเค็นการให้เหตุผลจะถูกเรียกเก็บเงินเป็นโทเค็นเอาต์พุตและนับไปยัง max_tokens ดังนั้นให้พื้นที่สําหรับการคิดและการตอบกลับ ฟิลด์การแสดงผลควบคุมเฉพาะว่า

คุณจะเห็นสรุปหรือไม่ “omitted” ซึ่งเป็นค่าเริ่มต้นในรุ่น Claude 5 และ Opus 4.7 และ 4.8 จะส่งคืนฟิลด์การคิดที่ว่างเปล่าและเร่งโทเค็นข้อความแรกเมื่อสตรีม แต่คุณยังคงต้องจ่ายเงินสําหรับการคิดเต็มรูปแบบ คุณยังสามารถควบคุมเมื่อการคิดแบบปรับตัวถูกกระตุ้น หากข้อความแจ้งเตือนของระบบขนาดใหญ่ทําให้ Claude คิดผ่านการถามคําถามเล็กน้อย ให้เพิ่มคําแนะนําที่บอกให้ตอบโดยตรงเมื่อการคิดจะไม่ปรับปรุงคําตอบอย่างมีนัยสําคัญ

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Exam Trap: Setting thinking display to "omitted" cuts thinking costs, because the thinking text is not returned. (ทำไมถึงผิด): Omitted display skips streaming the thinking text, which lowers latency, but every thinking token is still generated and billed.

คำอธิบายเจาะลึก: Exam Trap: การตั้งค่าการแสดงผลการคิดเป็น “omitted” ช่วยลดค่าใช้จ่ายในการคิด เนื่องจากข้อความการคิดจะไม่ถูกส่งคืน (ทําไมจึงผิดพลาด): การแสดงผลที่ละเว้นจะข้ามการสตรีมข้อความการคิด ซึ่งช่วยลดเวลาแฝง แต่โทเค็นการคิดทุกโทเค็นยังคงถูกสร้างและเรียกเก็บเงิน

A FAQ bot on Claude Opus 4.8 uses adaptive thinking, but it reasons at length over trivial questions and users notice the latency. The team wants thinking kept available for hard questions. What is the best fix?

คำแปลโจทย์: บอทคำถามที่พบบ่อยบน Claude Opus 4.8 ใช้การคิดแบบปรับตัว แต่ให้เหตุผลนานกว่าคำถามเล็กๆ น้อยๆ และผู้ใช้สังเกตเห็นความล่าช้า ทีมงานต้องการให้มีความคิดพร้อมสำหรับคำถามยากๆ การแก้ไขที่ดีที่สุดคืออะไร?
คำตอบที่ถูกต้อง: ตัวเลือก C
💡 Official Explanation (คำอธิบายเฉลย):

Adaptive thinking's triggering can be steered with a prompt. budget_tokens returns a 400 error on Opus 4.7 and later. "omitted" hides thinking but still generates it and charges for it. A non-default temperature is rejected on this model.

คำแปลไทย: การกระตุ้นการคิดแบบปรับตัวสามารถขับเคลื่อนได้ด้วยการแจ้ง Budget_tokens ส่งคืนข้อผิดพลาด 400 ใน Opus 4.7 และใหม่กว่า "ละเว้น" ซ่อนความคิดแต่ยังคงสร้างมันขึ้นมาและเรียกเก็บเงินจากมัน อุณหภูมิที่ไม่ใช่ค่าเริ่มต้นจะถูกปฏิเสธในรุ่นนี้
“The triggering behavior for adaptive thinking is promptable.”
คำแปล: พฤติกรรมที่กระตุ้นให้เกิดการคิดแบบปรับตัวนั้นสามารถถูกกระตุ้นได้

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A model that answers in one pass has to get everything right the first time, with no scratch work. Thinking lifts that limit. With thinking active, Claude works through the problem in its own words before it answers: it restates the question, tries approaches, checks intermediate results and drops paths that fail. This reasoning arrives in thinking content blocks before the text. It is why thinking helps on math, coding, analysis and long agentic tasks. The text you can see in a thinking block is a summary of the reasoning, never the raw chain of thought.

There are two ways to configure it. Extended thinking is the older, manual form: you send type: "enabled" with a fixed budget_tokens. It is deprecated on Opus 4.6 and Sonnet 4.6, and on Claude 4.7 and later models budget_tokens returns a 400 error. Adaptive thinking (type: "adaptive") lets Claude decide when to think and how much, based on the effort setting and how complex the query is. Easy queries get a direct answer. On Claude Opus 5.5, Fable 5.1 and the Fable and Mythos 5 models, adaptive thinking is always on and cannot be disabled.

Thinking is never free. Reasoning tokens are billed as output tokens and count toward max_tokens, so leave room for both the thinking and the reply. The display field only controls whether you see the summary. "omitted", the default on the Claude 5 models and Opus 4.7 and 4.8, returns an empty thinking field and speeds up the first text token when streaming, but you still pay for the full thinking. You can also steer when adaptive thinking triggers. If a large system prompt makes Claude reason through trivial questions, add an instruction telling it to answer directly when thinking would not meaningfully improve the answer.

The effort parameter sets how many tokens Claude spends on a response, so one model can trade thoroughness against token efficiency. You set it with output_config.effort. It affects every output token: the response text, tool calls and their arguments, and thinking when thinking is active. That is why effort works whether or not thinking is on, and why lower effort also means fewer, terser tool calls. On a model where adaptive thinking cannot be turned off, such as Opus 5.5, effort becomes the main control over how much the model reasons and what a request costs.

Most models default to high. Claude Opus 5.5 defaults to medium, so a request that leaves effort out runs one level lower than it did on Opus 5. Not every model has every level. max and xhigh exist only on newer models, and not every model with max also has xhigh. At the higher levels, set a large max_tokens, because it is a hard limit on total output, thinking plus response text.

คำแปล: Multishot prompting โดยมีตัวอย่างที่เกี่ยวข้องและหลากหลายสามถึงห้าตัวอย่างรวมอยู่ในแท็กตัวอย่างเป็นแนวทางที่แนะนำสำหรับรูปแบบการบังคับเลี้ยว โทน และโครงสร้างที่เชื่อถือได้
ตัวเลือก B: ตัวเลือกที่ไม่ถูกต้อง

A single untagged example gives Claude less structure to distinguish instructions from demonstrations and does not cover the diversity edge cases require.

คำแปล: ตัวอย่างเดียวที่ไม่ติดแท็กทำให้ Claude มีโครงสร้างน้อยลงในการแยกแยะคำสั่งจากการสาธิต และไม่ครอบคลุมกรณี Edge ที่หลากหลายที่ต้องการ
ตัวเลือก C: ตัวเลือกที่ไม่ถูกต้อง

Examples are one of the most reliable levers for output format; replacing them with prose instructions alone forgoes that benefit for a format-sensitive task.

คำแปล: ตัวอย่างคือหนึ่งในเครื่องมือที่เชื่อถือได้มากที่สุดสำหรับรูปแบบเอาต์พุต การแทนที่ด้วยคำแนะนำร้อยแก้วเพียงอย่างเดียวทำให้ลืมประโยชน์สำหรับงานที่ต้องคำนึงถึงรูปแบบ
ตัวเลือก D: ตัวเลือกที่ไม่ถูกต้อง

A large set of near-duplicate examples risks Claude picking up unintended narrow patterns instead of generalizing to the diverse cases the task actually requires.

คำแปล: ตัวอย่างจำนวนมากที่เกือบจะซ้ำกันเสี่ยงที่ Claude จะเลือกรูปแบบแคบๆ โดยไม่ได้ตั้งใจ แทนที่จะเน้นไปที่กรณีต่างๆ ที่หลากหลายที่งานต้องการจริงๆ
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage

Fast mode is a research preview that gives up to 2.5x more output tokens per second on Claude Opus 5.5, Opus 5 and Opus 4.8, at premium pricing. It is not a different model. It runs the same weights with the same behaviour on a faster inference configuration, so you keep Opus-level capability without moving to a smaller model. You opt in by setting speed: "fast" and sending the fast-mode-2026-02-01 beta header.

Where the speed shows up is important. Fast mode raises output tokens per second, not time to first token, so it pays off on long generations and is easiest to see when streaming. If your problem is the wait before the first token, fast mode is the wrong tool. Effort and fast mode also act on different things. Effort changes how many tokens Claude produces. Fast mode changes how quickly each one arrives.
