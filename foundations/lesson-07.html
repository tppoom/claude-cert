💡 แนวคิดหลักสำคัญ (Key Concept)

Model retirement — Every Claude model moves through a series of lifecycle states. A retired model stops serving requests altogether. Maintaining a Claude-powered system therefore includes planned migrations to replacement models, finished before the retirement date.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "The four states a model passes through" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

With most dependencies, you choose when to upgrade. Claude models work differently: Anthropic retires older models as newer ones launch, so the model your application calls has its own life cycle, separate from your release schedule. The deprecations page says it plainly: applications that rely on Anthropic models "may need occasional updates to keep working." Anthropic notifies affected customers by email and in the documentation.

Anthropic describes four states. Active models are fully supported and recommended. Legacy models no longer receive updates and may be deprecated later. Deprecated models still work, but each one has a recommended replacement and a retirement date. Retired models are gone, and any request to one fails. The difference between deprecated and retired is the one that matters operationally: deprecation starts your migration window, and retirement ends it. Nothing reroutes your traffic automatically. If your code still names a retired model, it breaks.

คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก C
ตัวเลือก A: ไม่ถูกต้อง

Incorrect -- this bypasses the self-service audit tool Anthropic already provides and adds unnecessary delay compared to exporting usage data directly.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect -- extended thinking is a reasoning feature unrelated to usage auditing and does not add model identifiers to a response payload for this purpose.

ตัวเลือก C: ถูกต้อง

Correct -- the Usage page's CSV export is the documented way to audit API usage broken down by API key and model, making it straightforward to locate deprecated-model traffic.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect -- searching internal logs for a literal string depends on logging conventions the team controls and won't reliably capture every call broken down by API key and model the way the Console export does.

The dates on the deprecations page cover only the platforms Anthropic runs itself: the Claude API, Claude Platform on AWS and Microsoft Foundry. Amazon Bedrock and Google Cloud are run by partners, and they set their own retirement schedules. On those platforms, the same model can have a different lifecycle status and different dates. Each partner publishes its own model table.

For a team that serves the same application through several platforms, this means one deprecation notice can lead to several migration deadlines. Plan each deployment against the schedule of the platform it runs on, not against a single date.

For publicly released models, Anthropic gives customers with active deployments at least 60 days' notice before retirement. Use that window in a set order. First, find out where the deprecated model is still in use. The Claude Console has a usage audit for this: open the Usage page, click Export, and review the CSV, which breaks usage down by API key and model. That shows you which services and keys still need changing, so you can prioritise them.

Next, test. Anthropic recommends testing your applications with newer models well before your current model retires, so you can measure how the replacement performs on your own tasks. Testing also catches breaking request changes, not only differences in output quality. For example, the Opus 5.5 migration guide notes that a manual thinking budget (thinking: {"type": "enabled", "budget_tokens": N}) is no longer supported on Claude Opus 4.7 and later and returns a 400 error. Request code that worked on the old model can fail on the new one, so read the model's migration guide before you change the model ID. Then update your code to the recommended replacement as soon as possible. Keep checking the deprecations documentation, and contact support if the migration stalls.

Models are not the only part of the platform with a life cycle. Every API request must send an anthropic-version header, such as anthropic-version: 2023-06-01. The client SDKs send it for you. Within a version, Anthropic keeps existing input and output parameters intact. It may still add optional inputs, add output values, change the conditions for specific error types, and add new variants to enum-like outputs such as streaming event types. Code that handles every possible enum value strictly can therefore still break within a version. Anthropic recommends using the latest API version, and older versions may be unavailable to new users.

Features have their own classifications, and these decide what you can safely build critical workflows on. When a platform appears in a feature's Availability column with no label, the feature is stable, fully supported and recommended for production, with standard versioning guarantees. Beta features are previews: they may change significantly or be discontinued, and they are not guaranteed for ongoing production use. A Deprecated feature still works and comes with a migration path and a removal timeline. A Retired feature is no longer available. Features don't all pass through every stage, and a feature can enter at any stage.
