💡 แนวคิดหลักสำคัญ (Key Concept)

Constrained Decoding — การจำกัด Token Sampling ของ Claude ให้สร้างเฉพาะผลลัพธ์ที่ถูกต้องตาม Schema ที่กำหนด การบังคับโครงสร้างตั้งแต่ขั้นตอน Generate ทำให้ผลลัพธ์ Parse ผ่านเสมอและมีฟิลด์กับ Data Types ครบถ้วนตามต้องการ โดยไม่ต้องลุ้นว่าโมเดลจะทำตามคำสั่งหรือไม่

  • ▸3. Strict tool use: รับประกัน Tool Inputs ตาม Schema

1. ทำไมการขอ JSON ผ่าน Prompt ถึงทำให้ Pipeline พัง

ปลายทางที่รับ Output ของ Claude มักเป็นโค้ด เช่น json.loads(), การ insert ลง Database หรือฟังก์ชันที่คาดหวังว่า passengers ต้องเป็น integer ซึ่งโค้ดไม่ยอมรับความคลาดเคลื่อน หากขอ JSON ผ่าน Prompt เพียงอย่างเดียว ผลลัพธ์ส่วนใหญ่อาจ Parse ผ่าน แต่จะมีบางครั้งที่หลุดประโยคปิดท้าย, ขาด Key สำคัญ หรือส่งตัวเลขมาเป็น String จนทำให้ Job พังตอนตีสามจากข้อมูล Record ที่ไม่มีใคร reproduce ได้

การจูน Prompt อย่างละเอียดช่วยลดโอกาสเกิดได้ แต่ไม่สามารถทำให้ Error เป็นศูนย์ โดยมี Failure 4 รูปแบบที่พบบ่อย: Syntax พังจน Parse ไม่ผ่าน, ขาด Required Fields, Data Types ไม่สอดคล้องกัน และ Schema Violations ที่ต้องคอย Catch เพื่อ Retry ตัวอย่างที่เห็นชัดคือ Booking Tool ที่ต้องการ passengers: int แต่ถ้าไม่มีการบังคับ Schema Claude อาจส่ง "two" หรือ "2" มาแทน

Structured Outputs แก้ปัญหานี้ตั้งแต่จังหวะ Generation โดยจำกัด Sampling ของ Claude ให้สร้างเฉพาะ Output ที่ถูกต้องตาม Schema เท่านั้น ส่งผลให้ได้ผลลัพธ์ที่ Valid เสมอ (หมดปัญหา JSON.parse() พัง), มี Type Safety (การันตีทั้ง Type และ Required Fields) และทำงานได้เสถียรโดยไม่ต้องคอย Retry ฟีเจอร์นี้แบ่งเป็น 2 ส่วน ซึ่งใช้งานแยกกันหรือใช้ร่วมกันใน Request เดียวได้: JSON Outputs ใช้คุม Response ของ Claude ส่วน Strict Tool Use ใช้คุม Arguments ที่ Claude ส่งเข้า Tools

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
A clear enough prompt with an example makes Claude's JSON reliable enough for an unguarded parser. (ทำไมถึงผิด): Prompting only improves the odds. Malformed JSON, missing fields and wrong types are ruled out only when constrained decoding enforces the schema.

Prompt ที่ชัดเจนพร้อมตัวอย่างเพียงพอที่จะทำให้ JSON จาก Claude ปลอดภัยสำหรับ Parser ทั่วไปโดยไม่ต้องมี Guard? (ทำไมถึงผิด): ไม่จริง: Prompting ทำได้เพียงเพิ่มโอกาสความน่าจะเป็นเท่านั้น ปัญหา Malformed JSON, ฟิลด์ตกหล่น หรือ Data Type ผิดพลาด จะถูกกำจัดได้อย่างเด็ดขาดก็ต่อเมื่อใช้ Constrained Decoding บังคับตาม Schema เท่านั้น

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Whatever consumes Claude's output is usually code: a json.loads(), a database insert, a function that expects passengers to be an integer. Code does not tolerate approximations. Ask for JSON in the prompt alone and most responses will parse. Then one arrives with a trailing sentence, a missing key or a number written as a string, and the job fails at 3 a.m. on a record nobody can reproduce.

Careful prompting lowers how often this happens, but it can't bring the rate to zero. Four kinds of failure keep appearing: parsing errors from invalid JSON syntax, missing required fields, inconsistent data types, and schema violations that you have to catch and retry. A booking tool shows the type problem clearly. It needs passengers: int, and without enforcement Claude might send "two" or "2".

Structured outputs fix this at generation time. Claude's sampling is restricted so that only schema-valid output can be produced. That makes the result always valid (no more JSON.parse() errors), type safe (required fields and their types are guaranteed), and reliable, because there are no schema violations left to retry. The feature has two parts, and you can use them separately or together in one request. JSON outputs shape Claude's response. Strict tool use shapes the arguments Claude passes to your tools.

2. การใช้งาน JSON Outputs ด้วย output_config.format

  1. 1
    กำหนดโครงสร้างที่ต้องการในรูปแบบ JSON Schema หรือ Type ในภาษานั้นๆ
  2. 2
    ส่งค่านั้นไปใน output_config.format ของ Request พร้อมระบุ type: "json_schema"
  3. 3
    อ่านผลลัพธ์จาก Text Content Block ของ Response ทั้งนี้ Schema จะอิงตามมาตรฐาน JSON Schema โดยมีข้อจำกัดบางประการ
A raw JSON schema sent in output_config.format, with the text block parsed afterwards
    output_config={
        "format": {
            "type": "json_schema",
            "schema": {
                "type": "object",
                "properties": {
                    "name": {"type": "string"},
                    "email": {"type": "string"},
                    "plan_interest": {"type": "string"},
                    "demo_requested": {"type": "boolean"},
                },
                "required": ["name", "email", "plan_interest", "demo_requested"],
                "additionalProperties": False,
            },
        }
    },
)
text = next(block.text for block in response.content if block.type == "text")
contact = json.loads(text)

Some JSON Schema constraints can't be expressed in the sent schema, and the helpers deal with that without hiding it. 3. Strict tool use: รับประกัน Tool Inputs ตาม Schema

จุดผิดพลาดของ Agents มักไม่ได้อยู่ที่คำตอบสุดท้าย แต่อยู่ที่ Arguments ที่ Claude ส่งเข้าไปยัง Functions เช่น หาก Handler ของ create_booking คาดหวังตัวเลข 2 แต่ได้สตริง "2" หรือขาด Required field ก็จะเกิด Runtime error ระหว่างทำ Multistep task ทันที การตั้งค่า strict: true ในนิยาม Tool จะคอมไพล์ input_schema ให้เป็น Grammar โดยใช้ Pipeline เดียวกับ Structured Outputs เพื่อจำกัดการ Sampling ของ Claude ให้ส่งเฉพาะ Inputs ที่ตรงตาม Schema เท่านั้น

Agents fail in a different place. The risk is not the final answer but the arguments Claude passes to your functions. If a create_booking handler gets "2" where it expected 2, or gets no value for a required field, it throws at runtime partway through a multistep task. Setting strict: true on a tool definition compiles its input_schema into a grammar, using the same pipeline as structured outputs, and limits Claude's sampling to inputs that match it.

strict is a top-level property of the tool, next to name, description and input_schema. With it on, you get two guarantees. The input in every tool_use block follows your input_schema, and the tool name is always valid: one of the tools you provided, or a server tool. Your handler can drop the validate-and-retry loop for tool arguments.

Strict mode has three operational limits. The computer use and browser use toolset entries (computer_toolset_20260801 and browser_toolset_20260801) don't accept strict: true, and a request that sets it on either one is rejected. Compiled tool schemas are cached for up to 24 hours after last use, apart from message content. Strict tool use is HIPAA eligible, but that cache doesn't get the same PHI protections as prompts and responses. Keep PHI out of property names, enum values, const values and pattern regexes.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Before giving up on constrained decoding, check whether the obstacle is just an unsupported constraint. A minimum, a maximum or a string length doesn't block structured outputs. transform_schema() or a validating SDK helper moves it into the description and checks it in your code. The cases that do force a fallback are a model where structured outputs aren't available and a schema that needs features the supported subset doesn't cover.

For those cases, you go back to asking for the format in the prompt. The techniques are taught in [Prompting for output format](lesson:6.2). In short: define the format precisely with JSON, XML or a template, prefill the assistant turn, and constrain with examples. What changes in your pipeline is that the output no longer comes with a guarantee. Every failure mode constrained decoding removed is possible again: syntax errors, missing fields, wrong types. Wrap the parse in error handling, validate against the schema in code, and budget for retries. You already had these steps before structured outputs existed.
