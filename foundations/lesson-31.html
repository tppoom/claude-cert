💡 แนวคิดหลักสำคัญ (Key Concept)

Constrained decoding — Claude's token sampling is limited to output that is valid under a schema you supply. Because the shape is enforced while the output is generated, the result always parses and always has the required fields and types. You don't need to hope the model followed the instructions.

1.Why JSON requested in the prompt breaks pipelines

สาระสำคัญและหลักการทำงานของหัวข้อนี้: หัวข้อนี้เจาะลึก Why JSON requested in the prompt breaks pipelines ตามมาตรฐานและพิมพ์เขียวการสอบของ Anthropic โดยมุ่งเน้นการทำความเข้าใจสถาปัตยกรรมเชิงลึก ข้อดีข้อเสียทางเทคนิค และแนวทางการปฏิบัติจริงในโปรดักชัน
⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

Exam trapA clear enough prompt with an example makes Claude's JSON reliable enough for an unguarded parser.Why is that wrong?Prompting only improves the odds. Malformed JSON, missing fields and wrong types are ruled out only when constrained decoding enforces the schema.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Why JSON requested in the prompt breaks pipelines" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Whatever consumes Claude's output is usually code: a json.loads(), a database insert, a function that expects passengers to be an integer. Code does not tolerate approximations. Ask for JSON in the prompt alone and most responses will parse. Then one arrives with a trailing sentence, a missing key or a number written as a string, and the job fails at 3 a.m. on a record nobody can reproduce.

Careful prompting lowers how often this happens, but it can't bring the rate to zero. Four kinds of failure keep appearing: parsing errors from invalid JSON syntax, missing required fields, inconsistent data types, and schema violations that you have to catch and retry. A booking tool shows the type problem clearly. It needs passengers: int, and without enforcement Claude might send "two" or "2".

Structured outputs fix this at generation time. Claude's sampling is restricted so that only schema-valid output can be produced. That makes the result always valid (no more JSON.parse() errors), type safe (required fields and their types are guaranteed), and reliable, because there are no schema violations left to retry. The feature has two parts, and you can use them separately or together in one request. JSON outputs shape Claude's response. Strict tool use shapes the arguments Claude passes to your tools.

There are three steps to a JSON output. Describe the structure you want as a JSON schema, or as a type in your language. Send it in the request's output_config.format with type: "json_schema". Then read the result from the response's text content block. The schema follows JSON Schema, with some limitations. The raw request looks like this:

The recommended route in Python is the SDK helper. Pass a Pydantic model to client.messages.parse() as output_format=. The SDK converts the model to a schema, sends it as output_config.format, validates the response and returns the typed object in parsed_output. output_format is the helper's argument and output_config.format is the request field the helper fills in. They are the same feature at two layers.

Some JSON Schema constraints can't be expressed in the sent schema, and the helpers deal with that without hiding it. Constraints such as minimum, maximum, minLength and maxLength are removed from the schema Claude receives and written into the field's description instead. The helpers also add additionalProperties: false to every object and filter string formats down to the supported list. A helper that validates responses still checks the result against your original schema in your own code. Take a field with minimum: 100: it goes to Claude as a plain integer with {minimum: 100} in its description, and the response is still validated against minimum: 100. If you build the request yourself, transform_schema() from the anthropic package does the same conversion and returns the schema for you to edit instead of sending it.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Strict tool use: guaranteed tool inputs" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Agents fail in a different place. The risk is not the final answer but the arguments Claude passes to your functions. If a create_booking handler gets "2" where it expected 2, or gets no value for a required field, it throws at runtime partway through a multistep task. Setting strict: true on a tool definition compiles its input_schema into a grammar, using the same pipeline as structured outputs, and limits Claude's sampling to inputs that match it.

strict is a top-level property of the tool, next to name, description and input_schema. With it on, you get two guarantees. The input in every tool_use block follows your input_schema, and the tool name is always valid: one of the tools you provided, or a server tool. Your handler can drop the validate-and-retry loop for tool arguments.

Strict mode has three operational limits. The computer use and browser use toolset entries (computer_toolset_20260801 and browser_toolset_20260801) don't accept strict: true, and a request that sets it on either one is rejected. Compiled tool schemas are cached for up to 24 hours after last use, apart from message content. Strict tool use is HIPAA eligible, but that cache doesn't get the same PHI protections as prompts and responses. Keep PHI out of property names, enum values, const values and pattern regexes.

ID: 55660

A weather tool occasionally fails because an upstream API times out. The integration currently returns a bare tool_result of "error" with is_error: true, and Claude keeps repeating the same failing call in a loop. What change to the tool_result content would most likely stop the repeated failing calls?

A Replace the generic "error" text with a specific message describing the failure and a retry delay
B Remove is_error entirely so Claude treats the repeatedly failing call as if it had succeeded
C Stop returning any tool_result at all and let the conversation end without a response
D Switch the tool from a client tool to a server tool so Anthropic retries it automatically
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. Instructive error messages that name the failure and suggest a concrete next step give Claude the context needed to adapt, such as waiting before retrying, instead of repeating the identical call.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. Hiding the error would cause Claude to treat failed data as valid, corrupting downstream output rather than stopping the loop.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Omitting a required tool_result block after a tool_use block violates the API's formatting requirements and produces a request error, not a resolved loop.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Converting a custom client tool into a server tool isn't a configuration option available to arbitrary user-defined tools, and it wouldn't address the message-quality problem.

Before giving up on constrained decoding, check whether the obstacle is just an unsupported constraint. A minimum, a maximum or a string length doesn't block structured outputs. transform_schema() or a validating SDK helper moves it into the description and checks it in your code. The cases that do force a fallback are a model where structured outputs aren't available and a schema that needs features the supported subset doesn't cover.

For those cases, you go back to asking for the format in the prompt. The techniques are taught in [Prompting for output format](lesson:6.2). In short: define the format precisely with JSON, XML or a template, prefill the assistant turn, and constrain with examples. What changes in your pipeline is that the output no longer comes with a guarantee. Every failure mode constrained decoding removed is possible again: syntax errors, missing fields, wrong types. Wrap the parse in error handling, validate against the schema in code, and budget for retries. You already had these steps before structured outputs existed.
