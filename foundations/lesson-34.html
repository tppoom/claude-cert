1. การให้สิทธิ์อนุญาต: โหมดสิทธิ์อนุญาต กฎและตะขอ

การอนุญาตกําหนดสิ่งที่เอเจนต์สามารถทําได้ และใน Claude Code มันถูกตั้งค่าด้วยกฎและโหมดการอนุญาต กฎอนุญาตอนุญาตให้เครื่องมือทํางานโดยไม่ได้รับการอนุมัติ กฎขอให้ยืนยันทุกครั้ง และกฎปฏิเสธจะบล็อกเครื่องมือทั้งหมด โหมดกําหนดสิ่งที่เกิดขึ้นกับทุกสิ่งที่กฎไม่ครอบคลุม

สำหรับตัวแทนแบบไม่มีส่วนหัวที่มีชุดเครื่องมือตายตัว DontAsk ร่วมกับกฎการอนุญาตที่ชัดเจนจะให้พฤติกรรมการปฏิเสธโดยค่าเริ่มต้น: สิ่งใดก็ตามที่ไม่ได้รับการอนุมัติล่วงหน้าจะถูกปฏิเสธ และไม่ได้รับแจ้ง bypassPermissions ทำงานในลักษณะอื่นและให้อำนาจในวงกว้าง

ทราบข้อจํากัดของเลเยอร์นี้ Claude Code จะแยกวิเคราะห์คําสั่ง Bash ให้เป็น AST และจับคู่กับกฎของคุณ คําสั่งที่ไม่สามารถแยกวิเคราะห์ได้อย่างสะอาด หรือที่ไม่ตรงกับกฎอนุญาตต้องได้รับการอนุมัติ เอกสารประกอบระบุอย่างชัดเจนว่านี่เป็นเกตเวย์สิทธิ์และไม่ใช่แซนด์บ็อกซ์ นอกเหนือจากการตรวจสอบในตัวบางประการแล้ว มันไม่ได้อนุมานว่าคําสั่งนั้นอันตรายจากเป้าหมายหรือผลลัพธ์ของมัน

ฮุคเพิ่มชั้นนโยบายที่แน่นอนในโค้ดของคุณเอง ฮุค PreToolUse สามารถส่งคืนการอนุญาตการตัดสินใจ: “ปฏิเสธ” เพื่อบล็อกการเรียกเครื่องมือ และเหตุผลจะแสดงให้ Claude เห็น อย่างไรก็ตาม ฮุคไม่สามารถเขียนทับการกําหนดค่าของคุณได้: กฎการปฏิเสธและถามจะยังคงได้รับการประเมินไม่ว่าฮุคจะส่งคืนอะไรก็ตาม

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Exam Trap: ห่วง PreToolUse ที่ส่งคืน “allow” จะแทนที่กฎการปฏิเสธใดๆ ในการตั้งค่า (ทําไมจึงผิดพลาด): ห่วงสามารถเพิ่มการปฏิเสธได้ แต่กฎการปฏิเสธและถามที่กําหนดค่าไว้จะยังคงได้รับการประเมินไม่ว่าห่วงจะส่งคืนอะไรก็ตาม

EN: Exam Trap: A PreToolUse hook returning "allow" overrides any deny rule in settings. (ทำไมถึงผิด): Hooks can add a deny, but configured deny and ask rules are still evaluated whatever the hook returns.

✓ ตอบถูกแล้ว ID: 55681

ทีมกําลังปรับใช้เอเจนต์ที่ประมวลผลเอกสารของบุคคลที่สามที่ไม่น่าเชื่อถือ และสามารถเข้าถึง API ภายในที่สามารถส่งอีเมลและโอนเงินได้ เพื่อจํากัดความเสียหายที่อาจเกิดขึ้นจากการฉีดพร็อกซ์ที่สําเร็จ ทีมควรทําอย่างไรเมื่อกําหนดค่าความสามารถของเอเจนต์

EN: A team is deploying an agent that processes untrusted third-party documents and has access to internal APIs that can send emails and transfer funds. To limit the damage a successful prompt injection could cause, what should the team do when configuring the agent's capabilities?

คำตอบที่ถูกต้อง: ตัวเลือก A
💡 คำอธิบายเฉลยภาษาไทยรายตัวเลือก (Option Analysis):
ตัวเลือก A: ✓ คำตอบที่ถูกต้อง

ถูกต้อง. การจำกัดการเข้าถึงข้อมูลที่ละเอียดอ่อนและการดำเนินการของตัวแทนภายใต้หลักการสิทธิ์ขั้นต่ำเป็นวิธีที่แนะนำในการลดรัศมีการระเบิดของการฉีดที่ประสบความสำเร็จ

EN: Correct. Limiting an agent's access to sensitive data and actions under the principle of least privilege is the recommended way to reduce the blast radius of a successful injection.
ตัวเลือก B: ตัวเลือกที่ไม่ถูกต้อง

ไม่ถูกต้อง. Broad, unscoped access maximizes rather than minimizes the damage a successful injection can cause and contradicts least-privilege guidance.

EN: Incorrect. Broad, unscoped access maximizes rather than minimizes the damage a successful injection can cause and contradicts least-privilege guidance.
ตัวเลือก C: ตัวเลือกที่ไม่ถูกต้อง

ไม่ถูกต้อง. บัญชีระดับผู้ดูแลระบบที่ใช้ร่วมกันนั้นตรงกันข้ามกับสิทธิ์ขั้นต่ำและให้การเข้าถึงสูงสุดทั่วทั้งระบบ

EN: Incorrect. A shared administrator-level account is the opposite of least privilege and gives any successful injection maximum reach across systems.
ตัวเลือก D: ตัวเลือกที่ไม่ถูกต้อง

ไม่ถูกต้อง. การลบระบบอัตโนมัติทั้งหมดจะทำลายจุดประสงค์ของการสร้างตัวแทน คำแนะนำคือกำหนดขอบเขตการเข้าถึงให้แคบ ไม่ใช่กำจัดออกไปทั้งหมด

EN: Incorrect. Removing all automation defeats the purpose of building the agent; the guidance is to scope access narrowly, not eliminate it entirely.

Authorization decides what an agent may do, and in Claude Code it is set with permission rules and modes. Allow rules let a tool run without approval, ask rules prompt for confirmation each time, and deny rules block the tool entirely. The mode sets what happens to everything the rules don't cover.

For a headless agent with a fixed toolset, dontAsk together with explicit allow rules gives deny-by-default behavior: anything not pre-approved is refused, not prompted. bypassPermissions works the other way and grants broad authority.

Know the limits of this layer. Claude Code parses Bash commands into an AST and matches them against your rules. Commands that can't be parsed cleanly, or that match no allow rule, require approval. The documentation is explicit that this is a permission gate and not a sandbox. Apart from a few built-in checks, it doesn't infer whether a command is dangerous from its target or effects.

Hooks add a deterministic policy layer in your own code. A PreToolUse hook can return permissionDecision: "deny" to block a tool call, and the reason is shown to Claude. A hook can't override your configuration, though: deny and ask rules are still evaluated whatever the hook returns.

An API key is how your application authenticates. If it leaks, someone else can authenticate as you. Anthropic's API key guidance says to load the key from the environment, never from a hard-coded string. In the cloud, use your hosting provider's mechanism for injecting environment variables.

The same guidance covers the rest of a key's life. Rotate keys on a consistent schedule, for example every 90 days, by creating new ones and deactivating the old ones. Separate keys for development, testing and production, so a compromised key can be disabled without affecting the other environments. Scan repositories for committed secrets: turn on your source-control provider's secret scanning, use tools such as Gitleaks, and add scanning to CI/CD so secrets are caught before they reach the main branch. Claude Code stores its own API keys and tokens in the macOS Keychain where available, and protects them with file permissions on Windows and Linux.

For agents, the stronger pattern is to keep credentials out of the agent entirely. In the Agent SDK deployment guidance, a proxy outside the agent's container injects credentials. The agent never sees them, the proxy enforces an endpoint allowlist and logs every request, and credentials live in one secure place instead of being copied to each agent. Don't mount credential files into the agent's filesystem either.

4. ความเป็นส่วนตัวและความเป็นส่วนตัว: การรั่วไหลข้อมูลเร่งด่วน PII และ PHI

การรั่วไหลของข้อความแจ้งเปิดเผยเนื้อหาที่คุณคาดว่าจะซ่อนไว้ในข้อความแจ้งของคุณ คําแนะนําของ Anthropic ระบุหลายวิธีในการลดการรั่วไหล แยกบริบทออกจากการสืบค้นโดยเก็บข้อมูลสําคัญไว้ในข้อความแจ้งของระบบ ประมวลผลเอาต์พุตของ Claude หลังการประมวลผลด้วยนิพจน์ทั่วไปหรือตัวกรองคําสําคัญ ตรวจสอบข้อความแจ้งและเอาต์พุตอย่างสม่ําเสมอ วิธีที่มีประสิทธิภาพที่สุดคือการละเว้นรายละเอียดที่เป็นกรรมสิทธิ์ที่ Claude ไม่จําเป็นต้องใช้สําหรับงาน ข้อควรระวังสองประการ การป้องกันการรั่วไหลเพิ่มความซับซ้อนที่สามารถลดประสิทธิภาพของงานได้ ดังนั้นให้ใช้เฉพาะเมื่อจําเป็นจริงๆ และเทคนิคเก่าในการเติมข้อมูลล่วงหน้าในปุ่มผู้ช่วยเพื่อรีเซ็ตคําแนะนําไม่รองรับในรุ่น Claude 4.6 ขึ้นไป

PII และ PHI ข้อมูลสุขภาพที่ได้รับการคุ้มครองคือข้อมูลสุขภาพที่สามารถระบุตัวตนได้เป็นรายบุคคล โดยทั่วไปจะปรากฏในเนื้อหาข้อความ ไฟล์แนบ และชื่อไฟล์หรือเมตาดาต้า องค์กรที่จัดการกับ PHI ควรใช้ความพร้อมของ HIPAA (BAA ที่ลงนามรวมกับองค์กรที่เปิดใช้งาน HIPAA) จากนั้น API จะปฏิเสธคุณสมบัติที่ไม่มีสิทธิ์ด้วยข้อผิดพลาด 400 รายละเอียดหนึ่งที่อาจพลาดได้ง่าย: สคีมา JSON ที่ใช้กับเอาต์พุตที่มีโครงสร้างหรือที่เข้มงวด: เครื่องมือที่แท้จริงจะคอมไพล์และแคชแยกต่างหาก โดยไม่มีการป้องกัน PHI อย่าใส่ข้อมูลผู้ป่วยในชื่อคุณสมบัติของสคีมา ค่า枚举 ค่าคงที่ หรือรูปแบบ Claude Code ไม่ครอบคลุมภายใต้ความพร้อมของ HIPAA

การเก็บรักษา ภายใต้การเก็บรักษาข้อมูลเป็นศูนย์ (ZDR) Anthropic จะไม่จัดเก็บข้อความแจ้งหรือการตอบสนองที่อยู่นิ่งหลังจากการตอบสนองของ API ถูกส่งคืน ข้อมูลที่ Anthropic เก็บไว้จะไม่ถูกใช้สําหรับการฝึกอบรมโดยไม่ได้รับอนุญาตจากคุณโดยชัดแจ้ง องค์กรที่จัดการ PHI ก็ไม่จําเป็นต้องใช้ ZDR เช่นกัน

Prompt leakage exposes material you expected to stay hidden in your prompt. Anthropic's guidance lists several ways to reduce it. Separate context from queries by keeping key information in the system prompt. Post-process Claude's outputs with regular expressions or keyword filters. Audit prompts and outputs regularly. Most effectively, leave out proprietary details Claude doesn't need for the task. Two cautions apply. Leak-proofing adds complexity that can degrade task performance, so use it only when it's really needed. And the older technique of prefilling the Assistant turn to restate instructions isn't supported on Claude 4.6 and later models.

PII and PHI. Protected health information is any individually identifiable health information. It usually appears in message content, attached files, and file names or metadata. Organizations handling PHI should use HIPAA readiness (a signed BAA plus a HIPAA-enabled organization). The API then rejects non-eligible features with a 400 error. One detail is easy to miss: JSON schemas used with structured outputs or strict: true tools are compiled and cached separately, without PHI protections. Never put patient data in schema property names, enum values, const values or patterns. Claude Code isn't covered under HIPAA readiness.

Retention. Under zero data retention (ZDR), Anthropic doesn't store prompts or responses at rest after the API response is returned. Data that Anthropic does retain is never used for training without your express permission. An organization handling PHI doesn't also need ZDR.
