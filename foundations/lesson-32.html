2. Truncated, tool and paused turns

Three stop reasons mean the work isn't finished

With max_tokens and model_context_window_exceeded the output was cut off

Text that ends mid-thought is a fragment, not an answer, and it should never reach a parser or a user as if it were complete

You can usually continue a truncated text response

Tool calls are the exception: if the last content block is an incomplete tool_use, continuing won't produce usable arguments

Send the request again with a higher max_tokens.

Detecting a tool call cut off by max_tokens and retrying with a larger limit
EN: Detecting a tool call cut off by max_tokens and retrying with a larger limit
# Check if response was truncated during tool use
if response.stop_reason == "max_tokens":
    # Check if the last content block is an incomplete tool_use
    last_block = response.content[-1]
    if last_block.type == "tool_use":
        # Send the request with higher max_tokens
        response = client.messages.create(
            model="claude-opus-5-5",
            max_tokens=4096,  # Increased limit
            messages=messages,
            tools=tools,
        )

tool_use means Claude is waiting for you

Run the tool and return its result A server tool call that doesn't have its result block yet completes in a later response, so you don't answer it yourself

pause_turn means a server-tool loop hit its iteration limit

Send the assistant content back as it is, and Claude continues from where it stopped.

A response can end with end_turn and still contain nothing. [Empty end_turn responses](lesson:4.1) usually appear after tool results, when Claude decides the turn is over. In a validation pipeline, that means end_turn alone isn't a passing check. Put the guard next to the stop-reason branch: if response.stop_reason == "end_turn" and not response.content:. Then handle that case explicitly instead of passing an empty list to a parser.

The recovery is the part people get wrong. Sending the conversation back unchanged gets the same empty answer, because Claude has already decided it is done. First fix the message structure, so there are no text blocks straight after tool results. Only if that doesn't work, add a continuation prompt in a new user message.

เทคนิคการต่อสายดินและการตรวจสอบหลายประการทำให้การตรวจสอบเป็นขั้นตอนที่ไปป์ไลน์ของคุณสามารถดำเนินการได้:

  • ▸
    Quote first: for long documents, have Claude extract word-for-word quotes before doing the task, and base the analysis only on those quotes.
  • ▸
    Cite and retract: require a supporting quote for each claim, and remove any claim that has no quote.
  • ▸
    Best-of-N: run the same prompt several times and compare the results. Inconsistencies across outputs could indicate hallucinations.
  • ▸
    Allow uncertainty: give Claude explicit permission to say it doesn't have enough information, so it doesn't fill the gap.
  • ▸
    Restrict knowledge: tell Claude to use only the provided documents and not its general knowledge.

A schema guarantees shape, not truth. Constrained decoding makes total_amount a float. It doesn't make it the total printed on the invoice. Fluent, well-formed text can still be wrong because of how [next-token generation and hallucination](lesson:5.1) work. A confidence: 0.92 field is also model output, constrained to be a number and nothing more. Treat confident, valid output as a claim to check against your sources.

Several grounding and verification techniques turn that check into steps your pipeline can run:

- Quote first: for long documents, have Claude extract word-for-word quotes before doing the task, and base the analysis only on those quotes. - Cite and retract: require a supporting quote for each claim, and remove any claim that has no quote. - Best-of-N: run the same prompt several times and compare the results. Inconsistencies across outputs could indicate hallucinations. - Allow uncertainty: give Claude explicit permission to say it doesn't have enough information, so it doesn't fill the gap. - Restrict knowledge: tell Claude to use only the provided documents and not its general knowledge.

Quotes are what make this something code can verify. If the schema asks for the supporting quote next to each extracted value, your validator can check that the quote really appears in the source document before it accepts the record.
