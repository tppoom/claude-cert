1. เช็ก stop_reason ก่อนอ่าน content เสมอ

Response ที่สำเร็จของ Messages API จะมีฟิลด์ stop_reason เพื่อบอกว่าทำไม Claude ถึงหยุด Generate เสมอ ซึ่งค่านี้ไม่ใช่ Error เพราะ Error คือ Request ล้มเหลว แต่ stop_reason คือคำอธิบายสถานะหลัง Generate เสร็จสิ้น แม้จะได้ HTTP 200 แต่ข้อมูลก็อาจยังไม่สมบูรณ์พอที่จะนำไปใช้งานจริง ดังนั้น Pipeline ของคุณควร Branch ตามค่า stop_reason ก่อนอ่าน content เสมอ เพื่อตัดสินใจว่าจะนำ Response ไปใช้ต่อ, สั่ง Continue, Retry หรือส่งต่อไปยัง Model อื่น

Which stop_reason means the content is complete and safe to process?

คำแปลโจทย์:
stop_reason ในข้อใดหมายความว่าเนื้อหาเสร็จสมบูรณ์และปลอดภัยในการประมวลผล
if response.stop_reason == "____":
    # Process the complete response
    for block in response.content:
        if block.type == "text":
            print(block.text)
คำตอบที่ถูกต้อง: ตัวเลือก A
💡 Official Explanation (คำอธิบายเฉลย):

end_turn means Claude finished naturally. max_tokens and pause_turn mean the turn is unfinished, and stop_sequence means one of your own sequences cut it off.

คำแปลไทย:
end_turn หมายถึง คลอดด์เสร็จสิ้นอย่างเป็นธรรมชาติ max_tokens และ Pause_turn หมายความว่าการเลี้ยวยังไม่เสร็จสิ้น และ stop_sequence หมายถึงหนึ่งในลำดับของคุณเองที่ตัดมันออกไป
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Every successful Messages API response has a stop_reason field that says why Claude stopped generating. It is not an error. Errors mean the request failed, while a stop reason describes a completed generation. A response can be a 200 and still be unusable as an answer. Have your pipeline branch on stop_reason before it reads the content. That one field decides whether you use the response, continue it, retry it or send it to another model.

2. การจัดการ Truncated, Tool และ Paused Turns

มี 3 stop_reason ที่บ่งชี้ว่างานยังไม่เสร็จสิ้น โดย max_tokens และ model_context_window_exceeded หมายถึง Output ถูกตัดตอน ข้อความที่ค้างอยู่กลางประโยคเป็นเพียง Fragment ไม่ใช่ผลลัพธ์ที่สมบูรณ์ จึงห้ามส่งเข้า Parser หรือส่งตรงถึง User โดยเด็ดขาด ปกติแล้วหากเป็น Text Response ธรรมดา คุณสามารถสั่งให้ Generate ต่อได้ แต่ข้อยกเว้นคือ Tool Calls: หาก Content Block สุดท้ายเป็น tool_use ที่ไม่สมบูรณ์ การสั่ง Continue จะไม่ได้ Arguments ที่ถูกต้อง ต้องส่ง Request ใหม่อีกครั้งพร้อมปรับค่า max_tokens ให้สูงขึ้น

Detecting a tool call cut off by max_tokens and retrying with a larger limit
# Check if response was truncated during tool use
if response.stop_reason == "max_tokens":
    # Check if the last content block is an incomplete tool_use
    last_block = response.content[-1]
    if last_block.type == "tool_use":
        # Send the request with higher max_tokens
        response = client.messages.create(
            model="claude-opus-5-5",
            max_tokens=4096,  # Increased limit
            messages=messages,
            tools=tools,
        )

tool_use หมายถึง Claude กำลังรอคุณอยู่ ให้รัน Tool นั้นแล้วส่งผลลัพธ์กลับไป ส่วน Server Tool Call ที่ยังไม่มี Result Block จะถูกประมวลผลต่อใน Response ถัดไป คุณจึงไม่ต้องจัดการด้วยตัวเอง สำหรับ pause_turn หมายถึง Server-tool Loop ชนเพดาน Iteration ให้ส่ง Assistant Content กลับไปตามเดิม Claude จะทำงานต่อจากจุดที่ค้างไว้ทันที

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
Any max_tokens stop can be fixed by asking Claude to continue. (ทำไมถึงผิด): When the truncated content ends in an incomplete tool_use block, the request has to be retried with a higher max_tokens to get the full tool call.

max_tokens แก้ได้เสมอโดยการสั่งให้ Claude ทำงานต่อ (Continue)? (ทำไมถึงผิด): ไม่จริง: หาก Content ที่ถูกตัดตอนลงท้ายด้วยบล็อก tool_use ที่ไม่สมบูรณ์ คุณไม่สามารถสั่ง Continue ต่อได้ แต่ต้อง Retry คำขอใหม่ทั้งหมดด้วยค่า max_tokens ที่สูงขึ้นเพื่อให้ได้ Tool Call ที่สมบูรณ์

A response stops with stop_reason "max_tokens", and its last content block is a tool_use. What should your code do?

คำแปลโจทย์:
การตอบสนองหยุดด้วย stop_reason "max_tokens" และบล็อกเนื้อหาสุดท้ายคือ tool_use รหัสของคุณควรทำอย่างไร?
คำตอบที่ถูกต้อง: ตัวเลือก C
💡 Official Explanation (คำอธิบายเฉลย):

A tool_use block cut off by the token limit has incomplete input. The fix is to retry with more room, not to run a partial call or continue the turn.

คำแปลไทย:
บล็อก tool_use ที่ถูกตัดออกด้วยขีดจำกัดโทเค็นมีอินพุตที่ไม่สมบูรณ์ การแก้ไขคือการลองอีกครั้งโดยมีพื้นที่มากขึ้น ไม่ใช่เรียกใช้ API Call บางส่วนหรือดำเนินการเทิร์นต่อ
“the truncated response contains an incomplete tool use block, you'll need to retry the request with a higher max_tokens value”
คำแปล: การตอบสนองที่ถูกตัดทอนมีบล็อกการใช้เครื่องมือที่ไม่สมบูรณ์ คุณจะต้องลองคำขออีกครั้งด้วยค่า max_tokens ที่สูงกว่า

Three stop reasons mean the work isn't finished. With max_tokens and model_context_window_exceeded the output was cut off. 5. Well-formed output ไม่ได้แปลว่า Correct output

Schema การันตีแค่ Shape (รูปแบบข้อมูล) แต่ไม่ได้การันตีความถูกต้องของเนื้อหา Constrained decoding บังคับให้ field `total_amount` ออกมาเป็น float ได้ แต่ไม่ได้การันตีว่ามันคือยอดรวมจริงบนใบแจ้งหนี้ ข้อความที่อ่านลื่นไหลและ Valid ตาม Schema ก็ยังผิดพลาดได้จากกลไก [Next-token generation และ Hallucination](lesson:5.1) แม้กระทั่ง field อย่าง `confidence: 0.92` ก็เป็นเพียง Output จากโมเดลที่ถูกบังคับให้อยู่ในรูปตัวเลขเท่านั้น ดังนั้น จงมอง Valid output ที่ดูน่าเชื่อถือว่าเป็นเพียง 'สมมติฐาน' ที่ต้องนำไป Verify เทียบกับ Source เสมอ

เทคนิค Grounding และ Verification ต่อไปนี้ ช่วยเปลี่ยนการตรวจสอบให้กลายเป็น Pipeline อัตโนมัติในระบบของคุณได้:

  • •
    Quote first: สำหรับเอกสารขนาดยาว ให้ Claude ดึงข้อความอ้างอิงแบบคำต่อคำ (word-for-word quotes) ออกมาก่อนเริ่มทำ Task และบังคับให้วิเคราะห์จาก Quote เหล่านั้นเท่านั้น
  • •
    Cite and retract: กำหนดให้ทุก Claim ต้องมี Quote ซัพพอร์ต หากไม่มี Quote รองรับ ให้ตัด Claim นั้นทิ้งทันที
  • •
    Best-of-N: ยิง Prompt เดิมซ้ำกันหลายครั้ง (N ครั้ง) แล้วนำผลลัพธ์มาเปรียบเทียบกัน หาก Output มีความขัดแย้งกันแสดงว่าอาจเกิด Hallucination
  • •
    Allow uncertainty: อนุญาตให้ Claude ตอบตรงๆ ได้ว่า 'ข้อมูลไม่เพียงพอ' ใน Prompt อย่างชัดเจน เพื่อป้องกันไม่ให้โมเดลพยายามแต่งเติมข้อมูลเพื่อเติมเต็มช่องว่าง
  • •
    Restrict knowledge: สั่ง Claude ให้ดึงข้อมูลเฉพาะจากเอกสารที่ให้ไปเท่านั้น โดยห้ามใช้ General knowledge ของตัวเอง

Quotes คือจุดสำคัญที่ทำให้ Code สามารถทำ Automated Verification ได้ หากคุณออกแบบ Schema ให้ส่ง Quote กำกับไว้ข้างๆ แต่ละ Value ที่สกัดออกมา Validator ของคุณจะสามารถตรวจสอบได้ทันทีว่า Quote นั้นมีอยู่จริงใน Source document หรือไม่ ก่อนที่จะยอมรับ Record นั้นเข้าสู่ระบบ

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

➔ Extract word-for-word quotes from the document before performing the task แยกข้อความที่อ้างอิงจากเอกสารทีละคําก่อนทํางาน
2 Citation verification (การตรวจสอบการอ้างอิง)
➔ Find a supporting quote for each claim and retract claims without one ค้นหาข้อเสนอสนับสนุนสําหรับแต่ละข้อเรียกร้องและเพิกถอนข้อเรียกร้องโดยไม่มีข้อเสนอ
3 Best-of-N verification (การตรวจสอบที่ดีที่สุดของ N)
➔ Run the same prompt several times and treat disagreement as a warning sign เรียกใช้ Prompt เดียวกันหลายครั้งและจัดการข้อขัดแย้งเป็นสัญญาณเตือน
4 External knowledge restriction (การจํากัดความรู้ภายนอก)
➔ Limit answers to the provided documents rather than general knowledge จํากัดคําตอบในเอกสารที่ให้ไว้ แทนที่จะเป็นความรู้ทั่วไป
💡 Key Takeaway (หลักการสำคัญ):

Each technique ties the output back to evidence. Quotes ground the analysis, citations make each claim auditable, repeated runs expose instability, and restriction keeps answers inside the documents.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A schema guarantees shape, not truth. Constrained decoding makes total_amount a float. It doesn't make it the total printed on the invoice. Fluent, well-formed text can still be wrong because of how [next-token generation and hallucination](lesson:5.1) work. A confidence: 0.92 field is also model output, constrained to be a number and nothing more. Treat confident, valid output as a claim to check against your sources.

Several grounding and verification techniques turn that check into steps your pipeline can run:

- Quote first: for long documents, have Claude extract word-for-word quotes before doing the task, and base the analysis only on those quotes. - Cite and retract: require a supporting quote for each claim, and remove any claim that has no quote. - Best-of-N: run the same prompt several times and compare the results. Inconsistencies across outputs could indicate hallucinations. - Allow uncertainty: give Claude explicit permission to say it doesn't have enough information, so it doesn't fill the gap. - Restrict knowledge: tell Claude to use only the provided documents and not its general knowledge.

Quotes are what make this something code can verify. If the schema asks for the supporting quote next to each extracted value, your validator can check that the quote really appears in the source document before it accepts the record.
