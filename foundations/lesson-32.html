1.Read stop_reason before the content

สาระสำคัญและหลักการทำงานของหัวข้อนี้: หัวข้อนี้เจาะลึก Read stop_reason before the content ตามมาตรฐานและพิมพ์เขียวการสอบของ Anthropic โดยมุ่งเน้นการทำความเข้าใจสถาปัตยกรรมเชิงลึก ข้อดีข้อเสียทางเทคนิค และแนวทางการปฏิบัติจริงในโปรดักชัน
stop_reasonWhen it occursWhat to do
end_turnClaude finished its response naturally.Use the response.
max_tokensThe response reached your max_tokens limit.Raise max_tokens or continue the response.
stop_sequenceClaude emitted one of your stop_sequences.Read stop_sequence to see which one fired.
tool_useClaude is calling a tool.Run the tool and return the result.
pause_turnA server-tool loop reached its iteration limit.Send the assistant content back to continue.
refusalClaude declined to respond.Read stop_details and retry on a fallback model.
model_context_window_exceededThe response filled the model's context window.Treat the response as truncated.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Read stop_reason before the content" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Every successful Messages API response has a stop_reason field that says why Claude stopped generating. It is not an error. Errors mean the request failed, while a stop reason describes a completed generation. A response can be a 200 and still be unusable as an answer. Have your pipeline branch on stop_reason before it reads the content. That one field decides whether you use the response, continue it, retry it or send it to another model.

A team builds a pipeline that extracts contact fields (name, email, plan) from support tickets and feeds them directly into a database insert without any try/except around the JSON parsing step. The pipeline occasionally crashes because Claude's response includes explanatory text before the JSON or omits a required field. What is the most effective fix to guarantee schema conformance without relying on prompt wording alone?

A Add a system-prompt instruction telling Claude to output only JSON and no other text
B Configure Structured Outputs with a JSON schema in the API's output format field
C Raise max_tokens so Claude has enough room to finish writing the full JSON object
D Have Claude wrap the JSON in triple backticks and strip them during post-processing
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก B
ตัวเลือก A: ไม่ถูกต้อง

Incorrect. Wording instructions can reduce but never guarantee stray text or missing fields; Claude can still deviate under load or ambiguity, so the pipeline remains fragile.

ตัวเลือก B: ถูกต้อง

Correct. Structured Outputs constrains generation to a declared JSON schema, guaranteeing valid, schema-conforming JSON in the response text and removing the need for prompt-based hoping.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Truncation from running out of tokens is a separate failure mode from stray prose or omitted fields; more tokens doesn't enforce schema conformance.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Backtick stripping only addresses one formatting quirk and does nothing to guarantee required fields are present or types are correct.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Three stop reasons mean the work isn't finished. With max_tokens and model_context_window_exceeded the output was cut off. Text that ends mid-thought is a fragment, not an answer, and it should never reach a parser or a user as if it were complete. You can usually continue a truncated text response. A server tool call that doesn't have its result block yet completes in a later response, so you don't answer it yourself. pause_turn means a server-tool loop hit its iteration limit. Send the assistant content back as it is, and Claude continues from where it stopped.

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Claude Fable 5.1, Fable 5, Opus 5.5, Opus 5 and Sonnet 5.5 include safety classifiers that can decline a request. A decline comes back as an ordinary response, so a pipeline that only catches exceptions will miss it. A loop that reads response.content[0] will crash on an empty list. A refusal looks like this:

Branch on stop_details.category, not on the explanation. The explanation text isn't stable, so show it to people and don't parse it. Both fields can be null when a refusal doesn't map to a named category, and that is a normal, permanent value. A refusal can also come mid-stream, after some output has already arrived. Discard that partial output rather than keeping it. To recover, send the same request to another Claude model. The beta fallbacks="default" setting does this on the server side, using the fallback model recommended for the refusal's category.

A response can end with end_turn and still contain nothing. [Empty end_turn responses](lesson:4.1) usually appear after tool results, when Claude decides the turn is over. In a validation pipeline, that means end_turn alone isn't a passing check. Put the guard next to the stop-reason branch: if response.stop_reason == "end_turn" and not response.content:. Then handle that case explicitly instead of passing an empty list to a parser.

First fix the message structure, so there are no text blocks straight after tool results. Only if that doesn't work, add a continuation prompt in a new user message.

A summarization service parses the response text as JSON. For very long transcripts, the JSON string is occasionally cut off mid-object and the parser raises a decode error. Investigating, the engineer finds stop_reason is "max_tokens" on every one of the failing calls. What should the defensive parsing logic do?

A Catch the decode error, check stop_reason for max_tokens, and treat the response as incomplete
B Ignore stop_reason and retry parsing with a lenient JSON parser that tolerates trailing commas
C Lower max_tokens further so Claude is forced to produce shorter, safer completions
D Treat every JSON decode error as a transient network issue and resend the identical request
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. stop_reason "max_tokens" is the documented signal that the response was cut off before completion; defensive code should branch on it and handle the response as incomplete rather than as malformed JSON.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. A lenient parser might mask trailing-comma typos, but it cannot recover data that was never generated because the response was truncated mid-object.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Lowering max_tokens makes truncation more likely, not less, worsening the exact failure being investigated.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. The failures are explained by output length, not network transience; blindly resending the same request risks the same truncation again.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A schema guarantees shape, not truth. Constrained decoding makes total_amount a float. It doesn't make it the total printed on the invoice. Fluent, well-formed text can still be wrong because of how [next-token generation and hallucination](lesson:5.1) work. A confidence: 0.92 field is also model output, constrained to be a number and nothing more. Treat confident, valid output as a claim to check against your sources.

Several grounding and verification techniques turn that check into steps your pipeline can run:

- Quote first: for long documents, have Claude extract word-for-word quotes before doing the task, and base the analysis only on those quotes. - Cite and retract: require a supporting quote for each claim, and remove any claim that has no quote. - Best-of-N: run the same prompt several times and compare the results. Inconsistencies across outputs could indicate hallucinations. - Allow uncertainty: give Claude explicit permission to say it doesn't have enough information, so it doesn't fill the gap. - Restrict knowledge: tell Claude to use only the provided documents and not its general knowledge.

Quotes are what make this something code can verify. If the schema asks for the supporting quote next to each extracted value, your validator can check that the quote really appears in the source document before it accepts the record.
