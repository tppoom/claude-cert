💡 แนวคิดหลักสำคัญ (Key Concept)

Tool use as a contract — You declare which operations exist and what shape their inputs take. Claude decides when to call them and sends back a structured request. Claude never runs code itself: your application or Anthropic's servers carry out the call and return the result.

1. Where a tool runs decides what you build

Tool use (also called function calling) lets Claude call functions that you define or that Anthropic provides

Before writing any schema, decide where the tool's code will run

The docs treat this as the main way tools differ, and it fixes what your application is responsible for

There are three buckets User-defined client tools carry most tool-use traffic: you write the schema, run the code, and return the result

Anthropic-schema client tools (memory, bash, text_editor, computer, browser) work the same way, except Anthropic publishes the schema

Server-executed tools (web_search, web_fetch, code_execution, tool_search) run on Anthropic's infrastructure, so you never build a tool_result for them.

คุณสามารถเขียนเครื่องมือเชลล์ของคุณเองได้? Claude ได้รับการปรับให้เหมาะสมกับเส้นทางที่ประสบความสําเร็จหลายเส้นทางที่ใช้ลายเซ็นที่แน่นอนเหล่านั้น ด้วยเหตุนี้จึงเรียกใช้งานได้อย่างน่าเชื่อถือมากขึ้นและกู้คืนจากข้อผิดพลาดได้ดีกว่าที่ทํากับแบบที่เทียบเท่ากันแบบกําหนดเอง

ที่เก็บข้อมูลทั้งสามแยกออกเป็นสองทาง: เครื่องมือฝั่งไคลเอ็นต์และฝั่งเซิร์ฟเวอร์ เครื่องมือฝั่งไคลเอ็นต์ (ที่ผู้ใช้กำหนดและ Anthropic-schema) ทำงานในแอปพลิเคชันของคุณ Claude ตอบด้วย stop_reason: "tool_use" และบล็อก tool_use หนึ่งบล็อกขึ้นไป รหัสของคุณเรียกใช้แต่ละครั้ง และ

คุณส่งบล็อก tool_result กลับมา เนื่องจากโมเดลไม่สามารถเรียกใช้โค้ดของคุณได้ การโทรทุกครั้งจึงเป็นไปกลับ และแอปพลิเคชันของคุณขับเคลื่อน while loop ซึ่งจะดำเนินต่อไปตราบเท่าที่ stop_reason คือ tool_use หากเครื่องมือไคลเอ็นต์ล้มเหลว คุณจะรายงานด้วย is_error: true เครื่องมือฝั่งเซิร์ฟเวอร์ทำงานบนโครงสร้างพื้นฐานของ Anthropic ภายในลูปของตัวเอง การตอบสนองประกอบด้วยบล็อก server_tool_use ที่แสดงสิ่งที่ทำงานและสิ่งที่กลับมา คุณไม่เคยสร้าง tool_result และ

คุณไม่จัดการกับ is_error สำหรับสิ่งเหล่านั้น สองกรณีต้องการความสนใจของคุณ หากลูปเซิร์ฟเวอร์ถึงขีดจำกัดการวนซ้ำ การตอบกลับจะมี stop_reason: "pause_turn" และ

คุณส่งการสนทนาอีกครั้ง รวมถึงการตอบกลับที่หยุดชั่วคราวและเครื่องมือเดียวกัน เพื่อให้ Claude ดำเนินการต่อ หาก Claude เรียกใช้เครื่องมือเซิร์ฟเวอร์และเครื่องมือไคลเอนต์ในกลุ่มเดียวกันของการเรียกแบบขนาน API จะยังไม่เรียกใช้เครื่องมือเซิร์ฟเวอร์: การตอบสนองมี stop_reason: "tool_use" และบล็อก server_tool_use ที่ไม่มีบล็อกผลลัพธ์ คุณส่งคืนบล็อก tool_result ของไคลเอ็นต์ เก็บอาร์เรย์เครื่องมือเดิมไว้ จากนั้น API จะรันเครื่องมือเซิร์ฟเวอร์ที่เลื่อนออกไป

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Exam Trap: Server-side tools need the same handling as client-side tools: build a tool_result and set is_error on failures. (ทำไมถึงผิด): Only client tools need your tool_result and is_error handling. Server tools run in Anthropic's own loop and show up as server_tool_use blocks. The exceptions to watch for are pause_turn and a turn that mixes server and client tools.

🇹🇭 คำอธิบายเจาะลึก: Exam Trap: เครื่องมือฝั่งเซิร์ฟเวอร์ต้องการการจัดการแบบเดียวกันกับเครื่องมือฝั่งไคลเอ็นต์: สร้าง tool_result และตั้งค่า is_error สําหรับความล้มเหลว (ทําไมถึงผิดพลาด): เฉพาะเครื่องมือฝั่งไคลเอ็นต์เท่านั้นที่ต้องการ tool_result ของคุณและการจัดการ is_error เครื่องมือฝั่งเซิร์ฟเวอร์ทํางานในลูปของตัวเองของ Anthropic และปรากฏเป็นบล็อก server_tool_use ข้อยกเว้นที่ควรระวังคือ pause_turn และ turn ที่ผสมผสานเครื่องมือฝั่งเซิร์ฟเวอร์และฝั่งไคลเอ็นต์

A response has stop_reason "tool_use" and contains a server_tool_use block with no result block, plus a client tool_use block. What do you do?

🇹🇭 คำแปลโจทย์: การตอบสนองมี stop_reason “tool_use” และมีบล็อก server_tool_use โดยไม่มีบล็อกผลลัพธ์ รวมถึงบล็อก client tool_use คุณจะทําอย่างไร
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Official Explanation (คำอธิบายเฉลย):

In a mixed turn the API holds the server tool until you return the client tool results. Unlike pause_turn, you continue with tool_result blocks rather than re-sending the response.

🇹🇭 คำแปลไทย: ในรอบผสม API จะเก็บเครื่องมือเซิร์ฟเวอร์ไว้จนกว่าคุณจะส่งคืนผลลัพธ์เครื่องมือไคลเอนต์ ต่างจาก Pause_turn ตรงที่คุณดำเนินการต่อด้วยบล็อก tool_result แทนที่จะส่งคำตอบซ้ำ

Tool use (also called function calling) lets Claude call functions that you define or that Anthropic provides. Before writing any schema, decide where the tool's code will run. The docs treat this as the main way tools differ, and it fixes what your application is responsible for. There are three buckets. User-defined client tools carry most tool-use traffic: you write the schema, run the code, and return the result. Anthropic-schema client tools (memory, bash, text_editor, computer, browser) work the same way, except Anthropic publishes the schema. Server-executed tools (web_search, web_fetch, code_execution, tool_search) run on Anthropic's infrastructure, so you never build a tool_result for them.

Why use Anthropic's bash schema when you could write your own shell tool? Claude has been optimized on many successful trajectories that use those exact signatures. As a result it calls them more reliably and recovers from errors better than it would with a custom equivalent.

The three buckets collapse into a two-way split: client-side vs. server-side tools. Client-side tools (user-defined and Anthropic-schema) run in your application. Claude answers with stop_reason: "tool_use" and one or more tool_use blocks, your code runs each call, and you send back a tool_result block. Because the model can't run your code, every call is a round trip, and your application drives a while loop that continues as long as stop_reason is tool_use. If a client tool fails, you report it with is_error: true. Server-side tools run on Anthropic's infrastructure inside their own loop. The response contains server_tool_use blocks showing what ran and what came back, you never construct a tool_result, and you don't handle is_error for them. Two cases need your attention. If the server loop hits its iteration limit, the response has stop_reason: "pause_turn", and you re-send the conversation, including the paused response and the same tools, to let Claude continue. If Claude calls a server tool and a client tool in the same group of parallel calls, the API does not run the server tool yet: the response has stop_reason: "tool_use" and a server_tool_use block with no result block. You return the client tool_result blocks, keep the same tools array, and the API then runs the deferred server tool.

4. Building a tool set that scales

Good individual tools can still add up to a confusing set

Anthropic gives three construction rules

Consolidate: one tool with an action parameter beats separate create_pr, review_pr, and merge_pr tools, because fewer tools leave less room for picking the wrong one

Namespace: when tools span services, prefix names with the service, as in github_list_prs and slack_send_message

This matters most when you use tool search

Return high-signal results: send back stable, meaningful identifiers such as slugs or UUIDs, and only the fields Claude needs for its next step

Bloated responses waste context.

Also check that a task needs a tool in the first place

Tools fit side effects, fresh or external data, outputs that must have a fixed shape, and calls into existing systems

They don't fit summarization, one-shot Q&A, or trivial work where the extra round trip would dominate

Anthropic's rule of thumb: if you're writing a regex to extract a decision from model output, that decision should have been a tool call.

Good individual tools can still add up to a confusing set. Anthropic gives three construction rules. Consolidate: one tool with an action parameter beats separate create_pr, review_pr, and merge_pr tools, because fewer tools leave less room for picking the wrong one. Namespace: when tools span services, prefix names with the service, as in github_list_prs and slack_send_message. This matters most when you use tool search. Return high-signal results: send back stable, meaningful identifiers such as slugs or UUIDs, and only the fields Claude needs for its next step. Bloated responses waste context.

Also check that a task needs a tool in the first place. Tools fit side effects, fresh or external data, outputs that must have a fixed shape, and calls into existing systems. They don't fit summarization, one-shot Q&A, or trivial work where the extra round trip would dominate. Anthropic's rule of thumb: if you're writing a regex to extract a decision from model output, that decision should have been a tool call.

The request also controls *whether* Claude calls tools. With the default tool_choice of auto, Claude decides on each turn. You can push it with the system prompt: "Use the tools to investigate before responding." increases tool use. To require a call rather than rely on prompting, set tool_choice. Adding disable_parallel_tool_use: true limits Claude to at most one tool call per turn.

Forcing a tool has costs. With any or tool, the API prefills the assistant turn, so Claude writes no explanation before its tool_use blocks. Forced tool use also isn't supported everywhere. Manual extended thinking rejects any and tool. On Claude Opus 5.5, Claude Sonnet 5.5, Claude Fable 5.1, and Claude Mythos 5.1, any and tool return a 400 error. On those models, use auto with strict tool use, or use structured outputs. Server tools need very little setup: you enable them with a date-versioned type. For remote MCP servers, the MCP connector connects from the Messages API without a separate MCP client.
