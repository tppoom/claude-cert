ทำไมถึงควรใช้ bash schema ของ Anthropic แทนการเขียน Shell tool ขึ้นมาเอง? เพราะ Claude ได้รับการ Optimize ผ่าน Trajectory จำลองงานจริงจำนวนมากที่ใช้ Signature เหล่านี้ ทำให้เรียกใช้งานได้แม่นยำกว่า และสามารถ Recover จาก Error ได้ดีกว่าการใช้ Tool ที่คุณเขียนขึ้นมาเองใหม่

  1. 1
    หาก Server loop ทำงานชนขีดจำกัด (Iteration limit) Response จะมี stop_reason: "pause_turn" คุณต้องส่ง Conversation ทั้งหมดกลับไปใหม่ (รวมถึง Paused response และ Tools ชุดเดิม) เพื่อให้ Claude ทำงานต่อ
  2. 2
    หาก Claude สั่งรันทั้ง Server tool และ Client tool พร้อมกันแบบ Parallel API จะยังไม่รัน Server tool ทันที แต่จะส่ง stop_reason: "tool_use" พร้อม server_tool_use block ที่ยังไม่มีผลลัพธ์ ให้คุณส่ง tool_result ของ Client tool กลับไปก่อนโดยคง Tools array เดิมไว้ จากนั้น API จะนำ Server tool ที่พักไว้ไปรันต่อให้อัตโนมัติ
⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
Server-side tools need the same handling as client-side tools: build a tool_result and set is_error on failures. (ทำไมถึงผิด): Only client tools need your tool_result and is_error handling. Server tools run in Anthropic's own loop and show up as server_tool_use blocks. The exceptions to watch for are pause_turn and a turn that mixes server and client tools.

คำถามหลอก / สิ่งที่มักเข้าใจผิด? (ทำไมถึงผิด): ไม่จริง: Server-side tools ไม่ได้จัดการเหมือน Client-side tools เพราะไม่ต้องสร้าง tool_result หรือคอยเซ็ต is_error เอง เนื่องจาก Server tools รันใน Loop ของ Anthropic และตอบกลับมาเป็น server_tool_use block ทั้งหมด จุดที่ต้องระวังมีเพียง 2 กรณีคือ การจัดการ stop_reason: "pause_turn" และรอบที่เกิดการเรียกแบบผสมระหว่าง Server กับ Client tools พร้อมกัน

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Tool use (also called function calling) lets Claude call functions that you define or that Anthropic provides. Before writing any schema, decide where the tool's code will run. The docs treat this as the main way tools differ, and it fixes what your application is responsible for. There are three buckets. User-defined client tools carry most tool-use traffic: you write the schema, run the code, and return the result. Anthropic-schema client tools (memory, bash, text_editor, computer, browser) work the same way, except Anthropic publishes the schema. Server-executed tools (web_search, web_fetch, code_execution, tool_search) run on Anthropic's infrastructure, so you never build a tool_result for them.

Why use Anthropic's bash schema when you could write your own shell tool? Claude has been optimized on many successful trajectories that use those exact signatures. As a result it calls them more reliably and recovers from errors better than it would with a custom equivalent.

The three buckets collapse into a two-way split: client-side vs. server-side tools. Client-side tools (user-defined and Anthropic-schema) run in your application. Claude answers with stop_reason: "tool_use" and one or more tool_use blocks, your code runs each call, and you send back a tool_result block. Because the model can't run your code, every call is a round trip, and your application drives a while loop that continues as long as stop_reason is tool_use. If a client tool fails, you report it with is_error: true. Server-side tools run on Anthropic's infrastructure inside their own loop. The response contains server_tool_use blocks showing what ran and what came back, you never construct a tool_result, and you don't handle is_error for them. Two cases need your attention. If the server loop hits its iteration limit, the response has stop_reason: "pause_turn", and you re-send the conversation, including the paused response and the same tools, to let Claude continue. If Claude calls a server tool and a client tool in the same group of parallel calls, the API does not run the server tool yet: the response has stop_reason: "tool_use" and a server_tool_use block with no result block. You return the client tool_result blocks, keep the same tools array, and the API then runs the deferred server tool.

You declare client tools in the top-level tools parameter of the request. A user-defined tool has a name, which must match ^[a-zA-Z0-9_-]{1,128}$. It also has a plaintext description and an input_schema, which is a JSON Schema object for the parameters. Behind the scenes, the API turns these definitions into a special system prompt, so everything you write in them becomes context for Claude.

Two optional fields make tool calls more dependable. input_examples is an array of sample inputs, which helps most with nested objects and format-sensitive parameters. Every example has to validate against input_schema, otherwise the request returns a 400. Examples also cost prompt tokens, and they don't work on server tools or on the computer use and browser use toolsets. strict: true turns on grammar-constrained sampling. That guarantees the inputs match your schema, so you get passengers: 2 and never the string "two".

    แทนที่จะปล่อยให้ Claude แยกวิเคราะห์ข้อมูลที่คลุมเครือ และข้อความให้คำแนะนำ (สิ่งที่ล้มเหลว สิ่งที่ควรลองต่อไป) ช่วยให้ Claude มีบริบทที่จำเป็นในการแจ้งผู้ใช้หรือลองอีกครั้งอย่างเหมาะสม
ตัวเลือก B: ตัวเลือกที่ไม่ถูกต้อง

Omitting `is_error` forces Claude to guess whether the returned content is valid invoice data or an error body, risking the 503 payload being treated as real data instead of being surfaced as a failure.

คำแปล:
  • ▸
    การละเว้น `is_error` จะบังคับให้ Claude คาดเดาว่าเนื้อหาที่ส่งคืนนั้นเป็นข้อมูลใบแจ้งหนี้ที่ถูกต้องหรือเนื้อหาข้อผิดพลาด ส่งผลให้น้ำหนักบรรทุก 503 เสี่ยงที่จะถือเป็นข้อมูลจริง
  • ▸
    แทนที่จะถูกแสดงเป็นความล้มเหลว
ตัวเลือก C: ตัวเลือกที่ไม่ถูกต้อง

Every `tool_use` block must be immediately followed by a matching `tool_result`; omitting it produces a malformed message sequence and the API will reject the request.

คำแปล:
ทุกบล็อก `tool_use` จะต้องตามด้วย `tool_result` ที่ตรงกันทันที การละเว้นจะสร้างลําดับข้อความที่ผิดรูปและ API จะปฏิเสธคําขอ
ตัวเลือก D: ตัวเลือกที่ไม่ถูกต้อง

Marking a failed call as `is_error: false` with empty content misrepresents the outcome, and Claude has no signal that the billing API call did not succeed.

คำแปล:
การทำเครื่องหมาย API Call ที่ล้มเหลวเป็น `is_error: false` ด้วยเนื้อหาว่างเปล่าเป็นการบิดเบือนผลลัพธ์ และ Claude ไม่มีสัญญาณว่าการเรียก API การเรียกเก็บเงินไม่สำเร็จ

Good individual tools can still add up to a confusing set. Anthropic gives three construction rules. Consolidate: one tool with an action parameter beats separate create_pr, review_pr, and merge_pr tools, because fewer tools leave less room for picking the wrong one. Namespace: when tools span services, prefix names with the service, as in github_list_prs and slack_send_message. This matters most when you use tool search. Return high-signal results: send back stable, meaningful identifiers such as slugs or UUIDs, and only the fields Claude needs for its next step. Bloated responses waste context.

Also check that a task needs a tool in the first place. Tools fit side effects, fresh or external data, outputs that must have a fixed shape, and calls into existing systems. They don't fit summarization, one-shot Q&A, or trivial work where the extra round trip would dominate. Anthropic's rule of thumb: if you're writing a regex to extract a decision from model output, that decision should have been a tool call.

5. การกำหนดค่า Request สำหรับระบบภายนอก: tool_choice และ Server Tools

The request also controls *whether* Claude calls tools. With the default tool_choice of auto, Claude decides on each turn. You can push it with the system prompt: "Use the tools to investigate before responding." increases tool use. To require a call rather than rely on prompting, set tool_choice. Adding disable_parallel_tool_use: true limits Claude to at most one tool call per turn.

Forcing a tool has costs. With any or tool, the API prefills the assistant turn, so Claude writes no explanation before its tool_use blocks. Forced tool use also isn't supported everywhere. Manual extended thinking rejects any and tool. On Claude Opus 5.5, Claude Sonnet 5.5, Claude Fable 5.1, and Claude Mythos 5.1, any and tool return a 400 error. On those models, use auto with strict tool use, or use structured outputs. Server tools need very little setup: you enable them with a date-versioned type. For remote MCP servers, the MCP connector connects from the Messages API without a separate MCP client.
