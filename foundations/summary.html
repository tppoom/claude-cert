💡 แก่นสถาปัตยกรรม (Core Architectural Law)

สิทธิ์การควบคุม Control Flow — เส้นแบ่งระหว่าง Workflow และ Agent คือผู้กำหนดขั้นตอนถัดไป สำหรับ Workflow โค้ดที่เขียนจะล็อกลำดับการเรียก LLM และ Tool ไว้ตายตัว ส่วน Agent ตัวโมเดลจะตัดสินใจเลือกขั้นตอนและ Tool ที่ต้องเรียกใช้เองที่ Runtime

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: Orchestrator-workers ก็แค่ Parallelization ที่เพิ่ม LLM เข้ามาครอบอีกตัว?
✓ ความจริง: ไม่จริง: แม้หน้าตาจะคล้ายกัน แต่ใน Orchestrator-workers ตัว Model จะเป็นผู้กำหนด Subtasks เองที่ Runtime ตาม Input ส่วน Parallelization นั้น Subtasks ทั้งหมดถูกกำหนดตายตัวไว้ล่วงหน้า
❌ เข้าใจผิด: Autonomous agent เป็นตัวเลือกที่ดีกว่า Workflow เสมอ?
✓ ความจริง: ไม่จริง: Agentic Systems ต้องแลก Latency และ Cost ที่สูงขึ้นกับ Performance สำหรับงานที่ Requirement ชัดเจนและตายตัว การใช้ Workflow หรือแม้แต่การ Optimize ให้เหลือ Single Call เพียงครั้งเดียว มักเป็นการออกแบบที่มีประสิทธิภาพและเหมาะสมกว่า
❌ เข้าใจผิด: Orchestrator มองเห็นทุก Tool Call และไฟล์ทั้งหมดที่ Subagent เปิดทำงาน?
✓ ความจริง: ไม่จริง: Intermediate Work ทั้งหมดของ Subagent จะถูกแยกและกักไว้ใน Conversation Context ของตัวเองเท่านั้น Parent Agent จะได้รับเพียงข้อความสรุปสุดท้าย (Final Message)
❌ เข้าใจผิด: การกระจายงานให้ Subagents ทำงานแบบ Parallel จะทำให้งานโดยรวมเสร็จเร็วกว่า Single Agent เสมอ?
✓ ความจริง: ไม่จริง: Parallelism มีไว้เพื่อเพิ่ม Coverage (ความครอบคลุมและละเอียดถี่ถ้วน) ระบบ Multi-Agent มีปริมาณ Total Work มากกว่าเดิมมหาศาล ทำให้เวลารวมทั้งหมดมักนานกว่า Single Agent
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •เปรียบตัวเลือกต่างๆ เป็นขั้นบันได (Autonomy Ladder) แต่ละขั้นจะส่งมอบ Control Flow ให้กับ Model มากขึ้นเรื่อยๆ โดยมี [Workflow Patterns ทั้ง 5 แบบ (Prompt Chaining, Routing, Parallelization, Orchestrator-Workers, Evaluator-Optimizer)](lesson:1.3) คั่นอยู่ระหว่าง Single Call กับ Fully Autonomous Agent ซึ่งส่วนใหญ่ยังคงลำดับขั้นตอนไว้ในโค้ด ยกเว้น Orchestrator-Workers ที่ Model เริ่มเข้ามามีบทบาทในการกำหนด Subtasks เองแบบ Dynamic ตาม Input ที่ได้รับ โดยไม่ได้ถูกกำหนดไว้ล่วงหน้า
  • •ฟีเจอร์ Research ของ Anthropic คือตัวอย่าง Production ของโครงสร้างนี้ LeadResearcher จะวางแผนและบันทึก Plan ลง Memory (เพื่อแก้ปัญหา Context ถูกตัดทอนหากเกิน 200,000 Tokens) จากนั้นจะสร้าง Subagents เพื่อทำงาน Research เฉพาะด้าน โดย Subagent แต่ละตัวจะค้นหาข้อมูลอิสระและส่งผลลัพธ์กลับมา Lead Agent จะรวบรวมข้อมูลและประเมินว่าต้องค้นหาเพิ่มหรือไม่ เมื่อข้อมูลเพียงพอ CitationAgent จะทำหน้าที่เชื่อมโยงข้อความกับ Sources ต้นทาง สถาปัตยกรรมนี้ใช้ Claude Opus 4 เป็น Lead และ Claude Sonnet 4 เป็น Subagents ซึ่งทำคะแนนชนะ Single-Agent Claude Opus 4 ได้ถึง 90.2% บน Internal Research Evaluation
  • •Specialization ยังช่วยเสริมเรื่อง Safety อีกด้วย โดยใน Agent SDK แต่ละ Subagent สามารถมี System Prompt แยกเฉพาะและจำกัด Toolset ได้ เช่น กำหนดให้ Reviewer Agent ถือเฉพาะ Read-only Tools เพื่อวิเคราะห์ไฟล์ได้แต่ไม่มีสิทธิ์แก้ไข

Agent Harness — โค้ดที่ควบคุม Agent Loop รอบตัวโมเดล ทำหน้าที่ส่ง Prompt, รัน Tools ตามที่ Claude ร้องขอ, ส่งผลลัพธ์กลับ และกำหนดเงื่อนไขการหยุด โดยความแตกต่างหลักของแต่ละวิธีสร้าง Claude Agent คือใครเป็นผู้พัฒนาและรัน Harness นั้น: ตัวคุณเอง, Library ภายใน Process ของคุณ หรือ Anthropic

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: Managed Agents สามารถใช้กับ Workload ที่ต้องการ Zero Data Retention (ZDR) ได้หรือไม่?
✓ ความจริง: ไม่จริง: Managed Agents ถูกออกแบบมาให้จัดเก็บ Session History, สถานะ Sandbox และ Outputs ไว้บน Server จึงยังไม่รองรับ ZDR หรือ HIPAA BAA ในปัจจุบัน
❌ เข้าใจผิด: Self-hosted Sandbox หมายถึงทั้ง Agent และ Model Calls จะรันอยู่บน Infrastructure ของคุณทั้งหมด?
✓ ความจริง: ไม่จริง: มีเพียงแค่การ Execute Tools เท่านั้นที่ย้ายมารันบน Host ของคุณ ส่วน Orchestration และ Model Inference ยังคงอยู่ที่ Anthropic โดย Tool Inputs และ Outputs ยังต้องถูกส่งกลับไปยัง Control Plane ของ Anthropic เสมอ

The Agent SDK query() loop, hooks and subagents

💡 แก่นสถาปัตยกรรม (Core Architectural Law)

การควบคุม Execution Loop ของ Agent SDK ด้วยการจัดการ Message Stream, การจำกัดทรัพยากร (Limits), การแทรกการทำงานด้วย Hooks และการประสานงาน Subagents

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: Stream จะจบลงทันทีที่ ResultMessage ส่งมาถึง จึงสามารถ break ออกจาก Loop ได้เลย?
✓ ความจริง: ไม่จริง: อาจยังมี Trailing System Events (เช่น prompt_suggestion) ถูกส่งตามหลัง ResultMessage มาอีก จึงควรอ่าน Message ต่อเนื่องจนกว่า Stream จะสิ้นสุดจริงๆ
❌ เข้าใจผิด: การระบุ Tools ใน allowedTools จะเป็นการจำกัดให้ Agent ใช้ได้เฉพาะ Tools เหล่านั้นเท่านั้น?
✓ ความจริง: ไม่จริง: allowedTools มีหน้าที่เพียง Auto-approve เท่านั้น Tools ที่ไม่ได้ระบุไว้ยังคงเรียกใช้ได้ตามปกติ เพียงแต่ต้องผ่านการตรวจสอบจาก Permission Mode และ canUseTool Callback ก่อน ส่วนการบล็อกไม่ให้ใช้เลยต้องตั้งค่าผ่าน disallowedTools
❌ เข้าใจผิด: ทุก Hook Event รองรับทั้งบน Python SDK และ TypeScript Agent SDK?
✓ ความจริง: ไม่จริง: Event บางตัว เช่น SessionStart, SessionEnd และ PostCompact มีให้ใช้เฉพาะใน TypeScript เท่านั้น ทำให้ Python App ไม่สามารถ Register Event เหล่านี้ได้
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •เมื่อ Compaction เสร็จสิ้น - Lifecycle tasks: ใช้ Stop บันทึก Session State และใช้ SubagentStop รวบรวมผลลัพธ์จาก Subagents ที่รันแบบ Parallel
  • •settingSources: ["project"] เป็นการโหลด Context หลัก โดยจะดึง CLAUDE.md, Skills และ Filesystem Hooks จาก Working Directory มาใช้ เพื่อให้ Agent ทำตาม Convention ของโปรเจกต์ตั้งแต่เริ่มต้น ส่วน effort เป็นตัวควบคุม Cost เช่น ตั้งเป็น "low"
  • •- Audit logging: ใช้ callback ของ PostToolUse บันทึกทุกการแก้ไขไฟล์ลง Audit Trail โดยมี tool use ID เป็นตัวเชื่อมโยงกับ Event PreToolUse ที่คู่กัน - Context injection: ใช้ UserPromptSubmit แทรกลงใน Context เพิ่มเติมให้แต่ละ Prompt ก่อนส่งไปให้ Claude - Transcript archiving: ใช้ PreCompact บันทึกประวัติการสนทนาฉบับเต็มไว้ ก่อนที่ SDK จะทำ Compaction ย่อ History ส่วนเก่า โดย Stream จะแสดง System Message ชื่อ compact_boundary

Workflow กับ Agent — ใน Workflow นั้น Code ของคุณจะเป็นตัวกำหนดทิศทางการเรียก LLM อย่างตายตัว แต่ใน Agent ตัว Model จะตัดสินใจ Step ถัดไปด้วยตัวเองจากสิ่งที่พบเจอ ให้เลือกโครงสร้างที่เรียบง่ายที่สุดสำหรับแก้งาน และใช้ Agent เมื่อขั้นตอนล่วงหน้าไม่สามารถคาดเดาได้เท่านั้น

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: งานที่ซับซ้อนและมีหลายขั้นตอน จำเป็นต้องใช้ Autonomous Agent เสมอไปหรือไม่?
✓ ความจริง: ไม่จริง: ควรเริ่มจากระบบที่เรียบง่ายที่สุดก่อน และเพิ่มความซับซ้อนเมื่อจำเป็นเท่านั้น Fixed Workflow หรือแม้แต่ Single LLM Call มักจะชนะเรื่อง Cost และความสามารถในการคาดเดา (Predictability) Agent จะเหมาะสมก็ต่อเมื่อไม่สามารถคาดเดาจำนวนและลำดับขั้นตอนล่วงหน้าได้เท่านั้น
❌ เข้าใจผิด: Server tools เช่น web_search ต้องให้ Code ฝั่งเราสั่ง Execute และส่ง tool_result blocks กลับไปใช่หรือไม่?
✓ ความจริง: ไม่จริง: Anthropic เป็นผู้รัน Server Tools และจัดการ Loop ภายในให้เอง Code ของเรามีหน้าที่แค่ Enable Tool และคอย Handle `pause_turn` เท่านั้น โดยไม่ต้องสร้างหรือประกอบผลลัพธ์ของ Tool เองเลย
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: การเรียก query() ต่อเนื่องจะเข้าถึง Subagent ที่รันใน Query ก่อนหน้าได้โดยอัตโนมัติ เพราะ query() แต่ละครั้งจะเริ่มต้น Session ใหม่เสมอ คุณต้องส่ง resume ด้วย Session ID เดิม และระบุ Agent ID เพื่อให้ Subagent นั้นทำงานต่อจาก Transcript เดิม

💡 แก่นสถาปัตยกรรม (Core Architectural Law)

Requirements-driven model selection — การเลือกโมเดลเริ่มต้นจากความต้องการของระบบ โดยแปลงโจทย์ทางธุรกิจแต่ละข้อเป็นเกณฑ์ด้าน Capability, Speed, Cost หรือข้อจำกัดด้านขนาด แล้วเลือกโมเดลที่ผ่านทุกเกณฑ์โดยมี Cost ต่อ Completed Task ต่ำที่สุด

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: หากมี Input ขนาดใหญ่มากใน Request เดียว ต้องใช้เฉพาะโมเดลตัวท็อปที่มี Capability สูงสุดเท่านั้นใช่หรือไม่?
✓ ความจริง: ไม่จริง: Fable 5.1, Opus 5.5 และ Sonnet 5.5 ล้วนรองรับ Context Window ขนาด 1M tokens เท่ากัน มีเพียง Haiku 4.5 (200K tokens) เท่านั้นที่ไม่รองรับ
❌ เข้าใจผิด: Model ที่คิดราคา Per-token ถูกที่สุด คือตัวเลือกที่ประหยัดที่สุด?
✓ ความจริง: ไม่จริง: ควบคุมและเปรียบเทียบจาก Cost per completed task เท่านั้น เพราะ Model ที่ราคาต่อ Token ถูกกว่า แต่อัตรา Failed สูงหรือต้อง Retry ซ้ำๆ จะทำให้ต้นทุนรวมต่อ Task ที่สำเร็จจริงแพงกว่า
❌ เข้าใจผิด: ถ้าเจอโจทย์ถามวิธีเลือก Model ควรตอบอย่างไร?
✓ ความจริง: ไม่จริง: การเทียบแค่ List prices เพียงอย่างเดียวคือตัวลวง ช้อยส์ที่ถูกต้องคือการสร้าง Evaluation set จาก Prompts และ Data ที่ใช้งานจริงมาทดสอบ
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •Business Requirements มักไม่ได้ถูกระบุมาในรูปแบบพารามิเตอร์ของโมเดล เช่น "Agents ต้องตอบกลับให้ได้ในขณะที่ลูกค้ายังถือสายอยู่" หรือ "งบประมาณฝั่ง Support ต้องไม่บานปลาย" หากจะนำมาใช้ตัดสินใจเลือกโมเดล ต้องแปลงโจทย์เหล่านี้ให้เป็น Functional Requirements ที่วัดผลได้ โดยข้อความแรกจะกลายเป็น Latency Target ส่วนข้อความหลังจะกลายเป็น Cost per Request ตามปริมาณ Request Volume ที่คาดการณ์ไว้ หัวข้อ [Model lineup and choosing a starting model](lesson:5.3) ได้สรุปภาพรวมของโมเดลแต่ละรุ่นไว้แล้ว ในส่วนนี้จะเน้นการแปลง Requirements ให้กลายเป็นเกณฑ์คัดเลือกโมเดลที่เหมาะสม
  • •Requirements บางอย่างถือเป็นข้อจำกัดขั้นต่ำ (Floor) ที่ไม่สามารถแก้ได้ด้วยการปรับ Prompt โดย [Context window](lesson:5.1) ของโมเดลจะเป็นตัวกำหนดขีดจำกัดสูงสุดของ Input ต่อหนึ่ง Request และ Maximum Output จะกำหนดความยาวสูงสุดที่โมเดลสามารถเขียนตอบได้ในหนึ่งรอบ ซึ่งทั้งสองอย่างนี้เป็น Hard Limits ที่ไม่สามารถ Trade-off ด้วย Cost หรือ Speed ได้ หาก Requirement ระบุว่า "ต้องวิเคราะห์เอกสารชุดใหญ่ที่รวมกันทั้งหมดใน Request เดียว โดยห้ามทำ Chunking" โมเดลใดก็ตามที่มี Context Window เล็กกว่าขนาด Input จะถูกตัดออกทันทีก่อนที่จะพิจารณาเรื่องราคา
  • •ให้วัดผลจาก Cost per completed task ไม่ใช่ Per-token price เพราะ Model ที่ถูกกว่าแต่รันพลาดไปครึ่งหนึ่ง หรือต้องยิง Prompt ซ้ำหลายรอบ อาจมีต้นทุนเฉลี่ยต่อ Task ที่สำเร็จสูงกว่า Model ตัวท็อปที่ทำผ่านได้ในรอบเดียว ตัวเลข Price per token จะนำมาใช้เปรียบเทียบได้ก็ต่อเมื่อ Eval วัด Success Rate ของแต่ละ Model ออกมาแล้วเท่านั้น

อ่านบทเต็ม →
💡 แก่นสถาปัตยกรรม (Core Architectural Law)

Stateless Messages API — Messages API ไม่มีการเก็บ memory ระหว่าง call โดย application ต้องเก็บประวัติ conversation ทั้งหมด และส่งบริบทก่อนหน้า ทั้ง turns, tool results และ images ไปในทุก request

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: เมื่อ Claude เคยเห็นภาพหรือเอกสารในเทิร์นก่อนหน้าแล้ว เทิร์นถัดไปสามารถอ้างอิงถึงได้เลยโดยไม่ต้องส่งซ้ำอีก?
✓ ความจริง: ไม่จริง: API ทำงานแบบ Stateless และไม่เก็บข้อมูลข้าม Call ใดๆ ทั้งสิ้น ตัวรูปภาพหรือการอ้างอิง file_id จะต้องถูกแนบไว้ใน History ของทุก Request ที่จำเป็นต้องใช้ข้อมูลนั้นเสมอ
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: Thinking blocks เป็นเพียงข้อความสำหรับแสดงผล UI ดังนั้นใน Tool loop จึงสามารถตัดทิ้ง หรือเลือกส่งกลับไปเฉพาะ tool_use blocks ได้ — ความจริงคือ Thinking blocks ต้องถูกส่งกลับไปให้ครบถ้วนสมบูรณ์รวมถึง signatures เสมอ หากมีการแก้ไข เรียงลำดับใหม่ หรือตัดทอนทิ้ง API จะตอบกลับด้วย HTTP 400 error ทันที
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: input_json_delta แต่ละตัวที่สตรีมมาในบล็อก tool_use เป็น JSON object ที่สมบูรณ์และสามารถ Parse ใช้งานได้ทันที — ความจริงคือ ตัว deltas เป็นเพียงเศษ String บางส่วนของ JSON เท่านั้น คุณต้องรวบรวมชิ้นส่วนทั้งหมดแล้วค่อย Parse เมื่อถึง content_block_stop หรือใช้ Streaming helper ของ SDK ในการจัดการ
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •Messages API ช่วยให้คุณเข้าถึง Model ได้โดยตรง และเป็น Endpoint หลักสำหรับสร้าง Agent Loop ของคุณเอง ในแต่ละ Call จะประกอบด้วย 3 ส่วนสำคัญที่จำเป็นต้องส่งเสมอ: model, max_tokens (เพดานจำกัดความยาว Token ของคำตอบ) และ messages list ที่แต่ละ Entry ต้องระบุ role (user หรือ assistant) พร้อมกับ content
  • •ยังมีอีก 2 ฟิลด์สำคัญที่ใช้สำหรับ Control Flow ในโค้ด: stop_reason ใช้บอกเหตุผลที่การ Generate สิ้นสุดลง (end_turn, max_tokens, stop_sequence, tool_use หรือ refusal) และ usage ที่รายงาน input_tokens กับ output_tokens สำหรับคำนวณ Context Size และคิดค่าบริการ
  • •เนื่องจากคุณเป็นผู้จัดการ History เอง คุณจึงสามารถปรับแต่งสิ่งต่างๆ ได้ เช่น Assistant Turn ไม่จำเป็นต้องมาจาก Claude เสมอไป การสร้าง Synthetic Few-shot Exchange ก็ถือเป็น Input ที่ถูกต้อง ใน Model รุ่นเก่าอย่าง Claude Sonnet 4.5 การใส่ Assistant Message ไว้ท้ายสุดจะทำงานเป็น Prefill เพื่อให้ Claude ตอบต่อจากจุดนั้น (เช่น Prefill ด้วย 'The answer is' คู่กับ max_tokens: 1 จะได้ตัวอักษรชอยส์ตัวเดียว) แต่ห้ามใช้ Pattern นี้กับโค้ดใหม่เด็ดขาด เพราะ Claude Opus 4.6 ปฏิเสธ Prefilled Assistant Turn แล้ว และ Migration Checklist ของ Opus 5.5 ก็ระบุให้ตัดออกอย่างชัดเจน

Message Batches API และการเลือกใช้ Batch แทน Realtime Calls ↗

Message Batches API and choosing batch over realtime calls
อ่านบทเต็ม →
💡 แก่นสถาปัตยกรรม (Core Architectural Law)

การประมวลผลคำขอปริมาณมากแบบ Asynchronous ด้วย Message Batches API เพื่อลดต้นทุนและเพิ่ม Throughput เทียบกับ Realtime Calls

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: Requests ที่ติดสถานะ Errored และ Expired ใน Batch ยังคงถูกคิดค่าบริการในอัตรา Batch rate — เพราะระบบจะคิดค่าบริการเฉพาะ Requests ที่ `succeeded` เท่านั้น สำหรับ Requests ที่ `errored`, `canceled` หรือ `expired` ไม่มีการสร้าง Message เกิดขึ้น จึงไม่มีค่าใช้จ่ายใดๆ ทั้งสิ้น
❌ เข้าใจผิด: ถ้าทุก Request ใน Batch ใช้ Cached system prompt เดียวกัน อัตรา Cache hit จะเกือบ 100% เสมอใช่หรือไม่?
✓ ความจริง: ไม่จริง: Batched requests ทำงานพร้อมกันแบบ Concurrently และไม่เรียงลำดับ Cache hit จึงเป็นแบบ Best-effort (อัตรา Hit rate ระดับ 35% ถือเป็นเรื่องปกติ) แนวทางปฏิบัติที่ถูกต้องคือส่ง Priming request ที่มี Shared prefix พร้อมระบุ Cache block แบบ 1 ชั่วโมงไปก่อน 1 คำขอ เมื่องานเสร็จสิ้นจึงค่อย Submit คำขอที่เหลือตามไป
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •Messages request เกือบทุกรูปแบบสามารถใส่ใน Batch ได้ทั้งหมด รวมถึง Server tools แต่มี 3 พารามิเตอร์ที่จะทำให้เกิด Validation error ได้แก่: `stream: true` (ไม่รองรับ เพราะผลลัพธ์ถูกส่งกลับมาเป็นไฟล์อยู่แล้ว), `speed` หรือ Fast mode (ไม่รองรับ เพราะมีไว้ปรับ Latency ของ Synchronous call) และ `max_tokens: 0`
  • •สำหรับงานที่ใช้รูปภาพจำนวนมาก (Image-heavy jobs) มีข้อจำกัดเพิ่มเติมที่ต้องคำนึงถึงต่อ 1 Request ไม่ว่าจะเป็นแบบ Realtime หรือ Batch โดย API กำหนดให้ส่งรูปภาพได้สูงสุด 100 รูปต่อ Request สำหรับโมเดลที่มี Context window ขนาด 200k tokens และสูงสุด 600 รูปต่อ Request สำหรับโมเดลอื่นๆ ทั้งหมด
  • •Claude Opus 5.5 ที่มี Context window ขนาด 1M tokens จึงรองรับได้สูงสุด 600 รูป ในขณะที่ Claude Haiku 4.5 (200K) จะจำกัดอยู่ที่ 100 รูป

Calling the Claude API: REST, JSON and sync vs async patterns
อ่านบทเต็ม →
💡 แก่นสถาปัตยกรรม (Core Architectural Law)

One request, several ways to wait — ทุกรูปแบบส่ง JSON Messages request เดียวกันและได้รับ Message object กลับมาเหมือนกัน ความแตกต่างระหว่าง Blocking, Async, Streaming และ Submit-and-poll อยู่ที่วิธีที่ Code รอรับผลลัพธ์ ดังนั้นจึงควรเลือกใช้ตาม Latency และรูปแบบของ Workload ไม่ใช่ตามโครงสร้างของ Response

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: API จดจำประวัติก่อนหน้าได้ จึงส่งเฉพาะ User Message ล่าสุดในแต่ละ Request ก็พอ?
✓ ความจริง: ไม่จริง: Messages API เป็น Stateless อย่างสมบูรณ์ ไม่มีการเก็บ State ฝั่ง Server ตัว Service ของคุณต้องเป็นผู้จัดเก็บ Conversation History เอง และส่งประวัติการสนทนาทั้งหมดแนบไปในทุก Request
❌ เข้าใจผิด: Streaming ใช้สำหรับ UI เท่านั้น และ Backend job ที่ต้องการผลลัพธ์ทั้งก้อนควรใช้ Blocking call เสมอหรือไม่?
✓ ความจริง: ไม่จริง: เมื่อกำหนดค่า `max_tokens` ขนาดใหญ่ SDK จำเป็นต้องใช้ Streaming เพื่อหลีกเลี่ยง HTTP timeouts และยังสามารถเรียก `get_final_message()` บน Stream เพื่อรับออบเจกต์ Message ที่สมบูรณ์ได้เช่นกัน
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •รูปแบบ Polling มีข้อพึงระวัง: Job ID จะต้องคงอยู่ต่อไปแม้ Process ที่ส่ง Job ไปจะจบการทำงานแล้ว จึงควรบันทึก Batch ID ควบคู่กับข้อมูลอ้างอิงของระบบคุณ จากนั้นจึงรัน Poller แยกเป็น Scheduled job ได้อย่างปลอดภัย แม้ Service จะ Restart งานก็ไม่สูญหาย ควรเลือกใช้ Pattern นี้เมื่อเน้น Throughput และ Cost มากกว่า Latency เช่น งานจำแนกข้อมูลประจำคืน (Nightly classification) หรืองาน Evaluation และหลีกเลี่ยงเมื่อมีผู้ใช้งานกำลังรอคำตอบแบบ Real-time
  • •การเรียกใช้งาน Claude คือ REST call ทั่วไป จึงใช้ Conventions เดียวกับที่ Service อื่นๆ ใช้งาน โดย API ให้บริการผ่าน https://api.anthropic.com และส่ง Request การสนทนาผ่าน POST /v1/messages ทุก Request ต้องส่ง Body เป็น JSON พร้อม Header content-type
  • •Bearer <token> (หรือใช้ Header เดิมอย่าง x-api-key เป็น Fallback ได้)

Claude Code in Git, CI, code review and refactoring
อ่านบทเต็ม →
💡 แก่นสถาปัตยกรรม (Core Architectural Law)

การผสาน Claude Code เข้ากับ Git และ CI/CD เพื่อสร้าง Workflow อัตโนมัติตั้งแต่เขียนโค้ด ทำ Code Review จนถึง Refactoring อย่างปลอดภัย

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: Bot ตัวอื่น (เช่น ตัวอัปเดต Dependency) สามารถ Trigger ให้ Claude Action ทำงานได้เพียงแค่ Mention @claude?
✓ ความจริง: ไม่จริง: Action จะปฏิเสธ Bot Actors ในทุก Event เสมอ เว้นแต่ Bot นั้นจะถูกเพิ่มชื่อไว้ใน allowed_bots เพื่อตัดปัญหา Trigger Loops
❌ เข้าใจผิด: แค่เพิ่ม code-review plugin ลงใน Workflow ก็เพียงพอที่จะให้ Findings แสดงบน PR แล้ว?
✓ ความจริง: ไม่จริง: หากไม่มี Flag --comment ตัว Claude จะไม่ Post อะไรลง PR เลย และ Findings จะปรากฏอยู่แค่ใน Workflow run log เท่านั้น | การเลือก "After every push" มีค่าใช้จ่ายเท่ากับการ Review ครั้งเดียวแค่ได้ผลลัพธ์ที่ใหม่กว่า? (ทำไมถึงผิด): ไม่จริง: ทุก Push จะ Trigger การ Review แบบเต็มรูปแบบ ทำให้ Cost แปรผันตรงตามจำนวน Push บน PR
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •ถ้า Comment นั้นไม่ได้ Mention @claude พฤติกรรมของ Action จะขึ้นอยู่กับว่ามีการกำหนด Prompt Input หรือไม่ หากไม่กำหนด จะรันใน Interactive Mode คือรอ Trigger Phrase แล้วตอบกลับเป็น Comment บน Issue หรือ PR แต่หากมีการกำหนด Prompt จะรันใน Automation Mode ทันทีโดยไม่ต้องรอ Mention และผลลัพธ์จะถูกบันทึกไว้ใน Workflow Run Log เว้นแต่จะระบุใน Prompt ให้ Claude โพสต์ผลลัพธ์และมี Tool ที่รองรับ
  • •วิธีแรกคือ Managed Code Review ซึ่งตั้งค่าผ่าน Claude Code Admin Settings ร่วมกับ Claude GitHub App โดยไม่ต้องเขียน Workflow file เอง ระบบจะรันการวิเคราะห์แบบ Multi-agent และจัดหมวดหมู่ Findings ออกเป็น 🔴 Important (ต้องแก้ก่อน Merge), 🟡 Nit (จุดเล็กน้อย ไม่บล็อกการ Merge) หรือ 🟣 Pre-existing (Bug เดิมที่มีอยู่แล้ว PR นี้ไม่ได้สร้างขึ้น) อีกวิธีคือการเขียน Workflow ขึ้นมาเองเพื่อรัน code-review plugin ผ่าน GitHub Action
  • •การทำงานแบบขนาน (Parallel Work) จำเป็นต้องแยก Checkout ออกจากกัน Git Worktrees ช่วยให้คุณรัน CLI Sessions แยกกันบน Git Checkout ที่แยกเป็นอิสระ เพื่อป้องกันไม่ให้ 2 Sessions ที่แก้ Repo เดียวกันเขียนทับกันเอง การแยกสภาพแวดล้อมแบบนี้ยังเหมาะกับรูปแบบ Writer และ Reviewer อีกด้วย เช่น ให้ Session แรกเขียนโค้ด Rate Limiter แล้วให้ Session ที่สองซึ่งมี Context ที่สดใหม่ (Fresh Context) ทำการ Review ไฟล์ @src/middleware/rateLimiter.ts เพื่อหา Edge Cases และ Race Conditions จากนั้นจึงส่ง Feedback กลับไปให้ Session แรกแก้ไข

Claude application design: surfaces, instruction placement and output schemas
อ่านบทเต็ม →
💡 แก่นสถาปัตยกรรม (Core Architectural Law)

Instruction Frame — Claude ไม่ได้รับ Prompt ของคุณเพียงลำพัง แต่ละ Surface จะครอบ Prompt ด้วย System Prompt และ Instruction Files ที่โหลดเข้ามา ซึ่ง Wrapper นี้จะแตกต่างกันระหว่าง Claude Code CLI และ Agent SDK Application โดย Agent SDK จะเริ่มต้นด้วย Minimal System Prompt เสมอ เว้นแต่จะระบุให้ใช้ Preset ของ Claude Code

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: ที่คิดว่า SDK Agent สูญเสียพฤติกรรมแบบ Claude Code เพราะไม่ได้โหลด CLAUDE.md เนื่องจากคิดว่า SDK ไม่โหลด Filesystem Settings เป็นค่าเริ่มต้น — ความจริงคือ หากไม่ได้กำหนด settingSources ตัว SDK จะยึดตามค่า Default ของ CLI และโหลดครบทุก Source ตามปกติ ปัญหาที่แท้จริงมักเกิดจาก System Prompt ที่เป็นค่า Minimal Default ซึ่งแก้ไขได้โดยการระบุ preset เป็น claude_code
❌ เข้าใจผิด: Constraints เช่น minimum หรือ maxLength จะถูกตัดทิ้งจาก Structured Output Schema อย่างเงียบๆ และไม่มีการบังคับใช้เลยใช่หรือไม่?
✓ ความจริง: ไม่จริง: Helper จะนำ Constraints เหล่านั้นออกจาก Schema ก่อนส่ง แล้วย้ายไปใส่ไว้ใน Field Description แทน ซึ่งหาก Helper มีการ Validate ตัว Response มันจะยังคงตรวจสอบตาม Constraints ดั้งเดิมครบทุกตัว
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •ผลลัพธ์ที่ Claude ตอบสนองต่อ Request ขึ้นอยู่กับ Context รอบข้าง ใน Interactive Claude Code Session ไฟล์ CLAUDE.md, Auto Memory, ชื่อ MCP Tools และคำอธิบาย Skills จะถูกโหลดเข้าสู่ Context ก่อนที่คุณจะพิมพ์อะไรด้วยซ้ำ นอกเหนือจาก System Prompt หลักของ Claude Code เอง
  • •การแบ่งแยกนี้ยังช่วยกำหนด Content Boundary เพื่อความปลอดภัย System Prompt, Append String, Instruction File และ Plugin Skill ทั้งหมดจะถูกส่งถึง Claude ในฐานะ "Instructions" ห้ามนำ Untrusted Text เช่น Email ของลูกค้า, รายละเอียด Ticket หรือ Web Page ที่ Fetch มา ใส่ลงในกลุ่มนี้เด็ดขาด เพราะหากอยู่ใน Instruction File ข้อความแปลกปลอมนั้นจะมีน้ำหนักเทียบเท่ากับ Rules หลักของคุณในทุก Session ให้ส่งข้อมูลเหล่านี้ผ่าน Per-Task Message แทนในฐานะ Material สำหรับประมวลผล ดูรายละเอียดการโจมตีเพิ่มเติมได้ใน [Prompt injection and jailbreaks (two threat models)](lesson:7.1)
  • •หากคุณย้าย Workflow จาก `claude -p` ไปเป็น Service บน Agent SDK แม้ตัว Prompt จะเหมือนเดิม แต่ Context รอบข้างอาจเปลี่ยนไปอย่างสิ้นเชิงโดยไม่มี Prompt

✓ ความจริง: ไม่จริง: สำหรับการตอบกลับแบบ Streaming Error จากฝั่ง Server หรือเครือข่ายสามารถเกิดขึ้นได้หลังจากที่ API ส่ง HTTP Status 200 เริ่มต้นไปแล้ว ซึ่งการจัดการ Error ในกรณีนี้จะไม่เป็นไปตาม Flow ปกติของ HTTP Error ทั่วไป

✓ ความจริง: ไม่จริง: 413 request_too_large เป็นปัญหาฝั่ง Capacity ที่แก้ได้ด้วยการ Retry หรือสลับไปใช้ Model ที่มี Context ขนาดใหญ่ขึ้น เพราะ 413 จะ reject ทันทีจากขนาด Byte ก่อนที่ Request จะส่งไปถึง API servers ทางแก้เดียวคือการลดขนาด Payload ให้เล็กลง
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: 400 invalid_request_error ทุกเคสแปลว่า Request Body ผิดรูปแบบและต้องเข้าไปแก้ไข เพราะ Spend limit ที่เราตั้งเอง (User-defined spend limit) ก็ส่งกลับมาเป็น 400 invalid_request_error เช่นกัน โดยที่ Body นั้นถูกต้องแล้ว ต้องแก้ด้วยการเพิ่มหรือปลด Limit เท่านั้น | ไม่จริง: 429 rate_limit_error ทุกตัวจะหายได้เองหากปล่อยให้ SDK ทำการ Retry ต่อไปเรื่อยๆ เพราะ Tier spend-cap 429 จะไม่มี header retry-after และจะส่ง Error ตลอดไปจนกว่าจะเริ่มรอบบิลใหม่ ให้ตรวจสอบว่า error.details.error_code เป็น enforced_spend_limit_reached หรือไม่
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •สำหรับ Request ที่ทำงานนานคือเปลี่ยนไปใช้ Streaming Messages API ส่วนปัญหา Idle connections ก็ทำให้เกิดความผิดพลาดแบบเงียบๆ ได้เช่นกัน โดย Network บางแห่งจะตัด Idle connection ทิ้งหลังผ่านไปสักระยะ ส่งผลให้การเรียกแบบ Non-streaming ที่ตั้ง max_tokens ไว้สูงอาจล้มเหลวหรือค้างไปโดยไม่มี Response ใดๆ กลับมาจาก Anthropic เลย SDK จึงป้องกันปัญหานี้ 2 วิธี: ตั้งค่า TCP keep-alive และตรวจสอบว่า Non-streaming request ไม่ควรทำงานนานเกิน 10 นาที หากเกิน ให้สลับไปใช้ Streaming ซึ่ง SDK สามารถอ่านทั้ง Stream แล้ว return เป็น Message ที่สมบูรณ์เหมือนการเรียกแบบ Non-streaming ได้ หรืออีกทางเลือกคือใช้ Message Batches API ที่ใช้วิธี Poll ผลลัพธ์แทนการเปิด Connection ค้างไว้
  • •โครงสร้างของ Error Body จะเป็นรูปแบบเดียวกันเสมอ คือ JSON ที่มี Object error ระดับบนสุด ประกอบด้วย type, message และ request_id โดย request_id นี้จะถูกส่งกลับมาใน Header request-id ของทุก Response เสมอ ไม่ว่าจะสำเร็จหรือล้มเหลว ควรสั่ง Log ค่านี้ไว้ทุกครั้งที่เกิดข้อผิดพลาด เพราะทีม Support จำเป็นต้องใช้เมื่อเกิด 500 ต่อเนื่อง ทั้งยังช่วยเชื่อมโยง Log ในแอปพลิเคชันเข้ากับการเรียก API แต่ละครั้งได้อย่างแม่นยำ
  • •ประการที่สอง 500 api_error จะเป็นกรณีตรงกันข้าม คือไม่ได้เกิดจากสิ่งที่อยู่ใน Request ของคุณเลย แนวทางคือให้ชะลอเวลาด้วย Backoff แล้ว Retry หากยังไม่หายจึงเปิด Support Ticket พร้อมแนบ Request ID

❌ เข้าใจผิด: ค่า refusal ใน stop_reason บน Response 200 แปลว่า Integration ส่ง Request มาผิดโครงสร้าง?
✓ ความจริง: ไม่จริง: refusal หมายถึง Model ปฏิเสธที่จะตอบคำขอด้วยเหตุผลด้าน Safety แม้ว่า Request จะถูกส่งมาถูกต้องตามโครงสร้างและประมวลผลสำเร็จก็ตาม ให้จัดการโดยอ่าน stop_details และ Retry ไปยัง Fallback Model
❌ เข้าใจผิด: Empty end_turn response เป็นแค่ Glitch ชั่วคราวของ Model การส่ง Conversation เดิมซ้ำจะแก้ปัญหาได้?
✓ ความจริง: ไม่จริง: Claude ตัดสินใจจบ Turn ไปแล้ว การ Retry ซ้ำแบบเดิมจึงไม่ได้ผล ต้องแก้โครงสร้าง Message ก่อนเป็นอันดับแรก และหากจำเป็นค่อยส่ง Continuation Prompt เป็น user message ใหม่ตามเข้าไป
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •บทสนทนาจบลงด้วย Assistant Message แต่ Model ตัวนี้ไม่รองรับการ Prefill แนวทางแก้ไขคือต้องจบลำดับด้วย User Message และควบคุม Output Format ผ่าน Structured Outputs หรือคำสั่งใน System Prompt แทน - A message ending but no web_search tool was provided
  • •refusal หมายถึง Model ปฏิเสธที่จะตอบ ฝั่ง Integration ส่ง Request ถูกต้องสมบูรณ์แล้ว จึงไม่ต้องเสียเวลาหา Bug ในโค้ด ให้ตรวจสอบ stop_details และทำ Retry ไปยัง Fallback Model แทน, max_tokens หมายถึง Token Limit ของคุณตัด Output ก่อนจะเสร็จสิ้น มักเห็นเป็นข้อความขาดกลางประโยค หรือ tool_use Block สุดท้ายไม่สมบูรณ์ แก้ไขด้วยการเพิ่มค่า max_tokens, model_context_window_exceeded หมายถึง Context เต็มจน Output ถูกตัดเช่นกัน มีเพียง end_turn เท่านั้นที่แสดงว่า Model ทำงานจนจบกระบวนการตามที่ตั้งใจ
  • •การ Debug แอปพลิเคชัน Claude เริ่มจากการแยกว่าปัญหาเกิดจากฝั่ง Integration หรือตัว Model ซึ่ง HTTP 400 invalid_request_error ตัดสินเรื่องนี้ได้ทันที: Request ถูกปฏิเสธตั้งแต่ก่อนที่ Model จะเริ่มประมวลผล

How LLMs work: tokens, context windows and sampling

💡 แก่นสถาปัตยกรรม (Core Architectural Law)

Next-token generation — โมเดลภาษาเขียนคำตอบทีละ Token โดยคัดเลือก Token ถัดไปจากความน่าจะเป็นของข้อความก่อนหน้า กระบวนการนี้ทำให้ประโยคมีความลื่นไหลเป็นธรรมชาติ แต่ก็เปิดช่องให้เกิดการแต่งข้อมูลเท็จที่ฟังดูสมเหตุสมผลได้เช่นกัน

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: Prompt caching ช่วยคืนพื้นที่ใน context window เพราะ cached tokens ไม่ต้องถูกส่งซ้ำใช่หรือไม่?
✓ ความจริง: ไม่จริง: Caching ช่วยลดราคาและ latency ของ prefix ที่ถูก cache เท่านั้น แต่ token เหล่านั้นยังคงกินพื้นที่ใน context window ตามปกติ
❌ เข้าใจผิด: การตั้ง temperature เป็น 0 จะทำให้ Claude ทำงานแบบ Deterministic เต็มรูปแบบ และ Prompt เดิมจะได้ Text เดิมเสมอ?
✓ ความจริง: ไม่จริง: temperature 0 เพียงแต่โน้มเอียงไปทางตัวเลือกที่มีความน่าจะเป็นสูงสุด แต่ Input เดียวกันยังคงสร้าง Output ที่ต่างกันได้ข้าม API calls
❌ เข้าใจผิด: การลดค่า temperature สามารถใช้เพิ่ม Consistency ให้กับคำตอบได้บน Claude ทุกโมเดลเสมอ?
✓ ความจริง: ไม่จริง: บนโมเดล Claude 5 และ Opus 4.7 ขึ้นไป การปรับเปลี่ยน temperature, top_p หรือ top_k เป็นค่าอื่นที่ไม่ใช่ Default จะถูก Reject ด้วย 400 Error ทันที ไม่ว่าจะเปิดใช้งาน Thinking หรือไม่ก็ตาม
❌ เข้าใจผิด: ถ้าเจอช้อยส์เสนอ "ตั้งค่า temperature เป็น 0" เพื่อการันตีว่าจะได้ Output เดิมทุกครั้ง?
✓ ความจริง: ไม่จริง: temperature 0 ทำให้ผลลัพธ์ Conservative ขึ้นเท่านั้น แต่ไม่ได้ทำให้เป็น Deterministic และบน Claude 5 กับ Opus 4.7 ขึ้นไป การเปลี่ยนค่า temperature จาก Default จะได้ 400 Error กลับมา
❌ เข้าใจผิด: Non-determinism เป็นเฉพาะข้อจำกัดของ Anthropic API เท่านั้น หากรัน Claude ผ่าน Third-party Cloud Provider จะได้ Output ที่เหมือนเดิมสำหรับ Input เดิมเสมอ?
✓ ความจริง: ไม่จริง: Input เดียวกันสามารถให้ Output ต่างกันได้ ทั้งบน First-party Inference Service ของ Anthropic และ Third-party Cloud Provider เหมือนกันทั้งหมด
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •ทุกอย่างใน request ล้วนกินพื้นที่ context window: ไม่ว่าจะเป็น system prompt, ทุกข้อความใน messages (รวมถึง tool results, รูปภาพ และเอกสาร) ตลอดจน tool definitions
  • •ขนาดของ window ถูกกำหนดตายตัวตามแต่ละโมเดล โดย Claude Opus 5.5, Opus 4.8, Sonnet 5.5, Sonnet 4.6 และโมเดล flagship ปัจจุบันมี context window ขนาด 1M tokens ซึ่ง 1M เป็นค่า default โดยไม่ต้องใส่ beta header ส่วน Claude Sonnet 4.5, Claude Haiku 4.5 และโมเดลรุ่นเก่าจะมีขนาด 200k tokens
  • •Non-determinism คือคุณลักษณะที่ Input แบบเดิมเป๊ะอาจสร้าง Output ที่ต่างกันได้ในการเรียก API แต่ละครั้ง ส่งผลกระทบโดยตรงต่อระบบที่พึ่งพาการเทียบ Response เช่น Regression Test ที่ใช้ Diff คำตอบกับ Baseline เดิม, Cache ที่ใช้ Text ของ Output เป็น Key หรือ Audit Workflow ที่คาดหวังให้การรันซ้ำสร้างผลลัพธ์เดิม ต้นเหตุเกิดจาก Per-token Sampling ตามที่กล่าวไว้ข้างต้น และพฤติกรรมนี้เกิดขึ้นเหมือนกันทั้งบน First-party Inference Service ของ Anthropic และ Third-party Cloud Providers การย้าย Workload ไป Cloud Provider อื่นจึงไม่ได้ช่วยให้ผลลัพธ์เป็น Deterministic แต่อย่างใด

Claude API คือ REST พื้นฐาน — ทุกฟีเจอร์ของ Claude API คือ HTTPS Request ไปยัง Path ภายใต้ api.anthropic.com พร้อม Headers และ JSON Body ตามที่กำหนด โดย Client SDKs ไม่ได้มาแทนที่ Contract ดังกล่าว แต่ช่วยสร้าง Request และ Parse Response ให้อัตโนมัติ

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: การเรียก Raw HTTP ส่งแค่ API Key กับ Content-Type แบบ JSON ก็พอ ส่วน API Version ตัว Model จะเป็นคนกำหนดเอง?
✓ ความจริง: ไม่จริง: anthropic-version เป็น Header บังคับที่ต้องส่งในทุก Request หากขาดไป Request จะถูก Reject ทันที ที่เราไม่ค่อยเห็นใน SDK เพราะตัว SDK ทำการ Inject ทั้ง Authentication, Content-Type และ anthropic-version ให้อัตโนมัติ
❌ เข้าใจผิด: เมื่อใช้ SDK แล้ว ไม่จำเป็นต้องจัดการ Header ใดๆ ด้วยตัวเองอีกต่อไป?
✓ ความจริง: ไม่จริง: SDK ช่วยจัดการ Header ด้าน Authentication, Version และ Content-Type ให้อัตโนมัติก็จริง แต่ `anthropic-workspace-id` ขึ้นอยู่กับเงื่อนไขของ API Key แต่ละตัว หาก Key นั้นจำเป็นต้องระบุ Workspace ID คุณยังคงต้องส่งค่านั้นเข้าไปเอง
❌ เข้าใจผิด: Client SDKs เป็นตัวควบคุม Agent Loop, Tools Execution และ Runtime?
✓ ความจริง: ไม่จริง: Client SDKs เป็น Low-level Libraries ที่ทำหน้าที่เพียงส่ง Request และรับ Response ทีละครั้งเท่านั้น ส่วน Agent Loop, Tool Execution และ Runtime จะอยู่ในระดับเลเยอร์ที่สูงกว่า ซึ่งจัดการโดย Claude Code, Claude Agent SDK และ Claude Managed Agents
❌ เข้าใจผิด: Error Responses ของแต่ละ Endpoint มีรูปแบบต่างกัน Client จึงต้องใช้ String-matching เช็กข้อความเพื่อแยกแยะประเภท Error?
✓ ความจริง: ไม่จริง: ทุก Error Response ใช้โครงสร้าง JSON มาตรฐานเดียวกันที่มี Typed Error Object ชัดเจน อีกทั้ง SDK ยังยก Typed Exceptions ขึ้นมาให้โดยตรง ทำให้สามารถใช้คำสั่งดักจับ (Catch) ข้อยกเว้นตาม Type ได้ทันทีโดยไม่ต้องตรวจเช็ก String ใน Message
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •ทุก Feature ของ Claude API ทำงานอยู่ภายใต้ Base URL เดียวกันคือ https://api.anthropic.com โดย Path จะตั้งชื่อตามหน้าที่การทำงาน Traffic ส่วนใหญ่จะวิ่งไปที่ POST /v1/messages ขณะที่งานอื่นๆ จะมี Endpoint เฉพาะของตัวเอง เช่น การนับ Token ก่อนส่ง Prompt, การส่ง Batch ขนาดใหญ่แบบ Asynchronous, การดึงรายชื่อ Model ที่ใช้งานได้ หรือการ Upload ไฟล์เก็บไว้ล่วงหน้าเพื่อให้ Request อื่นๆ อ้างอิง สำหรับการเชื่อมต่อแบบ Raw HTTP นั้น URL และ HTTP Method จะเป็นตัวระบุ Operation ส่วน Parameters จะส่งผ่าน JSON Body
  • •Agents, Sessions และ Environments APIs ซึ่งใช้ขับเคลื่อน Claude Managed Agents ปัจจุบันยังอยู่ในสถานะ Beta และวางตัวอยู่คู่ขนานกับชุด APIs หลัก
  • •application/json หากขาด anthropic-version ไป Request จะล้มเหลวทันทีแม้ API Key จะถูกต้อง Header นี้มีไว้เพื่อ Pin พฤติกรรมของ API ให้ตรงกับโค้ดที่เขียนไว้ ตามรายละเอียดใน [API versions and feature classifications (beta vs GA)](lesson:2.2)

💡 แก่นสถาปัตยกรรม (Core Architectural Law)

ทำความเข้าใจกลไก Server-Sent Events (SSE) บน HTTP สำหรับการสตรีมคำตอบของ Claude การเรียงต่อข้อมูลย่อย (deltas) หลากรูปแบบ และการจัดการข้อผิดพลาดเพื่อความเสถียรของระบบ

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: แต่ละ input_json_delta บรรจุ JSON object ที่พร้อมใช้งานของ Tool arguments ทันที?
✓ ความจริง: ไม่จริง: deltas เหล่านี้เป็นเพียงชิ้นส่วนของ string (string fragments) ต้องนำมาต่อกันให้ครบทั้งบล็อกแล้ว parse เมื่อ content_block_stop มาถึง หรือใช้ SDK helpers ช่วยจัดการ
❌ เข้าใจผิด: การคิดจำนวน billed output tokens ของ Stream response ต้องนำ output_tokens จากทุก message_delta event มาบวกกัน?
✓ ความจริง: ไม่จริง: ค่า usage ใน message_delta เป็นแบบสะสม (cumulative) ค่าที่รายงานในอีเวนต์สุดท้ายคือยอดรวมทั้งหมด การนำทุกอีเวนต์มาบวกกันจึงทำให้คิด usage สูงเกินจริง
❌ เข้าใจผิด: client.messages.create(..., stream=True) จะ return ผลลัพธ์ Message ที่ประกอบสมบูรณ์เหมือน stream helper แต่เร็วกว่า?
✓ ความจริง: ไม่จริง: คำสั่งนี้ return เพียง raw event iterable เท่านั้น และไม่มีการ build final message ให้ หากต้องการผลลัพธ์สุดท้ายที่ประกอบสมบูรณ์ ต้องใช้ client.messages.stream(...) คู่กับ get_final_message()
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •การทำ Streaming response ใน Claude คือการเรียก Messages API ตามปกติ แค่เพิ่ม "stream": true ใน Request Body โดยยังคงยิง POST ไปที่ /v1/messages ด้วย Headers เดิม จุดต่างสำคัญคือรูปแบบ Response ที่ส่งกลับมา: จะส่งกลับมาเป็น Server-Sent Events (SSE) ทยอยส่งข้อมูลมาทันทีที่สร้างเสร็จ
  • •แทนที่จะรอส่ง JSON ก้อนเดียวจบตอนท้าย แต่ละ Event จะมีชื่อระบุประเภท เช่น event: message_stop พร้อมกับ Payload ในรูปแบบ JSON data ที่บอก Type ซ้ำมาด้วย
  • •ฟิลด์ delta.type ใช้บอกวิธีนำ content_block_delta แต่ละตัวไปอัปเดตลงในบล็อกของมัน โดย text_delta จะส่งชิ้นส่วนข้อความมาให้ต่อท้าย (append) ส่วนการเรียก Tool จะแตกต่างออกไป ซึ่งอีเวนต์ input_json_delta จะส่ง partial_json มาเป็น string fragment ของ Tool arguments เช่น {"location"

💡 แก่นสถาปัตยกรรม (Core Architectural Law)

Capability–speed–cost tradeoff — การเลือกใช้โมเดลต้องชั่งน้ำหนักระหว่างความสามารถ (Capability), ความเร็วในการตอบสนอง (Speed) และค่าใช้จ่าย (Cost) คุณสามารถปรับสมดุลนี้ได้ทั้งการสลับข้าม tiers หรือปรับแต่งภายในโมเดลเดิมผ่านการตั้งค่า effort และการเปิดใช้ fast mode

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: เมื่อค่าใช้จ่ายสูงเกินไป ขั้นตอนแรกคือการเปลี่ยนไปใช้โมเดลที่ถูกกว่า?
✓ ความจริง: ไม่จริง: หากระดับคุณภาพยังยอมรับได้ ให้ลดค่า Effort บนโมเดลเดิมก่อนเป็นอันดับแรก ควรเปลี่ยนโมเดลก็ต่อเมื่อผล Evals ยืนยันว่าจำเป็นเท่านั้น | สำหรับงาน Autonomous Coding ที่มีความเสี่ยงสูงบน Claude Opus 4.8 ควรใช้ค่าเริ่มต้นหรือ max? (ทำไมถึงผิด): ไม่จริง: บน Opus 4.8 และ 4.7 แนะนำให้ตั้งค่าเป็น xhigh (อยู่ระหว่าง high กับ max) สำหรับงาน Coding และ Agentic Work ส่วนใหญ่
❌ เข้าใจผิด: Fast mode สลับไปใช้โมเดลที่มีขนาดเล็กกว่า ทำให้ต้องยอมแลกคุณภาพบางส่วนเพื่อความเร็ว?
✓ ความจริง: ไม่จริง: Fast mode รันบนโมเดลเดิมโดยใช้ Inference Configuration ที่เร็วกว่า ขีดความสามารถของโมเดลยังคงเดิมทุกประการ มีเพียง Output Rate และราคาเท่านั้นที่เปลี่ยนแปลง
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •สำหรับ Claude Sonnet 5.5 โดดเด่นเรื่องความสมดุลระหว่างความเร็วและ Capability เหมาะกับงาน Code Generation ทั่วไป, Data Analysis และ Agentic Tool Use สุดท้าย Claude Haiku 4.5 มี Latency ต่ำสุดและราคาถูกที่สุด เหมาะ
  • •สำหรับ Agent Sessions ที่รันต่อเนื่องหลายชั่วโมง หรืองาน Deep Research แบบหลายขั้นตอนจนได้เอกสารฉบับสมบูรณ์ Claude Opus 5.5 คือจุดเริ่มต้น
  • •การเลือก First Model สำหรับเริ่มต้นมี 2 แนวทางหลักขึ้นอยู่กับลักษณะงาน: Start Small and Step Up เหมาะสำหรับงาน Prototyping, งานที่จำกัด Latency อย่างเข้มงวด, Deployment ที่เน้น Cost-sensitive และ High-volume Tasks ที่ไม่ซับซ้อน โดยเริ่มพัฒนาบน Claude Haiku 4.5 ก่อน แล้วจึงขยับไปใช้โมเดลใหญ่ขึ้นเมื่อพบ Capability Gap ที่ชัดเจน วิธีนี้ช่วยให้ Loop การทำ Iteration รวดเร็ว และต้นทุน Development ต่ำ ซึ่งบ่อยครั้งโมเดลเล็กก็เพียงพอ

✓ ความจริง: ไม่จริง: หากการสลับโมเดลระหว่าง Conversation ทำให้ข้อมูล Thinking ก่อนหน้าหายไป API จะส่ง Error กลับมา — ความเป็นจริงคือ Thinking blocks ที่โมเดลใหม่ไม่รองรับจะถูกตัดออกทันทีโดยไม่มี Prompt Request ยังคงได้ Status 200 และ Block ที่ถูกตัดออกจะไม่ถูกนำไปคิดเงิน

Three-part input total — ระบบ Prompt caching เปิดให้ Request นำ Prefix ของ Prompt ที่บันทึกไว้ ณ จุด Cache breakpoint กลับมาใช้ซ้ำได้ ส่งผลให้ Response แยกรายงานจำนวน Input เป็น 3 ฟิลด์ตามอัตราคิดเงินที่ต่างกัน: Tokens ที่อ่านจาก Cache, Tokens ที่เขียนลง Cache และ Uncached tokens หลังจุด Breakpoint ล่าสุด โดยขนาดและต้นทุนของ Input ที่แท้จริงจะคำนวณได้จากผลรวมของทั้งสามส่วนนี้เท่านั้น

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: จำนวน Token ที่วัดจาก Model รุ่นเก่าจะยังคงเท่าเดิมเมื่อย้ายไปใช้ Model ที่ใช้ Tokenizer รุ่นใหม่กว่า?
✓ ความจริง: ไม่จริง: Endpoint จะนับ Token โดยอิงตาม Tokenizer ของ Model ที่คุณส่งเข้าไปเสมอ ดังนั้นหากต้องการย้าย Model ควรถือ Request เดิมไปนับ Token บนทั้งสอง Model เพื่อเปรียบเทียบผลลัพธ์จริง
❌ เข้าใจผิด: ฟิลด์ input_tokens ใน Response คือขนาด Input ทั้งหมดของ Request?
✓ ความจริง: ไม่จริง: input_tokens แสดงเฉพาะ Token ที่ไม่ได้ Cache หลัง Cache Breakpoint จุดสุดท้ายเท่านั้น หากต้องการทราบขนาด Input ทั้งหมด ต้องนำ input_tokens + cache_read_input_tokens + cache_creation_input_tokens มารวมกัน
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •Input Token ไม่ได้มีแค่ข้อความที่คุณพิมพ์ ในการทำ Tool Use นั้น Input จะนับรวมพารามิเตอร์ tools (ชื่อ, description และ schema ของทุก Tool), บล็อก tool_use และ tool_result ทั้งหมดในประวัติ Conversation รวมถึง System Prompt พิเศษที่ API ใส่เข้ามาให้อัตโนมัติเมื่อมีการประกาศใช้ Tools
  • •การนับ Token มีข้อจำกัด 3 ประการ: 1) ไม่คำนึงถึง Caching แม้จะระบุบล็อก cache_control มาด้วย แต่ผลลัพธ์ที่ได้จะเป็นขนาด Input ดิบทั้งหมด ไม่ใช่ค่าใช้จ่ายจริงหลังหัก Cache Hits 2) Input บางประเภทที่ Messages API รับได้จะถูกปฏิเสธที่นี่ เช่น Server Tools ส่วนใหญ่, MCP connector
  • •ตัวอย่างเช่น Fable 5.1, Mythos 5.1, Fable 5 และ Mythos 5 ใช้งาน Tokenizer ที่เปิดตัวพร้อม Opus 4.7 ซึ่ง Prompt เดียวกันจะถูกแปลงแล้วมีขนาดใหญ่ขึ้นราว 30% เมื่อเทียบกับ Model รุ่นเก่า ส่งผลให้ Cost Dashboard ที่คำนวณจากตัวเลขเดิมประเมินค่าใช้จ่ายต่ำกว่าความเป็นจริง หากต้องการทราบส่วนต่างที่แท้จริง ให้นับ Request เดียวกันสองครั้ง เทียบระหว่าง Model ปัจจุบันกับ Model ใหม่ แล้วนำค่า input_tokens มาเปรียบเทียบกัน

Prompt caching: breakpoints, TTLs and hit rates

💡 แก่นสถาปัตยกรรม (Core Architectural Law)

การใช้ Prompt Caching อย่างคุ้มค่าด้วย Breakpoints, TTLs ที่เหมาะสม และการมอนิเตอร์ Cache Hit Rate

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: การเพิ่ม cache_control breakpoint แต่ละจุดจะทำให้เสียค่าใช้จ่ายเพิ่มขึ้น จึงควรใช้ให้น้อยที่สุด?
✓ ความจริง: ไม่จริง: Breakpoint ไม่มีค่าใช้จ่ายเพิ่มเติม ค่าบริการคิดตามจำนวน token ที่ถูก write และ read จาก cache เท่านั้น
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: Cache TTL เริ่มนับหลังจาก Response สตรีมเสร็จสิ้น (ความจริงคือ เริ่มนับทันทีตั้งแต่ Request เริ่มส่งเข้ามา การ Generate ข้อความที่ยาวจึงลดทอนระยะเวลาของ Cache Window ลง)
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: TTL 1 ชั่วโมงประหยัดกว่าเสมอเพราะข้อมูลอยู่นานกว่า (ความจริงคือ ค่าเขียนของ TTL 1 ชั่วโมงสูงถึง 2x เทียบกับ 1.25x ของ 5 นาที และต้อง Hit อย่างน้อย 2 ครั้งถึงจะคุ้มทุน หากเป็น Agent Turn ที่ส่งเข้ามาถี่ระดับวินาที การใช้ TTL 5 นาทีตามค่า Default จะถูกกว่ามาก)
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •สามารถใช้ breakpoint ได้สูงสุด 4 จุด เมื่อส่วนต่างๆ ของ prompt มีความถี่ในการเปลี่ยนแปลงไม่เท่ากัน โครงสร้างทั่วไปของ 4-breakpoint agent มักแยก cache ระหว่าง tool definitions, static instructions, RAG documents และ conversation ออกจากกัน หากมีการแก้ไขที่ breakpoint ใด จะส่งผลให้ segment นั้นและ segment ที่อยู่ถัดไปหลุดจาก cache ทั้งหมด แต่ segment ก่อนหน้ายังคง reuse ได้ตามปกติ อีกเหตุผลในการเพิ่ม breakpoint คือกรณี conversation ขนาดยาวที่ข้อความเดินหน้าเกิน 20 บล็อกนับจาก cache write ล่าสุด ซึ่งหลุด lookback window
  • •สำหรับ Haiku 4.5 หาก prefix สั้นกว่าเกณฑ์ ระบบจะประมวลผลตามปกติโดยไม่ error และไม่เกิด cache write สังเกตได้จากค่า cache_creation_input_tokens ที่ยังเป็น 0 ตัวอย่าง automatic caching ด้านบนมี system prompt เพียงไม่กี่สิบ token จึงต่ำกว่า minimum threshold ทุกโมเดล
  • •Hit Rate คือสัดส่วนของ Input Tokens ที่ดึงมาจาก Cache คำนวณจาก `cache_read_input_tokens` หารด้วย Total Input ทั้งหมด ใน Request แรกของ Agent ที่เปิดใช้ Cache โทเค็นเกือบทั้งหมดจะไปปรากฏใน `cache_creation_input_tokens` และค่า Read จะเป็นศูนย์ แต่ใน Turn ถัดๆ ไป ค่า Read จะครอบคลุมบริบทเดิมทั้งหมดที่เคยแคชไว้ และส่วน Creation จะคิดเฉพาะ Turn ใหม่ล่าสุดเท่านั้น ในระดับองค์กร Usage API จะรายงานข้อมูลแยกย่อยแบบเดียวกัน และ Console จะพล็อตแสดง Cache Rate รายชั่วโมงให้ดู

Context Window Budget and Tool Output Pruning
อ่านบทเต็ม →
💡 แก่นสถาปัตยกรรม (Core Architectural Law)

Context Rot — ยิ่ง Context Window เต็ม ความแม่นยำและการ Recall ข้อมูลของโมเดลจะยิ่งลดลง เป้าหมายจึงเป็นการคัดสรรเฉพาะข้อมูลที่จำเป็น ไม่ใช่การยัดข้อมูลจนเต็มเพียงเพราะยังมีพื้นที่เหลือ

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: Prompt caching ช่วยลดพื้นที่ Context Window ของ Prefix ขนาดใหญ่ที่ไม่เปลี่ยนแปลงได้หรือไม่?
✓ ความจริง: ไม่จริง: Cached tokens ยังคงถูกนับเข้า Context Window เต็มจำนวนเท่าเดิม การทำ Caching ช่วยลดเพียงแค่ค่าใช้จ่าย (Cost) แต่ไม่ได้ช่วยแก้ปัญหา Context Rot หรือขยายขีดจำกัดของ Window เลย
❌ เข้าใจผิด: หลังจากเปิดใช้ Context Editing ฝั่ง Client ต้องลบ Tool Results ที่ถูกเคลียร์ออกจาก Message History ของตัวเองเพื่อ Sync ข้อมูลหรือไม่?
✓ ความจริง: ไม่จริง: Context Editing ทำงานฝั่ง Server ก่อนที่ Prompt จะส่งถึง Claude โดยฝั่ง Client ยังคงเก็บและส่ง History ฉบับเต็มแบบดั้งเดิมไปตามปกติ
❌ เข้าใจผิด: การเคลียร์ Tool Results ไม่มีผลกระทบต่อ Caching เพราะเป็นการลบ Token ออกเท่านั้นหรือไม่?
✓ ความจริง: ไม่จริง: การเคลียร์ข้อมูลจะทำให้ Cache Prefix บริเวณที่เนื้อหาถูกลบหลุด (Invalidate) ทันที ส่งผลให้การเคลียร์แต่ละครั้งต้องเสียค่า Cache Write ใหม่ จึงต้องมี clear_at_least เพื่อการันตีว่าการเคลียร์แต่ละรอบคุ้มค่ากับ Cost ที่ต้องจ่าย
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •โมเดลบางตัวสามารถรับรู้ Budget ของตัวเองได้ โดย Claude Sonnet 5, Sonnet 4.6, Sonnet 4.5 และ Haiku 4.5 มีฟีเจอร์ Context Awareness ซึ่ง API จะแทรกแท็ก <budget:token_budget> ใน System Prompt และส่ง usage ใน system_warning หลังจบแต่ละ Tool Call เพื่อให้โมเดลประเมินความเร็วในการทำงานกับพื้นที่ที่เหลือได้ โดยคุณไม่ต้องส่งแท็กเหล่านี้เอง ส่วน Claude Opus 4.7+ ขึ้นไป, Claude Sonnet 5.5, Fable และ Mythos จะไม่มีแท็กนี้ แต่สามารถกำหนด Budget แบบระบุชัดเจนผ่านฟีเจอร์ Task Budgets (Beta) ได้
  • •สำหรับ 1 Request ซึ่งบรรจุข้อความทั้งหมดที่ Claude ใช้อ้างอิงขณะเขียนคำตอบ รวมถึงตัวคำตอบเองก็กินพื้นที่ด้วยเช่นกัน ในการคุยผ่าน API ทั่วไปจะไม่มีข้อมูลส่วนใดหลุดออกไปเอง ข้อความ User และคำตอบ Assistant ของแต่ละ Turn จะถูกเก็บสะสมไว้ครบถ้วน ทำให้ทุก Request ต้องแบกทั้ง History เดิมและข้อความใหม่ไปด้วย แม้โมเดลขนาด 1M Token (เช่น Claude Opus 5.5, Claude Sonnet 5.5 และ Claude Fable 5.1) จะให้พื้นที่มหาศาล และโมเดลอื่น เช่น Claude Sonnet 4.5 มี 200k แต่เอกสารระบุชัดเจนว่า Context ที่ใหญ่กว่าไม่ได้ดีกว่าเสมอไป ยิ่ง Token เยอะ Accuracy และ Recall ยิ่งลดลง ซึ่งใน Exam Guide เรียกว่า "Context Drift" ส่วนเอกสารเรียกว่า "Context Rot" นี่คือเหตุผลว่าทำไมเนื้อหาส่วนที่เหลือของบทเรียนนี้จึงเน้นเรื่องการ Prune ข้อมูลทิ้ง
  • •Output ของ Turn ปัจจุบันก็ถูกนับด้วย รวม Extended Thinking เข้าไปด้วย ในแต่ละ Response ฟิลด์ usage จะรายงานสิ่งที่ Request นั้นใช้งาน และ Token Counting API สามารถช่วย Estimate ล่วงหน้าก่อนส่งได้ สำหรับ Thinking Blocks ก่อนหน้า แต่ละ Generation มีการจัดการต่างกัน: Claude Opus 4.5+ ขึ้นไป, Claude Sonnet 4.6+ ขึ้นไป, Fable และ Mythos จะเก็บไว้เป็นค่า Default และถูกนับเป็น Input ปกติ ส่วนโมเดล Opus/Sonnet รุ่นก่อนหน้าและ Haiku ทุกรุ่นจะ Strip ออกให้อัตโนมัติเมื่อส่งกลับไป

✓ ความจริง: ไม่จริง: คำสั่งหรือข้อกำหนดที่ผู้ใช้ป้อนไว้ใน User Prompt ช่วงแรกจะยังคงมีผลอยู่หลังทำ Compaction เพราะ Compaction ตัดทิ้งแค่ Tool Output เท่านั้น — แท้จริงแล้ว Compaction จะแทนที่บทสนทนาทั้งหมดด้วยบทสรุป ข้อมูลที่เซฟอยู่บน Disk อย่าง CLAUDE.md เท่านั้นที่จะถูก Re-injected กลับมาครบทุกคำ ส่วนคำสั่งใดๆ ที่อยู่แค่ในบทสนทนาจะคงอยู่ต่อเมื่อตัวสรุปเลือกเก็บไว้เท่านั้น
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด? Subagent ฝั่ง research รัน grep และอ่านไฟล์ไป 40 ไฟล์เพื่อตอบคำถามเดียว หลังทำงานเสร็จ ข้อมูลเหล่านั้นจะเข้าไปอยู่ใน Context ของ Parent Agent มากน้อยแค่ไหน?
✓ ความจริง: ไม่จริง: ข้อมูลการอ่านไฟล์และ Tool Calls ทั้งหมดจะไม่ถูกดึงเข้ามาใน Parent Agent เลย มีเพียงข้อความตอบกลับสรุปสุดท้าย (Final Message) เท่านั้นที่ส่งกลับมาเป็น Tool Result

✓ ความจริง: ไม่จริง: แต่ละ Turn ของ Subagent จะคงอยู่เฉพาะใน Conversation ของตัวมันเอง Context ของ Parent จะเพิ่มขึ้นเฉพาะข้อความตอบกลับสุดท้าย (Final Response) ของ Subagent เท่านั้น

💡 แก่นสถาปัตยกรรม (Core Architectural Law)

Explicit, Separated Prompt — Claude ทำงานได้ดีที่สุดเมื่อคำสั่งระบุเป้าหมายและเหตุผลอย่างชัดเจน พร้อมแยกประเภทเนื้อหา (คำสั่ง, Examples, เอกสาร, Untrusted Input) ออกเป็นสัดส่วนด้วย Label ซึ่งแทบทุกเทคนิคในบทเรียนนี้ล้วนต่อยอดมาจากแนวคิดดังกล่าว

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: การเขียนกฎด้วยตัวพิมพ์ใหญ่หรือการย้ำซ้ำๆ เป็นวิธีที่ดีที่สุดที่ทำให้ Claude ปฏิบัติตามคำสั่ง?
✓ ความจริง: ไม่จริง: การอธิบายเหตุผลเบื้องหลังกฎเกณฑ์ให้ผลลัพธ์ที่ดีกว่าอย่างมีนัยสำคัญ เพราะ Claude จะเข้าใจเป้าหมายและสามารถประยุกต์ใช้กับกรณีแวดล้อมที่ไม่ได้ระบุไว้ในกฎได้ด้วย
❌ เข้าใจผิด: ยิ่งใส่ตัวอย่างมากเท่าไหร่ก็ยิ่งดี ดังนั้นควรเริ่มต้นด้วยการใส่ตัวอย่างให้เยอะที่สุดเท่าที่เขียนได้?
✓ ความจริง: ไม่จริง: ควรเริ่มจาก 1 ตัวอย่างก่อน แล้วค่อยเพิ่มเมื่อ Output ยังไม่ได้ตามที่ต้องการเท่านั้น เพราะ Claude มีแนวโน้มที่จะเลียนแบบ Accidental Pattern ใดๆ ก็ตามที่ตัวอย่างเหล่านั้นมีร่วมกันติดไปด้วย
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: สำหรับเอกสารยาว ควรถามคำถามไว้ก่อนเพื่อ Claude จะได้รู้ว่าต้องหาอะไรระหว่างอ่าน เพราะในทางเทคนิคแล้ว เอกสารขนาดยาวต้องวางไว้ส่วนบนของ Prompt แล้วจึงตามด้วย Query, Instructions และ Examples ไว้ด้านล่างสุด
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: การทำ Prefill ที่ Assistant Turn สุดท้ายสามารถใช้ได้กับโมเดล Claude ทุกตัว เพราะโมเดลรุ่นใหม่ๆ จะปฏิเสธการทำ Prefill ใน Turn สุดท้าย ดังนั้นในโมเดลเหล่านั้นจึงต้องใส่ Format Guidance เข้าไปใน Instruction โดยตรงแทน
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •การปรับแต่ง (Adjustment) หมายรวมถึงการตัดข้อความออกพอๆ กับการเพิ่มเข้าไป เช่น Prompt ที่เคยเขียนให้โมเดลรุ่นเก่าอาจมีคำสั่งกำชับให้ตอบละเอียดเป็นพิเศษหรือเรียกใช้ Tools ให้ดุดันขึ้น แต่เมื่อย้ายมาใช้โมเดลรุ่นใหม่ คำสั่งเหล่านี้อาจทำให้โมเดลทำงานเกินความจำเป็น (Overdo) จึงควรลดทอนคำแนะนำดังกล่าวลงเมื่อทำการ Migrate และความล้มเหลวบางอย่างก็ไม่ใช่ปัญหาของ Prompt เลย หากตัวชี้วัดที่ตกคือ Latency หรือ Cost การเปลี่ยนไปใช้ Model อื่นที่เหมาะสมกว่าอาจแก้ปัญหาได้ง่ายกว่าการพยายามเขียน Prompt ใหม่ทั้งหมด
  • •ข้อความใดๆ ก็ตามที่คุณไม่ได้เขียนเอง ล้วนเป็นช่องทางที่อาจมีคำสั่งไม่พึงประสงค์แฝงเข้ามาได้ ไม่ว่าจะเป็นเนื้อหาอีเมล, หน้าเว็บที่ดึงมา (Fetched web page) หรือช่อง Free-text ที่ผู้ใช้กรอก โดยการโจมตีโดยตรงจากผู้ใช้ (Direct attack) และการโจมตีทางอ้อมจากเนื้อหา Third-party (Indirect attack) จัดเป็น Threat models คนละแบบ ซึ่งจะกล่าวถึงใน [Prompt injection and jailbreaks (two threat models)](lesson:7.1) แต่หน้าที่หลักของ Prompt Engineering ในส่วนนี้คือการจัดโครงสร้าง Prompt ให้ Claude สามารถแยกแยะความแตกต่างระหว่าง "คำสั่งระบบของคุณ" กับ "ข้อมูลที่นำมาประมวลผล" ได้อย่างชัดเจนเสมอ
  • •Prompt แรกใช้สร้างบทสรุป Prompt ที่สองตรวจสอบความถูกต้อง ความชัดเจน และความสมบูรณ์ และ Prompt ที่สามนำ Feedback นั้นมาปรับแก้ให้ดีขึ้น แต่ละรอบมีหน้าที่เฉพาะ โดยแลกกับ API Call และ Latency ที่เพิ่มขึ้น

✓ ความจริง: ไม่จริง: Prompting ทำได้เพียงเพิ่มโอกาสความน่าจะเป็นเท่านั้น ปัญหา Malformed JSON, ฟิลด์ตกหล่น หรือ Data Type ผิดพลาด จะถูกกำจัดได้อย่างเด็ดขาดก็ต่อเมื่อใช้ Constrained Decoding บังคับตาม Schema เท่านั้น
❌ เข้าใจผิด: การส่ง output_format=SomeModel ใน client.messages.parse() แตกต่างจาก output_config.format ใน messages.create()?

❌ เข้าใจผิด: strict: true สามารถตั้งค่ากับทุก Tool ใน tools array รวมถึง Computer และ Browser Use toolsets ได้หรือไม่?
✓ ความจริง: ไม่จริง: Toolsets ทั้งสองกลุ่มนี้ปฏิเสธ strict: true และ API Request จะ Error ทันทีหากมีการกำหนดค่านั้น

  • •หาก Content Block สุดท้ายเป็น tool_use ที่ไม่สมบูรณ์ การสั่ง Continue จะไม่ได้ Arguments ที่ถูกต้อง ต้องส่ง Request ใหม่อีกครั้งพร้อมปรับค่า max_tokens ให้สูงขึ้น

Prompt Injection and Jailbreak Defense for Claude Applications

💡 แก่นสถาปัตยกรรม (Core Architectural Law)

Instruction/data trust boundary — System Prompt และคำขอจากผู้ใช้ที่น่าเชื่อถือถือเป็น Instructions ในขณะที่ข้อมูลภายนอกใดๆ ที่ Claude อ่านแทนผู้ใช้ เช่น หน้าเว็บ, อีเมล, เอกสาร หรือผลลัพธ์จาก Tool ถือเป็น Untrusted Data ซึ่งต้องไม่ปล่อยให้เข้ามาเปลี่ยน Goals หรือ Actions ของ Claude ได้ การป้องกัน Injection ส่วนใหญ่ทำได้โดยการกำหนดขอบเขตนี้ให้ Claude รับรู้ชัดเจน และบังคับใช้ Trust Boundary นั้นอย่างเข้มงวดในโค้ดของคุณ

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: Claude มีความทนทานต่อ Injection สูงอยู่แล้ว แค่กำหนดกฎใน System Prompt อย่างเดียวก็เพียงพอที่จะทำให้ Agent ปลอดภัยแล้วใช่หรือไม่?
✓ ความจริง: ไม่จริง: การป้องกันระดับ Model Layer ช่วยกำหนดเพียงแนวโน้มพฤติกรรมเท่านั้นและไม่มีทางสมบูรณ์แบบ 100% จึงจำเป็นต้องมี Environmental Limits และหลักการ Least Privilege คอยควบคุมร่วมด้วยเสมอ
❌ เข้าใจผิด: การใส่คำสั่งควบคุมของเราไว้ใน tool_result เป็นวิธีที่น่าเชื่อถือที่สุดในการสั่งให้ Claude จัดการกับเนื้อหานั้น?
✓ ความจริง: ไม่จริง: Claude มองว่าข้อมูลใน tool_result ทั้งหมดเป็น Untrusted Content คำสั่งที่คุณใส่เข้าไปอาจถูกละเลยหรือมองว่าเป็น Injection ได้ หากต้องการสั่งการ ให้ใส่ไว้ใน User Turn ถัดไปแทน
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •ทั้ง Jailbreaking และ Prompt Injection ล้วนเป็นความพยายามหลอกให้ Claude ละเลยแนวทางความปลอดภัยหรือคำสั่งที่คุณกำหนดไว้ แม้แนวทางของ Anthropic จะระบุว่า Claude มีความทนทานต่อการโจมตีเหล่านี้สูงโดยธรรมชาติอยู่แล้ว และการเพิ่มการป้องกันระดับ Application-level จะช่วยเสริม Guardrails ให้แข็งแกร่งยิ่งขึ้น แต่คุณจะไม่สามารถเลือกใช้มาตรการป้องกันที่ถูกต้องได้เลยหากไม่รู้ว่าใครคือผู้โจมตี ซึ่งใน Documentation ได้แบ่ง Threat Models ออกเป็น 2 รูปแบบ
  • •รูปแบบแรกคือ Jailbreaks และ Direct Prompt Injection ซึ่งผู้ใช้งาน (User) ของแอปพลิเคชันคือผู้โจมตีเอง โดยจะพิมพ์ Input เพื่อเจาะทะลุ Guardrails ของคุณ ส่วนรูปแบบที่สองคือ Indirect Prompt Injection ซึ่งผู้ใช้งานเป็นกลุ่มที่ไว้ใจได้ (Trusted User) แต่ผู้โจมตีจะควบคุมเนื้อหาภายนอกที่ Claude ต้องประมวลผลแทน เช่น เนื้อหาใน Email ขาเข้า, หน้าเว็บที่ Fetch มา, ข้อความ OCR จากไฟล์ที่อัปโหลด หรือผลลัพธ์จาก Tool Call ซึ่งใครก็ตามที่แทรกแซงเนื้อหาเหล่านี้ได้ สามารถแฝงคำสั่งเพื่อเบี่ยงเบนการทำงานของ Claude ได้ทั้งสิ้น
  • •แทนที่จะพึ่งพาวิธีการเดียว แม้กลไกระดับ Model Layer อย่าง System Prompts, Classifiers และ Training จะทำงานได้ดีเยี่ยม (ใน Gray Swan Agent Red Teaming Benchmark ตัว Claude Opus 4.7 คุมอัตราความสำเร็จของการโจมตีครั้งเดียวไว้ได้ต่ำถึง ~0.1%) แต่เนื่องจากธรรมชาติของโมเดลเป็นแบบ Probabilistic กลไกเหล่านี้จึงกำหนดได้เพียง 'แนวโน้ม' พฤติกรรมของ Agent ไม่ใช่ 'ขีดความสามารถสูงสุด' ที่มันทำได้ การป้องกันที่ Model Layer จึงไม่มีทางได้ผล 100% และจำเป็นต้องมีข้อจำกัดระดับ Environment และการเข้าถึง External Content มาคอยกำกับเสมอ

  • •สำหรับ Claude Code จะควบคุมผ่าน Permission Rules และ Modes โดย Allow Rules อนุญาตให้ Tool ทำงานได้ทันทีโดยไม่ต้องขออนุมัติ, Ask Rules จะ Prompt ถามยืนยันทุกครั้ง และ Deny Rules จะบล็อก Tool นั้นโดยสิ้นเชิง ส่วน Mode จะเป็นตัวกำหนดพฤติกรรมสำหรับทุกคำสั่งที่ไม่อยู่ในขอบเขตของ Rules ที่ตั้งไว้

Guardrail Layering and Content Policy for Claude Applications
อ่านบทเต็ม →
💡 แก่นสถาปัตยกรรม (Core Architectural Law)

Guardrail Layering (Defense in Depth) — ไม่มีระบบควบคุมเดี่ยวใดป้องกันการ Misuse ได้ทั้งหมด การ Deploy ที่ปลอดภัยต้องซ้อนทับ Layer อิสระร่วมกัน: คัดกรอง Input, Hardened System Prompt, จัดการ Untrusted Content เชิงโครงสร้าง, คัดกรอง Tool Output, จำกัด Privileges ให้แคบที่สุด และทำ Monitoring เพื่อให้ Layer ถัดไปสามารถดักจับการโจมตีได้เมื่อ Layer ก่อนหน้าหลุดรอด

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: การใส่ Follow-up Instructions ของเราเองไว้ใน tool_result เป็นวิธีที่สะดวกในการคุม Control Flow ของ Claude หลังเรียก Tool เสร็จ เพราะ Claude มอง Content ใน Tool Result เป็น Untrusted Data คำสั่งที่ใส่ลงไปจึงอาจถูกเพิกเฉยหรือถูกมองว่าเป็น Injection Attempt ทางที่ถูกต้องคือต้องส่งคำสั่งมาใน User Turn ถัดไป
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: PostToolUse Hook สามารถทำหน้าที่เป็น Guardrail ป้องกันไม่ให้ Tool อันตรายทำงานได้ เพราะ PostToolUse ทำงานหลังจาก Tool รันเสร็จสิ้นไปเรียบร้อยแล้ว จึงไม่สามารถยับยั้งการทำงานได้ หากต้องการป้องกันแบบ Deterministic ต้องใช้ PreToolUse Hook เพื่อสั่ง Block Tool Call ล่วงหน้าก่อนรันเท่านั้น
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •ส่ง Untrusted Content เข้าทาง Tool Results เท่านั้น เพราะ Claude ถูก Train ให้ระแวงและตั้งข้อสงสัยต่อคำสั่งที่พบในจุดนี้ 2. ระบุบริบทและที่มาของ Content อย่างชัดเจน เช่น ใส่ใน Tool Description หรือตัว Result โดยตรง (เช่น "body of an inbound email from an unknown sender") เพื่อช่วยให้ Claude ตัดสินใจได้ว่าควรระวังข้อความที่ดูเหมือนคำสั่งมากน้อยเพียงใด 3. ประกาศ Security Policy ไว้ใน System Prompt โดยกำชับว่า Tool Content ถือเป็น Untrusted Data และห้าม Override คำสั่งหลักโดยเด็ดขาด 4. ทำ JSON-encode กับ Third-party Strings เสมอ การ Escape จะช่วยตีกรอบ Boundary ชัดเจน ป้องกันไม่ให้ Attacker ปิด Quote หรือ Tag เพื่อหลุดออกมาสั่งการใน Instruction Context 5. อย่าใส่ Instructions ของตัวเองลงใน Tool Results เพราะ Claude อาจมองข้ามหรือจัดว่าเป็น Injection ให้ส่งเป็น User Turn ถัดจาก tool_result แทน (หรือใช้ Mid-conversation System Message สำหรับ Models ที่รองรับ) 6. ตรวจกรอง Tool Outputs โดยรัน Raw Output ผ่าน Claude Haiku 4.5 Classifier เพื่อเช็คแฟล็ก injection_suspected หากเป็นจริง ให้ส่ง Error หรือสรุปเนื้อหาแบบ Strip ข้อมูลทิ้ง
  • •รูปแบบแรก ผู้ใช้งานหน้าแอปพลิเคชันคือผู้โจมตีโดยตรง พยายามเขียน Jailbreak หรือทำ Direct Prompt Injection เพื่อเลี่ยงกฎ รูปแบบที่สอง ผู้ใช้งานเป็นฝั่งที่เชื่อถือได้ (Trusted User) แต่ Claude ต้องไปอ่านเนื้อหาจากภายนอกแทนผู้ใช้ ซึ่งเนื้อหานั้นแฝงคำสั่งโจมตีไว้ การคัดกรองแค่หน้า Chat Box ไม่สามารถป้องกันเว็บเพจที่มีเนื้อหาเป็นพิษได้ และการ Escaping ผลลัพธ์จาก Tool ก็กันผู้ใช้ที่จงใจโจมตีไม่ได้เช่นกัน ระบบ Production จึงต้องมี Guardrails ทั้งสองด้านซ้อนทับกันเป็น Layer
  • •Hooks เหล่านี้ไม่ได้จำกัดอยู่แค่ Claude Code CLI แต่ Agent SDK ยังรองรับ Filesystem Hooks เดียวกันจาก settings.json

❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: การใช้ PostToolUse hook ส่ง exit code 2 จะช่วยหยุดคำสั่งที่สร้างความเสียหายได้ เพราะ PostToolUse ทำงานหลังจาก Tool รันสำเร็จไปแล้ว การส่ง exit 2 ทำได้เพียงส่ง stderr กลับไปให้ Claude เท่านั้น หากต้องการป้องกันจริงต้องดักที่ PreToolUse | คำถามหลอก / สิ่งที่มักเข้าใจผิด? (ทำไมถึงผิด): ไม่จริง: การส่ง exit code 2 จาก PermissionRequest hook จะเป็นการปฏิเสธ Permission เพราะ PermissionRequest จะไม่สนใจ exit code 2 หากต้องการ Deny สิทธิ์ จะต้องส่งผ่าน decision property ใน JSON Output ของ Hook เท่านั้น

✓ ความจริง: ไม่จริง: Matcher ที่ประกอบด้วยตัวอักษร, ตัวเลข, _, -, ช่องว่าง, จุลภาค และ | จะถูกประมวลผลเป็นรายการชื่อแบบตรงตัว (Exact Names) เท่านั้น จะเปลี่ยนเป็น Regular Expression ก็ต่อเมื่อมีตัวอักษรพิเศษอื่นนอกเหนือจากกลุ่มนี้

PreToolUse Guardrails: Exit Codes และการจัดการ Permissions ↗

PreToolUse guardrails: exit codes and permission decisions
อ่านบทเต็ม →
💡 แก่นสถาปัตยกรรม (Core Architectural Law)

การควบคุมความปลอดภัยก่อนรัน Tool (PreToolUse) ด้วย Hook Exit Codes, Permission Decisions (Deny/Ask/Allow) และ Agent SDK Callbacks

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: PreToolUse hook ที่ return exit 0 ถือเป็นการอนุมัติ (approve) ให้ tool call ทำงานได้ทันทีใช่หรือไม่?
✓ ความจริง: ไม่จริง: Exit 0 หมายถึง hook ไม่มีข้อคัดค้านเท่านั้น คำสั่งยังต้องผ่านการตัดสินจาก Permission flow ปกติ และอาจยังต้องรอการกดยืนยัน (prompt) จาก user อยู่ดี
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: exit 0 คือ allow (ความจริง: exit 0 หมายถึง "no objection" เท่านั้น ไม่ใช่ structured decision), และการ match decision ที่ถูกต้องตามโจทย์คือ: สั่งห้ามรันเด็ดขาด = deny, รันหลังจากมนุษย์กดอนุมัติ = ask, ข้าม prompt แต่ยังคงเคารพ deny rules ทุกข้อ = allow
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: Hook ที่ return ค่า permissionDecision เป็น allow จะสามารถอนุมัติได้ทุกอย่าง รวมถึงคำสั่ง rm บน critical path (เหตุผล: allow ทำหน้าที่แค่ข้าม prompt เท่านั้น แต่ deny และ ask rules ยังคงมีผลบังคับใช้ตามปกติ ซึ่งคำสั่ง rm และ rmdir บน critical path จะไม่มีทางถูก approve ด้วย allow ของ hook ได้เลย)
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •PreToolUse hook จะทำงานก่อนที่ Tool call จะถูก execute และเป็น Hook event ตัวเดียวที่สามารถสั่งยกเลิก (cancel) การเรียก Tool ได้ จึงเหมาะอย่างยิ่งสำหรับการทำ Guardrail ป้องกันคำสั่งอันตราย (destructive actions)
  • •เมื่อ event นี้ถูก trigger ตัว handler จะได้รับ payload เป็น JSON โดยมี shared fields พื้นฐานอย่าง session_id, cwd และ hook_event_name ตามด้วย tool_name และ tool_input ซึ่งเป็น arguments ที่ Claude ส่งมา เช่น หากเป็น Bash คำสั่ง shell จะอยู่ใน tool_input.command หรือหากเป็น File tools path ปลายทางจะอยู่ใน tool_input.file_path
  • •Guardrail ที่ดีควรตรวจสอบที่ arguments จริงเหล่านี้ ไม่ใช่ดูจาก intent หรือคำอธิบายที่โมเดลบอก เช่น การเขียน script ดึง tool_input.command ด้วย jq แล้ว grep หาคำสั่ง 'drop table' จะสามารถดักจับคำสั่งอันตรายได้เสมอ ไม่ว่าคำสั่งนั้นจะมาจากการที่ user สั่งตรงๆ หรือเกิดจาก Prompt Injection ที่แฝงมาในหน้าเว็บที่ถูกดึงมาก็ตาม

(ทำไมถึงผิด): ไม่จริง: 403 หมายถึง Key ผ่าน Authentication แล้ว แต่ขาด Permission/Scope ที่ Endpoint นั้นต้องการ เนื่องจาก Scope ถูกกำหนดตายตัวตั้งแต่สร้าง Key การแก้ไขจึงต้องสร้าง Key ใหม่ที่กำหนด Scopes ให้ครอบคลุม ไม่ใช่การขอ Re-issue Key สิทธิ์เดิมซ้ำ
❌ เข้าใจผิด: Key ที่หมดอายุแล้วสามารถเปิดใช้งานใหม่ (Reactivate) หรือขยายเวลา Expiration จาก Console ได้?
✓ ความจริง: ไม่จริง: Expiration จะถูก Fix ทันทีตั้งแต่ตอนสร้าง Key เมื่อหมดอายุแล้วจะ Return 401 authentication_error และไม่สามารถ Reactivate หรือขยายเวลาได้ ต้องสร้าง Key ใหม่เท่านั้น
❌ เข้าใจผิด: การ Delete Key ที่ต้องสงสัยสามารถย้อนกลับ (Reversible) ได้เหมือนกับการ Disable?
✓ ความจริง: ไม่จริง: เฉพาะคำสั่ง Disable เท่านั้นที่ย้อนกลับได้ด้วยการกด Re-enable ส่วนคำสั่ง Delete มีผลถาวร โดย Key จะถูก Archive ไว้เพื่อเป็นประวัติบันทึกเท่านั้น ไม่สามารถนำกลับมาใช้งานได้อีก

✓ ความจริง: ไม่จริง: สามารถ print log ทั่วไปลง stdout ได้ — เหตุผลทางเทคนิคคือ stdout ถูกสงวนไว้สำหรับ Protocol Traffic เท่านั้น หากมีคำสั่ง print() หรือ Debug Log หลุดเข้าไปจะทำให้ Message Stream เสียหายทันที ดังนั้น Log ทั้งหมดต้องส่งไปที่ stderr เท่านั้น
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: stdio Server สามารถพิมพ์ Debug Output ลง stdout ได้ แล้ว Client จะ Filter ออกให้เอง — เหตุผลคือ stdout รับได้เฉพาะ MCP Message ที่ถูกต้องตาม Spec เท่านั้น Logging ทั้งหมดต้องส่งผ่าน stderr ซึ่ง Client จะไม่นับว่าเป็นสัญญาณของ Error
❌ เข้าใจผิด: คำถามหลอก / สิ่งที่มักเข้าใจผิด?
✓ ความจริง: ไม่จริง: การรัน HTTP MCP Server ภายในเครื่องควร Bind เข้ากับ 0.0.0.0 เพื่อให้ทุก Client เข้าถึงได้ — เหตุผลคือ Local Server ต้อง Bind เฉพาะ localhost (127.0.0.1) เท่านั้น และต้องตรวจสอบ Origin Header เสมอเพื่อป้องกันช่องโหว่ DNS Rebinding
❌ เข้าใจผิด: ใน JSON config ใส่แค่ url ก็เพียงพอ เพราะ Claude Code จะ infer เป็น HTTP ให้อัตโนมัติจาก URL?
✓ ความจริง: ไม่จริง: config entry ที่ไม่ระบุ type จะถูกอ่านเป็น stdio เสมอ ดังนั้นรายการที่มี url จึงต้องระบุ type เป็น http, sse หรือ ws อย่างชัดเจนเสมอ

  • •TypeScript SDK ของ Anthropic ยังมี helper functions (mcpTools, mcpMessages, mcpResourceToContent) ที่ช่วยแปลง tools, prompts และ resources จาก server ให้อยู่ในรูปแบบ types ของ Claude API ได้โดยตรง

💡 แก่นสถาปัตยกรรม (Core Architectural Law)

Connections vs Know-how — Tools และ MCP Servers ให้ Claude เรียกใช้เพื่อ execute โค้ด (ทั้งแบบ local หรือ external system) ส่วน Skills ให้ Claude อ่านและปฏิบัติตามคู่มือหรือ reference โดยโหลดเฉพาะตอนที่จำเป็นต้องใช้ ซึ่งในระบบจริงมักต้องใช้งานร่วมกัน

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Traps & Key Insights)
❌ เข้าใจผิด: ในเมื่อ Anthropic เป็นผู้กำหนด Schema ของ bash และ text_editor ตัว Anthropic ก็น่าจะเป็นผู้ Execute คำสั่งเหล่านั้นเองใช่หรือไม่?
✓ ความจริง: ไม่จริง: ทั้งสองเป็น Client tools แม้ Anthropic จะเป็นผู้กำหนด Schema แต่ Application ของคุณยังคงต้องรันคำสั่งในเครื่องและส่ง tool_result กลับไป มีเพียง Server tools อย่าง web_search เท่านั้นที่รันบนระบบของ Anthropic
❌ เข้าใจผิด: การติดตั้ง Skills จำนวนมากจะทำให้ Context window เต็ม เพราะ Instructions ของทุก Skill จะถูกโหลดตั้งแต่ตอน Startup ใช่หรือไม่?
✓ ความจริง: ไม่จริง: ตอน Startup ระบบจะโหลดเพียงแค่ name และ description เข้าสู่ Context เท่านั้น เนื้อหาตัวเต็มจะถูกโหลดเข้ามาก็ต่อเมื่อ Skill นั้นถูก Trigger ใช้งานจริงเท่านั้น / สคริปต์ที่แนบไว้ใน Skill จะกิน Context ตามความยาวของโค้ด เพราะ Claude ต้องอ่านโค้ดก่อนรันใช่หรือไม่? (ทำไมถึงผิด): ไม่จริง: Claude รันสคริปต์ที่แนบมาผ่าน bash โดยตรง และนำเฉพาะ Output ที่ได้จากการรันเข้าสู่ Context เท่านั้น ตัว Source code ของสคริปต์จะไม่ถูกดึงเข้าสู่ Context แต่อย่างใด
❌ เข้าใจผิด: MCP และ Skills เป็นทางเลือกที่ใช้ทดแทนกันได้ สถาปัตยกรรมจึงต้องเลือกใช้อย่างใดอย่างหนึ่ง?
✓ ความจริง: ไม่จริง: ทั้งสองถูกออกแบบมาเพื่อแก้ปัญหาคนละส่วนและทำงานร่วมกัน โดย MCP จัดการด้านการเชื่อมต่อ (Connection) ส่วน Skill จัดการด้านองค์ความรู้และวิธีใช้งาน (Know-how)
❌ เข้าใจผิด: ข้อสอบ Scenario มักจะให้โจทย์ความต้องการมา แล้วถามหา Extension ที่เบาที่สุด (Lightest fitting)?
✓ ความจริง: ไม่จริง: การเลือก Extension ต้องดูโจทย์เป็นหลัก—หากไม่มีระบบภายนอกและไม่มี Custom Domain Logic คำตอบคือ Built-in Tools เสมอ, หากโจทย์ระบุถึงขั้นตอนการทำงาน (Procedure) หรือ Style Guide ให้เลือก Skill, หากโจทย์ระบุชื่อ Service เช่น Slack, Jira หรือ Database ให้เลือก MCP, และหากโจทย์ระบุทั้ง Service และข้อกำหนดวิธีใช้งาน (Conventions) ร่วมกัน คำตอบที่ถูกต้องคือต้องใช้ทั้งคู่
📌 สรุปสาระสำคัญประจำหัวข้อ (High-Yield Takeaways)
  • •ทั้งสองตัวเลือกยังมีความแตกต่างกันอย่างมากในแง่ของ Context Cost ทุกสิ่งที่ Claude อ่านในแต่ละ Turn จะถูกนับรวมใน [Context Window budget](lesson:6.1) ซึ่งรวมถึง Tool Definitions ด้วย เนื่องจาก API จะนำ Tool Definitions ที่ส่งไปมารวมเข้าเป็น System Prompt โดย MCP Clients ส่วนใหญ่จะโหลด Tool Definitions ทั้งหมดขึ้นมาตั้งแต่แรก (Upfront) ทำให้ Agent ที่เชื่อมกับ Tools นับพันรายการต้องอ่าน Token หลายแสน Tokens ก่อนที่จะเห็นข้อความ Request ด้วยซ้ำ
  • •เมื่อ Action นั้นเป็น Domain logic เฉพาะของคุณและ Agent ต้องเรียกใช้บ่อยๆ โครงสร้างของ Custom tool ประกอบด้วย name, description และ input_schema โดยฝั่ง Application ของคุณจะเป็นผู้รันคำสั่ง ใน Agent SDK คุณสามารถลงทะเบียน Custom tools ผ่าน In-process MCP server เพื่อให้ Claude เรียกใช้ Functions, ยิง API หรือจัดการ Business logic เฉพาะทาง ตัวอย่างคลาสสิกคือ Email agent ที่ต้องทำ fetchInbox และ searchEmails ซ้ำๆ จึงเหมาะที่จะทำเป็น Tools
  • •Skill จะแพ็ก "ขั้นตอนการทำงาน (Procedure)" ไม่ใช่การทำ Action เดี่ยวๆ โครงสร้างของมันคือ Directory ที่มีไฟล์ SKILL.md สำหรับเก็บ Instructions และ Metadata ร่วมกับ Scripts, Templates หรือ Reference files เสริม โดย Claude จะหยิบมาใช้โดยอัตโนมัติเมื่องานตรงกับเงื่อนไข เนื้อหาทั่วไปมักเป็น Deployment checklist, Code review workflow หรือ API style guide ซึ่งช่วยลดภาระการคัดลอก Prompt เดิมๆ วางใน Chat ทุกครั้งที่เริ่ม Session
