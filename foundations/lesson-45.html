💡 แนวคิดหลักสำคัญ (Key Concept)

Connections vs know-how — Tools and MCP servers give Claude something to call: an action that code carries out, locally or in an external system. Skills give Claude something to read and follow: a procedure or reference that loads only when the task needs it. Many real setups need both.

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 55798

A platform team keeps pasting the same multi-step production deployment checklist into chat every time someone ships a release, and the steps sometimes get skipped when typed manually. What is the most appropriate way to address this in Claude Code?

A Capture the checklist as a Skill invoked with a slash command like /deploy
B Add the entire checklist as a permanent block inside CLAUDE.md
C Configure an MCP server that exposes the checklist as a resource
D Create a custom tool whose handler prints the checklist to the transcript
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct: a repeated multi-step procedure pasted into chat is the canonical trigger for turning it into a Skill, which loads on demand via /deploy instead of being retyped.

ตัวเลือก B: ไม่ถูกต้อง

CLAUDE.md is meant for always-on conventions loaded every session; a deployment procedure is a workflow rather than a persistent fact, so it belongs in a Skill instead.

ตัวเลือก C: ไม่ถูกต้อง

MCP servers connect Claude to external systems and expose tools or resources from those systems; building one just to store static checklist text adds unnecessary infrastructure.

ตัวเลือก D: ไม่ถูกต้อง

A custom tool wraps a function Claude calls to perform an action or fetch data; simply printing static text is not a tool's purpose and adds needless complexity for no benefit.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Built-in tools first, custom tools for domain actions" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

You can extend Claude in four ways: tools Anthropic already provides, tools you write yourself, skills that carry know-how, and MCP servers that connect it to outside systems. Choosing wrongly costs you one of two things. Either you write code you didn't need, or you spend context you didn't need to spend. The first split is in tool use itself, which lets Claude call functions that you define or that Anthropic provides.

Anthropic-provided tools come in two kinds, and where the code runs separates them. Server tools such as web_search, web_fetch and code_execution run on Anthropic's infrastructure, so your application has no handler to write. Anthropic-schema client tools such as bash and text_editor work differently. Anthropic writes the schema and trains Claude on it, but your application still runs every call and returns the tool_result. When a tool is "built in", that tells you who designed it. It does not tell you who executes it.

Start with the built-in tools. Claude Code and the Agent SDK already ship tools for the everyday work of an agent: Read, Edit, Write, Bash, Grep, Glob, WebFetch and others. In the SDK you enable them by name in allowed_tools. Say the job is a one-off refactor that reads files, runs shell commands and searches the codebase. That job needs no new code at all. Bash on its own lets the agent do flexible, general-purpose work on a computer. The built-in list can also be cut down: pass a tools array that lists only the built-ins you want, and the rest stay out of Claude's context.

A custom tool earns its place when the action belongs to your domain and the agent will take it often. A custom tool is a name, a description and an input_schema, and your own code runs each call. The mechanics are taught in [defining and handling custom tools](lesson:8.1). In the Agent SDK, you register custom tools through an in-process MCP server so that Claude can call your functions, reach your APIs and carry out domain-specific operations. An email agent is the standard example. fetchInbox and searchEmails are the actions it takes over and over, so they become tools. Keep that set small. Rather than separate create_pr, review_pr and merge_pr tools, define one tool with an action parameter. Fewer tools give Claude fewer to choose between and less ambiguity when it picks one.

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A skill packages a procedure rather than an action. It is a directory with a SKILL.md file of instructions and metadata, plus optional scripts, templates and reference files, and Claude uses it automatically when it fits the task. Typical contents are a deployment checklist, a code review procedure, or an API style guide. These are things you would otherwise paste into chat at the start of every session.

Only two fields are required: name and description. name can be at most 64 characters, using only lowercase letters, numbers and hyphens. description can be at most 1024 characters. The description does the real work. Claude compares each request against it to decide whether to trigger the skill, so it has to say what the skill does and also when to use it. A description like "PDF helper" fails because it never says when.

Progressive disclosure means a skill loads in stages rather than all at once. At startup the system prompt holds only each skill's name and description. When a request matches a description, Claude uses bash to read SKILL.md from the filesystem, and only at that point does the body enter context. Bundled files load only if those instructions point to them. Scripts are the cheapest part: Claude runs them, and only their output enters context. Their code never does. A skill can therefore bundle a large API reference at no cost until Claude actually opens a file from it.

Skills are triggered in two ways. You can type /, or Claude can match the description to your task. In Claude Code they are plain directories: ~/.claude/skills/ for personal skills and .claude/skills/ for project skills, with no upload step. On the Claude API they run inside the code execution tool's container, so using skills there requires that tool. A skill can direct Claude to call tools and run code, so treat one from an unknown source the way you would treat software you are about to install.

3.MCP for connections, skills for procedures

Model Context Protocol (MCP) คือเกณฑ์วิธีมาตรฐานเปิดที่เชื่อมต่อ Claude เข้ากับแหล่งข้อมูลภายนอกและเครื่องมืออย่างปลอดภัย:

1. Tools (เครื่องมือ) ฟังก์ชันที่โมเดลสามารถสั่งรันได้เพื่อสร้างผลกระทบต่อระบบภายนอก (เช่น รันคำสั่ง SQL หรือยิง API)
2. Resources (ทรัพยากร) ข้อมูลแบบอ่านอย่างเดียว (Read-only data) ที่คล้ายกับไฟล์หรือเนื้อหาเอกสารสำหรับให้อ่านเป็นบริบท
3. Prompts (พร้อมต์) เทมเพลตคำสั่งและกระบวนการทำงานที่เตรียมไว้ให้ผู้ใช้หรือเอเจนต์เรียกใช้งานได้อย่างรวดเร็ว
AspectMCPSkill
What it isProtocol for connecting to external servicesKnowledge, workflows, and reference material
ProvidesTools and data accessKnowledge, workflows, reference material
ExamplesSlack integration, database queries, browser controlCode review checklist, deploy workflow, API style guide
⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

Exam trapMCP and skills are alternatives, so a design has to pick one or the other.Why is that wrong?They solve different problems and are designed to work together. MCP provides the connection, and a skill holds the know-how for using it.

An engineering team already has a working internal Slack bot with OAuth handled by Anthropic's published Slack MCP server. They now want Claude Code to post release notes to a channel. What should they do instead of writing a custom tool from scratch?

A Connect the existing Slack MCP server so Claude reuses its messaging tools and authentication
B Write a custom tool whose handler re-implements the Slack Web API client and OAuth refresh flow
C Create a Skill that contains hard-coded Slack API request examples to copy manually
D Use the built-in Bash tool to call curl against the Slack API endpoints from the shell
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct: when a maintained MCP server already exists for a service, connecting to it reuses its authentication and tool definitions instead of duplicating that work in a custom tool.

ตัวเลือก B: ไม่ถูกต้อง

Reimplementing the OAuth flow and API client duplicates work the existing MCP server already solved, adding maintenance burden without adding capability.

ตัวเลือก C: ไม่ถูกต้อง

A Skill can describe how to use a tool, but it cannot itself authenticate or make network calls, so release notes would never actually reach Slack.

ตัวเลือก D: ไม่ถูกต้อง

Shelling out with curl bypasses structured tool schemas and error handling, and requires managing credentials manually inside the Bash environment.

Use MCP when Claude has to reach a system it can't otherwise see, and a skill when it needs to know how to do something. MCP is a protocol for connecting to external services, and it gives Claude tools and data access: posting to Slack, querying a database, controlling a browser. A skill gives Claude knowledge, workflows and reference material. A simple test helps. If you keep copying data out of a browser tab that Claude can't see, connect that system as an MCP server. If you paste the same multi-step playbook into chat for the third time, turn it into a skill. Building the server itself is covered in [MCP server development](lesson:8.2).

The two also differ sharply in what they cost in context. Everything Claude reads in a turn counts against the [context window budget](lesson:6.1), and tool definitions are part of it. The API builds a system prompt from the tool definitions you pass. Most MCP clients load every tool definition upfront, so an agent wired to thousands of tools reads hundreds of thousands of tokens before it even sees the request. A skill pays about 100 tokens until it is triggered. When the tool list itself is the problem, tool search lets Claude load tools on demand instead of all at once.

The strongest setups combine the two. The MCP server provides the connection, and a skill teaches Claude how to use it well. Take an analytics database. MCP lets Claude run queries against it, but it says nothing about which tables matter or how your team writes joins. A skill holding the schema notes and query patterns covers that, and it loads only when a database question comes up.

A fintech startup is building an internal support agent with the Claude Agent SDK. The agent must look up account balances from a proprietary ledger service reachable only through an internal REST gateway with no existing MCP server or public SDK. Which approach best fits this requirement?

A Define a custom tool that calls the internal REST gateway and register it through an in-process MCP server
B Rely on the built-in WebFetch tool to query the gateway directly from the agent's prompt
C Write a Skill that documents the ledger schema and expects Claude to reason about balances from memory
D Search for a community MCP server that might expose a similar ledger balance capability
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct: a custom tool wraps the handler logic for calling the proprietary gateway and is registered via create_sdk_mcp_server/createSdkMcpServer, giving Claude a purpose-built function for this internal system.

ตัวเลือก B: ไม่ถูกต้อง

WebFetch is a general-purpose built-in tool for parsing public web pages; it is not designed for authenticated internal gateway calls with structured request/response handling.

ตัวเลือก C: ไม่ถูกต้อง

A Skill supplies knowledge or workflow instructions, not a live connection to an external system, so Claude would have no way to actually retrieve real balance data.

ตัวเลือก D: ไม่ถูกต้อง

No public integration exists for this proprietary internal service, so a community MCP server would not have the credentials or schema to reach it.

Work through the options in order of cost. First, check whether the built-in tools already cover the job. File reads, edits, shell commands and code search usually are. Next, ask whether Claude needs to reach an external system: if so, connect it over MCP. If Claude can reach everything but keeps getting a procedure wrong, write a skill. Write a custom tool only for a domain action the agent repeats often and that no existing tool expresses cleanly. When a second repository needs the same setup, package it all as a plugin, which is how these features are bundled and distributed.
