⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
Because Anthropic defines the bash and text_editor schemas, Anthropic also executes those tools. (ทำไมถึงผิด): They are client tools. Anthropic supplies the schema, but your application runs each call and returns the tool_result. Only server tools such as web_search run on Anthropic's side.

You can extend Claude in four ways: tools Anthropic already provides, tools you write yourself, skills that carry know-how, and MCP servers that connect it to outside systems. Choosing wrongly costs you one of two things. Either you write code you didn't need, or you spend context you didn't need to spend. The first split is in tool use itself, which lets Claude call functions that you define or that Anthropic provides.

Anthropic-provided tools come in two kinds, and where the code runs separates them. Server tools such as web_search, web_fetch and code_execution run on Anthropic's infrastructure, so your application has no handler to write. Anthropic-schema client tools such as bash and text_editor work differently. Anthropic writes the schema and trains Claude on it, but your application still runs every call and returns the tool_result. When a tool is "built in", that tells you who designed it. It does not tell you who executes it.

Start with the built-in tools. Claude Code and the Agent SDK already ship tools for the everyday work of an agent: Read, Edit, Write, Bash, Grep, Glob, WebFetch and others. In the SDK you enable them by name in allowed_tools. Say the job is a one-off refactor that reads files, runs shell commands and searches the codebase. That job needs no new code at all. Bash on its own lets the agent do flexible, general-purpose work on a computer. The built-in list can also be cut down: pass a tools array that lists only the built-ins you want, and the rest stay out of Claude's context.

A custom tool earns its place when the action belongs to your domain and the agent will take it often. A custom tool is a name, a description and an input_schema, and your own code runs each call. The mechanics are taught in [defining and handling custom tools](lesson:8.1). In the Agent SDK, you register custom tools through an in-process MCP server so that Claude can call your functions, reach your APIs and carry out domain-specific operations. An email agent is the standard example. fetchInbox and searchEmails are the actions it takes over and over, so they become tools. Keep that set small. Rather than separate create_pr, review_pr and merge_pr tools, define one tool with an action parameter. Fewer tools give Claude fewer to choose between and less ambiguity when it picks one.

A skill packages a procedure rather than an action. It is a directory with a SKILL.md file of instructions and metadata, plus optional scripts, templates and reference files, and Claude uses it automatically when it fits the task. Typical contents are a deployment checklist, a code review procedure, or an API style guide. These are things you would otherwise paste into chat at the start of every session.

Only two fields are required: name and description. name can be at most 64 characters, using only lowercase letters, numbers and hyphens. description can be at most 1024 characters. The description does the real work. Claude compares each request against it to decide whether to trigger the skill, so it has to say what the skill does and also when to use it. A description like "PDF helper" fails because it never says when.

Progressive disclosure means a skill loads in stages rather than all at once. At startup the system prompt holds only each skill's name and description. When a request matches a description, Claude uses bash to read SKILL.md from the filesystem, and only at that point does the body enter context. Bundled files load only if those instructions point to them. Scripts are the cheapest part: Claude runs them, and only their output enters context. Their code never does. A skill can therefore bundle a large API reference at no cost until Claude actually opens a file from it.

Skills are triggered in two ways. You can type /<name>, or Claude can match the description to your task. In Claude Code they are plain directories: ~/.claude/skills/ for personal skills and.claude/skills/ for project skills, with no upload step. On the Claude API they run inside the code execution tool's container, so using skills there requires that tool. A skill can direct Claude to call tools and run code, so treat one from an unknown source the way you would treat software you are about to install.

Use MCP when Claude has to reach a system it can't otherwise see, and a skill when it needs to know how to do something. MCP is a protocol for connecting to external services, and it gives Claude tools and data access: posting to Slack, querying a database, controlling a browser. A skill gives Claude knowledge, workflows and reference material. A simple test helps. If you keep copying data out of a browser tab that Claude can't see, connect that system as an MCP server. The two also differ sharply in what they cost in context. Everything Claude reads in a turn counts against the [context window budget](lesson:6.1), and tool definitions are part of it. The API builds a system prompt from the tool definitions you pass. Most MCP clients load every tool definition upfront, so an agent wired to thousands of tools reads hundreds of thousands of tokens before it even sees the request. A skill pays about 100 tokens until it is triggered. When the tool list itself is the problem, tool search lets Claude load tools on demand instead of all at once.

The strongest setups combine the two. The MCP server provides the connection, and a skill teaches Claude how to use it well. Take an analytics database. MCP lets Claude run queries against it, but it says nothing about which tables matter or how your team writes joins. A skill holding the schema notes and query patterns covers that, and it loads only when a database question comes up.

4. การเลือกเครื่องมือในตัว เครื่องมือแบบกำหนดเอง ทักษะ และ MCP

Model Context Protocol (MCP) คือเกณฑ์วิธีมาตรฐานเปิดที่เชื่อมต่อ Claude เข้ากับแหล่งข้อมูลภายนอกและเครื่องมืออย่างปลอดภัย:

1. Tools (เครื่องมือ) ฟังก์ชันที่โมเดลสามารถสั่งรันได้เพื่อสร้างผลกระทบต่อระบบภายนอก (เช่น รันคำสั่ง SQL หรือยิง API)
2. Resources (ทรัพยากร) ข้อมูลแบบอ่านอย่างเดียว (Read-only data) ที่คล้ายกับไฟล์หรือเนื้อหาเอกสารสำหรับให้อ่านเป็นบริบท
3. Prompts (พร้อมต์) เทมเพลตคำสั่งและกระบวนการทำงานที่เตรียมไว้ให้ผู้ใช้หรือเอเจนต์เรียกใช้งานได้อย่างรวดเร็ว

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Work through the options in order of cost. First, check whether the built-in tools already cover the job. File reads, edits, shell commands and code search usually are. Next, ask whether Claude needs to reach an external system: if so, connect it over MCP. If Claude can reach everything but keeps getting a procedure wrong, write a skill. Write a custom tool only for a domain action the agent repeats often and that no existing tool expresses cleanly. When a second repository needs the same setup, package it all as a plugin, which is how these features are bundled and distributed.
