1. การคิดแบบปรับตัวและขยายขอบเขต แบบจําลองต่อแบบจําลอง

Extended Thinking คือโหมดที่อนุญาตให้ Claude คิดไตร่ตรองขั้นตอนและกลยุทธ์ก่อนที่จะเริ่มเขียนคำตอบจริง:

  • โมเดลจะสร้างกระบวนการคิดอยู่ในแท็ก <thinking> ซึ่งมองเห็นได้ผ่าน API แต่ไม่ควรนำไปแสดงตรงให้ผู้ใช้ทั่วไป
  • ต้องกำหนดพารามิเตอร์ budget_tokens (ขั้นต่ำ 1,024 โทเค็น) และค่า max_tokens ต้องมากกว่า budget เสมอ
  • โทเค็นในการคิดจะคิดราคาในอัตราเดียวกับ Output Tokens ปกติ

การคิดช่วยให้ Claude ทํางานผ่านปัญหาก่อนที่จะตอบได้ มันจะถามคําถามใหม่ ทดลองแนวทาง ตรวจสอบผลลัพธ์ขั้นกลาง และทิ้งเส้นทางที่ไม่สามารถทนได้ นั่นคือเหตุผลที่การคิดช่วยได้มากที่สุดในด้านคณิตศาสตร์ การเขียนโค้ด การวิเคราะห์ และงานด้านเอเจนต์ที่ยาวนาน นอกจากนี้ยังมีค่าใช้จ่าย: โทเค็นการคิดจะถูกเรียกเก็บเงินเป็นโทเค็นเอาต์พุตแม้ว่า

คุณจะไม่เห็นข้อความเลย และจะถูกนับเป็น max_tokens

มีสองวิธีในการกําหนดค่าการคิด การคิดแบบปรับตัวได้ (ประเภท: “การคิดแบบปรับตัวได้”) ช่วยให้ Claude ตัดสินใจได้ว่าจะคิดเมื่อใดและคิดลึกแค่ไหน และ

คุณสามารถควบคุมได้ด้วยความพยายาม การคิดแบบขยาย (ประเภท: “เปิดใช้งาน” ด้วย budget_tokens) กําหนดงบประมาณโทเค็นด้วยตัวเอง งบประมาณต้องมีอย่างน้อย 1,024 โทเค็นและน้อยกว่า max_tokens และเป็นเป้าหมาย ไม่ใช่ขีดจํากัดสูงสุด max_tokens ยังคงเป็นขีดจํากัดสูงสุดสําหรับผลลัพธ์ทั้งหมด

effort เป็นพารามิเตอร์คําขอ output_config.effort ซึ่งควบคุมจํานวนโทเค็นที่ Claude ใช้จ่ายในการตอบสนอง รวมถึงการคิด ค่าใช้จ่ายมี 5 ระดับ โดยเริ่มจากค่าใช้จ่ายน้อยที่สุดไปจนถึงค่าใช้จ่ายมากที่สุด: ต่ํา ปานกลาง สูง xhigh และสูงสุด ไม่ใช่ทุก

Thinking lets Claude work through a problem before it answers. It restates the question, tries approaches, checks intermediate results and drops paths that don't hold up. That is why thinking helps most on math, coding, analysis and long agentic tasks. It also costs money: thinking tokens are billed as output tokens even when you never see the text, and they count toward max_tokens.

There are two ways to configure thinking. Adaptive thinking (type: "adaptive") lets Claude decide when to think and how deeply, and you steer it with effort. Extended thinking (type: "enabled" with budget_tokens) sets a token budget yourself. The budget must be at least 1,024 tokens and less than max_tokens, and it is a target, not a hard cap. max_tokens is still the hard limit on total output.

Effort is the request parameter output_config.effort, which controls how many tokens Claude spends on a response, thinking included. It has five levels, from least to most spending: low, medium, high, xhigh and max. Not every model accepts every level, and the default differs by model.

Support splits by model generation. On Opus 5.5, Sonnet 5.5 and Fable 5.1, adaptive thinking is on with no configuration, and manual budgets are rejected. On Opus 4.8 and 4.7, thinking stays off until you send "adaptive". Claude Haiku 4.5 goes the other way: it rejects "adaptive" and only supports extended thinking with budget_tokens. So if a workload needs an exact thinking budget at the lowest price per token, Haiku 4.5 is the model.

Thinking arrives in thinking content blocks before the text. Even when it is visible, it is a summary of Claude's reasoning, never the raw chain of thought. The display field controls what is returned, and it works with both adaptive and extended thinking. It takes three values:

- "summarized" returns a readable summary. It is the default on Claude Opus 4.6, Sonnet 4.6, Haiku 4.5 and earlier models. - "omitted" returns the block with an empty thinking field and an encrypted signature. It is the default on Opus 5.5, Sonnet 5.5, Fable 5.1, Opus 5, Opus 4.8 and Opus 4.7. - "updates" (beta) also leaves thinking empty but returns the short progress notes some models write between tool calls.

"omitted" speeds up delivery but does not lower cost. When streaming, the server skips the thinking text and sends only the signature, so the final answer starts sooner. You still pay for every thinking token. If your interface shows reasoning to users, "omitted" looks like a long pause before anything appears, so set "summarized" to bring back visible progress. Whichever value you choose, pass thinking blocks back unchanged in multi-turn conversations.

Moving a working integration to Claude Opus 5.5 or Sonnet 5.5 can turn previously valid requests into 400 errors. These failures are loud, which makes them the easy kind to fix. On these models the following are rejected:

- thinking: {"type": "enabled", "budget_tokens": N}. Control thinking depth with effort instead. - thinking: {"type": "disabled"}. Opus 5.5 cannot turn thinking off at all. Sonnet 5.5 uses "between_tools" as its lowest setting. - Non-default temperature, top_p or top_k. - A prefilled assistant turn at the end of the messages. - tool_choice of type any or tool. On Sonnet 5.5 this applies even on the token counting endpoint. - The computer_20251124 tool for Opus 5.5 on the Claude API and Google Cloud. Use the computer_toolset_20260801 toolset there.

between_tools suppresses up-front thinking but keeps thinking between tool calls: the model skips deliberation before it starts, and the short progress updates it writes while tools run still come back as thinking blocks. Choose it when a request should start answering immediately and you don't need deep reasoning first. Without tools, the response contains only text.

between_tools has its own limit. It works at low, medium and high effort and returns a 400 at xhigh or max. If you need those levels, use adaptive thinking. Code ported from Sonnet 5 that paired disabled with xhigh therefore needs two changes, not one.

Forced tool calls need a different approach on these models. Send tool_choice: {"type": "auto"}, mark the tool strict: true so its input matches the schema, and tell the model in the prompt when to call the tool. With auto, the model can now answer without calling the tool at all.

การเปลี่ยนแปลงเดียวกันนี้ยังส่งผลต่องบประมาณอีกด้วย max_tokens ยังคงเป็นขีดจํากัดที่เข้มงวดในการคิดรวมกับข้อความ ดังนั้นขนาดขีดจํากัดสําหรับเอาต์พุตแบบตอบเท่านั้นจึงสามารถตัดการตอบสนองได้ การคิดจะถูกเรียกเก็บเงินเป็นเอาต์พุต ดังนั้นค่าใช้จ่ายต่อคําขอจะเพิ่มขึ้นเช่นกัน ที่ xhigh หรือ max เริ่ม max_tokens ที่ 64k ค่าเริ่มต้นจะเปลี่ยนไปเช่นกัน Opus 5.5 ตั้งค่าเริ่มต้นเป็นความพยายามปานกลางในขณะที่ Opus 5 ตั้งค่าเริ่มต้นเป็นสูง ดังนั้นตั้งค่าความพยายามอย่างชัดเจนและเรียกใช้การสแกนความพยายามอีกครั้งแทนที่จะใช้การตั้งค่าเก่า โค้ดที่วิเคราะห์ข้อความการคิดจะได้รับสตริงเปล่า เนื่องจากการแสดงผลตอนนี้เป็นค่าเริ่มต้นเป็น “ละเว้น”

การสลับโมเดลระหว่างการสนทนาจะทําให้การคิดหยุดลงโดยไม่มีการเตือน Claude Sonnet 5.5 ไม่สามารถอ่านบล็อกการคิดจากโมเดล Opus 5, Opus 5.5, Fable หรือ Mythos ได้ API ลบบล็อกเหล่านั้นออกและยังคงส่งคืน 200 และบล็อกที่ลบออกจะไม่ถูกเรียกเก็บเงิน เราเตอร์ที่เปลี่ยนจาก Opus 5.5 เป็นโมเดลอื่นควรคาดหวังว่าโมเดลนั้นจะทํางานโดยไม่มีการให้เหตุผลก่อนหน้านี้ของ Opus 5.5

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The worst migration bugs return 200. The most common one comes from thinking that switches on by itself. A request that ran without thinking on an older model now thinks, so the response can start with a thinking block. Code that reads content[0].text, or a stream handler that treats the first block as text, breaks. Pick out blocks by their type field instead.

The same change also affects budgets. max_tokens is still a hard limit on thinking plus text together, so a limit sized for answer-only output can now cut responses off. Thinking is billed as output, so cost per request goes up too. At xhigh or max, start max_tokens at 64k. Defaults shift as well. Opus 5.5 defaults to medium effort where Opus 5 defaulted to high, so set effort explicitly and re-run your effort sweep instead of carrying over an old setting. Code that parsed thinking text gets empty strings, because display now defaults to "omitted".

Switching models partway through a conversation drops thinking without warning. Claude Sonnet 5.5 can't read thinking blocks from Opus 5, Opus 5.5, Fable or Mythos models. The API removes those blocks and still returns 200, and the removed blocks aren't billed. A router that falls back from Opus 5.5 to another model should expect that model to run without Opus 5.5's earlier reasoning.
