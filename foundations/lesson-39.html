1. ประเภทของ Key และ Identity ที่ผูกกับ Key

ทุก Request ที่ส่งไปยัง Claude API จะทำหน้าที่แทน Identity ของใครบางคนเสมอ โดยประเภทของ Key จะเป็นตัวกำหนด Static API key คือ Secret ที่ขึ้นต้นด้วย sk-ant-api... ซึ่งต้องส่งผ่าน Header Authorization: Bearer <key> ในทุก Request เมื่อสร้าง Key ใน Claude Console ภายใต้ Settings → API keys ช่อง Linked account จะเป็นตัวกำหนดประเภท เลือกลิงก์กับตัวเอง สำหรับ Personal key หรือลิงก์กับ Service Account สำหรับ Key ที่ต้องใช้ร่วมกันหลายคนหรือรันบน Workload ประเภทของ Key จะกำหนด Resource ที่เข้าถึงได้และเงื่อนไขการหมดอายุการใช้งาน

Personal key และ Service account key เป็นแบบ Identity-backed กล่าวคือทุก Request จะรันด้วย Permissions ของ User หรือ Service Account ภายใต้ Organization เสมอ ดังนั้นการลบ Identity นั้นทิ้งจะทำให้ Key ถูกตัดสิทธิ์ทันที ต่างจาก Workspace key (Legacy) ที่ไม่มี Owner จึงยังคงทำงานต่อได้แม้ Engineer ผู้สร้างจะลาออกไปแล้ว นี่คือเหตุผลที่ Workspace key ของอดีตพนักงานยังรัน Pipeline ต่อได้เป็นเดือนๆ และเป็นเหตุผลว่าทำไม Integration ใหม่จึงควรเปลี่ยนมาใช้ Identity-backed keys ทั้งหมด

การเลือกระหว่าง Identity-backed สองประเภทขึ้นอยู่กับว่าใครเป็นผู้รันโค้ด สคริปต์ส่วนตัวหรือช่วง Local Development ควรใช้ Personal key การนำ Personal key ไปแชร์ในทีมจะทำให้ระบบผูกกับตัวบุคคลคนเดียวและพังทันทีที่คนนั้นลาออก ส่วน CI Jobs และ Production Services ต้องใช้ Service account แยกต่าง หาก โดยให้ Organization Admin เป็นผู้สร้างเพื่อให้ Workload นั้นมี Identity อิสระเป็นของตัวเอง

Admin API keys เป็น Credential คนละประเภท ใช้สำหรับจัดการ Organization ไม่ใช่สำหรับเรียก Model สร้างได้เฉพาะผู้ใช้ที่มี Admin Role ใน Claude Console ภายใต้ Settings → Admin keys โดยมี Prefix เป็น sk-ant-admin01-... ใช้ Authenticate ได้ทั้ง Admin API, Usage and Cost API, Rate Limits API และ API หมวด Admin อื่นๆ โดย Key ที่สร้างใน Organization หนึ่งจะไม่สามารถนำไปจัดการ Organization อื่นได้

Authentication คือขั้นตอนที่ API ตรวจสอบว่าใครเป็นผู้เรียก โดยมี Key ทำหน้าที่เป็นหลักฐานยืนยัน Key จะถูกส่งเป็น Bearer token ใน Authorization Header แต่ระบบยังรองรับ Header เก่าอย่าง x-api-key อยู่ ซึ่งโดยทั่วไป Admin API มักส่งผ่านทางนี้ หาก Key ไม่ถูกต้อง, ถูก Archive หรือ Expired จะล้มเหลวที่ขั้นตอนนี้ด้วย 401 authentication_error ซึ่ง Key ที่หมดอายุแล้วจะไม่สามารถกู้คืนได้ ต้องสร้าง Key ใหม่เท่านั้น นอกจากนี้ยังมี Federated Workload Identity เป็นอีกวิธีในการรับ Claude Token ซึ่งจะมีเนื้อหาในส่วนถัดไป

Authorization (Level verification) คือการตรวจสอบแยกต่างหากว่า Caller ที่ Authenticate ผ่านแล้วมีสิทธิ์ทำ Action นั้นหรือไม่ หากล้มเหลวจะได้ Status 403 Forbidden สำหรับ Personal key ระดับสิทธิ์จะอิงตาม Organization Role ของเจ้าของ (เช่น Developer จัดการ API keys ได้ แต่การจัดการ Users ต้องใช้สิทธิ์ Admin) ส่วน Claude Enterprise keys จะมีการกำหนด Scope ชัดเจน เช่น read:members หรือ read:analytics ตั้งแต่ตอนสร้าง Key หากยิง Request นอก Scope จะได้รับ 403 พร้อมระบุ Scopes ที่ Key มีและ Scopes ที่ Endpoint ต้องการ การขยาย Scope ทำได้โดยสร้าง Key ใหม่เท่านั้น สำหรับ Console Admin API keys จะไม่มี Scope ให้เลือกและมีสิทธิ์เต็มในทุก Endpoint ที่รองรับ แต่ Service-account และ Federation Endpoints จะรับเฉพาะ org:admin OAuth token เท่านั้น Admin API key จึงถูกปฏิเสธเสมอไม่ว่าผู้สร้างจะมีสิทธิ์สูงแค่ไหนก็ตาม ให้ดู HTTP Status Code เป็นหลัก: 401 คือแก้ที่ Credential, 403 คือแก้ที่ Permission Level

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
Removing an engineer from the organization revokes every API key they created. (ทำไมถึงผิด): Removal archives their personal keys, but a legacy workspace key belongs to the workspace and keeps working until it expires, is disabled or deleted, or the workspace is archived. A 403 from the Admin or Compliance APIs means the key is invalid and should be replaced with a fresh one of the same kind. (ทำไมถึงผิด): A 403 means the key authenticated but lacks the level the endpoint needs. Scopes are fixed at creation, so the fix is a new key carrying the missing scopes, not a re-issue of the same one.

การลบ Engineer ออกจาก Organization จะ Revoke API Key ทั้งหมดที่เขาสร้างขึ้นจริงหรือไม่? (ทำไมถึงผิด): ไม่จริง: การลบผู้ใช้ออกจะ Archive เฉพาะ Personal keys ของเขาเท่านั้น แต่ Legacy workspace key เป็นกรรมสิทธิ์ของ Workspace จึงยังคงทำงานได้ต่อไปจนกว่าจะหมดอายุ, ถูก Disable, ถูกลบ หรือ Workspace ถูก Archive | หากได้ Status 403 จาก Admin หรือ Compliance APIs แสดงว่า Key เสียและควร Re-issue Key แบบเดิมมาเปลี่ยนใหม่จริงหรือไม่? (ทำไมถึงผิด): ไม่จริง: 403 หมายถึง Key ผ่าน Authentication แล้ว แต่ขาด Permission/Scope ที่ Endpoint นั้นต้องการ เนื่องจาก Scope ถูกกำหนดตายตัวตั้งแต่สร้าง Key การแก้ไขจึงต้องสร้าง Key ใหม่ที่กำหนด Scopes ให้ครอบคลุม ไม่ใช่การขอ Re-issue Key สิทธิ์เดิมซ้ำ

Every Claude API request acts as someone, and the type of key decides who. A static API key is an sk-ant-api... secret sent as Authorization: Bearer <key> on each request. When you create one in the Claude Console under Settings → API keys, the Linked account field sets its type. Link it to yourself for a personal key, or to a service account for a key that several people or a workload share. The type decides what the key can reach and when it stops working.

Personal and service account keys are identity-backed. Every request runs with the permissions of a user or service account the organization already manages, so removing that identity cuts off the key too. The legacy workspace key is the exception. It has no owner, so it keeps working after the engineer who created it leaves. That is why a departed colleague's workspace key can still drive a pipeline months later, and it is why new integrations should prefer identity-backed keys.

Choosing between the two identity-backed types depends on who runs the code. Your own scripts and development use a personal key. A personal key shared with a team acts as one person and breaks when that person leaves. CI jobs and production services need their own service account, which an organization admin creates so the workload has its own identity.

Admin API keys are a separate kind of credential, used to manage the organization rather than call models. In the Claude Console only organization members with the admin role can create one, under Settings → Admin keys, and it carries the prefix sk-ant-admin01-.... One Admin API key authenticates the Admin API, the Usage and Cost API, the Rate Limits API and the other Admin-section APIs. A key created in one organization cannot manage a different one.

Authentication is the API establishing who is calling, and the key is the proof. A key travels as a bearer token in the Authorization header; the older x-api-key header is still accepted in its place, and Admin API calls are normally sent that way. A key that is unknown, archived or expired fails at this step with 401 authentication_error. An expired key never comes back, so the fix is a new key. Federated workload identity is the other route to a Claude token, covered in the federation pages of this lesson.

Level verification is the separate check that an authenticated caller is allowed to do this particular thing, and its failure looks different: 403 Forbidden. For a personal key, the level is the owner's organization role. A developer can manage API keys, while managing users takes admin. Claude Enterprise keys carry explicit scopes such as read:members or read:analytics, fixed when the key is created. A call outside them returns a 403 naming the scopes the key has and the scopes the endpoint needs. Widening a key means creating a new one. Console Admin API keys have no selectable scopes and carry full access to every endpoint that accepts them, and the service-account and federation endpoints accept only an org:admin OAuth token, so an Admin API key is refused there however privileged its creator is. Read the status code first: 401 means fix the credential, 403 means fix the level.

Moving an integration off a workspace key follows a fixed sequence. The old key goes last, so traffic never runs without a working credential.

A key's workspace scope decides how much each request has to tell the API. If a key was created for one workspace, it works only there, and its requests can leave out the workspace ID. A key that isn't scoped to a workspace has to name one on every request in the anthropic-workspace-id header. If the header is missing, the API returns 400 invalid_request_error.

The header names a workspace, and the key's identity still has to be allowed in it. A malformed ID gets a 400. A well-formed ID for a workspace the key's user or service account can't access gets 404 not_found_error, the same response as for a workspace that doesn't exist. Because both cases look the same, a 404 here usually points to missing membership, not a typo. Service accounts are implicitly members of the Default Workspace, and every other workspace has to be added to them explicitly.

The Admin API checks scope the other way around. It accepts a personal or service account key only when that key is not scoped to a specific workspace. A single-workspace personal key from an admin's laptop will therefore fail against organization-management endpoints, even though the admin's role would allow the action.

3. Storing, expiring and rotating keys

API Key มักรั่วไหลได้ 2 ทางหลัก: เผลอ Commit key แบบ Plaintext ขึ้น Public Repository หรือนำ Key ไปวางใน Third-party tools โดย Service ใดก็ตามที่ได้รับ Key ไปจะสามารถเรียกใช้งานและตัดเงินจากบัญชีของคุณได้ทันที การอัปโหลด Key ไปยัง Web IDE, Cloud Provider หรือ CI/CD Platform จะทำให้ทีมผู้พัฒนา Tool นั้นเข้าถึง Claude Console Account ของคุณได้ จึงต้องเก็บเป็น Encrypted Secret เท่านั้น ห้ามใส่ใน Code หรือ Config Files เด็ดขาด และสมาชิกในทีมแต่ละคนควรมี Key แยกเป็นของตนเอง ไม่ควรใช้ร่วมกัน

สถานที่จัดเก็บ Key ขึ้นอยู่กับ Environment ที่ Code รัน: สำหรับ Local Development บน Laptop สามารถใช้ไฟล์.env ร่วมกับ python-dotenv ได้ โดยต้องระบุไฟล์ไว้ใน.gitignore เสมอ ส่วนบน Cloud แนะนำให้ใช้ Secret Manager แทนไฟล์.env เพื่อ Inject Key เข้าสู่ Environment Variable ANTHROPIC_API_KEY ซึ่ง SDK จะอ่านค่าให้อัตโนมัติ หากระบบมี Key จำนวนมาก ควรใช้ Key Management System (KMS) เพื่อรวมศูนย์การจัดเก็บแบบเข้ารหัส มี Fine-grained Access Control, มี Audit Trails และจัดการ Rotation ได้ง่ายขึ้น

Expiration ถูกกำหนดได้เพียงครั้งเดียวตอนสร้าง Key โดย Console มี Preset ให้เลือกคือ 3 hours, 1 day, 7 days, 30 days, Custom Duration หรือเลือก Never สำหรับ Key ที่เก็บใน Secret Manager และจัดการ Rotate เอง นอกจากนี้ Organization ยังสามารถตั้ง Maximum Expiration Policy เพื่อจำกัดตัวเลือกและตัดตัวเลือก Never ออกได้ เมื่อสร้าง Key แล้วจะไม่สามารถเปลี่ยน Expiration ได้อีก

ทั้งนี้ Anthropic จะส่งอีเมลแจ้งเตือนล่วงหน้าก่อนหมดอายุ (แจ้งเตือนล่วงหน้า 7 วันสำหรับ Key ที่มีอายุตั้งแต่ 14 วันขึ้นไป และล่วงหน้า 1 วันสำหรับ Key ที่มีอายุตั้งแต่ 7 วันขึ้นไป) เมื่อ Key หมดอายุ Request จะได้รับ 401 authentication_error ทันที และแก้ไขได้ด้วยการสร้าง Key ใหม่เท่านั้น

Rotation คือการสร้าง Key ใหม่ขึ้นมาก่อนที่จะปลดระวาง Key เดิม โดยทำตามรอบเวลาที่กำหนด เช่น ทุกๆ 90 วัน การตั้ง Expiration ช่วยจำกัดกรอบเวลาที่ Leaked Key จะถูกนำไปใช้ประโยชน์ได้ แต่ไม่สามารถทดแทนการดูแล Secret Hygiene ที่ถูกต้องได้

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
An expired key can be reactivated, or have its expiration extended, from the Console. (ทำไมถึงผิด): Expiration is fixed when the key is created. An expired key returns 401 and can't be reactivated, so you have to create a new key.

Key ที่หมดอายุแล้วสามารถเปิดใช้งานใหม่ (Reactivate) หรือขยายเวลา Expiration จาก Console ได้? (ทำไมถึงผิด): ไม่จริง: Expiration จะถูก Fix ทันทีตั้งแต่ตอนสร้าง Key เมื่อหมดอายุแล้วจะ Return 401 authentication_error และไม่สามารถ Reactivate หรือขยายเวลาได้ ต้องสร้าง Key ใหม่เท่านั้น

คำแปลไทย:
การหมดอายุได้รับการแก้ไขเมื่อสร้าง การมีอายุใช้งานที่แตกต่างหมายถึงการสร้างคีย์ใหม่และหมุนเวียนไป

คำแปล: การหมดอายุถูกตั้งค่าในเวลาการสร้างและไม่สามารถเปลี่ยนแปลงได้หลังจากนั้น

คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Leaks most often happen in two ways: a plaintext key committed to a public repository, or a key pasted into a third-party tool. Anything you give a key to can spend from your account. Uploading a key to a web IDE, cloud provider or CI/CD platform gives that tool's developer access to your Claude Console account, so add it only as an encrypted secret and never in code or config files. Each person who needs API access should get their own key rather than borrow yours.

Where you store a key depends on where the code runs. On a laptop, a.env file loaded with python-dotenv is fine, provided the file is listed in.gitignore. In the cloud, use encrypted secret storage instead of dotenv files: the platform's secret manager injects the key as ANTHROPIC_API_KEY, which the SDK reads automatically. As the number of keys grows, a key management system gives you one encrypted store with fine-grained access control, audit trails and easier rotation.

Expiration is set once, when the key is created. The Console offers presets of 3 hours, 1 day, 7 days or 30 days, a custom duration, or Never for keys you keep in a secrets manager and rotate yourself. An organization can set a maximum expiration policy, which caps the choices and removes Never. Once created, a key's expiration can't be changed. Anthropic emails the creator before expiry: 7 days ahead for keys with a lifetime of at least 14 days, and 1 day ahead for keys with a lifetime of at least 7 days. After expiry, requests return 401 authentication_error, and the only fix is a new key.

Rotation means creating the new key before retiring the old one, on a regular schedule such as every 90 days. Expiration limits how long a leaked key stays usable. It is not a substitute for good secret hygiene.

4. Detecting a leak, shutting it down and watching usage

Secret Scanning ช่วยตรวจจับ Key ก่อนหรือทันทีที่เกิดการรั่วไหล คุณสามารถเปิดใช้งาน Scanning บน Source Control Provider, รัน SAST Tool เช่น Gitleaks ตรวจสอบ Repository และผสานเข้ากับ CI/CD Pipeline เพื่อดักจับ Secret ก่อนถูก Merge เข้าสู่ Main Branch ยิ่งไปกว่านั้น GitHub (Public) ยังมี Safety Net เพิ่มเติมผ่านโครงการ Secret Scanning Partner Program หากตรวจพบ Claude API Key ใน Public Repository ข้อมูลจะถูกส่งตรงไปยัง Anthropic เพื่อ Deactivate Key นั้นโดยอัตโนมัติ พร้อมส่งอีเมลแจ้งเตือนผู้ใช้งานทันที

หากสงสัยว่า Key หลุด ให้ Revoke ทันที แล้วสร้าง Key ใหม่ไปใส่ใน Secret Manager โดยบน Console มี 2 คำสั่งจัดการ ซึ่งมีความแตกต่างเรื่องการย้อนกลับ (Reversible): คำสั่ง Disable สามารถย้อนกลับได้ Key จะมีสถานะเป็น Inactive และสามารถกด Re-enable เพื่อกลับมา Active ใหม่ได้ เหมาะสำหรับกรณีที่ยังไม่แน่ใจ ส่วนคำสั่ง Delete จะมีผลถาวร Key จะถูก Archive และยังแสดงผลใน List API Keys ด้วย status: "archived" สำหรับ Key ที่หมดอายุแล้วจะสามารถกดได้เฉพาะคำสั่ง Delete เท่านั้น

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
Deleting a suspect key is reversible, the same as disabling it. (ทำไมถึงผิด): Disable can be undone with Re-enable. Delete is permanent: the key is archived and only kept on record.

การ Delete Key ที่ต้องสงสัยสามารถย้อนกลับ (Reversible) ได้เหมือนกับการ Disable? (ทำไมถึงผิด): ไม่จริง: เฉพาะคำสั่ง Disable เท่านั้นที่ย้อนกลับได้ด้วยการกด Re-enable ส่วนคำสั่ง Delete มีผลถาวร โดย Key จะถูก Archive ไว้เพื่อเป็นประวัติบันทึกเท่านั้น ไม่สามารถนำกลับมาใช้งานได้อีก

Spend Controls ช่วยจำกัดความเสียหายด้านค่าใช้จ่ายก่อนที่จะมีคนสังเกตเห็นเมื่อ Key หลุด (อ่านรายละเอียดเรื่อง Limits เพิ่มเติมได้ที่ [Rate limits, spend limits and service tiers](lesson:2.1)) สำหรับกรณี Leaked Key ให้โฟกัสที่การตั้งค่าเหล่านี้: สำหรับ Custom Rate Limit Organizations ควรกำหนด Usage และ Spend Limits ให้ชัดเจน ส่วน Standard Rate Limit Organizations ควรตั้งค่า Auto-reload Threshold อย่างรัดกุม เพราะทุกครั้งที่มีการ Reload เติมเงินอัตโนมัติ จะกลายเป็น Credit เพิ่มเติมที่ Attacker สามารถนำไปผลาญได้

Monitoring เป็นวิธีแยกแยะการใช้งานที่ได้รับอนุญาตออกจากการบุกรุก ตรวจสอบ Logs และรูปแบบ Usage ของแต่ละ Key ใน Console อยู่เสมอ ควรแยก Key ออกจากกันตาม Environment เช่น Development, Testing และ Production เพื่อให้ Usage สัมพันธ์กับจุดประสงค์การใช้งานจริง และหากเกิด Key Compromise ก็ระงับใช้งานเฉพาะ Key นั้นได้ นอกจากนี้ Admin API ยัง Return ค่า expires_at ผ่าน List API Keys และ Retrieve API Key ช่วยให้คุณสามารถ Audit และทำ Rotation ล่วงหน้าก่อน Key หมดอายุได้ รวมถึงการใช้ Identity-backed Keys จะช่วยให้ระบุได้อย่างชัดเจนว่า User หรือ Service Account ใดเป็นผู้เรียกใช้ API ในแต่ละ Request

Secret scanning catches keys before or soon after they leak. You can turn on scanning in your source control provider, run a SAST tool such as Gitleaks over your repositories, and add scanning to CI/CD so a secret is caught before it reaches the main branch. Public GitHub has an extra safety net. Through GitHub's Secret scanning partner program, a Claude API key found in a public repository is reported to Anthropic, which deactivates it automatically and emails the affected user.

If you suspect a key is compromised, revoke it immediately, then create a replacement and store it in a secrets manager. The Console offers two actions, and they differ in whether you can undo them. Disable can be undone: the key reports inactive, and Re-enable makes it active again. That suits a key you aren't yet sure about. Delete is permanent: the key is archived and still shows in List API Keys with status: "archived". An expired key can only be deleted.

Spend controls limit what a leaked key can cost before anyone notices. The broader limits model is covered in [Rate limits, spend limits and service tiers](lesson:2.1). For a leaked key, the relevant settings are these: Custom Rate Limit organizations should set usage and spend limits, and Standard Rate Limit organizations should set the auto-reload threshold with care, because every reload is more credit an attacker can use.

Monitoring is how you tell authorized use from unauthorized use. Review logs and usage patterns for each key in the Console. Use separate keys for development, testing and production, so usage maps to one purpose and a compromise means disabling only that one. The Admin API returns each key's expires_at from List API Keys and Retrieve API Key, so you can audit keys and rotate them ahead of expiry. Identity-backed keys also make it clear which user or service account made each call.
