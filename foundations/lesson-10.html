1. Submitting, polling and fetching a batch

💡 แนวคิดหลักของหัวข้อนี้ (Core Concept)

การโทรด้วยข้อความเป็นคำขอแบบซิงโครนัสทั่วไป:

คุณส่งข้อความแจ้งและรอ การตอบกลับเพียงครั้งเดียว Message Batches API เรียกใช้คำขอ Messages เดียวกันเหล่านั้นแบบอะซิงโครนัสเป็นกลุ่มในราคาครึ่งหนึ่งของราคาปกติ

คุณส่งคำขอได้มากถึง 100,000 คำขอในการโทรครั้งเดียว แทนที่จะรอคำตอบแต่ละครั้ง และรวบรวมคำตอบทั้งหมดในภายหลัง แบทช์ส่วนใหญ่จะเสร็จสิ้นภายในไม่ถึงหนึ่งชั่วโมง

import time

client = anthropic.Anthropic()

MESSAGE_BATCH_ID = "msgbatch_01HkcTjaV5uDC8jWR4ZsDV8d"

message_batch = None
while True:
    message_batch = client.messages.batches.retrieve(MESSAGE_BATCH_ID)
    if message_batch.processing_status == "ended":
        break

    print(f"Batch {MESSAGE_BATCH_ID} is still processing...")
    time.sleep(60)
print(message_batch)

คำแปลไทย: แบทช์เริ่มต้นใน_progress การเปลี่ยนแปลงจะสิ้นสุดเมื่อทุกคำขอเสร็จสิ้น และเมื่อถึงเวลานั้นผลลัพธ์จะพร้อมที่ results_url
“It starts as in_progress, then updates to ended once all the requests in the batch have finished processing, and results are ready.”

🔗 เอกสารอ้างอิงทางการจาก Anthropic
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A Messages call is the ordinary synchronous request: you send a prompt and wait for a single reply. The Message Batches API runs those same Messages requests asynchronously, in bulk, at half the usual price. You send up to 100,000 requests in one call instead of waiting for each reply in turn, and collect all the answers later. Most batches finish in under an hour. The typical uses are offline jobs: large evaluation runs, moderating a backlog of user content, summarizing a dataset, generating product descriptions.

Each request in a batch has two parts. custom_id is your own key for the request: 1 to 64 letters, digits, hyphens or underscores. params holds the usual Messages API parameters, the same ones a single synchronous call takes. Because each request is processed independently, one batch can mix vision, tool use, extended thinking and multi-turn conversations. Creating the batch returns its id and a processing_status of in_progress. You poll with that id until the status changes to ended, then download results from the batch's results_url.

Batches belong to a Workspace. Any key working in that Workspace can list its batches and read their results, and the list endpoint pages through them for you. A pipeline that loses track of a batch id can therefore find it again by listing.

📌
A batch's limits are measured in time and size. It holds at most 100,000 requests or 256 MB, whichever is reached first. Results become available when every request is done or after 24 hours, whichever comes first, and requests not processed within 24 hours expire. When demand is high, processing slows and more requests expire after 24 hours. Results stay downloadable for 29 days. They can be large, so stream them rather than download the whole file in one go. Because batches run with high concurrency, they can go slightly over a Workspace's spend limit.
📌
Nearly any Messages request can go into a batch, server tools included, but three parameters return a validation error. stream: true is rejected because results come back as a file. speed (fast mode) is rejected because it tunes synchronous latency. max_tokens: 0 (cache pre-warming) is rejected because the cache entry would likely expire before a follow-up request ran.
⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Exam Trap: Errored and expired requests in a batch are still charged at the batch rate. (ทำไมถึงผิด): Only succeeded requests are billed. Errored, canceled and expired requests never created a message and cost nothing.

คำอธิบายเจาะลึก: กับดักการสอบ: คำขอที่มีข้อผิดพลาดและหมดอายุในชุดงานจะยังคงเรียกเก็บเงินตามอัตราชุดงาน (ทำไมถึงผิด): จะเรียกเก็บเงินเฉพาะคำขอที่สำเร็จเท่านั้น คำขอที่มีข้อผิดพลาด ยกเลิก และหมดอายุไม่เคยสร้างข้อความและไม่เสียค่าใช้จ่ายใดๆ

💡 Official Explanation (คำอธิบายเฉลย):

“Batch results come back as a single file, not a stream.”
คำแปล: ผลลัพธ์แบบเป็นชุดจะกลับมาเป็นไฟล์เดียว ไม่ใช่สตรีม

Every request in an ended batch has exactly one result, and the batch's request_counts totals them by type. Match each result to its input by custom_id. Only requests that succeeded are billed.

A batch that is still processing can be stopped with the cancel endpoint. Right after the call its processing_status is canceling; keep polling until it reaches ended. A canceled batch may contain partial results for requests that were processed before the cancellation, and the rest come back with the canceled result type.

A batch's limits are measured in time and size. It holds at most 100,000 requests or 256 MB, whichever is reached first. Results become available when every request is done or after 24 hours, whichever comes first, and requests not processed within 24 hours expire. When demand is high, processing slows and more requests expire after 24 hours. Results stay downloadable for 29 days. They can be large, so stream them rather than download the whole file in one go. Because batches run with high concurrency, they can go slightly over a Workspace's spend limit.

Nearly any Messages request can go into a batch, server tools included, but three parameters return a validation error. stream: true is rejected because results come back as a file. speed (fast mode) is rejected because it tunes synchronous latency. max_tokens: 0 (cache pre-warming) is rejected because the cache entry would likely expire before a follow-up request ran.

3. Choosing realtime or batch

💡 แนวคิดหลักของหัวข้อนี้ (Core Concept)

A realtime call is a plain Messages request: synchronous, one reply per request. The rule for choosing between it and a batch comes down to one question: is anyone waiting for the answer? If a user or a downstream step needs the reply in seconds, use a realtime Messages call, streamed when the reply is long. If the work can wait (overnight scoring, a backfill, an evaluation suite), use a batch and pay half. Claude Opus 5.5 costs $4 / $20 per million input/output tokens on realtime calls and $2 / $10 in a batch. Batching also raises throughput, because you are not paying for and pacing thousands of round trips yourself.

Prompt caching reuses a repeated prompt prefix at reduced cost and latency instead of processing it again. A cache entry lasts 5 minutes by default, refreshed each time it is used, unless you choose the 1-hour lifetime. Caching and batching do combine, but the savings are less predictable.
