🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Submitting, polling and fetching a batch" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A Messages call is the ordinary synchronous request: you send a prompt and wait for a single reply. The Message Batches API runs those same Messages requests asynchronously, in bulk, at half the usual price. You send up to 100,000 requests in one call instead of waiting for each reply in turn, and collect all the answers later. Most batches finish in under an hour. The typical uses are offline jobs: large evaluation runs, moderating a backlog of user content, summarizing a dataset, generating product descriptions.

Each request in a batch has two parts. custom_id is your own key for the request: 1 to 64 letters, digits, hyphens or underscores. params holds the usual Messages API parameters, the same ones a single synchronous call takes. Because each request is processed independently, one batch can mix vision, tool use, extended thinking and multi-turn conversations. Creating the batch returns its id and a processing_status of in_progress. You poll with that id until the status changes to ended, then download results from the batch's results_url.

Batches belong to a Workspace. Any key working in that Workspace can list its batches and read their results, and the list endpoint pages through them for you. A pipeline that loses track of a batch id can therefore find it again by listing.

Every request in an ended batch has exactly one result, and the batch's request_counts totals them by type. Match each result to its input by custom_id. Only requests that succeeded are billed.

A batch that is still processing can be stopped with the cancel endpoint. Right after the call its processing_status is canceling; keep polling until it reaches ended. A canceled batch may contain partial results for requests that were processed before the cancellation, and the rest come back with the canceled result type.

A batch's limits are measured in time and size. It holds at most 100,000 requests or 256 MB, whichever is reached first. Results become available when every request is done or after 24 hours, whichever comes first, and requests not processed within 24 hours expire. When demand is high, processing slows and more requests expire after 24 hours. Results stay downloadable for 29 days. They can be large, so stream them rather than download the whole file in one go. Because batches run with high concurrency, they can go slightly over a Workspace's spend limit.

Nearly any Messages request can go into a batch, server tools included, but three parameters return a validation error. stream: true is rejected because results come back as a file. speed (fast mode) is rejected because it tunes synchronous latency. max_tokens: 0 (cache pre-warming) is rejected because the cache entry would likely expire before a follow-up request ran.

⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

Exam trapWhen every request in a batch shares an identical cached system prompt, the batch should hit the cache almost every time.Why is that wrong?Batched requests run concurrently and in any order, so cache hits are best-effort. A 35% hit rate is normal behaviour. The documented way to raise it is to send one priming request with the shared prefix and a 1-hour cache block first, then submit the rest once it completes.

ID: 55442

A document-processing application needs to send up to 550 images in a single Messages API request. Which model configuration choice is required to support that volume?

A Use a model without a 200k-token context window, since only those models allow up to 600 images per API request, compared to a 100-image cap on 200k-context models
B Use any current model, since the per-request image cap is fixed at 600 images across the entire model lineup regardless of context window size
C Split the request across two calls of at most 300 images each, since no single model configuration permits more than 300 images per request
D Enable the Files API beta header, since only file_id-referenced images count toward the higher 600-image limit and base64 images remain capped at 100
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. The documented request limits are 100 images per request for models with a 200k-token context window, versus 600 images per request for other models, so reaching 550 images requires choosing a model outside the 200k-context tier.

ตัวเลือก B: ไม่ถูกต้อง

The cap is not uniform; it explicitly differs between 200k-context models (100) and other models (600), so this overstates the consistency across the lineup.

ตัวเลือก C: ไม่ถูกต้อง

300 is not a documented cap; the actual limits are 100 or 600 depending on the model's context window, so this invented threshold doesn't reflect the real constraint.

ตัวเลือก D: ไม่ถูกต้อง

The Files API changes how image bytes are referenced (by `file_id` instead of resent base64 data) to reduce payload size, but it doesn't change the per-request image count limits, which are tied to context window size, not source type.

A realtime call is a plain Messages request: synchronous, one reply per request. The rule for choosing between it and a batch comes down to one question: is anyone waiting for the answer? If a user or a downstream step needs the reply in seconds, use a realtime Messages call, streamed when the reply is long. If the work can wait (overnight scoring, a backfill, an evaluation suite), use a batch and pay half. Claude Opus 5.5 costs $4 / $20 per million input/output tokens on realtime calls and $2 / $10 in a batch. Batching also raises throughput, because you are not paying for and pacing thousands of round trips yourself.

Prompt caching reuses a repeated prompt prefix at reduced cost and latency instead of processing it again. A cache entry lasts 5 minutes by default, refreshed each time it is used, unless you choose the 1-hour lifetime. Caching and batching do combine, but the savings are less predictable. A cache hit needs an earlier request to have written the entry already. In a batch, requests run concurrently and in any order, so many of them start before any entry exists. Even a batch where every request shares one large system prompt can end up hitting the cache well below 100% of the time.

The documented fix is the 1-hour cache, used with a priming request. Gather the requests that share a prefix, then send a batch containing a single request with that prefix and a 1-hour cache block, which writes the prefix to the cache. As soon as it completes, submit the rest of the requests. You must monitor the job to know when it finishes. This beats the 5-minute cache because batch requests commonly take between 5 minutes and 1 hour.

Image-heavy jobs have one more limit to respect, and it applies per request, whether realtime or batched. The API accepts 100 images per request for models with a 200k-token context window, and 600 per request for all other models. Claude Opus 5.5 has a 1M-token context window, so it falls under the 600 limit, while Claude Haiku 4.5 (200K) falls under 100.
