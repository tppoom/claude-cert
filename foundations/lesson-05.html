🎯 สิ่งที่คุณจะสามารถทำได้หลังจบบทเรียนนี้ (What you will be able to do)

  • ✓แปลงโจทย์ทางธุรกิจเป็นเกณฑ์เลือกโมเดล: Capability, Speed, Cost และ Effort
  • ✓ตัดโมเดลที่ Context Window หรือ Maximum Output ไม่รองรับ Workload ออก

💡 แนวคิดหลักสำคัญ (Key Concept)

Requirements-driven model selection — การเลือกโมเดลเริ่มต้นจากความต้องการของระบบ โดยแปลงโจทย์ทางธุรกิจแต่ละข้อเป็นเกณฑ์ด้าน Capability, Speed, Cost หรือข้อจำกัดด้านขนาด แล้วเลือกโมเดลที่ผ่านทุกเกณฑ์โดยมี Cost ต่อ Completed Task ต่ำที่สุด

📑 หัวข้อในบทเรียนนี้ (In this lesson)

  • ▸2. Context Window และ Maximum Output: ข้อจำกัดแบบ Hard Limits
  • ▸3. เปรียบเทียบ Candidate Models ด้วย Eval ก่อนตัดสินใจเลือก

1. จาก Business Requirements สู่เกณฑ์การเลือกรุ่นโมเดล (Selection Criteria)

Business Requirements มักไม่ได้ถูกระบุมาในรูปแบบพารามิเตอร์ของโมเดล เช่น "Agents ต้องตอบกลับให้ได้ในขณะที่ลูกค้ายังถือสายอยู่" หรือ "งบประมาณฝั่ง Support ต้องไม่บานปลาย" หากจะนำมาใช้ตัดสินใจเลือกโมเดล ต้องแปลงโจทย์เหล่านี้ให้เป็น Functional Requirements ที่วัดผลได้ โดยข้อความแรกจะกลายเป็น Latency Target ส่วนข้อความหลังจะกลายเป็น Cost per Request ตามปริมาณ Request Volume ที่คาดการณ์ไว้ หัวข้อ [Model lineup and choosing a starting model](lesson:5.3) ได้สรุปภาพรวมของโมเดลแต่ละรุ่นไว้แล้ว ในส่วนนี้จะเน้นการแปลง Requirements ให้กลายเป็นเกณฑ์คัดเลือกโมเดลที่เหมาะสม

4 คำถามหลักในการแปลง Requirements เป็นเกณฑ์การคัดเลือก:

  • •
    Capabilities: Task นี้ต้องใช้ฟีเจอร์หรือความสามารถระดับใดบ้าง?
  • •
    Speed: Application ต้องการ Response เร็วแค่ไหน (Latency)?
  • •
    Cost: Budget สำหรับช่วง Development และ Production เป็นเท่าใด?
  • •
    Effort: โมเดลตัวเดิมสามารถรองรับโจทย์ได้หรือไม่ หากปรับระดับ Effort Setting ให้สูงขึ้นหรือต่ำลง?
⚠️
ข้อควรระวัง & จุดสังเกต: อย่ามองข้ามเรื่อง Effort Setting เนื่องจาก Claude หลายโมเดลสามารถใช้ Effort เพื่อปรับ Trade-off ระหว่างระดับความฉลาด กับ Latency และ Cost ได้ ดังนั้น Requirement ที่ดูเหมือนต้องเปลี่ยนรุ่นโมเดล อาจจัดการได้ง่ายๆ เพียงแค่ปรับ Effort ขึ้นหรือลงบนโมเดลตัวเดิมที่ใช้งานอยู่

Effort เป็นการตั้งค่าแบบ Per-request ผ่านพารามิเตอร์ effort บน Messages API (output_config.effort) เพื่อควบคุมจำนวน Tokens ที่ Claude จะใช้ในการตอบ โดยเป็น Trade-off ระหว่างความละเอียดรอบคอบ (Thoroughness) กับ Token Efficiency ซึ่งสามารถเปลี่ยนค่าได้ทันทีใน Request ถัดไป โมเดลที่รองรับได้แก่ Claude Fable 5.1 (Default: high), Opus 5.5 (Default: medium) และ Sonnet 5.5 (Default

: high) ในขณะที่ Claude Haiku 4.5 ไม่รองรับ ทั้งนี้ การเปลี่ยนค่า Effort จะส่งผลให้ Cached Message Prefixes ใช้ต่อไม่ได้ (Cache Invalidation) จึงควรคำนวณ Cost ใหม่อีกครั้งหลังการปรับเปลี่ยน

A requirement says the response is acceptable but too slow and too expensive at production volume. Which change should you try first?

คำแปลโจทย์:
ข้อกำหนดระบุว่าการตอบสนองเป็นที่ยอมรับแต่ช้าเกินไปและแพงเกินไปตามปริมาณการผลิต คุณควรลองการเปลี่ยนแปลงใดก่อน
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Official Explanation (คำอธิบายเฉลย):

Effort trades intelligence for latency and cost within one model. When quality already meets the requirement, lowering effort is often a better lever than switching models.

คำแปลไทย:
Thinking Effort แลกเปลี่ยนความชาญฉลาดกับเวลาแฝงและต้นทุนภายในโมเดลเดียว เมื่อคุณภาพตรงตามข้อกำหนดแล้ว การลดความพยายามมักเป็นแรงผลักดันที่ดีกว่าการเปลี่ยนรุ่น
“Tuning effort is often a better lever than switching models.”
คำแปล: ความพยายามในการปรับแต่งมักเป็นเครื่องมือที่ดีกว่าการเปลี่ยนโมเดล

A data team runs nightly analysis over millions of records. Results are only needed by the next business morning, and minimizing per-token cost is the top infrastructure priority. Which processing approach should the architecture use?

คำแปลโจทย์:
ทีม Data ต้องการรันงานวิเคราะห์ข้อมูลจำนวนหลายล้านระเบียน (records) ทุกคืน โดยผลลัพธ์ต้องการใช้งานในเช้าวันทำการถัดไปเท่านั้น และมีเป้าหมายหลักด้านโครงสร้างพื้นฐานคือการลดต้นทุนต่อโทเคน (per-token cost) ให้เหลือน้อยที่สุด สถาปัตยกรรมนี้ควรเลือกใช้แนวทางการประมวลผลแบบใด?
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Option Analysis (คำอธิบายเฉลยรายตัวเลือก):
ตัวเลือก A: ตัวเลือกที่ไม่ถูกต้อง

Synchronous Messages API calls are priced at standard rates and are built for immediate, per-request responses, not for minimizing cost on a large overnight-tolerant workload.

คำแปล:
การเรียกใช้ Synchronous Messages API มีราคามาตรฐานและสร้างขึ้นเพื่อการตอบกลับทันทีต่อคำขอ ไม่ใช่เพื่อลดต้นทุนสำหรับปริมาณงานขนาดใหญ่ที่ยอมรับข้ามคืนได้
ตัวเลือก B: ✓ คำตอบที่ถูกต้อง

The Message Batches API processes large volumes of requests asynchronously at 50% lower cost than standard API calls, matching an overnight, cost-first workload with no immediate latency need.

คำแปล:

A business requirement is rarely written in model terms. "Agents must get an answer while the customer is still on the call" and "the support budget can't grow" are business statements. To use them in a model decision, restate each one as a functional requirement you can measure. The first becomes a latency target. The second becomes a cost per request at the expected volume. [Model lineup and choosing a starting model](lesson:5.3) covers what each model is. This section covers how to turn requirements into the criteria that decide between them.

Four questions turn requirements into criteria.

- Capabilities: which features or capabilities does the task actually need? - Speed: how quickly must the application respond? - Cost: what is the budget for development, and what is it for production? - Effort: can a single model meet the requirement at a lower or higher effort setting?

Don't skip the effort question. On several Claude models, effort trades intelligence for latency and cost, so a requirement that seems to need a different model can often be met by moving effort up or down on the model you already use.

Effort is a per-request setting: the effort parameter on the Messages API (output_config.effort) controls how many tokens Claude spends on a response, trading thoroughness against token efficiency. You change it by sending a different value on the next request. Claude Fable 5.1, Opus 5.5 and Sonnet 5.5 support it, with defaults of high, medium and high; Claude Haiku 4.5 does not. Changing the value invalidates cached message prefixes, so re-measure cost after a change.

If the requirements don't point clearly at either end of the table, start in the middle of the lineup. Most workloads start with Claude Opus 5.5. Start with Haiku 4.5 when the requirements combine high volume, a tight latency budget and cost pressure. Start with Fable 5.1 when the task is demanding reasoning that runs for hours.

Some requirements set a floor that no prompt change can get around. A model's [Context window](lesson:5.1) caps how much input fits in one request, and its maximum output caps how much it can write in one response. Neither limit trades off against cost or speed. If a requirement says "analyse the whole merged document set in one request, without chunking", any model whose window is smaller than that input is out before you look at price.

Because the size limits split the lineup unevenly, they often settle the choice. When an input fits in 1M tokens but not in 200K, there are three candidates, and price and latency decide between them. Output works the same way: a requirement for a single long generated report has to fit inside 64K tokens on Haiku 4.5 or 128K on the others. To check these limits in code rather than from a table, the Models API returns each model's token limits.

After the hard limits, you usually still have more than one candidate. A benchmark built from the functional requirements decides between them. [Eval-driven iteration](lesson:2.2) covers the loop itself. In model selection, the eval's job is to turn each requirement into a test case, including the edge cases the business cares about, and run every remaining candidate against the same set.

Measure cost per completed task, not per-token price. A cheaper model that fails half the tasks, or needs several attempts, can cost more per solved task than a pricier model that gets them right the first time. Price per token belongs in the comparison only after the eval has measured how often each model succeeds.

#2 2. Context Window และ Maximum Output: ข้อจำกัดแบบ Hard Limits

อ่านเนื้อหา ↗
  • •
    Requirements บางอย่างถือเป็นข้อจำกัดขั้นต่ำ (Floor) ที่ไม่สามารถแก้ได้ด้วยการปรับ Prompt โดย [Context window](lesson:5.1) ของโมเดลจะเป็นตัวกำหนดขีดจำกัดสูงสุดของ Input ต่อหนึ่ง Request และ Maximum Output จะกำหนดความยาวสูงสุดที่โมเดลสามารถเขียนตอบได้ในหนึ่งรอบ ซึ่งทั้งสองอย่างนี้เป็น Hard Limits ที่ไม่สามารถ Trade-off ด้วย Cost หรือ Speed ได้ หาก Requirement ระบุว่า "ต้องวิเคราะห์เอกสารชุดใหญ่ที่รวมกันทั้งหมดใน Request เดียว โดยห้ามทำ Chunking" โมเดลใดก็ตามที่มี Context Window เล็กกว่าขนาด Input จะถูกตัดออกทันทีก่อนที่จะพิจารณาเรื่องราคา
  • •
    สามารถตรวจสอบขีดจำกัด Token ของแต่ละโมเดลผ่าน Models API ใน Code ได้โดยตรงแทนการดูจากตาราง
  • •
    หาก Input มีขนาดเกิน 200K แต่ไม่เกิน 1M tokens จะเหลือตัวเลือก 3 รุ่น ซึ่งจะตัดสินกันต่อด้วย Price และ Latency ส่วน Output ก็ใช้หลักการเดียวกัน เช่น หากระบบต้อง Generate รายงานขนาดยาวในรอบเดียว ต้องมั่นใจว่าจะไม่เกิน 64K tokens บน Haiku 4.5 หรือ 128K tokens บนรุ่นอื่นๆ

#3 3. เปรียบเทียบ Candidate Models ด้วย Eval ก่อนตัดสินใจเลือก

อ่านเนื้อหา ↗
  • •
    ให้วัดผลจาก Cost per completed task ไม่ใช่ Per-token price เพราะ Model ที่ถูกกว่าแต่รันพลาดไปครึ่งหนึ่ง หรือต้องยิง Prompt ซ้ำหลายรอบ อาจมีต้นทุนเฉลี่ยต่อ Task ที่สำเร็จสูงกว่า Model ตัวท็อปที่ทำผ่านได้ในรอบเดียว ตัวเลข Price per token จะนำมาใช้เปรียบเทียบได้ก็ต่อเมื่อ Eval วัด Success Rate ของแต่ละ Model ออกมาแล้วเท่านั้น
  • •
    หลังจากกรองด้วย Hard Limits แล้ว มักจะยังเหลือ Model Candidates มากกว่าหนึ่งตัว การตัดสินใจเลือกจะต้องใช้ Benchmark ที่สร้างขึ้นจาก Functional Requirements (อ่านเพิ่มเติมเรื่อง Loop ได้ที่ [Eval-driven iteration](lesson:2.2)) ในขั้นตอน Model Selection หน้าที่ของ Eval คือการแปลงทุก Requirement ให้เป็น Test Case ซึ่งรวมถึง Edge Cases ที่ธุรกิจให้ความสำคัญ แล้วนำ Candidate ทุกตัวมารันเทียบกับ Test Set เดียวกันนี้
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (3 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
หากมี Input ขนาดใหญ่มากใน Request เดียว ต้องใช้เฉพาะโมเดลตัวท็อปที่มี Capability สูงสุดเท่านั้นใช่หรือไม่?
For a very large single-request input, only the most capable model will do.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Fable 5.1, Opus 5.5 และ Sonnet 5.5 ล้วนรองรับ Context Window ขนาด 1M tokens เท่ากัน มีเพียง Haiku 4.5 (200K tokens) เท่านั้นที่ไม่รองรับ
Fable 5.1, Opus 5.5 and Sonnet 5.5 all have a 1M-token window. Only Haiku 4.5, at 200K, is ruled out.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Model ที่คิดราคา Per-token ถูกที่สุด คือตัวเลือกที่ประหยัดที่สุด?
The model with the lowest per-token price is the cheapest choice.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: ควบคุมและเปรียบเทียบจาก Cost per completed task เท่านั้น เพราะ Model ที่ราคาต่อ Token ถูกกว่า แต่อัตรา Failed สูงหรือต้อง Retry ซ้ำๆ จะทำให้ต้นทุนรวมต่อ Task ที่สำเร็จจริงแพงกว่า
Compare models on cost per completed task. Failed or repeated attempts can make a cheaper-per-token model more expensive overall.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
ถ้าเจอโจทย์ถามวิธีเลือก Model ควรตอบอย่างไร?
On the Exam:: When a scenario asks how to choose between models, look for the answer that builds an evaluation set from the real prompts and data. Comparing list prices alone is the distractor.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: การเทียบแค่ List prices เพียงอย่างเดียวคือตัวลวง ช้อยส์ที่ถูกต้องคือการสร้าง Evaluation set จาก Prompts และ Data ที่ใช้งานจริงมาทดสอบ
🎯 ทักษะที่ข้อสอบประเมินในบทนี้ (Exam Competency Checklist) 3 วัตถุประสงค์
  • ✓แปลงโจทย์ทางธุรกิจเป็นเกณฑ์เลือกโมเดล: Capability, Speed, Cost และ Effort
  • ✓ตัดโมเดลที่ Context Window หรือ Maximum Output ไม่รองรับ Workload ออก
  • ✓ประเมินและเปรียบเทียบโมเดลด้วย Eval จาก Functional Requirements เพื่อหา Cost ต่อ Completed Task ที่คุ้มค่าที่สุด
