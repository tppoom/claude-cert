Guardrail Layering (Defense in Depth) — ไม่มีระบบควบคุมเดี่ยวใดป้องกันการ Misuse ได้ทั้งหมด การ Deploy ที่ปลอดภัยต้องซ้อนทับ Layer อิสระร่วมกัน: คัดกรอง Input, Hardened System Prompt, จัดการ Untrusted Content เชิงโครงสร้าง, คัดกรอง Tool Output, จำกัด Privileges ให้แคบที่สุด และทำ Monitoring เพื่อให้ Layer ถัดไปสามารถดักจับการโจมตีได้เมื่อ Layer ก่อนหน้าหลุดรอด

1. ทำไม Guardrails ต้องมีหลาย Layer: Threat Models 2 รูปแบบ

แม้ Claude จะมีภูมิคุ้มกันต่อการถูกล่อลวงให้ละเมิด Guidelines ในตัวอยู่แล้ว แต่แอปพลิเคชันที่นำไป Deploy จำเป็นต้องมี Guardrails ของตัวเองเพิ่มเติม เพื่อควบคุมไม่ให้เกิดการใช้งานที่ขัดต่อ Terms of Service หรือ Usage Policy ของ Anthropic ซึ่งเป็น Content Policy ที่ระบบของคุณต้องบังคับใช้

การเลือกใช้กลไกควบคุมขึ้นอยู่กับว่าใครคือผู้โจมตี โดยแบ่ง Threat Models ออกเป็น 2 รูปแบบหลัก: รูปแบบแรก ผู้ใช้งานหน้าแอปพลิเคชันคือผู้โจมตีโดยตรง พยายามเขียน Jailbreak หรือทำ Direct Prompt Injection เพื่อเลี่ยงกฎ รูปแบบที่สอง ผู้ใช้งานเป็นฝั่งที่เชื่อถือได้ (Trusted User) แต่ Claude ต้องไปอ่านเนื้อหาจากภายนอกแทนผู้ใช้ ซึ่งเนื้อหานั้นแฝงคำสั่งโจมตีไว้ การคัดกรองแค่หน้า Chat Box ไม่สามารถป้องกันเว็บเพจที่มีเนื้อหาเป็นพิษได้ และการ Escaping ผลลัพธ์จาก Tool ก็กันผู้ใช้ที่จงใจโจมตีไม่ได้เช่นกัน ระบบ Production จึงต้องมี Guardrails ทั้งสองด้านซ้อนทับกันเป็น Layer

Anthropic says Claude is already resilient to attempts to make it ignore its guidelines. Even so, an application you deploy needs guardrails of its own. Anthropic's guidance aims these guardrails especially at uses that break its Terms of Service or Usage Policy. That is the content policy your deployment has to enforce.

The controls you choose depend on who the adversary is, and the documentation names two different threat models. In the first, the person typing into your app is the attacker. They write jailbreaks or direct prompt injections to get around your rules. In the second, the user is trusted, but Claude reads content from someone else on that user's behalf, and that content carries the hostile instructions. A screen on the chat box does nothing against a poisoned web page. Escaping a tool result does nothing against an abusive user. So a real deployment needs controls for both, layered on top of each other.

2. การบังคับใช้ Content Policy บน User Input

ในกรณีที่ผู้ใช้คือผู้โจมตี มีกลไกควบคุม 4 ระดับที่นำมาใช้ร่วมกันได้:

Harmlessness Screens: ก่อนส่ง Input ไปยัง Main Conversation ให้ส่งไปคัดกรองด้วย Lightweight Model อย่าง Claude Haiku 4.5 เสียก่อน โดยใช้ Structured Outputs เพื่อรับค่าที่ประมวลผลต่อได้ทันที เช่น `is_harmful: true/false` สำหรับนำไปทำ Branching Logic ในโค้ด

Input Validation: กรอง Input เพื่อตรวจหา Injection Patterns ที่พบบ่อย หรือสร้าง LLM Screening กว้างๆ โดยป้อนตัวอย่างข้อความ Jailbreak ให้โมเดลเรียนรู้

Prompt Engineering: ฝัง Content Policy ลงใน System Prompt ระบุค่านิยมและกฎเกณฑ์ที่ Assistant ต้องยึดถืออย่างชัดเจน เช่น Integrity, Compliance, Privacy และการเคารพทรัพย์สินทางปัญญา พร้อมทั้งกำหนดข้อความปฏิเสธ (Refusal Words) ที่แน่นอนให้โมเดลใช้ตอบกลับเมื่อเกิดการละเมิด

Respond to Repeat Offenders: หากตรวจพบว่าผู้ใช้รายเดิมพยายาม Trigger ให้เกิด Refusal ซ้ำๆ ให้แจ้งเตือนว่ากำลังละเมิด Usage Policies และพิจารณาใช้มาตรการ Throttling (จำกัดอัตราการเรียกใช้) หรือระงับการใช้งาน (Ban)

If the user is the adversary, the documentation gives four complementary controls.

Harmlessness screens. Before input reaches the main conversation, send it to a lightweight model such as Claude Haiku 4.5 for classification. Use structured outputs so the answer is one machine-readable value, for example is_harmful: true/false, that your code can branch on.

Input validation. Filter input for known injection patterns. You can also build a more general LLM screen by giving it known jailbreaking language as examples.

Prompt engineering. Write the content policy into the system prompt. State the values or rules the assistant must follow, such as integrity, compliance, privacy and respect for intellectual property, and give it the exact words to use when it refuses.

Respond to repeat offenders. If the same user keeps triggering the same kind of refusal, tell them they are breaking the usage policies. Consider throttling or banning them.

ตัวอย่างระบบระดับ Enterprise ของ Anthropic อย่าง AcmeFinBot (Financial-advisor Bot) ได้นำเลเยอร์เหล่านี้มาผสานร่วมกัน: System Prompt จะกำหนด Regulatory Directives ชัดเจน (Validate คำขอตามกฎเกณฑ์ SEC/FINRA, ปฏิเสธ Insider Trading, ไม่เปิดเผยข้อมูลส่วนบุคคลหรือข้อมูลทางการเงิน), มี harmlessness_screen Tool กรองทุก Query ล่วงหน้า และมี Fixed Refusal Message สำหรับคำขอที่ผิดกฎ โดยแยกเลเยอร์ชัดเจนระหว่าง Content Policy, Input Screening และ Refusal Handling

แนวทางปฏิบัติที่ครอบคลุมตลอด Lifecycle มี 2 ขั้นตอน: ก่อน Deploy ให้ทำ Red-team กับ Agent ของตนเอง โดยป้อนเอกสาร อีเมล และ Tool Outputs ที่จงใจฝัง Injection แล้วทดสอบว่า Claude เพิกเฉยต่อคำสั่งแฝงเหล่านั้น รวมถึงระบบ Screen และขั้นตอน Confirmation สามารถดักจับสิ่งที่หลุดรอดได้จริง และหลัง Deploy ให้คอยมอนิเตอร์และวิเคราะห์ Outputs เพื่อหาร่องรอย Injection ที่อาจสำเร็จ แล้วนำ Feedback มาปรับปรุง Prompts, Data Validation และ Filters อย่างต่อเนื่อง

แนวทางทั้งหมดที่กล่าวมาทำงานผ่าน Model Layer ซึ่งแม้ Prompts และ Classifiers จะช่วยลดความเสี่ยง แต่ไม่ได้รับประกัน 100% Claude Code จึงมี Deterministic Enforcement Layers นอกตัว Model เข้ามาเสริม: PreToolUse Hook สามารถสั่ง Block การเรียก Tool ได้ทันทีก่อนที่คำสั่งจะทำงาน ส่วน PostToolUse Hook ไม่สามารถ Block ได้เพราะ Tool รันเสร็จสิ้นไปแล้ว ขณะที่ Permission Deny Rules ใช้สั่งห้ามเรียกใช้ Tool นั้นๆ อย่างเด็ดขาด และ ConfigChange Hooks ใช้สำหรับ Audit หรือ Block การเปลี่ยนแปลง Settings ระหว่าง Session ยกเว้น policy_settings ที่ระบบไม่อนุญาตให้ Block

Hooks เหล่านี้ไม่ได้จำกัดอยู่แค่ Claude Code CLI แต่ Agent SDK ยังรองรับ Filesystem Hooks เดียวกันจาก settings.json รวมถึงรองรับ Programmatic Hooks ที่ส่ง Callback Functions เข้าไปใน query() ทำให้นักพัฒนาสามารถนำ PreToolUse Check ไปเป็น Gatekeeper ควบคุม Tool Calls ใน Custom Applications ที่สร้างขึ้นเองได้

Identity เป็นอีกหนึ่ง Deterministic Layer สำหรับ Shared Workloads หรือ Automated Workloads เช่น CI/CD และ Production Services ซึ่ง Organization Admin ควรกำหนด Service Account ให้เฉพาะ เพื่อให้ Workload มี Identity เป็นของตัวเอง แทนที่จะแชร์ API Key ของบุคคล และสามารถยกระดับความปลอดภัยด้วย Workload Identity Federation ที่เปลี่ยนจากการใช้ Static Keys มาเป็นการแลก Short-lived Tokens ผ่าน Identity Provider โดย Federation Rule จะเป็นตัวคัดกรอง Identity ที่อนุญาตให้ทำ Authentication จึงควรกำหนดเงื่อนไขให้ Match เฉพาะ Workflow Runs ที่เชื่อถือได้เท่านั้น

Anthropic's enterprise example, a financial-advisor bot called AcmeFinBot, puts the layers together. Its system prompt sets regulatory directives (validate requests against SEC and FINRA guidelines, refuse insider trading, never disclose personal or financial data). It runs every query through a harmlessness_screen tool before processing, and it has a fixed refusal message for non-compliant requests. Content policy, input screening and refusal handling each sit in a separate layer.

Two practices cover the full lifecycle. Before deployment, red-team your own agent: feed it documents, emails and tool outputs that contain injection attempts on purpose, and confirm that Claude ignores them and that your screens and confirmation steps catch whatever gets through. After deployment, keep analyzing outputs for signs of a successful injection, and use what you find to refine prompts, validation and filters.

Everything so far works through the model: prompts and classifiers make bad outcomes less likely but don't make them impossible. Claude Code also offers deterministic layers that run outside the model. A PreToolUse hook can block a tool call before it runs. A PostToolUse hook cannot block anything, because the tool has already run by then. Permission deny rules stop a tool from being used at all, and ConfigChange hooks can audit or block settings changes during a session, except changes to policy_settings, which cannot be blocked.

These hooks are Claude Code features, but they are not limited to the CLI. The Agent SDK runs the same filesystem hooks from settings.json and also accepts programmatic hooks, which are callback functions passed to query(), so a PreToolUse check can gate tool calls in an application you build yourself.

Identity is another deterministic layer. For shared or automated workloads such as CI or production services, an organization admin creates a service account so the workload has its own identity instead of borrowing a person's key. Workload Identity Federation goes further and replaces a static key with a short-lived token exchanged from your identity provider's token. A federation rule decides which identities may authenticate, so it should match only the workflow runs you intend to trust.

    Prompt Engineering: ฝัง Content Policy ลงใน System Prompt ระบุค่านิยมและกฎเกณฑ์ที่ Assistant ต้องยึดถืออย่างชัดเจน เช่น Integrity, Compliance, Privacy และการเคารพทรัพย์สินทางปัญญา พร้อมทั้งกำหนดข้อความปฏิเสธ (Refusal Words) ที่แน่นอนให้โมเดลใช้ตอบกลับเมื่อเกิดการละเมิด

#3 3. การจัดการ Untrusted Content จาก Tools

อ่านเนื้อหา ↗
  • •
    ส่ง Untrusted Content เข้าทาง Tool Results เท่านั้น เพราะ Claude ถูก Train ให้ระแวงและตั้งข้อสงสัยต่อคำสั่งที่พบในจุดนี้ 2. ระบุบริบทและที่มาของ Content อย่างชัดเจน เช่น ใส่ใน Tool Description หรือตัว Result โดยตรง (เช่น "body of an inbound email from an unknown sender") เพื่อช่วยให้ Claude ตัดสินใจได้ว่าควรระวังข้อความที่ดูเหมือนคำสั่งมากน้อยเพียงใด 3. ประกาศ Security Policy ไว้ใน System Prompt โดยกำชับว่า Tool Content ถือเป็น Untrusted Data และห้าม Override คำสั่งหลักโดยเด็ดขาด 4. ทำ JSON-encode กับ Third-party Strings เสมอ การ Escape จะช่วยตีกรอบ Boundary ชัดเจน ป้องกันไม่ให้ Attacker ปิด Quote หรือ Tag เพื่อหลุดออกมาสั่งการใน Instruction Context 5. อย่าใส่ Instructions ของตัวเองลงใน Tool Results เพราะ Claude อาจมองข้ามหรือจัดว่าเป็น Injection ให้ส่งเป็น User Turn ถัดจาก tool_result แทน (หรือใช้ Mid-conversation System Message สำหรับ Models ที่รองรับ) 6. ตรวจกรอง Tool Outputs โดยรัน Raw Output ผ่าน Claude Haiku 4.5 Classifier เพื่อเช็คแฟล็ก injection_suspected หากเป็นจริง ให้ส่ง Error หรือสรุปเนื้อหาแบบ Strip ข้อมูลทิ้ง
  • •
    สำหรับการรับมือ Indirect Injection แนวทางป้องกันหลักคือระดับ Structural: ออกแบบ Architecture ให้ Claude แยกแยะระหว่าง Instructions กับ Data ได้อย่างเด็ดขาด โดยผสานเลเยอร์การป้องกันร่วมกันดังนี้:
  • •
    แทนที่จะส่ง Raw Content พร้อมพิจารณาแจ้งเตือน User

#4 4. การผสานเลเยอร์, การทำ Red-teaming และ Deterministic Enforcement

อ่านเนื้อหา ↗
  • •
    Hooks เหล่านี้ไม่ได้จำกัดอยู่แค่ Claude Code CLI แต่ Agent SDK ยังรองรับ Filesystem Hooks เดียวกันจาก settings.json
  • •
    System Prompt จะกำหนด Regulatory Directives ชัดเจน (Validate คำขอตามกฎเกณฑ์ SEC/FINRA, ปฏิเสธ Insider Trading, ไม่เปิดเผยข้อมูลส่วนบุคคลหรือข้อมูลทางการเงิน), มี harmlessness_screen Tool กรองทุก Query ล่วงหน้า และมี Fixed Refusal Message สำหรับคำขอที่ผิดกฎ โดยแยกเลเยอร์ชัดเจนระหว่าง Content Policy, Input Screening และ Refusal Handling
  • •
    ก่อน Deploy ให้ทำ Red-team กับ Agent ของตนเอง โดยป้อนเอกสาร อีเมล และ Tool Outputs ที่จงใจฝัง Injection แล้วทดสอบว่า Claude เพิกเฉยต่อคำสั่งแฝงเหล่านั้น
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (2 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
Putting your own follow-up instructions inside a tool_result is a convenient way to steer Claude after a tool call.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: การใส่ Follow-up Instructions ของเราเองไว้ใน tool_result เป็นวิธีที่สะดวกในการคุม Control Flow ของ Claude หลังเรียก Tool เสร็จ เพราะ Claude มอง Content ใน Tool Result เป็น Untrusted Data คำสั่งที่ใส่ลงไปจึงอาจถูกเพิกเฉยหรือถูกมองว่าเป็น Injection Attempt ทางที่ถูกต้องคือต้องส่งคำสั่งมาใน User Turn ถัดไป
Claude treats tool-result content as untrusted data, so instructions placed there may be ignored or flagged as an injection. Send them in the user turn that follows.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
A PostToolUse hook can act as a guardrail that stops a dangerous tool call.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: PostToolUse Hook สามารถทำหน้าที่เป็น Guardrail ป้องกันไม่ให้ Tool อันตรายทำงานได้ เพราะ PostToolUse ทำงานหลังจาก Tool รันเสร็จสิ้นไปเรียบร้อยแล้ว จึงไม่สามารถยับยั้งการทำงานได้ หากต้องการป้องกันแบบ Deterministic ต้องใช้ PreToolUse Hook เพื่อสั่ง Block Tool Call ล่วงหน้าก่อนรันเท่านั้น
PostToolUse fires after the tool has already run and cannot block it. Use PreToolUse, which can block the call, for deterministic prevention.
🎯 ทักษะที่ข้อสอบประเมินในบทนี้ (Exam Competency Checklist) 4 วัตถุประสงค์
  • ✓อธิบายเหตุผลที่ User Input และ Third-party Content ต้องใช้ Guardrail แต่ละ Layer แยกจากกัน
  • ✓ประยุกต์ใช้การควบคุมตาม Content Policy: Harmlessness Screening, Input Validation, Value-based System Prompts และการจัดการ Repeat Offenders
  • ✓จัดโครงสร้าง Tool Content ที่ไม่น่าเชื่อถือให้ Claude มองเป็น Data พร้อมคัดกรอง Tool Outputs ก่อนที่ Claude จะนำไปประมวลผลต่อ
  • ✓ผสานแต่ละ Layer เป็น Defense in Depth, ทำ Red Teaming ก่อน Deploy และแยกแยะความแตกต่างระหว่าง Prompted Guardrails กับ Deterministic Guardrails
