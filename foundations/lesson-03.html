กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "How query() runs the agent turn by turn" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The Claude Agent SDK is a Python and TypeScript library that embeds Claude Code's prebuilt agent loop, with its built-in tools, permissions, sessions and hooks, inside an application you operate. You get a working agent without writing the loop yourself, and the rest of this page shows how to steer it.

In the Claude Agent SDK, query() is the agent loop. You pass a prompt and options, and you get back an async stream of messages while the SDK runs the tool-use cycle from [The tool-use (agentic) loop](lesson:8.1) for you. The cycle itself is fixed. You still control which tools run, how far the loop may go, what context it starts with, and how your code reacts to each message.

Here is the sequence:

1. The SDK yields a SystemMessage with subtype init that carries session metadata. 2. Claude evaluates the state and responds with text, tool calls or both. Each content block arrives as its own AssistantMessage. 3. The SDK runs each requested tool and yields a UserMessage with the result. 4. Steps 2 and 3 repeat, and each full cycle counts as one turn. This continues until Claude responds with no tool calls. 5. A final AssistantMessage holds the text answer, followed by a ResultMessage with the result, token usage, cost and session ID.

Which messages you handle depends on what you are building. A batch job only needs the ResultMessage. A progress display reads each AssistantMessage to show which tools Claude called. A live UI turns on partial messages (includePartialMessages in TypeScript) to receive StreamEvent text deltas. In TypeScript, assistant and user messages wrap the raw API message, so content blocks are at message.message.content. Do not stop reading at the ResultMessage: a few system events such as prompt_suggestion can arrive after it.

Tool access is set with three options, which apply in the SDK the rules taught in [Permission rules (allow / ask / deny)](lesson:7.1):

- allowedTools auto-approves the listed tools. Tools that are not listed are still available. Calls to them that need approval fall through to the permission mode and the canUseTool callback. - disallowedTools blocks the listed tools, whatever the other settings say. - permissionMode sets the level of human oversight, using the modes from [Permission modes and auto mode](lesson:3.1). The SDK checks it together with your allow and deny rules in a fixed order.

canUseTool is a callback you supply that is asked to approve or reject a tool call that needs approval and is not already covered by your allow rules. In default mode, a call that needs approval with no callback registered is denied.

settingSources: ["project"] is the main context lever. It loads CLAUDE.md, skills and filesystem hooks from the working directory, so the agent starts out following your project's conventions. effort is a cost lever. Setting it to "low" for agents that only read files or list directories cuts token use. Two options stop a run that goes on too long: maxTurns caps the number of turns and maxBudgetUsd caps spend. An open-ended prompt with neither one set can keep running and spending until the task is done.

The subtype field tells you which limit was hit. Only success includes the result text. A single-shot query() yields the error result and then raises an error such as "Reached maximum number of turns", so put the loop in a try block. Your subtype branches still run before the exception. To continue after error_max_turns, save the session ID and resume that session with a higher limit.

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 55319

An SRE wants an autonomous Claude Code agent to never modify secrets files. Regardless of what the system prompt tells the model, any attempt to write to a file named .env anywhere in the working tree must be rejected before it executes, and the block must hold even if a teammate later runs the same session in bypassPermissions mode. Which implementation satisfies this?

A Add an instruction to the system prompt telling Claude never to write to files named .env, relying on the model to follow that written policy during every session.
B Register a PreToolUse hook matched to Write|Edit that inspects tool_input.file_path and returns permissionDecision "deny" whenever the file name is .env.
C Add "Bash(rm .env)" to disallowed_tools so the agent cannot delete or overwrite the file through that specific shell command invocation.
D Set permission_mode to "plan" so Claude explores the codebase and proposes edits to .env without ever applying any change automatically.
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก B
ตัวเลือก A: ไม่ถูกต้อง

A system-prompt instruction is a guideline the model can deviate from under pressure or a crafted prompt; it is not enforced by the runtime and does not guarantee the block holds in every mode.

ตัวเลือก B: ถูกต้อง

Correct. Hooks run before permission-mode evaluation and a hook's deny decision is enforced regardless of the active permission mode, including bypassPermissions, so a PreToolUse deny on the .env file name blocks the write deterministically.

ตัวเลือก C: ไม่ถูกต้อง

This scoped rule only denies the specific Bash invocation "rm .env"; it does nothing to stop the same file from being overwritten through the Write or Edit tools.

ตัวเลือก D: ไม่ถูกต้อง

Plan mode still routes file-edit attempts to the canUseTool callback for a human decision rather than guaranteeing an outright block, and the restriction disappears once the session leaves plan mode.

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Hooks are your own code that runs at fixed points in the loop, no matter what the model decides. The event list and when each event fires are covered in [Hook events and when they fire](lesson:7.3). Blocking a dangerous command is the best-known use, but in an SDK app hooks also do the routine work that should never depend on the model remembering it.

Common non-guardrail uses include:

- Audit logging: a PostToolUse callback writes every file change to an audit trail. The tool use ID links it to the matching PreToolUse event. - Context injection: UserPromptSubmit adds extra context to each prompt before Claude sees it. - Transcript archiving: PreCompact saves the full conversation before the SDK summarizes older history. The stream then shows a compact_boundary system message once compaction finishes. - Lifecycle tasks: Stop saves session state, and SubagentStop collects results from parallel subagents.

Every callback receives the input data, a tool use ID and a context object. All inputs include session_id, cwd and hook_event_name, and agent_id is filled in when the hook fires inside a subagent. The callback returns a decision. Returning {} lets the action go ahead. The top-level systemMessage field shows the user a message, and continue (continue_ in Python) decides whether the agent keeps running. The two SDKs do not support the same events. SessionStart, SessionEnd and PostCompact exist in TypeScript only, so a Python app has to set up telemetry somewhere else.

ID: 55320

A team wants every Write tool call the agent makes to be transparently redirected into a /sandbox subdirectory, without the model being told about the redirection or being asked to approve each individual write. Which hook return value accomplishes this?

A hookSpecificOutput with permissionDecision "ask" and updatedInput containing the rewritten file_path, so a human reviews the redirected path before it is applied.
B hookSpecificOutput with permissionDecision "allow" and updatedInput containing the file_path rewritten to prepend /sandbox, so the modified input is auto-approved.
C A top-level systemMessage describing the sandbox policy, with hookSpecificOutput left empty so the default permission flow decides whether to apply the rewritten path.
D hookSpecificOutput with permissionDecision "defer" and updatedInput containing the rewritten path, so the query pauses until the session is resumed with the new path.
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก B
ตัวเลือก A: ไม่ถูกต้อง

"ask" still routes the call through canUseTool for human approval, which contradicts the requirement that no per-write approval be requested.

ตัวเลือก B: ถูกต้อง

Correct. updatedInput must be paired with permissionDecision "allow" to auto-approve the modified arguments; this rewrites file_path to the sandboxed path and executes it without prompting or informing the model of the substitution.

ตัวเลือก C: ไม่ถูกต้อง

Leaving hookSpecificOutput empty means the hook has no opinion on the call; the original, unmodified file_path is what proceeds to the rest of the permission flow, not the rewritten one.

ตัวเลือก D: ไม่ถูกต้อง

"defer" ends the query so it can be resumed later; per the documented behavior, updatedInput is ignored when the decision is "defer", so the rewrite would never actually be applied.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

An orchestrator hands focused subtasks to specialised child agents. The reasons for that design are covered in [Orchestrator–subagent hierarchy](lesson:1.1). In the Agent SDK you declare each child in the agents option, keyed by name. Its description tells Claude when to use it, prompt sets its behaviour, tools limits what it can do, and model can override the default model.

The orchestrator starts a subagent by calling the Agent tool. That is why Agent appears in allowedTools above. Older SDK versions called this tool Task, so code that watches the stream should match both names. In the stream, the call shows up as a tool_use block whose input names the subagent_type. Messages produced inside the child carry a parent_tool_use_id.

Subagents also help manage context. A child's isolated work stays out of the main conversation, which keeps the orchestrator's context small on long tasks. To read a child's transcript afterwards, resume the same session, because each query() call starts a new session by default.
