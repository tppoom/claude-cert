1. การทำงานของ query() ในการรัน Agent ทีละ Turn

Claude Agent SDK (รองรับทั้ง Python และ TypeScript) ช่วยฝัง Prebuilt Agent Loop ของ Claude Code ที่มาพร้อม Built-in Tools, Permissions, Sessions และ Hooks เข้ามาใน Application ของคุณโดยตรง ทำให้สร้าง Agent พร้อมใช้งานได้ทันทีโดยไม่ต้องเขียน Loop เอง

ใน SDK ฟังก์ชัน query() ทำหน้าที่เป็น Agent Loop หลัก เพียงส่ง Prompt และ Options เข้าไป คุณจะได้ Async Stream ของ Messages กลับมา ขณะที่ SDK จัดการ Tool-use Cycle ให้เบื้องหลัง แม้ Cycle หลักจะถูกกำหนดไว้แล้ว แต่คุณยังควบคุมได้ว่าจะเปิดใช้ Tools ใด, จำกัดขอบเขตการทำงานของ Loop แค่ไหน, เริ่มต้นด้วย Context ใด และจัดการ Response ในแต่ละ Message อย่างไร

ลำดับการทำงาน (Sequence):

  1. 1
    SDK ส่ง SystemMessage (subtype: init) ที่มี Session Metadata ออกมา
    The SDK yields a SystemMessage with subtype init that carries session metadata.
  2. 2
    Claude ประเมิน State แล้วตอบกลับด้วย Text, Tool Calls หรือทั้งคู่ โดยแต่ละ Content Block จะถูกส่งมาเป็น AssistantMessage แยกกัน
    Claude evaluates the state and responds with text, tool calls or both. Each content block arrives as its own AssistantMessage.
  3. 3
    SDK รัน Tool ที่ถูกเรียก แล้วส่ง UserMessage พร้อมผลลัพธ์กลับไป
    The SDK runs each requested tool and yields a UserMessage with the result.
  4. 4
    ขั้นตอนที่ 2 และ 3 จะวนซ้ำ โดยการครบรอบจะนับเป็น 1 Turn จนกว่า Claude จะตอบกลับโดยไม่มี Tool Calls เพิ่มเติม
    Steps 2 and 3 repeat, and each full cycle counts as one turn. This continues until Claude responds with no tool calls.
  5. 5
    ปิดท้ายด้วย AssistantMessage ที่บรรจุ Text Answer สุดท้าย ตามด้วย ResultMessage ที่ระบุผลลัพธ์, Token Usage, Cost และ Session ID
    A final AssistantMessage holds the text answer, followed by a ResultMessage with the result, token usage, cost and session ID.

การจัดการ Message ขึ้นอยู่กับ Use Case: หากเป็น Batch Job ให้อ่านเฉพาะ ResultMessage, หากต้องการ Progress Display ให้อ่านแต่ละ AssistantMessage เพื่อดูว่าเรียก Tools ใดบ้าง, หรือหากเป็น Live UI ให้เปิด includePartialMessages (TypeScript) เพื่อรับ StreamEvent แบบ Text Deltas ทั้งนี้ใน TypeScript ตัว Assistant และ User Messages จะ Wrap Raw API Message ไว้อีกชั้น Content Blocks จึงอยู่ที่ message.message.content และสำคัญคืออย่าเพิ่งหยุดอ่านที่ ResultMessage เพราะอาจมี System Events อื่นๆ เช่น prompt_suggestion ตามหลังมาได้

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
The stream is finished once the ResultMessage arrives, so you can break out of the loop there. (ทำไมถึงผิด): A few trailing system events can arrive after the ResultMessage, so keep reading until the stream ends.

Stream จะจบลงทันทีที่ ResultMessage ส่งมาถึง จึงสามารถ break ออกจาก Loop ได้เลย? (ทำไมถึงผิด): ไม่จริง: อาจยังมี Trailing System Events (เช่น prompt_suggestion) ถูกส่งตามหลัง ResultMessage มาอีก จึงควรอ่าน Message ต่อเนื่องจนกว่า Stream จะสิ้นสุดจริงๆ

🔗 เอกสารอ้างอิงทางการจาก Anthropic
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The Claude Agent SDK is a Python and TypeScript library that embeds Claude Code's prebuilt agent loop, with its built-in tools, permissions, sessions and hooks, inside an application you operate. You get a working agent without writing the loop yourself, and the rest of this page shows how to steer it.

In the Claude Agent SDK, query() is the agent loop. You pass a prompt and options, and you get back an async stream of messages while the SDK runs the tool-use cycle from [The tool-use (agentic) loop](lesson:8.1) for you. The cycle itself is fixed. You still control which tools run, how far the loop may go, what context it starts with, and how your code reacts to each message.

Here is the sequence:

1. The SDK yields a SystemMessage with subtype init that carries session metadata. 2. Claude evaluates the state and responds with text, tool calls or both. Each content block arrives as its own AssistantMessage. 3. The SDK runs each requested tool and yields a UserMessage with the result. 4. Steps 2 and 3 repeat, and each full cycle counts as one turn. This continues until Claude responds with no tool calls. 5. A final AssistantMessage holds the text answer, followed by a ResultMessage with the result, token usage, cost and session ID.

Which messages you handle depends on what you are building. A batch job only needs the ResultMessage. A progress display reads each AssistantMessage to show which tools Claude called. A live UI turns on partial messages (includePartialMessages in TypeScript) to receive StreamEvent text deltas. In TypeScript, assistant and user messages wrap the raw API message, so content blocks are at message.message.content. Do not stop reading at the ResultMessage: a few system events such as prompt_suggestion can arrive after it.

2. การตั้งค่า Tools, Limits และ Context

การกำหนดสิทธิ์เข้าถึง Tools ใน SDK ทำได้ผ่าน 3 Options หลัก ตามกฎ Permission Rules (allow / ask / deny):

  • •
    allowedTools: ระบุ Tools ที่ต้องการ Auto-approve (Tools อื่นที่ไม่ได้ระบุยังคงเรียกใช้ได้ โดยจะส่งไปตรวจสอบต่อที่ Permission Mode และ canUseTool Callback)
  • •
    disallowedTools: สั่งบล็อก Tools ที่ระบุทันที ไม่ว่าจะตั้งค่าส่วนอื่นไว้อย่างไร
  • •
    permissionMode: กำหนดระดับ Human Oversight โดย SDK จะประเมินร่วมกับ Allow และ Deny Rules ตามลำดับที่กำหนด

canUseTool คือ Callback Function ที่คุณกำหนดเองเพื่อ Approve หรือ Reject Tool Call ที่ต้องขอสิทธิ์และไม่อยู่ใน Allow Rules ทั้งนี้ใน Default Mode หาก Tool Call นั้นต้องขอสิทธิ์แต่ไม่มี Callback ลงทะเบียนไว้ คำขอนั้นจะถูก Denied โดยอัตโนมัติ

A debugging agent with auto-approved tools, project settings and a turn limit typescript
Agent การแก้จุดบกพร่องที่มีเครื่องมือที่ได้รับการอนุมัติโดยอัตโนมัติ การตั้งค่าโครงการ และสคริปต์การพิมพ์ขีดจํากัดการหมุน
for await (const message of query({
    prompt: "Find and fix the bug causing test failures in the auth module",
    options: {
      allowedTools: ["Read", "Edit", "Bash", "Glob", "Grep"], // Listing tools here auto-approves them (no prompting)
      settingSources: ["project"], // Load CLAUDE.md, skills, hooks from current directory
      maxTurns: 30, // Prevent runaway sessions
      effort: "high" // Thorough reasoning for complex debugging

Tool access is set with three options, which apply in the SDK the rules taught in [Permission rules (allow / ask / deny)](lesson:7.1):

- allowedTools auto-approves the listed tools. Tools that are not listed are still available. The SDK checks it together with your allow and deny rules in a fixed order.

canUseTool is a callback you supply that is asked to approve or reject a tool call that needs approval and is not already covered by your allow rules. In default mode, a call that needs approval with no callback registered is denied.

settingSources: ["project"] is the main context lever. An open-ended prompt with neither one set can keep running and spending until the task is done.

A single-shot query() yields the error result and then raises an error such as "Reached maximum number of turns", so put the loop in a try block. Your subtype branches still run before the exception. 3. Hooks ในฐานะ Callbacks สำหรับ Logging, Context และ Lifecycle

Hooks คือโค้ดที่เราเขียนขึ้นเองเพื่อให้ทำงาน ณ จุดที่กำหนดไว้ใน Loop ไม่ว่าโมเดลจะตัดสินใจ

⚠️
ข้อควรระวัง & จุดสังเกต: อย่างไรก็ตาม (ดูรายการ Event และจังหวะการ Trigger ได้ที่ [Hook events and when they fire](lesson:7.3)) แม้เคสยอดนิยมคือการบล็อกคำสั่งอันตราย (Guardrail) แต่ใน SDK App นั้น Hooks ยังใช้จัดการงานประจำที่ต้องทำแน่นอนเสมอ โดยไม่ต้องพึ่งพาให้โมเดลจำเอง

เคสการใช้งานทั่วไปที่ไม่ใช่ Guardrail ได้แก่:

  • •
    Audit logging: ใช้ callback ของ PostToolUse บันทึกทุกการแก้ไขไฟล์ลง Audit Trail โดยมี tool use ID เป็นตัวเชื่อมโยงกับ Event PreToolUse ที่คู่กัน
  • •
    Context injection: ใช้ UserPromptSubmit แทรกลงใน Context เพิ่มเติมให้แต่ละ Prompt ก่อนส่งไปให้ Claude
  • •
    Transcript archiving: ใช้ PreCompact บันทึกประวัติการสนทนาฉบับเต็มไว้ ก่อนที่ SDK จะทำ Compaction ย่อ History ส่วนเก่า โดย Stream จะแสดง System Message ชื่อ compact_boundary เมื่อ Compaction เสร็จสิ้น
  • •
    Lifecycle tasks: ใช้ Stop บันทึก Session State และใช้ SubagentStop รวบรวมผลลัพธ์จาก Subagents ที่รันแบบ Parallel
Registering a callback: event name as key, a list of matchers as value
options = ClaudeAgentOptions(
    hooks={"PreToolUse": [HookMatcher(matcher="Bash", hooks=[my_callback])]}
)

ทุก Callback จะได้รับ Input Data, tool use ID และ Context Object โดย Input ทุกตัวจะมี session_id, cwd และ hook_event_name เสมอ รวมถึงมี agent_id เพิ่มเข้ามา เมื่อ Hook ทำงานภายใน Subagent ตัว Callback จะ Return ผลการตัดสินใจกลับไป (หาก Return {} จะอนุญาตให้ดำเนินการต่อตามปกติ) ฟิลด์ระดับบนสุดอย่าง systemMessage ใช้แสดง Prompt ผู้ใช้ และฟิลด์ continue (หรือ continue_ ใน Python) ใช้กำหนดว่า Agent ควรทำงานต่อหรือไม่ ทั้งนี้ Event ที่รองรับใน 2 SDK แตกต่างกัน โดย SessionStart, SessionEnd และ PostCompact มีเฉพาะใน TypeScript เท่านั้น ดังนั้น Python App จึงต้องจัดการ Telemetry ผ่านช่องทางอื่นแทน

Hooks are your own code that runs at fixed points in the loop, no matter what the model decides. The event list and when each event fires are covered in [Hook events and when they fire](lesson:7.3). Blocking a dangerous command is the best-known use, but in an SDK app hooks also do the routine work that should never depend on the model remembering it.

Common non-guardrail uses include:

- Audit logging: a PostToolUse callback writes every file change to an audit trail. The tool use ID links it to the matching PreToolUse event. - Context injection: UserPromptSubmit adds extra context to each prompt before Claude sees it. - Transcript archiving: PreCompact saves the full conversation before the SDK summarizes older history. The stream then shows a compact_boundary system message once compaction finishes. - Lifecycle tasks: Stop saves session state, and SubagentStop collects results from parallel subagents.

Every callback receives the input data, a tool use ID and a context object. All inputs include session_id, cwd and hook_event_name, and agent_id is filled in when the hook fires inside a subagent. The callback returns a decision. Returning {} lets the action go ahead. The top-level systemMessage field shows the user a message, and continue (continue_ in Python) decides whether the agent keeps running. The two SDKs do not support the same events. SessionStart, SessionEnd and PostCompact exist in TypeScript only, so a Python app has to set up telemetry somewhere else.

4. การประกาศ Subagents ผ่าน agents Option

Orchestrator จะส่งต่องานย่อยที่เฉพาะเจาะจงไปให้ Child Agents ที่เชี่ยวชาญจัดการต่อ (ดูเหตุผลการออกแบบได้ที่ [Orchestrator –subagent hierarchy](lesson:1.1)) ใน Agent SDK เราสามารถประกาศ Child Agent แต่ละตัวไว้ใน agents Option โดยใช้ชื่อเป็น Key ซึ่งฟิลด์ description จะบอก Claude ว่าควรเรียกใช้เมื่อใด, prompt กำหนดพฤติกรรม, tools จำกัดขอบเขตเครื่องมือที่ใช้ได้ และ model สามารถใช้ Override โมเดลเริ่มต้นได้

Orchestrator จะเริ่มการทำงานของ Subagent ด้วยการเรียก Tool ที่ชื่อ Agent (เป็นเหตุผลว่าทำไม Agent ถึงปรากฏอยู่ใน allowedTools) ส่วนใน SDK เวอร์ชันเก่าจะเรียก Tool นี้ว่า Task ดังนั้นโค้ดที่ดักจับ Stream จึงควรเช็คทั้งสองชื่อ ใน Stream การเรียกนี้จะแสดงเป็น tool_use Block ที่ส่งค่า subagent_type มาใน Input และ Message ทั้งหมดที่สร้างขึ้นภายใน Child Agent จะมี parent_tool_use_id แนบมาด้วยเสมอ

Subagents ยังช่วยบริหารจัดการ Context ได้อย่างดี เพราะงานที่รันแบบแยกส่วน (Isolated) ภายใน Child จะไม่ถูกนำมารวมในบทสนทนาหลัก ช่วยรักษา Context ของ Orchestrator ให้มีขนาดเล็กอยู่เสมอแม้งานจะยาวนาน หากต้องการอ่าน Transcript ย้อนหลังของ Child จำเป็นต้อง Resume กลับไปยัง Session เดิมเสมอ เนื่องจากคำสั่ง query() แต่ละครั้งจะสร้าง Session ใหม่เป็นค่าเริ่มต้น

An orchestrator hands focused subtasks to specialised child agents. The reasons for that design are covered in [Orchestrator–subagent hierarchy](lesson:1.1). In the Agent SDK you declare each child in the agents option, keyed by name. Its description tells Claude when to use it, prompt sets its behaviour, tools limits what it can do, and model can override the default model.

The orchestrator starts a subagent by calling the Agent tool. That is why Agent appears in allowedTools above. Older SDK versions called this tool Task, so code that watches the stream should match both names. In the stream, the call shows up as a tool_use block whose input names the subagent_type. Messages produced inside the child carry a parent_tool_use_id.

Subagents also help manage context. A child's isolated work stays out of the main conversation, which keeps the orchestrator's context small on long tasks. To read a child's transcript afterwards, resume the same session, because each query() call starts a new session by default.
