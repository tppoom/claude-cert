1. Workflows และ Agents แตกต่างกันที่ผู้ควบคุม Control Flow

ทุกระบบที่นำ LLM มาใช้งานร่วมกับ Tools ล้วนมีจุดตัดสินใจทางสถาปัตยกรรมร่วมกันหนึ่งข้อ: ใครเป็นคนกำหนดว่าจะทำอะไรต่อไป? Anthropic นิยามระบบเหล่านี้ทั้งหมดว่า Agentic Systems และแบ่งออกเป็น 2 ประเภท ได้แก่ Workflow ที่รัน LLM และ Tools ตาม Code Path ที่กำหนดไว้ล่วงหน้า และ Agent ที่ปล่อยให้ LLM กำหนดกระบวนการและเลือกใช้ Tools ด้วยตัวเอง ทำให้ตัว Model เป็นผู้ควบคุมขั้นตอนการทำงานทั้งหมดจนกว่าภารกิจจะสำเร็จ

ความแตกต่างนี้เห็นได้ชัดจากโค้ด ใน Workflow ลำดับขั้นตอนจะถูกฮาร์ดโค้ดไว้ในโปรแกรม เช่น เรียก Model มาร่างข้อความ, รันตัวตรวจสอบ, แล้วเรียก Model อีกรอบเพื่อแปลภาษา เมื่ออ่านโค้ดคุณจะรู้ทุก Path ที่ระบบสามารถทำงานได้ แต่ใน Agent โค้ดจะรันเป็น Loop และ Model จะเป็นผู้เลือกตัดสินใจเอง ในแต่ละ Turn Claude จะประเมินสถานะปัจจุบันแล้วตัดสินใจว่าจะตอบกลับ, เรียกใช้ Tool หรือทำทั้งสองอย่าง ผลลัพธ์จาก Tool จะถูกส่งกลับไปให้ Model วน Loop ต่อไปเรื่อยๆ จนกว่า Claude จะตอบกลับโดยไม่เรียก Tool ใดๆ เพิ่ม (รายละเอียดการรัน Loop ดูได้ที่ [the Agent SDK query() loop](lesson:1.2)) สิ่งสำคัญคือทั้งจำนวน Turn และลำดับการเรียกใช้งานไม่ได้ถูกกำหนดไว้ในโค้ดของคุณ

ความแตกต่างเพียงข้อนี้ส่งผลต่อทุกมิติ การที่ Workflow มี Path ชัดเจนทำให้คาดเดาและควบคุม Consistency ได้ดี ทดสอบได้ง่าย และรู้ต้นทุนล่วงหน้า ในทางกลับกัน Agent ให้ความยืดหยุ่นสูงสำหรับงานที่ไม่สามารถระบุขั้นตอนล่วงหน้าได้ ตัวอย่างคลาสสิกคืองาน Research เพราะ Search ถัดไปขึ้นอยู่กับผลลัพธ์ของ Search ก่อนหน้า ซึ่ง Pipeline แบบ Linear ทั่วไปไม่สามารถตามสืบข้อมูลที่อยู่นอกเหนือจากที่คาดการณ์ไว้ได้

Every system that puts an LLM to work with tools makes one architectural choice: who decides what happens next. Anthropic groups all of these systems under the name agentic systems and splits them into two kinds. A workflow runs LLMs and tools along code paths you defined in advance. An agent lets the LLM direct its own process and tool use, so the model stays in control of how the task gets done.

You can see the difference in the code. In a workflow, the order of steps is written in your program: call the model to draft, run a check, call it again to translate. If you read the code, you know every path the system can take. In an agent, your code runs a loop and the model makes the choices. On each turn Claude looks at where things stand and decides whether to answer, call a tool, or both. Tool results go back to the model, and the loop continues until Claude replies without asking for a tool. How the Claude Agent SDK runs that loop for you is covered in [the Agent SDK query() loop](lesson:1.2). What matters here is that neither the number of turns nor the order of the calls is in your code.

That one difference drives everything else. Because a workflow has fixed paths, it gives you predictability and consistency: you can test each path and know what it costs. An agent gives you flexibility for tasks whose steps can't be known in advance. Research is the standard example. The next search depends on what the last one found, and a linear, one-shot pipeline can't follow leads it didn't know would appear.

2. เริ่มต้นจากขั้นต่ำสุดของ Autonomy Ladder

กฎการออกแบบที่ดีคือสร้างระบบที่เรียบง่ายที่สุดที่ยังทำงานได้ และเพิ่ม Complexity ต่อเมื่อมี Requirement บังคับเท่านั้น ซึ่งบางครั้งอาจแปลว่าไม่ต้องสร้าง Agentic System เลยก็ได้ สำหรับหลาย Use Case การใช้ Single LLM Call ร่วมกับ Retrieval และ In-Context Examples ก็เพียงพอแล้ว พึงระลึกเสมอว่าระดับ Autonomy ที่เพิ่มขึ้นแต่ละขั้นต้องแลกมาด้วย Latency และ Cost ที่สูงขึ้น เพื่อแลกกับ Task Performance ที่ดีขึ้น จึงควรพิจารณาความคุ้มค่าก่อนขยับขึ้นไปในบันไดขั้นที่สูงกว่า

The design rule is to build the simplest thing that works and add complexity only when a requirement forces it. Sometimes that means building no agentic system at all. For many applications, a single LLM call improved with retrieval and in-context examples is enough. Each added layer of autonomy costs latency and money in return for better task performance, so ask whether that trade is worth it before you climb.

Think of the options as rungs on a ladder. Each rung hands more of the control flow to the model. [The five workflow patterns (prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer)](lesson:1.3) sit between a single call and a fully autonomous agent. Most of them keep the step sequence in your code. Orchestrator-workers is the rung where the model starts choosing the subtasks: they aren't defined in advance but decided by the orchestrator from the specific input.

Swapping a tested workflow for an agent changes more than quality. An agent keeps calling tools until it decides it is done, so you no longer set the turn count, the token bill or the response time in code. A workflow's fixed paths are also what made it easy to test. Frameworks add a separate risk on top: their layers of abstraction can hide the underlying prompts and responses, which makes debugging harder and makes it tempting to add complexity a simpler setup didn't need.

3. Manager/Supervisor Hierarchies: An Orchestrator and its Subagents

โครงสร้างแบบ Manager/Supervisor Hierarchy หรือที่นิยมเรียกว่า Orchestrator–Subagent Pattern คือระบบ Multi-Agent System ที่มี Agent หลักระดับบนสุดตัวเดียว Lead Agent จะทำหน้าที่แบ่งงานใหญ่เป็นงานย่อย สร้างและควบคุม Specialized Subagents สำหรับ Subtask นั้นๆ โดย Agent แต่ละตัวจะแยกเป็น LLM Instance อิสระพร้อม Conversation Context ของตนเอง และใช้ Code ในการ Coordinate ระหว่างกัน รูปแบบนี้ถือเป็นจุดเริ่มต้นที่นิยมที่สุด เพราะมี Coordination Model ที่เรียบง่ายที่สุดในบรรดา Multi-Agent Patterns

หัวใจสำคัญเชิงโครงสร้างคือ "สิ่งที่ถูกส่งกลับขึ้นไปใน Hierarchy" โดย Subagent จะรันอยู่ใน Conversation ของตัวเอง Intermediate Tool Calls และผลลัพธ์ระหว่างทางทั้งหมดจะอยู่ภายใน Context นั้น และส่งเฉพาะข้อความสุดท้ายกลับไปยัง Parent Agent เท่านั้น ตัวอย่างเช่น Subagent ที่อ่านไฟล์เป็นสิบๆ ไฟล์จะส่งกลับแค่บทสรุปสั้นๆ ไม่ใช่ตัวไฟล์ทั้งหมด ส่งผลให้ Orchestrator ทำงานบนมุมมองที่ถูกบีบอัด (Compressed View) ของแต่ละ Subtask

The orchestrator's three jobs in code: break the query into parts, run a subagent for each part concurrently, combine the results
async def research_topic(query: str) -> dict:
    # Lead agent breaks query into research facets
    facets = await lead_agent.decompose_query(query)

    # Spawn subagents to research each facet in parallel
    tasks = [
        research_subagent(facet)
        for facet in facets
    ]
    results = await asyncio.gather(*tasks)

    # Lead agent synthesizes findings
    return await lead_agent.synthesize(results)

A manager/supervisor hierarchy, usually called the orchestrator–subagent pattern, is a multi-agent system with a single top agent. A lead agent breaks the task into parts, starts specialized subagents for specific subtasks, and manages them. Each agent is a separate LLM instance with its own conversation context, and code coordinates them. Among the multi-agent coordination patterns, this one has the simplest coordination model, so it is the usual starting point.

The key structural fact is what goes up the hierarchy. A subagent runs in its own conversation. Its intermediate tool calls and results stay inside that conversation, and only its final message returns to the parent. A subagent that reads dozens of files sends back a short summary, not the files. The orchestrator therefore works from a compressed view of each subtask.

Anthropic's Research feature is a production example of this structure. A LeadResearcher plans the approach and saves the plan to memory, because anything past 200,000 tokens of context gets truncated. It then creates subagents with specific research tasks. Each subagent searches on its own and returns findings. The lead combines them and decides whether more research is needed. When it has enough, a separate CitationAgent attributes the claims to sources. With Claude Opus 4 as lead and Claude Sonnet 4 subagents, this setup outperformed single-agent Claude Opus 4 by 90.2% on an internal research eval.

Two structural choices shape how well a hierarchy performs. First, the Research lead runs subagents synchronously: it waits for each batch to finish before it continues. That keeps coordination simple, but one slow subagent can hold up the whole system. Second, passing every output back through the lead turns into a game of telephone. Subagents can instead write their work to external storage and return only a lightweight reference, which keeps detail intact and avoids copying large outputs through the conversation.

ถูกต้อง -- การแบ่งส่วนจะแบ่งงานออกเป็นงานย่อยอิสระที่ทำงานคู่ขนานกับอินพุตเดียวกัน โดยจะรวบรวมผลลัพธ์ในภายหลัง โดยจับคู่บทวิจารณ์ 3 รายการที่มีจุดมุ่งหมายต่างกันไปพร้อมๆ กัน
ตัวเลือก B: ตัวเลือกที่ไม่ถูกต้อง

Incorrect -- voting runs the identical task multiple times for diverse outputs on the same question; here the three prompts each examine a different aspect, not the same question repeated.

คำแปล:
ไม่ถูกต้อง -- การลงคะแนนจะดำเนินการงานที่เหมือนกันหลายครั้งเพื่อให้ได้ผลลัพธ์ที่หลากหลายในคำถามเดียวกัน ที่นี่ทั้งสามแจ้งให้แต่ละฝ่ายตรวจสอบแง่มุมที่แตกต่างกัน ไม่ใช่คำถามเดิมซ้ำ

Incorrect -- evaluator-optimizer requires an iterative critique loop between two LLMs, but these three reviews run independently and simultaneously with no feedback loop between them.

คำแปล:

ตัวเลือก D: ตัวเลือกที่ไม่ถูกต้อง

Incorrect -- the three review categories are fixed and predetermined, not dynamically chosen at runtime by a central orchestrating LLM.

Subagents improve a task in three situations. Outside them, coordination usually costs more than it returns. Teams have spent months building multi-agent systems only to find that better prompting on a single agent got the same results. A single agent with good tools can do more than most developers expect.

Context isolation pays off most when a subtask produces a lot of output (more than 1000 tokens) and most of it doesn't matter to the main task. Lookups and retrieval that need filtering before use are typical examples. Specialization also works as a safety measure. In the Agent SDK, each subagent can have its own system prompt and a restricted tool list, so a reviewer given only read tools can analyze files but can't change them.

The cost is mainly tokens. For the same task, multi-agent systems typically use 3 to 10 times more tokens than a single agent. The extra comes from duplicating context in each agent, messages between agents, and summaries written for each handoff. Parallel subagents do finish in the time of the slowest one rather than the sum of all of them, but that only speeds up the multi-agent work itself. The real gain from parallelism is thoroughness, not speed. The money is worth spending only when the task is valuable enough to pay for the better result.

Some tasks resist this split. Work where every agent needs the same context, or where agents depend heavily on each other, is a poor fit, and most coding tasks have fewer truly parallel pieces than research does. Coordination also brings its own failures. Early versions of the Research system started 50 subagents for simple queries, and teams that split planning, execution and review into separate agents lost context at every handoff and spent more tokens coordinating than executing. Each extra agent is one more point of failure and one more prompt to maintain.

#1 1. Workflows และ Agents แตกต่างกันที่ผู้ควบคุม Control Flow

อ่านเนื้อหา ↗
  • •
    ใครเป็นคนกำหนดว่าจะทำอะไรต่อไป? Anthropic นิยามระบบเหล่านี้ทั้งหมดว่า Agentic Systems และแบ่งออกเป็น 2 ประเภท ได้แก่ Workflow ที่รัน LLM และ Tools ตาม Code Path ที่กำหนดไว้ล่วงหน้า และ Agent ที่ปล่อยให้ LLM กำหนดกระบวนการและเลือกใช้ Tools ด้วยตัวเอง ทำให้ตัว Model เป็นผู้ควบคุมขั้นตอนการทำงานทั้งหมดจนกว่าภารกิจจะสำเร็จ
  • •
    ความแตกต่างนี้เห็นได้ชัดจากโค้ด ใน Workflow ลำดับขั้นตอนจะถูกฮาร์ดโค้ดไว้ในโปรแกรม เช่น เรียก Model มาร่างข้อความ, รันตัวตรวจสอบ, แล้วเรียก Model อีกรอบเพื่อแปลภาษา เมื่ออ่านโค้ดคุณจะรู้ทุก Path ที่ระบบสามารถทำงานได้ แต่ใน Agent โค้ดจะรันเป็น Loop และ Model จะเป็นผู้เลือกตัดสินใจเอง ในแต่ละ Turn Claude จะประเมินสถานะปัจจุบันแล้วตัดสินใจว่าจะตอบกลับ, เรียกใช้ Tool หรือทำทั้งสองอย่าง ผลลัพธ์จาก Tool จะถูกส่งกลับไปให้ Model วน Loop ต่อไปเรื่อยๆ จนกว่า Claude จะตอบกลับโดยไม่เรียก Tool ใดๆ เพิ่ม (รายละเอียดการรัน Loop ดูได้ที่ [the Agent SDK query() loop](lesson:1.2)) สิ่งสำคัญคือทั้งจำนวน Turn และลำดับการเรียกใช้งานไม่ได้ถูกกำหนดไว้ในโค้ดของคุณ
  • •
    ทุกระบบที่นำ LLM มาใช้งานร่วมกับ Tools ล้วนมีจุดตัดสินใจทางสถาปัตยกรรมร่วมกันหนึ่งข้อ

#2 2. เริ่มต้นจากขั้นต่ำสุดของ Autonomy Ladder

อ่านเนื้อหา ↗
  • •
    เปรียบตัวเลือกต่างๆ เป็นขั้นบันได (Autonomy Ladder) แต่ละขั้นจะส่งมอบ Control Flow ให้กับ Model มากขึ้นเรื่อยๆ โดยมี [Workflow Patterns ทั้ง 5 แบบ (Prompt Chaining, Routing, Parallelization, Orchestrator-Workers, Evaluator-Optimizer)](lesson:1.3) คั่นอยู่ระหว่าง Single Call กับ Fully Autonomous Agent ซึ่งส่วนใหญ่ยังคงลำดับขั้นตอนไว้ในโค้ด ยกเว้น Orchestrator-Workers ที่ Model เริ่มเข้ามามีบทบาทในการกำหนด Subtasks เองแบบ Dynamic ตาม Input ที่ได้รับ โดยไม่ได้ถูกกำหนดไว้ล่วงหน้า
  • •
    กฎการออกแบบที่ดีคือสร้างระบบที่เรียบง่ายที่สุดที่ยังทำงานได้ และเพิ่ม Complexity ต่อเมื่อมี Requirement บังคับเท่านั้น ซึ่งบางครั้งอาจแปลว่าไม่ต้องสร้าง Agentic System เลยก็ได้ สำหรับหลาย Use Case การใช้ Single LLM Call ร่วมกับ Retrieval และ In-Context Examples ก็เพียงพอแล้ว พึงระลึกเสมอว่าระดับ Autonomy ที่เพิ่มขึ้นแต่ละขั้นต้องแลกมาด้วย Latency และ Cost ที่สูงขึ้น เพื่อแลกกับ Task Performance ที่ดีขึ้น จึงควรพิจารณาความคุ้มค่าก่อนขยับขึ้นไปในบันไดขั้นที่สูงกว่า
  • •
    การเปลี่ยนจาก Workflow ที่ผ่านการเทสต์มาอย่างดีไปเป็น Agent ส่งผลมากกว่าเรื่อง Quality เพราะ Agent จะเรียก Tools ไปเรื่อยๆ จนกว่ามันจะตัดสินใจว่างานเสร็จสิ้น คุณจึงไม่สามารถคุมจำนวน Turn, ค่า Token หรือ Response Time ผ่านโค้ดได้อีกต่อไป

#3 3. Manager/Supervisor Hierarchies: An Orchestrator and its Subagents

อ่านเนื้อหา ↗
  • •
    ฟีเจอร์ Research ของ Anthropic คือตัวอย่าง Production ของโครงสร้างนี้ LeadResearcher จะวางแผนและบันทึก Plan ลง Memory (เพื่อแก้ปัญหา Context ถูกตัดทอนหากเกิน 200,000 Tokens) จากนั้นจะสร้าง Subagents เพื่อทำงาน Research เฉพาะด้าน โดย Subagent แต่ละตัวจะค้นหาข้อมูลอิสระและส่งผลลัพธ์กลับมา Lead Agent จะรวบรวมข้อมูลและประเมินว่าต้องค้นหาเพิ่มหรือไม่ เมื่อข้อมูลเพียงพอ CitationAgent จะทำหน้าที่เชื่อมโยงข้อความกับ Sources ต้นทาง สถาปัตยกรรมนี้ใช้ Claude Opus 4 เป็น Lead และ Claude Sonnet 4 เป็น Subagents ซึ่งทำคะแนนชนะ Single-Agent Claude Opus 4 ได้ถึง 90.2% บน Internal Research Evaluation
  • •
    โครงสร้างแบบ Manager/Supervisor Hierarchy หรือที่นิยมเรียกว่า Orchestrator–Subagent Pattern คือระบบ Multi-Agent System ที่มี Agent หลักระดับบนสุดตัวเดียว Lead Agent จะทำหน้าที่แบ่งงานใหญ่เป็นงานย่อย สร้างและควบคุม Specialized Subagents
  • •
    หัวใจสำคัญเชิงโครงสร้างคือ "สิ่งที่ถูกส่งกลับขึ้นไปใน Hierarchy" โดย Subagent จะรันอยู่ใน Conversation ของตัวเอง Intermediate Tool Calls และผลลัพธ์ระหว่างทางทั้งหมดจะอยู่ภายใน Context นั้น และส่งเฉพาะข้อความสุดท้ายกลับไปยัง Parent Agent เท่านั้น

#4 4. เมื่อใดที่ Subagents ช่วยยกระดับผลลัพธ์ และ Trade-off ที่ต้องจ่าย

อ่านเนื้อหา ↗
  • •
    Specialization ยังช่วยเสริมเรื่อง Safety อีกด้วย โดยใน Agent SDK แต่ละ Subagent สามารถมี System Prompt แยกเฉพาะและจำกัด Toolset ได้ เช่น กำหนดให้ Reviewer Agent ถือเฉพาะ Read-only Tools เพื่อวิเคราะห์ไฟล์ได้แต่ไม่มีสิทธิ์แก้ไข
  • •
    Context Isolation ให้ผลตอบแทนคุ้มค่าที่สุดเมื่องานย่อยสร้าง Output ขนาดใหญ่ (เกิน 1,000 Tokens) ซึ่งเนื้อหาส่วนใหญ่ไม่ได้สำคัญกับงานหลัก ตัวอย่างคลาสสิกคือ Lookups และ Data Retrieval ที่ต้องกรองก่อนใช้งาน
  • •
    Cost หลักที่ต้องจ่ายคือ Token Usage โดยในงานเดียวกัน Multi-Agent System มักใช้ Token มากกว่า Single Agent ถึง 3–10 เท่า ปริมาณที่เพิ่มขึ้นมาจากการทำ Context Duplication ในแต่ละ Agent, ข้อความสื่อสารข้าม Agent และการ Generate Summary

Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Orchestrator-workers ก็แค่ Parallelization ที่เพิ่ม LLM เข้ามาครอบอีกตัว?
Orchestrator-workers is just parallelization with an extra LLM on top.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: แม้หน้าตาจะคล้ายกัน แต่ใน Orchestrator-workers ตัว Model จะเป็นผู้กำหนด Subtasks เองที่ Runtime ตาม Input ส่วน Parallelization นั้น Subtasks ทั้งหมดถูกกำหนดตายตัวไว้ล่วงหน้า Autonomous agent เป็นตัวเลือกที่ดีกว่า Workflow เสมอ? (ทำไมถึงผิด): ไม่จริง: Agentic Systems ต้องแลก Latency และ Cost ที่สูงขึ้นกับ Performance สำหรับงานที่ Requirement ชัดเจนและตายตัว การใช้ Workflow หรือแม้แต่การ Optimize ให้เหลือ Single Call เพียงครั้งเดียว มักเป็นการออกแบบที่มีประสิทธิภาพและเหมาะสมกว่า
The two look alike, but in orchestrator-workers the model decides the subtasks at runtime from the input. In parallelization the subtasks are fixed in advance. An autonomous agent is always the upgrade from a workflow. (ทำไมถึงผิด): Agentic systems trade latency and cost for performance. When the task is well defined, a workflow, or even one optimized call, is often the better design.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Orchestrator มองเห็นทุก Tool Call และไฟล์ทั้งหมดที่ Subagent เปิดทำงาน?
The orchestrator sees every tool call and file a subagent worked through.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Intermediate Work ทั้งหมดของ Subagent จะถูกแยกและกักไว้ใน Conversation Context ของตัวเองเท่านั้น Parent Agent จะได้รับเพียงข้อความสรุปสุดท้าย (Final Message)
A subagent's intermediate work stays in its own conversation. The parent gets only the final message, usually a short summary.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
การกระจายงานให้ Subagents ทำงานแบบ Parallel จะทำให้งานโดยรวมเสร็จเร็วกว่า Single Agent เสมอ?
Splitting work across parallel subagents makes the whole job finish faster than a single agent.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Parallelism มีไว้เพื่อเพิ่ม Coverage (ความครอบคลุมและละเอียดถี่ถ้วน) ระบบ Multi-Agent มีปริมาณ Total Work มากกว่าเดิมมหาศาล ทำให้เวลารวมทั้งหมดมักนานกว่า Single Agent
Parallelism buys coverage. A multi-agent system does so much more total work that it often takes longer overall than a single agent.
