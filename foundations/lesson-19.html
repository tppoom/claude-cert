After a refactor, every follow-up request after a tool call fails with a 400. The message begins messages.1.content.0 and says thinking blocks cannot be modified. Where is the fault?

คำแปลโจทย์:
หลังจากการรีแฟคเตอร์ ทุกคำขอติดตามผลหลังจากการเรียกใช้เครื่องมือจะล้มเหลวด้วยค่า 400 ข้อความเริ่มต้นข้อความ 1.content.0 และแจ้งว่าบล็อกการคิดไม่สามารถแก้ไขได้ ความผิดอยู่ที่ไหน?
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Official Explanation (คำอธิบายเฉลย):

This 400 means your application changed the thinking blocks before sending them back. The fix is to return the whole assistant message unchanged and then add the tool_result.

คำแปลไทย:
400 หมายความว่าแอปพลิเคชันของคุณเปลี่ยนบล็อกการคิดก่อนที่จะส่งคืน การแก้ไขคือการส่งคืน Assistant Message ทั้งหมดโดยไม่เปลี่ยนแปลง จากนั้นเพิ่ม tool_result
“your application is altering the assistant's thinking blocks before sending them back.”
คำแปล: แอปพลิเคชันของคุณกําลังเปลี่ยนแปลงบล็อกการคิดของผู้ช่วยก่อนที่จะส่งคืน

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Debugging a Claude application starts with deciding whether the integration or the model is at fault, and a 400 invalid_request_error settles that early: the request was rejected before the model produced anything, so the bug is in what your code sent. The harder part is finding which part of the request is wrong, and for the message and thinking structures that tool-use loops build, the error text usually says.

In tool-use and thinking flows, the 400 message is specific enough to point you at the code to fix. These are the ones integrations hit most often:

- tool_use ids were found without tool_result blocks immediately after: a tool_use id got no tool_result, or text was placed before the results. Return one tool_result for each tool_use, with the results first. - thinking or redacted_thinking blocks in the latest assistant message cannot be modified: your code edited, reordered or filtered thinking blocks before sending them back. The message starts with the position of the bad block, such as messages.1.content.0. Send the assistant message back unchanged. - This model does not support assistant message prefill: the conversation ends with an assistant message, and this model rejects prefill. End with a user message, and control the output format with structured outputs or system prompt instructions. - A message ending but no web_search tool was provided: a resume request left out a server tool that the previous turn is still waiting on. Keep the same tools array.

Thinking settings fail the same way. If you send a thinking.type the model doesn't accept, such as enabled to a model that no longer supports extended thinking, you get a 400 whose message names the rejected value. So when every call starts failing right after a model upgrade, the cause is usually a request setting that needs updating, not an outage.

2. ติดตาม stop_reason เมื่อไม่มีอะไรขว้าง

💡 แนวคิดหลักของหัวข้อนี้ (Core Concept)
  • ▸
    ความล้มเหลวแบบเงียบนั้นหายากกว่า: HTTP 200 ไม่มีข้อยกเว้น ผลลัพธ์ที่ไม่ถูกต้อง ตรวจสอบการเชื่อมต่อก่อน การตอบสนองแบบสตรีมมิ่งอาจล้มเหลวหลังจากที่ 200 มาถึง
  • ▸
    เนื่องจากเป็นเหตุการณ์ข้อผิดพลาดภายในสตรีมเหตุการณ์ที่เซิร์ฟเวอร์ส่ง ตัวจัดการที่ตรวจสอบสถานะเริ่มต้นเท่านั้นจะบันทึก API Call ที่ล้มเหลวว่าสำเร็จ จากนั้นตรวจสอบการตอบสนองของตัวเอง การตอบสนอง Messages API ที่ประสบความสำเร็จทุกครั้งจะมี [stop_reason](บทเรียน
  • ▸
    : 6.3) ซึ่งจะบันทึกสาเหตุที่โมเดลหยุดสร้าง ฟิลด์นั้นมักจะบอกคุณว่าฝ่ายใดเป็นเจ้าของปัญหา
  • ▸
    ค่า stop_reason แต่ละค่าชี้ไปยังเจ้าของที่แตกต่างกันและการแก้ไขที่แตกต่างกัน การปฏิเสธหมายถึงโมเดลปฏิเสธที่จะตอบสนอง การผสานรวมของคุณส่งคําขออย่างถูกต้อง
  • ▸
    ดังนั้นอย่ามองหาข้อบกพร่อง: อ่าน stop_details และลองใหม่บนโมเดลสํารอง max_tokens หมายถึงขีดจํากัดของคุณเองตัดเอาต์พุต คุณจะเห็นข้อความที่หยุดกลางประโยค หรือบล็อก tool_use สุดท้ายที่ไม่สมบูรณ์และจําเป็นต้องลองใหม่ด้วย max_tokens ที่สูงกว่า model_context_window_exceeded ยังหมายถึงเอาต์พุตถูกตัดออก เฉพาะ end_turn เท่านั้นที่บอกว่าโมเดลเสร็จสิ้นโดยเจตนา
⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Silent failures are harder to find: HTTP 200, no exception, wrong result. Check the connection first. A streaming response can fail after the 200 arrives, as an error event inside the server-sent event stream. A handler that only checks the initial status will log the failed call as a success. Then check the response itself. Every successful Messages API response includes [stop_reason](lesson:6.3), which records why the model stopped generating. That one field usually tells you which side owns the problem.

Each stop_reason value points to a different owner and a different fix. refusal means the model declined to respond. Your integration sent the request correctly, so don't look for a bug: read stop_details and retry on a fallback model. max_tokens means your own limit cut the output off. You see text that stops mid-sentence, or a last tool_use block that is incomplete and needs a retry with a higher max_tokens. model_context_window_exceeded also means the output was cut off. Only end_turn says the model finished on purpose.

Some behavior that looks like the model's own choice actually comes from the integration. Suppose Claude won't act on a tool result, or asks the user to confirm instructions it found there. Check whether your code is putting its own instructions inside the tool_result content. Claude treats instructions inside tool results as possibly untrusted content from a third party. Keep the tool result to just the data. Send your instructions in a user turn after the tool_result block, or, on models that support it, in a system message in the middle of the conversation. Exact string comparison on tool inputs is another example: it can break when the model version changes, because escaping of Unicode and forward slashes differs between versions. Parse the JSON instead.

        model="claude-opus-5-5", max_tokens=1024, messages=messages
    )

        # This won't work because Claude already decided it's done

        # CORRECT: Add a continuation prompt in a NEW user message
        messages.append({"role": "user", "content": "Please continue"})

        response = client.messages.create(

        )

💡 Reasoning (เหตุผลเบื้องหลังลำดับขั้น):

Fix the message structure first. Add a continuation prompt in a new user message only if the structure fix doesn't solve it.

คำแปลไทย:
แก้ไขโครงสร้างข้อความก่อน เพิ่ม Prompt ดําเนินการต่อใน User Message ใหม่เฉพาะเมื่อการแก้ไขโครงสร้างไม่สามารถแก้ไขได้เท่านั้น
“Use continuation prompts as a last resort: Only if these fixes don't resolve the issue.”
คำแปล: ใช้การแจ้งให้ดําเนินการต่อเป็นทางเลือกสุดท้าย: เฉพาะในกรณีที่การแก้ไขเหล่านี้ไม่สามารถแก้ไขปัญหาได้เท่านั้น

🔗 เอกสารอ้างอิงทางการจาก Anthropic
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

An empty end_turn shows up in the model's output, but the integration usually causes it. The response is exactly 2–3 tokens with no content and stop_reason: "end_turn", and it usually comes right after tool results. The most common cause is a habit many integrations have: adding a text block after the tool_result in the same user message, such as a friendly Here's the result. Claude learns that the user always adds text after tool results, so it ends its turn and waits for that text. Nothing throws, the status is 200, and the stop reason reports a normal finish. That is why this failure can go unnoticed in production for a long time.

The fix is in the message structure: send a user message that contains only the tool_result blocks. The second cause is sending Claude's finished response back with nothing added. That rules out the obvious workaround: retrying with the empty response unchanged won't help, because Claude has already decided it is done. If you still get empty responses after fixing the message structure, add a continuation prompt as a new user message. Use this only as a last resort, not as the first fix.

#1 1. เมื่อ 400 ชี้ไปที่ประวัติข้อความของคุณเอง

อ่านเนื้อหา ↗
  • ▸
    การสนทนาจะสิ้นสุดด้วย Assistant Message และโมเดลนี้จะปฏิเสธการเติมล่วงหน้า จบด้วย User Message และควบคุมรูปแบบเอาต์พุตด้วยเอาต์พุตที่มีโครงสร้างหรือคําแนะนํา System Prompt - การสิ้นสุดข้อความ แต่ไม่มีเครื่องมือ web_search ให้บริการ
  • ▸
    การแก้จุดบกพร่องของแอปพลิเคชัน Claude เริ่มต้นด้วยการตัดสินใจว่าการผสานรวมหรือโมเดลนั้นมีข้อผิดพลาด และข้อผิดพลาด 400 invalid_request_error จะแก้ไขข้อผิดพลาดนั้นตั้งแต่เนิ่นๆ: คําขอถูกปฏิเสธก่อนที่โมเดลจะสร้างอะไรออกมา
  • ▸
    ข้อผิดพลาดจึงอยู่ในสิ่งที่โค้ดของคุณส่งมา ส่วนที่ยากที่สุดคือการหาว่าส่วนใดของคําขอนั้นผิด และสําหรับข้อความและโครงสร้างการคิดที่ลูปใช้เครื่องมือสร้างขึ้น ข้อความข้อผิดพลาดมักจะบอกว่า

#2 2. ติดตาม stop_reason เมื่อไม่มีอะไรขว้าง

อ่านเนื้อหา ↗
  • ▸
    อย่ามองหาข้อบกพร่อง: อ่าน stop_details และลองใหม่บนโมเดลสํารอง max_tokens หมายถึงขีดจํากัดของคุณเองตัดเอาต์พุต คุณจะเห็นข้อความที่หยุดกลางประโยค หรือบล็อก tool_use สุดท้ายที่ไม่สมบูรณ์และจําเป็นต้องลองใหม่ด้วย max_tokens ที่สูงกว่า model_context_window_exceeded ยังหมายถึงเอาต์พุตถูกตัดออก เฉพาะ end_turn เท่านั้นที่บอกว่าโมเดลเสร็จสิ้นโดยเจตนา
  • ▸
    ความล้มเหลวแบบเงียบนั้นหายากกว่า: HTTP 200 ไม่มีข้อยกเว้น ผลลัพธ์ที่ไม่ถูกต้อง ตรวจสอบการเชื่อมต่อก่อน การตอบสนองแบบสตรีมมิ่งอาจล้มเหลวหลังจากที่ 200 มาถึง
  • ▸
    ค่า stop_reason แต่ละค่าชี้ไปยังเจ้าของที่แตกต่างกันและการแก้ไขที่แตกต่างกัน การปฏิเสธหมายถึงโมเดลปฏิเสธที่จะตอบสนอง การผสานรวมของคุณส่งคําขออย่างถูกต้อง

#3 3. การตอบสนอง end_turn ที่ว่างเปล่า

อ่านเนื้อหา ↗
  • ▸
    end_turn ที่ว่างเปล่าจะปรากฏขึ้นในเอาต์พุตของโมเดล แต่โดยปกติแล้วการผสานรวมจะเป็นสาเหตุของการเกิดปัญหา การตอบสนองคือโทเค็น 2-3 ตัวที่ไม่มีเนื้อหาและ stop_reason: “end_turn” โดยปกติแล้วจะเกิดขึ้นทันทีหลังจากผลของเครื่องมือ สาเหตุที่พบบ่อยที่สุดคือความเคยชินที่การผสานรวมหลายรายการมี: การเพิ่มบล็อกข้อความหลัง tool_result ในข้อความของผู้ใช้เดียวกัน เช่น Here‘s the result คล็อดเรียนรู้ว่าผู้ใช้มักจะเพิ่มข้อความหลังผลของเครื่องมือ
  • ▸
    จึงสิ้นสุดการหมุนและรอข้อความนั้น ไม่มีอะไรเกิดขึ้น สถานะคือ 200 และ stop_reason รายงานว่าเสร็จสมบูรณ์ตามปกติ นั่นคือเหตุผลที่ความล้มเหลวนี้อาจไม่มีใครสังเกตเห็นในการผลิตเป็นเวลานาน
  • ▸
    การแก้ไขอยู่ในโครงสร้างข้อความ: ส่ง User Message ที่มีเฉพาะบล็อก tool_result เท่านั้น สาเหตุที่สองคือการส่งการตอบกลับที่เสร็จสมบูรณ์ของ Claude กลับมาโดยไม่มีการเพิ่มอะไร สิ่งนี้ตัดวิธีแก้ปัญหาที่ชัดเจนออก: การลองใหม่ด้วยการตอบกลับที่ว่างเปล่าโดยไม่เปลี่ยนแปลงจะไม่ช่วยอะไร เพราะ Claude ได้ตัดสินใจแล้วว่ามันเสร็จแล้ว หาก
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (2 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
การปฏิเสธ stop_reason บนการตอบสนอง 200 หมายความว่าการผสานรวมส่งคําขอที่ล้มเหลว
A refusal stop_reason on a 200 response means the integration sent a broken request.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
การปฏิเสธหมายถึงโมเดลล้มเหลว แม้ว่าคําขอจะได้รับการประมวลผลสําเร็จก็ตาม จัดการโดยอ่าน stop_details และลองใหม่บนโมเดลสํารอง
A refusal means the model declined, even though the request was processed successfully. Handle it by reading stop_details and retrying on a fallback model.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
การตอบสนอง end_turn ว่างเปล่าเป็นข้อบกพร่องแบบจําลองครั้งเดียว ดังนั้นการรีเซ็ตการสนทนาเดียวกันจะแก้ไขได้
An empty end_turn response is a one-off model glitch, so resending the same conversation will fix it.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
Claude ได้ตัดสินใจแล้วว่าการเปลี่ยนนั้นเสร็จสิ้นแล้ว แก้ไขโครงสร้างข้อความก่อน แล้วจึงเพิ่ม Prompt ดําเนินการต่อใน User Message ใหม่
Claude has already decided the turn is done. Fix the message structure first, and only then add a continuation prompt in a new user message.
