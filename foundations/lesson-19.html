1. When a 400 points into your own message history

สาระสำคัญและหลักการทำงานของหัวข้อนี้: หัวข้อนี้เจาะลึก When a 400 points into your own message history ตามมาตรฐานและพิมพ์เขียวการสอบของ Anthropic โดยมุ่งเน้นการทำความเข้าใจสถาปัตยกรรมเชิงลึก ข้อดีข้อเสียทางเทคนิค และแนวทางการปฏิบัติจริงในโปรดักชัน

Debugging a Claude application starts with deciding whether the integration or the model is at fault, and a 400 invalid_request_error settles that early: the request was rejected before the model produced anything, so the bug is in what your code sent. The harder part is finding which part of the request is wrong, and for the message and thinking structures that tool-use loops build, the error text usually says.

In tool-use and thinking flows, the 400 message is specific enough to point you at the code to fix. These are the ones integrations hit most often:

- tool_use ids were found without tool_result blocks immediately after: a tool_use id got no tool_result, or text was placed before the results. Return one tool_result for each tool_use, with the results first. - thinking or redacted_thinking blocks in the latest assistant message cannot be modified: your code edited, reordered or filtered thinking blocks before sending them back. The message starts with the position of the bad block, such as messages.1.content.0. Send the assistant message back unchanged. - This model does not support assistant message prefill: the conversation ends with an assistant message, and this model rejects prefill. End with a user message, and control the output format with structured outputs or system prompt instructions. - A message ending but no web_search tool was provided: a resume request left out a server tool that the previous turn is still waiting on. Keep the same tools array.

Thinking settings fail the same way. If you send a thinking.type the model doesn't accept, such as enabled to a model that no longer supports extended thinking, you get a 400 whose message names the rejected value. So when every call starts failing right after a model upgrade, the cause is usually a request setting that needs updating, not an outage.

Silent failures are harder to find: HTTP 200, no exception, wrong result. Check the connection first. A streaming response can fail after the 200 arrives, as an error event inside the server-sent event stream. A handler that only checks the initial status will log the failed call as a success. Then check the response itself. Every successful Messages API response includes [stop_reason](lesson:6.3), which records why the model stopped generating. That one field usually tells you which side owns the problem.

Each stop_reason value points to a different owner and a different fix. refusal means the model declined to respond. Your integration sent the request correctly, so don't look for a bug: read stop_details and retry on a fallback model. max_tokens means your own limit cut the output off. You see text that stops mid-sentence, or a last tool_use block that is incomplete and needs a retry with a higher max_tokens. model_context_window_exceeded also means the output was cut off. Only end_turn says the model finished on purpose.

Some behavior that looks like the model's own choice actually comes from the integration. Suppose Claude won't act on a tool result, or asks the user to confirm instructions it found there. Check whether your code is putting its own instructions inside the tool_result content. Claude treats instructions inside tool results as possibly untrusted content from a third party. Keep the tool result to just the data. Send your instructions in a user turn after the tool_result block, or, on models that support it, in a system message in the middle of the conversation. Exact string comparison on tool inputs is another example: it can break when the model version changes, because escaping of Unicode and forward slashes differs between versions. Parse the JSON instead.

An empty end_turn shows up in the model's output, but the integration usually causes it. The response is exactly 2–3 tokens with no content and stop_reason: "end_turn", and it usually comes right after tool results. The most common cause is a habit many integrations have: adding a text block after the tool_result in the same user message, such as a friendly Here's the result. Claude learns that the user always adds text after tool results, so it ends its turn and waits for that text. Nothing throws, the status is 200, and the stop reason reports a normal finish. That is why this failure can go unnoticed in production for a long time.

The fix is in the message structure: send a user message that contains only the tool_result blocks. The second cause is sending Claude's finished response back with nothing added. That rules out the obvious workaround: retrying with the empty response unchanged won't help, because Claude has already decided it is done. If you still get empty responses after fixing the message structure, add a continuation prompt as a new user message. Use this only as a last resort, not as the first fix.
