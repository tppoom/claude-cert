กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Choosing the platform from the customer's cloud" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Infrastructure requirements usually start with where the customer already runs. If a company has AWS billing, IAM and CloudTrail auditing in place, it will want Claude on that cloud, not a new vendor relationship. Each platform bills through its own cloud and plugs into that cloud's identity and audit tools.

The two AWS rows look alike but have different operators, and that matters for compliance. Bedrock is AWS-operated. Claude Platform on AWS is Anthropic-operated and runs on AWS. Google Cloud is Google-operated, and Microsoft Foundry is Anthropic-operated on Azure. The operator decides whose retention and residency controls apply: on Bedrock and Google Cloud, the cloud provider is the data processor, so Anthropic's own controls described below don't apply there.

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 55342

A customer support session sends the same lengthy system prompt, containing product policies and tone guidelines, on every turn of a multi-turn conversation. The team wants to reduce the repeated processing cost and latency of that unchanged content. Which feature should they enable?

A Prompt caching
B Token counting
C Batch processing
D Data residency
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Prompt caching lets Claude reuse previously processed background content, such as a repeated system prompt, across turns to reduce cost and latency for the unchanged portion.

ตัวเลือก B: ไม่ถูกต้อง

Token counting only estimates how many tokens a prompt will use before sending it; it does not reduce the cost or latency of processing repeated content.

ตัวเลือก C: ไม่ถูกต้อง

Batch processing is for asynchronous, non-latency-sensitive bulk workloads, not for reducing repeated-content cost within an interactive multi-turn conversation.

ตัวเลือก D: ไม่ถูกต้อง

Data residency controls the geographic location where inference runs; it has no effect on reducing repeated processing cost for unchanged prompt content.

A requirement like "inference must run in the United States" maps to two independent settings. Inference geo controls where model inference runs. You set it per request with the inference_geo parameter or as a workspace default. Workspace geo controls where data is stored at rest and where endpoint processing such as code execution happens. You choose it when you create a workspace and can't change it later. Currently "us" is the only workspace geo, and inference_geo accepts only "us" or "global", which is the default.

Leaving the parameter in every request's code is not enough if a regulator needs the rule enforced. At the workspace level, allowed_inference_geos rejects any request that asks for a geo outside the list, and default_inference_geo applies when a request leaves the parameter out. Set both to "us" and every key in the workspace is held to US inference. You can confirm where a given request ran from its usage object:

US residency affects model choice and budget. inference_geo works only on Claude 4.6 and later models. On Haiku 4.5, the parameter returns a 400 error, so a US-only requirement removes it from the candidates. On supported models, US-only inference costs 1.1x the standard rate. That multiplier applies on the Claude API and Claude Platform on AWS. Bedrock and Google Cloud have their own regional pricing. Rate limits are shared across all geos, so moving traffic to "us" does not give you extra capacity.

An agent needs to retrieve and analyze the full content of specific web pages and PDF documents referenced during a conversation, using a platform-run tool rather than infrastructure the customer hosts. Which built-in tool satisfies this functional requirement?

A Web search tool
B Web fetch tool

คำตอบที่ถูกต้อง: ตัวเลือก B
ตัวเลือก A: ไม่ถูกต้อง

The web search tool augments Claude's knowledge with current search results from across the web; it returns search results rather than the full content of specific pages.

ตัวเลือก B: ถูกต้อง

The web fetch tool retrieves the full content from specified web pages and PDF documents for in-depth analysis, matching the requirement to pull specific referenced content.

ตัวเลือก C: ไม่ถูกต้อง

The code execution tool runs code in a sandboxed environment for data analysis and calculations; it does not retrieve web page or PDF content on its own.

ตัวเลือก D: ไม่ถูกต้อง

The MCP connector lets Claude call remote MCP servers directly from the Messages API; it is for tool connectivity, not for fetching arbitrary web pages or PDFs.

Zero Data Retention (ZDR) is the answer when a requirement says the vendor must not keep prompts or outputs. Without ZDR, the API deletes inputs and outputs within 30 days. With it, customer data isn't stored at rest once the API response is returned. ZDR is a contractual arrangement, not a request flag. It is enabled per organization, and a new organization under the same account doesn't inherit it.

ZDR has two exceptions. First, even under ZDR, Anthropic may keep data where the law requires it. If automated trust and safety systems flag a chat or session, inputs and outputs may be kept for up to 2 years. Second, ZDR covers only eligible features, and an ineligible feature isn't blocked. If a request uses one, that data falls outside the arrangement without any error.

For an architect, the rule is to design the solution around stateless Messages API calls and leave out stateful features. A ZDR customer also loses some cost options. The Batch API's 50% discount, for example, requires asynchronous storage. ZDR also limits model choice, through a designation called Covered Models. A Covered Model is one for which Anthropic requires limited data retention and review as part of its safety work, so it can't run under zero retention. Claude Fable 5.1 is one. Unless Anthropic has expressly authorized it for your organization, a request to a Covered Model from a zero-retention workspace fails with the error "In order to access this model, your organization or Workspace must have data retention enabled." The fix is to turn on 30-day data retention for a workspace, which an organization Admin or Owner can do under the workspace's Privacy controls in the Console; it applies to that workspace only and isn't retroactive. Check whether a model is Covered before promising ZDR alongside it. Finally, ZDR applies only where Anthropic is the data processor. It is available on the Claude API and, on request, on Claude Platform on AWS. On Bedrock and Google Cloud, use that provider's retention controls.

Expected volume is also a requirement, and it maps to limits that apply to the whole organization. Messages API rate limits are measured in requests per minute (RPM), input tokens per minute (ITPM) and output tokens per minute (OTPM). Each model has its own limits. Going over any of them returns a 429 with a retry-after header. Most current models allow 1,000 RPM, 2,000,000 ITPM and 400,000 OTPM. Claude Fable 5.x allows only 500,000 ITPM and 100,000 OTPM, so a high-throughput requirement can rule it out even when it would win on quality.

Two details change the sizing calculation. First, prompt caching lets you reuse repeated content, such as system instructions, tool definitions and large documents, across requests. The part of a request served from that cache is reported as cache_read_input_tokens, and for most models those cache reads don't count toward ITPM. With a 2,000,000 ITPM limit and an 80% cache hit rate, you can process about 10,000,000 input tokens per minute. Second, max_tokens doesn't count toward OTPM; only tokens actually generated do. One thing doesn't change: every limit is a ceiling, not a promise of capacity.

Limits and spend caps both come from the organization's usage tier. Anthropic places an organization on a tier automatically, based on usage history and account standing, and the organization can move to a higher tier over time as it uses the API. New organizations and those with little history may start in an Evaluation tier with limits below the standard ones, which rise automatically as history builds. The Console's Rate limits page shows your tier and current limits, and higher limits can be requested.

Spend caps fail differently from rate limits. When an organization reaches its tier's cap, usage pauses until 00:00 UTC on the first day of the next month. Requests return a 429 with error code enforced_spend_limit_reached and no retry-after header, so automatic retries keep failing. A spend limit you set yourself below the cap returns HTTP 400 instead. Budget the tier to cover peak months, not average months.

For a requirement of guaranteed throughput, use Priority Tier. It is available only with a capacity commitment: input and output tokens per minute, a term of 1, 3, 6 or 12 months, and a specific model version. Priority requests are served ahead of all other traffic, Priority Tier targets 99.5% uptime, and requests beyond the commitment fall back to standard tier. It isn't offered on Claude Fable 5.1, Opus 5.5, Opus 5, Sonnet 5.5 or Sonnet 5. A requirement for both guaranteed throughput and one of those models is a conflict you have to resolve, either by changing the model or by relaxing the guarantee.
