💡 แนวคิดหลักสำคัญ (Key Concept)

Three-part input total — Prompt caching lets a request reuse a stored copy of a prompt prefix that ends at a marked cache breakpoint. Because of that, a response reports its input in three separate fields, and each field is billed at its own rate: tokens read from cache, tokens written to cache, and uncached tokens after the last breakpoint. You only get the real input size, and the real input cost, by adding all three.

Claude bills by the token, and the price depends on which direction the token travels. [Tokens](lesson:5.1) are the units the model reads and writes. Everything you send in a request counts as input, and everything Claude generates counts as output. Each model has one price for input and another for output, both quoted in US dollars per million tokens (MTok).

On every model in that table, an output token costs five times as much as an input token. That changes how you read a cost estimate. Take a Sonnet 5.5 request with 10,000 input tokens and a 2,000-token answer: the input costs $0.02, and the much shorter output also costs $0.02. If you only budget for prompt length, a workload that writes long answers will cost more than you planned.

Input means more than the text you typed. With tool use, the input includes the tools parameter (each tool's name, description and schema), every tool_use and tool_result block in the conversation, and a system prompt the API adds automatically when tools are present. Server-side tools such as web search also charge per use on top of their tokens. A large tool catalogue is therefore paid for again on every turn.

The base price is only a starting point. Several request settings multiply it. Batch processing, explained in [Message Batches API and realtime vs batch](lesson:2.3), halves both input and output prices in exchange for asynchronous delivery. Fast mode, covered in [Effort levels and fast mode](lesson:5.3), goes the other way: on Claude Opus 5.5 it charges $8 input and $40 output per MTok, twice the standard rate. Setting inference_geo to US-only on Claude 4.6 and later models adds 1.1x to every token category.

Three of the rows below concern prompt caching. A prompt prefix that stays the same from request to request can be cached, and you mark where that prefix ends with a cache_control breakpoint. When a request arrives, the system checks whether the prefix up to the breakpoint is already cached. If it is, those tokens are a cache read; if not, the full prompt is processed and the prefix is stored as a cache write.

These modifiers combine. Cache multipliers apply together with the batch discount, so a batched request that reads a cached prefix gets both discounts. Fast mode pricing also stacks with caching and data residency, but you can't combine it with batch. Context length is not a modifier. Claude 4.6 and later models bill the full 1M-token window at the standard per-token rate, so a very long request costs more only because it has more tokens.

A document-analysis pipeline caches a 40,000-token reference manual using an ephemeral cache_control breakpoint with the default TTL. Analysts submit follow-up questions against the manual in bursts, but gaps between bursts are frequently 8 to 10 minutes. The team observes that cache reads are not occurring for most follow-up bursts, so they keep paying the full cache-write price again. What change best fits this usage pattern?

คำตอบที่ถูกต้อง: ตัวเลือก A
💡 คำอธิบายเฉลยภาษาไทยรายตัวเลือก (Option Analysis):
ตัวเลือก A: ✓ คำตอบที่ถูกต้อง

ถูกต้อง. TTL แคชชั่วคราวเริ่มต้นคือ 5 นาที ซึ่งสั้นกว่าช่องว่าง 8-10 นาทีที่สังเกตเห็น ดังนั้นแคชจะหมดอายุระหว่างการระเบิดแต่ละครั้ง ตัวเลือก TTL 1 ชั่วโมง (2x ราคาอินพุตพื้นฐานสำหรับการเขียน) ครอบคลุมช่องว่างนั้น และปล่อยให้การระเบิดแคชในภายหลังแทนที่จะเขียนใหม่

EN: Correct. The default ephemeral cache TTL is 5 minutes, which is shorter than the observed 8-10 minute gaps, so the cache expires between bursts. The 1-hour TTL option (2x base input price for the write) covers that gap and lets later bursts hit the cache instead of re-writing it.
ตัวเลือก B: ตัวเลือกที่ไม่ถูกต้อง

จังหวะก่อนวอร์ม 5 นาทีคงที่จะรีเฟรชแคชหากคำขอเข้ามาจริงภายในหน้าต่าง TTL 5 นาทีเท่านั้น มันไม่ได้จัดการกับช่องว่าง 8-10 นาทีโดยไม่ต้องรันงานพื้นหลังอย่างไม่มีกำหนด และไม่ใช่กลไกโดยตรงที่ Anthropic มอบให้เพื่อยืดอายุการใช้งานแคช

EN: A fixed 5-minute pre-warm cadence only refreshes the cache if requests actually land within the 5-minute TTL window; it does not address gaps of 8-10 minutes without essentially running a background job indefinitely, and it isn't the direct mechanism Anthropic provides for extending cache lifetime.
ตัวเลือก C: ตัวเลือกที่ไม่ถูกต้อง

การแบ่งจุดพักออกเป็นสี่จุดจะเปลี่ยนรายละเอียด ไม่ใช่ TTL แต่ละโทเค็น 10,000 ชิ้นจะยังคงหมดอายุหลังจากไม่มีการใช้งานเป็นเวลา 5 นาทีภายใต้ TTL เริ่มต้น ดังนั้นปัญหาเดียวกันนี้จึงเกิดขึ้นอีก

EN: Splitting into four breakpoints changes granularity, not TTL; each 10,000-token chunk would still expire after 5 minutes of inactivity under the default TTL, so the same problem recurs.
ตัวเลือก D: ตัวเลือกที่ไม่ถูกต้อง

There is no context-window setting that retains prompt content in server-side memory between sessions; the context window defines the maximum tokens per request, and caching is controlled through cache_control, not context window size.

EN: There is no context-window setting that retains prompt content in server-side memory between sessions; the context window defines the maximum tokens per request, and caching is controlled through cache_control, not context window size.

The count_tokens endpoint tells you a request's input size without running the model. It accepts the same structured input as message creation (system prompt, tools, images and PDFs) and returns one number, input_tokens. That makes it the right tool for cost estimates: count a representative request once and multiply by expected volume, without paying for inference. The endpoint is free, but it has its own requests-per-minute limit that depends on your usage tier.

The count has three limits. First, it ignores caching. You can include cache_control blocks, but the result is the raw input size, not what you'd pay after cache hits. Second, some inputs that the Messages API accepts are rejected here: most server tools, the MCP connector, and image or document blocks that use a url or file source. Send images and PDFs as base64 if you need them counted. Third, the count depends on which model you pass.

The model dependence matters when you migrate. Fable 5.1, Mythos 5.1, Fable 5 and Mythos 5 use the tokenizer introduced with Opus 4.7, and the same prompt comes out about 30 percent larger on it than on older models. Cost dashboards built from old counts will then underestimate. To find the real difference, count the same request twice, once with your current model and once with the new one, and compare the two input_tokens values.

Match each usage field to what it counts

คำตอบที่ถูกต้อง: ตัวเลือก A
💡 คำอธิบายเฉลยภาษาไทย (Thai Explanation):

ทั้งสามฟิลด์รวมกันเป็นข้อมูลเข้าทั้งหมด input_tokens เพียงอย่างเดียวครอบคลุมเฉพาะส่วนหลังเบรกพอยต์สุดท้าย

EN: The three fields together make up total input. input_tokens alone covers only the part after the last breakpoint.
“Important: input_tokens does NOT represent all input tokens, only the portion after your last cache breakpoint.”
🔗 เอกสารอ้างอิง Anthropic
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Each response's usage object records what you were actually billed for, and the input side is split three ways. cache_read_input_tokens were read from cache, cache_creation_input_tokens were written to cache, and input_tokens are the uncached tokens after the last breakpoint. A common mistake is to log input_tokens alone. With a 200,000-token cached document and a 50-token question, that field shows 50 even though 200,050 tokens went in.

The Usage and Cost Admin API gives you totals for the whole organization. It needs an Admin API key. Its /v1/organizations/usage_report/messages endpoint returns token counts in 1m, 1h or 1d buckets, and you can filter or group by model, workspace, API key, service tier, inference_geo or speed. The cost report returns amounts in USD, which finance teams use to reconcile internal records against Anthropic billing. The Console Usage and Cost pages show the same data, and both can be exported as CSV.

The same three input fields also show how close you are to your rate limits, which are explained in [Rate limits, spend limits and service tiers](lesson:2.1). On most models, input_tokens and cache_creation_input_tokens count toward input tokens per minute (ITPM), but cache_read_input_tokens do not. A higher cache rate therefore lowers both cost and pressure on ITPM. The Console Usage page plots hourly peak ITPM next to your cache rate and your current limit, so one chart shows both effects.
