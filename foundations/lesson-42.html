1. The harness loop: dispatching client tool calls

ใน Claude Agent SDK การทำงานหลักถูกขับเคลื่อนด้วยฟังก์ชัน query() ซึ่งทำหน้าที่จัดการวงรอบเอเจนต์ (Agentic Loop) ให้อัตโนมัติ:

วงรอบการทำงานของ query() Loop:
  1. ส่งพร้อมต์และประวัติการสนทนาไปยัง Claude API
  2. รับผลลัพธ์จากโมเดล หากโมเดลส่ง stop_reason: "tool_use" ระบบจะรันเครื่องมือที่ระบุ
  3. นำผลลัพธ์ของเครื่องมือส่งกลับไปให้ Claude ประเมินซ้ำ
  4. ลูปนี้จะหมุนต่อเนื่องไปเรื่อยๆ จนกระทั่งโมเดลส่ง stop_reason: "end_turn" โดยไม่มีการเรียกเครื่องมือเพิ่ม

Claude can't run your code, so every client tool call is a round trip. Claude asks, your harness runs the tool, and you report back. The standard harness is a while loop keyed on stop_reason. The loop exits on any other stop reason (end_turn, max_tokens, stop_sequence, refusal), and your application should handle each of those.

For each tool_use block, dispatch on name, pass in input, and keep the id. Blocks from the computer use or browser use toolsets also carry a toolset_name, so dispatch those on both fields. If you'd rather not write the loop yourself, the SDK's Tool Runner runs your tools and sends the results back automatically.

A tool result goes in a user message as a tool_result block. tool_use_id is required and matches the id of the request it answers. content is optional. It can be a plain string, or a list of text, image, document, or search_result blocks, so a tool can return a caption and a screenshot together. You may leave content out entirely. Results for toolset members are stricter: they must echo the same toolset_name, and the API rejects a member result without it.

There are two kinds of failure. In an execution error, the tool itself fails, for example the weather API returns HTTP 500. Return the error message as the content with is_error: true, and Claude will work the failure into its reply to the user. In an invalid call, Claude's request is malformed, for example a required parameter is missing. That usually means the definition didn't give Claude enough to go on. During development, the fix is a more detailed description. At runtime, you can return an is_error result that names the problem, and Claude will retry 2–3 times with corrections before apologizing. Strict tool use stops schema violations before they happen.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Server tools run their own loop inside Anthropic's infrastructure. In the response, they appear as server_tool_use blocks whose ids start with srvtoolu_, each followed by its result block. You never send a tool_result for them, and server tool errors are handled transparently, so there's no is_error to manage. Two exceptions hand control back to you. First, the server loop has an iteration cap. When Claude hits it, you get pause_turn: re-send the paused response as-is with the same tools, and repeat with a cap on continuations. Second, Claude may call a server tool and a client tool in the same parallel group. Then you get tool_use with a server_tool_use block that has no matching result. Send only the client tool_result blocks and keep the same tools array. The API then runs the deferred server tool.

💡 คำอธิบายเฉลยภาษาไทย (Thai Explanation):

เครื่องมือที่ไม่ได้รับอนุญาตจะถูกลบออกจากคำขอ ดังนั้น Claude จึงไม่สามารถลองทำได้เลย ในทางตรงกันข้าม การปฏิเสธจาก canUseTool เกิดขึ้นหลังจากที่ Claude โทรออกแล้ว

EN: A disallowed tool is removed from the request, so Claude can't attempt it at all. A denial from canUseTool, by contrast, happens after Claude has already made the call.
“The Bash tool definition is removed from the request. Claude does not see the tool and cannot attempt it.”
🔗 เอกสารอ้างอิง Anthropic
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Claude only ever sends a request, and your code runs every client tool. That makes your harness the natural place to approve or block calls. The Agent SDK builds this in with permission modes, hooks, and declarative allow/deny rules. Hooks run custom code that can allow, deny, or modify a tool request. Allow rules such as allowed_tools=["Read", "Grep"] auto-approve the tools they list. Unlisted tools still exist, and their calls fall through to the permission mode and the canUseTool callback. A disallowed_tools entry is a different thing: it removes the tool definition from the request entirely. When no earlier step settles a call, canUseTool asks the user at runtime.
