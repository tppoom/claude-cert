1. Hooks: เลเยอร์ที่ทำงานทุกครั้งที่มี Tool Call

Prompt เช่น "ห้ามรัน rm -rf เด็ดขาด" เป็นเพียงคำสั่งที่ Claude นำไปพิจารณา แต่ Hook คือสิ่งที่ Claude Code จะ execute จริงตามโค้ดเสมอ โดยคุณสามารถผูก Handler เข้ากับ Lifecycle Event เพื่อให้ทำงานทุกครั้งที่ Event นั้นถูกทริกเกอร์ ไม่ว่าโมเดลจะตัดสินใจ

⚠️
ข้อควรระวัง & จุดสังเกต: อย่างไรก็ตาม และในบรรดาแนวทางการป้องกันทั้งหมด Hook จัดว่าไม่อาศัยการปฏิบัติตามคำสั่งของโมเดลแม้แต่น้อย เพราะมันจะดักรันทุก Tool Call เสมอ แม้กระทั่งคำสั่งที่เกิดจากการโดน Prompt Injection ก็ตาม

Hook Events ถูกทริกเกอร์ด้วย 3 ความถี่ที่แตกต่างกัน: SessionStart และ SessionEnd ทำงานครั้งเดียวต่อหนึ่ง Session, UserPromptSubmit, Stop และ StopFailure ทำงานครั้งเดียวต่อหนึ่ง Turn, ส่วน PreToolUse และ PostToolUse จะทำงานครอบรอบทุก Tool Call ภายใน Agentic Loop (ยกเว้น EndConversation ที่จะข้ามทั้งคู่) ทั้งนี้ระบบ Guardrails จะโฟกัสคู่ Pre/Post Tool Call เป็นหลัก เพราะเป็นจุดที่ Agent ใช้แก้ไขไฟล์, รัน Shell Command และยิงเรียก External Services

กลไกของ Hook ไม่ได้จำกัดอยู่แค่การสั่งบล็อก (Blocking) เท่านั้น แต่ยังสามารถใช้ Log ทุกคำสั่ง Bash ลง Audit File, ดักรอให้คนกด Approve ก่อนแก้ Database หรือแม้แต่ Rewrite ค่า Input ของ Tool ก่อนรันจริง โดย Handler ทั้งหมดนี้คือโค้ดที่คุณเขียนเองและฝังไว้ที่จุดคงที่ของ Loop

A prompt instruction such as "never run rm -rf " is something Claude weighs. A hook is something Claude Code executes. You attach a handler to a lifecycle event, and the handler runs each time that event fires, whatever the model reasoned its way to. Of all the defences described in [Guardrail layering](lesson:7.2), this one does not depend on the model following instructions: it runs on every tool call, including calls the model was talked into by injected content.

Hook events fire at three different rates. SessionStart and SessionEnd fire once per session. UserPromptSubmit, Stop and StopFailure fire once per turn. PreToolUse and PostToolUse fire around every tool call inside the agentic loop, with one exception: EndConversation calls skip both. Guardrails care most about the tool-call pair, because tool calls are where an agent changes files, runs shell commands and calls external services.

The same mechanism covers more than blocking. One hook can log every Bash command to an audit file. Another can make a person approve database writes. A third can rewrite a tool's input before it runs. Whichever you build, the handler is your own code, sitting at a fixed point in the loop.

Whether a hook can block comes down to timing. A hook can stop an action only if its event fires before that action takes effect. PreToolUse fires before the tool executes, so it can cancel the call. UserPromptSubmit fires before Claude processes the prompt, so blocking it means the prompt never reaches Claude. UserPromptExpansion can stop a typed command from expanding into a prompt, and PreModelSwitch can veto a requested model switch. PostToolUse and PostToolUseFailure fire after the tool has already succeeded or failed. Use them to audit, lint or report back to Claude. They are too late to prevent anything.

"Block" does not always mean "refuse a dangerous action". On Stop and SubagentStop, blocking keeps Claude working. You would use that to stop a turn ending before the tests pass, not to protect the system. PermissionRequest catches people out the other way round. It fires exactly when a tool call needs approval, yet exit code 2 does nothing there, so a hook that wants to refuse must answer through the decision object in its JSON output.

Hook configuration has three levels. You choose an event, add a matcher group that filters when it fires, and list one or more handlers to run when it matches. For tool events (PreToolUse, PostToolUse, PostToolUseFailure, PermissionRequest, PermissionDenied), the matcher is compared with the tool name. Other events filter on other fields: SessionStart on how the session started, PreCompact on whether compaction was manual or auto. UserPromptSubmit, Stop, PostToolBatch and a few others have no matcher support and fire on every occurrence.

How a matcher string is read depends on the characters in it. *, an empty string or no matcher at all matches everything. A string made only of letters, digits, _, -, spaces, commas and | is an exact name or a list of exact names, so Edit|Write matches those two tools and nothing else. Any other character turns the whole string into an unanchored JavaScript regular expression. ^Notebook therefore matches every tool whose name starts with Notebook, and mcp__memory__.* matches every tool on the memory MCP server. MCP tools are named mcp__<server>__<action>, which is why a regex is the usual way to cover a whole server.

A matcher can only see the tool name. To narrow a hook further, add an if condition on the handler, written in permission-rule syntax such as Bash(rm *). The handler then starts only for calls whose arguments fit. A script that runs on every Bash call has to parse and dismiss most of them. With if, it runs only for the commands it exists to judge.

The handler's type field decides what kind of code makes the decision. A guardrail that pattern-matches a command string fits naturally in a command handler, which is a script that reads the event JSON and replies through its exit code or stdout. The other types send the event to a service you run, to an MCP tool, or to a model.

For a hard rule, prefer a command handler. It returns the same decision for the same input. Prompt and agent handlers put a model's judgment inside the check, which helps when a policy is too fuzzy for a regex. HTTP handlers can be restricted by an administrator: once allowedHttpHookUrls is set at any settings level, only hook URLs on the merged allowlist run.

Where you write the hook decides who it protects. A guardrail in ~/.claude/settings.json covers all of your own projects but no one else. Put it in.claude/settings.json and it is committed with the repository, so everyone who clones the repo gets it..claude/settings.local.json is gitignored and stays personal. Managed policy settings apply across the organization and are controlled by administrators. Hooks can also come with a plugin or be declared in a skill's or subagent's frontmatter, scoped to when that component is active.

(ทำไมถึงผิด): ไม่จริง: การส่ง exit code 2 จาก PermissionRequest hook จะเป็นการปฏิเสธ Permission เพราะ PermissionRequest จะไม่สนใจ exit code 2 หากต้องการ Deny สิทธิ์ จะต้องส่งผ่าน decision property ใน JSON Output ของ Hook เท่านั้น
PostToolUse fires after the tool has already succeeded. Exit 2 only sends stderr back to Claude. Prevention has to happen in PreToolUse. Exiting 2 from a PermissionRequest hook denies the permission request. (ทำไมถึงผิด): PermissionRequest ignores exit code 2. To refuse, the hook has to return a decision in its JSON output.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Edit|Write คือ Regular Expression จึง Match Tool อื่นๆ ที่แค่มีคำว่า Edit หรือ Write อยู่ในชื่อด้วย?
Edit|Write is a regular expression, so it also matches tools whose names merely contain Edit or Write.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Matcher ที่ประกอบด้วยตัวอักษร, ตัวเลข, _, -, ช่องว่าง, จุลภาค และ | จะถูกประมวลผลเป็นรายการชื่อแบบตรงตัว (Exact Names) เท่านั้น จะเปลี่ยนเป็น Regular Expression ก็ต่อเมื่อมีตัวอักษรพิเศษอื่นนอกเหนือจากกลุ่มนี้
A matcher made only of letters, digits, _, -, spaces, commas and | is a list of exact names. Only other characters switch it to a regular expression.

  • ✓ระบุ Hook Events ที่ถูกเรียกในแต่ละ Tool Call, แต่ละ Turn และแต่ละ Session
  • ✓แยกแยะว่า Hook Event ใดสามารถยับยั้ง Action ได้ และ Event ใดทำได้เพียงสังเกตการณ์ (Observe) ย้อนหลัง
  • ✓เขียน Matcher โดยใช้ชื่อแบบตรงตัวหรือ Regular Expressions เพื่อเจาะจง Tools ที่ต้องการ
  • ✓เลือก Handler Type และตำแหน่งการตั้งค่า (Settings Location) ที่เหมาะสมสำหรับ Guardrail Hook
