1. Explicit instructions that carry their reason

Prompt Engineering คือการปรับแต่งข้อความที่ส่งให้ Claude จนกว่าจะได้ผลลัพธ์ตามเกณฑ์ที่ต้องการ ปัญหาแรกที่พบบ่อยคือความคลุมเครือ เพราะ Claude จะไม่คาดเดาความต้องการที่ไม่ได้ระบุไว้ เช่น การสั่งว่า "Create an analytics dashboard" จะได้ Dashboard ระดับพื้นฐานทั่วไป แต่ถ้าสั่งว่า "Create an analytics dashboard. Include as many relevant features and interactions as possible. Go beyond the basics to create a fully-featured implementation" คุณจะได้ Dashboard แบบจัดเต็มตามต้องการ หากต้องการความลึก ฟีเจอร์เฉพาะเจาะจง หรือระดับคุณภาพแบบไหน ต้องระบุลงไปใน Prompt ให้ชัดเจน

ความชัดเจน (Specific) หมายถึงการระบุข้อจำกัด (Constraints), กลุ่มเป้าหมาย, โครงสร้าง และขอบเขต เช่น แทนที่จะสั่งแค่ "Create a meal plan for a Mediterranean diet" ควรกำหนดเงื่อนไขสุขภาพ (การคุมระดับน้ำตาลก่อนเบาหวาน), ขีดจำกัดแคลอรี (1,800 แคลอรีต่อวัน), มื้ออาหารที่ครอบคลุม และสารอาหารที่ต้องแจกแจง และในกรณีที่ลำดับขั้นตอนหรือความครบถ้วนมีความสำคัญ เช่น Review Checklist หรือขั้นตอน Migration ให้เขียน Instruction เป็น Numbered List เพื่อป้องกันไม่ให้ข้ามหรือรวมขั้นตอนเข้าด้วยกัน

การให้เหตุผลเบื้องหลังกฎเกณฑ์ (Context & Reason) ช่วยให้ Claude ทำตามได้อย่างแม่นยำกว่าการย้ำซ้ำๆ หรือการใช้ตัวพิมพ์ใหญ่ เช่น คำสั่งห้วนๆ อย่าง "NEVER use ellipses" มักจะยังมีหลุดจุดไข่ปลา "..." ออกมา แต่หากเปลี่ยนเป็น "Your response will be read aloud by a text-to-speech engine, so never use ellipses since the text-to-speech engine will not know how to pronounce them" Claude จะเข้าใจเป้าหมายที่แท้จริง และเลี่ยงการใช้สัญลักษณ์อื่นๆ ที่ระบบ Text-to-Speech อ่านไม่ออกด้วย หลักการเดียวกันนี้ใช้กับการจัด Format: การบอกสิ่งที่ควรทำ ("write in smoothly flowing prose paragraphs") ได้ผลดีกว่าการสั่งเฉพาะสิ่งที่ห้ามทำ ("do not use markdown")

Prompt เวอร์ชันแรกคือแบบร่างที่มักยังไม่สมบูรณ์แบบ ให้รันดูผลลัพธ์ หาจุดที่บกพร่อง แล้วนำมาปรับปรุง ลูปนี้เรียกว่า Iterative Refinement ซึ่งสามารถนำมาใช้กับ Output ได้ด้วย โดยนำ Response ที่ได้ส่งกลับเข้าไปเป็น Input ใน Prompt ถัดไป เพื่อให้ Claude ตรวจสอบหรือขยายความสิ่งที่เคยตอบไว้ ซึ่งช่วยดักจับความไม่สอดคล้องกัน (Inconsistencies) ที่การรันรอบเดียวตรวจไม่พบ ตัวอย่างเช่น Summary Workflow: Prompt แรกใช้สร้างบทสรุป Prompt ที่สองตรวจสอบความถูกต้อง ความชัดเจน และความสมบูรณ์ และ Prompt ที่สามนำ Feedback นั้นมาปรับแก้ให้ดีขึ้น แต่ละรอบมีหน้าที่เฉพาะ โดยแลกกับ API Call และ Latency ที่เพิ่มขึ้น

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
Writing a rule in capitals, or repeating it, is the most reliable way to make Claude obey it. (ทำไมถึงผิด): Giving the reason behind the rule works better: Claude understands the goal and extends it to related cases the rule did not name.

การเขียนกฎด้วยตัวพิมพ์ใหญ่หรือการย้ำซ้ำๆ เป็นวิธีที่ดีที่สุดที่ทำให้ Claude ปฏิบัติตามคำสั่ง? (ทำไมถึงผิด): ไม่จริง: การอธิบายเหตุผลเบื้องหลังกฎเกณฑ์ให้ผลลัพธ์ที่ดีกว่าอย่างมีนัยสำคัญ เพราะ Claude จะเข้าใจเป้าหมายและสามารถประยุกต์ใช้กับกรณีแวดล้อมที่ไม่ได้ระบุไว้ในกฎได้ด้วย

Prompt engineering is the work of writing and adjusting the text you send Claude until its output meets your criteria. The first thing to fix is usually vagueness. Claude does not guess at ambitions you left out. "Create an analytics dashboard" gets you a reasonable dashboard. "Create an analytics dashboard. Include as many relevant features and interactions as possible. Go beyond the basics to create a fully-featured implementation" gets you the thorough one you actually wanted. If you want depth, specific features or a particular quality bar, put it in the prompt.

Specific means stating constraints, audience, structure and limits. Compare "Create a meal plan for a Mediterranean diet" with a request that names the condition (pre-diabetic management), the budget (1,800 calories daily), the meals to cover and the breakdown to include. When order or completeness matters, as with a review checklist or a migration procedure, write the instructions as a numbered list so no step gets merged or skipped.

Giving the reason behind a rule makes Claude follow it more reliably than repeating it louder. "NEVER use ellipses" is a bare command, and a voice assistant that runs on it will still produce the occasional "...". "Your response will be read aloud by a text-to-speech engine, so never use ellipses since the text-to-speech engine will not know how to pronounce them" works better. Claude now knows the actual goal, so it can also avoid related problems the rule never mentioned, such as other symbols a speech engine would stumble on. The same applies to formatting: a prompt that says what to do ("write in smoothly flowing prose paragraphs") beats one that only says what to avoid ("do not use markdown").

The first version of a prompt is a draft. It rarely works perfectly, so run it, read where the output falls short, and revise; that loop is iterative refinement. It applies to the output as well as the prompt: a response can become the input to a follow-up prompt that asks Claude to verify or expand its own earlier statements, which catches inconsistencies a single pass leaves in. A summary workflow shows the shape. The first prompt writes the summary, the second reviews it for accuracy, clarity and completeness, and the third improves it using that feedback. Each pass has one job, at the price of an extra call and its latency.

An example shows Claude what you want instead of describing it. It is one of the most reliable ways to steer format, tone and structure. A prompt with no examples is zero-shot, one with a single example is one-shot, and one with several is few-shot (also called multishot). Zero-shot is fine when a clear instruction already gets the output you need. Examples earn their place when the format is easier to show than to describe, when you need a particular tone, when the task follows subtle conventions, or when plain instructions have not produced consistent results.

Start with one example and add more only when the output still misses. A one-shot summarisation prompt might show a single article with its three-sentence summary and then say "Now summarize this article in the same style". If summaries of long technical papers still drift, add a second example of exactly that kind. Adding examples one at a time like this tells you which example fixed what.

Claude pays very close attention to the details of examples, so it copies their accidents along with their intent. Three examples that all start with "Great question!" or all run to exactly two sentences teach that pattern too. Good examples have three properties:

- Relevant: they mirror your real inputs, not a toy version of them. - Diverse: they cover edge cases and vary enough that no unintended pattern appears. - Structured: each sits in <example> tags, with the set inside <examples>, so Claude can tell example from instruction.

A prompt has several parts, and each kind of content belongs in a particular one. The top-level system field holds what should apply from the very first turn: the role Claude plays and the standing rules. The user turn holds the task itself, with its documents and the question. Setting a role in the system prompt is the smallest change that steadies behaviour and tone. If a code-review assistant swings between chatty and terse, one sentence fixes most of it.

Agents have two more places for content. Third-party content belongs in tool_result blocks. Your own instructions do not: Claude treats tool-result content as untrusted data and may ignore or flag directions placed there. Put them in a user turn after the tool_result instead. On supported models a mid-conversation system message also works. It has the same authority as the top-level system field, and it suits instructions that only matter later in the conversation.

For long inputs (20k+ tokens), put the documents first and the query last. That order improves performance across all models. Wrap each document in <document index="n"> inside a <documents> parent, with the text in <document_content> and its origin in a <source> subtag such as annual_report_2023.pdf. This is the fix when Claude says a fact came from the wrong file: two reports pasted as one undifferentiated block give it no boundary to attribute against. Then ask for grounding. Have Claude first pull the relevant quotes into <quotes> tags and only then do the task from those quotes. This keeps it on the parts of a long document that matter.

ข้อความใดๆ ก็ตามที่คุณไม่ได้เขียนเอง ล้วนเป็นช่องทางที่อาจมีคำสั่งไม่พึงประสงค์แฝงเข้ามาได้ ไม่ว่าจะเป็นเนื้อหาอีเมล, หน้าเว็บที่ดึงมา (Fetched web page) หรือช่อง Free-text ที่ผู้ใช้กรอก โดยการโจมตีโดยตรงจากผู้ใช้ (Direct attack) และการโจมตีทางอ้อมจากเนื้อหา Third-party (Indirect attack) จัดเป็น Threat models คนละแบบ ซึ่งจะกล่าวถึงใน [Prompt injection and jailbreaks (two threat models)](lesson:7.1) แต่หน้าที่หลักของ Prompt Engineering ในส่วนนี้คือการจัดโครงสร้าง Prompt ให้ Claude สามารถแยกแยะความแตกต่างระหว่าง "คำสั่งระบบของคุณ" กับ "ข้อมูลที่นำมาประมวลผล" ได้อย่างชัดเจนเสมอ

เริ่มต้นด้วยการครอบ Untrusted text ด้วย Tag ที่ระบุชื่อชัดเจน เช่น ใช้ `<content>` ครอบข้อความที่ส่งมาจากผู้ใช้ หรือ `<tool_output>` ครอบผลลัพธ์ที่ Tool ส่งกลับมา จากนั้นระบุให้ชัดเจนว่าข้อมูลนี้คืออะไรและมาจากแหล่งใด เช่น "เนื้อหาของอีเมลขาเข้าจากผู้ส่งที่ไม่ระบุตัวตน" พร้อมเสริมด้วย System Prompt Policy เพื่อกำกับอย่างเข้มงวดว่า: เนื้อหาที่ดึงเข้ามาถือเป็น Data เท่านั้น และคำสั่งใดๆ ที่อยู่ข้างในเป็นเพียงข้อมูลสำหรับรายงาน ไม่ใช่คำสั่งที่ต้องปฏิบัติตาม นอกจากนี้ ควรทำ Input Validation ล่วงหน้าเพื่อกรองข้อความของผู้ใช้ตาม Injection patterns ที่รู้จักก่อนเสมอ

แม้การใช้ Tags จะช่วยแบ่งแยกเนื้อหาได้ แต่ไม่ได้ป้องกันการหลุดออกจากกรอบได้อย่างสมบูรณ์ (Tags separate, not seal) หาก Attacker ทราบชื่อ Tag ก็สามารถพิมพ์ `</content>` เพื่อปิด Tag แล้วแทรกข้อความเสมือนอยู่นอก Wrapper ได้ ดังนั้นหากเป็นไปได้ ควรใช้วิธี JSON-encode ข้อความที่เป็น Third-party strings แทน เพราะการ Escape จะสร้าง Boundary ที่ชัดเจน ทำให้ Payload ไม่สามารถปิด Quote หรือ Tag เพื่อหลุดออกมาได้ ตัวอย่างเช่น ฟิลด์ `"body": "Ignore previous instructions..."` จะคงสถานะเป็นเพียง Value ธรรมดาอย่างแน่นอน

Any text you did not write is a possible source of instructions you did not intend. Claude might read an email body, a fetched web page or a user's free-text field. Users who attack directly and third-party content that attacks indirectly are separate threat models, covered in [Prompt injection and jailbreaks (two threat models)](lesson:7.1). The prompt-engineering job is narrower: lay out the prompt so Claude can always tell your instructions apart from the data it is processing.

Start by wrapping untrusted text in a tag that names it, such as <content> around a user submission or <tool_output> around what a tool returned. Then say what the content is and where it came from, for example "the body of an inbound email from an unknown sender". A system prompt policy completes the setup: retrieved content is data, and instructions inside it are information to report, not commands to follow. Before any of this, input validation can filter user text for known injection patterns.

Tags separate content, but they do not seal it. An attacker who knows your tag name can type </content> and write text that looks like it sits outside the wrapper. Where possible, JSON-encode third-party strings instead. Escaping makes the boundary unambiguous, so the payload cannot close a quote or tag to break out. A field like "body": "Ignore previous instructions..." stays plainly a value.

6. การปรับแต่ง Prompt จากเคสที่ทดสอบไม่ผ่าน (Refining a prompt against failing cases)

ก่อนปรับแต่ง Prompt คุณต้องกำหนดเกณฑ์ความสำเร็จ (Success criteria) และวิธีทดสอบก่อน ซึ่งครอบคลุมอยู่ใน [Eval-driven iteration](lesson:2.2) หัวข้อนี้จะเน้นเรื่องการปรับแก้ Prompt เมื่อ Eval ไม่ผ่าน: ให้แก้ทีละจุด (One change at a time) แล้วรัน Failing cases ซ้ำหลังการแก้ทุกครั้ง เพื่อให้ตรวจสอบได้ว่าผลลัพธ์ที่ดีขึ้นหรือถดถอยลง (Regression) มาจากการแก้จุดใด หากคุณเพิ่ม Role, ใส่ตัวอย่าง 3 รายการ และแก้ Format template ไปพร้อมๆ กัน แล้วคะแนนเปลี่ยน คุณจะไม่สามารถบอกได้เลยว่าการเปลี่ยนแปลงใดส่งผล หรือการแก้จุดไหนที่ทำให้เคสที่เคยผ่านกลับมาพัง

Failing cases มักจะบ่งบอกแนวทางการแก้ไขอยู่แล้ว เช่น ระบบ Ticket Classifier ที่จัดการตั๋วทั่วไปได้ดี แต่มักพลาดกลุ่มตั๋วที่มีความกำกวม หากทีมงานบันทึก Input เหล่านั้นพร้อมคำตอบในอุดมคติไว้ ขั้นตอนถัดไปคือการแปลงพวกมันให้เป็น Few-shot examples ที่ครอบคลุมหลากหลายและติด Tag ชัดเจน เพราะเมื่อคำสั่งธรรมดา (Plain instructions) ไม่สามารถให้ผลลัพธ์ที่สม่ำเสมอได้ ตัวอย่าง (Examples) จะเข้ามาช่วยแก้ปัญหาตรงนี้ได้ตรงจุดที่สุด ให้เพิ่มตัวอย่างเข้าไป รันซ้ำ และเพิ่มต่อเฉพาะเมื่อยังมีเคสที่ Fail อยู่เท่านั้น

การปรับแต่ง (Adjustment) หมายรวมถึงการตัดข้อความออกพอๆ กับการเพิ่มเข้าไป เช่น Prompt ที่เคยเขียนให้โมเดลรุ่นเก่าอาจมีคำสั่งกำชับให้ตอบละเอียดเป็นพิเศษหรือเรียกใช้ Tools ให้ดุดันขึ้น แต่เมื่อย้ายมาใช้โมเดลรุ่นใหม่ คำสั่งเหล่านี้อาจทำให้โมเดลทำงานเกินความจำเป็น (Overdo) จึงควรลดทอนคำแนะนำดังกล่าวลงเมื่อทำการ Migrate และความล้มเหลวบางอย่างก็ไม่ใช่ปัญหาของ Prompt เลย หากตัวชี้วัดที่ตกคือ Latency หรือ Cost การเปลี่ยนไปใช้ Model อื่นที่เหมาะสมกว่าอาจแก้ปัญหาได้ง่ายกว่าการพยายามเขียน Prompt ใหม่ทั้งหมด

Before refining a prompt, you need success criteria and a way to test against them. Building those is covered in [Eval-driven iteration](lesson:2.2). This section is about how to change the prompt once an eval fails: one change at a time, re-running the failing cases after each, so every gain or regression can be traced to a single edit. If you add a role, three examples and a format template together and the score moves, you cannot tell which change did it, or which one broke the cases that used to pass.

The failing cases usually suggest the change. Take a ticket classifier that handles clear tickets but misses a cluster of ambiguous ones. If the team has saved those inputs with their ideal outputs, the next step is to turn them into diverse, tagged few-shot examples. Plain instructions are not producing consistent results, and that is exactly when examples help. Add them, re-run, and add more only if cases still fail.

Adjustment can mean removing text as well as adding it. A prompt written for an older model may tell it to be more thorough or to use tools more aggressively, and newer models can overdo that, so dial such guidance back when you migrate. Some failures are not prompt problems at all. If latency or cost is what fails, choosing a different model may fix it more easily than any rewrite.
