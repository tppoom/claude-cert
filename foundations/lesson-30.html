💡 แนวคิดหลักสำคัญ (Key Concept)

Explicit, separated prompt — Claude does best with a prompt that says exactly what you want and why, and that puts each kind of content (instructions, examples, documents, untrusted input) in its own labelled place. Almost every technique on this page applies that one idea.

A developer prompts Claude with the bare request "Create an analytics dashboard" and consistently gets a minimal, bare-bones implementation. The team wants a fully-featured result with rich interactions on the first attempt, without relying on multiple follow-up turns. What change to the prompt best achieves this?

A Rewrite the request to state the desired scope explicitly, such as asking for as many relevant features and interactions as possible and to go beyond the basics, rather than leaving scope for Claude to infer
B Resend the identical request in all capital letters so Claude interprets the wording with greater urgency and produces a more thorough response
C Raise the sampling temperature for the request so Claude generates more elaborate and creative dashboard markup than it would at default settings

ตัวเลือก A: ถูกต้อง

Correct. Claude responds well to explicit, specific instructions; if you want above-and-beyond behavior, you need to request it directly rather than relying on the model to infer elevated scope from a vague prompt.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. Capitalization is not a documented mechanism for increasing thoroughness; it does not substitute for stating the desired scope and features explicitly.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Temperature controls sampling randomness, not the thoroughness or feature-completeness of a response; it is not the lever for controlling scope.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Moving unchanged, vague wording into the system prompt does not add the specificity needed; the fix is adding detail about desired scope, not relocating the same wording.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Explicit instructions that carry their reason" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Prompt engineering is the work of writing and adjusting the text you send Claude until its output meets your criteria. The first thing to fix is usually vagueness. Claude does not guess at ambitions you left out. "Create an analytics dashboard" gets you a reasonable dashboard. "Create an analytics dashboard. Include as many relevant features and interactions as possible. Go beyond the basics to create a fully-featured implementation" gets you the thorough one you actually wanted. If you want depth, specific features or a particular quality bar, put it in the prompt.

Specific means stating constraints, audience, structure and limits. Compare "Create a meal plan for a Mediterranean diet" with a request that names the condition (pre-diabetic management), the budget (1,800 calories daily), the meals to cover and the breakdown to include. When order or completeness matters, as with a review checklist or a migration procedure, write the instructions as a numbered list so no step gets merged or skipped.

Giving the reason behind a rule makes Claude follow it more reliably than repeating it louder. "NEVER use ellipses" is a bare command, and a voice assistant that runs on it will still produce the occasional "...". "Your response will be read aloud by a text-to-speech engine, so never use ellipses since the text-to-speech engine will not know how to pronounce them" works better. Claude now knows the actual goal, so it can also avoid related problems the rule never mentioned, such as other symbols a speech engine would stumble on. The same applies to formatting: a prompt that says what to do ("write in smoothly flowing prose paragraphs") beats one that only says what to avoid ("do not use markdown").

The first version of a prompt is a draft. It rarely works perfectly, so run it, read where the output falls short, and revise; that loop is iterative refinement. It applies to the output as well as the prompt: a response can become the input to a follow-up prompt that asks Claude to verify or expand its own earlier statements, which catches inconsistencies a single pass leaves in. A summary workflow shows the shape. The first prompt writes the summary, the second reviews it for accuracy, clarity and completeness, and the third improves it using that feedback. Each pass has one job, at the price of an extra call and its latency.

An example shows Claude what you want instead of describing it. It is one of the most reliable ways to steer format, tone and structure. A prompt with no examples is zero-shot, one with a single example is one-shot, and one with several is few-shot (also called multishot). Zero-shot is fine when a clear instruction already gets the output you need. Examples earn their place when the format is easier to show than to describe, when you need a particular tone, when the task follows subtle conventions, or when plain instructions have not produced consistent results.

Start with one example and add more only when the output still misses. A one-shot summarisation prompt might show a single article with its three-sentence summary and then say "Now summarize this article in the same style". If summaries of long technical papers still drift, add a second example of exactly that kind. Adding examples one at a time like this tells you which example fixed what.

Claude pays very close attention to the details of examples, so it copies their accidents along with their intent. Three examples that all start with "Great question!" or all run to exactly two sentences teach that pattern too. Good examples have three properties:

- Relevant: they mirror your real inputs, not a toy version of them. - Diverse: they cover edge cases and vary enough that no unintended pattern appears. - Structured: each sits in tags, with the set inside , so Claude can tell example from instruction.

A prompt has several parts, and each kind of content belongs in a particular one. The top-level system field holds what should apply from the very first turn: the role Claude plays and the standing rules. The user turn holds the task itself, with its documents and the question. Setting a role in the system prompt is the smallest change that steadies behaviour and tone. If a code-review assistant swings between chatty and terse, one sentence fixes most of it.

Agents have two more places for content. Third-party content belongs in tool_result blocks. Your own instructions do not: Claude treats tool-result content as untrusted data and may ignore or flag directions placed there. Put them in a user turn after the tool_result instead. On supported models a mid-conversation system message also works. It has the same authority as the top-level system field, and it suits instructions that only matter later in the conversation.

For long inputs (20k+ tokens), put the documents first and the query last. That order improves performance across all models. Wrap each document in inside a parent, with the text in and its origin in a subtag such as annual_report_2023.pdf. This is the fix when Claude says a fact came from the wrong file: two reports pasted as one undifferentiated block give it no boundary to attribute against. Then ask for grounding. Have Claude first pull the relevant quotes into tags and only then do the task from those quotes. This keeps it on the parts of a long document that matter.

Users who attack directly and third-party content that attacks indirectly are separate threat models, covered in [Prompt injection and jailbreaks (two threat models)](lesson:7.1). Start by wrapping untrusted text in a tag that names it, such as around a user submission or around what a tool returned. A field like "body": "Ignore previous instructions..." stays plainly a value.

This section is about how to change the prompt once an eval fails: one change at a time, re-running the failing cases after each, so every gain or regression can be traced to a single edit. If you add a role, three examples and a format template together and the score moves, you cannot tell which change did it, or which one broke the cases that used to pass.

The failing cases usually suggest the change. Take a ticket classifier that handles clear tickets but misses a cluster of ambiguous ones. If the team has saved those inputs with their ideal outputs, the next step is to turn them into diverse, tagged few-shot examples. Plain instructions are not producing consistent results, and that is exactly when examples help. Add them, re-run, and add more only if cases still fail.

Adjustment can mean removing text as well as adding it. A prompt written for an older model may tell it to be more thorough or to use tools more aggressively, and newer models can overdo that, so dial such guidance back when you migrate. Some failures are not prompt problems at all. If latency or cost is what fails, choosing a different model may fix it more easily than any rewrite.
