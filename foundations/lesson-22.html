💡 แนวคิดหลักสำคัญ (Key Concept)

The Claude API is plain REST — Every Claude API feature is an HTTPS request to a path under api.anthropic.com, sent with a fixed set of headers and a JSON body. The client SDKs don't replace that contract. They build those requests for you and parse the responses.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Endpoints under one base URL" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Every Claude API feature sits at a path under https://api.anthropic.com, and each path is named after what it does. Most of your traffic goes to POST /v1/messages. Other jobs have their own endpoints: counting tokens before you send a prompt, submitting a large asynchronous batch, listing the models you can call, or uploading a file once so later requests can refer to it. In a raw integration the URL and the HTTP method pick the operation, and the JSON body carries the parameters.

The Agents, Sessions and Environments APIs, which power Claude Managed Agents, are in beta and sit alongside these. List endpoints such as GET /v1/models return results in pages. You pass a limit and a page cursor, and each response carries a data array plus a next_page cursor that is null once you reach the end.

A frontend engineer building a custom SSE parser for streaming Messages API responses needs to know when it is safe to treat one content block as fully received and move on to parsing the next one. Which event signals that a specific content block, identified by its index, will receive no further delta events?

A content_block_stop
B message_delta
C content_block_start
D message_stop
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct — content_block_stop is emitted once a content block at a given index has received all of its delta events and will not change further.

ตัวเลือก B: ไม่ถูกต้อง

message_delta communicates top-level changes to the Message object, such as stop_reason and cumulative usage, not the completion of an individual content block.

ตัวเลือก C: ไม่ถูกต้อง

content_block_start marks the beginning of a new content block and precedes its delta events, not the end.

ตัวเลือก D: ไม่ถูกต้อง

message_stop signals the end of the entire stream, after all content blocks have already closed with their own content_block_stop events.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Without the right headers, a request with a valid body is still rejected. A direct integration, such as a curl script, a language with no official SDK, or an HTTP client you wrote yourself, has to send three things on every call. First, a credential, normally your Console API key in x-api-key. Second, anthropic-version with a dated value such as 2023-06-01. Third, content-type: application/json. Leave out anthropic-version and the request fails even though the key is fine. That header pins the API behaviour your code was written against, as explained in [API versions and feature classifications (beta vs GA)](lesson:2.2).

You can send the credential as Authorization: Bearer instead of x-api-key. The Bearer form is also how short-lived Workload Identity Federation tokens are sent, while x-api-key remains supported as the legacy fallback. Exam scenarios still use the classic set: x-api-key, anthropic-version and content-type.

Moving a raw call into an SDK turns those headers from per-request code into client configuration. You hand the credential to the client once, delete the three header lines from every call site, and keep only anthropic-workspace-id when your key spans several workspaces. A migrated script that still sets anthropic-version by hand is carrying a line the client already owns.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "What the client SDKs add on top of REST" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The official SDKs make the same REST calls as a raw integration and handle the repetitive parts. Anthropic publishes client SDKs for Python, TypeScript, C#, Go, Java, PHP and Ruby. Each one does the following:

- sends the authentication, anthropic-version and content-type headers automatically - gives you typed request and response objects instead of raw dictionaries - retries transient failures with built-in logic and raises typed exceptions - supports streaming - manages request timeouts and connections

Some defaults matter in practice. The Python client reads ANTHROPIC_API_KEY from the environment if you don't pass a key, and it has both sync (Anthropic) and async (AsyncAnthropic) clients. The TypeScript SDK runs on Node.js, Deno, Bun and edge runtimes, but it refuses to run in a web browser unless you set dangerouslyAllowBrowser. That default protects your secret key from being shipped to end users.

Each SDK method is a thin wrapper over one endpoint, so what you know about the REST surface carries over directly. client.messages.create is POST /v1/messages, client.messages.batches.create is POST /v1/messages/batches, and token counting is a method on the same messages object that maps to POST /v1/messages/count_tokens. The parameters keep their REST names, so a JSON body from a curl script translates almost field for field into keyword arguments.

Retries and pagination are the two chores an SDK takes off your hands, and each is a setting to tune rather than code to write. The client retries connection errors, rate limits and 5xx responses twice by default, with exponential backoff, and it honors a retry-after header when the API sends one. max_retries on the client changes or disables that. A hand-written retry loop around an SDK call multiplies attempts with the built-in ones, so set max_retries to match whichever layer you want in charge.

For list endpoints, the SDK's auto-paginating iterator follows next_page for you, so a for loop walks every result without you touching a cursor. It only moves forward. Going back a page is the case where you read prev_page from the response and pass it back as page yourself.

The HTTP contract also covers what comes back. Every response carries a request-id header with a value like req_018EeWyXxfu5pfWkrYcMdjWG, and that is the identifier support will ask for. Responses also report which organization and workspace the credential resolved to, in anthropic-organization-id and anthropic-workspace-id. The Python and TypeScript SDKs expose the ID as _request_id on the response object. To read other headers, use with_raw_response.

Failures come back as JSON in a single, fixed shape. The top-level type is error, and the error object holds a machine-readable type and a human-readable message. The same request ID is repeated in the body as request_id, so a logged error body is enough to trace the call. Which status codes are worth retrying is covered in [API error types and recovery](lesson:4.1). On this page, the point is that every failure has this shape, and that the SDKs turn it into typed exceptions such as anthropic.NotFoundError rather than handing you raw JSON.

Request bodies have a size limit that depends on the endpoint. Messages and Token Counting accept up to 32 MB, Message Batches up to 256 MB and the Files API up to 500 MB. A request over its limit fails with 413 request_too_large before it reaches the API servers. If an application embeds large documents directly in a Messages request, it can hit this limit, which is a reason to upload those documents through the Files API instead.
