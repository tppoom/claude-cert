Every Claude API feature sits at a path under https://api.anthropic.com, and each path is named after what it does. Most of your traffic goes to POST /v1/messages. Other jobs have their own endpoints: counting tokens before you send a prompt, submitting a large asynchronous batch, listing the models you can call, or uploading a file once so later requests can refer to it. In a raw integration the URL and the HTTP method pick the operation, and the JSON body carries the parameters.

The Agents, Sessions and Environments APIs, which power Claude Managed Agents, are in beta and sit alongside these. List endpoints such as GET /v1/models return results in pages. You pass a limit and a page cursor, and each response carries a data array plus a next_page cursor that is null once you reach the end.

2. The headers a raw HTTP call must carry

Without the right headers, a request with a valid body is still rejected. A direct integration, such as a curl script, a language with no official SDK, or an HTTP client you wrote yourself, has to send three things on every call. First, a credential, normally your Console API key in x-api-key. Second, anthropic-version with a dated value such as 2023-06-01. Third, content-type: application/json. Leave out anthropic-version and the request fails even though the key is fine. That header pins the API behaviour your code was written against, as explained in [API versions and feature classifications (beta vs GA)](lesson:2.2).

คุณสามารถส่งข้อมูลประจำตัวเป็นการอนุญาต: ผู้<token>ถือแทน x-api-key แบบฟอร์มผู้ถือยังเป็นวิธีการส่งโทเค็นของ Workload Identity Federation ที่มีอายุการใช้งานสั้นในขณะที่ x-api-key ยังคงได้รับการสนับสนุนให้เป็นแบบดั้งเดิมสถานการณ์การสอบยังคงใช้ชุดคลาสสิก: x-api-key, anthropic-version และ content-type

Moving a raw call into an SDK turns those headers from per-request code into client configuration. You hand the credential to the client once, delete the three header lines from every call site, and keep only anthropic-workspace-id when your key spans several workspaces. A migrated script that still sets anthropic-version by hand is carrying a line the client already owns.

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Exam Trap: A raw HTTP call only needs an API key and a JSON content type, and the API version is implied by the model. (ทำไมถึงผิด): anthropic-version is required on every request. The SDKs hide this because they add it automatically, along with the authentication and content-type headers.

Without the right headers, a request with a valid body is still rejected. A direct integration, such as a curl script, a language with no official SDK, or an HTTP client you wrote yourself, has to send three things on every call. First, a credential, normally your Console API key in x-api-key. Second, anthropic-version with a dated value such as 2023-06-01. Third, content-type: application/json. Leave out anthropic-version and the request fails even though the key is fine. That header pins the API behaviour your code was written against, as explained in [API versions and feature classifications (beta vs GA)](lesson:2.2).

You can send the credential as Authorization: Bearer instead of x-api-key. The Bearer form is also how short-lived Workload Identity Federation tokens are sent, while x-api-key remains supported as the legacy fallback. Exam scenarios still use the classic set: x-api-key, anthropic-version and content-type.

Moving a raw call into an SDK turns those headers from per-request code into client configuration. You hand the credential to the client once, delete the three header lines from every call site, and keep only anthropic-workspace-id when your key spans several workspaces. A migrated script that still sets anthropic-version by hand is carrying a line the client already owns.

Responses also report which organization and workspace the credential resolved to, in anthropic-organization-id and anthropic-workspace-id. The Python and TypeScript SDKs expose the ID as _request_id on the response object. To read other headers, use with_raw_response.

Failures come back as JSON in a single, fixed shape. The top-level type is error, and the error object holds a machine-readable type and a human-readable message. The same request ID is repeated in the body as request_id, so a logged error body is enough to trace the call. Which status codes are worth retrying is covered in [API error types and recovery](lesson:4.1). On this page, the point is that every failure has this shape, and that the SDKs turn it into typed exceptions such as anthropic.NotFoundError rather than handing you raw JSON.

Request bodies have a size limit that depends on the endpoint. Messages and Token Counting accept up to 32 MB, Message Batches up to 256 MB and the Files API up to 500 MB. A request over its limit fails with 413 request_too_large before it reaches the API servers. If an application embeds large documents directly in a Messages request, it can hit this limit, which is a reason to upload those documents through the Files API instead.
