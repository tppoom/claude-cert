1. โครงสร้างของ Messages Request และ Response

Messages API ช่วยให้คุณเข้าถึง Model ได้โดยตรง และเป็น Endpoint หลักสำหรับสร้าง Agent Loop ของคุณเอง ในแต่ละ Call จะประกอบด้วย 3 ส่วนสำคัญที่จำเป็นต้องส่งเสมอ: model, max_tokens (เพดานจำกัดความยาว Token ของคำตอบ) และ messages list ที่แต่ละ Entry ต้องระบุ role (user หรือ assistant) พร้อมกับ content สำหรับ Instruction กลางที่ต้องการให้มีผลตลอดการสนทนา ให้ใส่ไว้ในฟิลด์ระดับบนสุดอย่าง system นอก List ดังกล่าว

Response ที่ได้กลับมาจะเป็น Assistant Message 1 ข้อความ ซึ่ง content จะเป็น Array ของ Typed Blocks ไม่ใช่ String ธรรมดา หากเป็นคำตอบทั่วไปจะเป็น Text Block เดี่ยวๆ แต่ Array นี้ยังสามารถบรรจุ tool_use blocks และ thinking blocks ได้ด้วย ดังนั้นโค้ดที่อ่านค่า content[0].text ตรงๆ จะพังทันทีเมื่อเปิดใช้ฟีเจอร์เหล่านั้น นอกจากนี้ยังมีอีก 2 ฟิลด์สำคัญที่ใช้สำหรับ Control Flow ในโค้ด: stop_reason ใช้บอกเหตุผลที่การ Generate สิ้นสุดลง (end_turn, max_tokens, stop_sequence, tool_use หรือ refusal) และ usage ที่รายงาน input_tokens กับ output_tokens สำหรับคำนวณ Context Size และคิดค่าบริการ

The Messages API gives you direct access to the model, and it is the surface you use when you want to write your own agent loop. Each call is one request with three required parts: a model, a max_tokens ceiling on the reply, and a messages list in which every entry has a role (user or assistant) and some content. Instructions that should hold from the first turn go in the top-level system field, outside the list.

The reply is one assistant message. Its content is an array of typed blocks, not a string. A plain answer is a single text block. The same array can also hold tool_use blocks and thinking blocks, so code that reads content[0].text will break once you turn those features on. Two other fields carry the facts your code branches on. stop_reason says why generation stopped: end_turn, max_tokens, stop_sequence, tool_use or refusal. usage reports input_tokens and output_tokens, which is where your billing and context-size numbers come from.

A stop_reason of max_tokens means the reply was cut off at your ceiling. It is not a finished answer. With refusal, the response also includes a stop_details object that names the policy category behind the refusal, so you can log it or tell the user why.

เนื่องจากคุณเป็นผู้จัดการ History เอง คุณจึงสามารถปรับแต่งสิ่งต่างๆ ได้ เช่น Assistant Turn ไม่จำเป็นต้องมาจาก Claude เสมอไป การสร้าง Synthetic Few-shot Exchange ก็ถือเป็น Input ที่ถูกต้อง ใน Model รุ่นเก่าอย่าง Claude Sonnet 4.5 การใส่ Assistant Message ไว้ท้ายสุดจะทำงานเป็น Prefill เพื่อให้ Claude ตอบต่อจากจุดนั้น (เช่น Prefill ด้วย 'The answer is' คู่กับ max_tokens: 1 จะได้ตัวอักษรชอยส์ตัวเดียว) แต่ห้ามใช้ Pattern นี้กับโค้ดใหม่เด็ดขาด เพราะ Claude Opus 4.6 ปฏิเสธ Prefilled Assistant Turn แล้ว และ Migration Checklist ของ Opus 5.5 ก็ระบุให้ตัดออกอย่างชัดเจน สำหรับ Model ยุคใหม่อย่าง Claude Opus 5.5 และ Sonnet 5.5 คุณสามารถเพิ่มข้อความ role: "system" หลัง User Turn เพื่อแทรก Instruction ระหว่างทางได้ แต่ข้อความนี้ต้องไม่อยู่เป็น Entry แรกใน messages

Prompt Caching ช่วยนำ History ที่ต้องส่งซ้ำๆ กลับมาใช้ใหม่ การใส่ cache_control Marker บน Content Block จะเป็นการตั้ง Cache Breakpoint ซึ่งทุกอย่างตั้งแต่ต้นจนถึง Block นั้นจะกลายเป็น Reusable Prefix ในส่วน usage ของ Response ตัว cache_read_input_tokens จะนับ Token ที่อ่านจาก Cached Prefix นั้น ส่วน cache_creation_input_tokens จะนับ Token ที่เพิ่งถูกเขียนลง Cache ใหม่ หากจำนวน Read ค้างอยู่ที่ 0 เสมอ แสดงว่า Prefix ไม่เคยซ้ำกันเลย

การส่ง Full History ซ้ำทุกครั้งคือเหตุผลที่ทำให้ [Prompt Caching](lesson:5.4) คุ้มค่า แต่มันมีข้อแม้สำคัญในการสร้าง Request: ตัว Prefix ต้องเหมือนกันแบบ Byte-identical เพราะ Cache Key เกิดจาก Hash ของ Prompt จนถึง Breakpoint หากมีสิ่งใดเปลี่ยนแปลงก่อนถึงจุดนั้น เช่น Timestamp ใน System Prompt, การเรียงลำดับ Tool List ใหม่ หรือการแก้ไขเทิร์นก่อนหน้า จะทำให้เกิด Cache Miss ทันที ดังนั้นควรวางส่วนที่เปลี่ยนแปลงบ่อยไว้ท้ายสุดเสมอ ส่วน Mid-conversation System Message จะถูก Append ต่อท้าย History จึงไม่กระทบ Cached Prefix ที่อยู่ข้างหน้า

อายุของ Cache ถูกกำหนดผ่าน Marker โดยค่าเริ่มต้นคือ 5 นาที (TTL จะถูกรีเฟรชฟรีทุกครั้งที่มีการเรียกใช้) และเริ่มนับตั้งแต่เริ่ม Request ดังนั้น Response แบบ Streaming ที่ใช้เวลานานจะกินเวลา Cache ไปด้วย หากระบุ "ttl": "1h" ใน cache_control จะขอ Cache อายุ 1 ชั่วโมงแทน

ทั้งนี้ การ Write Cache จะมีราคาสูงกว่าปกติ: เพิ่มขึ้น 25% สำหรับแบบ 5 นาที และ 2 เท่าของ Base Input Price สำหรับแบบ 1 ชั่วโมง ซึ่ง Cache แบบยาวจะคุ้มค่า เมื่อ Request เข้ามาห่างกันเกิน 5 นาที หรือ Response ใช้เวลาประมวลผลนานจนเกิน Window ปกติ

The API has no session, so your application is the conversation store. After each reply, append the assistant message to your list, append the next user turn, and send the whole list. Data access works the same way: anything Claude should be able to see in turn 7 (a document, a screenshot, a tool result from turn 2) has to be in the turn 7 request.

Since you write the history yourself, you can put things in it. Assistant turns don't have to come from Claude: a synthetic few-shot exchange is valid input. On older models such as Claude Sonnet 4.5, an assistant message in the last position works as a prefill, and Claude continues from where it ends. Pair a prefill of The answer is (with max_tokens: 1 and you get back a single multiple-choice letter. Don't build new code on that pattern: Claude Opus 4.6 already rejects prefilled assistant turns, and the Opus 5.5 migration checklist says to remove them. On recent models such as Claude Opus 5.5 and Sonnet 5.5, you can instead add a role: "system" message after a user turn to bring in an instruction partway through. It cannot be the first entry in messages.

Prompt caching reuses work across those resent histories. A cache_control marker on a content block sets a cache breakpoint: everything up to and including that block is the reusable prefix. In the response's usage, cache_read_input_tokens counts tokens served from that cached prefix, and cache_creation_input_tokens counts tokens newly written to it. A read count stuck at zero means the prefix never repeats.

Resending the full history on every call is what makes [prompt caching](lesson:5.4) worth using, and it puts one requirement on how you build requests: the prefix has to stay byte-identical. The cache key is a hash of the prompt up to the breakpoint, so anything that changes early in the request, like a timestamp in the system prompt, a reordered tool list or an edited earlier turn, produces a new key and a cache miss. Put changing content at the end. A mid-conversation system message is appended to the end of the history, so it leaves the cached prefix before it intact.

How long an entry survives is set on the marker. The default lifetime is 5 minutes, refreshed at no extra cost each time the entry is used, and it is measured from the start of the request, so a slow streamed response eats into it. Adding "ttl": "1h" to cache_control requests a one-hour entry instead. Writes cost more than ordinary input: 25% extra for the 5-minute entry and 2x the base input price for the 1-hour one. The longer entry pays for itself when requests arrive more than five minutes apart or responses run long enough to outlast the window.

Tool use runs on the same stateless request cycle. Claude never runs anything itself. When it wants a tool, the response has stop_reason: "tool_use" and one or more tool_use blocks, each with a tool name and a JSON object of arguments. Your code runs the operation and sends the output back as tool_result blocks in a new user message. That message goes at the end of the full history, after the assistant turn that asked for the tool. Keep looping while stop_reason is tool_use. Any other stop reason ends the loop. Writing the tool schemas themselves is covered in [Tool implementation](lesson:8.1).

Server tools are different. For web_search, web_fetch, code_execution and tool_search, Anthropic runs the code, and you never build a tool_result. The response shows server_tool_use blocks for what ran. That server-side loop has an iteration cap. When it hits the cap, the response comes back with stop_reason: "pause_turn", and you continue by sending the conversation again with the paused response included.

[Extended and adaptive thinking](lesson:5.3) adds thinking blocks to the assistant's content, and each one carries a signature. In a tool loop, send those blocks back exactly as you received them, including blocks whose thinking text is empty. The safe way is to append the assistant message as you received it. Don't filter its blocks by type and don't rebuild it from parts. The API rejects thinking blocks that have been edited, reordered or partly dropped with a 400 error.

On Claude Opus 5.5, thinking is not optional: every request runs with adaptive thinking, so any response can open with thinking blocks. Thinking tokens are billed as output tokens even when the thinking text is not returned, and they count against max_tokens, which stays a hard limit on thinking plus reply text. A ceiling tuned for a model that ran without thinking can now cut the answer short, and at xhigh or max effort the migration guide suggests starting at 64k.

Depth is controlled by the effort parameter rather than by a thinking budget. Set output_config={"effort": "medium"} (the Opus 5.5 default) and lower it to spend fewer tokens on thinking. The old thinking: {"type": "enabled", "budget_tokens": N} form is replaced by thinking: {"type": "adaptive"} plus effort, or by no thinking field at all. On models that still use manual extended thinking, the budget counts toward max_tokens too. What you see is also a setting: thinking.display defaults to "omitted", so thinking blocks arrive with an empty thinking field and a signature. Set "summarized" to receive readable summaries, and treat the field as display text only.

Set "stream": true and the response arrives as server-sent events, so a UI can show text as it is generated. Streaming also helps when nobody is watching. With a large max_tokens, the SDK requires streaming to avoid HTTP timeouts. Its accumulation helper streams under the hood and hands you the same complete Message object that messages.create() would.

Each kind of block streams a different delta. A text_delta carries a piece of text. Errors can also arrive mid-stream: overloaded_error is the streaming version of an HTTP 529. And because new event types may be added, a parser should skip unknown events rather than crash on them.

5. การส่ง Images และ Files: Inline, URL หรือ File ID

Image จะถูกส่งเป็น Content block รูปแบบหนึ่งใน User turn โดยระบุ source ได้ 3 แบบ: base64 (ฝัง Bytes ตรงๆ พร้อมระบุ media_type), url (ชี้ไปยัง URL ของรูปภาพ) หรือ file (อ้างอิงไฟล์ที่อัปโหลดไว้ล่วงหน้าผ่าน Files API) รองรับฟอร์แมต image/jpeg, image/png, image/gif และ image/webp ทั้งนี้ควรวาง Image block ไว้ก่อนหน้า Text ที่จะถามเสมอ

An image is just another content block in a user turn. Its source takes one of three types. base64 embeds the bytes and needs a media_type. url points at a hosted image. file refers to something already uploaded to the Files API. The supported formats are image/jpeg, image/png, image/gif and image/webp. Put the image block before the text that asks about it, as in this example.

Statelessness is what makes inline images expensive. Suppose a support tool sends two screenshots in turn 1 and asks about "the first image" in turn 3. Those screenshots have to be in the turn 3 request, so a base64 image is re-encoded and re-sent every turn. The Files API avoids that: upload once, get back a file_id, and from then on each request refers to the file by ID. The history still has to include the image, but now as a short reference. The same upload works for documents such as PDFs, and files can be listed, retrieved and deleted.

Which platform you buy Claude through is a decision about [data residency and platform choice](lesson:2.1). Once that is decided, your request code changes in specific ways. On Google Cloud's Agent Platform the body looks almost the same as a Messages API request, with two changes. The model moves out of the body and into the endpoint URL. The API version moves into the body as anthropic_version.

Model IDs also differ by platform. On Amazon Bedrock, for the models covered by its Opus 4.6-and-earlier guide, you pass an inference profile instead of the base model ID: a regional prefix plus the Bedrock ID, such as us.anthropic.claude-sonnet-4-5-20250929-v1:0, or the full inference-profile ARN. Model availability varies by region, and lifecycle dates on partner platforms are set by the partner, so the retirement date on Bedrock or Google Cloud can differ from the Claude API's. Some feature behaviour changes too. Prompt caches are isolated per workspace on the Claude API but per organization on Bedrock and Google Cloud.

The SDK client and the authentication change with the platform as well. For Bedrock models in the Opus 4.6-and-earlier guide, install anthropic[bedrock] and use AnthropicBedrock: it takes AWS keys or the default AWS credential providers, or a bearer token through the AWS_BEARER_TOKEN_BEDROCK environment variable. Opus 4.7 and later models run on Claude in Amazon Bedrock instead, through AnthropicBedrockMantle, which resolves credentials by the standard AWS precedence and uses IDs with an anthropic. prefix, such as anthropic.claude-opus-5-5. On Google Cloud, AnthropicVertex takes a project_id and a region, where global gives dynamic routing for maximum availability. Authenticate first, usually with gcloud auth application-default login.
