1. Message API เป็นตําแหน่งข้อมูล REST ที่พูด JSON

💡 แนวคิดหลักของหัวข้อนี้ (Core Concept)
  • ▸
    การเรียกใช้งาน Claude เป็น
  • ▸
    การเรียก REST ปกติ ดังนั้นแนวทางที่บริการอื่นของคุณใช้ก็สามารถนำมาใช้ได้เช่นกัน API ให้บริการจาก https://api.anthropic.com และคำขอสนทนาจะใช้ POST /v1/messages ทุกคำขอมีร่าง JSON พร้อม content-type: application/json, header anthropic-version เช่น 2023-06-01 และข้อมูลรับรองใน Authorization: Bearer <token> header เก่า x-api-key ยังสามารถใช้เป็นทางเลือกสำรองได้
📌 SDK อย่างเป็นทางการจะ ตั้งค่า headers
  • ▸
    สำหรับการยืนยันตัวตน รุ่น และประเภทเนื้อหาให้คุณ พวกมันยังเพิ่มคำขอและการตอบสนองที่มีประเภทกำหนดไว้ การลองใหม่ในตัว การสนับสนุนการสตรีม และการหมดเวลาของคำขอ ด้วยไคลเอนต์ HTTP ดิบ สิ่งเหล่านี้ทั้งหมด
  • ▸
    คุณต้องเขียน โค้ดเอง ส่วน header เดียวที่คุณยังต้องส่งด้วยตัวเองคือ anthropic-workspace-id และเฉพาะเมื่อคีย์ของคุณครอบคลุมมากกว่าหนึ่ง workspace
A Messages API response is a JSON object: content blocks, the stop reason and token usage json
การตอบกลับ Messages API คือออบเจ็กต์ JSON ซึ่งได้แก่ บล็อกเนื้อหา เหตุผลในการหยุด และ json การใช้โทเค็น
{
  "id": "msg_01XFDUDYJgAACzvnptvVoYEL",
  "type": "message",
  "role": "assistant",
  "content": [
    {
      "type": "text",
      "text": "Hello!"
    }
  ],
  "model": "claude-opus-5-5",
  "stop_reason": "end_turn",
  "stop_sequence": null,
  "usage": {
    "input_tokens": 12,
    "output_tokens": 6
  }
}
📌 เนื่องจาก API ไม่มีสถานะ
  • ▸
    การสนทนา บริการของคุณจึงต้องจัดเก็บไว้
  • ▸
    ไคลเอ็นต์: จะส่งประวัติทั้งหมดพร้อมกับทุกคําขอ ตามที่อธิบายไว้ใน 📖 Stateless Messages API (ไคลเอ็นต์ถือการสนทนา) (2.3) ในทางปฏิบัติ ให้เก็บอาร์เรย์ข้อความเป็น JSON แบบธรรมดา ซึ่งเป็นรายการของอ็อบเจกต์ {“role”, “content”} ในฐานข้อมูลของคุณเองหรือที่เก็บเซสชันที่คีย์ตาม
  • ▸
    การสนทนา โหลด ผนวกทัวร์ใหม่ของผู้ใช้ ส่ง
  • ▸
    จากนั้นผนวกเนื้อหาของผู้ช่วยและบันทึกอีกครั้ง ทัวร์ก่อนหน้านี้ไม่จําเป็นต้องมาจาก Claude
  • ▸
    ดังนั้นประวัติที่จัดเก็บไว้สามารถมีข้อความของผู้ช่วยสังเคราะห์ที่คุณเขียนเองได้
📌 ประวัติที่เก็บไว้จะเพิ่มขึ้นตาม
  • ▸
    แต่ละรอบ และขนาดของคำขอมีการจำกัด ข้อความและคำขอการนับโทเค็นสามารถมีขนาดได้สูงสุด 32 MB และสิ่งที่ใหญ่กว่าจะส่งกลับ 413 request_too_large การแชทที่มีอายุยาวซึ่งบันทึกทุกรอบตลอดไป
  • ▸
    ในที่สุดจะถึงขีดจำกัดนั้น
  • ▸
    ดังนั้นให้ตัดสินใจว่าประวัติจะถูกตัดอย่างไรก่อนที่มันจะเกิดขึ้น
📌 การเรียก REST ใช้เวลาส่วนใหญ่ไปกับการรอเครือข่าย และการเขียนโปรแกรมแบบอะซิงโครนัสคือวิธีที่โปรแกรมใช้เวลารอนั้นทำงานอย่างอื่น
  • ▸
    แทนที่จะค้างอยู่ ด้วยไคลเอนต์แบบ async การใช้ await client.messages.create(...) จะระงับเฉพาะคอร์รัวทีนปัจจุบัน; วงจรเหตุการณ์จะรันคอร์รัวทีนอื่น ๆ จนกว่าการตอบกลับจะมาถึง การร้องขอและ Message ที่ส่งกลับเหมือนกับการเรียกแบบบล็อก
  • ▸
    ดังนั้นการเปลี่ยนแปลงนั้นอยู่ที่วิธี
  • ▸
    การจัดการ: รอ ไม่ใช่ที่ JSON
📌 การแทรกแซงทำให้เกิดอันตรายที่โค้ดการบล็อกไม่มี Coroutines สามารถแทรกแซงได้
  • ▸
    ดังนั้น การเรียก API บนเครื่องบินหลายครั้งที่ต่อท้ายรายการหรือ dict ที่แชร์รายการเดียวอาจทำให้รายการเสียหายได้ ซึ่งเป็นการแข่งขันสถานะที่แชร์แบบไม่แน่นอนแบบเดียวกับที่เธรดเป็นสาเหตุ ให้แต่ละโครูทีนส่งคืนผลลัพธ์ของตัวเองแล้วรวมเข้าด้วยกันในภายหลัง
  • ▸
    แทนที่จะเปลี่ยนสถานะที่แชร์จากภายในการโทร
  • ▸
    นอกจากนี้ API ยังมีการทำงานแบบอะซิงโครนัสที่ระดับตำแหน่งข้อมูลอีกด้วย โดย Message Batches API ยอมรับคำขอทันทีและประมวลผลในภายหลัง
  • ▸
    ดังนั้น การตอบสนอง HTTP จะยอมรับเฉพาะการส่งเท่านั้น
⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
The API remembers earlier turns, so each request only needs the newest user message. (ทำไมถึงผิด): The Messages API is stateless. Your service has to store the history and send all of it on every request.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Calling Claude is an ordinary REST call, so the conventions your other services already follow carry over. The API is served from https://api.anthropic.com, and a conversational request is POST /v1/messages. Every request has a JSON body with content-type: application/json, an anthropic-version header such as 2023-06-01, and credentials in Authorization: Bearer <token>. The older x-api-key header still works as a fallback.

The official SDKs set the authentication, version and content-type headers for you. They also add typed requests and responses, built-in retries, streaming support and request timeouts. With a raw HTTP client, all of that is your code to write. The one header you still pass yourself is anthropic-workspace-id, and only when your key covers more than one workspace.

Because the API keeps no conversation state, your service has to store it. The client sends the whole history with every request, as covered in [Stateless Messages API (client holds the conversation)](lesson:2.3). In practice, keep the messages array as plain JSON, a list of {"role", "content"} objects, in your own database or session store keyed by conversation. Load it, append the user's new turn, send it, then append the assistant's content and save it again. Earlier turns don't have to come from Claude, so a stored history can include synthetic assistant messages you wrote yourself.

That stored history grows with every turn, and request size is capped. Messages and Token Counting requests can be at most 32 MB, and anything larger returns 413 request_too_large. A long-lived chat that saves every turn forever will eventually hit that limit, so decide how history is trimmed before it does.

A REST call spends almost all of its time waiting on the network, and asynchronous programming is how a program uses that wait for other work instead of freezing. With the async client, await client.messages.create(...) suspends only the current coroutine; the event loop runs other coroutines until the response arrives. The request and the returned Message are identical to a blocking call, so the change is in how the waiting is scheduled, not in the JSON.

Interleaving brings a hazard that blocking code doesn't have. Coroutines can interleave, so several in-flight API calls that append to one shared list or dict can corrupt it, the same shared-mutable-state race that threads cause. Have each coroutine return its own result and combine them afterwards, rather than mutating shared state from inside the call. The API also offers asynchronous work at the endpoint level: the Message Batches API accepts requests now and processes them later, so the HTTP response only acknowledges the submission.

The simplest pattern is a blocking call. client.messages.create(...) on the synchronous Anthropic client waits until Claude has finished, then returns the full Message. That suits scripts, CLI tools and worker processes that handle one request at a time, where nothing else needs the thread while the request is in flight.

A service built on an event loop needs something else, because a blocking call there holds up every other coroutine while one request waits on the network. The Python SDK's AsyncAnthropic client has the same messages.create method, and you await it inside an async function. The request body and the returned Message are unchanged. The only difference is that your code yields while it waits. The async client can also use an aiohttp HTTP backend instead of the default one when you need better async throughput.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Streaming sits between a blocking call and a background job. The response arrives in pieces over one open HTTP connection, as covered in [Streaming over server-sent events](lesson:5.2). It wins in two situations. In the first, a person is waiting, so printing text as it arrives makes the response feel fast. In the second, the response is long enough that one silent connection would hit an HTTP timeout. For that second case the SDK requires streaming, even when you don't want partial text.

Streaming also changes how failures reach you. A problem that a blocking call reports as an HTTP status can arrive mid-stream as an error event. Overload is the common case: an overloaded_error event where a non-streaming call would get HTTP 529. Error handling written only around the initial HTTP response will miss it. The Python SDK offers both sync and async streams, so streaming works with either client from the previous section.

Submit-and-poll decouples sending work from collecting results. You submit a job, get back an ID, and check its status later. The Message Batches API, which handles large volumes of requests asynchronously at lower cost, is the standard example. Its pricing and limits are covered in [Message Batches API and realtime vs batch](lesson:2.3). For the code you write, what matters is the shape: a batch starts with processing_status set to in_progress and moves to ended once every request has finished and results are ready.

Polling has a cost: the job ID has to outlive the process that submitted it. Store the batch id along with whatever you need to match results back to your records. The poller can then run as a separate scheduled job, and a restart doesn't lose the work. Choose this pattern when throughput and cost matter more than latency, for example nightly classification or evaluation runs. Don't choose it when a user is waiting for the answer.
