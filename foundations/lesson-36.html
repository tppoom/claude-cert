1. Least privilege: limit how much damage a mistake can do

รั้วป้องกันทําให้การโจมตีมีแนวโน้มที่จะประสบความสําเร็จน้อยลง การติดตั้งที่ปลอดภัยตามการออกแบบจะถือว่าการโจมตีบางครั้งจะประสบความสําเร็จอยู่ดี และจํากัดสิ่งที่พวกเขาสามารถทําได้ แนวทางของ Anthropic กล่าวไว้อย่างตรงไปตรงมา: อย่าให้ความลับกับ Claude ที่มันไม่ต้องการ เรียกใช้เครื่องมือใน Sandbox และให้สิทธิ์การเข้าถึงในขอบเขตที่แคบที่สุดเท่าที่จะทําได้

ใน Claude Code และ Agent SDK สิทธิพิเศษขั้นต่ำจะแสดงผ่านกฎการอนุญาต อนุญาตให้กฎเรียกใช้เครื่องมือโดยไม่ต้องถาม ถามกฎขอคำยืนยันทุกครั้ง กฎการปฏิเสธจะบล็อกเครื่องมืออย่างสมบูรณ์ กฎสามารถตั้งชื่อเครื่องมือทั้งหมด (Bash, WebFetch, Read) หรือการใช้งานเฉพาะอย่างใดอย่างหนึ่ง (Read(./.env), WebFetch(domain:example.com)) และองค์กรต่างๆ ก็สามารถส่งนโยบายไปยังผู้ใช้ทุกคนได้

Guardrails make an attack less likely to succeed. Secure-by-design deployment assumes some attacks will succeed anyway and limits what they can do. Anthropic's guidance says it directly: give Claude no secrets it doesn't need, run tools in sandboxes, and scope permissions as narrowly as you can.

In Claude Code and the Agent SDK, least privilege is expressed through permission rules. Allow rules run a tool without asking. Ask rules ask for confirmation every time. Deny rules block the tool completely. Rules can name a whole tool (Bash, WebFetch, Read) or one specific use of it (Read(./.env), WebFetch(domain:example.com)), and organizations can push policies to every user.

Permission rules are a gate, not a sandbox. Claude Code parses each Bash command and matches it against your rules. Apart from a few built-in checks, it does not judge whether a command is dangerous from its effects. To contain what a command can actually do, use OS-level sandboxing.

ด้วยพร็อกซีการป้อนข้อมูลประจําตัว ความลับจะไม่เข้าสู่สภาพแวดล้อมของเอเจนต์เลย การติดตั้งแบบอ่านอย่างเดียวยังคงอนุญาตให้เอเจนต์อ่านได้

EN: With a credential-injecting proxy, the secret never enters the agent's environment at all. A read-only mount still lets the agent read it.
““เจ้าหน้าที่ไม่เคยเห็นข้อมูลประจำตัวจริง””
EN: “The agent never sees the actual credentials”
🔗 แหล่งอ้างอิง: https://code.claude.com/docs/en/agent-sdk/secure-deployment

For an agent, identity and access management mostly means keeping secrets out of its reach

Anthropic's secure-deployment guide recommends running a proxy outside the agent's environment, such as Envoy with its credential_injector filter

The proxy validates each request, enforces a domain allowlist, adds the credential and logs the traffic

The agent never sees the credential Credentials live in one secure place instead of being copied to every agent, and you get an audit trail of every request

On the cloud side, give the agent's service account minimal IAM permissions, and block all egress except to the proxy.

For an agent, identity and access management mostly means keeping secrets out of its reach. Anthropic's secure-deployment guide recommends running a proxy outside the agent's environment, such as Envoy with its credential_injector filter. The proxy validates each request, enforces a domain allowlist, adds the credential and logs the traffic. The agent never sees the credential. Credentials live in one secure place instead of being copied to every agent, and you get an audit trail of every request. On the cloud side, give the agent's service account minimal IAM permissions, and block all egress except to the proxy.

Isolation backs this up. A hardened container drops privileges and mounts only what the agent needs:

Access management also covers the people and workloads that call the Claude API. In the Claude Console, a key's type decides who it acts as:

- A personal key acts as you, with your roles and permissions. - A service account key acts as a service account. - A workspace key is legacy. It acts as no one, and identity-backed keys or Workload Identity Federation are preferred.

Personal and service account keys are identity-backed. When the user or service account is removed from the organization, the key stops working, so keys don't outlive the people or workloads that own them. Use a personal key for your own development and scripts. For shared or automated workloads such as CI and production services, an organization admin creates a service account so the workload has its own identity. Don't share one person's key.

A key can also be scoped to a single workspace, where it works only in that workspace. For production workloads on cloud platforms or CI/CD, Workload Identity Federation exchanges your identity provider's token for a short-lived token, which removes the static secret.

Three habits keep the damage small if a key leaks:

- Rotate on a schedule, for example every 90 days, by creating new keys and deactivating old ones. Don't wait for a leak. - Use separate keys per environment (development, testing, production), so you can disable only the compromised one. - Scan for committed secrets. Turn on secret scanning in your source-control provider, use SAST tools such as Gitleaks, and put scanning in CI/CD so a secret is caught before it reaches the main branch.

4. Privacy: data retention and zero data retention

Privacy by design starts with the prompt

The guardrail examples on Anthropic's jailbreak-mitigation page write data protection directly into the system prompt, for example "Protect client privacy; never disclose personal or financial data." The other half is the data's lifecycle: what the platform keeps, and for how long.

การลดข้อมูลให้เหลือน้อยที่สุดเป็นหลักการพื้นฐาน Anthropic เก็บเฉพาะสิ่งที่จําเป็นทางเทคนิคสําหรับการทํางานของฟีเจอร์ และเนื้อหาการสนทนา (การแจ้งเตือนของคุณและผลลัพธ์ของ Claude) จะไม่ถูกเก็บไว้ตามค่าเริ่มต้น ข้อมูล API ที่เก็บไว้จะไม่ถูกใช้สําหรับการฝึกอบรมโมเดลโดยไม่ได้รับอนุญาตจากคุณโดยชัดแจ้ง

  • ▸
    ZDR ถูกเปิดใช้งานต่อองค์กร องค์กรใหม่ต้องเปิดใช้งานแยกต่างหาก
  • ▸
    คุณสมบัติที่ระบุว่า “ไม่” ในตารางคุณสมบัติ เช่น การดําเนินการโค้ด ไม่ครอบคลุมแม้ว่าจะใช้ /v1/messages ก็ตาม
  • ▸
    บนแพลตฟอร์มเอเจนต์ของ Amazon Bedrock และ Google Cloud ผู้ให้บริการคลาวด์เป็นตัวประมวลผลข้อมูล ดังนั้นการควบคุมของพวกเขาจึงมีผลแทน

Privacy by design starts with the prompt. The guardrail examples on Anthropic's jailbreak-mitigation page write data protection directly into the system prompt, for example "Protect client privacy; never disclose personal or financial data." The other half is the data's lifecycle: what the platform keeps, and for how long.

Data minimization is the underlying principle. Anthropic keeps only what is technically necessary for a feature to work, and conversation content (your prompts and Claude's outputs) is not retained by default. Retained API data is never used for model training without your express permission.

For stricter needs, Anthropic offers two data handling arrangements for the Claude API: zero data retention (ZDR) and HIPAA readiness. They are separate arrangements, and the feature eligibility table lists which API features each one covers. Under ZDR, Anthropic does not store prompts or responses at rest once the response is returned. Plan around a few details:

- ZDR is enabled per organization. A new organization needs it enabled separately. - Features marked "No" in the eligibility table, such as code execution, are not covered even though they use /v1/messages. - On Amazon Bedrock and Google Cloud's Agent Platform, the cloud provider is the data processor, so their controls apply instead.

Some retention sits outside both arrangements. The Activity Feed retains data for 6 years, and claude.ai chat, file and project content follows your organization's retention policy. Check which model applies before you promise users that data is not stored.
