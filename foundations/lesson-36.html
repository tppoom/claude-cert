1. Least privilege: จำกัดขอบเขตความเสียหายหากเกิดข้อผิดพลาด

Guardrails ช่วยลดโอกาสที่การโจมตีจะสำเร็จ แต่แนวคิดแบบ Secure-by-design จะตั้งสมมติฐานว่าการโจมตีอาจหลุดรอดเข้ามาได้เสมอ จึงมุ่งจำกัดสิ่งที่ตัวโจมตีจะทำได้ Anthropic แนะนำไว้อย่างชัดเจนว่า: ห้ามส่ง Secrets ใดๆ ที่ไม่จำเป็นให้กับ Claude, รัน Tools ทั้งหมดใน Sandbox เสมอ และจำกัดขอบเขต Permissions ให้แคบที่สุดเท่าที่เป็นไปได้

สำหรับ Claude Code และ Agent SDK หลักการ Least privilege จะถูกควบคุมผ่าน Permission Rules โดย Allow rules จะรัน Tool ทันทีโดยไม่ต้องถาม, Ask rules จะถามยืนยันทุกครั้ง และ Deny rules จะบล็อก Tool นั้นอย่างสมบูรณ์ ซึ่ง Rules สามารถระบุครอบคลุมทั้ง Tool (เช่น Bash, WebFetch, Read) หรือเจาะจงเฉพาะ Parameter ที่เรียกใช้ (เช่น Read(./.env), WebFetch(domain:example.com)) และองค์กรยังสามารถ Push Policies ไปยังผู้ใช้ทุกคนได้ด้วย

A permission policy that allows build and commit commands but denies git push json
นโยบายการอนุญาตที่อนุญาตให้สร้างและคอมมิตคำสั่ง แต่ปฏิเสธ git push json
{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Bash(git push *)"
    ]
  }
}

Permission rules ทำหน้าที่เป็นเพียง Gate ไม่ใช่ Sandbox โดย Claude Code จะ Parse คำสั่ง Bash แล้วนำไป Match กับ Rules ที่ตั้งไว้ ซึ่งนอกจาก Built-in checks พื้นฐานสองสามอย่างแล้ว ระบบไม่ได้วิเคราะห์เลยว่าผลลัพธ์ของการรันคำสั่งจริงจะเป็นอันตรายหรือไม่ หากต้องการจำกัดการกระทำของคำสั่งจริงๆ จำเป็นต้องใช้ OS-level sandboxing

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
A Bash deny rule or allowlist sandboxes the agent and contains what a command can do. (ทำไมถึงผิด): Permission rules match command text. Claude Code says this is a permission gate, not a sandbox; use OS-level sandboxing to restrict filesystem and network access.

Bash deny rule หรือ allowlist ช่วยทำ Sandboxing ให้กับ Agent และจำกัดสิ่งคำสั่งสามารถทำได้จริง? (ทำไมถึงผิด): ไม่จริง: Permission rules เป็นเพียง Gate ที่ตรวจจับ Pattern ของข้อความคำสั่ง (Text-matching) เท่านั้น ไม่ใช่ Sandbox ของระบบปฏิบัติการ หากต้องการจำกัดการเข้าถึง Filesystem และ Network จริงๆ ต้องใช้ OS-level sandboxing

Guardrails make an attack less likely to succeed. Secure-by-design deployment assumes some attacks will succeed anyway and limits what they can do. Anthropic's guidance says it directly: give Claude no secrets it doesn't need, run tools in sandboxes, and scope permissions as narrowly as you can.

In Claude Code and the Agent SDK, least privilege is expressed through permission rules. Allow rules run a tool without asking. Ask rules ask for confirmation every time. Deny rules block the tool completely. Rules can name a whole tool (Bash, WebFetch, Read) or one specific use of it (Read(./.env), WebFetch(domain:example.com)), and organizations can push policies to every user.

Wildcards are easy to write too broadly. The * matches whatever text is in its position, and a missing space changes the result:

Permission rules are a gate, not a sandbox. Claude Code parses each Bash command and matches it against your rules. Apart from a few built-in checks, it does not judge whether a command is dangerous from its effects. To contain what a command can actually do, use OS-level sandboxing.

2. Identity and access management: แยก Credentials ออกจากตัว Agent อย่างเด็ดขาด

💡 คำถามท้าทายความคิดก่อนอ่านเนื้อหา (Predict First Challenge)
✓ ตอบถูกแล้ว Predict

An agent has to call an authenticated external API. Which design gives the agent the least access to the credential?

คำแปลโจทย์:
Agent ต้องเรียก API ภายนอกที่ได้รับการตรวจสอบสิทธิ์ การออกแบบใดที่ทำให้ Agent เข้าถึงข้อมูลรับรองได้น้อยที่สุด
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Official Explanation (คำอธิบายเฉลย):

With a credential-injecting proxy, the secret never enters the agent's environment at all. A read-only mount still lets the agent read it.

คำแปลไทย:
ด้วยพร็อกซีการป้อนข้อมูลประจําตัว ความลับจะไม่เข้าสู่สภาพแวดล้อมของ Agent เลย การติดตั้งแบบอ่านอย่างเดียวยังคงอนุญาตให้ Agent อ่านได้
““The agent never sees the actual credentials””
คำแปล: “Agent ไม่เคยเห็นข้อมูลประจำตัวจริง”
🔗 Source: https://code.claude.com/docs/en/agent-sdk/secure-deployment
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage

สำหรับ Agent เรื่อง Identity and Access Management (IAM) หัวใจสำคัญคือการกันไม่ให้ Agent เข้าถึง Secrets ได้โดยตรง คำแนะนำด้านความปลอดภัยของ Anthropic ระบุให้รัน Proxy ไว้นอก Environment ของ Agent เช่น การใช้ Envoy ร่วมกับ credential_injector filter โดย Proxy จะคอย Validate ทุก Request, บังคับใช้ Domain allowlist, Inject credentials เข้าไป และ Log ทราฟฟิกทั้งหมด ทำให้ Agent ไม่เคยเห็น Credentials เลย Credentials จึงถูกเก็บไว้ที่ส่วนกลางอย่างปลอดภัย ไม่ต้องกระจายไปยังทุก Agent แถมยังมี Audit trail ตรวจสอบได้ครบถ้วน สำหรับฝั่ง Cloud ให้ตั้งค่า Service Account ของ Agent ด้วยสิทธิ์ IAM ที่ต่ำที่สุด และบล็อก Egress ทั้งหมด ยกเว้นปลายทางที่วิ่งไปยัง Proxy เท่านั้น

การทำ Isolation คือหัวใจสำคัญอีกชั้น โดย Hardened Container จะดรอปสิทธิ์ที่ไม่จำเป็นทิ้ง และ Mount เฉพาะสิ่งที่ Agent ต้องใช้เท่านั้น:

Option
Purpose
--cap-drop ALL
Removes Linux capabilities like NET_ADMIN and SYS_ADMIN that could enable privilege escalation
ตัด Linux capabilities ทั้งหมด เช่น NET_ADMIN และ SYS_ADMIN เพื่อป้องกันการทำ Privilege Escalation
--network none

Access management ยังครอบคลุมถึงผู้ใช้งานและ Workloads ที่เรียกใช้ Claude API อีกด้วย ซึ่งใน Claude Console ชนิดของ Key จะเป็นตัวระบุ Identity ว่ากำลังทำงานในฐานะใคร:

  • •
    Personal key ทำงานในฐานะตัวคุณ โดยได้รับ Roles และ Permissions ตามบัญชีของคุณ
  • •

  • •
    Workspace key เป็นแบบ Legacy ไม่ได้ผูกกับ Identity ใดๆ ปัจจุบันแนะนำให้เปลี่ยนไปใช้ Identity-backed keys หรือ Workload Identity Federation แทน

Personal และ Service account keys เป็นแบบ Identity-backed กล่าวคือเมื่อ User หรือ Service Account ถูกลบออกจาก Organization ตัว Key ก็จะหยุดทำงานทันที ป้องกันปัญหา Key ค้างหลังเจ้าของหรือ Workload ถูกยกเลิก ควรใช้ Personal key สำหรับการ Dev และรัน Script ส่วนตัว ส่วนงาน Shared หรือ Automated workloads เช่น CI และ Production services ให้ Organization Admin สร้าง Service Account ขึ้นมา เพื่อให้ Workload มี Identity ของตนเอง ห้ามแชร์ Key ส่วนตัวร่วมกันเด็ดขาด

นอกจากนี้ Key ยังสามารถ Scope ให้ใช้งานได้เฉพาะในระดับ Workspace เดียวได้ และสำหรับ Production workloads บน Cloud platforms หรือ CI/CD แนะนำให้ใช้ Workload Identity Federation แลก Identity Token เพื่อรับ Token แบบชั่วคราว (Short-lived token) ซึ่งช่วยขจัดความเสี่ยงจากการใช้ Static Secret ไปได้อย่างสิ้นเชิง

For an agent, identity and access management mostly means keeping secrets out of its reach. Anthropic's secure-deployment guide recommends running a proxy outside the agent's environment, such as Envoy with its credential_injector filter. The proxy validates each request, enforces a domain allowlist, adds the credential and logs the traffic. The agent never sees the credential. Credentials live in one secure place instead of being copied to every agent, and you get an audit trail of every request. On the cloud side, give the agent's service account minimal IAM permissions, and block all egress except to the proxy.

Isolation backs this up. A hardened container drops privileges and mounts only what the agent needs:

Access management also covers the people and workloads that call the Claude API. In the Claude Console, a key's type decides who it acts as:

- A personal key acts as you, with your roles and permissions. - A service account key acts as a service account. - A workspace key is legacy. It acts as no one, and identity-backed keys or Workload Identity Federation are preferred.

Personal and service account keys are identity-backed. When the user or service account is removed from the organization, the key stops working, so keys don't outlive the people or workloads that own them. Use a personal key for your own development and scripts. For shared or automated workloads such as CI and production services, an organization admin creates a service account so the workload has its own identity. Don't share one person's key.

A key can also be scoped to a single workspace, where it works only in that workspace. For production workloads on cloud platforms or CI/CD, Workload Identity Federation exchanges your identity provider's token for a short-lived token, which removes the static secret.

4. ความเป็นส่วนตัว: Data Retention และ Zero Data Retention (ZDR)

Privacy by Design เริ่มต้นที่ Prompt ตัวอย่าง Guardrails บนหน้า Jailbreak Mitigation ของ Anthropic ระบุให้เขียนข้อกำหนดการปกป้องข้อมูลลงใน System Prompt โดยตรง เช่น "Protect client privacy; never disclose personal or financial data." ส่วนอีกด้านคือ Data Lifecycle: ข้อมูลใดบ้างที่แพลตฟอร์มจะเก็บไว้ และเก็บไว้นานเท่าใด

Data Minimization คือหลักการพื้นฐาน Anthropic จัดเก็บเฉพาะข้อมูลที่จำเป็นทางเทคนิคเพื่อให้ฟีเจอร์ทำงานได้เท่านั้น และเนื้อหาบทสนทนา (Prompts และ Claude's Outputs) จะไม่ถูกเก็บไว้เป็นค่าเริ่มต้น (Not retained by default) ข้อมูล API ที่ถูกเก็บไว้จะไม่ถูกนำไปใช้เทรนโมเดลโดยเด็ดขาด เว้นแต่จะได้รับอนุญาตอย่างชัดเจน

สำหรับ Use Case ที่ต้องการความปลอดภัยเข้มงวดเป็นพิเศษ Anthropic มีข้อตกลงการจัดการข้อมูล 2 รูปแบบ สำหรับ Claude API ได้แก่ Zero Data Retention (ZDR) และ HIPAA Readiness ซึ่งเป็นข้อตกลงคนละส่วนกัน และตาราง Feature Eligibility จะระบุว่าแต่ละข้อตกลงครอบคลุม API Features ใดบ้าง ภายใต้ ZDR นั้น Anthropic จะไม่เก็บ Prompts หรือ Responses ในระดับ Data at Rest เลยหลังจากส่ง Response คืนไปแล้ว แต่ต้องวางแผนรับมือเงื่อนไขต่อไปนี้:

  • •
    ZDR เปิดใช้งานแยกราย Organization หากเปิด Organization ใหม่จะต้องตั้งค่าเปิดใช้งานแยกต่างหาก
  • •

  • •
    บน Amazon Bedrock และ Google Cloud's Agent Platform ตัว Cloud Provider จะทำหน้าที่เป็น Data Processor จึงต้องยึดตาม Data Controls ของ Provider รายนั้นๆ แทน

Privacy by design starts with the prompt. The guardrail examples on Anthropic's jailbreak-mitigation page write data protection directly into the system prompt, for example "Protect client privacy; never disclose personal or financial data." The other half is the data's lifecycle: what the platform keeps, and for how long.

Data minimization is the underlying principle. Anthropic keeps only what is technically necessary for a feature to work, and conversation content (your prompts and Claude's outputs) is not retained by default. Retained API data is never used for model training without your express permission.

For stricter needs, Anthropic offers two data handling arrangements for the Claude API: zero data retention (ZDR) and HIPAA readiness. They are separate arrangements, and the feature eligibility table lists which API features each one covers. Under ZDR, Anthropic does not store prompts or responses at rest once the response is returned. Plan around a few details:

- ZDR is enabled per organization. A new organization needs it enabled separately. - Features marked "No" in the eligibility table, such as code execution, are not covered even though they use /v1/messages. - On Amazon Bedrock and Google Cloud's Agent Platform, the cloud provider is the data processor, so their controls apply instead.

Some retention sits outside both arrangements. The Activity Feed retains data for 6 years, and claude.ai chat, file and project content follows your organization's retention policy. Check which model applies before you promise users that data is not stored.

อ่านเนื้อหา ↗
  • •
    การทำ Isolation คือหัวใจสำคัญอีกชั้น โดย Hardened Container จะดรอปสิทธิ์ที่ไม่จำเป็นทิ้ง และ Mount เฉพาะสิ่งที่ Agent ต้องใช้เท่านั้น:
  • •
    Access management ยังครอบคลุมถึงผู้ใช้งานและ Workloads ที่เรียกใช้ Claude API อีกด้วย ซึ่งใน Claude Console ชนิดของ Key จะเป็นตัวระบุ Identity ว่ากำลังทำงานในฐานะใคร:
  • •
    สำหรับ Agent เรื่อง Identity and Access Management (IAM) หัวใจสำคัญคือการกันไม่ให้ Agent เข้าถึง Secrets ได้โดยตรง คำแนะนำด้านความปลอดภัยของ Anthropic ระบุให้รัน Proxy ไว้นอก Environment ของ Agent เช่น การใช้ Envoy ร่วมกับ credential_injector filter โดย Proxy จะคอย Validate ทุก Request, บังคับใช้ Domain allowlist, Inject credentials เข้าไป และ Log ทราฟฟิกทั้งหมด ทำให้ Agent ไม่เคยเห็น Credentials เลย Credentials จึงถูกเก็บไว้ที่ส่วนกลางอย่างปลอดภัย ไม่ต้องกระจายไปยังทุก Agent แถมยังมี Audit trail ตรวจสอบได้ครบถ้วน สำหรับฝั่ง Cloud ให้ตั้งค่า Service Account ของ Agent ด้วยสิทธิ์ IAM ที่ต่ำที่สุด และบล็อก Egress ทั้งหมด ยกเว้นปลายทางที่วิ่งไปยัง Proxy เท่านั้น

#3 3. การจัดเก็บ, หมุนเวียน (Rotate) และสแกนหา API Keys

อ่านเนื้อหา ↗
  • •
    หาก Claude API key หลุดขึ้น Public Repository ทาง Anthropic จะ Deactivate Key ให้อัตโนมัติและส่งอีเมลแจ้งเตือนเจ้าของทันที
  • •
    Agents ยังอาจทำ Secrets อื่นรั่วไหลได้เช่นกัน ไฟล์อย่าง.env, ~/.aws/credentials, ~/.kube/config และ *.pem ต้องไม่ถูก Mount เข้าไปยังจุดที่ Agent สามารถอ่านได้เด็ดขาด
  • •
    Claude API key ต้องได้รับการดูแลอย่างเข้มงวดเช่นเดียวกัน แนวทางของ Anthropic แนะนำให้โหลด Key จาก Environment Variables แทนการ Hard-code ในโค้ด สำหรับบน Cloud ให้ใช้กลไกการ Inject Environment Variables ของ Cloud Provider และเมื่อระบบมี Secrets เพิ่มขึ้น ควรใช้ Key Management System (KMS) เพื่อจัดเก็บแบบเข้ารหัสที่ศูนย์กลาง มีระบบ Fine-grained Access Control, บันทึก Audit Trails และจัดการ Rotate ได้ง่ายขึ้น

#4 4. ความเป็นส่วนตัว: Data Retention และ Zero Data Retention (ZDR)

อ่านเนื้อหา ↗
  • •
    Privacy by Design เริ่มต้นที่ Prompt ตัวอย่าง Guardrails บนหน้า Jailbreak Mitigation ของ Anthropic ระบุให้เขียนข้อกำหนดการปกป้องข้อมูลลงใน System Prompt โดยตรง เช่น "Protect client privacy
  • •
    Data Minimization คือหลักการพื้นฐาน Anthropic จัดเก็บเฉพาะข้อมูลที่จำเป็นทางเทคนิคเพื่อให้ฟีเจอร์ทำงานได้เท่านั้น และเนื้อหาบทสนทนา (Prompts และ Claude's Outputs) จะไม่ถูกเก็บไว้เป็นค่าเริ่มต้น (Not retained by default) ข้อมูล API ที่ถูกเก็บไว้จะไม่ถูกนำไปใช้เทรนโมเดลโดยเด็ดขาด เว้นแต่จะได้รับอนุญาตอย่างชัดเจน
  • •
    สำหรับ Claude API ได้แก่ Zero Data Retention (ZDR) และ HIPAA Readiness ซึ่งเป็นข้อตกลงคนละส่วนกัน และตาราง Feature Eligibility จะระบุว่าแต่ละข้อตกลงครอบคลุม API Features ใดบ้าง ภายใต้ ZDR นั้น Anthropic จะไม่เก็บ Prompts หรือ Responses ในระดับ Data at Rest เลยหลังจากส่ง Response คืนไปแล้ว แต่ต้องวางแผนรับมือเงื่อนไขต่อไปนี้:
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (2 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Bash deny rule หรือ allowlist ช่วยทำ Sandboxing ให้กับ Agent และจำกัดสิ่งคำสั่งสามารถทำได้จริง?
A Bash deny rule or allowlist sandboxes the agent and contains what a command can do.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Permission rules เป็นเพียง Gate ที่ตรวจจับ Pattern ของข้อความคำสั่ง (Text-matching) เท่านั้น ไม่ใช่ Sandbox ของระบบปฏิบัติการ หากต้องการจำกัดการเข้าถึง Filesystem และ Network จริงๆ ต้องใช้ OS-level sandboxing
Permission rules match command text. Claude Code says this is a permission gate, not a sandbox; use OS-level sandboxing to restrict filesystem and network access.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
API keys จำเป็นต้อง Rotate เฉพาะตอนที่สงสัยว่า Key หลุดเท่านั้น?
API keys only need rotating after a suspected leak.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Anthropic แนะนำให้ Rotate เป็นรอบปกติ เช่น ทุกๆ 90 วัน เพื่อจำกัดอายุการใช้งานและลดความเสี่ยง หาก Key เกิดหลุดโดยที่ไม่มีใครสังเกตเห็น
Anthropic recommends rotating on a consistent schedule, such as every 90 days, so a key that is compromised without anyone noticing has a limited lifetime.
🎯 ทักษะที่ข้อสอบประเมินในบทนี้ (Exam Competency Checklist) 4 วัตถุประสงค์
  • ✓กำหนดสิทธิ์ Least Privilege ให้กับ Tools ของ Agent ด้วยกฎ allow, ask และ deny
  • ✓ออกแบบ IAM สำหรับ Agents: จำกัดสิทธิ์ระดับต่ำสุดและ inject credentials ผ่าน Proxy
  • ✓จัดเก็บ หมุนเวียน (Rotate) และตรวจจับ API Keys ตาม Best Practices ของ Anthropic
  • ✓กำหนด Data Retention และ Zero Data Retention (ZDR) ให้สอดคล้องกับข้อกำหนดด้าน Privacy
