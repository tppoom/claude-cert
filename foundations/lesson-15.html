💡 แนวคิดหลักสำคัญ (Key Concept)

Pin versus pointer — A pin names one fixed thing, such as a snapshot model ID, an exact plugin version or a numbered prompt version, and it behaves the same until you change the configuration yourself. A pointer, such as an alias, a version range or an unscoped default, resolves to whatever is current, so its behaviour can change without any edit on your side.

B Only the root `CLAUDE.md` loads at launch; `frontend/CLAUDE.md` loads on demand only when Claude reads a file inside a subdirectory nested below `frontend/`, not `frontend/` itself
C Only `frontend/CLAUDE.md` loads at all, since Claude Code loads the CLAUDE.md closest to the working directory and ignores ancestor files further up the tree

คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. Claude Code walks up the directory tree from the working directory, loading CLAUDE.md files found there and above at launch; content is concatenated in order from the filesystem root down to the working directory, so the root file is read before `frontend/CLAUDE.md`, which sits at the launch directory itself.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. `frontend/CLAUDE.md` sits at the working directory itself, not in a subdirectory below it, so it loads at launch along with the root file rather than being deferred to on-demand loading.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Ancestor CLAUDE.md files above the working directory are loaded in full at launch, not ignored; the root file is included alongside the working-directory file.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. The documented order runs from the filesystem root down to the working directory, meaning instructions closer to the launch point are read last, not first, so the root file precedes `frontend/CLAUDE.md` in context.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "CLAUDE.md scopes, AGENTS.md and path-scoped rules" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

CLAUDE.md files carry the standing instructions Claude reads at the start of every session, and where a file lives decides who it applies to. There are four scopes. An organization-wide file sits at a managed policy path that IT deploys. Your personal file at ~/.claude/CLAUDE.md follows you into every project. The project file, ./CLAUDE.md or ./.claude/CLAUDE.md, is committed so the whole team shares it. ./CLAUDE.local.md holds your own notes for one project and belongs in .gitignore.

These scopes do not override one another. They all load and add up. That is why contradictions matter: when two instructions disagree, Claude may follow either one, so review the root file, nested CLAUDE.md files in subdirectories and .claude/rules/ together. @path imports such as @docs/git-instructions.md help you split up a long file. They do not save context, because imported files also load at launch. If a monorepo pulls in another team's instructions, claudeMdExcludes lists glob patterns for files to skip.

Not everything loads at launch. Files in the working directory and the directories above it load when the session starts. A subdirectory's instruction files and its .claude/rules/ files load later, when Claude reads a file there. In a monorepo, a frontend/CLAUDE.md therefore stays out of context until Claude works under frontend/.

Path-scoped rules are how you cut a long CLAUDE.md down. A file in .claude/rules/ with a paths list in its frontmatter loads only when Claude works on files that match those globs. Aim for under 200 lines per CLAUDE.md. Move the narrow rules out, such as the API conventions for src/api/, and keep the general conventions in the always-loaded file. Personal rules can go in ~/.claude/rules/.

AGENTS.md is the cross-tool instruction file, and by default it is a fallback, not an addition. Claude reads every AGENTS.md in your working directory and the directories above it only when there is no CLAUDE.md, .claude/CLAUDE.md or CLAUDE.local.md in those directories. If one of those exists, AGENTS.md is skipped. Your user CLAUDE.md, the managed CLAUDE.md and .claude/rules/ files do not count toward that test, so they load either way. There are two ways to get both files. You can put an @AGENTS.md line in CLAUDE.md, and Claude never reads the file twice. Or you can set the built-in agents-md plugin to claude-md-and-agents-md. On Windows, use the import rather than a symlink: a clone without symlink support checks out a one-line CLAUDE.md.

CLAUDE.md files add together, but settings resolve key by key. When the same key is set in more than one place, the highest scope wins. Keys you leave out keep the value from a lower scope. There are four files, plus a flag for a single session.

From strongest to weakest, the order is: managed settings, command-line arguments (including JSON passed with --settings), .claude/settings.local.json, .claude/settings.json, and ~/.claude/settings.json. The local file is yours. The first time Claude Code writes it, it adds the file to your global git excludes. It also writes your "Yes, and don't ask again" approvals there as allow rules.

Some keys are merged rather than replaced. permissions.allow combines across every scope, and an allow rule in your local file does not outrank an ask rule from a project or managed file.

Your own settings cannot override managed settings, and that is what makes them enforceable. Use managed settings for technical controls: permissions.deny to block tools, commands or paths, sandbox.enabled to require isolation, env for provider routing, forceLoginMethod and forceLoginOrgUUID for sign-in, and allowManagedPermissionRulesOnly to ignore everyone else's allow rules. Guidance about behaviour belongs in the managed CLAUDE.md. A rule like "never push to main" therefore needs both: an instruction in the managed CLAUDE.md and a deny rule in managed settings.

A few security keys work the other way. Any scope can make them stricter, so a project's disableClaudeAiConnectors: true stays on even when a managed source sets false.

Values in a committed project file do not all apply as soon as someone clones the repository. permissions.allow rules, extraKnownMarketplaces and most env values wait until each teammate trusts the folder. deny and ask rules apply straight away. Some values never apply from project or local settings. For example, permissions.defaultMode set to bypassPermissions has to come from user or managed settings.

A model ID is a pin. The model behind it stays the same for as long as the ID exists. From the Claude 4.6 generation onward, IDs have no date, such as claude-opus-4-6 or claude-sonnet-5, and each one is the canonical name of a single snapshot. Older models carry a date, as in claude-sonnet-4-5-20250929, and on the Claude API they also have short aliases such as claude-sonnet-4-5. Those aliases point to the newest dated snapshot for that minor version. Each ID has its own deprecation and retirement schedule. A pin fixes the weights, but the serving infrastructure around them can still change. If a pinned ID starts behaving differently, an infrastructure update is the first thing to suspect.

The ID format depends on the provider, so a pin copied from one platform fails on another. Dateless IDs are claude-sonnet-4-6 on the Claude API and Google Cloud, and anthropic.claude-sonnet-4-6 on Amazon Bedrock. Dated models differ more: claude-sonnet-4-5-20250929 on the Claude API, anthropic.claude-sonnet-4-5-20250929-v1:0 on Bedrock, and claude-haiku-4-5@20251001 on Google Cloud, where the date follows an @.

Claude Code adds its own family aliases, and these drift by design. opus and sonnet resolve to the latest model in their family, and what that is depends on your provider. opus resolves to Opus 5.5 on the Anthropic API but to Opus 4.6 on Microsoft Foundry. default is not an alias. It clears any override. Use an alias on a developer machine where newer is better. Use a full ID wherever two environments must run the same model.

To keep an alias but freeze what it points to, set the ANTHROPIC_DEFAULT_OPUS_MODEL, ANTHROPIC_DEFAULT_SONNET_MODEL, ANTHROPIC_DEFAULT_HAIKU_MODEL or ANTHROPIC_DEFAULT_FABLE_MODEL variable to a full ID. Under an organization's availableModels list, these variables cannot redirect an allowed alias to a model outside the list.

The model a session starts on is chosen in a fixed order. The --model flag comes first, then the ANTHROPIC_MODEL environment variable, then a model value in any settings file (including the one /model saves), then an organization default. A model in project or managed settings applies again at every launch and outranks your saved /model choice. The startup header names the file it came from. A resumed session usually keeps the model it was using. If the requested model is outside the organization's availableModels, Claude Code swaps it at startup and prints a warning.

The default choice depends on what is recorded. When no organization default model is set, Default can resolve to the model recorded from your earlier choice. If model restrictions exclude that recorded model, or your account cannot use it, Default resolves as if nothing were recorded. A /model switch takes effect immediately in the running session, so changing models never needs a restart.

A system prompt affects output as much as the model does, so manage it the same way: keep immutable versions, pin each environment to one version, and make every change an explicit move between versions. Anthropic follows this rule for models. A model ID never changes in place, and an update ships under a new ID. Your prompts need the same guarantee. Otherwise you cannot tell whether a regression came from a model change or a prompt change.

Managed Agents is an Anthropic API service that stores an agent, including its system prompt, on the server. agents.update is the call that changes the agent, and sessions.create is the call that starts a session against it. Each agents.update creates a new immutable version, and sessions.create can pin a session to a specific version. Promoting a prompt becomes a change to one version number in config, not a code diff that needs a rebuild.

What you pass to sessions.create decides whether you hold a pointer or a pin. A plain agent ID string gets whatever the latest version is. An object of the form {"type": "agent", "id": ..., "version": ...} pins one exact version. Production callers that pass the bare ID pick up a new prompt on their very next session.

Nothing gates agents.update. There is no built-in approval workflow, and any key in the workspace can call it. The review step therefore moves to the pin: production callers always pass an explicit version, and that version number in config goes through your normal review. Anyone can create version 2, 3 or 10, and those versions sit unused until a reviewed change promotes one.

The safe workflow follows a fixed sequence. Create version 1 and score it against a labelled test set. Ship version 2 and score it the same way. If it regresses, point callers back at version 1. Rolling back needs no deploy, because version 1 still exists unchanged.

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A plugin is a package of Claude Code extensions that you install from a marketplace (see [Claude Code plugins](lesson:2.5)). A plugin can depend on other plugins, listed in the dependencies array of its plugin.json. Each entry is either a bare name or an object with a name, a semantic-version range in version, and an optional marketplace. Claude Code installs the highest git tag that satisfies the range, so the dependency's maintainer must tag releases. A plugin with its own repository is tagged by its author. A plugin referenced by a relative path is tagged by the marketplace maintainer. claude plugin tag --push creates the tag after it validates the plugin, and it refuses if the tag already exists.

With no satisfying tag, the outcome depends on where the dependency lives. A plugin with its own repository fails to install with a message that no git tag satisfies the range. A plugin referenced by a relative path installs the marketplace's current copy instead, and the range is checked when the plugin loads. If that copy falls outside the range, the dependent plugin stays disabled and claude plugin list shows the required range next to the installed version.

How wide you make a range decides how well it holds up when two plugins need the same dependency. Ranges that overlap resolve to a single install. Ranges that cannot overlap make the second install fail, and the first plugin keeps working. An exact pin is a version of =2.1.0 in the dependency object, for example { "name": "secrets-vault", "version": "=2.1.0" }. It also stops auto-update from moving the dependency for as long as the pinning plugin is installed. Use an exact pin when you have tested one specific build. Use a caret or tilde range when you want fixes to arrive on their own.
