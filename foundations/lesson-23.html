กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "One HTTP request, streamed back: SSE rather than a websocket" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A streamed Claude response is an ordinary Messages API call with "stream": true in the body. You send the same POST to /v1/messages with the same headers. The difference is in how the response comes back: a series of server-sent events (SSE) delivered as soon as they are produced, instead of one JSON object at the end. Each event has a name, such as event: message_stop, and a JSON data payload that repeats that type.

Teams used to chat backends often expect a websocket here: a persistent, two-way channel the client keeps open and pushes new user messages into. The Messages API is not built that way. It is stateless, so every turn is a new request that carries the whole conversation history. Streaming only changes how that one request's answer arrives: the HTTP connection stays open while events flow from server to client. A chat feature therefore sends a new request per user turn and reads each answer as an event stream.

Every stream follows the same overall structure, which lets a parser track its position. message_start comes first and carries a Message object whose content is still empty. Each content block follows with a content_block_start, one or more content_block_delta events and a content_block_stop. A block's index is its position in the final content array, so you can merge deltas by index even when there are several blocks. One or more message_delta events then report top-level changes such as stop_reason, and message_stop ends the stream. ping events can appear at any point, and the parser should simply ignore them.

D Buffer all unrecognized events until message_stop is received, then discard the entire response if any unrecognized events were present.
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct — Anthropic's versioning policy states new event types may be added, and client code should handle unknown event types gracefully rather than failing.

ตัวเลือก B: ไม่ถูกต้อง

Falling back and dropping the connection on unfamiliar events causes unnecessary failures for forward-compatible additions that carry no breaking change.

ตัวเลือก C: ไม่ถูกต้อง

Downgrading anthropic-version does not prevent new event types from appearing and is not the documented mitigation; the correct behavior is graceful handling, not version rollback.

ตัวเลือก D: ไม่ถูกต้อง

Discarding an otherwise valid response because of harmless new event types would break the application for no reason tied to actual errors.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Reading text, tool-input and thinking deltas" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The delta.type field tells you how to apply each content_block_delta to its block. A text_delta carries a piece of text to append. A tool call is different. Its input_json_delta events carry partial_json, which are string fragments of the tool's arguments such as {"location": "San Fra. These fragments are not valid JSON on their own. Concatenate them per block index and parse the result when that block's content_block_stop arrives. The SDK helpers, or a partial-JSON parser, can do this for you. Expect gaps between tool-input events: current models produce one complete key and value at a time, and then send it as several chunks.

Thinking blocks stream their reasoning as thinking_delta events. Each one ends with a single signature_delta, which is used to verify that the block is intact. If thinking display is set to omitted, the block still opens and closes, but its thinking_delta holds an empty string and is followed only by the signature. A UI that waits for reasoning text in that mode will show nothing.

Token usage comes in two places in a stream. message_start reports the input tokens. Each message_delta reports output tokens as a running total, not a per-event increment. Take the value from the last event. A billing job that adds up every message_delta will report more than the dashboard shows, and the gap grows with the number of events.

A stream can fail after the server has already returned 200 OK. Because the status line has been sent by then, the failure arrives as an event: error in the stream, using the same type and error object as a normal error body. An overloaded_error here is the streaming equivalent of an HTTP 529. Treat it the way [API error types and recovery](lesson:4.1) describes, and throw away the partial content you received. Also, the API may add new event types under its versioning policy, so a parser should skip unknown events rather than fail on them.

The SDKs offer two streaming styles, and they suit different needs. client.messages.create(..., stream=True) gives you the raw events as an iterable. It uses less memory because it does not build up a final message. client.messages.stream(...) adds helpers on top: text_stream for text only, event handlers in TypeScript, and accumulation into a complete Message through get_final_message() in Python or finalMessage() in TypeScript. Use the raw iterator if you are forwarding events somewhere else. Use the helper if you want the assembled result. In TypeScript, you cancel a stream by breaking out of the loop or calling stream.controller.abort().

Long outputs are where streaming stops being optional. A non-streaming request sends nothing back until the whole response has been generated. With a large max_tokens, that wait can outlast HTTP timeouts, and for these requests the SDK requires streaming. A streamed request keeps the connection busy with events. If your code just wants the finished report, it still gets an object identical to what create() returns by calling get_final_message(). Long requests can also fail with a 504 timeout_error, and streaming is the suggested fix for that too.
