1. การร้องขอ HTTP ครั้งหนึ่ง ส่งกลับแบบสตรีม: SSE แทนที่จะเป็น websocket

การตอบสนองของ Claude แบบสตรีมเป็นการเรียก Messages API ธรรมดาที่มี "สตรีม": เป็นจริงในส่วนเนื้อหา คุณส่ง POST เดียวกันไปที่ /v1/messages โดยมีส่วนหัวเดียวกัน ความแตกต่างอยู่ที่วิธีที่การตอบสนองกลับมา

: ชุดของเหตุการณ์ที่เซิร์ฟเวอร์ส่ง (SSE) จะถูกส่งทันทีที่มีการสร้าง แทนที่จะเป็นออบเจ็กต์ JSON หนึ่งรายการในตอนท้าย แต่ละเหตุการณ์จะมีชื่อ เช่น เหตุการณ์: message_stop และเพย์โหลดข้อมูล JSON ที่ทำซ้ำประเภทนั้น

ทีมที่ใช้ในการแชทแบ็กเอนด์มักจะคาดหวัง websocket ที่นี่: ช่องทางสองทางที่คงอยู่ซึ่งไคลเอนต์เปิดค้างไว้และส่ง User Message ใหม่เข้าไป Messages API ไม่ได้ถูกสร้างขึ้นในลักษณะนั้น ไม่มีสถานะ ดังนั้นทุกเทิร์นจึงเป็นคำขอใหม่ที่มีประวัติการสนทนาทั้งหมด การสตรีมจะเปลี่ยนวิธีที่คำตอบของคำขอหนึ่งมาถึงเท่านั้น: การเชื่อมต่อ HTTP ยังคงเปิดอยู่ในขณะที่เหตุการณ์ไหลจากเซิร์ฟเวอร์ไปยังไคลเอนต์ คุณสมบัติการแชทจึงส่งคำขอใหม่ต่อเทิร์นผู้ใช้และอ่านแต่ละคำตอบในรูปแบบสตรีมกิจกรรม

A mobile chat app wants a user's follow-up message to reach Claude over the connection it already used to stream the previous answer. How does the Messages API handle conversation turns?

คำแปลโจทย์:
แอปแชทบนมือถือต้องการให้ข้อความติดตามผลของผู้ใช้เข้าถึง Claude ผ่านการเชื่อมต่อที่ใช้ในการสตรีมคำตอบก่อนหน้า Messages API จัดการการเปลี่ยนการสนทนาอย่างไร

💡 Official Explanation (คำอธิบายเฉลย):

The API is stateless and the client resends the history on every call. Streaming delivers the answer to that single request as server-sent events.

คำแปลไทย:
API ไม่มีสถานะและไคลเอ็นต์จะส่งประวัติอีกครั้งทุกครั้งที่โทร การสตรีมมอบคำตอบให้กับคำขอเดียวนั้นเป็นเหตุการณ์ที่เซิร์ฟเวอร์ส่ง
“The Messages API is stateless, which means that you always send the full conversational history to the API.”
คำแปล: API ข้อความเป็นแบบไร้สัญชาติซึ่งหมายความว่าคุณจะส่งประวัติการสนทนาทั้งหมดไปยัง API เสมอ

คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A streamed Claude response is an ordinary Messages API call with "stream": true in the body. You send the same POST to /v1/messages with the same headers. The difference is in how the response comes back: a series of server-sent events (SSE) delivered as soon as they are produced, instead of one JSON object at the end. Each event has a name, such as event: message_stop, and a JSON data payload that repeats that type.

Teams used to chat backends often expect a websocket here: a persistent, two-way channel the client keeps open and pushes new user messages into. The Messages API is not built that way. It is stateless, so every turn is a new request that carries the whole conversation history. Streaming only changes how that one request's answer arrives: the HTTP connection stays open while events flow from server to client. A chat feature therefore sends a new request per user turn and reads each answer as an event stream.

2. ลำดับของเหตุการณ์ในสตรีม

ทุกสตรีมตามโครงสร้างโดยรวมเหมือนกัน ซึ่งช่วยให้ตัววิเคราะห์ตำแหน่งของมันได้ message_start มาก่อนเสมอและมีวัตถุ Message ที่เนื้อหายังคงว่าง ทุกบล็อกเนื้อหามี content_block_start ตามด้วยเหตุการณ์ content_block_delta หนึ่งรายการหรือมากกว่า และ content_block_stop ดัชนีของบล็อกคือ ตำแหน่งของมันในอาร์เรย์เนื้อหาสุดท้าย ดังนั้นคุณสามารถรวม deltas ตามดัชนีได้แม้ว่าจะมีหลายบล็อก จากนั้นเหตุการณ์ message_delta หนึ่งรายการหรือมากกว่าจะแจ้งการเปลี่ยนแปลงระดับบน เช่น stop_reason และ message_stop สิ้นสุดสตรีม เหตุการณ์ ping สามารถปรากฏในจุดใดก็ได้ และตัววิเคราะห์ควรเพิกเฉยต่อมัน

Token usage comes in two places in a stream. message_start reports the input tokens. Each message_delta reports output tokens as a running total, not a per-event increment. The SDKs offer two streaming styles, and they suit different needs. client.messages.create(..., stream=True) gives you the raw events as an iterable. It uses less memory because it does not build up a final message. client.messages.stream(...) adds helpers on top: text_stream for text only, event handlers in TypeScript, and accumulation into a complete Message through get_final_message() in Python or finalMessage() in TypeScript. Use the raw iterator if you are forwarding events somewhere else. Use the helper if you want the assembled result. In TypeScript, you cancel a stream by breaking out of the loop or calling stream.controller.abort().

Long outputs are where streaming stops being optional. A non-streaming request sends nothing back until the whole response has been generated. With a large max_tokens, that wait can outlast HTTP timeouts, and for these requests the SDK requires streaming. A streamed request keeps the connection busy with events. If your code just wants the finished report, it still gets an object identical to what create() returns by calling get_final_message(). Long requests can also fail with a 504 timeout_error, and streaming is the suggested fix for that too.

    สตรีมสามารถล้มเหลวได้หลังจากที่เซิร์ฟเวอร์ได้ส่ง 200 OK ไปแล้ว เนื่องจากบรรทัดสถานะถูกส่งไปแล้ว ความล้มเหลวจะมาถึงในรูปแบบของเหตุการณ์: ข้อผิดพลาดในสตรีม ใช้ประเภทและวัตถุข้อผิดพลาดเดียวกับร่างข้อผิดพลาดปกติ overloaded_error ที่นี่เทียบเท่ากับ HTTP 529 แบบสตรีมมิ่ง ปฏิบัติตามวิธีที่ [ประเภทข้อผิดพลาด API และการกู้คืน](lesson:4.1) อธิบาย และทิ้งเนื้อหาบางส่วนที่คุณได้รับ นอกจากนี้ API อาจเพิ่มประเภทเหตุการณ์ใหม่ภายใต้แนวนโยบายเวอร์ชันของมัน
  • •
    ตัวแยกวิเคราะห์ควรข้ามเหตุการณ์ที่ไม่รู้จัก
  • •
    การใช้โทเค็นมีอยู่สองแห่งในสตรีม message_start รายงานโทเค็นอินพุต แต่ละ message_delta จะรายงานโทเค็นเอาท์พุตเป็นผลรวมที่กำลังรันอยู่ ไม่ใช่การเพิ่มขึ้นต่อเหตุการณ์ เอาค่าจากเหตุการณ์ที่แล้ว งานการเรียกเก็บเงินที่รวมทุก message_delta จะรายงานมากกว่าที่แดชบอร์ดแสดง และช่องว่างจะเพิ่มขึ้นตามจำนวนเหตุการณ์

#5 5. เครื่องมือช่วยสตรีมของ SDK และผลลัพธ์ยาว

อ่านเนื้อหา ↗
  • •
    เอาต์พุตแบบยาวคือเมื่อการสตรีมไม่เป็นทางเลือกอีกต่อไป คําขอที่ไม่มีการสตรีมจะส่งคืนอะไรจนกว่าจะสร้างการตอบสนองทั้งหมด ด้วย max_tokens ขนาดใหญ่ การรอนั้นสามารถอยู่ได้นานกว่าการหมดเวลา HTTP และสําหรับคําขอเหล่านี้ SDK ต้องการการสตรีม คําขอแบบสตรีมทําให้การเชื่อมต่อยุ่งอยู่กับเหตุการณ์ หากโค้ดของคุณต้องการเพียงรายงานที่เสร็จสมบูรณ์ มันจะยังคงได้รับอ็อบเจกต์ที่เหมือนกันกับที่ create() ส่งคืนโดยการเรียก get_final_message() คําขอแบบยาวอาจล้มเหลวด้วย 504 timeout_error และการสตรีมเป็นวิธีแก้ไขที่แนะนําสําหรับสิ่งนั้นเช่นกัน
  • •
    SDK นำเสนอสไตล์การสตรีมสองสไตล์ และเหมาะกับความต้องการที่แตกต่างกัน client.messages.create(..., stream=True) ให้เหตุการณ์ดิบแก่คุณซึ่งสามารถทำซ้ำได้ ใช้หน่วยความจำน้อยลงเนื่องจากไม่ได้สร้างข้อความสุดท้าย client.messages.stream(...) เพิ่มตัวช่วยที่ด้านบน
  • •
    text_stream สำหรับข้อความเท่านั้น ตัวจัดการเหตุการณ์ใน TypeScript และการสะสมเป็นข้อความที่สมบูรณ์ผ่าน get_final_message() ใน Python หรือ FinalMessage() ใน TypeScript ใช้ตัววนซ้ำหากคุณกำลังส่งต่อกิจกรรมไปที่อื่น ใช้ตัวช่วยหากคุณต้องการผลลัพธ์ที่ประกอบกัน ใน TypeScript คุณยกเลิกการสตรีมโดยแยกออกจากลูปหรือเรียก stream.controller.abort()
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (3 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
แต่ละ input_json_delta มีออบเจ็กต์ JSON ที่ใช้งานได้พร้อมกับอาร์กิวเมนต์ของเครื่องมือ
Each input_json_delta contains a usable JSON object with the tool's arguments.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
สันดอนเป็นส่วนย่อยของสตริง เข้าร่วมบล็อกและแยกวิเคราะห์เมื่อ content_block_stop มาถึง หรือปล่อยให้ผู้ช่วยเหลือ SDK ทำ
The deltas are fragments of a string. Join them for the block and parse once content_block_stop arrives, or let the SDK helpers do it.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
หากต้องการรับโทเค็นเอาต์พุตที่เรียกเก็บเงินของการตอบกลับแบบสตรีม ให้เพิ่ม output_tokens จากทุกเหตุการณ์ message_delta
To get a streamed response's billed output tokens, add up output_tokens from every message_delta event.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
การใช้งาน message_delta เป็นแบบสะสม ค่าที่รายงานล่าสุดคือผลรวม ดังนั้นการเพิ่มเหตุการณ์เข้าด้วยกันจะเกินการใช้งาน
message_delta usage is cumulative. The last reported value is the total, so adding the events together overstates usage.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
client.messages.create(..., stream=True) ส่งคืน Message ที่ประกอบขึ้นแบบเดียวกับตัวช่วยสตรีมซึ่งเร็วขึ้น
client.messages.create(..., stream=True) returns the same assembled Message as the stream helper, just faster.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ส่งคืนเฉพาะเหตุการณ์ดิบที่สามารถทำซ้ำได้ และไม่สร้างข้อความสุดท้าย ใช้ client.messages.stream(...) กับ get_final_message() เมื่อคุณต้องการผลลัพธ์ที่ประกอบกัน
It returns only the raw event iterable and does not build a final message. Use client.messages.stream(...) with get_final_message() when you want the assembled result.
