🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Compaction: summarizing older turns on the server" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Pruning works well for content you can throw away, such as stale tool results or old thinking. A long conversation also builds up content that still matters but no longer needs to be kept word for word. Compaction handles that. It replaces older turns with a summary that Claude writes on the server, so you write no summarization code. The context windows guide calls server-side compaction the primary strategy for long-running conversations and agentic workflows. It keeps the task within the limit and keeps the active context small, because quality drops as the conversation grows. Compaction is in beta for Claude 4.6 and later models and Claude Mythos Preview.

The docs give a clear default: use on-demand compaction wherever it is available. Threshold compaction fits when you want the API to manage context inside ordinary requests. On-demand compaction has optional variants. You can keep the last few turns word for word and summarize only the older ones, run the summary in the background while work continues, supply your own summarization prompt when the default summary drops something a later turn needs, and compact again when an already-compacted conversation grows long. The TypeScript and Ruby SDKs also offer client-side compaction through tool_runner, but server-side compaction is generally preferred.

2.What survives compaction in Claude Code and the Agent SDK

ใน Claude Agent SDK การทำงานหลักถูกขับเคลื่อนด้วยฟังก์ชัน query() ซึ่งทำหน้าที่จัดการวงรอบเอเจนต์ (Agentic Loop) ให้อัตโนมัติ:

วงรอบการทำงานของ query() Loop:
  1. ส่งพร้อมต์และประวัติการสนทนาไปยัง Claude API
  2. รับผลลัพธ์จากโมเดล หากโมเดลส่ง stop_reason: "tool_use" ระบบจะรันเครื่องมือที่ระบุ
  3. นำผลลัพธ์ของเครื่องมือส่งกลับไปให้ Claude ประเมินซ้ำ
  4. ลูปนี้จะหมุนต่อเนื่องไปเรื่อยๆ จนกระทั่งโมเดลส่ง stop_reason: "end_turn" โดยไม่มีการเรียกเครื่องมือเพิ่ม
MechanismAfter compaction
System prompt and output styleBoth still apply
Project-root CLAUDE.md, unscoped rules, auto memoryRe-injected from disk
Files Claude read or editedUp to five re-read, most recently modified first
Invoked skill bodiesRe-injected, capped at 5,000 tokens per skill and 25,000 total

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 55601

An engineer is building a research agent that needs to read dozens of files across a large repository to answer one question, without letting all that file content pile up in the main conversation's context. Which design best achieves this?

A Delegate the file exploration to a subagent, whose fresh context absorbs all the intermediate reads while only its final summary message returns to the parent
B Read every file directly in the main agent loop, then issue a manual /compact command immediately afterward to shrink the accumulated history
C Read every file directly in the main agent loop, but set effort to low so the extra file content consumes fewer tokens per turn
D Store all file contents in a custom MCP resource and have the main agent fetch a single combined resource URI instead of individual files
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. A subagent runs in its own fresh conversation; intermediate tool calls and results stay inside the subagent, and only its final message returns to the parent, so the main context grows by a summary rather than every file read.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. Reading everything in the main loop still pays the full context cost of every file during exploration; manual compaction afterward summarizes history but doesn't prevent that cost from accumulating first, and it also risks losing detail the task still needs.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. The effort setting controls how much reasoning Claude applies per turn; it reduces token usage from reasoning, not the token cost of the file contents themselves being read into context.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Combining file contents into one MCP resource still delivers that same total content into the main agent's context when fetched; it does not isolate it the way a subagent's separate conversation does.

In Claude Code, /compact replaces the conversation with a structured summary. Most startup content reloads automatically. That difference matters: anything stored on disk comes back word for word, while anything that existed only in the conversation is reduced to whatever the summary kept.

You can steer the summary in several ways. /compact focus on the auth bug fix makes the summary keep what you choose instead of what the automatic pass guesses is important. /autocompact 500k sets how full the window gets before automatic compaction runs. /clear is a different tool: use it when switching to unrelated work, so old conversation doesn't crowd out the files you need next. The Agent SDK works the same way. The compactor reads CLAUDE.md like any other context, so a section there can say what every summary must preserve. A PreCompact hook can run custom logic first, such as archiving the full transcript, and sending /compact as a prompt string triggers compaction on demand.

A code review workflow runs a style-checker subagent, a security-scanner subagent, and a test-coverage subagent for the same pull request. The team wants the review to finish as fast as possible while still keeping each subagent's exploration out of the main conversation. What should they do?

A Invoke the three subagents so they run concurrently, since independent subtasks then finish in the time of the slowest one rather than the sum of all three
B Invoke the three subagents sequentially in a fixed order, since subagents are only supported one at a time within a single main-agent turn
C Merge all three review responsibilities into one subagent's system prompt so a single subagent invocation covers everything in one pass
D Run the three checks directly in the main agent's own tool calls instead of subagents, since only the main agent can run tools concurrently
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. Multiple subagents can run concurrently, so independent subtasks like style, security, and coverage checks finish in the time of the slowest one rather than sequentially, while each subagent's exploration still stays isolated from the main conversation.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. Subagents are not limited to one at a time; running them concurrently is a documented benefit for independent subtasks.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Merging responsibilities into a single subagent removes the parallelization benefit and mixes specialized instructions that were meant to stay separate and focused.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. The main agent's own tool calls that modify state run sequentially, and running checks directly in the main loop would also pull all that exploration content into the main conversation's context, which is what subagents are meant to avoid.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Context isolation with subagents" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Compaction shrinks history after it has built up. Isolation stops it building up at all. Each subagent runs in its own conversation, which starts fresh unless it is a fork. Its intermediate tool calls and results stay inside the subagent, and only its final message goes back to the parent as a tool result. The main agent's context grows by that summary, not by the whole transcript. That is why Claude Code's advice is to send large reads to a subagent: the file contents stay in its window instead of yours. Isolation brings other benefits too. Independent subagents can run in parallel. Each can have a specialised system prompt that would only be noise in the main agent's instructions. Each can be limited to the tools it needs, and that limit saves context, because every tool definition takes up space.
