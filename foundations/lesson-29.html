1. Compaction: การสรุปบทสนทนาย้อนหลังบน Server

Pruning เหมาะสำหรับลบข้อมูลที่ไม่จำเป็นทิ้ง เช่น ผลลัพธ์เครื่องมือ (stale tool results) หรือ old thinking แต่สำหรับบทสนทนายาวๆ ที่ยังมีข้อมูลสำคัญซึ่งไม่จำเป็นต้องเก็บไว้ครบทุกคำ Compaction คือคำตอบ โดยระบบจะแทนที่ข้อความรอบก่อนหน้าด้วยข้อความสรุปที่ Claude เขียนขึ้นบน Server ทำให้ไม่ต้องเขียนโค้ดทำ Summarization เอง คู่มือ Context Windows ยกให้ Server-Side Compaction เป็นกลยุทธ์หลัก สำหรับ Long-running Conversations และ Agentic Workflows ช่วยคุม Context ให้อยู่ในขีดจำกัดและมีขนาดกะทัดรัด ป้องกันปัญหาคุณภาพดรอป

เมื่อ Context ยาวขึ้น ฟีเจอร์นี้อยู่ในสถานะ Beta สำหรับ Claude 4.6 เป็นต้นไป รวมถึง Claude Mythos Preview

เมื่อ Context กลับมาโตอีกรอบ สำหรับ TypeScript และ Ruby SDK มีตัวเลือก Client-Side Compaction ผ่าน tool_runner ให้ใช้เช่นกัน แต่แนะนำให้ใช้ Server-Side Compaction เป็นหลัก

Pruning works well for content you can throw away, such as stale tool results or old thinking. A long conversation also builds up content that still matters but no longer needs to be kept word for word. Compaction handles that. It replaces older turns with a summary that Claude writes on the server, so you write no summarization code. The context windows guide calls server-side compaction the primary strategy for long-running conversations and agentic workflows. It keeps the task within the limit and keeps the active context small, because quality drops as the conversation grows. Compaction is in beta for Claude 4.6 and later models and Claude Mythos Preview.

The docs give a clear default: use on-demand compaction wherever it is available. Threshold compaction fits when you want the API to manage context inside ordinary requests. On-demand compaction has optional variants. You can keep the last few turns word for word and summarize only the older ones, run the summary in the background while work continues, supply your own summarization prompt when the default summary drops something a later turn needs, and compact again when an already-compacted conversation grows long. The TypeScript and Ruby SDKs also offer client-side compaction through tool_runner, but server-side compaction is generally preferred.

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
An instruction given once in an early user prompt stays in force after compaction, because compaction only removes tool output. (ทำไมถึงผิด): Compaction replaces the conversation with a summary. ไม่ถูกต้อง การเรียกใช้เครื่องมือของ Lead Agent ที่แก้ไขสถานะจะทํางานตามลําดับ และการเรียกใช้การตรวจสอบโดยตรงในลูปหลักจะดึงเนื้อหาการสํารวจทั้งหมดนั้นเข้าสู่บริบทของการสนทนาหลัก ซึ่งเป็นสิ่งที่ Subagents ควรหลีกเลี่ยง
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Compaction shrinks history after it has built up. Isolation stops it building up at all. Each subagent runs in its own conversation, which starts fresh unless it is a fork. Its intermediate tool calls and results stay inside the subagent, and only its final message goes back to the parent as a tool result. The main agent's context grows by that summary, not by the whole transcript. That is why Claude Code's advice is to send large reads to a subagent: the file contents stay in its window instead of yours. Isolation brings other benefits too. Independent subagents can run in parallel. Each can have a specialised system prompt that would only be noise in the main agent's instructions. Each can be limited to the tools it needs, and that limit saves context, because every tool definition takes up space.

#1 1. Compaction: การสรุปบทสนทนาย้อนหลังบน Server

อ่านเนื้อหา ↗
  • •
    Pruning เหมาะสำหรับลบข้อมูลที่ไม่จำเป็นทิ้ง เช่น ผลลัพธ์เครื่องมือ (stale tool results) หรือ old thinking แต่สำหรับบทสนทนายาวๆ ที่ยังมีข้อมูลสำคัญซึ่งไม่จำเป็นต้องเก็บไว้ครบทุกคำ Compaction คือคำตอบ โดยระบบจะแทนที่ข้อความรอบก่อนหน้าด้วยข้อความสรุปที่ Claude เขียนขึ้นบน Server ทำให้ไม่ต้องเขียนโค้ดทำ Summarization เอง คู่มือ Context Windows ยกให้ Server-Side Compaction เป็นกลยุทธ์หลัก
  • •
    สำหรับ Long-running Conversations และ Agentic Workflows ช่วยคุม Context ให้อยู่ในขีดจำกัดและมีขนาดกะทัดรัด ป้องกันปัญหาคุณภาพดรอป
  • •
    ตาม Official Docs แนะนำให้เลือกใช้ On-Demand Compaction เป็นตัวเลือกหลักเสมอหากรองรับ ส่วน Threshold Compaction จะเหมาะกับกรณีที่ต้องการให้ API คุม Context ระหว่างส่ง Request ปกติให้เองโดยอัตโนมัติ

#2 2. สิ่งที่ยังคงอยู่หลังทำ Compaction ใน Claude Code และ Agent SDK

อ่านเนื้อหา ↗
  • •
    สำหรับ Agent SDK ก็ทำงานในรูปแบบเดียวกัน โดย Compactor จะอ่าน CLAUDE.md เข้ามาเป็น Context เหมือนข้อมูลอื่นๆ เราจึงสามารถระบุหัวข้อในนั้นเพื่อกำหนดสิ่งที่ระบบต้องเก็บรักษาไว้ในทุกๆ บทสรุปได้ รวมถึงตั้ง PreCompact Hook ให้รัน Logic เสริมก่อนได้ (เช่น เซฟ Transcript ฉบับเต็มลง Archive) และสามารถส่งสตริง `/compact` เข้าไปใน Prompt เพื่อทริกเกอร์ Compaction แบบ On-Demand ได้ทันที
  • •
    ใน Claude Code คำสั่ง /compact จะแทนที่ประวัติบทสนทนาด้วยบทสรุปแบบ Structured Summary โดยไฟล์และค่าเริ่มต้นส่วนใหญ่จะถูก Reload ขึ้นมาใหม่โดยอัตโนมัติ จุดสำคัญคือ
  • •
    เราสามารถควบคุมทิศทางของบทสรุปได้หลายวิธี เช่น ใช้คำสั่ง `/compact focus on the auth bug fix` เพื่อสั่งให้สรุปเฉพาะประเด็นที่เราเลือก แทนที่จะปล่อยให้ระบบเดาเองว่าอะไรสำคัญ, ใช้ `/autocompact 500k` เพื่อกำหนดขนาด Window ก่อนที่ระบบจะ Compaction ให้อัตโนมัติ ส่วนคำสั่ง `/clear` จะทำงานต่างออกไป คือใช้เมื่อต้องการเปลี่ยนไปทำงานอื่นที่ไม่เกี่ยวข้องกัน เพื่อไม่ให้บทสนทนาเดิมแย่งพื้นที่ Context ของไฟล์ชุดใหม่

#3 3. Context isolation with subagents

อ่านเนื้อหา ↗
  • •
    Isolation ยังมีข้อดีอื่นอีก เช่น รองรับการรัน Subagent แบบ Parallel พร้อมกัน, กำหนด System Prompt เฉพาะทางได้โดยไม่กวนคำสั่งหลักของ Main Agent และจำกัดเฉพาะ Tools ที่จำเป็นเพื่อประหยัด Context เนื่องจาก Tool Definition ทุกตัวล้วนกินพื้นที่ Context ทั้งสิ้น
  • •
    Compaction ช่วยย่อประวัติหลังสะสมจนแน่น แต่ Isolation ป้องกันไม่ให้ Context บวมตั้งแต่แรก Subagent แต่ละตัวทำงานใน Conversation แยกของตัวเอง ซึ่งเริ่มต้นใหม่เสมอ (ยกเว้นกรณี Fork) โดย Tool Calls และผลลัพธ์ระหว่างทางจะอยู่เฉพาะภายใน Subagent เท่านั้น มีเพียงข้อความสรุปสุดท้ายที่จะส่งกลับไปยัง Parent ในฐานะ Tool Result Context ของ Main Agent จึงเพิ่มขึ้นแค่ส่วนสรุป ไม่ใช่ Transcript ทั้งหมด นี่คือเหตุผลที่ Claude Code แนะนำให้โยนงานอ่านไฟล์ขนาดใหญ่ไปให้ Subagent จัดการ เพราะเนื้อหาไฟล์จะถูกจำกัดอยู่ใน Context Window ของมันเอง
  • •
    ตารางเปรียบเทียบสำคัญ: AgentDefinition fields that shape a subagent's context (ฟิลด์ของ AgentDefinition ที่มีผลต่อ Context ของ Subagent)
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (3 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
An instruction given once in an early user prompt stays in force after compaction, because compaction only removes tool output.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: คำสั่งหรือข้อกำหนดที่ผู้ใช้ป้อนไว้ใน User Prompt ช่วงแรกจะยังคงมีผลอยู่หลังทำ Compaction เพราะ Compaction ตัดทิ้งแค่ Tool Output เท่านั้น — แท้จริงแล้ว Compaction จะแทนที่บทสนทนาทั้งหมดด้วยบทสรุป ข้อมูลที่เซฟอยู่บน Disk อย่าง CLAUDE.md เท่านั้นที่จะถูก Re-injected กลับมาครบทุกคำ ส่วนคำสั่งใดๆ ที่อยู่แค่ในบทสนทนาจะคงอยู่ต่อเมื่อตัวสรุปเลือกเก็บไว้เท่านั้น
Compaction replaces the conversation with a summary. Content on disk, such as CLAUDE.md, is re-injected word for word, but a conversation-only instruction survives only if the summary happened to keep it.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด? Subagent ฝั่ง research รัน grep และอ่านไฟล์ไป 40 ไฟล์เพื่อตอบคำถามเดียว หลังทำงานเสร็จ ข้อมูลเหล่านั้นจะเข้าไปอยู่ใน Context ของ Parent Agent มากน้อยแค่ไหน?
Predict First:: A research subagent greps and reads 40 files to answer one question. Afterwards, how much of that work is in the parent agent's context?
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: ข้อมูลการอ่านไฟล์และ Tool Calls ทั้งหมดจะไม่ถูกดึงเข้ามาใน Parent Agent เลย มีเพียงข้อความตอบกลับสรุปสุดท้าย (Final Message) เท่านั้นที่ส่งกลับมาเป็น Tool Result
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด? ประวัติการอ่านไฟล์และผลลัพธ์ของ Tools ใน Subagent จะถูกรวมเข้ากับ History ของ Parent เมื่อทำงานเสร็จ ดังนั้นการกระจายงานให้ Subagent จึงไม่ได้ช่วยประหยัด Context ของ Parent เลย
A subagent's file reads and tool results are merged into the parent's history once it finishes, so delegating doesn't save parent context.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: แต่ละ Turn ของ Subagent จะคงอยู่เฉพาะใน Conversation ของตัวมันเอง Context ของ Parent จะเพิ่มขึ้นเฉพาะข้อความตอบกลับสุดท้าย (Final Response) ของ Subagent เท่านั้น
The subagent's turns stay in its own conversation. The parent's context grows only by the subagent's final response.
