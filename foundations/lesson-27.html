🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "How a prompt prefix becomes a cache hit" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Prompt caching lets a request reuse the processed prefix of an earlier, identical prompt, so you pay a fraction of the input price for that prefix. When caching is enabled, the API checks whether the prompt up to a cache breakpoint was cached by a recent request. If it was, the cached version is used. If not, the full prompt is processed and the prefix is cached once the response begins. The cache key is a cryptographic hash of the prompt up to the breakpoint, so only an identical prefix can hit.

The simplest way to turn it on is automatic caching: a single top-level cache_control field. The system places the breakpoint on the last cacheable block and moves it forward as a conversation grows. Each turn then reads everything before the new turn from cache and writes only the new content.

Because a hit needs an exact prefix, some changes outside the text also break it. The cache is layered: tools, then system, then messages. Editing a tool definition invalidates all three layers. Turning web search or citations on or off changes the system layer and everything after it. Changing tool_choice, adding or removing images, or changing thinking parameters or the effort setting invalidates at least the message layer. Prompt caching has needed no beta prefix for some time. Code that calls client.beta.prompt_caching is outdated and should use client.messages.create.

ID: 55624

A finance team wants a monthly cost model for an internal Claude-powered summarization service. They know the average input tokens per call, average output tokens per call, and call volume, but the engineering team also plans to introduce prompt caching for a shared instruction block. Which combination of usage fields should the cost model consume from the API responses to produce an accurate blended cost once caching is live?

A input_tokens, cache_creation_input_tokens, cache_read_input_tokens, and output_tokens, applying each field's own per-token rate since they are billed at different prices
B Only the total of input_tokens plus output_tokens, since caching does not change how usage fields are reported once a request completes
C Only output_tokens, since cached input segments are provided to the customer at no charge and therefore need not appear in a cost model
D input_tokens and output_tokens averaged across the month, ignoring cache_creation_input_tokens and cache_read_input_tokens since these are internal diagnostic fields not tied to billing
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. With caching enabled, the usage object separately reports input_tokens (uncached, post-breakpoint), cache_creation_input_tokens (billed at the write multiplier), and cache_read_input_tokens (billed at roughly 0.1x base price), each with distinct pricing; a cost model must apply each field's rate separately, plus output_tokens at the output rate, to be accurate.

ตัวเลือก B: ไม่ถูกต้อง

Once caching is active, input_tokens alone excludes the cache_creation and cache_read fields, which carry different prices than standard input tokens; summing only input_tokens and output_tokens would misstate the true blended cost.

ตัวเลือก C: ไม่ถูกต้อง

Cached reads are discounted, not free; cache_read_input_tokens is still billed, just at a reduced rate (roughly 10% of base input price), so omitting it understates cost.

ตัวเลือก D: ไม่ถูกต้อง

cache_creation_input_tokens and cache_read_input_tokens are billing-relevant usage fields with their own prices, not merely diagnostic; excluding them produces an inaccurate cost model once caching is live.

Put the breakpoint on the last block that stays the same from one request to the next. A cache write happens only at the block you mark, and every later request with the same prefix reads that entry. If you put the breakpoint on something that changes every time, such as a timestamp or the user's latest message, each request writes a new entry and never hits. For most prompts, one breakpoint at the end of the static content is enough.

Use more than one breakpoint, up to four, when parts of the prompt change at different rates. A typical four-breakpoint agent caches the tool definitions, the static instructions, the RAG documents and the conversation separately. A change at one breakpoint invalidates that segment and the segments after it, but the earlier segments stay valid. A second reason for extra breakpoints is a long conversation that has moved 20 or more blocks past the last cache write, outside the lookback window. Breakpoints themselves cost nothing. You pay only for the tokens written and read.

A breakpoint also does nothing if the prefix before it is too short. Each model has a minimum cacheable length: 512 tokens for Fable 5.1, Mythos 5.1, Opus 5.5, Opus 5 and Sonnet 5.5; 1,024 for Opus 4.8 and Sonnet 5; 4,096 for Haiku 4.5. A shorter prefix is processed normally with no cache write and no error. The only sign is cache_creation_input_tokens staying at zero. The automatic-caching sample above has a system prompt of a few dozen tokens, well under any minimum.

A latency-sensitive voice assistant relies on a large cached system prompt to keep response times low. Product wants to guarantee the cache is always warm the instant a user starts speaking, even after periods with no traffic, without waiting for an actual user request to trigger the cache write. Which technique addresses this directly?

A Issue a periodic request with max_tokens: 0 that includes the cached prefix and its cache_control breakpoint, refreshing the cache before it expires so it is warm when real traffic arrives
B Increase the model's temperature parameter so cached content is retained in memory for a longer duration between requests
C Enable extended thinking on every request so Claude proactively pre-loads the system prompt into a persistent cache that never expires
D Set stream to true on all requests, since streaming responses automatically extend the TTL of any cache entries touched during the request
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. Pre-warming with a max_tokens: 0 request that includes the cached prefix and its breakpoint writes or refreshes the cache entry ahead of real traffic, which is the documented technique for keeping latency-sensitive, large cached prompts ready without waiting on an actual user request.

ตัวเลือก B: ไม่ถูกต้อง

temperature controls output randomness/sampling and has no relationship to cache retention duration.

ตัวเลือก C: ไม่ถูกต้อง

Extended thinking affects reasoning behavior and token accounting for thinking blocks; it does not create a persistent, non-expiring cache, and thinking blocks themselves cannot be marked with cache_control.

ตัวเลือก D: ไม่ถูกต้อง

Streaming affects how response content is delivered incrementally; it does not extend or otherwise modify cache TTL behavior.

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Choosing the 5-minute or 1-hour TTL" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Cache writes cost more than plain input, and how much more depends on how long the entry lives. A 5-minute entry costs 1.25x the base input price to write. A 1-hour entry costs 2x. Reads cost 0.1x on most models, 0.05x on Opus 5.5 and 0.025x on Fable 5.1. Each time an entry is used, its lifetime is refreshed at no extra cost. So a 5-minute entry stays warm as long as requests keep arriving within five minutes of each other.

The lifetime starts when the request begins, not when its response ends, so long generations shorten the window for reuse. The TTL choice then comes down to the gaps between requests, because a miss on either duration bills the whole prefix at the write price again.

The break-even points follow from the table. Take a 1M-token prefix on Sonnet 5.5, where a request without caching pays $2 for the prefix. With the 5-minute TTL, a write plus one read costs $2.50 + $0.20 = $2.70, against $4.00 for two uncached requests, so one read already pays for the write. With the 1-hour TTL, a write plus one read costs $4.00 + $0.20 = $4.20, still above $4.00; a second read brings it to $4.40 against $6.00 uncached. Two reads is the break-even for the 1-hour entry. These counts assume the standard 0.1x read price; Opus 5.5 and Fable 5.1 read for less, so they pay off sooner.

When turns arrive seconds apart, the 5-minute entry never expires, so the 1-hour entry's extra write cost (2x instead of 1.25x) buys nothing. In Anthropic's measurements of agent runs with no pauses, the 5-minute setting cost 15% less than the 1-hour one on Sonnet 5 and about 15% to 18% less on Opus 5.5. That figure is a whole-task cost, so it is smaller than the gap on the prefix alone. The 1-hour entry wins once pauses start to cause misses: a gap between 5 minutes and an hour expires the 5-minute entry and rebills the prefix at 1.25x, where the 1-hour entry would have read it at 0.1x. Anthropic's rule of thumb is to switch to the 1-hour TTL when more than about 1 gap in 20 falls in that range, and it is a measured threshold rather than a derived one. Gaps longer than an hour expire either kind of entry.

Your hit rate is the share of input tokens served from cache: cache_read_input_tokens divided by total input. On the first request of a cached agent, almost all input appears in cache_creation_input_tokens and reads are zero. On later turns, reads cover everything already cached, and creation covers only the newest turn. Organization-wide, the Usage API reports the same split, and the Console plots cache rate hour by hour.

Caching makes the biggest difference in agent loops. Every turn resends the system prompt, the tools and all previous turns, so cost grows roughly with the square of the number of turns. In Anthropic's measurements, caching cut agent-loop cost by a factor of 2.7 to 5.3. Over a day of real traffic, agent loops read a median 84% of their input from cache, and the top tenth read 94% or more. A rate below about 80% usually means something is breaking the cache. Common causes are a timestamp ahead of the breakpoint, tool definitions that change between turns, or gaps longer than the TTL.
