In this lifecycle frame, which stage covers configuring environments and managing deployments?

คำแปลโจทย์:
ในกรอบวงจรการใช้งานนี้ ขั้นตอนใดครอบคลุมการกำหนดค่าสภาพแวดล้อมและการจัดการการปรับใช้งาน
คำตอบที่ถูกต้อง: ตัวเลือก C
💡 Official Explanation (คำอธิบายเฉลย):

The Deploy stage covers automating CI/CD, configuring environments and managing deployments. Build covers implementation, tests and PRs.

Early in building an agent, how large does an eval set need to be before it tells you anything useful?

คำแปลโจทย์:
ในช่วงแรกของการสร้าง Agent ชุดการประเมินต้องมีขนาดใหญ่แค่ไหนก่อนที่มันจะบอกอะไรที่เป็นประโยชน์แก่คุณ?
คำตอบที่ถูกต้อง: ตัวเลือก A
💡 Official Explanation (คำอธิบายเฉลย):

Early changes tend to have large effects, so a small set built from real usage patterns is enough to see them. Anthropic warns specifically against waiting for a large eval set before starting.

On the Exam:: The same discipline applies when you migrate models. Anthropic's advice to test your applications with newer models well before your current model retires is an eval run: score the replacement on your own labelled cases before you switch traffic to it.
คำอธิบายเจาะลึก (Deep Dive):
ในการสอบ วินัยเดียวกันนี้มีผลเมื่อคุณย้ายโมเดล คำแนะนำของ Anthropic ในการทดสอบแอปพลิเคชันของคุณด้วยโมเดลที่ใหม่กว่าก่อนที่โมเดลปัจจุบันของคุณจะเลิกใช้นั้นเป็นการประเมิน: ให้คะแนนการแทนที่บนเคสที่มีป้ายกำกับของคุณเองก่อนที่คุณจะเปลี่ยนการรับส่งข้อมูลไปใช้
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

In the Build stage, write and run tests. For an LLM system, that means evals you run every time you change a prompt or swap a model. Anthropic's research-agent team found that early changes have dramatic effects: a single prompt tweak might lift success rates from 30% to 80%. Differences that large show up in a handful of cases. So start evaluating straight away with a small set built from real usage patterns, and don't wait until you have hundreds of cases. The team says plainly that delaying evals for that reason is a mistake they often see.

As the eval set grows, grading becomes the bottleneck. Free-form outputs rarely have one correct answer, so the team used an LLM judge that scored each output against a rubric. The rubric covered factual accuracy, citation accuracy, completeness, source quality and tool efficiency. They tried several judges, one per criterion, but a single call with a single prompt that output 0.0–1.0 scores plus a pass/fail grade was the most consistent and agreed best with human judgement. Automation still doesn't replace people. Human testers noticed that early agents preferred SEO-optimised content farms to authoritative sources, and the evals had not caught it.

🔗 เอกสารอ้างอิงทางการจาก Anthropic
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The API already makes callers pin what they depend on: every request must send an anthropic-version header. Prompts need the same treatment. In a typical codebase a prompt is a string in the source, so changing or reverting it takes a PR, a CI run and a deploy. Claude Managed Agents stores prompts on the server instead. Each agents.update creates a new immutable version under the same agent ID, and each session chooses which version it runs.

The cookbook walks through a full cycle. It creates a ticket-triage agent, which comes back as version 1, and scores it on 20 labelled tickets. It then ships a v2 prompt that sends API-usage tickets to the platform team. Scored again with the pin set to v2, billing accuracy falls from 4/5 to 2/5, because billing tickets on a usage-billed product also mention API usage. Version 1 is still on the server, so rolling back means callers pass version: 1 again, and no rebuild is needed.

Why does Anthropic use rainbow deployments for its multi-agent research system?

คำแปลโจทย์:
เหตุใด Anthropic จึงใช้การปรับใช้ Rainbow สำหรับระบบการวิจัยแบบหลาย Agent
คำตอบที่ถูกต้อง: ตัวเลือก B
💡 Official Explanation (คำอธิบายเฉลย):

Updating every agent at once could break sessions that are already running. Rainbow deployments keep both versions live and move traffic over gradually.

คำแปลไทย:
การอัปเดต Agent ทุกตัวพร้อมกันสามารถขัดจังหวะเซสชันที่ทํางานอยู่แล้วได้ การปรับใช้ Rainbow จะทําให้ทั้งสองเวอร์ชันใช้งานได้และย้ายการรับส่งข้อมูลไปเรื่อยๆ
“we use rainbow deployments to avoid disrupting running agents, by gradually shifting traffic from old to new versions while keeping both running simultaneously.”
คำแปล: เราใช้การปรับใช้สายรุ้งเพื่อหลีกเลี่ยงการรบกวน Agent ที่ทํางานอยู่ โดยค่อยๆ เปลี่ยนการรับส่งข้อมูลจากเวอร์ชันเก่าไปยังเวอร์ชันใหม่ ในขณะที่ยังคงให้ทั้งสองเวอร์ชันทํางานพร้อมกัน

Server-side versioning has a cost: any key in the workspace can call agents.update, and there is no built-in approval workflow. The review step comes back if production callers always pin an explicit version and that pinned number is put under change control. Anyone can create new versions, and they receive no traffic until promoted. Promotion is a config change that goes through normal review. Because of this, the cookbook says the version pin can work like a feature flag. For higher-stakes agents, send a fraction of traffic to the new version and compare results before you promote it fully.

Agents add a deployment problem that stateless services don't have. They are long-running, stateful combinations of prompts, tools and execution logic, so when you deploy an update, some agents are in the middle of a task. Anthropic's research system doesn't move every agent to the new version at once. It uses rainbow deployments: old and new versions run side by side while traffic shifts gradually. This is one reason Anthropic says the gap between a prototype and a production agent is often wider than teams expect. In agentic systems, errors compound, and one failed step can send an agent down an entirely different path.
