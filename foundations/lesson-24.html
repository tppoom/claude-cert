1. ผู้เล่นตัวจริงของ Claude ในปัจจุบันและแต่ละระดับมีไว้เพื่ออะไร

กลุ่มผลิตภัณฑ์ปัจจุบันมี 4 รุ่นที่ครอบคลุมความสามารถ เวลาแฝง และราคา ทั้งสี่จัดการพื้นฐานเดียวกัน: การป้อนข้อความและรูปภาพ เอาต์พุตข้อความ การมองเห็น และการใช้เครื่องมือ คำถามที่แท้จริงไม่ค่อยเกิดขึ้นว่า

โมเดลจะทำงานได้หรือไม่ ขึ้นอยู่กับว่าโมเดลทำงานได้ดีเพียงใด รวดเร็วเพียงใด และโทเค็นแต่ละรายการมีราคาเท่าใด

คอลัมน์การคิดจะตั้งชื่อวิธีที่โมเดลคิดก่อนที่จะตอบ การคิดแบบปรับเปลี่ยนจะปล่อยให้คล็อดตัดสินใจ: สําหรับแต่ละคําขอ มันจะตัดสินว่าควรคิดหรือไม่และคิดมากน้อยเพียงใด ดังนั้นคําถามข้อเท็จจริงที่เรียบง่ายจึงสามารถได้รับคําตอบโดยตรงโดยไม่ต้องคิดเลย การคิดแบบขยายเป็นโหมดแบบแมนนวล: คุณกําหนดงบประมาณโทเค็นการคิดสําหรับแต่ละคําขอด้วย budget_tokens และคล็อดจะคิดเทียบกับงบประมาณนั้นก่อนที่จะตอบ เลือกระดับที่มีการคิดแบบปรับเปลี่ยนเมื่อคําขอแตกต่างกันจากเล็กน้อยไปจนถึงหนักหน่วง และคาดว่าจะกําหนดงบประมาณด้วยตนเองใน Haiku 4.5

แต่ละเลเยอร์มีงานเป็นของตัวเอง Claude Fable 5.1 เป็นโมเดลที่มีความสามารถมากที่สุด มันมีไว้สําหรับเซสชันเอเจนต์ที่ทํางานเป็นเวลาหลายชั่วโมง และการวิจัยเชิงลึกแบบหลายขั้นตอนที่นําไปสู่เอกสารที่เสร็จสมบูรณ์ Claude Opus 5.5 เป็นจุดเริ่มต้นของเวิร์กโหลดส่วนใหญ่: เอเจนต์การเขียนโค้ดอัตโนมัติหลายชั่วโมง การปรับโครงสร้างขนาดใหญ่ เวิร์กโฟลว์ที่เน้นการมองเห็นและการใช้งานคอมพิวเตอร์ Claude Sonnet 5.5 มีความสมดุลระหว่างความเร็วและความสามารถสําหรับการสร้างโค้ดประจําวัน การวิเคราะห์ข้อมูล และการใช้งานเครื่องมือเอเจนต์ Claude Haiku 4.5 มีเวลาแฝงและราคาต่ําที่สุด เหมาะสําหรับแอปพลิเคชันแบบเรียลไทม์ การประมวลผลปริมาณมาก และงานซับเอเจนต์ และเป็นเลเยอร์เดียวที่ยังคงใช้การคิดแบบขยายแทนการคิดแบบปรับตัว

ความแตกต่างของราคาจะเพิ่มขึ้นตามปริมาณ โทเค็นเอาต์พุตของ Fable มีราคาสูงกว่าของ Haiku ถึง 10 เท่า ดังนั้นงานที่มีอัตราการโอนถ่ายข้อมูลสูงที่ Haiku จัดการได้ดีจึงประหยัดได้มาก Haiku ยังมีขีดจํากัดที่เล็กกว่า: หน้าต่างบริบท 200K และเอาต์พุตสูงสุด 64K ในขณะที่อีกสามแห่งมี 1M และ 128K

The current lineup has four models that cover a range of capability, latency and price. All four handle the same basics: text and image input, text output, vision and tool use. So the real question is rarely whether a model can do a task. It is how well the model does it, how fast, and what each token costs.

The Thinking column names the way a model reasons before it answers. Adaptive thinking leaves the decision to Claude: for each request it judges whether to think and how much, so a simple factual question can get a direct reply with no thinking at all. Extended thinking is the manual mode: you set a thinking token budget on each request with budget_tokens, and Claude thinks against that budget before answering. Pick a tier with adaptive thinking when requests vary from trivial to hard, and expect to set the budget yourself on Haiku 4.5.

Each tier has its own kind of work. Claude Fable 5.1 is the most capable model. It is meant for agent sessions that run for hours and for multistep deep research carried through to a finished document. Claude Opus 5.5 is where most workloads start: multihour autonomous coding agents, large-scale refactoring, vision-heavy workflows and computer use. Claude Sonnet 5.5 balances speed and capability for everyday code generation, data analysis and agentic tool use. Claude Haiku 4.5 has the lowest latency and price. It fits real-time applications, high-volume processing and sub-agent tasks, and it is the only tier that still uses extended thinking instead of adaptive thinking.

The price differences add up at volume. Fable's output tokens cost ten times what Haiku's do, so a high-throughput job that Haiku handles well saves a lot. Haiku also has smaller limits: a 200K context window and 64K maximum output, where the other three have 1M and 128K.

There are two sensible ways to pick a first model, and the task decides which one to use. Start small and step up works well for prototyping, tight latency budgets, cost-sensitive deployments and high-volume tasks that are simple. You build on Claude Haiku 4.5 and only move to a larger model when you find a specific gap in capability. Iteration stays fast and development stays cheap, and for many common applications the small model turns out to be good enough.

Start capable and step down is for complex reasoning, scientific or mathematical work, tasks that need nuanced understanding, advanced coding, and any case where accuracy matters more than cost. Build on Claude Opus 5.5, tune your prompts for it, and check the results against your requirements. Over time, lower the effort or move to a cheaper model. If Opus 5.5 still falls short at xhigh or max effort on demanding reasoning or long-horizon agentic work, the next step up is Claude Fable 5.1.

Evals settle the choice either way. Write benchmark tests from your real prompts and data. Then compare models on accuracy, response quality and edge cases. When you weigh cost, compare cost per completed task, not cost per token. In Anthropic's measurements, each newer model solved at least as many tasks as the one before it, usually for less per solved task.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Effort sets how many tokens a model spends on a response. It trades thoroughness against token efficiency, and you set it per request as output_config.effort. It has five levels: low, medium, high, xhigh and max. Effort applies to every output token, which includes the text, tool calls and their arguments, and thinking when thinking is running. Lowering it saves time and money but gives up some capability. Raising it to max gives the most capability.

The default level, and the best place to start, depends on the model. Most models default to high, and on Claude Fable 5.1 and Claude Opus 5 that is the right starting point. Claude Opus 5.5 defaults to medium, so start there. On Claude Opus 4.8 and 4.7, xhigh is the best setting for most coding and agentic work, not the default. Claude Haiku 4.5 does not support effort.

Your results tell you which way to move. If cost is too high and quality is fine, lower the effort on the model you already use. If quality falls short after you lowered effort, put it back. If quality falls short and you never lowered effort, try the next tier up at low effort before you commit to a bigger model at its default.

Fast mode runs the same model on a faster inference configuration. It changes the speed of output, not the model. Weights, behaviour and capability stay the same, and output tokens per second rise by up to 2.5x. The gain is in output speed, not time to first token, so it shows most when you stream a long response. You opt in with speed: "fast" and the fast-mode-2026-02-01 beta header.

Only Claude Opus 5.5, Claude Opus 5 and Claude Opus 4.8 support fast mode. Claude Opus 4.7 rejects it. Fast mode is billed at a premium: on Opus 5.5 it costs $8 per million input tokens and $40 per million output tokens, double the standard $4 and $20. That makes it the opposite of effort. Effort changes how much work the model does and can lower cost. Fast mode keeps the work the same and buys quicker delivery. Use fast mode when a person is waiting on a long generated output and the speed is worth paying for. Use effort when the problem is the bill.
