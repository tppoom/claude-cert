1. Tokens: หน่วยพื้นฐานที่ Model ใช้อ่านและเขียน

Model ไม่เคยมองเห็นตัวอักษรหรือคำโดยตรง แต่มองเห็นเป็น Tokens โดยก่อนที่ Claude จะอ่าน Prompt ข้อความจะถูกตัดย่อยเป็นลำดับของ Tokens และทุกคำตอบที่ Claude สร้างขึ้นก็ออกมาเป็น Tokens เช่นกัน โดย 1 Token อาจเป็นได้ทั้งคำเต็มคำ, บางส่วนของคำ, ตัวอักษรเดี่ยวๆ หรือแม้กระทั่ง Byte ซึ่ง Tokens ขนาดใหญ่ช่วยให้ประมวลผลได้เร็ว ส่วน Tokens ขนาดเล็กช่วยให้ Model จัดการกับคำหายากที่ไม่เคยพบเห็นมาก่อนได้

สำหรับภาษาอังกฤษ เกณฑ์คร่าวๆ คือ 1 Claude Token จะครอบคลุมข้อความประมาณ 3.5 ตัวอักษร แต่อัตราส่วนนี้จะเปลี่ยนไปตามแต่ละภาษา ส่งผลให้ประโยคความหมายเดียวกันในภาษาอื่นอาจมีจำนวน Token ไม่เท่ากัน เรื่องนี้ส่งผลต่อการพัฒนาระบบจริง เพราะ Token คือหน่วยวัดขนาดของ Context Window, เป็นค่าลิมิตของ max_tokens และเป็นหน่วยคิดเงินต่อ Request เมื่อ API ส่ง Usage กลับมาใน Response จึงแสดงผลเป็นหน่วย Tokens เสมอ ไม่ใช่จำนวนคำหรือตัวอักษร

A product manager estimates a 7,000-character English document at about 7,000 tokens, "one per character". What is the better estimate, and why?

คำแปลโจทย์:
ผู้จัดการผลิตภัณฑ์ประเมินเอกสารภาษาอังกฤษ 7,000 อักขระที่ประมาณ 7,000 โทเค็น “หนึ่งโทเค็นต่ออักขระ” การประเมินที่ดีกว่าคืออะไรและทําไม?
คำตอบที่ถูกต้อง: ตัวเลือก A
💡 Official Explanation (คำอธิบายเฉลย):

Tokens can be words, subwords or characters. For Claude, an English token averages about 3.5 characters, so 7,000 characters comes to roughly 2,000 tokens. The exact count varies by language.

คำแปลไทย:
  • ▸
    โทเค็นอาจเป็นคำ คำย่อย หรืออักขระก็ได้ สำหรับ Claude โทเค็นภาษาอังกฤษมีความยาวเฉลี่ยประมาณ 3.5 อักขระ
  • ▸
    ดังนั้น 7,000 อักขระจึงคิดเป็นประมาณ 2,000 โทเค็น จำนวนที่แน่นอนจะแตกต่างกันไปตามภาษา
“For Claude, a token approximately represents 3.5 English characters, though the exact number can vary depending on the language used.”
คำแปล: สําหรับคล็อด โทเค็นแสดงถึงอักขระภาษาอังกฤษประมาณ 3.5 ตัว แม้ว่าจํานวนที่แน่นอนอาจแตกต่างกันขึ้นอยู่กับภาษาที่ใช้

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A model never sees characters or words directly. It sees tokens. Before Claude reads a prompt, the text is broken into a sequence of tokens, and every answer Claude writes is produced as tokens too. A token can be a whole word, part of a word, a single character or even a byte. Large tokens make processing efficient, and small ones let the model handle rare words it has never seen whole.

For English, a rough rule is that one Claude token covers about 3.5 characters. The ratio changes with language, so the same sentence in another language can produce a different token count. This matters well beyond trivia. Tokens are what a context window is measured in, what max_tokens caps, and what a request is billed by. When an API response reports usage, it reports tokens, not words or characters.

คุณขอให้โมเดลอธิบายแนวคิดที่รู้จักกันดี จากนั้นขอคําอ้างอิงสามคําพร้อมวันที่ตีพิมพ์ที่แน่นอน การสร้างสรรค์มีแนวโน้มมากที่สุดอยู่ที่ไหน?
คำตอบที่ถูกต้อง: ตัวเลือก C
💡 Official Explanation (คำอธิบายเฉลย):

Common concepts follow patterns the model has seen many times. Exact names, dates and citations need a true-versus-plausible distinction that next-token generation does not make.

คำแปลไทย:
แนวคิดทั่วไปเป็นไปตามรูปแบบที่โมเดลเคยเห็นมาหลายครั้ง ชื่อ วันที่ และการอ้างอิงที่แม่นยําจําเป็นต้องมีความแตกต่างระหว่างจริงและสมเหตุสมผล ซึ่งรุ่นถัดไปที่ได้รับโทเค็นไม่ได้ทํา
““Fabrication concentrates in specificity: names, dates, statistics, citations, URLs, quotes.””
คำแปล: “การผลิตมุ่งเน้นไปที่ความเฉพาะเจาะจง: ชื่อ วันที่ สถิติ การอ้างอิง URL การอ้างอิง”

Generative AI has more in common with a very sophisticated autocomplete than with a search engine. It writes an answer token by token, each time choosing what tends to follow the text so far. Nothing in that loop looks up a fact or checks one. The model keeps extending a sequence in the way its training makes most natural.

That one mechanism explains both what the model is good at and how it fails. When a task resembles patterns the model has seen many times, such as summarizing, reformatting or explaining a common concept, the likely continuation is usually also the correct one. 3. Context Window คือ Working Memory ของโมเดล

Context window คือข้อความทั้งหมดที่โมเดลสามารถนำมาอ้างอิงขณะสร้าง response ได้ ซึ่งนับรวมตัว response เองด้วย โดยส่วนนี้จะแยกจากข้อมูลมหาศาลที่โมเดลใช้ pre-train อย่างสิ้นเชิง ให้มองว่ามันคือ working memory สำหรับการเรียกใช้งาน 1 request หากข้อมูลใดไม่ได้อยู่ใน window โมเดลจะไม่สามารถ attend ถึงข้อมูลนั้นใน request นั้นได้เลย

ทุกอย่างใน request ล้วนกินพื้นที่ context window: ไม่ว่าจะเป็น system prompt, ทุกข้อความใน messages (รวมถึง tool results, รูปภาพ และเอกสาร) ตลอดจน tool definitions นอกจากนี้ output ที่ Claude สร้างขึ้นในแต่ละ turn ก็นับรวมด้วย (รวมถึง extended thinking) ในการสนทนาแบบ multi-turn ผ่าน API แต่ละ response จะกลายเป็นส่วนหนึ่งของ input ใน turn ถัดไป และระบบจะเก็บ turn ก่อนหน้าไว้ครบถ้วน ทำให้ window ค่อยๆ เต็มขึ้นเรื่อยๆ ตามการสนทนา โดยทุก response จะระบุจำนวน token ที่ใช้ไปในฟิลด์ usage

The context window is all the text the model can refer to while generating a response, including the response itself. It is separate from the huge body of data the model was trained on. Think of it as working memory for one request. If something is not in the window, the model cannot attend to it in that request.

Everything in the request takes up space: the system prompt, every message in messages (tool results, images and documents included) and your tool definitions. The output Claude generates for the turn also counts, including any extended thinking. In a multi-turn conversation over the API, each response becomes part of the input for the next turn and earlier turns are kept in full, so the window fills as the conversation goes on. Every response reports what it consumed in its usage field.

Window size is fixed per model. Claude Opus 5.5, Opus 4.8, Sonnet 5.5, Sonnet 4.6 and the other current flagship models have a 1M-token window, and 1M is the default with no beta header. Claude Sonnet 4.5, Claude Haiku 4.5 and other older models have 200k. A 700,000-token contract therefore fits in one request to Opus 4.8 but not to Sonnet 4.5. Bigger is not automatically better, though. As the token count grows, accuracy and recall degrade, which is called context rot. What you put in the window matters as much as how much room it has.

A prompt can include no examples, one, or several: zero-shot, single-shot and multi-shot prompting. How to write each one is covered in [Zero-, one- and few-shot prompting](lesson:6.2). The question here is why they work at all.

Examples work because they sit in the context window. The model picks up the pattern there during the request, the same way it picks up any other text it attends to. Nothing about the model changes. Changing the model itself is fine-tuning, which means further training a pretrained model on additional data, and the Claude API does not currently offer it. Whatever a few-shot prompt teaches lasts only for that request. The next request has to carry the examples again, and they take up window space every time.

Next-token generation also explains why example choice matters. The model continues whatever patterns the context shows, including ones you did not intend. If every example has the same length or opening phrase, the output will copy that as well. Diverse examples that cover edge cases teach the pattern you want and not an accident of how the examples were written.

Run the same request twice in fresh conversations and you will usually get two different answers. This is how generation works, not a bug. At each step the model has many possible next tokens, and it samples one of them instead of always taking the most likely. The variation between runs is that sampling at work.

Three parameters shape the sampling:

- temperature controls how random the choices are. It defaults to 1.0 and ranges from 0.0 to 1.0. Lower values keep to the most probable phrasing; higher values allow rarer, more surprising words. Use values near 0.0 for analytical or multiple-choice work and near 1.0 for creative work. - top_k samples only from the K most likely options for each next token, which cuts off the long tail of unlikely choices. - top_p (nucleus sampling) cuts the options off by cumulative probability instead of by count.

Two cautions apply. First, temperature 0 does not make Claude deterministic: identical inputs can still give different outputs across API calls. Design for variation by validating outputs and not relying on byte-identical responses. Second, on current models these knobs are mostly locked. On Claude Opus 5.5, Opus 4.8, Opus 4.7, Sonnet 5.5, Sonnet 5 and the other Claude 5 models, any non-default temperature, top_p or top_k returns a 400 error. On older models the restriction applies only while thinking is on.

Non-determinism คือคุณลักษณะที่ Input แบบเดิมเป๊ะอาจสร้าง Output ที่ต่างกันได้ในการเรียก API แต่ละครั้ง ส่งผลกระทบโดยตรงต่อระบบที่พึ่งพาการเทียบ Response เช่น Regression Test ที่ใช้ Diff คำตอบกับ Baseline เดิม, Cache ที่ใช้ Text ของ Output เป็น Key หรือ Audit Workflow ที่คาดหวังให้การรันซ้ำสร้างผลลัพธ์เดิม ต้นเหตุเกิดจาก Per-token Sampling ตามที่กล่าวไว้ข้างต้น และพฤติกรรมนี้เกิดขึ้นเหมือนกันทั้งบน First-party Inference Service ของ Anthropic และ Third-party Cloud Providers การย้าย Workload ไป Cloud Provider อื่นจึงไม่ได้ช่วยให้ผลลัพธ์เป็น Deterministic แต่อย่างใด

ความผันแปรนี้ส่งผลไปถึงจำนวน Token ด้วย ไม่ใช่แค่การเลือกคำ ด้วยฟีเจอร์ Adaptive Thinking ตัว Claude จะตัดสินใจ Allocation ของ Thinking Token เองในแต่ละ Request ทำให้การใช้งาน Thinking Token (ซึ่งถูกคิดเงินเป็น Output) เปลี่ยนแปลงไปในแต่ละ Run แม้ใช้ Prompt เดิม การประเมิน Cost จากการยิงเพียง Run เดียวจึงอาจคลาดเคลื่อนได้ ควรคำนวณ Budget และ max_tokens จาก Range ค่าเฉลี่ยที่ได้จากการทดสอบหลายๆ Run แทน

Non-determinism is the property that identical inputs may produce different outputs across API calls. It breaks anything that compares two responses: a regression test that diffs today's answer against a stored one, a cache keyed on output text, an audit that expects a rerun to reproduce a decision. The cause is the per-token sampling described in [the sampling section above], and it holds on Anthropic's first-party inference service and through third-party cloud providers alike. Moving a workload to a cloud provider does not buy repeatable output.

No setting has ever switched it off. Temperature 0 never guaranteed identical outputs, even on older models that accepted it, so code migrating to a newer model loses nothing real when it drops temperature=0. Drop the assumption of repeatability along with the parameter.

The variation reaches token counts, not just wording. With adaptive thinking, Claude decides its thinking allocation per request, so thinking token usage, billed as output, changes from one run of the same prompt to the next. A cost estimate taken from a single run can be off in either direction; size budgets and max_tokens from the range seen over many runs.

A pipeline that expects non-deterministic output checks it the way a lab handles a noisy measurement:

- Validate structure and meaning (a parseable JSON object, the right label, the required fields) instead of byte equality. - Run each eval case more than once and note which parts hold steady and which shift between runs. - Store the response you acted on when a decision must be auditable, because a rerun is a new sample, not a replay.

Next-token generation — โมเดลภาษาเขียนคำตอบทีละ Token โดยคัดเลือก Token ถัดไปจากความน่าจะเป็นของข้อความก่อนหน้า กระบวนการนี้ทำให้ประโยคมีความลื่นไหลเป็นธรรมชาติ แต่ก็เปิดช่องให้เกิดการแต่งข้อมูลเท็จที่ฟังดูสมเหตุสมผลได้เช่นกัน

📌 สาระสำคัญแยกตามทุกหัวข้อ (Topic-by-Topic Key Points)
6 หัวข้อ

#1 1. Tokens: หน่วยพื้นฐานที่ Model ใช้อ่านและเขียน

อ่านเนื้อหา ↗
  • •
    Model ไม่เคยมองเห็นตัวอักษรหรือคำโดยตรง แต่มองเห็นเป็น Tokens โดยก่อนที่ Claude จะอ่าน Prompt ข้อความจะถูกตัดย่อยเป็นลำดับของ Tokens และทุกคำตอบที่ Claude สร้างขึ้นก็ออกมาเป็น Tokens เช่นกัน โดย 1 Token อาจเป็นได้ทั้งคำเต็มคำ, บางส่วนของคำ, ตัวอักษรเดี่ยวๆ หรือแม้กระทั่ง Byte ซึ่ง Tokens ขนาดใหญ่ช่วยให้ประมวลผลได้เร็ว ส่วน Tokens ขนาดเล็กช่วยให้ Model จัดการกับคำหายากที่ไม่เคยพบเห็นมาก่อนได้
  • •
    สำหรับภาษาอังกฤษ เกณฑ์คร่าวๆ คือ 1 Claude Token จะครอบคลุมข้อความประมาณ 3.5 ตัวอักษร แต่อัตราส่วนนี้จะเปลี่ยนไปตามแต่ละภาษา ส่งผลให้ประโยคความหมายเดียวกันในภาษาอื่นอาจมีจำนวน Token ไม่เท่ากัน เรื่องนี้ส่งผลต่อการพัฒนาระบบจริง เพราะ Token คือหน่วยวัดขนาดของ Context Window, เป็นค่าลิมิตของ max_tokens และเป็นหน่วยคิดเงินต่อ Request
  • •
    เมื่อ API ส่ง Usage กลับมาใน Response จึงแสดงผลเป็นหน่วย Tokens เสมอ ไม่ใช่จำนวนคำหรือตัวอักษร

#2 2. การสร้าง Next-token และสาเหตุของการ Hallucinate

อ่านเนื้อหา ↗
  • •
    หลักการทำงานของ Generative AI มีความคล้ายคลึงกับระบบ Autocomplete ขั้นสูงมากกว่า Search Engine โดย Model จะสร้างคำตอบทีละ Token และในแต่ละสเต็ปจะเลือก Token ที่น่าจะตามหลังข้อความก่อนหน้ามากที่สุด ไม่มีกระบวนการใดใน Loop นี้ที่ไปค้นหา Fact หรือ Verify ความถูกต้อง Model เพียงแค่ต่อเติม Sequence ไปข้างหน้าตามรูปแบบที่ถูกเทรนมาให้ดูเป็นธรรมชาติที่สุด
  • •
    นำหลักการนี้มาเป็นเกณฑ์ในการตั้ง Guardrails และ Review
  • •
    รวมถึง Generator-Verifier Loops จึงถูกนำมาใช้เพื่อก้าวข้ามข้อจำกัดธรรมชาตินี้ของ Model

#3 3. Context Window คือ Working Memory ของโมเดล

อ่านเนื้อหา ↗
  • •
    ทุกอย่างใน request ล้วนกินพื้นที่ context window: ไม่ว่าจะเป็น system prompt, ทุกข้อความใน messages (รวมถึง tool results, รูปภาพ และเอกสาร) ตลอดจน tool definitions
  • •
    ขนาดของ window ถูกกำหนดตายตัวตามแต่ละโมเดล โดย Claude Opus 5.5, Opus 4.8, Sonnet 5.5, Sonnet 4.6 และโมเดล flagship ปัจจุบันมี context window ขนาด 1M tokens ซึ่ง 1M เป็นค่า default โดยไม่ต้องใส่ beta header ส่วน Claude Sonnet 4.5, Claude Haiku 4.5 และโมเดลรุ่นเก่าจะมีขนาด 200k tokens
  • •
    เอกสารสัญญาขนาด 700,000 tokens จึงใส่ใน request เดียวของ Opus 4.8 ได้ แต่ใส่ใน Sonnet 4.5 ไม่ได้ อย่างไรก็ตาม ขนาดที่ใหญ่กว่าไม่ได้แปลว่าดีกว่าเสมอไป

#4 4. ทำไมตัวอย่างถึงช่วยชี้นำโมเดลได้โดยไม่ต้อง Retrain

อ่านเนื้อหา ↗
  • •
    ตัวอย่างทำงานได้เพราะมันอยู่ใน context window โมเดลจะจับ pattern จากตรงนั้นระหว่างประมวลผล request เช่นเดียวกับการ attend ข้อความอื่นๆ โดยไม่มีการเปลี่ยนแปลงตัวโมเดลแต่อย่างใด การเปลี่ยนตัวโมเดลจริงๆ คือการ fine-tuning ซึ่งเป็นการนำ pretrained model มาเทรนต่อด้วยข้อมูลเพิ่มเติม ซึ่งปัจจุบัน Claude API ยังไม่มีฟีเจอร์นี้ สิ่งที่ few-shot prompt สอนโมเดลจะคงอยู่เฉพาะใน request นั้นเท่านั้น request ถัดไปจำเป็นต้องส่งตัวอย่างเข้าไปใหม่ และยังคงกินพื้นที่ context window ทุกครั้ง
  • •
    กลไกการสร้าง next-token ยังอธิบายได้ว่าทำไมการคัดเลือกตัวอย่างถึงสำคัญ โมเดลจะสานต่อ pattern ใดก็ตามที่ปรากฏใน context
  • •
    Prompt สามารถกำหนดได้ทั้งแบบไม่มีตัวอย่าง มีหนึ่งตัวอย่าง หรือมีหลายตัวอย่าง ได้แก่ zero-shot, single-shot และ multi-shot prompting ส่วนวิธีการเขียนแต่ละแบบมีอธิบายไว้ใน [Zero-, one- and few-shot prompting](lesson:6.2) แต่ประเด็นสำคัญในที่นี้คือทำไมวิธีเหล่านี้ถึงใช้งานได้ผล

#5 5. Sampling: ทำไม Prompt เดิมถึงได้คำตอบต่างกัน

อ่านเนื้อหา ↗
  • •
    การยิง Request เดิมซ้ำใน Conversation ใหม่มักจะได้คำตอบไม่เหมือนกัน นี่คือพฤติกรรมปกติของโมเดล Generative ไม่ใช่ Bug เพราะในแต่ละ Step ตัวโมเดลจะมี Next Token ที่เป็นไปได้มากมาย และใช้วิธีการสุ่มเลือก (Sampling) หนึ่งในนั้น
  • •
    สุ่มเลือกจาก Token ที่น่าจะเป็นไปได้มากที่สุดเพียง K ลำดับแรก ช่วยตัด Long-tail ของคำที่ไม่ค่อยเกิดขึ้นออกไป - top_p (nucleus sampling)
  • •
    ข้อควรระวัง 2 ประการ: ข้อแรก การตั้ง temperature เป็น 0 ไม่ได้ทำให้ Claude กลายเป็น Deterministic เพราะ Input ที่เหมือนกันทุกประการยังคงให้ Output ที่ต่างกันได้ข้าม API calls

#6 6. Non-determinism: การออกแบบระบบรับมือกับ Output ที่เปลี่ยนแปลงได้ในแต่ละ Run

อ่านเนื้อหา ↗
  • •
    Non-determinism คือคุณลักษณะที่ Input แบบเดิมเป๊ะอาจสร้าง Output ที่ต่างกันได้ในการเรียก API แต่ละครั้ง ส่งผลกระทบโดยตรงต่อระบบที่พึ่งพาการเทียบ Response เช่น Regression Test ที่ใช้ Diff คำตอบกับ Baseline เดิม, Cache ที่ใช้ Text ของ Output เป็น Key หรือ Audit Workflow ที่คาดหวังให้การรันซ้ำสร้างผลลัพธ์เดิม ต้นเหตุเกิดจาก Per-token Sampling ตามที่กล่าวไว้ข้างต้น และพฤติกรรมนี้เกิดขึ้นเหมือนกันทั้งบน First-party Inference Service ของ Anthropic และ Third-party Cloud Providers การย้าย Workload ไป Cloud Provider อื่นจึงไม่ได้ช่วยให้ผลลัพธ์เป็น Deterministic แต่อย่างใด
  • •
    ความผันแปรนี้ส่งผลไปถึงจำนวน Token ด้วย ไม่ใช่แค่การเลือกคำ ด้วยฟีเจอร์ Adaptive Thinking ตัว Claude จะตัดสินใจ Allocation ของ Thinking Token เองในแต่ละ Request ทำให้การใช้งาน Thinking Token (ซึ่งถูกคิดเงินเป็น Output) เปลี่ยนแปลงไปในแต่ละ Run แม้ใช้ Prompt เดิม การประเมิน Cost จากการยิงเพียง Run เดียวจึงอาจคลาดเคลื่อนได้ ควรคำนวณ Budget และ max_tokens จาก Range ค่าเฉลี่ยที่ได้จากการทดสอบหลายๆ Run แทน
  • •
    ไม่เคยมีการตั้งค่าใดที่สามารถปิด Non-determinism ได้ การเซ็ต temperature เป็น 0 ไม่เคยการันตีว่าจะได้ Output เหมือนเดิม แม้ในโมเดลรุ่นเก่าที่ยังยอมรับค่านั้น
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (4 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Prompt caching ช่วยคืนพื้นที่ใน context window เพราะ cached tokens ไม่ต้องถูกส่งซ้ำใช่หรือไม่?
Prompt caching frees context window space, because cached tokens are not re-sent.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Caching ช่วยลดราคาและ latency ของ prefix ที่ถูก cache เท่านั้น แต่ token เหล่านั้นยังคงกินพื้นที่ใน context window ตามปกติ
Caching changes the price of the cached prefix, but those tokens still occupy the context window.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
การตั้ง temperature เป็น 0 จะทำให้ Claude ทำงานแบบ Deterministic เต็มรูปแบบ และ Prompt เดิมจะได้ Text เดิมเสมอ?
Setting temperature to 0 makes Claude's output fully deterministic, so identical prompts always return identical text.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: temperature 0 เพียงแต่โน้มเอียงไปทางตัวเลือกที่มีความน่าจะเป็นสูงสุด แต่ Input เดียวกันยังคงสร้าง Output ที่ต่างกันได้ข้าม API calls การลดค่า temperature สามารถใช้เพิ่ม Consistency ให้กับคำตอบได้บน Claude ทุกโมเดลเสมอ? (ทำไมถึงผิด): ไม่จริง: บนโมเดล Claude 5 และ Opus 4.7 ขึ้นไป การปรับเปลี่ยน temperature, top_p หรือ top_k เป็นค่าอื่นที่ไม่ใช่ Default จะถูก Reject ด้วย 400 Error ทันที ไม่ว่าจะเปิดใช้งาน Thinking หรือไม่ก็ตาม
Temperature 0 favours the most probable choices, but identical inputs can still produce different outputs across API calls. Lowering temperature is always a valid way to make answers more consistent on any Claude model. (ทำไมถึงผิด): On Claude 5 models and Opus 4.7 or later, any non-default temperature, top_p or top_k returns a 400 error, whether or not thinking is used.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
ถ้าเจอช้อยส์เสนอ "ตั้งค่า temperature เป็น 0" เพื่อการันตีว่าจะได้ Output เดิมทุกครั้ง?
On the Exam:: If a question offers "set temperature to 0" as the way to guarantee identical outputs, it is wrong. Temperature 0 makes outputs more conservative, not deterministic. On Claude 5 models and Opus 4.7 or later, changing temperature from its default is rejected with a 400 error.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: temperature 0 ทำให้ผลลัพธ์ Conservative ขึ้นเท่านั้น แต่ไม่ได้ทำให้เป็น Deterministic และบน Claude 5 กับ Opus 4.7 ขึ้นไป การเปลี่ยนค่า temperature จาก Default จะได้ 400 Error กลับมา
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
Non-determinism เป็นเฉพาะข้อจำกัดของ Anthropic API เท่านั้น หากรัน Claude ผ่าน Third-party Cloud Provider จะได้ Output ที่เหมือนเดิมสำหรับ Input เดิมเสมอ?
Non-determinism is a quirk of Anthropic's own API; running Claude through a third-party cloud provider returns identical outputs for identical inputs.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Input เดียวกันสามารถให้ Output ต่างกันได้ ทั้งบน First-party Inference Service ของ Anthropic และ Third-party Cloud Provider เหมือนกันทั้งหมด
Identical inputs can produce different outputs on Anthropic's first-party inference service and on third-party cloud providers alike.

  • ✓อธิบายความหมายของ Token และประเมินการแปลงข้อความเป็น Tokens ได้
  • ✓อธิบายกลไก Next-Token Generation ที่สร้างผลลัพธ์สละสลวยแต่เสี่ยงต่อการ Fabricate และระบุจุดที่มักเกิดความคลาดเคลื่อน
  • ✓คำนวณสิ่งที่นับรวมใน Context Window ของแต่ละ Request และเลือกโมเดลที่รองรับขนาด Input ที่กำหนดได้
  • ✓อธิบายเหตุผลที่การใส่ Examples ใน Prompt ช่วยชี้นำ Output ได้โดยไม่ต้อง Retrain โมเดล
  • ✓อธิบายสาเหตุที่ Prompt เดียวกันให้ Output ต่างกัน พร้อมเข้าใจบทบาทของ Temperature, top_k และ top_p
  • ✓ออกแบบ Tests, Caching และ Cost Budget ให้รองรับ Non-Determinism ข้ามรอบการรันและต่าง Provider ได้
