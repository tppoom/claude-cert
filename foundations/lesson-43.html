💡 แนวคิดหลักสำคัญ (Key Concept)

MCP server primitives — An MCP server is a small, focused program that offers three kinds of capability to a host application: tools the model can call, resources that supply context, and prompts that act as reusable message templates. The host keeps control of the conversation, and the server only answers the requests it receives.

MCP involves three roles, and it helps to keep them apart. The host is the application the user works in, such as Claude Code or your own agent. It creates and manages several client instances, enforces security policies and consent, handles authorization decisions, and coordinates the LLM integration. Each client lives inside the host and holds exactly one connection to one server. It attaches the protocol version and capabilities to every request, routes messages in both directions, and keeps servers isolated from each other. The server exposes tools, resources, and prompts, and it can run as a local process or as a remote service.

The spec gives a few design principles for this split. Servers should be extremely easy to build, because the host does the complex orchestration. They should be composable, so several focused servers can be combined. And they should not be able to read the whole conversation or see into other servers. A server receives only the context it needs, and the full conversation history stays with the host.

A server implements a `tools/call` handler but leaves `tools` out of its capabilities. What does the spec say?

คำตอบที่ถูกต้อง: ตัวเลือก B
💡 คำอธิบายเฉลยภาษาไทย (Thai Explanation):

การเจรจาต่อรองความสามารถมีผลผูกพัน เซิร์ฟเวอร์ที่ไม่ได้ประกาศความสามารถของเครื่องมือจะไม่สามารถเรียกใช้เครื่องมือได้

EN: Capability negotiation is binding. A server that has not declared tool capabilities cannot have its tools invoked.
“Tool invocation requires the server to declare tool capabilities”
🔗 เอกสารอ้างอิง Anthropic
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Features are negotiated, not assumed. A server declares capabilities such as tool support, resource subscriptions, and prompt templates. A client declares its own capabilities, such as support for sampling and elicitation. Both sides must then respect what was declared for the rest of the interaction. In practice, any feature your server implements has to be advertised in its capabilities. A server that registers tool handlers but never declares tools cannot have those tools invoked.

With listChanged: true, the server is promising to send notifications/tools/list_changed when its tool set changes, so the client knows to fetch the list again. Resources and prompts use the same pattern under their own capability keys.

Capabilities describe what a server offers. The communication pattern describes how its messages travel, and the two are independent. The first pattern is stdio, used for local servers. The client launches the server as a child process, and the server reads JSON-RPC messages from stdin and writes JSON-RPC messages to stdout. Each message is a single JSON-RPC request, notification, or response. Messages are delimited by newlines and must not contain embedded newlines. Claude Code connects this way, as in claude mcp add --transport stdio airtable -- npx -y airtable-mcp-server. There the command after -- is the process Claude Code spawns. An SDK server does the same by connecting a StdioServerTransport.

Because stdout carries the protocol, a stdio server must never print anything else to it, and the client must never send anything to stdin that is not a valid MCP message. A stray print or console.log corrupts the stream. Log to stderr instead, which the spec allows for any logging purposes. The client may capture, forward, or ignore that output, and it should not assume stderr output means an error. To shut down, the client closes the input stream to the child process and waits for the server to exit. If the server does not exit in a reasonable time, the client forcibly terminates it.

The second pattern is Streamable HTTP, used for remote servers. Here the server is a standalone service that exposes a single HTTP endpoint accepting POST, and the client sends every JSON-RPC request or notification as its own POST. The server answers with either one JSON object or an SSE stream. Claude Code reaches such a server with claude mcp add --transport http . The older sse transport and a ws WebSocket entry are also accepted in Claude Code configuration. In both patterns the client opens the connection and the server answers requests. The difference is whether the client starts the server process (stdio) or connects to one that is already running (HTTP).

คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A tool definition has a unique name, an optional display title, a description, an inputSchema, an optional outputSchema, and optional annotations and icons. Tool names should be 1–128 characters, are treated as case-sensitive, should use only ASCII letters, digits, _, -, and., and should be unique within a server. getUser, DATA_EXPORT_v2 and admin.tools.list are all valid names.

inputSchema defaults to JSON Schema 2020-12 when no $schema field is present. For a tool with no parameters, the recommended schema is { "type": "object", "additionalProperties": false }. Clients find tools with tools/list, which is paginated with a cursor, and run them with tools/call, passing name and arguments. A result carries a content array, which can hold text, image, audio, resource_link, or embedded resource items, plus an isError flag. If you declare an outputSchema, the server must also return structuredContent that conforms to it.

Some tools create state that later calls refer to by handle, for example a create_basket call that returns a basket_id. For these tools, state the retention policy in the creation tool's description. When a call uses an expired or unknown handle, return a tool execution error so the model can recover. On the host side, the spec expects a human in the loop: the UI should make exposed tools visible, show when a tool is invoked, and ask the user to confirm operations.

🔗 เอกสารอ้างอิง Anthropic
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A resource is data identified by a uri. It also has a name and, optionally, a title, description, mimeType, size, and icons. Clients list resources with resources/list and fetch them with resources/read. Each item in the returned contents holds either text or base64 blob data. For parameterised access, resources/templates/list returns URI templates such as file:///{path}. Annotations tell the client how to use a resource: audience (user and/or assistant), priority from 0.0 to 1.0, and lastModified.

The resources capability has two optional flags. listChanged means the server will send a notification when the set of resources changes. subscribe means it supports update notifications for individual resources requested through subscriptions/listen. Security falls on the server. It must validate every resource URI, must encode binary data properly, should apply access controls to sensitive resources, and must sanitize file paths when serving file:// resources. If a resource does not exist, the server returns error -32602 with the URI in data.
