💡 แนวคิดหลักสำคัญ (Key Concept)

MCP Server Primitives — MCP Server คือโปรแกรมขนาดเล็กที่ออกแบบมาเฉพาะทางเพื่อส่งมอบ 3 ขีดความสามารถหลักแก่ Host Application ได้แก่ Tools ที่โมเดลเรียกใช้ได้, Resources สำหรับป้อน Context และ Prompts ที่ทำหน้าที่เป็น Reusable Message Templates โดยที่ Host ยังคงเป็นผู้ควบคุมทิศทางการสนทนาทั้งหมด และ Server ทำหน้าที่เพียงตอบกลับตามคำขอที่ได้รับเท่านั้น

1. Host, client, and server

  1. 1
    Host คือแอปพลิเคชันหลักที่ผู้ใช้ทำงานด้วย (เช่น Claude Code หรือ Custom Agent ของคุณ) ทำหน้าที่สร้างและจัดการ Client instances, บังคับใช้ Security Policies/Consent, จัดการสิทธิ์ (Authorization) และเชื่อมโยงการทำงานร่วมกับ LLM
  2. 2
    Client จะรันอยู่ภายใน Host โดย 1 Client instance จะเชื่อมต่อกับ 1 Server เสมอ มีหน้าที่แนบ Protocol Version และ Capabilities ไปกับทุก Request, จัดการ Route ข้อความแบบ 2 ทิศทาง และแยกแต่ละ Server ไม่ให้ยุ่งเกี่ยวกัน (Isolation)
  3. 3
    Server คือตัวที่ Provide เครื่องมือ (Tools), ข้อมูล (Resources) และ Templates (Prompts) ซึ่งสามารถรันเป็น Local Process หรือ Remote Service ก็ได้

หลักการออกแบบ (Design Principles) ตามข้อกำหนดของ MCP ในการแบ่งบทบาทนี้คือ: Server ควรสร้างง่ายที่สุด เพราะหน้าที่ Orchestration ที่ซับซ้อนยกให้ Host จัดการ

; แต่ละ Server ต้อง Composable เพื่อรวมหลายๆ Server ที่โฟกัสเฉพาะทางเข้าด้วยกันได้; และ Server ต้องไม่สามารถอ่านประวัติ Conversation ทั้งหมด หรือสอดส่อง Server ตัวอื่นได้ โดย Server จะได้รับเฉพาะ Context ที่จำเป็นเท่านั้น ส่วน Full Conversation History จะอยู่กับ Host ตลอดเวลา

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

MCP involves three roles, and it helps to keep them apart. The host is the application the user works in, such as Claude Code or your own agent. It creates and manages several client instances, enforces security policies and consent, handles authorization decisions, and coordinates the LLM integration. Each client lives inside the host and holds exactly one connection to one server. It attaches the protocol version and capabilities to every request, routes messages in both directions, and keeps servers isolated from each other. The server exposes tools, resources, and prompts, and it can run as a local process or as a remote service.

The spec gives a few design principles for this split. Servers should be extremely easy to build, because the host does the complex orchestration. They should be composable, so several focused servers can be combined. And they should not be able to read the whole conversation or see into other servers. A server receives only the context it needs, and the full conversation history stays with the host.

2. Declaring capabilities

Features ใน MCP ทำงานผ่านการตกลง (Negotiated) ร่วมกัน ไม่มีการทึกทักเอาเอง ฝั่ง Server ต้องประกาศ Capabilities เช่น Tools Support, Resource Subscriptions และ Prompt Templates ขณะที่ฝั่ง Client จะประกาศ Capabilities ของตนเอง เช่น Sampling และ Elicitation จากนั้นทั้งสองฝั่งต้องยึดตามสิ่งที่ประกาศไว้ตลอด Session ในทางปฏิบัติ ฟีเจอร์ใดๆ ที่ Server สร้าง Handler รองรับไว้ จะต้องถูกระบุใน Capabilities ด้วยเสมอ หาก Server มี Tool Handler แต่ไม่ประกาศ Tools ใน Capabilities ฝั่ง Client จะไม่สามารถเรียกใช้ Tool นั้นได้เลย

A server declaring tool support and promising list-change notifications json
เซิร์ฟเวอร์ประกาศการสนับสนุนเครื่องมือและสัญญา Prompt การเปลี่ยนแปลงรายการ json
{
  "capabilities": {
    "tools": {
      "listChanged": true
    }
  }
}

เมื่อตั้งค่า `listChanged: true` Server กำลังรับปากว่าจะส่ง Prompt `notifications/tools/list_changed` เมื่อชุด Tools มีการเปลี่ยนแปลง เพื่อให้ Client รับรู้และเรียก Fetch รายการ Tools ใหม่อีกครั้ง สำหรับ Resources และ Prompts ก็ใช้รูปแบบเดียวกันภายใต้ Capability Keys ของตนเอง

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
Implementing a handler is enough for clients to use a feature, so capability declaration is optional. (ทำไมถึงผิด): Server features must be advertised in the server's capabilities, and tool invocation specifically requires the tools capability to be declared. A stdio server can print debug output to stdout, since the client simply ignores text it does not recognise. (ทำไมถึงผิด): stdout carries the protocol, so anything that is not a valid MCP message breaks the stream. Logging belongs on stderr.

แค่ Implement Handler ก็เพียงพอให้ Client เรียกใช้ฟีเจอร์ได้แล้ว Capability Declaration เป็นแค่ Optional? (ทำไมถึงผิด): ไม่จริง: Features ของ Server ต้องประกาศใน Capabilities เสมอ และการเรียกใช้ Tool ต้องมีการประกาศ tools capability อย่างชัดเจน มิเช่นนั้น Client จะเรียกใช้งานไม่ได้ | stdio Server สามารถ Print Debug ออก stdout ได้ เพราะ Client จะ Ignore Text ที่ไม่รู้จักทิ้งไปเอง? (ทำไมถึงผิด): ไม่จริง: stdout ถูกใช้ส่ง MCP Protocol (JSON-RPC) โดยเฉพาะ ข้อความใดๆ ที่ไม่ใช่ Valid MCP Message จะทำให้ Stream เสียหายทันที การ Log ต้องส่งไปที่ stderr เท่านั้น

Capabilities กำหนดว่า Server ให้บริการอะไร ส่วน Communication Pattern กำหนดว่าข้อความถูกรับส่งอย่างไร ซึ่งทั้งสองส่วนเป็นอิสระต่อกัน รูปแบบแรกคือ `stdio` ใช้สำหรับ Local Server โดย Client จะ Spawn Server เป็น Child Process ตัว Server จะอ่าน JSON-RPC Messages ผ่าน `stdin` และส่ง JSON-RPC Messages ผ่าน `stdout` แต่ละ Message คือ 1 Request, Notification หรือ Response แยกบรรทัดด้วย Newlines และห้ามมี Newlines ภายในตัว Message เด็ดขาด ตัวอย่างเช่น Claude Code เชื่อมต่อด้วยคำสั่ง `claude mcp add --transport stdio airtable -- npx -y airtable-mcp-server` (คำสั่งหลัง `--` คือ Process ที่ถูก Spawn) หรือใน SDK จะใช้ `StdioServerTransport`

เนื่องจาก `stdout` ถูกสงวนไว้ สำหรับ Protocol โดยเฉพาะ stdio Server จึงห้าม Print ข้อความอื่นใดลงไปอย่างเด็ดขาด และ Client ก็ห้ามส่งข้อความที่ไม่ใช่ Valid MCP Message เข้า `stdin` เช่นกัน หากมี `print` หรือ `console.log` แปลกปลอมหลุดเข้าไปจะทำให้ Stream เสียหาย (Corrupted) ให้ Log ผ่าน `stderr` แทน ซึ่งข้อกำหนดของ MCP อนุญาตให้ใช้สำหรับทุกประเภทการ Log ฝั่ง Client อาจดักอ่าน, ส่งต่อ หรือข้าม Log นั้นได้ และจะไม่ทึกทักว่า `stderr` คือ Error ส่วนขั้นตอน Shutdown ฝั่ง Client จะปิด Input Stream ของ Child Process แล้วรอให้ Server Exit หาก Server ไม่ยอมปิดในเวลาที่เหมาะสม Client จะทำการ Force Terminate ทันที

รูปแบบที่สองคือ Streamable HTTP ใช้สำหรับ Remote Server โดย Server จะเป็น Standalone Service ที่เปิด HTTP Endpoint เดี่ยวรองรับ POST และ Client จะส่งทุก JSON-RPC Request หรือ Notification เป็นแต่ละ POST Call ฝั่ง Server จะตอบกลับเป็น JSON Object ตัวเดียวหรือ SSE Stream ก็ได้ ใน Claude Code สามารถเพิ่มผ่านคำสั่ง `claude mcp add --transport http <name> <url>` (รวมถึงรองรับ `sse` และ `ws` WebSocket แบบเดิมในการคอนฟิก) ทั้งสองรูปแบบ Client จะเป็นฝ่ายเริ่ม Connect และ Server เป็นผู้ตอบกลับ ข้อแตกต่างหลักคือ Client เป็นตัว Spawn Process เอง (stdio) หรือเชื่อมต่อไปยัง Service ที่รันอยู่แล้ว (HTTP)

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Features are negotiated, not assumed. A server declares capabilities such as tool support, resource subscriptions, and prompt templates. A client declares its own capabilities, such as support for sampling and elicitation. Both sides must then respect what was declared for the rest of the interaction. In practice, any feature your server implements has to be advertised in its capabilities. A server that registers tool handlers but never declares tools cannot have those tools invoked.

With listChanged: true, the server is promising to send notifications/tools/list_changed when its tool set changes, so the client knows to fetch the list again. Resources and prompts use the same pattern under their own capability keys.

Capabilities describe what a server offers. The communication pattern describes how its messages travel, and the two are independent. The first pattern is stdio, used for local servers. The client launches the server as a child process, and the server reads JSON-RPC messages from stdin and writes JSON-RPC messages to stdout. Each message is a single JSON-RPC request, notification, or response. Messages are delimited by newlines and must not contain embedded newlines. Claude Code connects this way, as in claude mcp add --transport stdio airtable -- npx -y airtable-mcp-server. There the command after -- is the process Claude Code spawns. An SDK server does the same by connecting a StdioServerTransport.

Because stdout carries the protocol, a stdio server must never print anything else to it, and the client must never send anything to stdin that is not a valid MCP message. A stray print or console.log corrupts the stream. Log to stderr instead, which the spec allows for any logging purposes. The client may capture, forward, or ignore that output, and it should not assume stderr output means an error. To shut down, the client closes the input stream to the child process and waits for the server to exit. If the server does not exit in a reasonable time, the client forcibly terminates it.

The second pattern is Streamable HTTP, used for remote servers. Here the server is a standalone service that exposes a single HTTP endpoint accepting POST, and the client sends every JSON-RPC request or notification as its own POST. The server answers with either one JSON object or an SSE stream. Claude Code reaches such a server with claude mcp add --transport http <name> <url>. The older sse transport and a ws WebSocket entry are also accepted in Claude Code configuration. In both patterns the client opens the connection and the server answers requests. The difference is whether the client starts the server process (stdio) or connects to one that is already running (HTTP).

A tool definition has a unique name, an optional display title, a description, an inputSchema, an optional outputSchema, and optional annotations and icons. Tool names should be 1–128 characters, are treated as case-sensitive, should use only ASCII letters, digits, _, -, and., and should be unique within a server. getUser, DATA_EXPORT_v2 and admin.tools.list are all valid names.

inputSchema defaults to JSON Schema 2020-12 when no $schema field is present. For a tool with no parameters, the recommended schema is { "type": "object", "additionalProperties": false }. Clients find tools with tools/list, which is paginated with a cursor, and run them with tools/call, passing name and arguments. A result carries a content array, which can hold text, image, audio, resource_link, or embedded resource items, plus an isError flag. If you declare an outputSchema, the server must also return structuredContent that conforms to it.

Some tools create state that later calls refer to by handle, for example a create_basket call that returns a basket_id. For these tools, state the retention policy in the creation tool's description. When a call uses an expired or unknown handle, return a tool execution error so the model can recover. On the host side, the spec expects a human in the loop: the UI should make exposed tools visible, show when a tool is invoked, and ask the user to confirm operations.

4. Resources: Context ที่ระบุตำแหน่งด้วย URI

Resource คือข้อมูลที่ระบุตำแหน่งด้วย uri โดยมี name และฟิลด์เสริม (optional) เช่น title, description, mimeType, size และ icons ฝั่ง Client สามารถเรียกดูรายการผ่าน resources/list และดึงข้อมูลผ่าน resources/read ซึ่งแต่ละ item ใน contents ที่ส่งกลับมาจะเป็น text หรือ base64 blob data สำหรับการเข้าถึงแบบรับ parameter จะใช้ resources/templates/list ซึ่งคืนค่ากลับมาเป็น URI templates เช่น file:///{path} นอกจากนี้ยังมี Annotations ที่ช่วยบอก Client ถึงวิธีใช้งาน ได้แก่ audience (user และ/หรือ assistant), priority (0.0 ถึง 1.0) และ lastModified

A resource is data identified by a uri. It also has a name and, optionally, a title, description, mimeType, size, and icons. Clients list resources with resources/list and fetch them with resources/read. Each item in the returned contents holds either text or base64 blob data. For parameterised access, resources/templates/list returns URI templates such as file:///{path}. Annotations tell the client how to use a resource: audience (user and/or assistant), priority from 0.0 to 1.0, and lastModified.

The resources capability has two optional flags. listChanged means the server will send a notification when the set of resources changes. subscribe means it supports update notifications for individual resources requested through subscriptions/listen. Security falls on the server. It must validate every resource URI, must encode binary data properly, should apply access controls to sensitive resources, and must sanitize file paths when serving file:// resources. If a resource does not exist, the server returns error -32602 with the URI in data.

A client calls prompts/get for code_review but leaves out the required code argument. Which error should the server return?

คำแปลโจทย์:
  • ▸
    ไคลเอ็นต์เรียกใช้ prompts/get
  • ▸
    สําหรับ code_review แต่ละเว้นอาร์กิวเมนต์โค้ดที่จําเป็น ข้อผิดพลาดใดที่เซิร์ฟเวอร์ควรส่งคืน
คำตอบที่ถูกต้อง: ตัวเลือก C
💡 Official Explanation (คำอธิบายเฉลย):

Missing required arguments and invalid prompt names both map to -32602. Code -32603 is reserved for internal server errors.

คำแปลไทย:
อาร์กิวเมนต์ที่ขาดหายไปและชื่อ Prompt ที่ไม่ถูกต้องจะถูกแมปไปยัง -32602 รหัส -32603 ถูกสงวนไว้สําหรับข้อผิดพลาดของเซิร์ฟเวอร์ภายใน
“Missing required arguments: -32602 (Invalid params)”
คำแปล: อาร์กิวเมนต์ที่จําเป็นขาดหายไป: -32602 (พารามิเตอร์ไม่ถูกต้อง)

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A prompt is a named template with optional arguments, each of which has a name, a description, and a required flag. A client lists prompts with prompts/list and fills one in with prompts/get. The server returns a list of messages. Each message has a role of user or assistant and content that can be text, image, audio, a resource link, or an embedded resource.

Servers should validate prompt arguments before processing them. An unknown prompt name or a missing required argument returns -32602 (Invalid params), and internal failures return -32603. The table below puts the three primitives side by side.

MCP Server Primitives — MCP Server คือโปรแกรมขนาดเล็กที่ออกแบบมาเฉพาะทางเพื่อส่งมอบ 3 ขีดความสามารถหลักแก่ Host Application ได้แก่ Tools ที่โมเดลเรียกใช้ได้, Resources สำหรับป้อน Context และ Prompts ที่ทำหน้าที่เป็น Reusable Message Templates โดยที่ Host ยังคงเป็นผู้ควบคุมทิศทางการสนทนาทั้งหมด และ Server ทำหน้าที่เพียงตอบกลับตามคำขอที่ได้รับเท่านั้น

5 หัวข้อ

#1 1. Host, client, and server

อ่านเนื้อหา ↗
  • •
    Host คือแอปพลิเคชันหลักที่ผู้ใช้ทำงานด้วย (เช่น Claude Code หรือ Custom Agent ของคุณ) ทำหน้าที่สร้างและจัดการ Client instances, บังคับใช้ Security Policies/Consent, จัดการสิทธิ์ (Authorization) และเชื่อมโยงการทำงานร่วมกับ LLM 2) Client จะรันอยู่ภายใน Host โดย 1 Client instance จะเชื่อมต่อกับ 1 Server เสมอ มีหน้าที่แนบ Protocol Version และ Capabilities ไปกับทุก Request, จัดการ Route ข้อความแบบ 2 ทิศทาง และแยกแต่ละ Server ไม่ให้ยุ่งเกี่ยวกัน (Isolation) 3) Server คือตัวที่ Provide เครื่องมือ (Tools), ข้อมูล (Resources) และ Templates (Prompts) ซึ่งสามารถรันเป็น Local Process หรือ Remote Service ก็ได้
  • •
    หลักการออกแบบ (Design Principles) ตามข้อกำหนดของ MCP ในการแบ่งบทบาทนี้คือ
  • •
    สถาปัตยกรรม MCP แบ่งออกเป็น 3 บทบาทหลักที่ต้องแยกให้ออก

#2 2. Declaring capabilities

อ่านเนื้อหา ↗
  • •
    Features ใน MCP ทำงานผ่านการตกลง (Negotiated) ร่วมกัน ไม่มีการทึกทักเอาเอง ฝั่ง Server ต้องประกาศ Capabilities เช่น Tools Support, Resource Subscriptions และ Prompt Templates ขณะที่ฝั่ง Client จะประกาศ Capabilities ของตนเอง เช่น Sampling และ Elicitation จากนั้นทั้งสองฝั่งต้องยึดตามสิ่งที่ประกาศไว้ตลอด Session ในทางปฏิบัติ ฟีเจอร์ใดๆ ที่ Server สร้าง Handler รองรับไว้ จะต้องถูกระบุใน Capabilities ด้วยเสมอ
  • •
    เมื่อตั้งค่า `listChanged: true` Server กำลังรับปากว่าจะส่ง Prompt `notifications/tools/list_changed` เมื่อชุด Tools มีการเปลี่ยนแปลง เพื่อให้ Client รับรู้และเรียก Fetch รายการ Tools ใหม่อีกครั้ง
  • •
    ตัวอย่างเช่น Claude Code เชื่อมต่อด้วยคำสั่ง `claude mcp add --transport stdio airtable -- npx -y airtable-mcp-server` (คำสั่งหลัง `--` คือ Process ที่ถูก Spawn) หรือใน SDK จะใช้ `StdioServerTransport`

#3 3. Tools: ฟังก์ชันที่โมเดลสามารถเรียกใช้ได้ (Model-Callable Functions)

อ่านเนื้อหา ↗
  • •
    โครงสร้างนิยาม Tool ประกอบด้วย: name ที่ไม่ซ้ำกัน, display title (optional), description, inputSchema, outputSchema (optional), ตลอดจน annotations และ icons (optional) โดย name ต้องมีความยาว 1
  • •
    หากไม่ได้ระบุฟิลด์ $schema ค่า inputSchema จะตั้งต้นเป็น JSON Schema 2020-12
  • •
    สำหรับ Tool ที่ไม่มี parameters แนะนำให้กำหนด schema เป็น { "type": "object", "additionalProperties": false } ฝั่ง Client จะค้นหา Tools ผ่าน tools/list (รองรับ pagination ด้วย cursor) และสั่งรันผ่าน tools/call โดยส่ง name และ arguments ผลลัพธ์ที่ได้จะส่งกลับผ่าน content array ซึ่งบรรจุข้อมูลได้ทั้ง text, image, audio, resource_link หรือ embedded resource พร้อมกับแฟล็ก isError

#4 4. Resources: Context ที่ระบุตำแหน่งด้วย URI

อ่านเนื้อหา ↗
  • •
    Capabilities ของ resources มี 2 แฟล็กทางเลือก ได้แก่ listChanged (Server จะส่ง notification เมื่อรายการ resources มีการเปลี่ยนแปลง) และ subscribe (รองรับ Prompt update สำหรับแต่ละ resource ที่ร้องขอผ่าน subscriptions/listen) ด้านความปลอดภัยเป็นหน้าที่ของ Server ที่ต้อง validate resource URI ทุกครั้ง, encode ข้อมูล binary อย่างถูกต้อง, บังคับใช้ Access Control กับ sensitive resources และ sanitize file paths เมื่อให้บริการ resources แบบ file://
  • •
    Resource คือข้อมูลที่ระบุตำแหน่งด้วย uri โดยมี name และฟิลด์เสริม (optional) เช่น title, description, mimeType, size และ icons ฝั่ง Client สามารถเรียกดูรายการผ่าน resources/list และดึงข้อมูลผ่าน resources/read ซึ่งแต่ละ item ใน contents ที่ส่งกลับมาจะเป็น text หรือ base64 blob data สำหรับการเข้าถึงแบบรับ parameter จะใช้ resources/templates/list ซึ่งคืนค่ากลับมาเป็น URI templates เช่น file:///{path}
  • •
    ยังมี Annotations ที่ช่วยบอก Client ถึงวิธีใช้งาน ได้แก่ audience (user และ/หรือ assistant), priority (0.0 ถึง 1.0) และ lastModified

#5 5. Prompts: Reusable Message Templates

อ่านเนื้อหา ↗
  • •
    Prompt คือ Template ข้อความที่มีการตั้งชื่อระบุไว้ พร้อมรองรับ Arguments เสริม (ซึ่งแต่ละตัวจะมี Name, Description และ Flag กำหนด Required) โดย Client จะค้นหารายการ Prompts ผ่าน `prompts/list` และเรียกใช้งานเพื่อกรอกข้อมูลผ่าน `prompts/get` จากนั้น Server จะส่งรายการ Messages กลับมา โดยแต่ละ Message จะกำหนด Role เป็น `user` หรือ `assistant` และมี Content เป็น Text, Image, Audio, Resource Link หรือ Embedded Resource
  • •
    Server ควร Validate Prompt Arguments ก่อนนำไปประมวลผลเสมอ หากไม่พบ Prompt Name หรือขาด Required Argument จะ Return Error Code `-32602` (Invalid params) และหากเกิด Internal Error จะ Return `-32603` ตารางด้านล่างนี้สรุปเปรียบเทียบความแตกต่างของ Server Primitives ทั้ง 3 รูปแบบ
  • •
    ตารางเปรียบเทียบสำคัญ: The three server primitives compared (ตารางเปรียบเทียบ Server Primitives ทั้งสามรูปแบบ)
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (2 ข้อควรระวัง)
Exam Traps Checklist
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
แค่ Implement Handler ก็เพียงพอให้ Client เรียกใช้ฟีเจอร์ได้แล้ว Capability Declaration เป็นแค่ Optional?
Implementing a handler is enough for clients to use a feature, so capability declaration is optional.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Features ของ Server ต้องประกาศใน Capabilities เสมอ และการเรียกใช้ Tool ต้องมีการประกาศ tools capability อย่างชัดเจน มิเช่นนั้น Client จะเรียกใช้งานไม่ได้ | stdio Server สามารถ Print Debug ออก stdout ได้ เพราะ Client จะ Ignore Text ที่ไม่รู้จักทิ้งไปเอง? (ทำไมถึงผิด): ไม่จริง: stdout ถูกใช้ส่ง MCP Protocol (JSON-RPC) โดยเฉพาะ ข้อความใดๆ ที่ไม่ใช่ Valid MCP Message จะทำให้ Stream เสียหายทันที การ Log ต้องส่งไปที่ stderr เท่านั้น
Server features must be advertised in the server's capabilities, and tool invocation specifically requires the tools capability to be declared. A stdio server can print debug output to stdout, since the client simply ignores text it does not recognise. (ทำไมถึงผิด): stdout carries the protocol, so anything that is not a valid MCP message breaks the stream. Logging belongs on stderr.
❌
สิ่งที่ข้อสอบมักหลอก (Common Trap / Misconception):
คำถามหลอก / สิ่งที่มักเข้าใจผิด?
A tool with no parameters can set inputSchema to null or leave it out.
✅
ความเป็นจริงทางเทคนิค (Anthropic Reality / Deep Insight):
ไม่จริง: Tool ที่ไม่มี parameters สามารถกำหนด inputSchema เป็น null หรือละเว้นไม่ต้องใส่ได้ เพราะ inputSchema ต้องเป็น valid JSON Schema object เสมอ โดยรูปแบบที่แนะนำคือ object type ที่มี additionalProperties: false
inputSchema must always be a valid JSON Schema object. For a tool with no parameters, the recommended form is an object type with additionalProperties: false.
