🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Branches, commits and pull requests with Claude Code" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Claude Code fits into version control the same way a developer does: plan the change, make it with tests, then commit and open a pull request. The order matters. Asking first which files need to change and what the flow is produces a plan you can correct before any code exists. The implementation prompt then points back to that plan and asks for tests, a test-suite run, and fixes for any failures. Only then does Claude commit with a descriptive message and open the PR.

Parallel work needs separate checkouts. Worktrees let you run separate CLI sessions in isolated git checkouts, so two sessions editing the same repository don't overwrite each other. The same isolation supports a writer and reviewer split. One session implements a rate limiter, and a second session with a fresh context reviews @src/middleware/rateLimiter.ts for edge cases and race conditions. Its findings then go back to the first session to fix.

📝 ข้อสอบจำลองทางการ (Official Exam Question)
ID: 55419

A team wants every file edit that an autonomous coding agent makes to be recorded in a version-control-friendly audit log before the change is written to disk, so that the change history stays traceable alongside normal git commits. Which Agent SDK mechanism should they use?

A Register a PreToolUse hook matched to the Edit and Write tools that appends the intended change to the audit log before the tool executes
B Rely on the git commit history alone, since every Edit tool call automatically creates a corresponding git commit with a descriptive message
C Set the permission_mode to acceptEdits, which by itself writes a structured audit trail of every file change to a log file
D Configure a subagent named auditor with no tools, expecting it to passively observe and log every Edit and Write call made by the main agent
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. A PreToolUse hook matched on Edit and Write runs custom logic, such as appending to an audit file, before the tool executes, which is exactly the interception point needed.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. The SDK does not automatically create git commits for tool calls; commits only happen if the agent or a hook explicitly runs git commands.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. acceptEdits only controls whether edit-type tool calls are auto-approved without a prompt; it does not produce any audit logging on its own.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. A subagent with no tools cannot observe tool calls made by a separate agent context; hooks, not passive subagents, are the interception mechanism.

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

In CI, Claude Code runs without a terminal. It is the same non-interactive mode described in [Headless mode (claude -p) and streaming output](lesson:3.1), packaged as the anthropics/claude-code-action GitHub Action. The quickest setup is to run /install-github-app from Claude Code. That installs the Claude GitHub App, adds the authentication secret and opens a pull request with the workflow file. The secret is either ANTHROPIC_API_KEY from the Console or CLAUDE_CODE_OAUTH_TOKEN, which authenticates with a Claude subscription. For an organization, install the app once at the org level and store the secret as an organization-level Actions secret.

Each line has a job. actions/checkout gives Claude a copy of the repository to work in. actions: read lets it read CI results on the PR. The if: stops runners from starting on comments that don't mention @claude. Whether a prompt input is set decides how the action behaves. Without one, it runs in interactive mode: it waits for the trigger phrase and replies as a comment on the issue or PR. With one, it runs in automation mode and starts without a mention. Results then go to the workflow run log unless the prompt tells Claude to post and it has a tool that can.

Two guards limit who can start a run. On issue and PR events, the triggering user needs write access to the repository. On every event, bot actors are rejected unless listed in allowed_bots, so one bot's comment can't keep triggering Claude in a loop. Scheduled runs are attributed to a repository user. If that user is a bot, it has to be listed as well.

คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. The Edit tool is documented for making precise edits to existing files, which matches a small, localized rename inside one function.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. Write creates or fully overwrites files; using it for a single variable rename risks discarding unrelated content and is not the tool built for precise edits.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. Bash runs terminal commands and scripts; it is not the documented precise-edit tool, even though a shell command could technically perform text replacement.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. Glob only finds files by pattern; it has no capability to modify file contents.

There are two ways to get Claude reviewing every PR. Managed Code Review is set up from Claude Code admin settings with the Claude GitHub App, and needs no workflow file. It runs a multi-agent analysis and marks each finding 🔴 Important (fix before merging), 🟡 Nit (minor, not blocking) or 🟣 Pre-existing (a bug the PR didn't introduce). Alternatively, you write your own workflow that runs the code-review plugin through the GitHub Action.

When a review runs drives both noise and cost. Each repository picks a trigger, and anyone with write access can also request a review from a top-level PR comment.

Reviews stay focused because you tell the reviewer what matters. CLAUDE.md is general project context, and Code Review flags newly introduced violations of it as nits. REVIEW.md holds review-only rules: what to flag, at what severity, and how findings are reported. A good REVIEW.md saves Important for findings that would break behavior or leak data, caps the number of nits, and excludes anything CI already enforces.

In a self-built review workflow, the step that most often goes missing is posting. Without --comment, the plugin writes its findings only to the workflow run log, and the PR shows nothing.

A small refactor or fix is safe when each step is checked against a test. For a bug, have Claude write a failing test that reproduces it, then fix the code until the test passes. For a change with a plan, a subagent can review the diff against PLAN.md. It checks that every requirement is implemented and that nothing outside the task's scope changed, and reports gaps rather than style preferences. Keep the scope tight: a refactor that wanders into unrelated files is harder to review than two separate PRs.

A large migration is a different problem. Too many files for one session, but each file is a similar, independent task. The pattern is to generate a task list, write a script that runs headless Claude once per file, test the script on a few files, and only then run it on all of them. Narrow --allowedTools to editing and git commit, so each file becomes its own commit and nothing else is allowed. Asking for OK or FAIL gives the loop a result it can check. When batches run at the same time, give each its own worktree.

The trial run exists to fix the instructions, not to make progress. In one Anthropic migration, translating three files first exposed two critical issues that would otherwise have spread across all 1,448 files. Those trial outputs were then thrown away. After that, each batch goes through the same loop: implement, review, fix.
