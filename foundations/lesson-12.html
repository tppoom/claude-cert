1. การจัดการ Branches, Commits และ Pull Requests ด้วย Claude Code

Claude Code ทำงานร่วมกับ Version Control เหมือน Developer ทั่วไป: วาง Plan, เขียนโค้ดพร้อม Tests, จากนั้นจึง Commit และเปิด Pull Request โดยลำดับขั้นตอนมีความสำคัญมาก การเริ่มจากการถามว่าต้องแก้ไฟล์ไหนบ้างและมี Flow อย่างไร จะช่วยให้ได้ Plan ที่เราสามารถรีวิวตรวจสอบก่อนลงมือเขียนโค้ดจริง จากนั้น Implementation Prompt จะอ้างอิงกลับไปยัง Plan นั้น สั่งให้เขียน Tests, รัน Test Suite และแก้ข้อผิดพลาดจนผ่าน เมื่อทุกอย่างเรียบร้อย Claude จึงจะ Commit พร้อมเขียน Commit Message ที่ชัดเจน แล้วเปิด PR ให้ทันที

การทำงานแบบขนาน (Parallel Work) จำเป็นต้องแยก Checkout ออกจากกัน Git Worktrees ช่วยให้คุณรัน CLI Sessions แยกกันบน Git Checkout ที่แยกเป็นอิสระ เพื่อป้องกันไม่ให้ 2 Sessions ที่แก้ Repo เดียวกันเขียนทับกันเอง การแยกสภาพแวดล้อมแบบนี้ยังเหมาะกับรูปแบบ Writer และ Reviewer อีกด้วย เช่น ให้ Session แรกเขียนโค้ด Rate Limiter แล้วให้ Session ที่สองซึ่งมี Context ที่สดใหม่ (Fresh Context) ทำการ Review ไฟล์ @src/middleware/rateLimiter.ts เพื่อหา Edge Cases และ Race Conditions จากนั้นจึงส่ง Feedback กลับไปให้ Session แรกแก้ไข

Claude Code fits into version control the same way a developer does: plan the change, make it with tests, then commit and open a pull request. The order matters. Asking first which files need to change and what the flow is produces a plan you can correct before any code exists. The implementation prompt then points back to that plan and asks for tests, a test-suite run, and fixes for any failures. Only then does Claude commit with a descriptive message and open the PR.

Parallel work needs separate checkouts. Worktrees let you run separate CLI sessions in isolated git checkouts, so two sessions editing the same repository don't overwrite each other. The same isolation supports a writer and reviewer split. One session implements a rate limiter, and a second session with a fresh context reviews @src/middleware/rateLimiter.ts for edge cases and race conditions. Its findings then go back to the first session to fix.

2. การรัน Claude Code บน GitHub Actions

บน CI นั้น Claude Code จะทำงานแบบ Non-interactive (ไม่มี Terminal) เหมือนกับ Headless Mode (claude -p) ซึ่งถูก Packaged มาเป็น GitHub Action ภายใต้ anthropics/claude-code-action วิธี Setup ที่เร็วที่สุดคือสั่งรัน /install-github-app ผ่าน Claude Code คำสั่งนี้จะช่วยติดตั้ง Claude GitHub App, ใส่ Authentication Secret และเปิด Pull Request พร้อมไฟล์ Workflow ให้โดยอัตโนมัติ สำหรับ Secret สามารถเลือกใช้ ANTHROPIC_API_KEY จาก Console หรือ CLAUDE_CODE_OAUTH_TOKEN จาก Claude Subscription ก็ได้ หากใช้ในระดับองค์กร แนะนำให้ติดตั้ง App ในระดับ Organization และเก็บ Secret ไว้ที่ระดับ Organization-level Actions Secret

A workflow that responds to @claude mentions in comments yaml
เวิร์กโฟลว์ที่ตอบสนองต่อการกล่าวถึง @claude ในความคิดเห็น yaml
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}

แต่ละบรรทัดใน Workflow ล้วนมีหน้าที่ชัดเจน: actions/checkout ทำการ Clone โค้ดลง Runner, actions: read เปิดให้ Claude อ่านผล CI บน PR ได้, ส่วน if: จะช่วยป้องกันไม่ให้ Runner ทำงาน ถ้า Comment นั้นไม่ได้ Mention @claude พฤติกรรมของ Action จะขึ้นอยู่กับว่ามีการกำหนด Prompt Input หรือไม่ หากไม่กำหนด จะรันใน Interactive Mode คือรอ Trigger Phrase แล้วตอบกลับเป็น Comment บน Issue หรือ PR แต่หากมีการกำหนด Prompt จะรันใน Automation Mode ทันทีโดยไม่ต้องรอ Mention และผลลัพธ์จะถูกบันทึกไว้ใน Workflow Run Log เว้นแต่จะระบุใน Prompt ให้ Claude โพสต์ผลลัพธ์และมี Tool ที่รองรับ

มีระบบป้องกัน 2 ชั้นเพื่อจำกัดสิทธิ์การรัน: สำหรับ Event บน Issue และ PR ผู้ใช้ที่เป็นคน Trigger จะต้องมีสิทธิ์ Write Access ต่อ Repository และสำหรับทุกๆ Event ระบบจะปฏิเสธ Bot Actors เสมอ ยกเว้นจะมีชื่ออยู่ใน allowed_bots เพื่อป้องกันไม่ให้ Bot ตอบโต้กันเองจนเกิด Trigger Loop ส่วน Scheduled Runs จะอ้างอิงสิทธิ์ตาม User ของ Repository ซึ่งหาก User นั้นเป็น Bot ก็ต้องถูกใส่ชื่อไว้ใน allowed_bots ด้วยเช่นกัน

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
Another bot, such as a dependency updater, can trigger the Claude action just by mentioning @claude. (ทำไมถึงผิด): The action rejects bot actors on every event unless they are listed in allowed_bots, which prevents trigger loops.

Bot ตัวอื่น (เช่น ตัวอัปเดต Dependency) สามารถ Trigger ให้ Claude Action ทำงานได้เพียงแค่ Mention @claude? (ทำไมถึงผิด): ไม่จริง: Action จะปฏิเสธ Bot Actors ในทุก Event เสมอ เว้นแต่ Bot นั้นจะถูกเพิ่มชื่อไว้ใน allowed_bots เพื่อตัดปัญหา Trigger Loops

In CI, Claude Code runs without a terminal. It is the same non-interactive mode described in [Headless mode (claude -p) and streaming output](lesson:3.1), packaged as the anthropics/claude-code-action GitHub Action. The quickest setup is to run /install-github-app from Claude Code. That installs the Claude GitHub App, adds the authentication secret and opens a pull request with the workflow file. The secret is either ANTHROPIC_API_KEY from the Console or CLAUDE_CODE_OAUTH_TOKEN, which authenticates with a Claude subscription. For an organization, install the app once at the org level and store the secret as an organization-level Actions secret.

Each line has a job. actions/checkout gives Claude a copy of the repository to work in. actions: read lets it read CI results on the PR. The if: stops runners from starting on comments that don't mention @claude. Whether a prompt input is set decides how the action behaves. Without one, it runs in interactive mode: it waits for the trigger phrase and replies as a comment on the issue or PR. With one, it runs in automation mode and starts without a mention. Results then go to the workflow run log unless the prompt tells Claude to post and it has a tool that can.

Two guards limit who can start a run. On issue and PR events, the triggering user needs write access to the repository. On every event, bot actors are rejected unless listed in allowed_bots, so one bot's comment can't keep triggering Claude in a loop. Scheduled runs are attributed to a repository user. There are two ways to get Claude reviewing every PR. Managed Code Review is set up from Claude Code admin settings with the Claude GitHub App, and needs no workflow file. It runs a multi-agent analysis and marks each finding 🔴 Important (fix before merging), 🟡 Nit (minor, not blocking) or 🟣 Pre-existing (a bug the PR didn't introduce). Alternatively, you write your own workflow that runs the code-review plugin through the GitHub Action.

When a review runs drives both noise and cost. Each repository picks a trigger, and anyone with write access can also request a review from a top-level PR comment.

Reviews stay focused because you tell the reviewer what matters. CLAUDE.md is general project context, and Code Review flags newly introduced violations of it as nits. REVIEW.md holds review-only rules: what to flag, at what severity, and how findings are reported. A good REVIEW.md saves Important for findings that would break behavior or leak data, caps the number of nits, and excludes anything CI already enforces.

In a self-built review workflow, the step that most often goes missing is posting. Without --comment, the plugin writes its findings only to the workflow run log, and the PR shows nothing.

4. การทำ Refactoring ทีละ Step และการ Migrate โค้ดแบบ Batch

การ Refactor หรือแก้ไขจุดเล็กๆ จะปลอดภัยเมื่อทุกขั้นตอนถูกตรวจสอบด้วย Test เสมอ: กรณีแก้ Bug ให้ Claude เขียน Failing Test ขึ้นมา Reproduce ก่อน แล้วจึงแก้โค้ดจนกว่า Test จะผ่าน ส่วนการปรับแก้ตามแผน ให้ใช้ Subagent ตรวจสอบ Diff เทียบกับ PLAN.md เพื่อเช็กว่า Implementation ครบถ้วนตาม Requirement และไม่มีการแก้ไขนอกเหนือ Scope ของงาน พร้อมทั้งรายงานเฉพาะ Gap มากกว่าเรื่อง Style Preference โดยต้องคุม Scope ให้กระชับ เนื่องจากการ Refactor ที่ลามไปแตะไฟล์ที่ไม่เกี่ยวข้องจะ Review ยากกว่าการแยกเป็น 2 PR

การ Migration ขนาดใหญ่ต้องใช้แนวทางที่ต่างออกไป เนื่องจากมีไฟล์มากเกินกว่าจะจัดการใน Session เดียว แต่ละไฟล์มีความซ้ำและเป็นงานอิสระต่อกัน แพทเทิร์นที่เหมาะสมคือ: สร้าง Task List ขึ้นมา, เขียน Script เพื่อรัน Headless Claude แยกไฟล์ละหนึ่งรอบ, ทดสอบ Script กับไฟล์จำนวนน้อยๆ ก่อน แล้วค่อยรันจริงกับไฟล์ทั้งหมด โดยจำกัด --allowedTools ให้ใช้ได้แค่การ Edit และ Git Commit เพื่อให้แต่ละไฟล์มี Commit ของตัวเองและป้องกันการทำคำสั่งอื่น การกำหนด Output ให้ตอบเป็น OK หรือ FAIL จะช่วยให้ Loop ตรวจสอบผลได้ง่าย และหากต้องรันหลาย Batch พร้อมกัน ให้แยกแต่ละ Batch ไปยัง Worktree ของตัวเอง

Fanning a migration out file by file, with restricted tools and a checkable result bash
การกระจายการโยกย้ายออกทีละไฟล์ด้วยเครื่องมือที่จํากัดและ Bash ผลลัพธ์ที่ตรวจสอบได้
for file in $(cat files.txt); do
  claude -p "Migrate $file from Python 2 to Python 3. Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)"
done

วัตถุประสงค์ของ Trial Run คือการปรับปรุง Prompt และ Instructions ไม่ใช่การมุ่งหน้าทำงานจริง ในโปรเจกต์ Migration หนึ่งของ Anthropic การทดสอบรัน 3 ไฟล์แรกช่วยตรวจพบ Critical Issue ได้ 2 จุด ซึ่งหากไม่ทดสอบก่อน ปัญหาจะลามไปทั่วทั้ง 1,448 ไฟล์ โดย Output จากการทดสอบนั้นจะถูกลบทิ้ง จากนั้นทุก Batch จึงเข้าสู่ Loop มาตรฐานเดียวกัน: Implement, Review, Fix

A small refactor or fix is safe when each step is checked against a test. For a bug, have Claude write a failing test that reproduces it, then fix the code until the test passes. For a change with a plan, a subagent can review the diff against PLAN.md. It checks that every requirement is implemented and that nothing outside the task's scope changed, and reports gaps rather than style preferences. Keep the scope tight: a refactor that wanders into unrelated files is harder to review than two separate PRs.

A large migration is a different problem. Too many files for one session, but each file is a similar, independent task. The pattern is to generate a task list, write a script that runs headless Claude once per file, test the script on a few files, and only then run it on all of them. Narrow --allowedTools to editing and git commit, so each file becomes its own commit and nothing else is allowed. Asking for OK or FAIL gives the loop a result it can check. When batches run at the same time, give each its own worktree.

The trial run exists to fix the instructions, not to make progress. In one Anthropic migration, translating three files first exposed two critical issues that would otherwise have spread across all 1,448 files. Those trial outputs were then thrown away. After that, each batch goes through the same loop: implement, review, fix.

ลงมือปฏิบัติจริง

ตั้งค่า automated Claude review ให้กับ repository ของคุณ แล้วทดลองดูผลการ review และ comment บน Pull Request จริง

  1. 1
    1. เรียกใช้ /install-github-app จาก Claude Code ในที่เก็บและตั้งค่าให้เสร็จสิ้น เหตุผล: ติดตั้งแอป Claude GitHub เพิ่มความลับการรับรองความถูกต้องและเตรียม PR เวิร์กโฟลว์ในขั้นตอนเดียว คุณควรเห็น: คําขอ pull ที่เพิ่มไฟล์เวิร์กโฟลว์ Claude และความลับ ANTHROPIC_API_KEY หรือ CLAUDE_CODE_OAUTH_TOKEN บนที่เก็บ
  2. 2
    2. เพิ่มเวิร์กโฟลว์การตรวจสอบเหตุการณ์ pull_request ที่เรียกใช้ปลั๊กอินการตรวจสอบโค้ดด้วย --comment และอนุญาตเครื่องมือแสดงความคิดเห็นแบบอินไลน์ เหตุผล: --comment เป็นสิ่งที่ทําให้ผลการค้นหาปรากฏบน PR แทนที่จะปรากฏเฉพาะในบันทึกการดําเนินการ คุณควรเห็น: เวิร์กโฟลว์ใหม่ที่แสดงรายการอยู่ภายใต้แท็บ Actions ของคลัง
  3. 3
    3. เปิด PR ขนาดเล็กที่แนะนําข้อบกพร่องที่เห็นได้ชัด เช่น ข้อผิดพลาดหนึ่งข้อในลูป ทําไม: ข้อบกพร่องที่จงใจแสดงให้เห็นว่าการตรวจสอบติดธงปัญหาจริงหรือไม่ คุณควรเห็น: ความคิดเห็นแบบอินไลน์บนบรรทัดที่มีข้อบกพร่อง หรือความคิดเห็นสรุปหนึ่งข้อหากคล็อดไม่พบอะไร
  4. 4
    4. ลบ --comment จากพรอมต์ กดอีกครั้งแล้วเปิดบันทึกการทำงานเวิร์กโฟลว์ สาเหตุ: แสดงว่าผลการวิจัยไปอยู่ที่ไหนเมื่อปิดการโพสต์ คุณควรเห็น: ไม่มีความคิดเห็น PR ใหม่ โดยที่ผลการวิจัยมองเห็นได้ในบันทึกการทำงาน
