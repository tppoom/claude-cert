1. แบ่งแยก ยืนยัน และดึงคําขอด้วย Claude Code

โค้ดคล็อดเข้ากันกับการควบคุมเวอร์ชันในลักษณะเดียวกับที่นักพัฒนาทํา: วางแผนการเปลี่ยนแปลง ทําด้วยการทดสอบ จากนั้นยืนยันและเปิด PR ลําดับมีความสําคัญ การถามว่าไฟล์ใดที่ต้องเปลี่ยนแปลงก่อนและโฟลว์คืออะไรจะสร้างแผนที่คุณสามารถแก้ไขได้ก่อนที่โค้ดใดๆ จะมีอยู่ จากนั้นพร้อมท์การนําไปใช้จะชี้กลับไปยังแผนนั้นและร้องขอการทดสอบ การเรียกใช้ชุดทดสอบ และการแก้ไขความล้มเหลวใดๆ จากนั้นคล็อดจึงยืนยันด้วยข้อความอธิบายและเปิด PR

การทํางานแบบขนานจําเป็นต้องมีการเช็คเอาต์แยกต่างหาก Worktree ช่วยให้คุณเรียกใช้เซสชัน CLI แยกต่างหากในเช็คเอาต์ Git ที่แยกกันได้ ดังนั้นสองเซสชันที่แก้ไขที่เก็บข้อมูลเดียวกันจะไม่เขียนทับกัน การแยกกันแบบเดียวกันรองรับการแยกผู้เขียนและผู้ตรวจสอบ เซสชันหนึ่งใช้ตัวจํากัดอัตรา และเซสชันที่สองที่มีบริบทใหม่จะตรวจสอบ @src/middleware/rateLimiter.ts สําหรับกรณีที่ใกล้เคียงและเงื่อนไขการแข่งขัน จากนั้นจะกลับไปยังเซสชันแรกเพื่อแก้ไข

✓ ตอบถูกแล้ว Check

A developer asks Claude Code to "implement OAuth and commit it" in one prompt, and the PR arrives with no tests and a design nobody agreed on. Which workflow change fixes both problems?

คำแปลโจทย์: นักพัฒนาขอให้ Claude Code "ใช้งาน OAuth และคอมมิต" ได้ในครั้งเดียว จากนั้น PR ก็มาถึงโดยไม่มีการทดสอบและการออกแบบที่ไม่มีใครเห็นพ้องต้องกัน การเปลี่ยนแปลงเวิร์กโฟลว์ใดช่วยแก้ไขปัญหาทั้งสองอย่างได้
คำตอบที่ถูกต้อง: ตัวเลือก A
💡 Official Explanation (คำอธิบายเฉลย):

Separating plan, implement-with-tests and commit gives a reviewable plan and a passing test suite before anything is committed.

คำแปลไทย: การแยกแผน การนําไปใช้กับการทดสอบ และการดําเนินการให้แผนที่สามารถตรวจสอบได้และชุดการทดสอบที่ผ่านก่อนที่จะมีการดําเนินการใดๆ
“implement the OAuth flow from your plan. write tests for the callback handler, run the test suite and fix any failures.”
คำแปล: ใช้โฟลว์ OAuth จากแผนของคุณ เขียนการทดสอบสําหรับตัวจัดการการโทรกลับ เรียกใช้ชุดทดสอบ และแก้ไขความล้มเหลวใดๆ

🔗 เอกสารอ้างอิงทางการจาก Anthropic
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Claude Code fits into version control the same way a developer does: plan the change, make it with tests, then commit and open a pull request. The order matters. Asking first which files need to change and what the flow is produces a plan you can correct before any code exists. The implementation prompt then points back to that plan and asks for tests, a test-suite run, and fixes for any failures. Only then does Claude commit with a descriptive message and open the PR.

Parallel work needs separate checkouts. Worktrees let you run separate CLI sessions in isolated git checkouts, so two sessions editing the same repository don't overwrite each other. The same isolation supports a writer and reviewer split. One session implements a rate limiter, and a second session with a fresh context reviews @src/middleware/rateLimiter.ts for edge cases and race conditions. Its findings then go back to the first session to fix.

2. การเรียกใช้โค้ด Claude ใน GitHub Actions

ใน CI Claude Code จะทํางานโดยไม่มีเทอร์มินัล เป็นโหมดที่ไม่มีการโต้ตอบแบบเดียวกันกับที่อธิบายไว้ใน 📖 โหมด Headless (claude -p) และเอาต์พุตการสตรีม (3.1) ซึ่งจัดแพ็คเกจเป็น GitHub Action anthropics/claude-code-action การตั้งค่าที่เร็วที่สุดคือการเรียกใช้ /install-github-app จาก Claude Code ซึ่งจะติดตั้ง Claude GitHub App เพิ่มความลับการรับรองความถูกต้อง และเปิด PR ที่มีไฟล์เวิร์กโฟลว์ ความลับนี้คือ ANTHROPIC_API_KEY จาก Console หรือ CLAUDE_CODE_AUTH_TOKEN ซึ่งจะรับรองความถูกต้องด้วยการสมัครใช้งาน Claude สําหรับองค์กร ให้ติดตั้งแอปหนึ่งครั้งในระดับองค์กร และจัดเก็บความลับเป็นความลับ Actions ระดับองค์กร

A workflow that responds to @claude mentions in comments yaml
เวิร์กโฟลว์ที่ตอบสนองต่อการกล่าวถึง @claude ในความคิดเห็น yaml
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}

แต่ละบรรทัดมีงาน actions/checkout มอบสําเนาของคลังให้ Claude เพื่อทํางานใน actions: read ช่วยให้สามารถอ่านผลลัพธ์ CI บน PR ได้ if: หยุดผู้เรียกใช้ไม่ให้เริ่มความคิดเห็นที่ไม่ได้กล่าวถึง @claude การตั้งอินพุตพร้อมท์จะกําหนดว่าการทํางานจะทํางานอย่างไร หากไม่มี จะทํางานในโหมดโต้ตอบ: รอวลีทริกเกอร์และตอบกลับเป็นความคิดเห็นเกี่ยวกับปัญหาหรือ PR เมื่อมีพร้อมท์หนึ่ง จะทํางานในโหมดอัตโนมัติและเริ่มต้นโดยไม่มีการกล่าวถึง จากนั้นผลลัพธ์จะไปที่บันทึกการเรียกใช้เวิร์กโฟลว์ เว้นแต่พร้อมท์จะบอก Claude ให้โพสต์และมันมีเครื่องมือที่สามารถทําได้

การป้องกันสองตัวจํากัดว่าใครสามารถเริ่มการเรียกใช้ได้ สําหรับเหตุการณ์ปัญหาและ PR ผู้ใช้ที่ทริกเกอร์ต้องมีการเข้าถึงการเขียนไปยังที่เก็บ สําหรับทุกเหตุการณ์ ตัวแสดงบอตจะถูกปฏิเสธเว้นแต่จะอยู่ใน allowed_bots ดังนั้นความคิดเห็นของบอตหนึ่งตัวจะไม่สามารถทริกเกอร์ Claude ต่อไปในลูปได้ การเรียกใช้ที่กําหนดเวลาไว้จะถูกกําหนดให้กับผู้ใช้ที่เก็บ ถ้าผู้ใช้คนนั้นเป็นบอต ก็ต้องอยู่ในรายการด้วย

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)

Exam Trap: Another bot, such as a dependency updater, can trigger the Claude action just by mentioning @claude. (ทำไมถึงผิด): The action rejects bot actors on every event unless they are listed in allowed_bots, which prevents trigger loops.

คำอธิบายเจาะลึก: Exam Trap: บอตอื่น เช่น การอัปเดตการขึ้นต่อกัน สามารถทริกเกอร์การกระทําของ Claude ได้เพียงแค่พูดถึง @claude (ทําไมถึงผิดพลาด): การกระทําปฏิเสธแอคเตอร์บอตในทุกเหตุการณ์เว้นแต่จะอยู่ใน allowed_bots ซึ่งป้องกันลูปทริกเกอร์

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

In CI, Claude Code runs without a terminal. It is the same non-interactive mode described in [Headless mode (claude -p) and streaming output](lesson:3.1), packaged as the anthropics/claude-code-action GitHub Action. The quickest setup is to run /install-github-app from Claude Code. That installs the Claude GitHub App, adds the authentication secret and opens a pull request with the workflow file. The secret is either ANTHROPIC_API_KEY from the Console or CLAUDE_CODE_OAUTH_TOKEN, which authenticates with a Claude subscription. For an organization, install the app once at the org level and store the secret as an organization-level Actions secret.

Each line has a job. actions/checkout gives Claude a copy of the repository to work in. actions: read lets it read CI results on the PR. The if: stops runners from starting on comments that don't mention @claude. Whether a prompt input is set decides how the action behaves. Without one, it runs in interactive mode: it waits for the trigger phrase and replies as a comment on the issue or PR. With one, it runs in automation mode and starts without a mention. Results then go to the workflow run log unless the prompt tells Claude to post and it has a tool that can.

Two guards limit who can start a run. On issue and PR events, the triggering user needs write access to the repository. On every event, bot actors are rejected unless listed in allowed_bots, so one bot's comment can't keep triggering Claude in a loop. Scheduled runs are attributed to a repository user. If that user is a bot, it has to be listed as well.

คำแปล: ไม่ถูกต้อง. Bash รันคำสั่งเทอร์มินัลและสคริปต์ ไม่ใช่เครื่องมือแก้ไขที่แม่นยำที่ได้รับการบันทึกไว้ แม้ว่าในทางเทคนิคแล้วคำสั่งเชลล์จะสามารถทำการแทนที่ข้อความได้ก็ตาม
ตัวเลือก D: ตัวเลือกที่ไม่ถูกต้อง

Incorrect. Glob only finds files by pattern; it has no capability to modify file contents.

คำแปล: ไม่ถูกต้อง. Glob ค้นหาไฟล์ตามรูปแบบเท่านั้น ไม่มีความสามารถในการแก้ไขเนื้อหาไฟล์
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

There are two ways to get Claude reviewing every PR. Managed Code Review is set up from Claude Code admin settings with the Claude GitHub App, and needs no workflow file. It runs a multi-agent analysis and marks each finding 🔴 Important (fix before merging), 🟡 Nit (minor, not blocking) or 🟣 Pre-existing (a bug the PR didn't introduce). Alternatively, you write your own workflow that runs the code-review plugin through the GitHub Action.

When a review runs drives both noise and cost. Each repository picks a trigger, and anyone with write access can also request a review from a top-level PR comment.

Reviews stay focused because you tell the reviewer what matters. CLAUDE.md is general project context, and Code Review flags newly introduced violations of it as nits. REVIEW.md holds review-only rules: what to flag, at what severity, and how findings are reported. A good REVIEW.md saves Important for findings that would break behavior or leak data, caps the number of nits, and excludes anything CI already enforces.

In a self-built review workflow, the step that most often goes missing is posting. Without --comment, the plugin writes its findings only to the workflow run log, and the PR shows nothing.

4. การปรับโครงสร้างใหม่ในขั้นตอนเล็กๆ และการย้ายข้อมูลเป็นชุด

การรีแฟคเตอร์หรือการแก้ไขเล็กๆ น้อยๆ จะปลอดภัยเมื่อมีการตรวจสอบ

แต่ละขั้นตอนกับการทดสอบ สำหรับข้อบกพร่อง ให้ Claude เขียนการทดสอบที่ล้มเหลวและทำซ้ำ จากนั้นแก้ไขโค้ดจนกว่าการทดสอบจะผ่าน สำหรับการเปลี่ยนแปลงแผน เอเจนต์ย่อยสามารถตรวจสอบความแตกต่างกับ PLAN.md โดยจะตรวจสอบว่าทุกข้อกำหนดได้รับการปฏิบัติแล้ว และไม่มีอะไรเปลี่ยนแปลงนอกขอบเขตของงาน และรายงานช่องว่างมากกว่าการตั้งค่าสไตล์ รักษาขอบเขตให้เข้มงวด: การรีแฟคเตอร์ที่เข้าไปในไฟล์ที่ไม่เกี่ยวข้องนั้นตรวจสอบได้ยากกว่า PR ที่แยกกันสองตัว

การโยกย้ายขนาดใหญ่เป็นปัญหาที่แตกต่าง ไฟล์มากเกินไปสําหรับเซสชันเดียว แต่แต่ละไฟล์เป็นงานที่คล้ายคลึงกันและเป็นอิสระ รูปแบบคือการสร้างรายการงาน เขียนสคริปต์ที่เรียกใช้ Claude แบบไม่มีส่วนหัวหนึ่งครั้งต่อไฟล์ ทดสอบสคริปต์กับไฟล์ไม่กี่ไฟล์ แล้วจึงเรียกใช้กับไฟล์ทั้งหมดเท่านั้น Narrow --allowedTools เพื่อแก้ไขและ git commit เพื่อให้แต่ละไฟล์กลายเป็น commit ของตัวเองและไม่อนุญาตให้ทําสิ่งอื่นใด การขอ OK หรือ FAIL ให้ลูปผลลัพธ์ที่สามารถตรวจสอบได้ เมื่อเรียกใช้ชุดงานพร้อมกัน ให้แต่ละชุดงานมีเวิร์กทรีของตัวเอง

Fanning a migration out file by file, with restricted tools and a checkable result bash
การกระจายการโยกย้ายออกทีละไฟล์ด้วยเครื่องมือที่จํากัดและ Bash ผลลัพธ์ที่ตรวจสอบได้
for file in $(cat files.txt); do
  claude -p "Migrate $file from Python 2 to Python 3. Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)"
done

การทดลองใช้มีอยู่เพื่อแก้ไขคำแนะนำไม่ใช่เพื่อสร้างความคืบหน้าในการย้ายถิ่นแบบแอนโทรปิกหนึ่งการแปลสามไฟล์เผยให้เห็นปัญหาที่สำคัญสองประการเป็นครั้งแรกซึ่งอาจแพร่กระจายไปทั่วทั้ง 1,448 ไฟล์ผลการทดลองเหล่านั้นก็ถูกโยนทิ้งไปหลังจากนั้นแต่ละชุดจะผ่านลูปเดียวกัน: ดำเนินการตรวจสอบแก้ไข

🔢 แบบฝึกหัดเรียงลำดับขั้นตอน (Step Sequencing)
✓ ตอบถูกแล้ว Order (4 ขั้นตอน)

Put the steps of a large file-by-file migration in order

คำแปลโจทย์: จัดลําดับขั้นตอนของการโยกย้ายไฟล์ขนาดใหญ่ทีละไฟล์
👉คำแนะนำ: คลิกเลือกขั้นตอนตามลำดับที่ถูกต้องตั้งแต่ขั้นตอนที่ 1 ถึง 4 เรียงแล้ว 0/4
คลิกจัดลำดับจนครบเพื่อตรวจสอบคำตอบ
✓ Correct Sequence 1 ➔ 4 (ลำดับขั้นตอนที่ถูกต้อง):
1
Generate a task list of files to migrate สร้างรายการงานของไฟล์ที่จะย้ายข้อมูล
2
Write a script that loops over the list calling claude -p เขียนสคริปต์ที่วนผ่านรายการโดยเรียกใช้ claude -p
3
Test the script on a few files ทดสอบสคริปต์กับไฟล์ไม่กี่ไฟล์
4
Run it on all of them เรียกใช้กับพวกเขาทั้งหมด
💡 Reasoning (เหตุผลเบื้องหลังลำดับขั้น):

Trying a few files first catches rule errors before they spread to every file in the migration.

คำแปลไทย: การลองใช้ไฟล์บางไฟล์ก่อนจะตรวจจับข้อผิดพลาดของกฎก่อนที่จะแพร่กระจายไปยังทุกไฟล์ในการย้ายข้อมูล
“Test on a few files, then run on all of them”
คำแปล: ทดสอบกับไฟล์ไม่กี่ไฟล์ แล้วเรียกใช้ทั้งหมด

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

A small refactor or fix is safe when each step is checked against a test. For a bug, have Claude write a failing test that reproduces it, then fix the code until the test passes. For a change with a plan, a subagent can review the diff against PLAN.md. It checks that every requirement is implemented and that nothing outside the task's scope changed, and reports gaps rather than style preferences. Keep the scope tight: a refactor that wanders into unrelated files is harder to review than two separate PRs.

A large migration is a different problem. Too many files for one session, but each file is a similar, independent task. The pattern is to generate a task list, write a script that runs headless Claude once per file, test the script on a few files, and only then run it on all of them. Narrow --allowedTools to editing and git commit, so each file becomes its own commit and nothing else is allowed. Asking for OK or FAIL gives the loop a result it can check. When batches run at the same time, give each its own worktree.

The trial run exists to fix the instructions, not to make progress. In one Anthropic migration, translating three files first exposed two critical issues that would otherwise have spread across all 1,448 files. Those trial outputs were then thrown away. After that, each batch goes through the same loop: implement, review, fix.

  1. 1
    1. เรียกใช้ /install-github-app จาก Claude Code ในที่เก็บและตั้งค่าให้เสร็จสิ้น เหตุผล: ติดตั้งแอป Claude GitHub เพิ่มความลับการรับรองความถูกต้องและเตรียม PR เวิร์กโฟลว์ในขั้นตอนเดียว คุณควรเห็น: คําขอ pull ที่เพิ่มไฟล์เวิร์กโฟลว์ Claude และความลับ ANTHROPIC_API_KEY หรือ CLAUDE_CODE_OAUTH_TOKEN บนที่เก็บ
  2. 2
    2. เพิ่มเวิร์กโฟลว์การตรวจสอบเหตุการณ์ pull_request ที่เรียกใช้ปลั๊กอินการตรวจสอบโค้ดด้วย --comment และอนุญาตเครื่องมือแสดงความคิดเห็นแบบอินไลน์ เหตุผล: --comment เป็นสิ่งที่ทําให้ผลการค้นหาปรากฏบน PR แทนที่จะปรากฏเฉพาะในบันทึกการดําเนินการ คุณควรเห็น: เวิร์กโฟลว์ใหม่ที่แสดงรายการอยู่ภายใต้แท็บ Actions ของคลัง
  3. 3
    3. เปิด PR ขนาดเล็กที่แนะนําข้อบกพร่องที่เห็นได้ชัด เช่น ข้อผิดพลาดหนึ่งข้อในลูป ทําไม: ข้อบกพร่องที่จงใจแสดงให้เห็นว่าการตรวจสอบติดธงปัญหาจริงหรือไม่ คุณควรเห็น: ความคิดเห็นแบบอินไลน์บนบรรทัดที่มีข้อบกพร่อง หรือความคิดเห็นสรุปหนึ่งข้อหากคล็อดไม่พบอะไร
  4. 4
    4. ลบ --comment จากพรอมต์ กดอีกครั้งแล้วเปิดบันทึกการทำงานเวิร์กโฟลว์ สาเหตุ: แสดงว่าผลการวิจัยไปอยู่ที่ไหนเมื่อปิดการโพสต์ คุณควรเห็น: ไม่มีความคิดเห็น PR ใหม่ โดยที่ผลการวิจัยมองเห็นได้ในบันทึกการทำงาน
