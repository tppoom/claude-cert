1. การแทนที่คีย์คงที่ด้วยข้อมูลประจําตัวแบบรวมศูนย์

เวิร์กโหลดการผลิตบน AWS, Google Cloud, Azure, Kubernetes หรือ CI มีข้อมูลประจําตัวที่ออกโดยแพลตฟอร์มอยู่แล้ว Workload Identity Federation (WIF) ช่วยให้พวกเขาสามารถใช้ข้อมูลประจําตัวนั้นกับ Claude API ได้ เวิร์กโหลดนําเสนอ JWT OIDC ที่ลงชื่อแล้วจากผู้ให้บริการข้อมูลประจําตัว และ Anthropic จะส่งคืนโทเค็นการเข้าถึงระยะสั้นที่ผูกกับบัญชีบริการ ไม่มีใครสร้าง แจกจ่าย หรือหมุนเวียนสตริง sk-ant-api... ดังนั้นจึงไม่มีข้อมูลระยะยาวที่จะรั่วไหล โทเค็นแบบรวมศูนย์ให้สิทธิ์การเข้าถึงตําแหน่งข้อมูล Claude API เหมือนกับคีย์ API สิ่งที่เปลี่ยนแปลงคือระยะเวลาที่ข้อมูลประจําตัวที่ถูกขโมยยังคงมีประโยชน์: นาที ไม่ใช่ตลอดไป

ทรัพยากร Console สามรายการสร้างความไว้วางใจ อ่านร่วมกันแล้ว ระบุว่าโทเค็นที่ลงชื่อโดยผู้ออก X พร้อมคําอ้างอิงที่ดูเหมือน Y สามารถทําหน้าที่เป็นบัญชีบริการ Z ได้:

  • •
    บัญชีบริการ (svac_...) เป็นข้อมูลประจําตัวที่ไม่ใช่มนุษย์ที่ไม่มีอีเมล รหัสผ่าน หรือการเข้าสู่ระบบคอนโซล เป็นสมาชิกโดยนัยของพื้นที่ทํางานเริ่มต้น และคุณสามารถเพิ่มไปยังพื้นที่ทํางานอื่นใดที่ต้องการได้
  • •
    ตัวออกการเชื่อมโยง (fdis_...) จะลงทะเบียนผู้ให้บริการ OIDC ตามค่า iss ที่แน่นอนและแหล่งข้อมูล JWKS สําหรับการตรวจสอบลายเซ็น โดยปกติแล้ว Teams จะลงทะเบียนตัวออกหนึ่งตัวต่อสภาพแวดล้อม
  • •
    กฎการเชื่อมโยง (fdrl_...) จะเชื่อมโยงทั้งสองรายการ โดยจะตั้งค่าเงื่อนไขการจับคู่ (subject_prefix, กลุ่มเป้าหมาย, การอ้างอิงที่แน่นอน หรือนิพจน์ CEL ซึ่งต้องมีอย่างน้อยหนึ่งรายการ) บัญชีบริการเป้าหมาย ขอบเขต OAuth (พื้นที่ทํางานเริ่มต้น:developer) และ token_lifetime_seconds ระหว่าง 60 และ 86400

การอนุมัติการเข้าถึงเกิดขึ้นในกฎ คู่ที่ตรงกันทั้งหมดของกฎต้องผ่าน ลูกค้าตั้งชื่อกฎตาม ID ในแต่ละการแลกเปลี่ยน และ Anthropic จะไม่ค้นหากฎอื่นที่อาจตรงกัน การตั้งค่าทั้งหมดนี้ต้องใช้บทบาทผู้ดูแลระบบ เจ้าของ หรือเจ้าของหลัก การตรวจสอบก็ง่ายขึ้นเช่นกัน: คีย์เวิร์กสเปซเป็นข้อมูลประจําตัว ในขณะที่บัญชีบริการ *มี*ข้อมูลประจําตัว คุณจึงสามารถดูได้ว่าเวิร์กโหลดใดทําหน้าที่เป็นตัวตนใด

⚠️ จุดที่ข้อสอบชอบหลอก & จุดสังเกต (Exam Trap & Key Insight)
On the Exam:: Federation is only as strong as the identity provider that signs the JWT. A static cloud credential that can mint IdP tokens puts a long-lived secret back into the chain, one hop upstream. Pair WIF with your IdP's own controls, such as conditional access, MFA, IP allowlists and audit logging.

ในการสอบ: การเชื่อมโยงจะแข็งแกร่งเท่ากับผู้ให้บริการข้อมูลประจําตัวที่ลงชื่อใน JWT เท่านั้น ข้อมูลประจําตัวแบบสแตติกบนคลาวด์ที่สามารถสร้างโทเค็น IdP ได้จะนําความลับที่มีอายุการใช้งานยาวนานกลับเข้าไปในห่วงโซ่อีกครั้ง โดยการกระโดดขึ้นไปเพียงครั้งเดียว จับคู่ WIF กับการควบคุมของ IdP ของคุณ เช่น การเข้าถึงแบบมีเงื่อนไข MFA รายการอนุญาต IP และการบันทึกการตรวจสอบ

💡 Key Takeaway (หลักการสำคัญ):

The issuer decides whose signatures count, the rule decides which claims qualify and what scope they get, and the service account is the identity the resulting token acts as.

🔗 เอกสารอ้างอิงทางการจาก Anthropic
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Production workloads on AWS, Google Cloud, Azure, Kubernetes or CI already have an identity issued by their platform. Workload Identity Federation (WIF) lets them use that identity with the Claude API. The workload presents a signed OIDC JWT from its identity provider, and Anthropic returns a short-lived access token bound to a service account. Nobody mints, distributes or rotates an sk-ant-api... string, so there is nothing long-lived to leak. Federated tokens give the same access to Claude API endpoints as API keys. What changes is how long a stolen credential stays useful: minutes, not forever.

Three Console resources set up the trust. Read together, they say that tokens signed by issuer X, with claims that look like Y, may act as service account Z:

- A service account (svac_...) is a non-human identity with no email, password or Console login. It is implicitly a member of the default workspace, and you add it to any other workspace it needs. - A federation issuer (fdis_...) registers an OIDC provider by its exact iss value and a JWKS source for checking signatures. Teams usually register one issuer per environment. - A federation rule (fdrl_...) links the two. It sets the match conditions (subject_prefix, audience, exact claims or a CEL expression, of which at least one must be set), the target service account, an OAuth scope (default workspace:developer) and token_lifetime_seconds between 60 and 86400.

Access approval happens in the rule. All of the rule's matchers have to pass. The client names the rule by ID in each exchange, and Anthropic never searches for some other rule that might match. Setting all of this up requires the admin, owner or primary owner role. Auditing is also easier: a workspace key is a credential, while a service account *has* credentials, so you can see which workload acted as which identity.

2. วิธีที่เวิร์กโหลดแลกเปลี่ยน JWT เป็นโทเค็น Claude

เวิร์กโหลดมักจะได้รับ JWT จากแพลตฟอร์มโดยไม่ต้องร้องขอ: โทเค็นบัญชีบริการที่คาดการณ์โดย Kubernetes, เซิร์ฟเวอร์เมตาดาต้า Google Cloud, Azure IMDS หรือตําแหน่งข้อมูล GitHub Actions OIDC SDK โพสต์ JWT ไปยัง POST /v1/oauth/token โดยใช้ RFC 7523 jwt-bearer grant ร่วมกับ ID กฎ ID องค์กร และ ID บัญชีบริการ Anthropic ตรวจสอบลายเซ็นเทียบกับ JWKS ของผู้ออกและตรวจสอบการอ้างอิงเทียบกับกฎ หากทั้งสองผ่าน มันจะส่งคืนโทเค็น sk-ant-oat01-...bearer SDK ส่งโทเค็นนั้นในแต่ละคําขอและเรียกใช้การแลกเปลี่ยนอีกครั้งก่อนที่โทเค็นจะหมดอายุ

Constructing a client with explicit federation credentials

client = Anthropic(
    credentials=WorkloadIdentityCredentials(
        identity_token_provider=IdentityTokenFile(
            "/var/run/secrets/anthropic.com/token"
        ),
        federation_rule_id="fdrl_...",
        organization_id="00000000-0000-0000-0000-000000000000",
        service_account_id="svac_...",
        workspace_id="wrkspc_...",
    ),
)

ในการผลิต แบบฟอร์มที่แนะนําจะไม่ส่งอาร์กิวเมนต์ใดๆ เลย ส่งภาพคอนเทนเนอร์หนึ่งภาพและตั้งค่า ANTHROPIC_FEDERATION_RULE_ID, ANTHROPIC_ORGANIZATION_ID, ANTHROPIC_SERVICE_ACCOUNT_ID, ANTHROPIC_WORKSPACE_ID และ ANTHROPIC_IDENTITY_TOKEN_FILE ต่อสภาพแวดล้อม SDK จะอ่านไฟล์โทเค็นใหม่ในแต่ละการแลกเปลี่ยน ดังนั้นโทเค็นที่คาดการณ์ซึ่งหมุนบนดิสก์จึงเป็นปัจจุบันเสมอ พื้นที่ทํางานจะถูกเลือกเมื่อมีการแลกเปลี่ยนและต้องเป็นพื้นที่ที่บัญชีบริการเป็นเจ้าของ การย้ายไปยังพื้นที่ทํางานอื่นต้องใช้การแลกเปลี่ยนใหม่ ไม่ใช่ส่วนหัว

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The workload usually gets its JWT from the platform without asking for it: a Kubernetes projected service-account token, the Google Cloud metadata server, Azure IMDS or the GitHub Actions OIDC endpoint. The SDK posts that JWT to POST /v1/oauth/token using the RFC 7523 jwt-bearer grant, along with the rule ID, organization ID and service account ID. Anthropic checks the signature against the issuer's JWKS and checks the claims against the rule. If both pass, it returns an sk-ant-oat01-... bearer token. The SDK sends that token on each request and runs the exchange again before the token expires.

In production, the recommended form passes no arguments at all. Ship one container image and set ANTHROPIC_FEDERATION_RULE_ID, ANTHROPIC_ORGANIZATION_ID, ANTHROPIC_SERVICE_ACCOUNT_ID, ANTHROPIC_WORKSPACE_ID and ANTHROPIC_IDENTITY_TOKEN_FILE per environment. The SDK re-reads the token file on every exchange, so a projected token that rotates on disk is always current. The workspace is chosen at exchange time and must be one the service account belongs to. Moving to another workspace takes a new exchange, not a header.

A platform team configures a federation rule with `subject_prefix` set to `system:serviceaccount:prod:worker` and no `claims` or `condition` matchers. A JWT arrives from the cluster with `sub` equal to `system:serviceaccount:staging:worker-2`. Will this JWT be accepted by the rule, and why?

คำแปลโจทย์:
ทีมแพลตฟอร์มกำหนดค่ากฎสหพันธรัฐโดยตั้งค่า "subject_prefix" เป็น "system:serviceaccount:prod:worker" และไม่มีตัวจับคู่ "การอ้างสิทธิ์" หรือ "เงื่อนไข" JWT มาจากคลัสเตอร์โดยมี `sub` เท่ากับ `system:serviceaccount:staging:worker-2` JWT นี้จะได้รับการยอมรับตามกฎหรือไม่ และเพราะเหตุใด
คำตอบที่ถูกต้อง: ตัวเลือก A
💡 Option Analysis (คำอธิบายเฉลยรายตัวเลือก):
ตัวเลือก A: ✓ คำตอบที่ถูกต้อง

Correct. subject_prefix performs a literal prefix match on the sub claim; `system:serviceaccount:staging:worker-2` does not start with `system:serviceaccount:prod:worker`, so the match fails and the token exchange is denied.

คำแปล:
  • ▸
    ถูกต้อง. subject_prefix ทำการจับคู่คำนำหน้าตามตัวอักษรในการอ้างสิทธิ์ย่อย `system:serviceaccount:staging:worker-2` ไม่ได้ขึ้นต้นด้วย `system:serviceaccount:prod:worker`
  • ▸
    ดังนั้นการจับคู่จึงล้มเหลวและการแลกเปลี่ยนโทเค็นถูกปฏิเสธ
ตัวเลือก B: ตัวเลือกที่ไม่ถูกต้อง

Incorrect. subject_prefix is a literal string prefix check, not a set-membership or reordering check across segments.

คำแปล:
ไม่ถูกต้อง. subject_prefix คือการตรวจสอบคำนำหน้าสตริงตามตัวอักษร ไม่ใช่การตรวจสอบการเป็นสมาชิกชุดหรือการเรียงลำดับข้ามเซ็กเมนต์
ตัวเลือก C: ตัวเลือกที่ไม่ถูกต้อง

Incorrect. There is no automatic fallback to audience matching; unset matchers simply are not evaluated, and the configured subject_prefix still applies and fails.

คำแปล:
ไม่ถูกต้อง. การจับคู่ผู้ชมจะไม่เป็นทางเลือกโดยอัตโนมัติ ตัวจับคู่ที่ไม่ได้ตั้งค่าจะไม่ถูกประเมิน และ subject_prefix ที่กำหนดค่าไว้ยังคงใช้และล้มเหลว
ตัวเลือก D: ตัวเลือกที่ไม่ถูกต้อง

Incorrect. A rule is valid with just one of subject_prefix, claims, or condition set; at least one, not at least two, is required.

คำแปล:
ไม่ถูกต้อง. กฎใช้ได้กับ subject_prefix การอ้างสิทธิ์ หรือชุดเงื่อนไขเพียงรายการเดียว ต้องมีอย่างน้อยหนึ่งรายการ ไม่ใช่อย่างน้อยสองรายการ
คลิกเลือกคำตอบได้จนกว่าจะถูกต้อง · บันทึกผลใน LocalStorage
📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The SDK checks credential sources in a fixed order and uses the first one that yields a credential. It doesn't merge sources or warn about conflicts. Credentials left over from an earlier setup therefore quietly decide which identity your requests run as.

Two details trip up migrations. The federation path at step 4 turns on only when all four required variables are present. ANTHROPIC_WORKSPACE_ID is read too, but it doesn't count toward that check, so a missing service account ID makes the SDK skip federation silently. Profiles and environment variables also combine: once a profile is loaded, environment variables fill only the fields the profile leaves out and never override a field the profile sets.

    ทรัพยากร Console สามรายการสร้างความไว้วางใจ อ่านร่วมกันแล้ว ระบุว่าโทเค็นที่ลงชื่อโดยผู้ออก X พร้อมคําอ้างอิงที่ดูเหมือน Y สามารถทําหน้าที่เป็นบัญชีบริการ Z ได้:
  • •
    - บัญชีบริการ (svac_...) เป็นข้อมูลประจําตัวที่ไม่ใช่มนุษย์ที่ไม่มีอีเมล รหัสผ่าน หรือการเข้าสู่ระบบคอนโซล เป็นสมาชิกโดยนัยของพื้นที่ทํางานเริ่มต้น และคุณสามารถเพิ่มไปยังพื้นที่ทํางานอื่นใดที่ต้องการได้ - ตัวออกการเชื่อมโยง (fdis_...) จะลงทะเบียนผู้ให้บริการ OIDC ตามค่า iss ที่แน่นอนและแหล่งข้อมูล JWKS สําหรับการตรวจสอบลายเซ็น โดยปกติแล้ว Teams จะลงทะเบียนตัวออกหนึ่งตัวต่อสภาพแวดล้อม - กฎการเชื่อมโยง (fdrl_...) จะเชื่อมโยงทั้งสองรายการ โดยจะตั้งค่าเงื่อนไขการจับคู่ (subject_prefix, กลุ่มเป้าหมาย, การอ้างอิงที่แน่นอน หรือนิพจน์ CEL ซึ่งต้องมีอย่างน้อยหนึ่งรายการ) บัญชีบริการเป้าหมาย ขอบเขต OAuth (พื้นที่ทํางานเริ่มต้น:developer) และ token_lifetime_seconds ระหว่าง 60 และ 86400

#2 2. วิธีที่เวิร์กโหลดแลกเปลี่ยน JWT เป็นโทเค็น Claude

อ่านเนื้อหา ↗
  • •
    เวิร์กโหลดมักจะได้รับ JWT จากแพลตฟอร์มโดยไม่ต้องร้องขอ
  • •
    โทเค็นบัญชีบริการที่คาดการณ์โดย Kubernetes, เซิร์ฟเวอร์เมตาดาต้า Google Cloud, Azure IMDS หรือตําแหน่งข้อมูล GitHub Actions OIDC SDK โพสต์ JWT ไปยัง POST /v1/oauth/token โดยใช้ RFC 7523 jwt-bearer grant ร่วมกับ ID กฎ ID องค์กร และ ID บัญชีบริการ Anthropic ตรวจสอบลายเซ็นเทียบกับ JWKS ของผู้ออกและตรวจสอบการอ้างอิงเทียบกับกฎ หากทั้งสองผ่าน มันจะส่งคืนโทเค็น sk-ant-oat01-...bearer SDK ส่งโทเค็นนั้นในแต่ละคําขอและเรียกใช้การแลกเปลี่ยนอีกครั้งก่อนที่โทเค็นจะหมดอายุ
  • •
    ในการผลิต แบบฟอร์มที่แนะนําจะไม่ส่งอาร์กิวเมนต์ใดๆ เลย ส่งภาพคอนเทนเนอร์หนึ่งภาพและตั้งค่า ANTHROPIC_FEDERATION_RULE_ID, ANTHROPIC_ORGANIZATION_ID, ANTHROPIC_SERVICE_ACCOUNT_ID, ANTHROPIC_WORKSPACE_ID และ ANTHROPIC_IDENTITY_TOKEN_FILE ต่อสภาพแวดล้อม SDK จะอ่านไฟล์โทเค็นใหม่ในแต่ละการแลกเปลี่ยน

#3 3. ข้อมูลประจําตัวใดที่ SDK ใช้จริง

อ่านเนื้อหา ↗
  • •
    ID บัญชีบริการที่ขาดหายไปทําให้ SDK ข้ามการเชื่อมโยงแบบเงียบๆ โปรไฟล์และตัวแปรสภาพแวดล้อมยังรวมกันอีกด้วย: เมื่อโหลดโปรไฟล์แล้ว ตัวแปรสภาพแวดล้อมจะเติมเฉพาะช่องที่โปรไฟล์ไม่รวมไว้ และจะไม่เขียนทับช่องที่โปรไฟล์ตั้งค่าไว้
  • •
    รายละเอียดสองประการทําให้การย้ายข้อมูลล้มเหลว เส้นทางการเชื่อมโยงในขั้นตอนที่ 4 จะเปิดใช้งานเฉพาะเมื่อมีตัวแปรที่จําเป็นทั้งสี่ ตัวแปร ANTHROPIC_WORKSPACE_ID ก็ถูกอ่านเช่นกัน แต่จะไม่นับรวมในการตรวจสอบนั้น
  • •
    SDK จะตรวจสอบแหล่งข้อมูลประจําตัวตามลําดับที่กําหนดไว้ และใช้แหล่งข้อมูลแรกที่ให้ข้อมูลประจําตัว มันจะไม่ผสานแหล่งข้อมูลหรือแจ้งเตือนเกี่ยวกับความขัดแย้ง ข้อมูลประจําตัวที่เหลืออยู่จากการตั้งค่าก่อนหน้าจึงตัดสินใจอย่างเงียบๆ ว่าคําขอของคุณจะทํางานภายใต้ตัวตนใด
⚠️ รวมจุดที่ข้อสอบชอบหลอก & สิ่งที่มักเข้าใจผิด (2 ข้อควรระวัง)
