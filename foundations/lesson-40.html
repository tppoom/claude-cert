กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Replacing static keys with federated identity" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

Production workloads on AWS, Google Cloud, Azure, Kubernetes or CI already have an identity issued by their platform. Workload Identity Federation (WIF) lets them use that identity with the Claude API. The workload presents a signed OIDC JWT from its identity provider, and Anthropic returns a short-lived access token bound to a service account. Nobody mints, distributes or rotates an sk-ant-api... string, so there is nothing long-lived to leak. Federated tokens give the same access to Claude API endpoints as API keys. What changes is how long a stolen credential stays useful: minutes, not forever.

Three Console resources set up the trust. Read together, they say that tokens signed by issuer X, with claims that look like Y, may act as service account Z:

- A service account (svac_...) is a non-human identity with no email, password or Console login. It is implicitly a member of the default workspace, and you add it to any other workspace it needs. - A federation issuer (fdis_...) registers an OIDC provider by its exact iss value and a JWKS source for checking signatures. Teams usually register one issuer per environment. - A federation rule (fdrl_...) links the two. It sets the match conditions (subject_prefix, audience, exact claims or a CEL expression, of which at least one must be set), the target service account, an OAuth scope (default workspace:developer) and token_lifetime_seconds between 60 and 86400.

Access approval happens in the rule. All of the rule's matchers have to pass. The client names the rule by ID in each exchange, and Anthropic never searches for some other rule that might match. Setting all of this up requires the admin, owner or primary owner role. Auditing is also easier: a workspace key is a credential, while a service account *has* credentials, so you can see which workload acted as which identity.

The workload usually gets its JWT from the platform without asking for it: a Kubernetes projected service-account token, the Google Cloud metadata server, Azure IMDS or the GitHub Actions OIDC endpoint. The SDK posts that JWT to POST /v1/oauth/token using the RFC 7523 jwt-bearer grant, along with the rule ID, organization ID and service account ID. Anthropic checks the signature against the issuer's JWKS and checks the claims against the rule. If both pass, it returns an sk-ant-oat01-... bearer token. The SDK sends that token on each request and runs the exchange again before the token expires.

In production, the recommended form passes no arguments at all. Ship one container image and set ANTHROPIC_FEDERATION_RULE_ID, ANTHROPIC_ORGANIZATION_ID, ANTHROPIC_SERVICE_ACCOUNT_ID, ANTHROPIC_WORKSPACE_ID and ANTHROPIC_IDENTITY_TOKEN_FILE per environment. The SDK re-reads the token file on every exchange, so a projected token that rotates on disk is always current. The workspace is chosen at exchange time and must be one the service account belongs to. Moving to another workspace takes a new exchange, not a header.

A platform team configures a federation rule with `subject_prefix` set to `system:serviceaccount:prod:worker` and no `claims` or `condition` matchers. A JWT arrives from the cluster with `sub` equal to `system:serviceaccount:staging:worker-2`. Will this JWT be accepted by the rule, and why?

A No, because the subject does not start with `system:serviceaccount:prod:worker`; the `staging` namespace fails the prefix match even though the trailing segment is similar.
B Yes, because `subject_prefix` only checks that the subject contains the same set of colon-separated segments somewhere in the string, regardless of order.
C Yes, because omitting `claims` and `condition` causes the rule to fall back to matching on `audience` alone, which is satisfied by any workload in the same cluster.
D No, because a federation rule requires at least two of `subject_prefix`, `claims`, or `condition` to be set, so this rule is invalid and rejects every JWT.
คลิกดูเฉลยคำตอบพร้อมคำอธิบายแบบเจาะลึก (Reveal Answer & Detailed Analysis) ▼
คำตอบที่ถูกต้อง: ตัวเลือก A
ตัวเลือก A: ถูกต้อง

Correct. subject_prefix performs a literal prefix match on the sub claim; `system:serviceaccount:staging:worker-2` does not start with `system:serviceaccount:prod:worker`, so the match fails and the token exchange is denied.

ตัวเลือก B: ไม่ถูกต้อง

Incorrect. subject_prefix is a literal string prefix check, not a set-membership or reordering check across segments.

ตัวเลือก C: ไม่ถูกต้อง

Incorrect. There is no automatic fallback to audience matching; unset matchers simply are not evaluated, and the configured subject_prefix still applies and fails.

ตัวเลือก D: ไม่ถูกต้อง

Incorrect. A rule is valid with just one of subject_prefix, claims, or condition set; at least one, not at least two, is required.

🔍 อธิบายขยายความเชิงลึก & จุดสังเกตสำหรับข้อสอบ (In-Depth Technical Insights)

กลไกการทำงานเบื้องหลัง (Under the Hood): ในหัวข้อ "Which credential the SDK actually uses" หัวใจสำคัญตามแนวทางของ Anthropic คือการมองเห็นความแตกต่างระหว่าง Predefined Code Logic (Deterministic) กับ Model Autonomy (Stochastic) ระบบที่ควบคุมด้วยโค้ดจะให้ผลลัพธ์ที่คาดเดาได้ (Predictability) สูงกว่า ใช้โทเค็นน้อยกว่า และวัดผลได้ง่ายกว่าเสมอ

ผลกระทบต่อต้นทุนและประสิทธิภาพ (Cost & Token Trade-offs): การเพิ่มระดับความเป็นอิสระ (Autonomy) หรือการแยกงานเป็น Multi-Agent จะทำให้การใช้โทเค็นเพิ่มขึ้นประมาณ 3x ถึง 10x เนื่องจากต้องส่ง Context ซ้ำในแต่ละ Subagent และต้องใช้รอบข้อความ (Turns) เพิ่มขึ้นในการสรุปข้อมูลกลับสู่ Orchestrator

💡 จุดที่ข้อสอบเน้นย้ำ: หากโจทย์ระบุว่ากระบวนการทำงานมีขั้นตอนที่แน่นอนตายตัว (Fixed sequence) หรือประเภทงานแบ่งกลุ่มชัดเจน (Predictable paths) ให้เลือก Workflow (เช่น Chaining หรือ Routing) เสมอ อย่าเลือก Autonomous Agent เพียงเพราะต้องการความทันสมัย!

📄 ดูเนื้อหาและศัพท์ต้นฉบับภาษาอังกฤษ (Original English Reference) ▼

The SDK checks credential sources in a fixed order and uses the first one that yields a credential. It doesn't merge sources or warn about conflicts. Credentials left over from an earlier setup therefore quietly decide which identity your requests run as.

Two details trip up migrations. The federation path at step 4 turns on only when all four required variables are present. ANTHROPIC_WORKSPACE_ID is read too, but it doesn't count toward that check, so a missing service account ID makes the SDK skip federation silently. Profiles and environment variables also combine: once a profile is loaded, environment variables fill only the fields the profile leaves out and never override a field the profile sets.
